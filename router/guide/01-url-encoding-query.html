URL 分段编码与查询串 ​

从一个让人抓狂的场景说起 ​

想象你在写一个路由器。它最频繁的日常，就是把「路径段、路径参数、查询键值、哈希」这些零件拼成一条 URL，再从一条 URL 把它们拆回来。听起来平淡无奇，但这里藏着两个不显眼、却能把人逼疯的坑。

第一个坑：地址栏会自作主张。你拼出的 URL，交给浏览器后，地址栏会按它自己的脾气再编码、再解码一次。于是「我写出来的串」和「地址栏里看到的串」对不上，有时还会来回抖——每次导航 URL 都变一下，看着像 bug，其实是字符没编对地方。

第二个坑藏得更深：查询串里的「?key」（只有键、没有等号，表示一个开关型标志）和「压根不带这个键」是两种不同的 URL。可如果你只用普通字符串去存查询值，根本分不出这两种「没有」——字符串空值 '' 是空字符串，可 ?key 的值既不是空字符串、也不是不存在，它是「存在，但没有等号」。

这一章要解决的就是这两件事。一句话核心思想：别想着用一个万能编码函数走天下，而是按 URL 所属的段（路径 / 参数 / 查询键 / 查询值 / 哈希）分别决定「哪些字符要编、哪些要留」，并且贴着浏览器的真实行为走。

同一个字符，换个位置，命运就完全不同 ​

你可能觉得，编码嘛，JavaScript 不是有现成的 encodeURIComponent 吗，一把梭不就行了？

不行。关键原因在于：同一个字符，放在 URL 的不同段里，意义和待遇天差地别。 把 URL 想象成一封分了格的信——「收件人、邮编、正文」各占一格，你不能拿同一个橡皮章往所有格子上乱盖。

举几个真实例子：

字符放在路径段放在查询值段放在哈希段
#必须编码成 %23（否则它会被当成哈希起点，把后面全切走）必须编码（否则截断查询）不编码（哈希是最后一节，里面再出现 # 浏览器也不会再切）
&保留明文必须编码成 %26（否则被当成键值分隔符）保留明文
/保留明文（它本就是路径分隔符）保留明文保留明文
{ } ^编码成 %7B %7D %5E还原成明文 { } ^还原成明文 { } ^

最后一行尤其有意思：花括号和 ^ 在路径段是被编码的，可一旦挪到查询段或哈希段，反而要特意还原成明文。为什么？因为浏览器在这些段对它们就不编码——路由器要是编码了，就和地址栏对不上，又掉进第一个坑。

更麻烦的是，浏览器压根不严格遵守 URL 标准。标准（RFC 3986）列了一串「保留字符」要求编码，但实际浏览器的宽松编码连 !'()* 都不编；而且在哈希段，不同浏览器对 "<>{} 的处理还不一致（有的编、有的不编）。这意味着：如果你死守标准去编码，生成的 URL 反而和真实地址栏对不上。

所以正确的姿势不是「更严格」，而是「贴着浏览器走」——只留 ASCII 字母数字加 -._~ 这几个最安全的明文，其余看浏览器脸色决定编不编。

自底向上：先搭一个宽松基底，再按段修整 ​

承认了「不同段就是不一样」，接下来怎么做？分两步走，这是整章的核心心智模型。

原始文本
  │
  │ ① 判定它属于哪个段（path / param / queryKey / queryValue / hash）
  ▼
宽松基底 commonEncode：平台 encodeURI 跑一遍，再把浏览器
   实际会保留的 |  [  ]  三个符号还原成明文
  │
  │ ② 按段做「补编码 + 还原」修正
  ▼
最终编码串

第一步：宽松基底。 平台的 encodeURI 已经能把中文、空格、各种非 ASCII 字符处理掉，是个好起点。但 encodeURI 会顺手把 | [ ] 也编成 %7C %5B %5D——而浏览器实际在 URL 里是保留这三个明文的。所以基底干完活，得把它们还原回来。这就是「先全编、再把不该编的还原」的套路。

第二步：按段修整。 在基底之上，每个段再加自己的补丁。路径段要把会破坏路径语法的 # ? 补编码；路径参数段在路径基础上再补一个 /（下面专门讲为什么）；查询值段有一套关于加号和空格的特殊戏法；查询键段再补一个 =；哈希段则把花括号和 ^ 还原成明文。

下面这段几十行的演示，把这个二步法演透：

ts
// demo.ts —— 分段编码演示（可 node demo.ts / bun run demo.ts 跑）
// 演的是核心权衡①：按段细分字符集，而非一刀切

// 各段在「基底」之上需要追加的步骤（成对的 [正则, 替换值]）
const STEPS: Record<string, [RegExp, string][]> = {
  path: [
    [/#/g, '%23'], [/\?/g, '%3F'],          // 补编码会破坏路径语法的 # ?
  ],
  param: [
    [/#/g, '%23'], [/\?/g, '%3F'], [/\//g, '%2F'],  // 再补编码 / ，防穿越段边界
  ],
  queryValue: [
    [/\+/g, '%2B'],                          // ① 真实加号先占位成 %2B
    [/%20/g, '+'],                           // ② 再把空格编成 +
    [/#/g, '%23'], [/&/g, '%26'],            // 补编码会破坏查询语法的 # &
    [/%60/g, '`'], [/%7B/g, '{'], [/%7D/g, '}'], [/%5E/g, '^'], // 还原浏览器保留的符号
  ],
  queryKey: [
    [/\+/g, '%2B'], [/%20/g, '+'], [/#/g, '%23'], [/&/g, '%26'], [/=/g, '%3D'],
    [/%60/g, '`'], [/%7B/g, '{'], [/%7D/g, '}'], [/%5E/g, '^'], // 比 queryValue 多编一个 =
  ],
  hash: [
    [/%7B/g, '{'], [/%7D/g, '}'], [/%5E/g, '^'],   // 哈希段只还原，不补编码
  ],
}

// 第一步：宽松基底 —— 平台能力 + 还原浏览器实际保留的 | [ ]
function commonEncode(text: string | number | null | undefined): string {
  if (text == null) return ''                // null/undefined 统一变空串
  return encodeURI('' + text)
    .replace(/%7C/g, '|')
    .replace(/%5B/g, '[')
    .replace(/%5D/g, ']')
}

// 第二步：基底 + 按段补编码/还原
function segEncode(text: string | number | null | undefined, segment: string): string {
  let s = commonEncode(text)
  for (const [re, to] of STEPS[segment]) s = s.replace(re, to)
  return s
}

来看一个真实的执行轨迹。把 a b?c#d 当作路径段：

'a b?c#d'
  → encodeURI 得 'a%20b?c#d'   （空格→%20，但 ? # 没被编）
  → 还原 | [ ]，无变化
  → 路径段补编码 ? → %3F、# → %23
  → 'a%20b%3Fc%23d'

注意那个 / 的特殊处理：路径主体的 / 是分隔符，绝对不能编码（编码了路径就断成一段了）；可一旦这段文本是「路径参数的值」，就必须把 / 编成 %2F。想象参数值是用户名 a/b，如果不编 /，URL 里 /user/a/b 会被理解成三层路径，参数就穿越了段边界。所以 param 段单独存在，就是为这一刀。

关于加号，值得单独说一句。 查询值段那两步 +→%2B 再 %20→+ 顺序绝对不能反。为什么？因为空格在查询里要按老传统编成 +（这是和早期表单 application/x-www-form-urlencoded 兼容的历史包袱）。可如果文本里本来就有个真实的加号，它和「空格变成的加号」就撞脸了。解法是：先把真实加号藏起来（编成 %2B 占住位），再让空格变成 +。反过来解析时，先一律把 + 当空格还原，真加号因为有 %2B 的壳保护，不受影响。这套「先藏后换」的小把戏，是查询段独有的，路径和哈希段根本不管加号。

查询串里的两种「没有」 ​

再看第二个坑。这里要回答一个听着哲学、其实很实在的问题：查询串里什么叫「没有这个值」？

答案是两种不同的「没有」：

  • 标志型空值：?key，键后面没有等号。它表示「这个开关是打开的」。解析回来，它的值是 null。
  • 省略型空值：整个键压根不出现。它表示「这个开关根本不存在」。定义时用 undefined 表达。

举个例子，URL ?isNull&isEmpty=&other=other 解析出来是 { isNull: null, isEmpty: '', other: 'other' }。看清楚：isNull 是 null（无等号），isEmpty 是空字符串 ''（有等号但值为空），这俩完全不同。

把这两层区分从「靠人记」提升到「靠类型保证」，就是这一节的全部目的。下面这段迷你 stringify / parse 演示，演的是核心权衡④（两种空值的二分）：

ts
// 查询串演示 —— null = 标志型(?key)，undefined = 省略型(完全不要)

function stringifyQuery(query: Record<string, any>): string {
  let search = ''
  for (const key in query) {
    const value = query[key]
    const ek = segEncode(key, 'queryKey')
    if (value == null) {                     // 命中 null 或 undefined
      if (value !== undefined) {             // 只有 null 会把键写进去（无等号）
        search += (search ? '&' : '') + ek
      }
      continue                              // undefined：整个键都跳过
    }
    const vals = Array.isArray(value) ? value : [value]
    for (const v of vals) {
      if (v === undefined) continue          // 数组里的 undefined 也当作不存在
      search += (search ? '&' : '') + ek
      if (v != null) search += '=' + segEncode(v, 'queryValue')   // null 只输出键、不写 =
    }
  }
  return search                              // 注意：不前置 ?
}

function parseQuery(search: string): Record<string, any> {
  const query: Record<string, any> = {}
  if (search === '' || search === '?') return query
  const params = (search[0] === '?' ? search.slice(1) : search).split('&')
  for (const p of params) {
    const seg = p.replace(/\+/g, ' ')        // 先把 + 还原成空格
    const eq = seg.indexOf('=')
    const key = decodeURIComponent(eq < 0 ? seg : seg.slice(0, eq))
    const value = eq < 0 ? null : decodeURIComponent(seg.slice(eq + 1))  // 无等号 → null
    if (key in query) {                      // 同名键累积成数组
      const cur = query[key]
      query[key] = Array.isArray(cur) ? [...cur, value] : [cur, value]
    } else {
      query[key] = value
    }
  }
  return query
}

跑一遍完整往返：

ts
// 编码侧
segEncode('a b?c#d', 'path')                       // → 'a%20b%3Fc%23d'
segEncode('x+y z', 'queryValue')                   // → 'x%2By+z'  (真加号藏成%2B，空格变+)

// 序列化：flag 是标志型、gone 是省略型、q 的值里带 &
stringifyQuery({ flag: null, gone: undefined, q: 'a&b' })
// → 'flag&q=a%26b'   （flag 无等号、gone 整个消失、a&b 的 & 被补编码）

// 反向解析回来
parseQuery('flag&q=a%26b')
// → { flag: null, q: 'a&b' }   （语义和输入完全一致，往返无损）

最后补一句解码的兜底：解析时用的是 decodeURIComponent，万一碰到坏掉的百分号串（比如孤零零的 %），它不抛异常、而是悄悄退回原文。编码可以严格，但解码必须宽容——因为你永远不知道用户手敲了什么进地址栏。

这一章做了哪些选择，又各付了什么代价 ​

讲完原理，回头看这一整套设计到底换来了什么、又牺牲了什么。这些权衡比上面的演示更值得记住。

权衡一：按 URL 段细分保留字符集（而非一刀切编码所有保留字符）。 选择：为 path、param、query、hash 各自维护一套「该编什么、该留什么」的字符表。 换来：每段都贴合浏览器的实际行为，生成的 URL 既可读（该明文的地方明文），又不会被地址栏二次改写——彻底躲掉了开篇第一个坑。 代价：要维护一组分层函数和一长串「先编码、再还原」的替换链，替换顺序敏感、不直观（加号那两步顺序一反就全错）。

权衡二：对齐浏览器实际行为，而非死守严格的 URL 标准。 选择：明知标准要求编码 !'()*、要求哈希段也规规矩矩，却选择跟着浏览器走，甚至把 { } ^ 在某些段还原成明文。 换来：编码结果和地址栏一致、跨浏览器可预测，URL 还更短更好看。 代价：牺牲了和「严格遵循标准」的工具之间的互操作可预期性；必须靠注释维护一张「各浏览器差异表」（比如某浏览器在哈希段不编 "<>{}），哪天浏览器改了行为，这里就得跟着改。

权衡三：用一个宽松的平台编码函数作基底，再按段做「补编码 + 还原」修正。 选择：不自己从零实现编码，而是复用平台的 encodeURI 处理非 ASCII，再在上面打补丁。 换来：非 ASCII、Unicode 全交给平台，实现极短、还白嫖了平台长期维护的健壮性。 代价：写法是「先全部编码、再把不该编码的百分号串还原回来」，跟人的直觉正好相反，非常容易漏改某一项、或把替换顺序写错——这是一种对维护者不友好的实现风格。

权衡四：用两种不同的「空值」分别表达 ?key（无等号标志）与「完全省略」。 选择：解析后的值类型是 string | null（null 专门承载「有键无等号」），定义时的原始类型再加一个 undefined（专门承载「移除该键」）。 换来：用类型精确描述了两种 URL 形态，序列化和解析双向无损，调用方在类型层面就被迫理解这层区别，而不是靠口头约定。 代价：查询的序列化、规整（把数字转字符串、删掉 undefined 键、把数组里的 undefined 换成 null）逻辑因为空值判断而多了不少分支；调用方也确实得先搞懂 null 和 undefined 这一字之差，否则容易用错。

小结 ​

这一章把「URL 怎么安全地编、怎么安全地解」这件事一次讲透：核心就是放弃万能函数、改成按段细分字符集，外加用 null / undefined 两种空值把查询串的领域语义钉死在类型上。记住一句话就够——字符的命运取决于它站在 URL 的哪一节车厢里。
