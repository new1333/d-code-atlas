导航期数据加载器 ​

你大概遇到过这种页面：点一个链接，新页面立刻弹出来，但内容是空的，中间一个转圈，等数据回来才"啪"地填上。再点快一点，从列表连点到两个不同的详情页，有时候还会看到先显示了对的数据、一秒后又被一条迟到的旧请求盖成了错的数据。

读者真正想要的是另一回事：跳转完成的那一刻，这一页要用的所有数据都已经就位，而且是一起出现的——不闪、不跳、不被一条迟到的旧请求改回去。

这一章讲的就是怎么做到这件事。核心思路一句话：把"取数据"这件事从组件挂载之后，挪到导航完成之前；并且让数据"能不能被看到"严格跟着导航走——导航没确认，数据就算回来了也先藏着。

一、先把数据从组件树里搬出来 ​

传统写法里，数据请求多半写在组件的 onMounted 或 setup 里。这意味着请求要等组件挂载之后才发，而组件挂载发生在导航之后。于是顺序永远是：导航完成 → 组件出现（空白/骨架）→ 这才发请求 → 数据回来 → 画面跳一下。一个页面有多个组件各自请求，就各自跳，散成一盘。

那用 Suspense 行不行？它能等异步组件。但 Suspense 是把"异步"绑在组件树的渲染上的：它没有"所有加载器一起提交"这个点，也没法在组件挂载之前就让请求先并行跑起来。换句话说，它给得了"组件渲染时数据就绪"，却给不了"导航完成即数据就绪、而且原子地一起出现"。

打个比方（只用这一次）：导航管线是一条传送带，组件是盒子，数据是盒子里的零件。我们希望零件在传送带走到终点（导航确认）的那一刻，和盒子一起到位——而不是盒子先空着到终点、零件事后补投。

所以这里的做法是：直接把加载器挂到导航管线上——导航一开始就建一个"这次导航专属"的上下文，把这一页要用的加载器全部并行启动，等它们都回来、导航也确认了，再统一把数据露给组件。

权衡 1｜挂导航，不挂组件树 选了：把加载器挂在导航守卫上，而不是组件树或 Suspense。 换来：数据在导航期就并行加载、组件挂载时数据已就绪、多个加载器有一个统一的提交点（所以能"一起出现"）。 代价：必须自己接管一整套生命周期——暂存、提交、取消、父子加载器同步——放弃了 Suspense 那种声明式异步组件的简洁；而且加载器从此和路由绑死（这能力必须作为插件装在路由上）。

二、两阶段：先暂存，等导航确认了再提交 ​

这条是整章的心脏，我们慢慢拆。先看最底层的一块：一个加载器在多次跳转之间，到底替你记着什么。

每个加载器都有一份"条目"，它在多次导航之间复用（同一个加载器函数从 A 跳到 B 再跳回 A，用的是同一份状态）。这份条目里最关键的是三样：

  • data：组件真正能读到的数据。
  • staged：暂存区。加载器算出来的结果先写这里。
  • 一个"我正在为哪次导航干活"的身份标记（下面用 navId 表示）。

关键规矩只有一条：加载器算完结果，只许写 staged，绝不许直接写 data。 data 只在导航确认后，由一个统一的"提交"动作从 staged 搬过去。

为什么要这么别扭？两个好处，正好对应两个麻烦场景。

第一，防中途闪烁。 如果加载器一算完就写 data，几个并行的加载器谁先到谁先露，画面就会"用户信息先到、文章后到"分两次跳。先全部进 staged、确认后一次提交，组件看到的就是两者同时到位。

第二，防旧请求回滚新数据。 这是连点导航最坑的地方。想象用户从列表连点：先点了 /users/1（请求慢），没等回来又点了 /users/2（请求快）。/users/2 的数据先到、先提交、页面显示 /users/2。这时候 /users/1 的慢请求才姗姗来迟——如果它直接写 data，就会把已经显示的 /users/2 盖回 /users/1，画面错乱。

解法就是那个身份标记：每次导航开始，把所有条目的身份标记换成"最新这次导航"。加载器算完、准备写 staged 之前，先对一眼——"我这次导航，还是最新的吗？"对不上，说明我早被新导航顶替了，结果直接丢弃，连 staged 都不写。迟到的旧请求自然就影响不了任何东西。

这里要回指一句：第 9 章讲 Router 主循环时，"用待定位置在各阶段做取消检查、让任何阶段都能被新导航作废"这套已经讲透。本章只看它延伸到数据上的新侧面——给数据结果也配一道身份校验，让被作废的慢请求即便之后完成，也回滚不了已经显示的新数据。

下面这段几十行的演示，把上面这些一口气演透：暂存隔离、身份校验防回滚、并行启动、统一提交。

ts
// loader-staged-commit.ts
// 演透：暂存隔离可见性 + 身份校验防回滚 + 并行启动 + 统一提交

// 一个加载器条目：data 是组件能看到的，staged 是暂存（组件看不到），navId 记录"我在为哪次导航干活"
function makeEntry() {
  return {
    data: undefined, // 可见：组件读的就是它
    staged: null, // 暂存：结果先落这儿，确认后才搬进 data
    hasStaged: false,
    navId: null, // 正在飞的那次导航的身份
  }
}

// 一次导航：loaders 是 [{ entry, fetch }]，每个加载器有自己的请求函数
async function navigate(navId, loaders) {
  // ① 抢占：把身份换成最新这次导航，旧的那次立刻过气
  for (const { entry } of loaders) entry.navId = navId

  // ② 解析前：所有加载器并行启动，互不相等
  await Promise.all(
    loaders.map(async ({ entry, fetch }) => {
      const result = await fetch(navId) // 慢请求；期间可能已被更新的导航取代
      if (entry.navId !== navId) {
        // ⭐ 身份校验失败：我已过气 → 丢弃，连暂存都不写（防回滚）
        console.log(`  [nav ${navId}] 我已过气，丢弃结果（不回滚）`)
        return
      }
      entry.staged = result // 只写暂存，组件此时还看不到
      entry.hasStaged = true
      console.log(`  [nav ${navId}] 结果暂存（组件不可见）：${result}`)
    })
  )

  // ③ 导航确认后：统一提交，暂存一次性搬进可见的 data
  for (const { entry } of loaders) {
    if (entry.hasStaged) {
      entry.data = entry.staged
      entry.hasStaged = false
      console.log(`  [nav ${navId}] 提交进可见 data：${entry.data}`)
    }
  }
}

// ---- 连点演示：A 慢、B 快 ----
const userInfo = makeEntry()
const userPosts = makeEntry()

const slowInfo = (id) => new Promise((r) => setTimeout(() => r(`${id}·用户信息`), 100))
const fastInfo = (id) => new Promise((r) => setTimeout(() => r(`${id}·用户信息`), 10))
const slowPosts = (id) => new Promise((r) => setTimeout(() => r(`${id}·文章`), 100))
const fastPosts = (id) => new Promise((r) => setTimeout(() => r(`${id}·文章`), 10))

console.log('--- 连点：先跳 A（慢），不等回来立刻跳 B（快）---')
// A 在飞，不 await
navigate('A', [
  { entry: userInfo, fetch: slowInfo },
  { entry: userPosts, fetch: slowPosts },
])
// B 抢占身份，先完成、先提交
await navigate('B', [
  { entry: userInfo, fetch: fastInfo },
  { entry: userPosts, fetch: fastPosts },
])
console.log('B 完成后组件看到：', userInfo.data, '/', userPosts.data)

await new Promise((r) => setTimeout(r, 120)) // 等 A 的慢请求晚到
console.log('A 晚到后组件看到：', userInfo.data, '/', userPosts.data, '（没被 A 回滚）')

配一个最小的 package.json 就能跑（npm i && npm start，或直接 bun loader-staged-commit.ts）：

json
{
  "name": "loader-staged-commit",
  "private": true,
  "scripts": { "start": "tsx loader-staged-commit.ts" },
  "devDependencies": { "tsx": "^4" }
}

跑出来的执行轨迹是这样的：

--- 连点：先跳 A（慢），不等回来立刻跳 B（快）---
  [nav B] 结果暂存（组件不可见）：B·用户信息
  [nav B] 结果暂存（组件不可见）：B·文章
  [nav B] 提交进可见 data：B·用户信息
  [nav B] 提交进可见 data：B·文章
B 完成后组件看到： B·用户信息 / B·文章
  [nav A] 我已过气，丢弃结果（不回滚）
  [nav A] 我已过气，丢弃结果（不回滚）
A 晚到后组件看到： B·用户信息 / B·文章 （没被 A 回滚）
  • 输入：连点两次导航，A 的请求要 100ms、B 只要 10ms。
  • 中间态：B 先抢占了身份标记，两个加载器并行算完、各自写进暂存（组件此时读 data 还是旧值）；然后统一提交，data 一次性跳到 B 的值。
  • 输出：A 的慢请求 100ms 后才到，可这时身份标记早就不是 A 了——校验失败，结果被丢，data 始终是 B，没有被回滚。

注意 B 的两个加载器是并行的（都 10ms，几乎同时返回），暂存两行连着出、提交两行连着出——这正是"并行启动 + 统一提交"换来的"无闪烁"。

权衡 2｜暂存→提交两阶段 + 身份校验 选了：结果先写暂存，确认后统一提交；每次加载器完成、以及提交时，都做一道"我还是最新导航吗"的身份校验。 换来：多个并行加载器的数据原子可见（一起出现、不闪烁）；被新导航作废的慢请求就算之后完成，也回滚不了已显示的新数据。 代价：每个条目得多挂一对暂存字段和一个"在飞的导航"槽位；提交时机还分散在"加载器一完成立即提交"和"所有加载器都完成后统一提交"两条分支，状态机变复杂了。

三、三个接缝：加载器到底挂在导航的哪几步 ​

上面那套暂存/提交，是靠三个导航钩子撑起来的：

  • 导航一开始：建一个这次导航专属的"中止信号"，并把"当前待定导航"指向这次；同时把上一条还没完成的待定导航的中止信号触发掉（连点时，旧的那条立刻被作废）。
  • 解析前（所有守卫通过、组件都能解析了）：收集这一页用到的全部加载器，把中止信号交给它们，用 Promise.all 并行启动。
  • 导航确认后：挨个把加载器的暂存提交成可见数据；如果导航失败，则触发中止信号、把待定状态清掉。

这里再回指一句：第 7 章讲导航守卫管线时，"守卫怎么按 leave → beforeEach → ... → beforeResolve 的严格顺序串成 promise 链、任一环节 reject 就短路"已经讲透。本章只是借用其中一道天然接缝——"解析前 → 导航确认后"——把它当成"并行加载 → 统一提交"的挂载点，不重复演示那套串联机制。

文字流程图：

导航开始              解析前                      导航确认后
  │                    │                            │
  ├─ 触发上一条的中止   ├─ 收集本页全部加载器        ├─ 失败：触发中止信号
  ├─ 建本次中止信号 →  ├─ Promise.all 并行启动    → │       清掉待定状态
  └─ 标记待定导航      ├─ 结果只写暂存(组件不可见)   └─ 成功：暂存 → 统一提交进 data
                       └─ 懒加载器不阻塞导航              （组件此时才看到新数据）

两个补充点：

  • 中止信号能传进加载器函数。 加载器作者拿到这个信号，可以在请求里用它取消（比如 fetch 的 signal）。这样连点导航时，旧请求不只是在结果上被丢弃，连请求本身都能被真正打断，省掉无谓的网络开销。
  • 条目是按"加载器函数本身"存起来的。 用的是一张弱引用表，键就是加载器这个函数对象。所以同一个加载器定义，不管你跳去哪再跳回来，用的永远是同一份条目、同一份"在飞"状态——往返不会重复建状态，加载器函数被回收时条目也自动跟着回收。

四、返回值既是对象又是 Promise：一个加载器依赖另一个加载器 ​

到这里还有一个现实需求：加载器 B 想用加载器 A 的结果。比如"用户文章"加载器，需要先知道"用户信息"加载器拿到的用户 id。

这里有个设计上的巧思（权衡 3 的核心）：加载器的返回值，是一个既是对象、又是 Promise 的东西。

  • 在组件里用，你解构它：const { data, error, isLoading } = useUser()，拿到响应式字段直接渲染。
  • 在另一个加载器里用，你 await 它：const user = await useUser()，拿到的是这一次算出来的原始数据。

同一个返回值，两种用法都对。它的好处是天然支持"加载器依赖加载器"——你不用学第二套 API，在加载器体里 await 另一个加载器就行。

那"我在 B 里 await 了 A，系统怎么知道 B 依赖 A、提交时要先提交 A"？这里用了一个有点冒险但很省事的招（权衡 4）：维护一份模块级的"当前上下文"。调用一个加载器之前，先把"当前条目"设成它；加载器体里去 await 另一个加载器时，后者读到前者，就自动把自己登记成前者的"孩子"。父加载器提交时，会递归地先把孩子提交了。

代价也实在：这是一份隐式的全局可变状态，而且每跨过一个 await 都得手动把它存起来、用完再恢复，时序非常微妙，调试起来不直观。

两段小代码点透这两点：

ts
// 双面 API：把结果字段直接拍到一个 promise 上返回
const ret = Object.assign(
  pendingPromise.then(() => stagedValue), // await 它 → 拿到原始数据
  { data, error, isLoading, reload } // 解构它 → 拿到响应式字段
)

// 父子提交：父提交时，先把所有孩子提交了
function commit(entry, to) {
  if (entry.pendingTo !== to) return // 身份校验，和第二节同一套
  if (entry.staged !== NO_VALUE) entry.data.value = entry.staged
  for (const child of entry.children) commit(child, to) // 递归提交孩子
}

权衡 3｜对象即 Promise 的双面 API 选了：把结果字段直接拍到一个 promise 上返回。 换来：同一个返回值，组件里能解构出响应式字段、另一个加载器里能 await 取原始数据，于是"加载器依赖加载器"零额外语法。 代价：类型层面得发明"既是对象又是 Promise"的交叉类型；错误处理得在两种调用方式间分流——只有被别的加载器嵌套调用时才把错误往上抛，组件顶层调用时则吞掉（错误已经进了 error 字段，避免抛出没人接的 promise 拒绝）。

权衡 4｜用一份全局上下文隐式传依赖关系 选了：靠模块级的"当前父子上下文"建立加载器之间的依赖，而不是让作者显式传参。 换来：加载器作者只要在函数体里 await 另一个加载器()，就自动登记成父子依赖，API 表面零侵入。 代价：这是一份隐式的全局可变状态，每个 await 前后都要手动保存/恢复上下文，时序极微妙，出问题很难查。

五、还能更聪明：只在"我读过的字段"变化时才重取 ​

这是更激进的一档（属于接外部查询缓存的高阶实现），本章不展开，只点一下它换来了什么：用一层代理去盯"加载器这次到底读了路由的哪些字段"——只读了参数 id，那就只在 id 变化时重取；query 变了但加载器压根没读 query，就不重取。换来精准的按需重取，代价是引入读取追踪、已读字段比对，复杂度明显上去。知道有这一档即可。

小结 ​

这一章的内核可以收成一句话：把数据的可见性和导航的生命周期绑死。 数据在导航解析阶段就并行跑起来，但只要导航还没确认，结果就只许躺在暂存里；导航一确认，所有加载器的暂存一次性提交，组件看到的就是整页数据同时到位。连点导航时，靠"我还是最新导航吗"的身份校验，迟到的旧请求连暂存都进不去，回滚不了已经显示的新数据。这一切之所以可能，是因为加载器没有挂在组件树上，而是挂在了导航管线的三道接缝上——代价是你得自己背起暂存、提交、取消、父子同步这一整套生命周期。

下一章会换个方向：不再往导航里加东西，而是看一套全新的路由解析器——它把路由表的动态性从运行时推到构建时，用独立的 path / query / hash 三段匹配器和"抛异常当作不匹配"的控制流，重新设计匹配这件事。
