导读：yt-dlp 源码解读 ​

这本书在讲什么：一句话主线 ​

打开 yt-dlp 的源码，你会被它的体量吓一跳——能下上千个站点、支持几十种协议、自带一个 JS 解释器、还能从浏览器里偷登录态。但它内部真正反复在做的事，凝练成一句话是：

把「谁来做这件事」从「到底要干什么」里彻底剥出来，让前者交给一份带标签的数据、或一套约定去自动决定；再把成百上千个因此变得可插拔的零件，缝在一条贯穿全程的胖字典上。

这句话拆开就是全书的骨架。「做什么」和「谁来做」被分开后，换来的是一组可以无限换、无限加的零件——换个网络引擎、加个新站点、塞个新下载器、补一道后处理工序，都是「丢一个文件、起对名字」级别的动作，核心流程一行都不用改。而把这些零件黏在一起的，是一个字段极丰富的普通字典（info_dict）：它从提取器手里出发，一路流过选格式、下载、后处理、命名，每一段都只是对它读几个字段、写几个字段。最后，一个胖协调器（YoutubeDL）把所有零件按顺序串起来，并把登录态、请求引擎、去重归档这些谁都要用、谁都不该自己造一份的东西攥在手里。

全书 13 章可以看成这个骨架的三层落地：最底下两块地基（怎么把请求和零件都做成可插拔的），中间九个围着那条胖字典转的各阶段零件，最顶上把这一切缝成一条线、再把命令行接进来的两层。

小提示：outline 里给每章标了 layer——primitive（地基）/ composite（各阶段零件）/ system（把零件缝成线）。下文脉络图就按这个分层画。

怎么读这本书：两条阅读路线 ​

一、线性路线（按依赖顺序从头读到尾） ​

按各章的依赖关系排好的顺序读，每一章都承接了上一章打开的口子、又为下一章铺路：

  1. 可插拔传输层——把「发什么请求」和「用哪个引擎发」拆开，立起第一块能无限换引擎的地基。
  2. 插件注册——立起第二块地基：丢个文件、起对名字就注册新能力，整个生态可扩展的源头。
  3. 指纹伪装——第一块地基的首次实战：怎么「只挂一种新能力、骨架一字不改」（能力走扩展槽、路由走偏好）。
  4. info_dict 数据总线——引出贯穿全书的那条胖字典，从此各阶段都对着同一个对象做纯变换。全书枢纽，建议精读。
  5. JS 解释器——为对付会下发混淆脚本的狡猾站点，在进程里手搓一个迷你 JS 引擎，把对手的脚本当数据本地跑。
  6. 下载分派——把「用什么下载器」下沉成数据里的 protocol 标签 + 一张分派表，编排器从此对下载细节彻底无感。
  7. 分片下载——把不可靠的长流（HLS/DASH）拆成一片一片可恢复的工作单元，靠一个记片号的簿记文件实现断点续传。
  8. 后处理流水线——把一堆加工开关翻译成一条有序的链，每个站对 info 做一次纯变换、顺带声明该删什么。
  9. 格式选择 DSL——把一行 -f bestvideo+bestaudio/best 编译成选择器：排序器定基准序、选择器只取下标从不比较。
  10. 输出模板——把命名、进度、命令都变成「同一份元数据的投影」，关键是「编译而非解释」。
  11. cookies——把浏览器五花八门的加密登录态还原成一个统一罐子，再按域名注入请求。
  12. 编排器 YoutubeDL——把上面所有零件串成一条主管线，攥住所有横切底座（自己也因此胖成上帝对象）。
  13. CLI 层——把混乱多源的命令行表面洗成一张干净纯参数表，核心对终端一无所知。

二、按主题路线（带着具体问题跳读） ​

  • 「只想搞懂请求怎么发出去、引擎怎么选、登录态怎么带上」：读 [1] 可插拔传输层 → [3] 指纹伪装 → [11] cookies。这三章讲的全是「请求这趟旅程」上的事。
  • 「只想搞懂一个站点是怎么被解析成数据的」：读 [2] 插件注册（站点怎么被发现）→ [4] info_dict（解析结果长什么样）→ [5] JS 解释器（碰到下发脚本的站点怎么办）。
  • 「只想搞懂文件到底怎么被下载下来」：读 [6] 下载分派（选哪个下载器）→ [7] 分片下载（长流怎么拆着下）。这俩是下载主题的连续两步。
  • 「只想搞懂下完怎么加工、怎么选格式、怎么起名」：读 [8] 后处理流水线 → [9] 格式选择 → [10] 输出模板。三章都是「对那条胖字典做不同投影」。
  • 「只想搞懂整条流水线怎么被串起来、命令行怎么进来」：读 [12] 编排器 → [13] CLI 层。前者是内部总线，后者是外部入口，首尾相接。
  • 「想最快抓住全书设计哲学」：只读 [1] 可插拔传输层 + [4] info_dict + [12] 编排器三篇——「中立请求」「胖字典」「胖协调器」三点一线，就是全书骨架。

贯穿全书的核心原理 ​

下面几条原理，在多章里以不同化身反复出现。一旦认出「这其实是同一个原理的又一次现身」，理解就会贯通。

1. 「把『谁来做』从『做什么』里剥出来，让前者靠数据/约定自动决定」——全书最深的复现原理。 本质：永远不让调用方去 if/else 挑执行者，而是让执行者靠一份带标签的数据或一套约定自己冒出来。 现身：[1] 传输层（中立请求是「做什么」、偏好函数选引擎是「谁来做」）、[6] 下载分派（下什么是「做什么」、protocol 字段选下载器是「谁来做」）、[9] 格式选择（要什么规格是「做什么」、排序器定基准序是「谁算更好」）、[12] 编排器（拿到啥结果是「做什么」、_type 字段 switch 决定走哪条路是「谁来做」）、[8]/[13] 后处理（开关是「做什么」、生成器翻成有序流水线是「怎么排」）。认出这一点，你会发现这五章表面毫无关系，内里是同一个套路。

2. 「数据自带标签，分派表照标签择路」——『谁来做』最常用的落地姿势。 本质：往数据里塞一个字符串标签，再配一张「标签 → 执行者」的表，分派就退化成查表。 现身：[6] 下载器看 protocol、[12] 编排器看 _type、[11] cookie 解密看 v10/v11 版本前缀、[8] 后处理按 when 字段挂到 8 个阶段、[1] 引擎能力自检看 extensions 口袋里剩没剩东西。同一个「标签驱动分派」的想法，被用了五遍。

3. 「自报能力 + 候选择优，不支持就跳过、再问下一个」——可插拔的竞争机制。 本质：让每个候选把自己「能干什么」老实写出来，分派方逐个问，谁说能就用谁，全部说不通才报错，而且报错时把每家拒绝的理由都带上。 现身：[1] 传输引擎自报 schemes/扩展 + 抛「不支持」降级、[6] 外部下载器自报 SUPPORTED_PROTOCOLS + can_download 自荐、[3] 会伪装的引擎自报支持目标表 + 偏好加分胜出、[2] 后缀即类型 + 前置合并让插件盖过同名内置。注意这条原理的代价也跨章一致：能力清单漏报或误报，bug 就藏在那道缝里。

4. 「基类吸收所有横切样板，子类只填一个钩子」——把脏活集中、把业务做薄。 本质：和协议/站点无关的重复劳动（限速、重试、下载网页、进度上报）全收进基类，子类只剩一个「真正干这站点/这协议特有的事」的方法要写。 现身：[4] 提取器基类把抓网页/正则/结构化数据全吸收，子类只写 _real_extract；[6] 下载器基类把限速/断点续传/.part/进度钩子全吸收，子类只写 real_download；[8] 后处理用元类在类创建时自动给 run 包一层进度通知，作者只写纯业务。三次同一个分工思想。

5. 「一份数据对象贯穿多阶段，各阶段对它做纯变换」——那条胖字典本身就是原理。 本质：全系统说同一种语言（一个无固定 schema 的胖字典），每段流程的签名都统一成「吃一个字典、吐一个字典」，谁也不必关心别的阶段需要什么参数。 现身：[4] 定义这条总线，[6] 读 protocol、[7] 边下边写回、[8] 反复改写 filepath、[9] 读 formats、[10] 把字典投影成字符串、[12] 让它一路贯穿到底。它的代价也跨章一致：schema 只靠注释约定、拼错字段名编译器不提醒、字段语义还会随阶段漂移。

6. 「把不可信、会变、来自外部的东西，当数据在本地处理」——对『对抗』的统一态度。 本质：不从外部拉重型引擎，而是自己写一个「刚好够用」的本地处理者，把对手下发的、或锁在外部存储里的东西当输入就地消化掉。 现身：[5] 不拉 V8、在进程内手写 JS 解释器跑站点下发的对抗脚本；[11] 不调浏览器 API、纯文件层 + 系统密钥环把加密 cookie 还原成明文。两次都是「宁可自己手搓一个脆弱但可控的处理者，也不依赖外部黑盒」。
