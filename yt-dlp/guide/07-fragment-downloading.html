分片化下载：把长流拆成可恢复的工作单元 ​

本章属于 composite 层。前置：协议字段驱动的下载策略分派。 学完你能：用一句话讲清"为什么长流要拆成分片序列来下、簿记文件和协作式中断各自在权衡什么"。

1. 为什么需要它（设计动机） ​

上一章讲了 protocol 字段如何把整条下载委派给合适的 FileDownloader——HttpFD/HlsFD/RtmpFD 各司其职，基类吸收限速、字节续传、.part 临时文件等横切能力。但这件事到此只解决了"为这条流选对下载器"，没解决一个更深的矛盾：HLS/DASH 这类流在网络层根本不是一个文件。

想象一部两小时的网课：浏览器后面拉的是几百段几秒钟一个的独立小分片，清单（m3u8/MPD）只是分片 URL 的目录。若仍把它当一个整体下，会撞上几堵墙：

  • 在 89% 处断网，得从 0 重来。字节续传只能续到临时文件已有的字节，而分片流的逻辑进度是"片数"，不是字节偏移
  • 任意一段 503 或超时，整条流失败。你无法分辨是这一片暂时不可得还是整流完蛋
  • 中间夹杂的广告段、加密段、字幕段，它们需要的不是"原样拼接"而是"跳过、就地解密、合并去重"

使用者要的是"下完能播的一个文件"，网络只肯给"一堆易碎的小段"。这两者之间的鸿沟，就是本章要填的。

2. 核心思想 ​

把一条不可靠的长下载建模成一个可迭代的"分片工作单元"序列：每片独立下载、独立重试、可跳过、可解密、下完即追加并记账，崩了能从记账处接着干。

这条流水线把"长下载"的容错颗粒度从"整文件"细化到"片"，把"断点"从字节偏移升级到"逻辑片号"，并允许在每片字节流过时插入变换。

3. 心智模型 ​

七个动作串成一条流水线：

  1. 拿到分片源：要么是清单文本（HLS 的 m3u8），要么是提取器预解析好的分片列表（DASH 的 fmt['fragments']）。把它看成一条可迭代的分片序列。
  2. 准备：按目标临时文件已有大小决定以写或追加模式打开；读簿记文件 .ytdl 恢复"已下到第几片"；派生一个关掉屏幕输出与进度、重置 sleep/test 的"静音子下载器"；挂一个把子级字节进度翻译成总级分片进度的钩子。
  3. 逐片循环：用子下载器把当前片下到独立临时文件。注意单片内部仍然走前置章讲过的字节续传、Range、重定向、限速，复用一切既有能力。
  4. 逐片重试：用 RetryManager 包住每片下载，捕获 HTTP 错误与不完整读。该片最终失败时按"是否致命、是否允许跳过"决定跳过还是中止整流。
  5. 追加：读出字节 →（若加密）就地解密 → 过变换钩子 → 追加到目标流并 flush。
  6. 记账：把"当前片号"写回簿记文件，删除该片临时文件（除非开了 keep_fragments）。
  7. 收尾：关流、把临时文件改名成最终名、删簿记文件、发出"完成"进度。

一条不变量贯穿全程：簿记里的片号 = 已成功落盘的分片数。后面所有容错语义都挂在这条不变量上。

4. 关键权衡 ​

4.1 片级续传用独立"簿记文件"，不靠字节偏移 ​

选择：每追加完一片，把"当前片号"写进一个 JSON 簿记文件 .ytdl，结构是 {downloader:{current_fragment:{index}, extra_state?, fragment_count?}}。

换来：按"逻辑片边界"精确续传。哪怕分片是各自独立抓取再拼接的，也能从"已下到第几片"恢复；簿记还能承载额外状态（如解密器游标），给未来扩展留口子。

代价：磁盘上多了一份必须与数据文件保持一致的簿记状态。系统必须主动检测两种病态并各自从 0 重来：

  • 簿记损坏：JSON 解析失败——置 ytdl_corrupt 标志，重置
  • 状态不一致：簿记说片号 > 0 但数据文件为空（用户删了临时数据却留下了簿记）——直接重置

本质矛盾：这是"恢复颗粒度"与"状态一致性维护成本"的对立。颗粒度越细（按片甚至按字节），恢复越精确，但要维护的状态机也越复杂。任何"数据已落盘但簿记未更新"或反向情况都会破坏不变量，所以必须额外花力气检测病态。

4.2 每片用一个"静音子下载器"复用，不直连 HTTP ​

选择：为整个分片流派生一个关掉 to_screen/to_console_title、强制 noprogress、重置各 sleep/test 的子下载器实例，由它逐片下到独立临时文件。

换来：完整继承既有单文件下载器的断点、Range、重定向、限速能力，零成本复用前置章 HttpFD 的全套基础设施；同时父下载器独占唯一一条聚合进度条，避免几百片各刷一行进度把屏幕撑爆。

代价：引入了一层"嵌套下载器"和一层进度翻译——把子下载器报告的字节级进度，映射、平滑、外推出"分片级 + 总量估算"的进度。非直播时总量用均摊外推：(已下字节 + 当前片字节) / (当前片号 + 1) × 总片数。

本质矛盾：这是"复用已造好的轮子"与"避免输出噪声"的对立。不复用就得重新实现 Range/重定向/限速；不静音则几百片各刷一条进度。派生静音子下载器是同时解决两者的最小代价，但代价转嫁到了"进度翻译"这一层。

4.3 内容变换走可插拔钩子，不硬编码追加 ​

选择：核心循环接受两个钩子——pack_func（每片字节追加前变换）与 finish_func（收尾时再写一段）。默认恒等，字幕流则用来做碎片化 WebVTT 的合并、去重、时间戳溢出修正。

换来：同一条逐片循环既能做"原始字节拼接"（音视频分片），又能做"字幕合并去重 + 时间戳修正"（碎片化字幕）而核心不动。AES-128 解密也挂在同一变换位点：unpad_pkcs7(aes_cbc_decrypt_bytes(...)) 就是一个纯函数钩子，密钥按 URL 缓存避免反复抓。

代价：字幕合并逻辑复杂且需要跨片状态（去重窗口、MPEG-TS 33 位时间戳修正量）在线程间正确传递。一旦上并发，可变状态就要靠锁或线程局部来保护。

本质矛盾：这是"核心循环的通用性"与"特定流类型的正确性"的对立。把变换硬编码进循环，则每加一种流类型都要改核心；走钩子，则核心稳定，但变换状态的管理成本外推到每个具体钩子的实现者。

4.4 中断用"共享可变标志"做协作式取消，不强杀线程 ​

选择：用一个被所有工作线程共享的单元素可变列表 [True] 做中断标志，在每个分片边界检查；用户中断时只把标志置 False。

换来：线程池的干净收尾——无需不可靠且不安全的强杀（Python 没有原生线程取消 API）；并且对直播流能返回"已下的中间结果"而非抛 KeyboardInterrupt，让用户拿到部分视频而不是全损。

代价：取消是协作式的、有延迟。工作线程可能再多下一片才察觉，中断响应延迟上限约等于一片下载耗时。

本质矛盾：这是"取消的即时性"与"系统可恢复性"的对立。强杀线程能立刻停，但留下半开连接、未刷新的缓冲、未释放的锁；协作式取消干净但慢。分片流天然有"片边界"这个良好检查点，恰好让协作式的代价变得可以接受。

5. 最小原理演示 ​

下面这段 TS 只演透三件事：分片序列的逐片处理 + 簿记续传 + 协作式中断。AES 解密、字幕合并、并发池、HLS 清单解析统统砍掉——它们不服务于讲透原理。

typescript
import { promises as fs } from 'fs';

type Frag = { index: number; url: string };
type Bookkeeping = { fragment_index: number };

// 模拟"第 3 片首次失败、重试后成功"的 fetch
async function fetchFrag(url: string, attempt: number): Promise<Buffer> {
  if (url.includes('/frag-3') && attempt === 0) {
    throw new Error('HTTP 503');
  }
  return Buffer.from(`content-of-${url}\n`);
}

// 逐片重试；最终失败返回 null（这里按"跳过"策略，不演示 is_fatal 区分）
async function downloadFragmentWithRetry(
  frag: Frag, maxRetries: number,
): Promise<Buffer | null> {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fetchFrag(frag.url, attempt);
    } catch {
      if (attempt === maxRetries) return null;
    }
  }
  return null;
}

async function downloadStream(
  frags: Frag[], destPath: string, bookPath: string,
  interrupt: boolean[],  // 单元素列表，按引用共享给所有"线程"
): Promise<boolean> {
  // 准备阶段：读簿记恢复"已下到第几片"
  let resumeIndex = 0;
  try {
    const book: Bookkeeping = JSON.parse(await fs.readFile(bookPath, 'utf8'));
    resumeIndex = book.fragment_index;
    // 病态检测：簿记说下到片 N 但目标文件是空的——重置
    const stat = await fs.stat(destPath).catch(() => null);
    if (resumeIndex > 0 && (!stat || stat.size === 0)) {
      resumeIndex = 0;
    }
  } catch {
    // 病态检测：簿记损坏（解析失败）——重置
    resumeIndex = 0;
  }

  const flags = resumeIndex === 0 ? 'w' : 'a';
  const dest = await fs.open(destPath, flags);

  for (const frag of frags) {
    // 片边界查中断标志——协作式取消的检查点
    if (!interrupt[0]) {
      await dest.close();
      return false;
    }
    if (frag.index <= resumeIndex) continue;  // 簿记账本：已下过的片跳过

    const bytes = await downloadFragmentWithRetry(frag, 1);
    if (bytes === null) continue;  // 不可得则跳过

    // 追加 → flush → 写簿记：这个顺序保证"簿记片号 = 已落盘片数"
    await dest.write(bytes);
    await dest.flush();
    await fs.writeFile(bookPath, JSON.stringify({
      fragment_index: frag.index,
    }));
  }

  await dest.close();
  await fs.unlink(bookPath);  // 收尾：删簿记
  return true;
}

这几十行没有解密、没有进度估算、没有静音子下载器，但它已经能演示"用簿记文件做片级续传"的核心控制流长什么样。

6. 执行轨迹 ​

输入：4 片的流，第 3 片首次失败、重试后成功。在下完第 2 片后被用户中断、随后重启。

第一次运行：

步骤动作状态变化
准备数据文件不存在、簿记不存在 → w 模式打开，resumeIndex=0dest=空
片 1下载成功 → 写 28 字节 → flush → 簿记 {fragment_index:1}dest=28B, book=
片 2下载成功 → 写 28 字节 → flush → 簿记 {fragment_index:2}dest=56B, book=
中断用户 Ctrl-C，外层把 interrupt[0]=false，循环在下一片边界察觉后退出dest=56B（保留）, book={2}（保留）

第二次运行（重启）：

步骤动作状态变化
准备读簿记 → resumeIndex=2；数据文件 56B > 0，一致 → a 模式打开dest=56B
片 1、2frag.index <= resumeIndex → 跳过（簿记账本生效）dest=56B
片 3（attempt 0）fetchFrag 抛 503 → 进入重试—
片 3（attempt 1）成功 → 写 28 字节 → flush → 簿记 {fragment_index:3}dest=84B, book=
片 4下载成功 → 写 28 字节 → flush → 簿记 {fragment_index:4}dest=112B, book=
收尾关流 → 删簿记dest=112B（最终），book=删除

输出：完整拼接的 112 字节文件。全程实际网络拉取：片 1×1 次、片 2×1 次、片 3×2 次、片 4×1 次。簿记让片 1、2 在重启后没有重下。

7. 教学简化说明 ​

本章演示故意省略：

  • 静音子下载器与进度翻译：上面用单线程串行，真实系统派生子下载器以复用 HttpFD 的 Range/重定向/限速，并把子级字节进度均摊外推出总量
  • AES-128 就地解密：演示里删掉了，真实系统在 decrypt_fragment 钩子做 unpad_pkcs7(aes_cbc_decrypt_bytes(...))，密钥按 URL 缓存
  • 字幕合并钩子（碎片化 WebVTT 去重 + MPEG-TS 33 位时间戳溢出修正），其状态化复杂度独立成题，不展开
  • 并发分片下载（多 ThreadPoolExecutor + DASH 多轨的"第 0 轨致命"策略）
  • 直播特例：禁用簿记、被中断时返回中间结果而非抛异常
  • HLS 能力探测与内部降级：HLS 下载器扫清单发现 DRM 或非 AES-128 加密即 can_download=False，主动把整条下载转交 ffmpeg。这是前置章"外部下载器自荐接管"在同一层内的反向应用——native 自报不足，让位给外部工具

8. 小结 ​

分片化下载的本质不是"下得更快"，而是把不可靠的长下载切成可恢复的工作单元。容错颗粒度从整文件细化到片、断点从字节偏移升级到逻辑片号、变换从硬编码升级到钩子，簿记文件、静音子下载器、协作式中断各自为这条主线付出可接受的代价。

分片下完只是字节数对了；把这些字节加工成最终的音视频文件，要走下一章的声明式后处理流水线。
