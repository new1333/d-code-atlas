# 提示词优化计划 · 面向初级程序员 + 概念分层 + 跨章一致性

> 跨里程碑的提示词优化任务。目标:解决批产文档的两个系统性问题——(1) **系统性啰嗦**:对所有人都懂的基础概念也打比方、同一比喻在多章反复展开(但进阶概念的首次比喻是教学必需,需保留);(2) 分章节并行跑、无跨章视角导致的**跨章风格不一致**。
>
> **核心机制**:不按读者水平一刀切(那样对初级太干、对熟练太水),而是**按概念本身分层处理**——基础概念直接用、进阶概念首次配简短比喻且后续复用、设计决策鼓励比喻+权衡三段。读者画像是**初级程序员**:懂基本语法,但不必然熟悉该领域进阶概念。
>
> 所有改动**完全通用化**,不假设 Vue/Pinia 或任何具体技术栈,适用于 Atlas 跑的任意仓库。

---

## 0. 背景与根因诊断

### 0.1 现状评估

基于对 `atlas/pinia/` 产出的全量 review(15 章 + index + config),质量总评:

- **内容质量 9/10**:关键权衡(做了/换来/代价)、可跑演示、执行轨迹、技术准确性细节(如 PINIA_R1004 门控、nextTick 窗口、Symbol token 恢复权)都到位。
- **一致性 6/10**:15 章像 15 篇独立文章——标题编号(中文数字 vs 无编号)、演示节命名("最小演示" vs "40 行看清整个机制")、权衡小标题格式、开场钩子方式各章自创。
- **啰嗦**:比喻被用在**所有人都懂的基础概念**上、或**同一比喻反复展开**(进阶概念每章都重新铺成多行排比);动机段铺垫一整屏。注意:进阶概念(effectScope、watcher、reactive 解包等)的**首次**比喻是教学必需,不是啰嗦——初级读者需要它。

### 0.2 根因(都在提示词层)

| #   | 缺口                                     | 位置                                                         | 后果                                                            |
| --- | ---------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| 1   | **双轨 prompt 且不同步**                 | `writer.md`(权威但未注入) vs `writer.ts`(实际生效)           | 靠人工同步,易漂移;且 `writer.ts` 对结构骨架只给推荐不给硬约束   |

### 0.3 读者画像校准(本计划的校准基准)

> Atlas 跑的是任意开源仓库。读者画像是**初级程序员**:

读者是**初级程序员**:掌握主语言的基本语法(变量、函数、条件、循环、基本数据结构、能读懂常见代码),但**不必然熟悉该领域的进阶概念**(响应式、依赖注入、effectScope、AST、序列化、中间件、并发同步等)。他们读这份导读是为了「**理解这个项目做了什么设计决策、为什么这么取舍**」,需要被照顾的是那些**初次见到的进阶概念**,而不是他们已经懂的基本语法。

一切文风指令都以此为校准基准。

#### 关键机制:按概念分层而非按读者水平一刀切

本计划不采用「按读者水平卡死比喻预算」(那种做法对初级太干、对熟练太水),而是**按概念本身分层处理**。这样无论读者实际水平高低都能自适应:

| 概念层级 | 例子 | 处理策略 |
|---------|------|---------|
| **基础概念**(所有人都懂) | 变量、函数、if/for、数组、对象、基本赋值 | 直接用,**不解释、不比喻** ← **啰嗦的真正来源** |
| **进阶概念**(初级可能不懂) | 响应式、依赖注入、effectScope、AST、序列化、中间件、并发同步、Map/Set、闭包 | 首次出现配 **1 个简短比喻点透**(压成 1~2 句,不展开成多行排比);后续复用同一比喻,不重复解释 |
| **设计决策**(所有人都没见过) | 本项目特有的取舍:先注册半成品、影子store、暂停watcher、payload 搭车 | **鼓励配比喻** + 完整「做了/换来/代价」权衡三段 |

**判别一个概念属于哪层**:
- 写在所有主流语言入门教程里 → 基础概念。
- 写在该领域专门教程/章节里(响应式原理、编译器、并发模型)→ 进阶概念。
- 在被分析仓库的源码里第一次出现、是该项目的独创取舍 → 设计决策。

#### 啰嗦的真正定义(修订后)

啰嗦 ≠ 比喻多。啰嗦 = **比喻被用在了基础概念上**(对 if/赋值/数组打比方)或 **同一比喻被反复展开**(同一概念每章都重新解释一遍)。
进阶概念的**首次**比喻是教学必需,不是啰嗦;设计决策的比喻是产品核心,更不是啰嗦。

## 2. 阶段一(P0)详细计划

### 改动 1:重写 `src/agents/writer.ts` 的「文体」段

#### 位置

`src/agents/writer.ts` 第 107-119 行,实际生效的 user prompt(当前注入到每个 Writer agent)。

#### 现状(待替换)

```
### 文体：通俗、像人说话（最高优先级文风要求）
- 这是教学文...读者是「想搞懂原理的人」...
- 每节正文必须以人话开头：用一个具体场景、「想象一下」起手...
- 禁用生硬抽象词...原语、载体、归一...
- 抽象概念第一次出现时配一个类比：全局指针 = 公共留言板...
- 允许并鼓励过渡人话：「说人话就是…」每节可有 1～2 句...
```

**问题**:隐含"越通俗越好";"每节必须有类比/过渡人话"导致比喻泛滥。

#### 目标文本(通用化,完整替换)

```
### 文体：面向初级程序员，按概念分层讲解（最高优先级文风要求）

#### 读者画像（一切文风的校准基准）
读者是**初级程序员**：掌握主语言的基本语法（变量、函数、条件、循环、基本数据结构、
能读懂常见代码），但**不必然熟悉该领域的进阶概念**（响应式、依赖注入、effectScope、
AST、序列化、中间件、并发同步等）。他们读这份导读是为了理解「这个项目做了什么设计决策、
为什么这么取舍」。需要被照顾的是**初次见到的进阶概念**，而不是他们已经懂的基本语法。

#### 按概念分层处理（核心机制，不是按读者水平一刀切）
写作时把每个概念归入三层，各层用不同策略：

**A. 基础概念（所有人都懂）**：变量、函数、if/for、数组、对象、基本赋值、常见 API。
→ **直接用，不解释、不比喻。** 这是「啰嗦感」的主要来源——不要对 if 赋值、数组操作、
  普通函数调用打比方。

**B. 进阶概念（初级可能不懂）**：响应式、依赖注入、effectScope、AST、序列化、中间件、
  并发同步、Map/Set、闭包、Promise、发布订阅等。
→ **首次出现时配 1 个简短比喻点透**（压成 1～2 句，不要展开成多行排比）；**后续章节
  复用同一比喻，不重复解释**。例：「effectScope 像一张可整体掀翻的桌面——一次 stop()
  就把桌上所有东西都倒掉」，首次出现讲这一句，后面再用就写「桌面（第 1 章引入过）」即可。

**C. 设计决策（所有人都没见过）**：本项目特有的取舍，如「先注册半成品再装配」「影子store
  器官捐献」「暂停 watcher 后手动触发」「payload 搭车运输」。
→ **鼓励配比喻**（这是产品核心，不算啰嗦）+ 完整「做了什么/换来了/代价是什么」权衡三段。

**判别一个概念属于哪层**：
- 写在所有主流语言入门教程里 → 基础概念（A）。
- 写在该领域专门教程/章节里 → 进阶概念（B）。
- 在被分析仓库的源码里第一次出现、是该项目的独创取舍 → 设计决策（C）。

#### 过渡人话（按需使用，非强制）
- 「说人话就是…」「换句话说…」**只在讲完一个抽象的进阶概念或复杂权衡后用于浓缩**，
  每个进阶概念/权衡至多配 1 句。基础概念和已讲过的进阶概念不再配过渡句。
- 过渡句泛滥会形成「哄读者」语感，但该用的时候要用——不要为了「显得专业」而硬省。

#### 信息密度要求（硬约束，与「关键权衡」并列为产品核心）
- **每段技术陈述必须携带至少一个「读者看代码看不出来的信息」**：设计原因、边界条件、
  失败模式、历史坑、权衡代价、与朴素实现的差异。
- **纯机制复述要压到极简**：演示代码已演透「是什么」，正文不在「是什么」上铺陈。
  判断标准：删掉这段，读者看演示代码仍能理解机制 → 该段该删或压成一句。
- 注意：进阶概念的首次比喻讲解**不算**低密度复述，那是教学必需。

#### 动机段（按需长度）
- 「## 为什么需要它」用一句具体痛点钩子开场，长度依概念难度而定：基础机制 3～5 句，
  涉及多个进阶概念的复杂动机可适度展开，但仍**不要把使用场景铺成一整屏**。

#### 仍禁止的写法（防退化，但防退化 ≠ 强制通俗）
- 论文摘要腔：「一句话概括底层原语…」开场
- 源码行号 walkthrough：叙事主轴是「文件→符号→行号」
- 类型签名/重载罗列当主菜
- 反复念叨同一句抽象概括：每段都以「核心思想是…」收束
- 生硬抽象词堆砌：原语/载体/归一/收口/载荷/地基层（换成日常说法或删掉）
- **对基础概念（A 层）打比方**：如「把变量赋值想成给盒子贴标签」「把 if 想成十字路口」——这是啰嗦的典型
- **同一比喻反复展开**：首次讲透后，后续章节还把同一比喻重新铺成多行
```

#### 设计要点

- **保留**防退化条款(论文摘要腔、源码 walkthrough、类型罗列)——这些仍要防。
- **核心机制换成「概念分层」**:A 层(基础)直接用不比喻、B 层(进阶)首次配简短比喻+后续复用、C 层(设计决策)鼓励比喻+权衡三段。这取代了原先的「熟练程序员 + 比喻预算 ≤ 2」。
- **过渡人话从「预算硬约束」改为「按需」**:每个进阶概念/权衡至多配 1 句,不强制全章总数。
- **保留**信息密度要求(每段携带看代码看不出来的信息)——这点不随读者水平改变。
- 文件头注释(第 13 行)提到的「通俗化文风」同步改为「按概念分层的文风」。

### 改动 3:Critic 加第 7 条验收标准

#### 位置

```markdown
### ⑦ 概念分层与一致性（面向初级程序员读者）

读者是初级程序员：懂基本语法，但不必然熟悉该领域进阶概念。评审时按概念分层判定，

**reject 若出现以下任一：**

- **对基础概念打比方**：变量、函数、if/for、数组、对象、基本赋值等所有人懂的概念
  被配上比喻（如「把赋值想成给盒子贴标签」「把 if 想成十字路口」）。这是啰嗦的典型。
- **同一比喻反复展开**：某个进阶概念（如 effectScope、watcher）的比喻首次讲透后，

- **比喻展开成多行排比**：进阶概念首次该配比喻，但应压成 1~2 句点透，不要展开成
  4 行以上的排比清单。
- **低密度铺陈**：大段正文只是复述演示代码做了什么，没有补充设计原因/边界条件/失败模式/权衡代价。
  （注意：进阶概念的首次比喻讲解不算低密度复述。）

**允许（不扣分）：**
- 进阶概念（响应式、依赖注入、effectScope、AST、序列化、并发同步等）首次出现配 1 个简短比喻。
- 设计决策（本仓库特有取舍）配比喻 + 完整权衡三段。
- 每个进阶概念/复杂权衡配 1 句过渡人话（「说人话就是…」）。

**通过信号：** 比喻只出现在进阶概念（首次）和设计决策上；基础概念直接用术语；
每段技术陈述携带看代码看不出来的信息。
```

### 改动 4:A/B 验证

#### 验证方式

挑一章用新 prompt 重跑 Writer + Critic,对比 before/after。

**选章建议**:机制丰富、当前较啰嗦的(如 pinia 的 `$patch 与深度合并`、`Setup Store 构建器`)。

#### 验证指标

| 维度 | 指标 | 预期 |
| ---- | ---- | ---- |
| 篇幅 | 行数变化 | 降 20-35%(比旧预算温和,因为 B/C 层比喻要保留) |
| 基础概念比喻 | 对变量/函数/if/数组/赋值等 A 层概念是否打了比方 | **应为 0(硬约束)** |
| 进阶概念首次比喻 | effectScope/watcher/reactive 等 B 层概念首次出现是否配了简短比喻 | **应有(照顾初级读者)** |
| 比喻展开长度 | 单个比喻是否被压成 1~2 句 | **不应展开成 4 行以上排比** |
| 同一比喻复用 | 后续章节引用前章比喻时是否一句话带过 | **不应重新铺成多行** |
| 信息密度 | 抽样几段,检查是否每段都有"看代码看不出来的信息" | 提升 |
| 权衡完整度 | 关键权衡条数和篇幅(C 层设计决策) | **不能降(硬约束)** |
| 技术细节 | 硬货(边界条件、失败模式、历史坑) | **不能丢(硬约束)** |

#### 风险红线

如果压缩后出现以下任一,说明压过头了,回调:
- **权衡条数减少或技术细节丢失**(C 层硬货被砍)。
- **进阶概念首次出现没配比喻**(B 层没照顾到初级读者,退回"对初级太干")。
- **对基础概念反而开始打比方**(没抓准啰嗦的真正来源)。

正确状态:**A 层干、B 层首次润、C 层丰满**——三层各得其所。

### 改动 6:新增 `style-guide.md` + system prompt 注入

#### 动机

跨章一致性的信息(标题模板、命名规范、比喻库)**不属于任何单章,属于整个站点**。把它从 per-chapter 的 user prompt 抽出来,做成全站共享、固定的契约,通过 system prompt 注入每个 Writer。

#### 新建文件 `src/prompts/style-guide.md`(草案)

```markdown
# 全站文风契约（所有章节共享，内容固定，不随单章变化）

> 通用化，不绑定任何具体技术栈。

## 1. 章节骨架（标题用语义化短句，不编号——VitePress 右侧大纲会自动编号）

每章用以下小节（只改 {占位符}）：

# {概念名}：{一句话核心思想}

## 核心思想

## 心智模型

## 关键权衡

## 小结

## 2. 关键权衡小标题格式（全站统一）

### 权衡 N：{做了什么选择}

**做了什么**：...
**换来了**：...
**代价是什么**：...

- 用阿拉伯数字「权衡 1/2/3」，不用中文数字，不用 emoji，不用「(核心)」括注。
- 加粗小标题全站统一为「做了什么 / 换来了 / 代价是什么」。

## 3. 比喻库（首次引入后后续章节复用，不重新发明）

本项目反复用同一个抽象时（如「模块级全局变量当公共看板」「集中 state 当中心桶」），
首次出现的章节配比喻并记录在 outline.json 的 metaphors 字段；后续章节写「这块看板（第 N 章引入过）」即可。

> 规则：首次出现时配比喻，后续章节复用，不必重新打比方。

## 4. 开场钩子（每章统一）

- 「想象你在写…，某天你发现…」
- 「你刚接手…，结果…」

**禁止**定义式开场：「一句话概括底层原语…」「X 的本质是 Y」。
```

## 7. Before/After 对比示例(让效果直观)

拿 $patch 那章的「核心思想」段做实验。

**关键**:这里 watcher 静音对初级程序员属于 **B 层进阶概念**(不是所有人都熟 Vue 的 watcher 机制),所以修订后的版本**保留**一个比喻——但把它从 4 行排比**压成 1 句**点透。这印证了「概念分层」的核心:啰嗦的不是比喻本身,而是比喻被展开成多行排比。

### Before(现状,啰嗦版,约 14 行)

```
## 二、核心思想：先静音，再一次性通知

把 patch 窗口想成「开会时手机静音」：

- 进会议室前，先把手机调成静音（关掉监听开关）。
- 会议期间别人发你十条消息，你都没收到提示，但消息本身都正常到达（state 的值都改了）。
- 会议一结束，你打开手机，**只看到一条「有 10 条未读」的汇总通知**（手动触发一次订阅）。
- 半分钟后你恢复实时推送（异步监听在下一个 microtask 恢复）。

`$patch` 干的就是这件事。它用两个模块级开关控制监听状态：isListening（异步监听）和
isSyncListening（同步监听）。一进 patch 立刻都关掉，函数/对象两条路径任选其一改完 state 后，
**手动**调一次订阅触发，再把监听开关打开。
```

### After(目标,面向初级程序员 + 概念分层,约 6 行)

```
## 核心思想：暂停 watcher，改完手动触发一次

$patch 的核心是把「多次赋值」合并成「一次通知」。它用两个模块级开关 `isListening`
（异步监听）和 `isSyncListening`（同步监听）来「静音」Vue 的 watcher——说人话就是开会
时把手机调静音，会中十条消息都正常到达但不打扰你，散会后才看到一条「10 条未读」的汇总。
具体做法：进 $patch 立刻把两个开关置 false，mutator 改完 state 后手动 `triggerSubscriptions`
发一次通知，异步监听在 `nextTick` 恢复。

注意开关恢复的不对称：同步监听在手动触发前就开了，异步要等 microtask。这留下一个窗口——
patch 后立刻 `store.x = 1` 直改，异步订阅会丢一次事件（详见权衡 1）。
```

### 差异分析(为什么这版改对了)

- **比喻保留但压成 1 句**:watcher 是 B 层进阶概念,初级读者需要这个比喻;但 Before 版展开成 4 行排比就是啰嗦。After 版用「说人话就是开会时把手机调静音…」一句点透,既照顾初级读者又不冗长。
- **直接上开关名和函数名**:基础机制讲清后,术语(`isListening` / `triggerSubscriptions`)直接用——这部分对初级读者也不是障碍(配着比喻已点透),反而比 Before 版后半段的冗长复述更清晰。
- **保留非显然的边界**:把"不对称恢复 + 丢事件窗口"这个**看代码看不出来的硬货**提前点一句——这是所有读者(无论水平)都要的,删了就是损失。
- **字数从 14 行降到 6 行**,但 B 层比喻、C 层设计决策、信息密度三者都保住了。
