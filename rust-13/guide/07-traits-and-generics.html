Trait 与泛型：编译期单态化的静态多态 ​

本章属于 composite 层。前置：代数数据类型：枚举与穷尽模式匹配。 学完你能：用一句话讲清 trait 加泛型靠「编译期单态化」把多态变成零成本的直接调用，以及 Rust 为此付出的代价。

1. 为什么需要它 ​

想象你在写一个求最大值的函数。你希望它既能比整数、又能比字符串、又能比浮点，但又不愿意为每种类型把同一份逻辑 copy-paste 一遍。更麻烦的是，函数体里要用 > 来比较，可「并不是所有类型都能比大小」。在 JavaScript 里，这意味着你得等到运行时，某次调用传进来一个不能比较的东西，程序才当场崩掉；在 Java 那样的 OOP 语言里，你得把所有想复用的类型塞进同一条继承链，再用虚函数表跳转，每一次调用都额外绕一下。

这里同时卡着三件事：跨类型复用代码、零运行时开销、类型安全。传统方案里它们互相打架：继承多态牺牲性能，动态语言牺牲类型安全，C 的宏牺牲类型检查。Rust 换了个起点：把「一个类型具备什么能力」单独写成一份契约，让函数声明「我只接受具备这些能力的类型」，再把「能力到底满不满足」的检查整个搬到编译期。

上一章用 enum 配穷尽 match，对付的是「一个类型有多种形态、而且分支一条都不能漏」，那是数据的形状问题。本章换一条线：好几个互不相干的类型，想共用同一份行为。这两件事在 Rust 里是两条正交的轴线，所以别把「让非法状态不可表达」那份功劳记到 trait 头上。

2. 核心思想 ​

trait 把「能力」从继承链里拆出来，做成一张独立的契约；泛型配合 trait bound，在编译期为每一个具体类型单独复制一份专属代码。多态在编译期就被消解成了「几个直接调用」，运行时没有任何派发开销。

3. 心智模型 ​

把类型想象成求职者，trait 是一张「能力证书」。求职者不必来自同一家族（不需要继承链），只要考下这张证书就能上岗；函数门口挂块牌子「须持证上岗」，而证书真伪在你出门上班之前（编译期）就验完了，不用等到干活那天才发现谁滥竽充数。

整套流程是这样走的：

  1. 用 trait 声明一组方法签名，这就是证书上的考核项；方法可以只写签名，也可以顺手给个默认实现。
  2. 在某个具体类型上 impl Trait for Type，相当于去考这张证，把考核项真正填上。
  3. 写泛型函数 fn f<T: Trait>(x: T)，T: Trait 这个 bound 就是门口那块牌子。
  4. 编译器扫遍所有调用点，记下 T 实际被填进去了哪些具体类型。
  5. 单态化：为每一个具体类型复制一份专属的 f，把 T 全部替换掉。
  6. 在每个副本里，T 已经是具体类型，方法调用是静态直达的，编译器还能顺手把它内联。
  7. 运行时既不查类型、也不跳方法表，多态早在编译期就变成了好几个普通调用。

关键是第 5 步：bound 既是「允许谁进门」的闸门，也是「为谁复印一份」的依据，这两件事在同一次编译期检查里一起办完。

4. 关键权衡 ​

编译期复制换零运行时开销 ​

单态化换来的是：每一个副本都是直接调用，没有间接跳转，编译器还能针对这个具体类型把整段函数体重新优化、甚至整段内联进去。这是 Rust 敢把泛型叫「零成本抽象」的底气所在。

代价是实打实的。每多一个具体类型，就多一整个函数副本，二进制体积随之膨胀（一些项目实测有约 30% 的增长），编译时间也跟着涨，因为每个副本都得单独编译、单独优化。泛型参数一旦变多，副本数是乘法增长，膨胀可能在某条类型组合上突然爆发。

这里化解的本质矛盾，是**「极致性能」和「二进制体积 / 编译速度」**在抢同一块地：你想让每个类型都被照顾到最优，就得为每个类型单独花一份功夫，没有两全其美。

能力检查前移到编译期 ​

把 bound 做成编译期证明，换来的是运行时彻底不用查类型、不用查方法表。动态语言里「调了一个不存在的方法」要等程序真跑起来、走到那行才崩；Rust 把它前移成编译错误，这种错误根本进不了运行时。

代价落在写代码的人身上：泛型签名变复杂了，多个能力要拿 + 串起来，复杂约束还得另起 where 子句；而且「bound 不满足」时报出来的错误往往一长串，不直接指向你真正写错的地方。你换来的是「跑得起来就一定类型安全」，付的是「让它跑起来」这件事本身更费劲。

本质矛盾是**「编译期类型安全」和「签名简洁 / 报错友好」**：检查越往前做、做得越严，签名就越啰嗦，报错离第一现场也就越远。

能力与类型解耦换生态可组合 ​

Rust 的 impl 写在独立的 impl 块里，既不在 trait 定义里、也不在类型定义里。再配上一条孤儿规则：你只能为「trait 或类型至少有一个是本 crate 自己定义的」组合写 impl，不能给「外部的 trait 加外部的类型」实现。

换来的是 ad-hoc 多态：任何人都能为自己的类型实现任何能力，不需要拉继承链、不需要改原作者的代码。两个互不相识的 crate 能在第三个 crate 里无协调地拼到一起，这是 Rust 生态能做大的前提。换句话说，孤儿规则保证了「任意一个（类型, 能力）组合在整个生态里只有一份实现」，所以谁都不会撞车。

代价是这条规则也挡了你。想给标准库的 Vec 实现某个第三方 trait？不行，两个都是「外部的」。你得用 newtype 模式，把 Vec 包一层自己的新类型，再为新类型实现。另外，impl 块散落在各处，既不在类型旁边、也不在 trait 旁边，找实现得靠工具跳转。

本质矛盾是**「跨 crate 无协调地自由组合」和「局部想随便给外部类型加能力」**：为了保证全局唯一、不冲突，就得牺牲「我手上的外部类型想加什么就加什么」的局部自由。

关联类型还是泛型参数 ​

trait 里表达「某个附属类型」有两种写法。关联类型说「这份实现唯一确定一个类型」（一对一），比如迭代器产出的元素类型，一个迭代器只产出一种元素。泛型参数说「允许同一类型有多份实现」（一对多），比如 From<T>，一个类型可以从好几种 T 转换而来。

选关联类型，换来的是更简洁的签名：用这个 trait 的人不用每次都把那个附属类型再写一遍。代价是一个类型只能有一份实现、对应唯一一个关联类型，想表达「多种」就无能为力。这本质上是「输入参数还是输出参数」在类型层面的取舍：泛型参数像输入，由调用方指定；关联类型像输出，由实现方定死。

5. 最小原理演示 ​

这一节用 Rust 写主演示，因为「单态化」是 Rust 的语言特有语义，TS 演不了这半边。先看一份最小代码：

rust
// 能力契约：凡是能被总结的东西，都得会 summary 这一手
trait Summarize {
    fn summary(&self) -> String;
}

// 两个互不相关的类型，各自去考这张证
struct Article { title: String }
struct Product  { name: String }

impl Summarize for Article {
    fn summary(&self) -> String { format!("[文章] {}", self.title) }
}
impl Summarize for Product {
    fn summary(&self) -> String { format!("[商品] {}", self.name) }
}

// 泛型函数：T 必须持证（实现 Summarize），bound 是编译期闸门
fn print_summary<T: Summarize>(item: &T) {
    println!("{}", item.summary());
}

fn main() {
    let a = Article { title: String::from("学 Rust") };
    let p = Product  { name: String::from("机械键盘") };
    print_summary(&a);    // 调用点 1：T 被填成 Article
    print_summary(&p);    // 调用点 2：T 被填成 Product
    // print_summary(&42); // 取消注释：i32 没实现 Summarize，编译失败，根本进不了运行时
}

编译器扫到两个调用点，单态化之后，源码里那一个泛型 print_summary 会变成两份具体副本，T 被替换掉：

rust
// 单态化展开后的样子（伪代码，示意编译器的产物）
fn print_summary_Article(item: &Article) {
    // 这里的 summary() 是静态直达调用，能被内联进 println!
    println!("{}", Article::summary(item));
}
fn print_summary_Product(item: &Product) {
    println!("{}", Product::summary(item));
}
// 没有第三份：i32 那个调用在 bound 求解时就被拒了，连副本都不会生成

这就是「多态在编译期消解为多个直接调用」的本来面目。运行时 main 里的 print_summary(&a) 直接跳到 print_summary_Article，中间没有任何方法表。

那 TS 停在哪里？同样一份逻辑，TS 也能写出「能力契约 + 泛型约束」这半边：

ts
interface Summarize { summary(): string }
function printSummary<T extends Summarize>(item: T): void {
  console.log(item.summary())
}

但 TS 编译完会做类型擦除：整个程序里最后只剩一个 printSummary，所有类型信息都被抹掉。它把「能力约束留在类型层」这半边做得很好，可「为每个具体类型复制一份专属代码」这半边，TS 没有。TS 停下的地方，正是 Rust 继续往前的地方，这一段落差，就是单态化的全部价值所在。

6. 执行轨迹 ​

拿一个具体输入走一遍。源码里就是上面那个泛型 print_summary，调用点分别传入了 Article 和 Product。

  1. 扫描调用点：编译器在 main 里看到两处 print_summary，分别记下 T = Article 和 T = Product。
  2. bound 求解：查 Article: Summarize？有 impl，通过。查 Product: Summarize？也有，通过。两个都拿到了「持证上岗」的许可。
  3. 单态化：生成 print_summary::<Article> 与 print_summary::<Product> 两份副本，T 被替换成具体类型。
  4. 副本内优化：在每个副本里，item.summary() 已经是静态直达调用，编译器可以把它内联展开，甚至针对 Article / Product 的具体内存布局再做一轮优化。
  5. 运行时：print_summary(&a) 直接跳到 Article 那份副本，没有方法表查询，没有间接跳转。

反方向再看那行被注释掉的 print_summary(&42)：如果你真写出来，编译器在 bound 求解阶段查 i32: Summarize，找不到 impl，直接报编译错误。错误停在编译期，不会产出任何运行时代码，这就是 bound 作为「编译期闸门」的含义。

7. 教学简化说明 ​

本章演示故意省略了这些：需要异构集合或运行时多态时改用的 dyn Trait 与 vtable（那是动态派发的主题，本书后面会专门对照讲解）；关联类型带生命周期的 GATs、for<'a> 这类高阶 bound；编译器内部那个真正在判断 bound 满不满足的 trait solver；以及多 bound 用 + 串、where 子句、impl Trait 在参数位和返回位的全部语法变体。这些都不影响你理解「单态化为什么是零成本」。

8. 小结 ​

trait 把能力从继承链里解放出来，泛型再借单态化为每个类型复制一份专属的直接调用代码，多态在编译期就办妥了，运行时看到的就是几个普通调用。你为此付的是二进制体积、编译时间，以及更费劲的泛型签名。这套机制第一个重量级的客户马上就到：下一章的闭包，正是靠 Fn / FnMut / FnOnce 三个 trait，把所有权和借用的规则延伸到了函数式抽象上。
