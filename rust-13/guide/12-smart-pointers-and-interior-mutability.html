智能指针与内部可变性：借用规则的运行时逃生舱 ​

本章属于 composite 层。前置：「借用与引用：编译期的别名分析」「生命周期：编译期证明引用有效性」。 学完你能：讲清智能指针为什么存在。它把所有权和借用规则里编译器证明不了的部分，有代价地搬到运行期去执行。

上一章讲集合与迭代器，把「堆上动态数据 + 链式高阶表达」办成了零成本抽象。但那里的数据结构都默认一个前提：一个值只有一个主人。这件事把很多顺手的写法挡在了门外，本章就从这个挡路的口子讲起。

1. 为什么需要它 ​

想象你在写一个图。两个图节点要互相持有对方，才能表达「A 的邻居是 B，B 的邻居也是 A」。按所有权规则，A 属于谁？B 又属于谁？一个值只能有一个主人，可这里两个节点天然地要「共同拥有」彼此。

再想象一个 GUI：按钮被点击时要去改它注册的某个观察者列表，而这个列表又被多个组件共享。到底谁能改、什么时候改，要等到运行期点了按钮才知道。

这都是同一类麻烦：一个数据需要被多方共享，而且要在共享的状态下被修改。可前面学过的所有权、借用、生命周期这几条编译期铁律，在这里直接顶牛：

  • 「一个值只有一个主人」，挡住了「多方共同拥有」；
  • 「要么一个可变借用，要么多个不可变借用，二者不能并存」，挡住了「拿到共享引用还想改」；
  • 「引用不能比被引用者活得久」，要求这套共享关系能在编译期用签名证明清楚。

问题不在于这些写法错了，它们逻辑上完全合法。问题在于编译器没办法在编译期静态推断出它们的合法性：图节点之间的环状引用、回调在运行期才触发的修改，都不是盯着源码看几眼就能证明清楚的。

于是 Rust 给这类场景开了一扇逃生舱：既然编译期证明不了，那就承认「这里要付一点运行时的代价」，换回表达能力。这扇舱门，就是智能指针。

2. 核心思想 ​

把所有权与借用规则里「编译器证明不了」的那一部分，从编译期搬到运行期去执行。

所有权要证明「谁是唯一主人」、借用要证明「此刻的借用会不会冲突」、生命周期要证明「引用会不会悬垂」。这三件事里凡是编译期摆不平的，智能指针就提供一个运行期机制替你兜住：用一份计数替你管「到底有几个主人、最后谁负责释放」，用一份运行期的借用状态检查替你管「现在到底能不能借」。代价写在类型名上，由你按需开启。

注意这是「搬家」，不是「废除」。借用规则没消失，只是换了个时间点执行；所有权也没消失，只是「唯一主人」放宽成了「计数决定的集体所有」。

3. 心智模型 ​

智能指针有两套正交的维度，套在一起就能覆盖绝大多数场景。

所有权维度，这个值有几个主人？

  • 只有一个主人：Box<T>。把值塞进堆上，自己独占，是堆分配和单一所有权的基线。它还有个独家本领：让递归类型能编译。enum List { Cons(i32, List), Nil } 因为大小无限递归算不出来，写成 Cons(i32, Box<List>) 后，那一格固定成一个指针大小，递归就被打断了。
  • 多个主人：Rc<T>（单线程）或 Arc<T>（多线程）。

引用计数的画面很好记：像合租公寓的门禁卡。搬进来发一张，clone 再发一张，每张都指向同一把锁；谁出门 drop 一次就少一人，最后一个人刷卡出门，公寓才真正断电退租。clone 不复制数据，只给计数器加一。

可变性维度，拿到共享引用后，要不要能改内部值？

  • 不需要改：什么都不用加，Rc<T> / Arc<T> 默认就是只读的共享。
  • 需要改：再套一层「内部可变性」。单线程用 RefCell<T>，多线程用 Mutex<T>（写互斥）或 RwLock<T>（读多写少）。

两个维度正交，拼出四个经典落点：

单线程多线程
单主人Box<T>Box<T>（所有权 move 过去）
多主人 · 只读Rc<T>Arc<T>
多主人 · 可变Rc<RefCell<T>>Arc<Mutex<T>>

Rc<RefCell<T>> 是图、树、观察者列表的标配；Arc<Mutex<T>> 是并发共享状态的事实标准。

撑起所有智能指针的还有两件事：Deref 让它们能像普通引用一样被解引用、自动链式解引用调方法，所以你写 rc.method() 时感觉不到中间隔了一层指针；Drop 让作用域结束时自动跑析构。这俩合起来，才是它们「智能」的来源。

最后点透一件事：到底是谁决定一个值何时回收？Box 由唯一主人离场决定；Rc / Arc 由计数归零决定，跟生命周期签名无关了；而 RefCell / Mutex 决定的是「现在能不能借」，根本不插手回收时机。这一步分清，就看清了「运行期化」到底化了什么。

4. 关键权衡 ​

用引用计数换「一个值多个主人」 ​

选 Rc / Arc：多方各自持有一份句柄，clone 增计数、drop 减计数，计数归零才真正释放数据。换来的是「所有权唯一」这条硬约束被绕开，一个值终于名正言顺地有了多个主人。

代价分两层。一层是每次 clone 和 drop 都要改计数，Arc 更狠，因为计数本身得是原子操作，跨核同步的成本不便宜。另一层更阴险：一旦几个 Rc 互相强引用围成一圈，环上每个计数都至少为一，永远降不下来，析构永远不触发，等于内存泄漏。所以共享所有权不是拿来就完事，还得手动用 Weak 弱引用去「打环」。

这里化解的本质矛盾，是「逻辑上一个数据属于多方」和「物理上必须有个明确的回收时机」之间的冲突。引用计数把这个冲突显式化成了「谁持卡、谁退卡、最后谁断电」的协议。

用内部可变性换「拿到只读引用也能改值」 ​

选 RefCell / Mutex：你手里明明只有个不可变引用，却能改它内部包着的值。换来的是 Rust 默认那堵「不可变引用指向的值动不得」的墙被凿开一个口子，让 Rc 这种共享句柄真正能配合上「可变」，Rc<RefCell<T>> 才拼得出来。

代价是借用规则那套检查被推迟到了运行期。一旦违约，比如同一个 RefCell 已经被可变借用了你还想再借，就不再是编译器温柔地报错，而是程序直接 panic。Mutex 换到多线程，违约的代价则变成死锁或锁中毒。而且 RefCell 是单线程的：它的借用状态不是原子量，没法跨线程共享。换句话说，这扇逃生舱的代价，正是你原本想逃避的那条规则，只不过现在由运行时用更激烈的方式替你执行。

它戳中的本质矛盾，是「外部看是不可变」和「内部确实需要变」之间的张力。观察者列表、缓存、图节点，全都卡在这道缝上。

用确定性析构换可预测的回收 ​

智能指针靠 Drop trait 在作用域结束那一刻确定性回收，主人一走，资源立刻释放。换来的是可预测的性能：什么时候释放、按什么顺序释放，都摆在明面上，不像带 GC 的语言那样要等一个不可预测的停顿。

代价是确定性析构救不了循环引用。前面说过，Rc 围成的环计数永不归零，析构永远不触发。这件事恰好卡在「确定性的那一刻」上：析构本身是确定的，但它只由计数触发，环上的计数又下不来，于是这套完美可预测的机制在环面前束手无策。这其实是 Rust 内存安全保证的一条真实边界：它保证不 double-free、不 use-after-free、不数据竞争，但从没保证过「不会泄漏」。检测循环的代价太高，Rust 选择把泄漏留给程序员，用 Weak 自己处理。

这里真正的取舍，是「要可预测地回收」和「只有 GC 才能自动收拾环」之间。Rust 用确定性换走了 GC 的不可预测，代价是用人工契约补上环这一块。

让「代价」写在类型名上，从隐式变显式 ​

这一条不是某个具体指针的取舍，而是 Rust 整体的设计立场：把智能指针当成「零成本抽象的自觉例外」。在 JS 里，对象默认就在堆上、默认就被引用共享、改它天经地义，所有运行时代价都藏在 GC 背后，你看不见。Rust 反过来，凡是要付运行时代价的地方，类型名上就明明白白写着：Rc 写着「我在计数」，Arc 写着「我在做原子计数」，RefCell 写着「我在运行期查借用」，Mutex 写着「我在加锁」。

代价是学习负担前移。你不能像 JS 那样「能 clone 就 clone」一招吃遍天，而要在「这里该上 Rc<RefCell<T>> 还是 Arc<Mutex<T>>」之间，学会按所有权维度和线程维度做选择题。但回报是，读代码的人只要看到类型名，就知道这一处花了什么代价、承担了什么风险。

5. 最小原理演示 ​

下面用 TypeScript 从零搭一个最小的 Rc 和 RefCell，再把它们拼成 Rc<RefCell<T>>。JS 本来就有 GC，并不需要这套东西，这反而成了最好的教学对照：亲手写一遍计数和借用状态，你才会真切感到，在没有 GC 的世界里，共享所有权和可变性都得靠显式机制管起来。

ts
// 内部盒子：真正的数据 + 共享计数
class RcBox<T> {
  value: T
  strong: number
  constructor(value: T) {
    this.value = value
    this.strong = 1          // 出生即有一名主人
  }
}

class Rc<T> {
  private constructor(public box: RcBox<T>) {}

  static new<T>(value: T): Rc<T> {
    return new Rc(new RcBox(value))
  }

  // 共享所有权：clone 只给计数器加一，绝不复制 value
  clone(): Rc<T> {
    this.box.strong += 1
    return new Rc(this.box)   // 新句柄指向同一个 box
  }

  // 模拟 Drop：每个句柄离场时减一，归零才真正释放
  drop(): boolean {
    this.box.strong -= 1
    if (this.box.strong === 0) {
      // 无 GC 的世界里，这一步是显式的资源回收
      return true
    }
    return false
  }
}

Rc 的全部秘密，就在 clone 和 drop 各加减一次计数上。下面是 RefCell：

ts
class RefCell<T> {
  private value: T
  // 借用状态：>0 是 N 个不可变借用，-1 是 1 个可变借用，0 是空闲
  private state = 0

  constructor(value: T) { this.value = value }

  // 不可变借用：只要当前没有可变借用就放行
  borrow(): T {
    if (this.state < 0) throw Error("已被可变借用，不能同时不可变借")
    this.state += 1
    return this.value
  }

  // 可变借用：必须独占，任何其他活跃借用都不行
  borrowMut(): T {
    if (this.state !== 0) throw Error("已有活跃借用，不能可变借")
    this.state = -1
    return this.value
  }

  // 守卫离开作用域时把借用还回去（真实 Rust 由 Ref/RefMut 的 Drop 自动做）
  releaseImmutable() { this.state -= 1 }
  releaseMutable() { this.state = 0 }
}

borrowMut 里那两个 throw，就是借用检查被搬到运行期的全部含义：编译期放你过，运行期一旦违约就 panic。最后把两层套起来，得到「多主人 + 可变」的等价物：

ts
// 两个主人共享同一份 RefCell，而且都能改里面的值
const shared = Rc.new(RefCell.new({ count: 0 }))

const ownerA = shared
const ownerB = shared.clone()          // strong: 1 -> 2

// 外部只握着不可变的 Rc 句柄，内部值却被改了：内部可变性的落点
const inner = ownerB.box.value.borrowMut()
inner.count = 42
ownerB.box.value.releaseMutable()

ownerA.drop()                          // strong: 2 -> 1，数据还在
ownerB.drop()                          // strong: 1 -> 0，此刻才真正释放

外部明明只持有不可变的 Rc 句柄，内部值却被改了，这就是「内部可变性」四个字的落点。

6. 执行轨迹 ​

来看引用计数到底怎么决定回收时机。三个图节点 A → B → C：A 强引用 B，B 强引用 C，C 反过来又指回 A。一开始外部持有 A 的一个强引用。

第一幕：C → A 用强引用，围成环。

初始计数：A 的 strong = 2（外部一个、C 一个），B 的 strong = 1（A 持着），C 的 strong = 1（B 持着）。

外部释放对 A 的最后一个强引用：A 的 strong 从 2 降到 1。因为 C 还持着 A，A 没归零，不析构。于是 A 不释放它对 B 的强引用，B 的 strong 还停在 1，B 也不析构。B 不析构，就不释放对 C 的强引用，C 的 strong 还停在 1。C 还活着，就继续持着 A。整条环谁都不动，三个节点的计数全是 1，谁也降不到 0：内存泄漏。数据明明没人再用，却永远释放不掉。

第二幕：把 C → A 换成 Weak 弱引用。

初始计数变了：A 的 strong = 1（只有外部），B 的 strong = 1，C 的 strong = 1。C 指回 A 用的是弱引用，不给 A 的 strong 加一。

外部释放 A：A 的 strong 从 1 降到 0，归零，析构 A。析构 A 的字段时，释放 A 对 B 的强引用，B 的 strong 降到 0，析构 B。析构 B 时释放 B 对 C 的强引用，C 的 strong 降到 0，析构 C。C 身上那个指向 A 的弱引用不阻止任何事，因为它从一开始就不进 strong 计数。整条链一路析构到底，泄漏消除。

关键就在 Weak 不增 strong 计数这一条：它让「反向边」不参与决定存活，于是正向那条所有权链能干净地从头拆到尾。

7. 教学简化说明 ​

本章演示故意省略了不少东西：Weak 弱引用的完整语义（它另有 weak 计数，释放分两阶段）、Arc 用原子操作维护计数、Cell 与 RefCell 的细粒度区别（Cell 只给 Copy 类型、整体替换、没有借用检查）、Mutex 的锁中毒机制、Deref 自动解引用链能跳几跳。这些要么属于后续的并发章，要么是工程细节，不影响你看懂「计数管共享、运行时检查管可变」这条主线。

8. 小结 ​

智能指针不是 Rust 的补丁，而是它对「编译期证明有边界」这件事的诚实承认：证明不了的部分，就用计数和运行时检查顶上，代价摆在类型名里让你自选。所以遇到图、回调、缓存这类多方共享的场景，你不必再和借用检查器死磕，而是问自己三个问题：几个主人、几个线程、要不要改。三个答案一拼，该用哪个指针就清楚了。

到目前为止，我们改写代码都还在运行期里打转。下一章要跨到编译期另一侧的利器：宏系统，看 Rust 怎么在编译期生成代码，做出类型系统够不着的抽象。
