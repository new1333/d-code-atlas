模块、Crate 与 Cargo：工程组织与标准化工具链 ​

本章属于 system 层。前置：Rust 的设计哲学与编译模型总览。 学完你能：讲清 Rust 为什么把「代码组织、编译单元、工程发布」切成三层正交抽象，以及它靠强约定换来零配置体验的同时，在显式挂载、约定布局、SemVer 依赖、edition 这几处各付了什么代价。

1. 为什么需要它 ​

上一章把 async 函数拆成了"编译器生成的状态机 + 可选的外部运行时"。你可能已经感觉到，Rust 的语言机制越往深里走，精细度越高：所有权、借用、生命周期、Future 状态机……但这些机制最终都得装进一个个能编译、能测试、能发布给别人用的工程单元里。问题是：一个几百个文件、几十个第三方依赖的项目，怎么组织才不会乱？

如果是前端，你大概已经习惯了这种碎片化：package.json 管依赖、tsconfig.json 管类型、vite.config.ts 管打包、.eslintrc 管风格，CI 里还得再拼一套构建脚本；改一个文件的位置，牵动一堆 import 路径；每个库还各自定义"怎么构建、怎么测试、怎么发布"。Rust 工程师面对同样规模的项目，往往只打开一个清单文件，一条命令就完成构建、测试、跑文档、发布；新机器 clone 下来，一条命令全量编译。

这份"省心"不是偶然。它源于一个更底层的需求：要让编译期的静态检查（借用检查、单态化）在工程规模下依然可控，编译器必须有一个明确的"作用域边界"，它得知道"这一堆代码是一个整体，借用检查在这个范围内完成，单态化生成的代码也在这个范围内链接"。这个边界就是 crate。围绕这个边界，Rust 向下拆出 module（管代码怎么分组、谁看得见谁），向上拆出 package（管一组 crate 怎么一起发布、依赖怎么管版本）。

第 1 章已经把"Cargo/rustc 提前编译 + 借用检查"的心智总图立起来了，本章不再重讲"为什么要编译期"，而是换一个侧面：编译单元的边界怎么定、代码怎么组织进这个边界、工程怎么围绕它标准化。

2. 核心思想 ​

把「代码组织（module）、编译单元（crate）、工程发布（package）」拆成三个正交的层，每层只管一件事；再用一套强约定，让构建工具对其中两层几乎零配置。

打个比方点透这三层：module 是你抽屉里分门别类的文件夹（只管"东西怎么归类、谁能拿"），crate 是出厂时装订好的一整本书（一个完整的编译单元，借用检查就在这本书的封皮内完成），package 则是上架销售的一个产品 SKU（带版本号、带依赖清单、能被别人一条命令装走）。三层各管一段，互不越界。

3. 心智模型 ​

先记住三条边界谁管什么：

  • module（语言级，编译器管）：crate 内部的命名空间分组，管两件事——代码怎么分组、谁看得见谁（可见性）。一个 crate 里的所有 module 构成一棵以 crate 根为顶点的树。
  • crate（语言级，编译器管）：编译器的最小独立编译单位，分库 crate 和二进制 crate 两类，编译后各产生一个产物（库中间件或可执行文件）。借用检查、单态化都以 crate 为作用域，这正是它作为"编译单元"的字面含义。
  • package（工具级，构建工具管）：由一个清单文件定义、包含一个或多个 crate 的发布单元。关键一句：编译器本身不认识 package，它纯粹是构建工具的概念。一个 package 最多含一个库 crate，但可以含任意多个二进制 crate。

模块树怎么长出来？从 crate 根源文件出发，编译器每遇到一行模块声明（mod foo;），就按约定的文件查找规则找到 foo 的源码，把它挂为当前模块的子节点，然后递归进入 foo 重复这个过程。挂上去之后，pub 决定哪些项能被别的模块看见（默认私有），use 只是给一条已经存在的长路径起个短别名——它不创建模块，也不绕过可见性。

这套机制能让构建"零配置"，是因为构建工具认死了几个固定位置：src/lib.rs 就是库 crate 根、src/main.rs 就是默认二进制 crate 根、src/bin/ 下每个文件都是一个额外二进制、tests/ 放集成测试、benches/ 放基准、examples/ 放示例、target/ 放产物。不必在清单里罗列源文件，工具自己会找。

4. 关键权衡 ​

这一节是全章重点。Rust 在工程组织上的几乎每一个设计决定，都是"显式换可控"这个一贯取舍的延伸。

模块靠挂载登记，不靠文件名自动生效 ​

Node 的世界里，建一个 foo.js，别处 require('./foo') 立刻能用——文件存在就等于模块可见。Rust 偏不。你建了 tcp.rs，只要它的父模块里没写 mod tcp;，编译器就当这个文件不存在：tcp 根本不在模块树里。

这是初学者撞墙第一名的问题："我明明建了文件，为什么编译器说找不到？"Rust 为什么宁肯让新手吃苦头也要这么设计？因为它选的是"模块树和文件系统解耦"：模块的逻辑结构必须能从 crate 根一眼推读出来，而不必去翻磁盘上文件怎么摆。

换来的是：你可以重构文件位置（把 foo.rs 挪进 foo/ 目录）而不动任何导入路径；可见性能精确推理（看一行 mod 就知道这棵子树被挂上来了）；背后没有任何隐式魔法帮你解析。代价是每个子模块要多写一行挂载声明，且这条"文件存在不等于出生"的规则跟大多数语言的直觉相反，这是 Rust 为"显式换可控"付的学费。

这条权衡化解的本质矛盾，是**"逻辑组织想独立于物理摆放"和"工具想自动发现代码"**之间的冲突。Node 选了后者（自动发现，但逻辑被文件位置绑架），Rust 选了前者（逻辑独立，但要你手动登记）。

约定死一套布局，换全生态同一套工程词汇 ​

构建工具本可以让你自由配置"入口在哪、测试在哪、产物放哪"。Rust 选择把这套全锁死成固定约定：固定入口代表二进制、固定入口代表库、固定目录放测试/基准/示例、固定目录放产物。

换来的是真正的"开箱即用"：构建、测试、运行、生成文档、发布，五条命令全生态统一；你 clone 任何一个陌生 Rust 项目，不必读它的构建脚本，cargo build 就是能跑；整个生态共享同一套工程词汇，换个项目零迁移成本。代价是灵活性受限：想深度定制构建流程，你得写构建脚本（build.rs），甚至干脆绕过这套工具；偏离约定就会处处碰壁，工具不会迁就你的特殊偏好。

说人话就是，Rust 宁可让少数需要深度定制的人去写脚本，也要让绝大多数项目共享同一套零配置体验。它本质上化解的是**"个体的特殊灵活性"和"生态的统一性"**之争——Rust 一贯把秤砣压在生态统一这一侧。

依赖按 SemVer 兼容解析，但用锁文件分两种策略 ​

在清单里写 version = "1.2.3"，在 Rust 里它等价于 ^1.2.3，意思是允许兼容范围内的自动升级（>=1.2.3, <2.0.0）。这跟某些 JS 包管理器"手写裸版本号就是精确锁定"正好相反：Rust 的裸版本号默认就是兼容范围。同时，构建工具用一个锁文件把这个范围解析出的具体版本钉死。

这里有个常踩的坑：在 0.x 阶段，SemVer 把 minor 当成破坏性变更（^0.3.0 只允许 >=0.3.0, <0.4.0），新手常因此困惑"明明只升了一个 minor 怎么升不动"。

更妙的是锁文件策略的二选一惯例：二进制 crate 提交锁文件以保证可复现构建，库 crate 不提交——下游根本不会用你的锁文件，发布时它还会被自动剥离。换来的是两边都照顾到了：库生态能平滑演进，下游自动获得兼容修复；应用构建又能精确复现。代价是开发者必须理解 SemVer 契约（主版本号递增就是破坏性变更），库作者一旦违约会波及整个下游，而且 patch 升级偶尔会引入未预期的行为变化。

它化解的是**"生态想平滑演进"和"构建想精确复现"**这对矛盾：用一个范围解析加一个锁文件钉死，再配上"库不锁、二进制锁"的分工，把两个对立需求都安顿了。

edition 让语言能进化，又不撕裂生态 ​

语言总要往前走，但任何破坏性变更都会让生态痛苦。Rust 的解法是 edition：每隔约三年发一个（已有 2015、2018、2021、2024），允许语言做小幅不向后兼容的演进，但以单个 crate 为单位可选启用。

最关键的性质是：同一依赖树里不同 crate 用不同 edition 能无缝互操作，可以任意顺序逐个迁移。语言因此能持续进化，既不像某些老语言那样背着历史包袱寸步难行，也不像某些语言的大版本切换那样撕裂整个生态、强迫所有依赖同步升级。代价是读者要多一个"edition"概念，偶尔会遇到 edition 特有的语义差异（比如未声明 edition 默认回退到 2015，而不是最新版），迁移时要用专门的工具按 crate 独立升级。

它化解的是**"语言核心想保持稳定以兼容旧生态"和"语言想持续清理历史包袱"**之争，edition 用"可选启用的兼容层"把这两个对立需求拆开了。

5. 最小原理演示 ​

下面用几十行 TS 演透本章的灵魂：文件存在 ≠ 模块可见，必须先挂载、再标记公开，才能被路径解析到。每一行都对应上面某个原理点：挂载是模块树的父子边，可见性是跨边界过滤，路径解析是沿树下行。

ts
type Visibility = "private" | "pub";

// 一个源码文件：它声明了哪些子模块（挂载），定义了哪些项（带可见性）
interface SourceFile {
  declares: string[];                          // 形如 mod tcp; 把子模块挂到树上
  items: { name: string; vis: Visibility }[];  // 本文件定义的函数/类型
}

// 模拟磁盘上的源码。tcp.rs 躺在磁盘上，但 network 没有声明它
const disk: Record<string, SourceFile> = {
  root:    { declares: ["network"], items: [] },
  network: { declares: [],         items: [{ name: "connect", vis: "pub" }] }, // 故意漏掉 declares: ["tcp"]
  tcp:     { declares: [],         items: [{ name: "connect", vis: "pub" }] },
};

interface Module {
  name: string;
  children: Map<string, Module>;
  items: Map<string, Visibility>;
}
const makeModule = (name: string): Module => ({ name, children: new Map(), items: new Map() });

// 从根源码出发长出整棵模块树。
// 灵魂在这：只挂载 declares 里点名的子模块，磁盘上有但没登记的根本不进树
function grow(parent: Module) {
  const file = disk[parent.name];
  if (!file) throw Error(`找不到源码：${parent.name}`);
  for (const it of file.items) parent.items.set(it.name, it.vis);
  for (const childName of file.declares) {       // 只有被声明的子模块才会被挂上
    const child = makeModule(childName);
    parent.children.set(childName, child);
    grow(child);                                  // 递归进入子模块继续长
  }
}

// 沿模块树下行解析路径，跨模块边界时做可见性过滤
function resolve(root: Module, path: string[]) {
  let cur: Module = root;                         // path 形如 ["network", "tcp", "connect"]
  for (let i = 0; i < path.length - 1; i++) {
    const next = cur.children.get(path[i]);
    if (!next) throw Error(`找不到模块 ${path[i]}（提示：需要在 ${cur.name} 里写 mod ${path[i]};）`);
    cur = next;
  }
  const last = path[path.length - 1];
  const vis = cur.items.get(last);
  if (!vis) throw Error(`找不到项 ${last}`);
  if (vis !== "pub") throw Error(`${last} 是私有的，跨模块不可见`);
  return last;
}

const root = makeModule("root");
grow(root);
try {
  resolve(root, ["network", "tcp", "connect"]);   // 失败：network 没挂载 tcp
} catch (e) {
  console.log((e as Error).message);
  // → 找不到模块 tcp（提示：需要在 network 里写 mod tcp;）
}
// 修复：给 network 的 declares 加上 "tcp"，再 grow 一次，路径就通了

跑完你会看到一个具象的结果：磁盘上的 tcp.rs 是死的，模块树是活的，唯一让 tcp "出生"的动作是 network 里那行挂载声明。

6. 执行轨迹 ​

拿一个具体例子走一遍，看构建工具和编译器怎么配合，把一个 package 变成可执行文件。

输入：一个 package，清单里声明了名字、edition、一个外部依赖 serde = "1.0"；二进制根 main.rs 里写：挂载 network 模块，然后调用 network::tcp::connect()——但 network 里漏写了 mod tcp;。

第 1 步（构建工具）：读清单，把 serde = "1.0" 按 caret 解析成兼容范围，读锁文件锁定一个具体版本（比如 1.0.210），定位到二进制 crate 根 src/main.rs，把它交给编译器。

第 2 步（编译器建树）：从 main.rs 出发长模块树。mod network; 成功，network 挂上来了；但 network 内没有 mod tcp;，所以 tcp 根本不在树里，尽管它的源文件正躺在磁盘上。这一步是全章灵魂的具象化：文件存在不等于模块出生。

第 3 步（路径解析）：编译器解析 network::tcp::connect，走到 network 后找不到子模块 tcp，报错"找不到模块 tcp（提示：需要声明 mod tcp;）"。

输出：你在 network 里补上 mod tcp;，树完整了，tcp::connect 即使跨了模块边界，因为它标了 pub，可见性检查通过，编译通过，链接成可执行文件写进 target/。

从这条轨迹带走一句话：磁盘文件是死的，模块树是活的，唯一让子代码"出生"的动作是父模块里那行挂载声明。

7. 教学简化说明 ​

本章演示故意省略了一堆工程化细节：edition 迁移的具体步骤、workspace 多 crate 编排、构建脚本 build.rs 的执行时机、feature flag 条件编译、锁文件的精确格式、注册表发布流程、路径前缀 self/super 的枚举、pub(in path) 这类可见性细分。它们都是"配置"层面的产物，不是原理——原理就是那三层切分加显式挂载这一件事。

8. 小结 ​

Rust 的工程省心，是用"把 module、crate、package 切成三个正交层，再用一套死约定锁住布局"换来的：编译器拿到一个明确的编译单元边界去做借用检查，构建工具靠固定约定省掉所有配置，开发者用一行 mod 声明换对模块结构的精确掌控。代价是"显式"本身——多写声明、按约定办事、理解 SemVer 与 edition。下一章我们会看到 Rust 安全保证的最后一道口子：当编译期证明力不够用、必须碰裸指针或调 C 时，unsafe 怎么把危险收缩到最小、可审计的区域。
