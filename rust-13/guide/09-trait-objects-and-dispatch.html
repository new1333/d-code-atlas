动态派发：dyn Trait 与 vtable ​

本章属于 composite 层。前置：Trait 与泛型（编译期单态化）、生命周期（编译期证明引用有效性）。 学完你能：用一句话讲清「为什么同一份 trait 契约要有静态、动态两种兑现方式，以及动态派发用一次间接调用换来了什么、付了什么代价」。

1. 为什么需要它 ​

上一章讲了闭包按捕获方式被归为 Fn/FnMut/FnOnce 三类 trait，把闭包也收进了 trait 契约的世界。这马上引出一个非常现实的需求：把一堆不同的闭包（点击回调、键盘回调、定时回调……）塞进同一个集合统一调用，比如一个事件总线。

可你一试就会发现，第 7 章的泛型 + trait bound 这条路在这里撞了墙。泛型集合 Vec<T> 的元素类型必须唯一；单态化要求编译期就把所有具体类型枚举穷尽。一个想把 Button、TextBox、Panel 三种 GUI 控件混在一起统一 redraw 的控件树，或者一个想把多种 AST 节点放进同一个 Vec 求值的解析器，都过不了这一关。

单态化在两类场景下束手无策：

  • 异构集合：一个容器要装好几种不同类型，统一调用它们共有的方法；
  • 开放扩展：调用方在编译期根本不知道实现者是谁——插件系统、依赖注入、用户注册的回调，具体类型是运行时才确定的。

使用者真正想要的是一种「只认能力契约、不认具体身份」的多态。Rust 给的另一条路，就是 dyn Trait。

2. 核心思想 ​

把具体类型擦除成只剩 trait 契约的 trait 对象，用一张方法分发表（vtable）在运行时按具体类型找回正确的实现，以一次间接调用换取异构多态。

打个比方：trait 对象像一张「只写职务、不写姓名」的派工单，你只知道「要找个会画图的人」，到底是 Button 还是 Circle 已经被擦掉了；vtable 就是那本「职务到真人」的花名册，运行时按职务查出该派谁去。

3. 心智模型 ​

从一段最普通的 trait 定义开始：定义一个 Draw，声明 fn draw(&self)，再给 Button、Circle 两个具体类型各自实现它。到这一步，和第 7 章没区别。

差异从「类型擦除」开始。把一个 Button 强制转换（coercion）成 trait 对象后，编译器只记得「它实现了 Draw」，忘了它原本是 Button。可擦除后的 dyn Draw 在编译期不知道自己多大（不同实现者大小不一），是 Rust 里的动态大小类型（DST）。DST 不能直接按值放进变量，也不能当泛型 T 默认要求的 Sized。它必须藏在一根指针背后：借用就写 &dyn Draw，拥有就写 Box<dyn Draw>。

这根指针因此「长胖」了。普通引用是一个字（一个地址），而指向 trait 对象的指针是胖指针，两个字宽（64 位机上 16 字节）：

  • 第 1 个字：指向堆上的真实数据；
  • 第 2 个字：指向一张 vtable。

编译器为每一个「(具体类型, trait)」组合静态生成一张全局 vtable。(Button, Draw) 一张，(Circle, Draw) 另一张。表里装着该类型实现该 trait 的各方法的函数指针，外加这个类型的布局信息：析构函数指针、大小、对齐。

调用 item.draw() 时，编译器不再生成「直接跳到 Button::draw」的指令，而是从胖指针第 2 字取出 vtable 地址，在表里找到 draw 槽位，拿到函数指针，再以第 1 个字（数据地址）作为 self 做一次间接调用。于是 Vec<Box<dyn Draw>> 里每个元素的胖指针可以指向不同的 vtable、不同的具体类型——这就是运行时多态，正是第 7 章单态化给不了的能力。

承第 4 章的生命周期：trait 对象既然藏在指针背后，它内部如果还借了别人的数据，老问题一样存在，引用不能比被引用者活得久。所以 dyn Trait 自带一个可省略的生命周期，写成 dyn Trait + 'a。常见的坑是裸写 Box<dyn Trait> 会被默认推断成 Box<dyn Trait + 'static>（因为没有别的输入生命周期可借）；如果 trait 对象里装的是借用数据，就得显式写 + 'a 或 + '_ 把它翻回来。这是生命周期机制在「擦除类型的胖指针」上的延伸，原理第 4 章已讲透，这里只看新冒出来的约束。

4. 关键权衡 ​

擦掉身份只留能力，换来异构多态——代价是丢掉编译期的具体类型信息 ​

这是动态派发的根本交易。把 Button 擦成 dyn Draw，换来的是 Vec<Box<dyn Draw>> 能装任意实现了 Draw 的类型、能跨编译期边界传递（插件、动态加载）。代价落在三处：trait 必须对象安全；调用无法被编译器内联；每次调用多一次 vtable 查找加间接跳转。

对象安全这条最容易踩坑，值得展开。vtable 是「每个具体类型一张表」，但通过 dyn 调用时调用方只知道 trait、不知道具体类型。于是凡是「需要编译期就知道具体 Self」的方法都塞不进单一 vtable：泛型方法要在调用点按类型参数实例化，实例有无穷多个，一张表装不下；按值返回 Self 要求编译期知道返回值大小；按值 self 要求知道大小才能压栈。这些方法在类型已擦除的前提下根本生不成统一调用序列，所以 Rust 干脆禁止用 dyn 调它们。实践中常用的补救是给个别违规方法加 where Self: Sized，让它不进 vtable、不能走 dyn 调用，但 trait 整体恢复对象安全。

这条权衡化解的本质矛盾，是「想要开放、异构的集合」与「编译期必须知道全部具体类型」之间的冲突——动态派发用「把具体类型藏到运行时」把这对立掰开了。

只留一份代码，换来更小的体积与更快的编译——代价是每次调用的运行时开销 ​

单态化为每个具体类型复制一份方法代码；动态派发只生成一份。所以用 dyn 的代码编译更快、二进制更小。代价是这「一份代码」必须在运行时通过查表才知道跳到哪个实现，静态派发的「编译期直接跳转、零运行时开销」在这里变成了「一次间接调用」。

本质矛盾是「代码膨胀（每类型一份）」与「运行时查表开销」二选一，动态派发选了后者。（「单态化换极致性能、代价是代码膨胀与编译时间」这条已在第 7 章讲透，这里只看它的镜像。）

静态派发并非永远更快——指令缓存会反转结论 ​

这条反直觉，但是与第 7 章形成完整对照的关键一环，值得单独点出。单态化生成大量独立代码，会把二进制撑大，进而加大指令缓存（i-cache）的压力；在 hot path 上，i-cache 未命中带来的停顿可能盖过「直接跳转省下的那点」开销。动态派发代码紧凑、对 i-cache 友好，在「类型很多、但单次方法调用的工作量大」的场景里，那一次间接调用的开销能被摊薄到几乎看不见。

所以「无脑选泛型一定更快」是个迷思。真实选择取决于几个因素：调用有多频繁（极频繁的小方法，静态派发的内联优势才明显）、类型有多少种（极多则 i-cache 压力大）、单次调用工作量多大（大则间接调用被摊薄）。

本质矛盾在于：「单次调用本身的间接开销」与「代码体积对缓存的全局影响」常常反向，局部最优不等于全局最优。

把析构函数也塞进 vtable，换类型擦除后的正确释放 ​

这是个精巧的设计点。vtable 里除了方法指针，还存着该具体类型的 drop 函数指针、大小、对齐。所以 Box<dyn Draw> 析构时，哪怕编译器已经忘了里面装的是 Button 还是 Circle，也能顺着 vtable 找到正确的析构逻辑、按正确的大小和对齐释放内存。类型擦除没有破坏 Rust「确定性析构」的保证。代价很薄，无非是每张 vtable 多存几个字，换来的是 trait 对象这条通道完全不掉安全链子。

5. 最小原理演示 ​

下面这段只演「类型擦除 + 胖指针 + vtable 查表」这条链，并附一段泛型单态化的对照，让你肉眼看到静态与动态的差别。每一行都对应该前面的某个原理点。

rust
// trait 定义能力契约：任何「会画」的东西都实现 Draw
trait Draw {
    fn draw(&self);
}

struct Button { label: String }
struct Circle { radius: f64 }

impl Draw for Button {
    fn draw(&self) { println!("画一个按钮：{}", self.label); }
}
impl Draw for Circle {
    fn draw(&self) { println!("画一个半径 {} 的圆", self.radius); }
}

fn main() {
    // 关键一步：Box::new(Button{..}) 把 Button 擦除成 dyn Draw。
    // 编译器在这里做两件事：把 Button 实例搬到堆上、记下 data 指针；
    // 同时记下「为 (Button, Draw) 生成的那张 vtable」地址。
    // 于是每个 Box<dyn Draw> 是一个胖指针（64 位机 16 字节）：
    //
    //   items[0] 的胖指针：           items[1] 的胖指针：
    //   ┌──────────┬──────────┐      ┌──────────┬──────────┐
    //   │ data_ptr │ ──► Button│      │ data_ptr │ ──► Circle│
    //   │ vtable_p │ ──► VT_B  │      │ vtable_p │ ──► VT_C  │
    //   └──────────┴──────────┘      └──────────┴──────────┘
    //
    //   VT_B = 为 (Button, Draw) 静态生成的全局 vtable：
    //   ┌──────┬──────┬───────┬──────────────────────┐
    //   │ drop │ size │ align │ draw ──► Button::draw │
    //   └──────┴──────┴───────┴──────────────────────┘
    //   VT_C 同构，只是 draw 槽位指向 Circle::draw。
    let items: Vec<Box<dyn Draw>> = vec![
        Box::new(Button { label: "确定".into() }),
        Box::new(Circle { radius: 3.0 }),
    ];

    for item in &items {
        // 这一行编译出的不是「直接跳到 Button::draw」，
        // 而是：取胖指针第 2 字的 vtable_ptr → 读 draw 槽位 → 间接调用，self = data_ptr。
        item.draw();
    }
    // 输出：
    //   画一个按钮：确定
    //   画一个半径 3 的圆
}

// 对照：同样的需求若用泛型（静态派发 / 单态化），写出来是这样。
// 这条路编译期为每个具体类型生成一份代码，调用点直接跳转、可内联，
// 但「集合元素类型必须唯一」——同一个 Vec 装不下 Button 和 Circle 混存。
fn draw_all<T: Draw>(items: &[T]) {
    for item in items {
        item.draw(); // 直接编译为跳到 T::draw，零间接调用
    }
}

注意 VT_B 里那个 drop 槽位：它正是上一节「把析构函数塞进 vtable」那条权衡的落点。items 离开作用域时，每个 Box<dyn Draw> 都通过自己胖指针指向的 vtable 找到正确的析构函数，按正确的 size/align 释放——编译器明明已经忘了元素的具体类型，释放却一点没出错。

6. 执行轨迹 ​

拿 items[0].draw() 走一遍，看动态派发到底发生了什么。

输入：items 是个 Vec<Box<dyn Draw>>，两项的胖指针分别是：

  • items[0]：(data_ptr → 堆上 Button 实例, vtable_ptr → VT_B)
  • items[1]：(data_ptr → 堆上 Circle 实例, vtable_ptr → VT_C)

两张 vtable 是编译期就生成好的全局静态表，VT_B.draw 指向 Button::draw，VT_C.draw 指向 Circle::draw。

执行 items[0].draw()：

  1. 从 items[0] 胖指针的第 2 个字读出 vtable_ptr，得到 VT_B 的地址；
  2. 在表里按 draw 槽位的偏移读出函数指针，即 &Button::draw；
  3. 以胖指针第 1 个字（data_ptr，指向那个 Button 实例）作为 self，对上一步的函数指针做一次间接调用。

调用最终落到 Button::draw，打印「画一个按钮：确定」。整个过程编译器完全不知道 items[0] 是 Button，它只知道「按 vtable 的 draw 槽位跳过去」。换成 items[1].draw()，机器指令序列完全一样，只是第 2 个字指向 VT_C，于是落到了 Circle::draw。异构、开放、运行时多态，就这样达成。

7. 教学简化说明 ​

本章演示故意省略了：对象安全的全部穷举规则与每条 where Self: Sized 豁免分支；默认 trait 对象生命周期的完整推断规则表；Box 以外的载体（Rc<dyn> / Arc<dyn>）；dyn A + B 多 trait 组合的 supertrait 约束；enum dispatch、devirtualization 等性能优化技巧。还有一点要提醒：vtable 的内存布局（drop/size/align/方法指针的排列）当前不是语言保证的稳定 ABI，而是 rustc 的实现约定，版本间可能调整，所以别在 unsafe 里手算 vtable 偏移。这些都是实战会遇到的细节，但不是理解「为什么要动态派发、它付了什么代价」的必要部分。

8. 小结 ​

同一份 trait 契约有两种兑现：第 7 章在编译期单态化，本章在运行期查 vtable。动态派发把「找回正确实现」推迟到运行期，换来异构集合与开放扩展，付的是一次间接调用加对象安全的限制；何况静态派发并不总更快，代码膨胀会反噬指令缓存。值得放心的是 trait 对象虽擦掉了身份，vtable 里仍留着析构函数，确定性析构的链子没断。有了运行期这种灵活组合不同类型的能力，下一步自然要面对「调用可能失败」，下一章《错误即值：Result/Option 与 ? 运算符》就看 Rust 怎么把失败编进类型。
