unsafe 与 FFI：安全边界的逃逸舱 ​

本章属于 system 层。前置：生命周期、智能指针与内部可变性。 学完你能：讲清 unsafe 为什么是一扇"诚实的边界"而不是"关闭检查的开关"，以及 Rust 怎样把最危险的少数操作压缩成可 grep、可审计的人工契约。

1. 为什么需要它 ​

上一章里，Cargo 把一个 Rust 工程从代码切分、依赖解析到编译发布安排得明明白白。可一个真正能打的系统语言没法只活在自己的安全泡泡里：你想 cargo add 一个 OpenSSL 绑定去跑 TLS，想调系统的 mmap，想手写一个自引用的双向链表或一把比标准库更贴合场景的锁——这时撞上的不是工程组织问题，而是 Rust 安全模型的边界。

这堵墙是从第 2、3、4 章一路砌起来的：所有权、借用、生命周期，让编译器在编译期就证明"没有悬垂引用、没有数据竞争"。但前面也埋了伏笔。第 4 章把引用有效性检查前移到编译期签名标注；第 12 章又给了运行时逃生舱：编译期证不出来时，用 RefCell/Mutex 把检查延迟到运行期。可这两档都假设"检查总做得成"，只是换了个时间点。

问题在于，有三类场景，编译期证不了，运行时也兜不住：

  • 调用一段你压根看不到实现的 C 代码。abs(-5) 到底安不安全，取决于 libc 二进制里的实现，编译器无从分析。
  • 裸指针运算。借用检查器只认引用（&/&mut），对裸指针 *const T/*mut T 不做别名和有效性分析。一旦你需要在"同一个切片里切出两段不重叠的可变借用"这种事上绕开它，它只能拒绝。
  • 跨语言、跨线程的底层契约。一个内部藏着裸指针的类型到底能不能安全搬到另一个线程？编译器推不出来，因为这取决于人定的规矩。

如果没有逃生舱，Rust 就是一座安全的孤岛：既接不上几十年攒下的 C 生态，也实现不了最底层的抽象，更别提编译到 WebAssembly（wasm 边界本身就是一种 FFI）。unsafe 就是这扇逃逸舱。

2. 核心思想 ​

unsafe 是一扇诚实的边界：它不关闭任何安全检查，只是把编译器证明不了的少数操作隔离出来，交给程序员接手证明责任。

关键词是"只增不减"。进了一个 unsafe { ... } 块，借用检查、生命周期、类型系统全部照常工作；块里新增的，仅仅是借用检查器本来就不覆盖的那一小片地盘（裸指针等）的操作权。它标的是"这里需要人来论证"，不是"这里无法无天"。

3. 心智模型 ​

理解 unsafe 要先抓住它身上的两副面孔。这个关键字既出现在声明端，也出现在使用端，干的是两件相反的事：

  • 声明端写 unsafe fn、unsafe trait，是在喊"此处存在一个编译器查不出来的契约，谁来用谁负责"。
  • 使用端写 unsafe { ... }、unsafe impl，是在应答"这个契约我已经核实过了，我来担保"。

所以一个 unsafe fn 不带 unsafe 块是调不动的——声明方交出来的责任，调用方得明确接住。

那到底有哪些事必须这么交接？官方列了五项超级能力，unsafe 额外放行且仅放行这些：

  1. 解引用裸指针 *const T / *mut T；
  2. 调用 unsafe 函数或方法（含所有 FFI 外部函数）；
  3. 实现 unsafe trait（如 Send/Sync）；
  4. 访问或修改可变 static 变量；
  5. 访问 union 的字段。

有个容易踩的坑值得先点破：创建裸指针是 safe 的。let p: *const i32 = &x; 在普通代码里合法，真正需要 unsafe 的是拿它去解引用那一刻，因为只有解引用才会真的读那块内存。

unsafe 把五种能力交到你手上，但整个 Rust 安全模型立在一个更硬的承诺上，叫 soundness（健全性）：不管 safe 代码怎么写、怎么乱组合，都不可能触发未定义行为（UB）。所有 unsafe 代码的最终义务，就是别让这条承诺在自己的 crate 里破掉。

那怎么守住？靠 safe wrapper 模式：把 unsafe 藏进模块内部，用 Rust 的私有性（字段不加 pub、内部函数不导出）挡住外部代码破坏它依赖的不变式，对外只暴露不带 unsafe 字样的普通函数。soundness 不只看 unsafe 块内的逻辑对不对，还得看外部 safe 代码有没有办法违反不变式，而私有性正是堵住这条路的关键。

把整条逃生路线拉到一张图里，是贯穿全书的安全保证谱系：

编译期证明（所有权 + 借用 + 生命周期）   零开销，全在编译期        第 2~4 章
      │  编译器证不出来时，向下逃生
运行时检查（RefCell / Mutex）            有运行时开销，失败=panic   第 12 章
      │  连运行时也兜不住（外部世界契约）时，再向下逃生
人工契约（unsafe）                       无检查，靠人 uphold，失败=UB  本章

RefCell 和 unsafe 经常被并称为"两个逃生舱"，但方向不同：RefCell 是把检查延迟到运行期，unsafe 是把检查放弃、换成一份由人签字的契约。前者的失败是一个可定位的 panic，后者的失败是不可靠的 UB。

给前端读者一个类型层的直觉（仅作类比，点到即止）：TS 里常见的 branded type，用一个不导出构造函数的内部 brand 标记，外部只能通过你提供的工厂函数拿到这个类型——精神上很像 safe wrapper，危险操作被私有性锁住，外部只能走审计过的入口。差别在于，TS 的 brand 是类型层的约定，编译后就消失；Rust 的 unsafe 守的是真实的内存安全，契约错了真的会段错误。

4. 关键权衡 ​

把危险收进一扇可 grep 的窄门 ​

Rust 选择只开放固定的五种超能力，而且任何一处用到都必须显式写 unsafe 块、unsafe fn 或 unsafe impl。换来的是危险点可定位、可审计：grep -r "unsafe" 就能列出一个 crate 里所有需要人工担保的位置，code review 时盯着这几处看就行。代价是程序员要为每一处 unsafe 写安全论证（紧挨着写 // SAFETY: ... 注释，讲清为什么不违反不变式），心智负担不轻；更要命的是，一旦论证错了，惩罚不是 panic 而是 UB——UB 连出错的现场都不可靠，可能在毫不相干的代码里炸给你看。这条权衡化解的本质矛盾，是"底层能力"和"全局可推理"的对立：要么彻底放弃底层（Java 式，把指针藏起来），要么放弃可推理（C 式，处处皆险地），Rust 选了第三条路，危险存在，但被压缩进最小、最显眼的围栏。

只增不减，换来可组合的 soundness ​

前面说过 unsafe 是"只增不减"，不关闭任何检查。这个选择换来的是 soundness 可以组合：一个 safe 的 API 内部偷偷用一点 unsafe，只要封装正确，污染绝不会漏到调用方；调用方哪怕完全不知道里面有 unsafe，也享受完整的"绝不可能触发 UB"承诺。代价是 unsafe 的真实语义远比大众直觉复杂。它是 Rust 最被误解的关键字：相当多人以为"unsafe = 关掉安全检查 / 这段代码危险"，于是要么不敢用，要么用了就以为块内随便写。学习曲线陡，而这种误解会直接导致对 soundness 的错误推理。这里对立的是"语言表达力"和"概念简洁性"：把 unsafe 设计成一个简单的开关最直观，但那样就保不住 soundness 的可组合性，整个生态的安全保证会从根上松掉。

拿 C ABI 当世界语，代价是边界处类型降级 ​

FFI 选择用 C ABI（extern "C" + #[repr(C)] + #[no_mangle]）作为对外互通的统一接口。换来的是能和几乎所有语言生态对接——C 是跨语言的最低共同语言，Python、Node、Java、Go 都能讲。代价是在 FFI 边界上，你必须放弃 Rust 的高级类型：String/Vec/Result/生命周期统统不能直接过界，得降级成裸指针加手动内存管理。边界因此成了 bug 高发区，而且每个坑都很硬：

  • 内部 NUL 字节：Rust 字符串里允许 \0，但 C 字符串拿 NUL 当终止符。CString::new("a\0b") 会返回 Err，因为传过去 C 会把字符串截断在第一个 NUL。
  • panic 越界 = UB：Rust 的 panic 若一路 unwind 穿过 extern "C" 边界进入 C 的栈帧，是未定义行为。要么用 catch_unwind 在边界拦住，要么干脆 panic = "abort" 编译。
  • 分配器不匹配：CString::into_raw() 交给 C 的指针，必须用 CString::from_raw() 收回来，绝不能让 C 的 free 去释放 Rust 分配的内存，两边分配器不是一回事，混用就是双重释放或堆损坏。

对立面同样是"互通广度"和"表达力"：边界越通用，能带过去的类型就越贫瘠。Rust 把所有复杂度压到边界两侧的封装层，让边界本身尽量 dumb。

藏进最小模块，代价是最隐蔽的 bug ​

配合前几条，Rust 社区有一条几乎不成文的规矩：把 unsafe 藏进尽可能小的模块，对外只暴露 safe API。换来的是普通使用者完全无感，照样享受完整安全保证；整个 crate 里真正需要审计的常常只有寥寥几行。代价是封装的正确性极难保证。soundness bug 是 Rust 生态里最隐蔽、最难复现的一类 bug：它不会在测试里稳定复现，往往要等特定编译器版本、特定平台、特定输入组合下才爆出来，一旦爆出来就是 UB。守这种 bug 靠三件套——私有性守住不变式、严格 review、针对不变式的测试。这里打架的是"用户省心"和"正确性证明的难度"：封装越严，用户越省心，但证明这个封装 sound 的担子就越重，而这副担子没有任何编译器帮忙兜底。

5. 最小原理演示 ​

这一章的核心是 Rust 特有的内存语义，TS/JS 里没有对应物，演示老老实实用 Rust。两段极小代码，共同演透同一条主线：编译器证明不了 → 降级为人工契约 → 重新封装成 safe API。

第一段复刻标准库 slice::split_at_mut 的灵魂。需求很朴素：把一个可变切片从中间劈成两段，各自可变借用。可这在 safe Rust 里直接写会被拒——借用检查器没法证明"这两段不会重叠"。

rust
// 把一个可变切片劈成不重叠的左右两段，对外完全 safe
fn split_at_mut<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    let len = slice.len();
    // 先在 safe 代码里守住前置条件：mid 越界就 panic，绝不进 unsafe
    assert!(mid <= len);

    let ptr = slice.as_mut_ptr();

    // 借用检查器证不出"两段不重叠"，但 mid <= len 保证了它在数学上成立
    // 这里由人接管证明责任，写成 SAFETY 注释交给 reviewer
    unsafe {
        let left = std::slice::from_raw_parts_mut(ptr, mid);
        let right = std::slice::from_raw_parts_mut(ptr.add(mid), len - mid);
        (left, right)
    }
}

// 调用方全程无感，看不到任何 unsafe 字样
let mut v = [1, 2, 3, 4, 5];
let (a, b) = split_at_mut(&mut v, 2);
a[0] = 99;   // a = [99, 2]
b[0] = 88;   // b = [88, 3, 4, 5]

注意三处设计都对应前面的原理：assert! 留在 safe 区，把能机器检查的先检查掉；进 unsafe 只为绕开借用检查器证不了的"不重叠"；签名上没有 unsafe，调用者拿到的就是两个普普通通的可变切片。这就是 safe wrapper 最干净的样本。

第二段演 FFI 的两步走：声明一个 C 符号，在 unsafe 块里调用。

rust
use std::os::raw::c_int;

// extern "C" 声明一个走 C ABI 的外部符号，链接器会去 libc 里找它
extern "C" {
    fn abs(input: c_int) -> c_int;
}

fn main() {
    // 外部 C 函数的实现编译器看不到，必须由人担保这次调用安全
    let n = unsafe { abs(-5) };
    assert_eq!(n, 5);
}

extern "C" { ... } 在声明端喊"这里有份 C 的契约"，unsafe { abs(-5) } 在使用端应"我接了"。整段不到十行，但 FFI 的核心动作——C ABI 声明加 unsafe 块调用——已经齐了。

6. 执行轨迹 ​

拿 split_at_mut(&mut [1,2,3,4,5], 2) 走一遍，看那条主线怎么一步步落地。

  • 输入：一个可变切片 &mut [T]（指向 5 个元素的缓冲区）和索引 mid = 2。
  • 编译器视角：函数想返回两个 &mut [T]，但"它们会不会指向重叠的内存"它证不出来，按借用规则只能拒绝。这正是要逃逸的边界。
  • safe 区前置检查：assert!(mid <= len) 即 assert!(2 <= 5) 通过。这一步把能在 safe 区拦住的错误（越界 mid）全部拦掉，不让它们混进 unsafe。
  • 取裸指针：ptr = slice.as_mut_ptr()，拿到缓冲区起始地址。这一步是 safe 的，创建裸指针不需要 unsafe。
  • 进 unsafe 块，人工切分：因为 mid <= len，区间 [ptr, ptr+2) 与 [ptr+2, ptr+5) 在数学上必不重叠。这是人 uphold 的契约，写进 // SAFETY 注释；编译器在此放行裸指针运算和 from_raw_parts_mut。
  • 重新封装：两段裸指针被 from_raw_parts_mut 各自包回可变切片引用，类型重新回到 safe 世界。
  • 输出：返回 (&mut [1, 2], &mut [3, 4, 5])。对外签名完全 safe，调用者不需要写一个字的 unsafe，更不知道内部发生过指针运算。

这条轨迹把三步——编译期证不了 → 降级人工契约 → 重封为 safe API——压进一个函数里演完，是全章的缩影。

7. 教学简化说明 ​

为了把主线讲透，本章有意省略了不少东西：union 字段访问和可变 static 的细节、unsafe trait（Send/Sync 手动实现）与并发的衔接、Drop 检查与析构顺序的交互、指针 provenance 和别名内存模型（这部分在学术界都还没定论，规范层面仍是 open question）、bindgen/build.rs 的工程化流程、以及 catch_unwind 与 panic = "abort" 的机制差异。它们都是真实存在的话题，但不演进本章的核心思想，留给你有需要时再深入。

8. 小结 ​

unsafe 不是 Rust 安全机制的反面，而是它的最后一档兜底：当编译期证明和运行时检查都够不着的地方，它诚实地画一条线，把证明责任交还给人，再让你用私有性把这份危险封进一个对外完全 safe 的壳。FFI 是这条线最常被踩到的那一段，C ABI 让 Rust 接得上整个外部世界，代价是边界处必须放弃高级类型、手动伺候内存。下一章你会看到，这同一套 extern/#[repr(C)]/跨边界封装的思路，在 Rust 编译到 WebAssembly 时会以 wasm-bindgen 的面目重新登场。
