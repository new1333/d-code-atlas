# 函数工厂与无 this 的方法

## 一个让人困惑的崩溃

你写了个事件发射器，用得很顺手。某天你想把它的 `on` 方法单独抽出来，交给一个日志库当回调：

```ts
const emitter = new SomeEmitter()
const { on } = emitter
logLibrary.subscribe(on)   // 把 on 单独递出去用
```

结果一运行，`on` 内部抛错：`Cannot read properties of undefined (reading 'all')`。你没动过 `on` 的代码，只是把它从 `emitter` 上「摘」下来单独用了一下，它就崩了。

如果 `on` 是被存进变量、塞进 `setTimeout`、或者丢给 `Promise.then` 的——也就是任何「不是当场用 `emitter.on(...)` 这种带点号的方式调用」的场景——同样的崩溃都会复现。为了绕开它，你被迫到处补 `.bind(emitter)`，或拿箭头函数再包一层。每补一次，都在提醒你同一件事：**这个方法自己记不住自己的状态。**

mitt 这套库，就是为了把上面这个坑彻底填平而存在的。

## 罪魁是 JS 的 this 绑定

为什么把方法摘下来就崩？因为类的方法里，状态是挂在 `this` 上的——而 `this` 是个极不靠谱的东西。

```ts
class ClassEmitter {
  constructor() { this.all = new Map() }
  on(type, handler) {
    const list = this.all.get(type)   // ← 读状态，全靠 this
    // ...
  }
}
```

`this` 不是方法自带的东西，而是「调用那一刻、点号前面是谁」临时决定的。`emitter.on(...)` 时点号前面是 `emitter`，`this` 就是 `emitter`；可一旦你 `const { on } = emitter` 再单独 `on(...)`，点号没了，`this` 就成了 `undefined`（严格模式下），方法自然读不到那张表。

说白了，`this` 是个看「谁在叫我」才决定指向哪儿的、随时可能丢的绑定。这就是 mitt 想整个拿掉的东西。

## 解药：让方法出生时就记住状态的地址

mitt 的做法是——方法不问「谁在叫我」，而是「出生那天」就把状态的位置记死了。

这里给一个类比，点一次就够：

> 类方法像那种「只认传话人」的员工：必须有人喊他「老张叫你去拿」，他才知道去老张的柜子找文件；换个不认识的人喊、或者直接喊他，他就懵了。mitt 的方法则像「入职第一天就把柜子坐标背下来」的员工——不管谁喊、不管派去多远，他都能凭记忆径直走回那个柜子。

这个「入职第一天背下坐标」的动作，就是**闭包**。方法记住的不是状态本身，而是「那个装着状态的变量在哪儿」——只要那张表还在内存里，方法随时摸得到它。

而「入职第一天」发生在哪？发生在**工厂函数被调用的那一刻**。所以「用函数工厂」和「方法不用 this」其实是同一件事的两面：**工厂存在的全部意义，就是替 `this` 去制造那个记住状态的闭包**。

## 从零实现：闭包替 this 绑状态

现在动手写一个最小版本，把上面的原理跑给你看。

上一章我们已经知道，整个发射器的状态就是一张 `Map<事件类型, 处理器数组>`——这一章我们只看这张表「怎么被方法绑定到」「怎么被工厂暴露出去」这两个新侧面，不重演它为什么是一张表。

一个从零写的、mitt 式的发射器，全篇找不到一个 `this`：

```ts
// 工厂：一个普通函数，接受一张可选的注册表
function createEmitter(all = new Map()) {
  // 工厂返回一个对象字面量，里面挂着表本身和三个方法
  return {
    all,                                       // ← 把表直接当公开属性挂出去

    on(type, handler) {
      const list = all.get(type)               // ← 读闭包里的那张表，没有 this
      if (list) list.push(handler)
      else all.set(type, [handler])
    },

    emit(type, evt) {
      ;(all.get(type) || []).forEach(h => h(evt))   // ← 同样只认闭包里的表
    },
  }
}
```

三个方法体里出现的 `all`，不是参数，也不是某个属性——它就是工厂调用那一刻被闭包「包进来」的那个 `all`。这正是上一节说的「背下坐标」。注意 `on` 里那段 `if (list) push / else set` 的写法本身另有讲究，那是下一章的主题，这里先用着、不展开。

### 对照实验：解构后再单独调用

光说不管用，跑一下。同样的逻辑，一份用工厂写、一份用类写，然后都把方法拆出来单独用：

```ts
// —— 函数工厂版本 ——
const { on: fOn, emit: fEmit } = createEmitter()
fOn('tick', () => console.log('工厂版：tock'))
fEmit('tick')   // ✅ 输出：工厂版：tock

// —— 类版本 ——
class ClassEmitter {
  constructor() { this.all = new Map() }
  on(type, handler) {
    const list = this.all.get(type)
    if (list) list.push(handler); else this.all.set(type, [handler])
  }
  emit(type, evt) { ;(this.all.get(type) || []).forEach(h => h(evt)) }
}

const { on: cOn } = new ClassEmitter()
cOn('tick', () => console.log('类版本：tock'))   // ❌ 抛错：Cannot read properties of undefined (reading 'all')
```

工厂版安然无恙，类版本当场崩溃。差别只在一个地方：工厂版的 `on` 出生时就把表坐标记进了闭包，你把它扔到天涯海角，它依然摸得到那张表；类版本的 `on` 出生时什么都没记，每次都指望「点号前面有人」给它指路，点号一没，它就成了无头苍蝇。

说人话就是：**有没有点号，对工厂版的方法没区别；对类方法，是生与死的区别。** 这就是 mitt 把 `this` 整个拿掉、换成闭包所换来的东西。

## 执行轨迹：两个发射器共享一张表

工厂签名里那个 `all = new Map()` 的默认值，还藏着第三个能力：**注册表可以从外面传进来**。这给了我们一条有意思的执行轨迹。

先新建一张空表，用它造两个发射器：

```ts
const shared = new Map()
const a = createEmitter(shared)
const b = createEmitter(shared)
```

此刻 `a` 和 `b` 是两个独立的发射器对象，但它们的闭包指向**同一张** `shared` 表。接着做一件看起来反直觉的事：

```ts
a.on('ping', () => console.log('pong'))   // 用 a 注册
b.emit('ping')                             // 用 b 触发
// ✅ 输出：pong
```

用 A 注册，用 B 触发，处理器照样被调到。因为注册动作把处理器写进了 `shared`，触发动作又从同一张 `shared` 里读到了它——两个发射器不过是对同一张表的两个观察口。

整个工厂调用链可以画成这样：

```
调用 createEmitter(可选的表)
  → 工厂函数执行，为这次调用建一个闭包作用域
  → 闭包把 registry 变量包了进去（替 this 记下状态坐标）
  → 工厂 return 对象字面量 { all, on, emit }
  → 任意位置拿到方法、单独调用
  → 方法体访问 all → 命中闭包里那张表（不需要点号、不需要 this）
```

## 关键权衡

闭包替 `this` 绑状态，是这一章真正值得记住的取舍——在它旁边，还伴着两个同源的取舍。三条放在一起看，才能理解 mitt 为什么是现在这副样子。

### 权衡一：用闭包替 this 绑状态（本章的核心取舍）

**做了什么选择**：方法彻底不依赖 `this`，状态全部由工厂调用产生的闭包捕获。三个方法体读写订阅信息时，直接引用闭包里的 `all`，全文不出现一个 `this`。

**换来什么**：方法可被安全解构、单独传递、当回调挂载。`const { on } = createEmitter()` 之后，`on` 无论被存进变量、塞进 `setTimeout`、交给 `Promise.then`，都不会因为丢失 `this` 而读错状态或报错。前面的对照实验已经把这一点钉死了：这是「this 版本解构即崩、闭包版本解构照常工作」的根源。

**代价是什么**：每个发射器实例都要新生成一份方法，没有原型共享。可以亲手验证：

```ts
const a = createEmitter(), b = createEmitter()
a.on === b.on              // false —— 工厂版每实例各自一份方法

class C { on() {} }
new C().on === new C().on  // true  —— 类版共享原型上同一个方法
```

类的方法挂在原型上、所有实例共用一份；工厂返回的对象字面量，每次调用都把 `on/emit` 现写一遍。实例一多，内存和分配开销会比类略高。mitt 的判断是：发射器实例通常很少（一个应用里顶多几个），这点开销远不如「方法可安全传递」和「体积更小」来得值，于是坦然接受了无原型共享。换句话说，这个设计是拿「多实例的内存」换「方法的可移植性」。顺带一提，闭包里的局部变量能被压缩工具重命名成单字符，而 `this` 是关键字、改不了——这对一个把体积压到极致的库是加分项，虽是顺带的好处，并非该设计的主要动机。

### 权衡二：把注册表当公开可变属性直接交出去

**做了什么选择**：把内部那张注册表，原封不动作为返回对象的公开属性挂出来（`return { all, ... }`）。它不是私有的，连类型契约里 `all` 都和 `on/emit` 并列，是个公开成员。

**换来什么**：调用方可以直接对底层表动手，一行完成那些库方本来得专门加 API 才能做的事：

```ts
emitter.all.clear()                    // 清空全部订阅
emitter.all.get('click')?.length       // 瞄一眼谁订阅了 click
emitter.all.delete('login')            // 直接删掉某类事件
```

不需要等库方提供 `clearAll()`、`count(type)`、`removeType(type)`——表是一张 `Map`，`Map` 自带的全部能力都白送给你。这是上一章「把 pubsub 退化成一张查找表」红利的延续：既然状态就是一张普通的 Map，那它天生就该能被当普通 Map 操作。

**代价是什么**：彻底放弃封装。任何人都能绕过 `on/emit` 直接改这张表——往里塞非法结构、在派发途中清空它、偷改别人的处理器——库方完全无法保证任何不变式，也无从做访问控制。mitt 的取舍很清楚：对一个定位「极简」的小库，封装换来的安全收益，不如「少写几个包装 API、把 Map 原力直接交出」换来的简洁来得实在。

### 权衡三：注册表可注入、缺省自建

**做了什么选择**：工厂第一个参数是那张可选的注册表，`all = all || new Map()`——传了用你的，不传内部新建一张。

**换来什么**：多个发射器可以共享同一张表，实现了上一节执行轨迹里那种「跨发射器事件汇流」（A 注册、B 触发，因为底层是同一张表）。它也允许外部先构造好一张表——比如从别处序列化恢复、或预先填好一批订阅——再注入进发射器复用，而不必把数据倒一遍。

**代价是什么**：API 表面多了一个参数，并且需要「传了就用、没传就建」这一句兜底逻辑。注意它用的是 `||` 而非 `??`——因为空 `Map` 是对象、恒为真值，`||` 不会把一张合法的空表误覆盖成新表，语义是安全的；顺带也照顾了库宣称要支持的 IE9+ 这类老运行时（`??` 在那里用不了）。

## 小结

这一章只回答了两个问题：方法靠什么绑定到那张状态表上，工厂又怎么把这张表暴露与注入出去。答案是同一件事的两面——**方法不靠 `this`，靠的是工厂调用时形成的闭包；工厂存在的全部理由，就是替 `this` 去造那个闭包**。代价也看得清清楚楚：放弃原型共享、放弃封装、API 多一个参数。换来的，是「方法拿到哪儿都能用」这件在事件系统里非常实用的事。

那么 `on` 把处理器写进这张表时，具体是怎么写的？你会发现第一个处理器和第十个处理器的写法并不一样——这里头藏着一段「能省则省」的小心思。那是下一章《惰性初始化的追加式订阅》要拆开看的东西。
