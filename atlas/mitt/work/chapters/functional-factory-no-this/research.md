# 函数工厂与无 this 的方法 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：用传统「类 + this」写的事件发射器，一旦把方法单独抽出来用就会踩坑——解构出来当回调传给别的模块、挂到Promise/事件循环里异步调用，`this` 一丢就读不到内部状态、要么静默失效要么直接报错。使用者被迫到处写 `.bind(this)` 或包一层箭头函数。mitt 想让「拿到方法就能随便传、随便存、随便异步调」这件事零成本成立。

- **一句话核心思想**：方法不靠 `this` 绑定状态，而是靠「工厂调用产生的闭包」捕获状态——`this` 这个 JS 里最容易出错的绑定机制被整个拿掉了。

- **设计动机（为什么需要它）**：要让方法可被安全解构/传递，就必须消灭方法对 `this` 的依赖；而消灭了 `this` 之后，方法还能共享同一份状态，靠的正是「工厂函数被调用时形成闭包、把状态变量包进去」。于是「函数工厂」和「无 this」其实是同一个设计的两面：**工厂存在的意义，就是替 `this` 去造那个闭包**。承前关系：（已在第 1 章『把 pubsub 退化成一张查找表』讲透「注册表是一张 Map、是整个发射器的唯一状态」，本章不重演状态本身，只看这张表的两个新侧面——① 方法靠什么绑定到这张表；② 工厂如何把这张表暴露与注入出去）。

- **关键权衡（机制丰富章，列 3 条）**：
  1. **选「方法完全不依赖 this、状态由工厂闭包捕获」** → 换来「方法可安全解构、单独传递、当回调挂载，绝不因 this 丢失而读错状态或报错」 → 代价是「每个发射器实例都新生成一份方法（没有原型共享、多实例内存略高），且要求状态必须以闭包变量形式被所有方法共同捕获」。
  2. **选「把内部注册表当作公开、可变的属性直接交出去」** → 换来「调用方能直接清空/窥探/批量操作底层表（一行清空全部订阅、遍历看谁订阅了什么），无需库方为每种操作各加一个 API」 → 代价是「彻底放弃封装：任何人都能绕过增删方法直接改表，没有访问控制，也无法对外保证不变式」。
  3. **选「工厂接受一个可选的注册表入参、缺省时内部新建」** → 换来「多个发射器可共享同一张表，实现跨发射器事件汇流、或外部预构造后注入」 → 代价是「API 表面多一个参数，且需要『传了就用、没传就建』的兜底逻辑」。

- **最小心智模型（3～7 步）**：
  1. 调用工厂，可传入一张已有的注册表（不传则内部新建一张空表）。
  2. 工厂把这张表的引用，关进本次调用形成的闭包里。
  3. 工厂返回一个普通对象字面量，里面挂着「这张表本身」和若干方法。
  4. 每个方法内部要读写订阅状态时，直接引用闭包里那张表，全文不出现 `this`。
  5. 因为不靠 `this`，方法被解构出来单独调用时，闭包照旧把状态喂给它——不丢绑定。
  6. 因为表是公开属性、且工厂可接受外部表，两个发射器可以共享同一张表。

- **最小原理演示（替代旧"复刻范围"）**：
  - 应演示：一个几十行的从零实现，演透**「闭包替 this 绑状态」**这一条核心思想。要点：① 工厂接受可选注册表、缺省自建；② 返回对象字面量、方法用闭包引用注册表、**全篇不写 `this`**；③ 一个对照实验——把方法解构出来单独调用依然正常工作（与「类 + this」版本解构后即崩溃形成对比）；④ 再演「两个发射器共享同一张注册表」印证可注入性。每一行都要对应上面某条权衡。
  - 应故意省略：通配符派发、快照派发、类型泛型与条件类型、移除的位运算技巧、IE9 兼容脚手架、产物多格式打包。
  - **演示载体建议：首选 TS/JS**。本章核心功能就是 JS 的 `this` 绑定语义与闭包机制，TS/JS 能最忠实地演透（对照实验里「this 版本解构即崩」恰恰依赖 JS 原生 `this` 行为），且本 Atlas 产物本身是 JS 生态站点，配最小 `package.json` 即可 `bun run`/`node` 跑。无需退回其它语言。

- **正文不宜展开的细节**：闭包里每次用注册表都带非空断言（`all!`），是因为「缺省自建」用赋值兜底而非类型守卫，编译器无法收窄（属类型边角，点到即可）；方法用对象字面量「方法简写」而非箭头函数（二者都不绑定实例 `this`，简写更短）；`all = all || new Map()` 用 `||` 而非 `??`（空表是对象恒为真值，`||` 不会误覆盖，且利于老运行时）；「无 this 利好压缩」这一动机是推断（见下文推断区，未在源码字面写明）。

- **推荐的一个执行轨迹例子**：先新建一张空注册表；用它造两个发射器；向其中一个发射器注册某事件的处理器；用**另一个**发射器触发该事件 → 处理器被调用。中途态：两个发射器的闭包指向同一张表，注册动作把处理器写进了这张共享表，触发动作又从同一张表里读到了它——这正是「可注入共享注册表」的直接体现。

## 概念要点
- **工厂是一个普通函数，返回对象字面量**：`mitt` 是 `export default function`，返回值是 `return { all, on, off, emit }`——不是 `class`、不带 `new`、不挂原型。源码位置: src/index.ts:46-54
- **状态由闭包捕获，全文无 `this`**：三个方法 `on/off/emit` 内部一律用 `all!.get(...)`/`all!.set(...)` 读写注册表，引用的是工厂参数 `all`（被闭包捕获），全文件检索不到任何 `this` 关键字。这是「无 this 函数式方法」的字面事实。源码位置: src/index.ts:66-73（on）、src/index.ts:82-91（off）、src/index.ts:103-121（emit）
- **注册表可注入、缺省自建**：工厂签名 `mitt(all?: EventHandlerMap<Events>)`，第一行兜底 `all = all || new Map()`——传了用你的、不传内部新建。这是「可注入共享注册表」的入口。源码位置: src/index.ts:46-52
- **注册表对外公开且可变**：`all` 直接作为返回对象的属性挂出（`return { all, ... }`），README 示例 `emitter.all.clear()` 直接在外部清空整张表，证明它是公开可变属性、无封装。源码位置: src/index.ts:54-58；外部直接操作证据: README.md:73
- **设计意图由官方特性背书**：README 特性清单明确列出「Functional: methods don't rely on `this`」作为头条卖点，证明无 this 是刻意设计而非无心之作。源码位置: README.md:16
- **Emitter 接口把 `all` 写进公开契约**：`Emitter<Events>` 接口里 `all: EventHandlerMap<Events>` 是公开成员，与 `on/off/emit` 并列——类型层面也确认了「注册表是公开 API 的一部分」。源码位置: src/index.ts:23-39

## 关键调用链
调用方 → `mitt(all?)`（工厂，建立闭包、可选注入注册表） → `return { all, on, off, emit }`（对象字面量） → 任一方法内部 `all!.get/set`（闭包读写共享注册表）
两条「无 this」证据链：
- 注册：`on(type, handler)` → `all!.get(type)` 命中则 `push`、否则 `all!.set(type, [handler])` 源码位置: src/index.ts:66-73
- 派发：`emit(type, evt)` → `all!.get(type)` 取快照遍历、再 `all!.get('*')` 取通配符表遍历 源码位置: src/index.ts:103-121

## 易混淆 / 边界 / 推断
- **事实**：`on/off/emit` 三处都用 `all!`（非空断言）。原因是 `all = all || new Map()` 用赋值兜底重赋值，TS 无法据此把参数类型从「可能 undefined」收窄为「已非空」，故每次取用都需手动断言。源码位置: src/index.ts:52、67、83、104、113
- **事实**：`all` 用 `||` 兜底而非 `??`：即便传入一张空 `Map`，对象恒为真值，`||` 不会误覆盖，语义安全；同时 `||` 对 IE9+ 等老运行时更友好（mitt 宣称支持 IE9+）。源码位置: src/index.ts:52；运行时支持声明: README.md:19
- **事实**：方法以对象字面量「方法简写」定义（`on(...){...}`）。简写函数同样不绑定调用处实例的 `this`，与方法「不依赖 this」的目标一致；与「写成箭头函数」相比更短、更适合追求极小体积。
- **推断（标注为推断）**：「避免 `this` 利好代码压缩」可能是该设计的隐性动机之一——闭包里的局部变量可被压缩器重命名为单字符，而 `this` 是关键字不可重命名；这与 README 把「Tiny 200b」作为头条目标（README.md:11,13）方向一致。但源码与 README 均未字面写明这一动机，故仅作推断，不作为确证事实。
- **推断（标注为推断）**：放弃原型共享、每实例重建方法，会带来轻微的内存/分配开销；mitt 以「实例通常很少、追求极致体积与无 this 安全性」为由接受了这一代价。源码未直接讨论此取舍，属合理推断。
- **未理解**：无。本章机制清晰，唯一的设计动机（无 this 的函数式方法）由 README 特性清单直接确认，无臆测空间。
