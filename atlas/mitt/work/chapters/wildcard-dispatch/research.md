# 通配符星号的第二条派发路径 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：事件系统里有一类"横切"需求——日志、调试、遥测、把事件转发到另一个总线、做 AOP 式拦截——它们需要"监听所有事件"。如果没有这个能力，使用者就得为每一个事件类型各订阅一遍，或被迫修改每一次派发的代码去塞广播逻辑。使用者真正想要的是：一处订阅就能收到任意事件，并且能知道"刚才到底是什么事件被触发了"。

- **一句话核心思想**：以一个保留键复用同一张查找表，零成本地获得 catch-all 派发。

- **设计动机（为什么需要它）**：通配符是这个发射器"一张 Map 退化 pubsub"哲学的自然延伸——不引入第二套注册表、也不引入第二套订阅 API，而是约定一个特殊键当作"全部事件"的语义，让订阅/退订完全复用已有路径。它换来的是"一处订阅即收到任意事件且能区分类型"的能力。**承前**：本章依赖的"先复制数组再遍历"的快照式派发手法（已在第 5 章『快照式派发抵御中途改表』讲透，本章只看它的新侧面——同一次派发内这个快照手法被调用了**两次**，形成两条独立派发路径，且第二趟改用双参签名）。

- **关键权衡**：
  1. **复用同一张表 + 保留键，而非引入独立的通配符注册表** → 换来了通配符的订阅/退订完全复用已有的惰性建表与无分支移除逻辑（零新增代码路径）→ 代价是占用了 `'*'` 这个命名空间，用户再也不能把星号当普通事件名用。
  2. **通配符处理器用双参 `(类型, 事件)`，普通处理器用单参 `(事件)`** → 换来了 catch-all 处理器能区分"是什么事件被触发了"（否则一个监听全部的处理器拿不到类型信息就毫无用处）→ 代价是同一张表里并存两种不同签名的函数，类型层只能用联合类型存储、并在派发时分别断言还原；也正因签名不同，手动触发通配符会引发参数错位与重复派发，故被刻意禁止。
  3. **第二条派发路径无条件执行（每次派发都去查一次星号槽）** → 换来了 catch-all 语义的确定性与代码极简（无需维护"是否有人订阅了通配符"的标志位）→ 代价是每次派发多一次 Map 查找（命中为空即短路，开销极小），以及通配符处理器**固定**排在类型匹配处理器之后、优先级不可配置。

- **最小心智模型（3～7 步）**：
  1. 约定一个保留键，其语义为"全部事件"。
  2. 订阅通配符时，把处理器存进表里那个保留键的槽位——走与普通事件**完全相同**的注册逻辑。
  3. 派发某类型事件时，先跑第一趟：取出该类型的处理器，复制一份快照后遍历，用**单参**调用。
  4. 无论第一趟是否命中，紧接着跑第二趟：取出保留键槽位里的处理器。
  5. 第二趟用**双参**调用每个通配符处理器——把"被触发的真实事件类型"作为第一个参数补进去。
  6. 两趟各自独立做快照、各自独立短路（没有处理器就跳过）。
  7. 于是同一次派发会同时通知"该类型的订阅者"和"全部事件的订阅者"；后者额外知道自己收到的是什么类型。

- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个几十行的从零实现，演透三件事——① 保留键与普通键共用同一张表（订阅一视同仁）；② 派发时两趟独立快照遍历；③ 第二趟用双参把真实类型补进去。每一行都对应上面某条权衡/某个步骤。
  - **应故意省略**：完整泛型、symbol 事件、退订逻辑、非空断言、类型联合与断言还原的细节。
  - **演示载体建议**：**首选 TS/JS**。本章是纯数据结构 + 控制流机制，无任何语言特有语义，TS/JS 完全讲得透，且本 Atlas 产物本身就是 JS 生态站点，读者用 `node`/`bun run` 即可跑通。无需退回原仓库语言。
  - 演示骨架（演的是权衡 1+2+3 与步骤 3-7）：
    ```ts
    type Handler = (event: any) => void;              // 单参：普通处理器
    type StarHandler = (type: string, event: any) => void; // 双参：通配符处理器
    function mitt() {
      const all = new Map<string, Function[]>();      // 一张表，星号只是其中一个键
      return {
        on(type: string, h: Function) {               // 对星号与普通事件一视同仁
          const list = all.get(type);
          if (list) list.push(h); else all.set(type, [h]);
        },
        emit(type: string, evt: any) {
          all.get(type)?.slice().forEach((h: any) => h(evt));        // 第一路径：单参
          all.get('*')?.slice().forEach((h: any) => h(type, evt));   // 第二路径：双参，补类型
        }
      };
    }
    const bus = mitt();
    bus.on('foo', (e:any) => console.log('foo:', e));
    bus.on('*', (t:string, e:any) => console.log('star:', t, e));
    bus.emit('foo', { a: 1 });   //→ foo: {a:1} / star: foo {a:1}   同一次派发两趟各跑一次
    bus.emit('bar', { b: 2 });   //→ star: bar {b:2}                无人订阅 bar，第二路径仍触发
    ```

- **正文不宜展开的细节**：通配符处理器的泛型签名如何由用户那张事件映射反推（属第 7 章『一张 Events 映射派生全 API 类型』）；"可选载荷事件"的条件类型重载（属第 8 章）；遍历用 `map` 还是 `forEach`、为何先复制数组（属第 5 章，本章只指出第二路径**同样**借用了这个快照手法）；非空断言等类型边角。

- **推荐的一个执行轨迹例子**：
  - 初始：表为空。
  - 订阅 `foo` 与通配符 → 表：`{ foo:[f], '*':[g] }`。
  - `emit('foo', {a:1})`：第一趟命中 `[f]`，单参调用 `f({a:1})`；第二趟命中 `[g]`，双参调用 `g('foo', {a:1})`。
  - 输出：`f` 收到 `{a:1}`；`g` 收到 `('foo', {a:1})`。
  - 对比 `emit('bar', {b:2})`：第一趟查 `bar` 落空跳过；第二趟仍命中 `[g]`，调用 `g('bar', {b:2})`——证明 catch-all 与具体类型是否有人订阅无关。

## 概念要点
- 要点 1：通配符就是一个被保留的**普通 Map 键**——类型定义里整张表的键类型显式写成 `keyof Events | '*'`，证明星号并非独立数据结构，而是表里的一个槽位。源码位置: src/index.ts:18-21
- 要点 2：通配符处理器有独立类型，签名是 `(type, event)` 双参，比普通处理器的 `(event)` 单参多出一个"事件类型"参数。源码位置: src/index.ts:5-9
- 要点 3：内部用一个联合类型把两种签名的函数统一塞进同一张表的同一个数组，作为运行时存储的公共类型。源码位置: src/index.ts:49-51
- 要点 4：订阅/退订接口各有两个重载（普通键 + 字面量星号），但**实现体只有一个**——通配符与普通事件共用同一套"查表→追加/移除"逻辑，无任何分支特殊对待。源码位置: src/index.ts:26-27,66-73（订阅）；src/index.ts:29-33,82-91（退订）
- 要点 5：派发接口的两个重载都绑定到普通键类型，**没有**针对星号的重载——类型层面就禁止了手动触发通配符。源码位置: src/index.ts:35-38
- 要点 6：派发实现里有两条独立路径：先查"当前类型"的处理器做单参派发，再查星号槽做双参派发；两趟各自先复制数组快照、各自 `if (handlers)` 短路。源码位置: src/index.ts:104-120
- 要点 7：第二路径调用每个通配符处理器时，把当前事件类型作为第一参数注入：`handler(type, evt!)`。源码位置: src/index.ts:118
- 要点 8：源码注释明确两条规则——星号处理器在类型匹配处理器**之后**调用；手动触发星号不被支持。源码位置: src/index.ts:95-97

## 关键调用链
订阅通配符：`on('*', g)` → `all.get('*')` 为空 → `all.set('*', [g])`（与 `on('foo', f)` 同构，无分支差异）
源码位置: src/index.ts:66-73

派发：`emit('foo', evt)` →
  ① `all.get('foo')` → `slice()` → `handler(evt)`（第一路径，单参）
  ② `all.get('*')`  → `slice()` → `handler('foo', evt)`（第二路径，双参，type 注入）
源码位置: src/index.ts:104-120

## 源码摘录（带行号，全文累计 ≤ 30 行）

export type Handler<T = unknown> = (event: T) => void;
export type WildcardHandler<T = Record<string, unknown>> = (

	event: T[keyof T]

export type EventHandlerMap<Events extends Record<EventType, unknown>> = Map<

派发的两条独立路径（演心智模型步骤 3-7 与权衡 3：无条件第二路径 + 双参注入）：
```ts
emit<Key extends keyof Events>(type: Key, evt?: Events[Key]) {
	let handlers = all!.get(type);
	if (handlers) {
		(handlers as EventHandlerList<Events[keyof Events]>)
			.slice()
			.map((handler) => {
				handler(evt!);
			});
	}

	handlers = all!.get('*');
	if (handlers) {
		(handlers as WildCardEventHandlerList<Events>)
			.slice()
			.map((handler) => {
				handler(type, evt!);
			});
	}
}
```
源码位置: src/index.ts:103-121

## 易混淆 / 边界 / 推断
- 事实：通配符处理器**固定**排在类型匹配处理器之后触发，顺序不可配置（注释明示）。源码位置: src/index.ts:95
- 事实：测试只注册了星号处理器、未注册被发射的类型，但派发仍触发了星号处理器，且其收到的参数是 `('foo', ea)` 双参——同时验证了"第二路径独立于第一路径"与"双参注入真实类型"。源码位置: test/index_test.ts:189-202
- 推断（标注为推断）：手动 `emit('*')` 之所以被刻意禁止，深层原因是双路径设计：若强行触发星号类型，第一路径会以单参调用星号处理器（参数错位，类型当成事件、第二参丢失），紧接着第二路径又以双参正确调用一次——同一个星号处理器会被触发两次且第一次参数错位。这是双路径 + 签名差异的直接推论，而非任性限制。
- 事实：第二路径与第一路径共享同一张表，因此第 5 章的"快照式派发"对通配符路径同样生效——星号处理器在自己的派发中途去订阅/退订/清空，也不会漏触发或重复触发（承前复用）。
- 推断：第二路径每次派发都无条件查一次星号槽，作者宁可多一次查找也不维护"是否存在通配符订阅者"的标志位，符合该库一贯的极简哲学。
- 未理解：无重大未理解项。
