# 一张 Events 映射派生全 API 类型 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：用一个发布订阅库时，如果没有类型联动，监听器和触发器只能是宽泛的"事件名 + 任意回调"——传错载荷类型（给一个字符串事件传了数字）编译期完全不报错，等运行时才炸；若要安全，又得为每个事件手写一套重载或具名方法，样板代码随事件数线性膨胀。用户真正想要的是：只声明一份"事件名→载荷类型"的清单，之后每个监听/触发调用点的参数类型自动按这份清单查表得出。

- **一句话核心思想**：一处定义事件清单，所有监听/触发 API 的参数类型自动按这张清单查表得出。

- **设计动机（为什么需要它）**：运行时的那张"事件名→处理器数组"查找表，与监听/移除/派发的实现（无 this 的闭包方法、首次注册即建表、位运算抹平边界、快照式派发）已在第 2~5 章讲透，本章只看它的**类型层外衣**——给那张运行时查找表套上一层"键→值类型"的类型映射，让运行时的 key→value 关系在类型层也成立。它要解决的矛盾是：**运行时存储是异质的**（一张表/一个数组装着所有事件类型的处理器），**但类型层想让每个调用点是同质且精确的**（监听某个事件就只接受该事件的载荷）。"运行时异质 vs 类型层精确"这一张力，正是本章全部设计的出发点。

- **关键权衡（本 Atlas 的核心，4 条）**：
  1. **以单张映射表作为唯一类型源**：选择让用户只供给一个"事件名→载荷类型"的类型参数（其值类型上界为 unknown，故载荷可任意）→ 换来"一处定义、全 API 派生"，监听回调里的事件参数自动收窄为该键的值类型，声明成本仅一张类型字面量 → 代价是事件清单必须**静态**（编译期已知），无法运行时动态增删事件类型并保持类型安全。
  2. **用"键"类型参数反向索引，而非正向具名枚举**：选择每个方法都声明一个"键"类型参数（约束为映射表所有键的子集），让类型检查器从**调用点的事件名字面量**反向推断出"键"、再从映射表查出对应载荷类型 → 换来事件名与载荷**自动联动**（换事件名则载荷类型随之收窄），无需为每个事件手写一套具名方法 → 代价是推断**依赖字面量实参**（必须传字符串字面量而非宽泛的字符串变量，否则"键"退化为全联合、载荷也随之退化），且事件名要同时充当运行时键与类型键、二者必须同名同形。
  3. **内部存储用联合类型 + 类型断言，换取类型层与运行时解耦**：选择在实现里把所有处理器揉成一个"所有事件类型处理器的联合"，存取时用类型断言在"联合"和"具体"之间转换 → 换来运行时只需**一个异质容器**（与极简状态章一致），公开接口对外呈现精确类型、内部实现却保持异质与极小 → 代价是类型断言是**不安全的逃生口**，类型系统不再校验存取一致性，类型安全仅存在于公开 API 边界、越过边界进入实现即退化为联合。
  4. **通配符星号用独立的具体重载，而非并入泛型签名**：选择为监听/移除各写两个签名——泛型版（键为任意事件名）+ 具体版（键固定为通配符星号、处理器为双参）→ 换来通配符处理器有**独立且精确的双参签名**（第一参为事件名联合、第二参为全载荷联合），且通配符字面量与事件名键正交、不冲突 → 代价是每加一个通配符相关 API 签名数翻倍，且通配符处理器的载荷是**全联合**、失去逐事件的精确性，用户须自行收窄。

- **最小心智模型（7 步）**：
  1. 用户传入一张"事件名 → 载荷类型"的映射表，作为整个发射器唯一的类型源。
  2. 每个方法（监听/移除/触发）声明一个"键"类型参数，约束为"映射表所有键的子集"。
  3. 调用时，类型检查器从第一个实参（事件名字面量）推断出"键"，再从映射表查得对应载荷类型。
  4. 该载荷类型被自动套用到第二个参数（回调的事件参数 / 触发的实参），实现"事件名 ↔ 载荷"联动。
  5. 与此同时，运行时存储刻意保持异质：一个数组装着所有事件类型的处理器，类型上是一个联合。
  6. 写入时用类型断言把"具体回调"塞进异质联合容器；读出时再用类型断言转回"具体回调"。
  7. 净效果：公开 API 边界处类型精确联动，越过边界进入实现则退化为联合——**类型安全是一种边界属性**。

- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个几十行的 TypeScript 类型化发射器骨架——定义 `TypedEmitter<Events>`，实现 `on<Key extends keyof Events>(type: Key, handler: (e: Events[Key]) => void)`，内部用一个联合/any 数组存储并配类型断言存取；然后展示"监听某事件时回调参数自动收窄""误传不兼容回调则编译报错"。这段演示演的是**权衡 2（反向索引联动）+ 权衡 3（联合存储与断言）**。
  - **应故意省略**：通配符第二条路径（留作练习或省略）、移除/触发的完整实现（仅保留监听足以演透核心）、可选载荷的条件类型判定（属下一章）、运行时发布订阅行为（前置章已讲）。
  - **演示载体建议：本章选 TypeScript（首选）**。核心原理是**编译期类型派生**——泛型类型参数的反向推断、键类型查询、联合类型、类型断言——这些是 TypeScript 类型系统特有的语义，**纯 JavaScript 没有类型层、根本讲不透**，因此必须用带类型的 TS 演示（TS 本就是原仓库语言、亦属 JS 生态，对读者最友好）。配最小 `package.json`，用 `tsc --noEmit` 做编译期类型检查来验证"收窄"与"报错"两个效果。一句话：**载体是 TS，因为本章演的就是类型层；离了类型层，原理不复存在。**

- **正文不宜展开的细节**：触发方法用条件类型 `undefined extends Events[Key] ? Key : never` 区分"可选载荷事件"的那条重载——属紧邻下一章的核心，本章只展示触发的基础双参签名、点到为止；`Record<EventType, unknown>` 中 unknown 上界为何不用 any 的细节；可选属性 `bar?: number` 在键查询下展开为 `number | undefined`（正是下一章条件类型所利用的点）；严格函数类型模式下函数参数变异性（为何通配符处可传入更窄回调的深层原因）；全值联合 `Events[keyof Events]` 与单值 `Events[Key]` 的区分。

- **推荐的一个执行轨迹例子**：输入 `{ foo: string; someEvent: {name:string}; bar?: number }` 这张映射表，并监听 `foo` 事件传入一个回调 → 关键中间态：类型检查器从字面量 `'foo'` 推断"键"为 `'foo'`、查表得载荷类型 `string`、回调签名锁定为"(事件: string) => void" → 输出：回调体内事件参数类型为 `string`；若误传"(事件: number) => void"的回调，则在编译期报错。这条轨迹演的是"反向索引联动"这一个核心思想，不演全量调用。

## 概念要点
- 整个类型系统的**唯一输入源**是函数工厂的那个类型参数，约束为"以事件类型为键、unknown 为值上界"的记录类型，意味着载荷可以是任何类型（含 undefined）。 源码位置: src/index.ts:46
- 监听方法有**两条重载**：一条泛型版（键为任意事件名、处理器为"该键值类型的单参函数"），一条具体版（键固定为通配符星号、处理器为双参）。 源码位置: src/index.ts:26-27
- 反向推导骨架就在泛型版签名里："键"约束为映射表所有键的子集，处理器参数类型由 `Events[Key]` 查表得出——这正是"事件名↔载荷联动"的来源。 源码位置: src/index.ts:26
- 移除方法与监听**同构**：同样一个泛型版 + 一个通配符具体版，handler 还可选（省略即清空，属前置章运行时语义）。 源码位置: src/index.ts:29-33
- 触发方法的**基础签名**也是同套反向索引（`type: Key, event: Events[Key]`）；其第二条条件类型重载（`undefined extends Events[Key] ? ...`）属下一章，本章不展开。 源码位置: src/index.ts:35-38
- 内部实现把所有处理器揉成**一个联合类型**（所有事件类型处理器 ∪ 通配符处理器），这是"运行时异质存储"在类型层的直接表达。 源码位置: src/index.ts:49-51
- 写入新数组时用 `as` 把联合成员**断言回具体类型数组**——类型系统不再校验这次转换。 源码位置: src/index.ts:71
- 容器类型本身也是联合友好的：映射表的值类型被声明为"所有键的值类型之并"的数组，而非某个具体键的数组。 源码位置: src/index.ts:18-21
- 单事件处理器为 `(event: T) => void`；通配符处理器为双参 `(type: keyof T, event: T[keyof T]) => void`——后者第二参是**全载荷联合**。 源码位置: src/index.ts:5-9
- 测试用 `mitt<{ foo: string; someEvent: SomeEventData; bar?: number }>()` 建立三键映射（含一个可选键），逐条验证类型联动。 源码位置: test/test-types-compilation.ts:9-13
- 测试验证监听联动：给字符串事件传数字回调会报错（`@ts-expect-error`）、传匹配回调则通过。 源码位置: test/test-types-compilation.ts:25-39
- 测试验证移除联动：与监听完全同构的一组正反例。 源码位置: test/test-types-compilation.ts:44-58
- 测试验证触发联动：载荷类型不符即报错；可选键 `bar` 的无参与有参触发均合法（无参那条走的是下一章条件类型）。 源码位置: test/test-types-compilation.ts:60-78

## 关键调用链
类型推导链（公开 API 边界）：
调用 `on('foo', handler)` → 类型检查器从字面量 `'foo'` 推断 `Key = 'foo'`（满足 `Key extends keyof Events`）→ 签名展开为 `handler: (event: Events['foo']) => void` → 在调用点校验 handler 是否兼容。
源码位置: src/index.ts:26

实现内部存储链（越过边界，退化为联合）：
`on(type, handler)` → `all.get(type)` 返回联合数组 → 命中则 push、未命中则 `all.set(type, [handler] as EventHandlerList<...>)` 用断言包装。
源码位置: src/index.ts:66-72

## 源码摘录（带行号，全文累计 ≤ 30 行）

类型层骨架——演权衡 1（单表为源）+ 权衡 2（键反向索引联动）：

```ts
// src/index.ts:46-48 — 唯一类型源：一张事件名→载荷(上界 unknown)的映射
export default function mitt<Events extends Record<EventType, unknown>>(
	all?: EventHandlerMap<Events>
): Emitter<Events> {
// src/index.ts:26-27 — 监听的两条重载：泛型反向索引 + 通配符具体签名
on<Key extends keyof Events>(type: Key, handler: Handler<Events[Key]>): void;
on(type: '*', handler: WildcardHandler<Events>): void;
// src/index.ts:35 — 触发的基础签名（载荷同样由 Key 反查；条件类型那条属下一章）
emit<Key extends keyof Events>(type: Key, event: Events[Key]): void;
```

内部存储——演权衡 3（联合 + 断言）+ 权衡 4（通配符全联合双参）：

```ts
// src/index.ts:49-51 — 所有处理器揉成一个联合（运行时异质容器的类型表达）
type GenericEventHandler =
	| Handler<Events[keyof Events]>
	| WildcardHandler<Events>;
// src/index.ts:71 — 写入时用 as 把联合成员断言回具体数组（不安全的逃生口）
all!.set(type, [handler] as EventHandlerList<Events[keyof Events]>);
// src/index.ts:6-9 — 通配符处理器：双参，第二参是全载荷联合（失去逐事件精确性）
export type WildcardHandler<T = Record<string, unknown>> = (
	type: keyof T,
	event: T[keyof T]
) => void;
```

## 易混淆 / 边界 / 推断
- **事实**：约束用 `Record<EventType, unknown>` 而非 `Record<EventType, any>` 作值上界——unknown 会强制调用方显式收窄、保留类型安全，但仍允许任意载荷（含 undefined）。 源码位置: src/index.ts:46
- **事实**：用户传具体字面量对象类型 `{ foo: string }` 也能满足该约束（结构子类型），不必显式写 `Record`。 源码位置: test/test-types-compilation.ts:9-13
- **推断**：可选属性 `bar?: number` 使键查询 `Events['bar']` 展开为 `number | undefined`——这正是下一章条件类型"能否无参触发"判定的依据；本章视为边界、不展开。 源码位置: test/test-types-compilation.ts:12,74
- **事实 + 推断**：测试中给通配符星号传一个 `(x: string)=>void` 的窄回调是合法的——因为通配符处理器第一参是事件名联合 `'foo'|'bar'|'someEvent'`（这些字面量可赋给 string），且回调可忽略第二参；而 `(x?: number)=>void` 非法，因为 number 不能接受字符串联合。源码注释明确点出此原因。 源码位置: test/test-types-compilation.ts:35-36,17-20
- **推断**：类型安全是"边界属性"——公开 `Emitter` 接口对外精确，实现内部一律走联合 + 断言，故库自身实现代码的类型正确性不靠类型系统验证、而靠作者人为保证（"存时 Key 与 Events[Key] 对应、取时断言回正确类型"）。
- **边界（跨章去重信号）**：触发方法的条件类型重载 `undefined extends Events[Key] ? Key : never` 是紧邻下一章（条件类型区分可选载荷事件）的主角，本章只引用其存在、不展开原理。
- **未理解**：无显著未理解项；本文件类型层机制清晰，唯一晦涩点（条件类型重载）已划归下一章。
