# 快照式派发抵御中途改表 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：一个事件触发时，某个处理器在执行过程中顺手把自己或别的处理器注销掉（甚至清空整个类型），又或者新注册一个处理器。如果没有保护，正在进行的这一次派发就会"脚下地板被抽走"——该触发的被跳过、不该触发的被重复触发，顺序与次数变得不可预测。使用者根本没法推理"我这次 emit 到底会调到谁"。

- **一句话核心思想**：**派发前先把处理器名单冻结一份副本，本次遍历只认这份快照，外界对原表的任何改动都影响不到正在跑的这一轮。**

- **设计动机（为什么需要它）**：发布订阅的注册表是一张可变的活动数组，而"派发"恰恰是要遍历这张数组、并把控制权交给用户回调——回调里天然可以反手改这张表。这就构成了"一边遍历一边被改"的根本矛盾。本章机制正是为化解它而生：在交出控制权（调用第一个处理器）之前，先把名单拍成静态快照。
  - 承前关系①：注册端用 push 往活动数组追加新处理器——**（已在第 3 章『惰性初始化的追加式订阅』讲透 push 追加语义，本章只看它的新侧面：当 push 发生在派发中途时，会对正在进行的遍历构成"意外纳入新成员"的威胁）**。
  - 承前关系②：注销端用 splice 删一个、或用整表替换成空数组来清空——**（已在第 4 章『无分支安全移除与重载清空』讲透这两种原地改写语义，本章只看它的新侧面：当它们发生在派发中途时，splice 会造成下标漂移、整表替换会让"当前数组"语义模糊，二者都对遍历构成"漏触发"威胁）**。
  - 本章不重复讲 on/off 本身，只讲 emit 如何在它们之上做安全的遍历。

- **关键权衡（本 Atlas 的核心）**：
  1. **选择在 emit 入口对处理器数组做浅拷贝再遍历 → 换来了"本次派发集合在 emit 被调用的那一刻就被冻结"的强确定性，对中途任意 on/off/clear 完全免疫 → 代价是每次 emit 都多一次 O(n) 的数组分配与拷贝；并且语义上"中途被 off 掉、但还没轮到的处理器，本轮依然会触发"（移除要到下一次 emit 才真正生效），这与"立刻不触发"的直觉相悖，需要文档化。**（这是全章主权衡，务必讲透。）
  2. **选择用 `.map` 当作遍历器（而非语义更贴切的 `.forEach`）→ 换来更短的方法名（契合库 "~200b" 的极致体积目标）→ 代价是把"映射"语义错用为"副作用循环"、且 `.map` 还会再分配一个随即被丢弃的结果数组，可读性轻微下降。**（推断为体积优先；标注为推断。）

- **最小心智模型（3～7 步）**：
  1. emit 被调用，先从注册表里取出该事件类型的"活动处理器数组"（这是会被 on/off 原地改写的引用）。
  2. **入口立即对这份活动数组拍一份浅拷贝**——这就是本次派发的"冻结名单"。
  3. 依次对冻结名单里的每个处理器调用，传入事件载荷，把控制权交给用户代码。
  4. 某个处理器在执行中调用 on / off / clear，改的都是注册表里的"活动数组"，而不是手里这份快照。
  5. 因此本次派发从头到尾只跑"emit 入口那一刻"的名单：被中途删掉的仍会跑（不漏），中途新加的不会跑（不重）。
  6. （旁路）类型匹配的名单跑完后，通配符名单会用同样的"先拍快照再遍历"方式再跑一遍——快照原理对两条路径通用。

- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个极简 emitter，只演透"快照 vs 不快照"的差异。构造两个处理器 a、b（a 注册在前、b 在后），让 a 的函数体里当场把 b 注销掉，然后触发事件。**对比两版**：有快照版里 b 仍然被调用（因为它在入口快照里）；无快照版（直接遍历活动数组）里 b 被跳过（注销使下标漂移）。这一组对比演的就是上面的主权衡①——"冻结名单"到底换来了什么、代价是什么。整个演示只需几十行。
  - **应故意省略**：通配符第二条派发路径（下章讲）、泛型与类型签名、事件载荷的多种形态、symbol 私有频道、大小写不归一化、生产级的错误隔离（单个 handler 抛错的处理）——这些都不是"快照原理"的必要组成。
  - **演示载体建议**：**首选 TS/JS**。本章核心是"遍历一个数组时它被中途改写会出什么问题、复制一份就能免疫"——这是纯粹的数组遍历与可变性原理，TS/JS 完全能忠实演透，配一个最小 `package.json` 让读者 `node`/`bun run` 即可跑出"b 是否被调用"的对照结果。无需退回原仓库语言。

- **正文不宜展开的细节**（供 Writer 裁剪）：通配符 `'*'` 为何是独立第二条路径（属下一章）；`as` 类型断言与 `evt!` 非空断言仅是内部存储类型擦除的补救（属类型推导章）；`.map` 返回值被丢弃这一代码风格瑕疵；symbol 作为私有事件频道、字符串大小写刻意不归一化（已在更早章覆盖）。

- **推荐的一个执行轨迹例子**：`on('foo', a)` → `on('foo', b)` → 在 `a` 函数体里 `off('foo', b)` → `emit('foo')`。**有快照**：入口名单=[a,b]，依次调用 a（此时活动表里 b 被删，但快照不变）、b 仍被调用 → 共触发 2 次。**无快照（直接遍历活动数组）**：调完 a 后活动表=[a]，b 被跳过 → 只触发 1 次。这条轨迹直接演透主权衡①。

## 概念要点

- **快照发生在"取数组之后、调用任何处理器之前"**：emit 取出某类型的活动数组后，第一步就是对它 `.slice()` 复制，再对副本遍历调用。复制动作严格先于任何用户回调，这是安全性的时序前提。源码位置: src/index.ts:104-110
- **快照原理对两条派发路径都成立**：类型匹配路径和通配符路径各自独立地"取数组 → `.slice()` → 遍历"。本教的是二者共享的快照思想；通配符为何单独成一路是下一章主题。源码位置: src/index.ts:104-110（类型路径）, src/index.ts:113-120（通配符路径）
- **遍历器选用 `.map` 而非 `.forEach`，返回值被丢弃**：`.slice().map(h => h(evt))` 把 map 当副作用循环用，map 的返回数组未赋值给任何变量、随即被 GC。功能上与 `.slice().forEach(...)` 等价（安全性都来自 `.slice()`），选用 map 推断为缩短方法名以压体积。源码位置: src/index.ts:107-110
- **威胁遍历的"改表"来自 on 与 off 两个方向**：
  - 注册方向活动数组 `push` 新处理器（中途 on 会"意外纳入新成员"）。
  - 注销方向用 `splice` 删单个（造成下标漂移、被删元素后的处理器被跳过或错位），或用 `all.set(type, [])` 整表替换清空。
  - 快照使这三种原地改写都不影响本轮遍历。源码位置: src/index.ts:69（push）, src/index.ts:86（splice）, src/index.ts:88（set 空数组）
- **快照带来"移除延迟一拍生效"的语义**：中途被 off 掉、但尚未轮到的处理器，因仍在入口快照内，本轮照样触发；真正的移除要到下一次 emit 才生效。这是"入口冻结名单"的直接推论，需对用户讲清。源码位置: src/index.ts:104-110（结合 off 的 splice 语义推断）
- **测试套件未直接覆盖"中途改表"场景**：emit 的测试只验证了"正常触发单个处理器""大小写不归一化""通配符触发"，没有任何用例在处理器内部调用 on/off 来断言快照行为。快照的防御动机在仓库内没有对应的回归测试，属"为正确性而设、但未被测试直接主张"的推断。源码位置: test/index_test.ts:160-203

## 关键调用链

`emit(type, evt)` → `all.get(type)` 取活动数组 → `.slice()` 拍快照 → `.map(h => h(evt))` 遍历副本逐个调用处理器 →（处理器体内可能）`on`/`off` 反手改 `all` 里的活动数组 →（本轮遍历不受影响，因遍历的是副本）→ 类型路径结束后 → `all.get('*')` → 同样 `.slice()` → `.map(h => h(type, evt))` 跑通配符路径。
源码位置: src/index.ts:103-121

## 源码摘录（带行号，全文累计 ≤ 30 行）

emit 类型路径的"先快照、再遍历"（本章主角）：
源码位置: src/index.ts:103-111

```ts
emit<Key extends keyof Events>(type: Key, evt?: Events[Key]) {
	let handlers = all!.get(type);
	if (handlers) {
		(handlers as EventHandlerList<Events[keyof Events]>)
			.slice()
			.map((handler) => {
				handler(evt!);
			});
	}
```

改表威胁源①——on 的 push（向活动数组追加）：
源码位置: src/index.ts:66-73

```ts
on<Key extends keyof Events>(type: Key, handler: GenericEventHandler) {
	const handlers: Array<GenericEventHandler> | undefined = all!.get(type);
	if (handlers) {
		handlers.push(handler);
	} else {
		all!.set(type, [handler] as EventHandlerList<Events[keyof Events]>);
	}
}
```

改表威胁源②——off 的 splice 删除与 set([]) 清空（两种原地改写）：
源码位置: src/index.ts:82-91

```ts
off<Key extends keyof Events>(type: Key, handler?: GenericEventHandler) {
	const handlers: Array<GenericEventHandler> | undefined = all!.get(type);
	if (handlers) {
		if (handler) {
			handlers.splice(handlers.indexOf(handler) >>> 0, 1);
		} else {
			all!.set(type, []);
		}
	}
}
```

## 易混淆 / 边界 / 推断

- **事实**：`.slice()` 是无参调用，等价于"浅拷贝整个数组"，复杂度 O(n)；每次 emit 必然发生（只要该类型/通配符有处理器），无任何惰性或缓存优化。源码位置: src/index.ts:107, src/index.ts:116
- **事实**：`on`/`off`/`emit` 共享同一个闭包变量 `all`（注册表 Map），且都通过 `all!` 非空断言访问——这意味着派发中途调用 on/off 改的就是 emit 正在读取的同一张表，快照是隔离二者的唯一手段。源码位置: src/index.ts:52, src/index.ts:67, src/index.ts:83, src/index.ts:104
- **推断**：选用 `.map`（而非 `.forEach`）当遍历器、并丢弃返回值，目的是缩短方法名以契合 "~200b" 体积目标（map 3 字符 vs forEach 7 字符）；安全性完全来自前置的 `.slice()`，与用 map 还是 forEach 无关。仓库无注释说明此选择，故标注为推断。源码位置: src/index.ts:107-110
- **推断**：快照语义与 Node.js `EventEmitter` 一致（Node 也是在触发时克隆 listeners 数组，中途移除的处理器本轮仍触发）。mitt 的 on 测试注释显式引用了 Node EventEmitter 语义作为对齐基准，据此推断快照行为也是同一对齐意图。源码位置: test/index_test.ts:98-99
- **未理解 / 需 Architect/Critic 留意**：测试套件中没有任何"处理器在派发中途改注册表"的用例，快照的防御价值在本仓库内处于"无直接回归测试"状态。Writer 若要演示该机制，应自行构造对照实验（见钩子中的执行轨迹例子），不能指望引用现有测试作为佐证。源码位置: test/index_test.ts:160-203
