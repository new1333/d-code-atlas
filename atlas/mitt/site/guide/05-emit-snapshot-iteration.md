# 快照式派发抵御中途改表

## 一个会"自己拆台"的处理器

想象你在写一个聊天室，给 `user-joined` 事件登记了两个处理器：`logToDb` 负责把这次登录写进数据库，`announce` 负责播报"某某来了"。某天你给 `announce` 加了个小需求——播报完就把自己注销掉，免得刷屏。于是它的函数体里多了句 `off('user-joined', announce)`。

跑起来你愣住了：`logToDb` 这次压根没被调用。它明明登记在前，`announce` 登记在后，凭什么轮不到它？

问题既不在 `logToDb`，也不在 `announce`，而在于"派发"和"改注册表"这两件事撞到一起了。`emit` 正挨个通知处理器，`announce` 在被通知的当口反手改了名单——派发脚下的地板，被它自己抽走了。

这还不算谁在捣乱。一个处理器在执行中顺手注销别人、清空整类、甚至临时塞进一个新处理器，都是再正常不过的需求。真正要回答的问题是：**派发该怎么遍历一张随时会被改的表？**

## 矛盾：一边遍历，一边被改

发布订阅的心脏是一张映射表，把"事件类型"对应到"处理器数组"。`on` 往数组里塞，`off` 从数组里删，`emit` 则要把数组从头到尾走一遍，把事件参数喂给每一个处理器。

关键在于：`emit` 把控制权交出去的那一刻，等于把"改这张表"的权力也一起交了出去。因为用户回调 `handler(evt)` 里，天生可以再调 `on`、再调 `off`。而 `on`、`off`、`emit` 三兄弟，盯的是**同一张表**。

于是矛盾就摆在这了：派发要遍历的那张表，正是可能被它自己遍历到的处理器随手改写的表。一边遍历，一边被改。某个处理器到底会不会被这一轮触发，变得谁也说不准——使用者根本没法推理"我这次 `emit` 到底会调到谁"。

## 三种"抽地板"的方式

先说清楚：`on` 怎么塞、`off` 怎么删，前面两章已经讲透了——`on` 是往活动数组末尾 `push`（第 3 章），`off` 是用 `splice` 删一个、或把整张表替换成空数组来清空（第 4 章）。这里不重讲这些动作本身，只看它们发生在**派发进行中**时，对"直接遍历活动数组"这种朴素写法会闯什么祸。

假设我们天真地用下标循环遍历那张会被改的活动表：

```js
for (let i = 0; i < handlers.length; i++) {
  handlers[i](evt);   // ← 遍历的就是这张会被原地改写的表
}
```

那么改表会从三个方向抽掉地板：

- **删一个（splice）→ 下标漂移，后面的被跳过**。名单是 `[a, b, c]`，遍历到 `a` 时，`a` 顺手 `off(c)`，`c` 被删，数组原地变成 `[a, b]`，元素整体左移一格。循环的下标还在按部就班地往前走，结果 `b` 被错位、`c` 直接消失——该触发的没触发。这正是开场那个 `logToDb` 消失的原因。
- **加一个（push）→ 新成员被这一轮顺手捎带**。`a` 执行时临时 `on` 了一个 `d`，数组从 `[a, b]` 变成 `[a, b, d]`，循环一不小心就走到了 `d`。可 `d` 在 `emit` 被调用的那一刻根本还没登记——它本不该出现在这一轮里。
- **清空（替换成空数组）→ 名单凭空少了一截**。`a` 执行时把整类清空，剩下的处理器要么集体消失，要么进入"该跑的到底还跑不跑"的灰色地带。

三种改法的共同后果只有一个词：**不可预测**。轮到谁、跑几次、顺序对不对，全看改表恰好发生在哪个下标上。

## 解法：进门先把名单复印一份

把问题想成点名。你拿着一张名单挨个念名字，但这张名单是张"活名单"——谁都能往上涂改。你念到张三，张三站起来顺手把李四的名字划掉了；等你念下一个，李四就没了。怎么防？最朴素也最稳的办法：**点名之前，先把名单复印一份，这一轮点名只照着复印件念**。活名单随你怎么涂涂改改，复印件纹丝不动。

`emit` 用的就是这个办法。它一进门，做的第一件事不是调任何处理器，而是先把当前这张活动数组复制一份（在 JS 里就是无参的 `.slice()`）。本轮遍历从头到尾只认这份副本，外界对原表的所有改动，都溅不到这份副本上。

复制这件事的时序是铁律：**必须发生在"取出数组之后、调用任何处理器之前"**。只要在交出控制权之前拍好快照，之后再怎么 `on`、`off`，都只动那张活动表，碰不到手里这份冻结的副本。

文字版流程：

```
emit('foo') 被调用
   │
   ├─ all.get('foo')        取出活动数组（引用，会被 on/off 原地改写）
   │
   ├─ .slice()              进门先复印一份 ← 本轮只认这份
   │
   └─ 遍历副本，逐个 handler(evt)
          │
          └─ handler 体内可能 on / off / 清空
                 改的是 all 里的活动数组
                 ┄┄┄ 这一切，都改不到手里那份副本 ┄┄┄
```

说人话就是：派发一旦开始，本轮"会调到谁"就被锁死了，锁死在 `emit` 入口的那一瞬间。

## 原理演示：快照版 vs 不快照版

光说不练看不出差别。我们手写一个极简 emitter，给它装两个版本的 `emit`：一个直接遍历活动数组（不快照），一个进门先复制（快照）。两个处理器 `a`、`b`，`a` 在执行中把 `b` 注销掉，然后看 `b` 到底还触不触发。

```js
function mitt() {
  const all = new Map();

  const on = (type, handler) => {
    const list = all.get(type);
    if (list) list.push(handler);          // 追加：第 3 章讲过
    else all.set(type, [handler]);
  };

  const off = (type, handler) => {
    const list = all.get(type);
    if (!list) return;
    if (handler) list.splice(list.indexOf(handler) >>> 0, 1); // 删除：第 4 章讲过
    else all.set(type, []);                                     // 清空：第 4 章讲过
  };

  // 版本 A：不快照，直接遍历那张会被改的活动表
  const emitUnsafe = (type, evt) => {
    const handlers = all.get(type);
    if (!handlers) return;
    for (let i = 0; i < handlers.length; i++) {  // ← 边遍历，边被改
      handlers[i](evt);
    }
  };

  // 版本 B：进门先复制，本轮只认副本
  const emitSafe = (type, evt) => {
    const handlers = all.get(type);
    if (!handlers) return;
    const snapshot = handlers.slice();           // ← 复制发生在调任何处理器之前
    for (let i = 0; i < snapshot.length; i++) {
      snapshot[i](evt);
    }
  };

  return { all, on, off, emitUnsafe, emitSafe };
}

// 同一个剧本，分别用两个版本跑一遍
function run(pickSafe) {
  const { on, off, emitUnsafe, emitSafe } = mitt();
  const emit = pickSafe ? emitSafe : emitUnsafe;
  const log = [];
  const b = () => log.push('b');
  const a = () => { log.push('a'); off('foo', b); };  // a 执行时把 b 注销掉
  on('foo', a);
  on('foo', b);
  emit('foo');
  return log;
}

console.log('不快照版：', run(false));  // → ['a']      b 被跳过
console.log('快照版：  ', run(true));   // → ['a', 'b']  b 照常触发
```

存成 `demo.js`，`node demo.js` 就能看到两行对照结果。

**为什么 `b` 的命运不一样？**

不快照版遍历的是那张会被改写的活动表。`a` 一执行，`off` 就把 `b` 从表里删掉，数组从 `[a, b]` 缩成 `[a]`，下标却还在傻乎乎地往前走，`b` 就这么被下标漂移挤掉了——典型的漏触发。

快照版遍历的是进门就复印好的副本。`a` 执行时 `off` 删的是活动表里的 `b`，副本纹丝不动，`b` 安然无恙地待在副本里，照样被叫到。本轮"会调到谁"，在 `emit` 入口那一刻就定死了。

注意一个细节：快照版里 `b` **这一轮照样触发**，哪怕它在 `a` 执行时就已经被 `off` 掉了。换句话说，`off` 的效果要到**下一次 `emit`** 才真正显现。这条"延迟一拍"的语义，正是快照方案自带的代价，下面专门讲。

## 关键权衡

这一章的机制很集中——说白了就一个动作"进门先复制"——所以核心权衡只展开这一条，但要把它讲透。

### 主权衡：复制换确定，代价是分配和"延迟一拍"

**做了什么选择**：在 `emit` 入口，对取出的处理器数组做一次浅拷贝（`.slice()`），本轮遍历只走这份副本，绝不碰那张会被 `on`/`off` 改写的活动表。

**换来了什么**：极强的确定性。本次派发的"触发集合"，在 `emit` 被调用的**那一瞬间**就被冻结了，之后无论处理器怎么 `on`（加）、`off`（删）、清空，都动摇不了这一轮的名单。上一节演示里 `b` 照常触发，就是这个确定性的直接体现——使用者终于能笃定地推理"我这次 `emit` 会调到谁"，而不再取决于改表恰好发生在哪个下标。前面列的三种"抽地板"威胁，被这一个动作一次性全部免疫。

**代价一：每次派发多一次 O(n) 的数组分配与拷贝**。只要这个事件类型有处理器，每次 `emit` 都会复制一整份数组，没有惰性、没有缓存。处理器越多，这口开销越大。对一个标榜"~200b 极小体积"的库来说，这个选择是拿一点 CPU 和内存，去换语义上的安全与可预测——它在字节数上抠门到骨子里，却愿意在每次派发上花一次拷贝，可见"安全遍历"在这套设计里优先级极高。

**代价二：移除要"延迟一拍"才生效**。这是最反直觉的一点，必须跟用户讲清楚。一个处理器在派发中途被 `off` 掉，只要它还没轮到，本轮**照样会触发**——因为它已经躺在入口那份快照里了。真正的移除，要等到下一次 `emit` 重新拍快照时才生效。这跟"我 `off` 了它，它就该立刻不再被调"的直觉正好相反。所以用这类库时，"中途注销自己或别人"是允许的、安全的，但你要知道它的效果不是即时的，而是下一轮才生效。这个语义和 Node.js 的 `EventEmitter` 完全一致——它也是在触发时克隆一份监听器数组，中途移除的本轮照常触发。这里选择对齐这套老牌语义，省得使用者多记一套规则。

一句话收束这条权衡：**用一次数组拷贝，买断了"派发途中改表"带来的全部不可预测**；买来的副作用，是每轮派发的固定开销，以及"移除慢半拍"这个需要写进文档的语义。

### 附带一笔：遍历器为什么用 `.map` 而不是 `.forEach`

你可能在真实代码里注意到，遍历副本的写法是 `.slice().map(handler => handler(evt))`，而不是语义更贴切的 `.slice().forEach(...)`。安全性其实**完全来自前面的 `.slice()`**——只要复制了，用 `map` 还是 `forEach` 来遍历都一样安全。选 `map` 的理由很可能是纯体积考虑：`map` 三个字符，`forEach` 七个字符，对一个死磕字节数的库来说，能短则短。代价是双重的——把"映射"这个本该返回新数组的语义，错用成了"跑一圈副作用"；而且 `map` 还会再分配一个随即被丢弃的结果数组（这点比 `forEach` 多花一次分配）。仓库里没有注释解释这个选择，所以这段是推断；但方向上，它和全库"为字节数让步"的风格是一致的。

## 小结

`emit` 面对的难题，是它要遍历的处理器数组，可能被它自己遍历到的处理器随手改写——一边遍历，一边被改，于是漏触发、多触发、顺序错乱全冒出来。它给出的答案干净利落：**进门先把名单复印一份，本轮只认这份快照**。这一个动作，把 `on` 的 `push`、`off` 的 `splice`、清空的整表替换，统统挡在了本轮派发之外，换来"触发集合在入口瞬间冻结"的强确定性；代价是每轮一次 O(n) 的拷贝，以及"移除延迟一拍生效"这个必须文档化的语义。

值得一提的是，这套"先快照、再遍历"的办法并不只服务于类型匹配这一条派发路径。在这个发射器里，类型匹配的处理器跑完之后，还有第二条派发路径会以同样的方式（取数组 → 复制 → 遍历）再跑一遍——它服务的是那个特殊的保留键 `'*'`。第二条路径为什么要单独存在、它的处理器签名又为什么和普通处理器不一样，正是下一章的主题。
