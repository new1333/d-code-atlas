# 惰性初始化的追加式订阅

> 本章属于 primitive 层。前置：把 pubsub 退化成一张查找表。
> 学完你能用一句话讲清：mitt 的 `on` 为什么「首次才建表、永远追加不查重」，以及这个选择换来了什么、放弃了什么。

## 1. 为什么需要它：写入策略不是只有一种

上一章把发射器的方法和那张查找表用闭包绑在了一起——`mitt()` 返回的对象有了 `on`/`off`/`emit`，三个方法共享同一张表。但方法有了不等于写法定了。`on` 是发布订阅库最常被调用的方法（往某类事件上挂处理器），乍看「不就是把函数塞进数组里嘛」没什么好纠结的，但只要你停下来想，会撞上一连串分叉：

- 表里某个事件类型从来没人监听过，要不要给它预先留一个空数组占位？
- 同一个函数被同一类事件注册了两次，触发时应该叫它一次还是两次？
- 注册时要不要先扫一遍数组，看看这函数是不是已经在里面了？

每一条都没有唯一正确的答案——它们都是在「省内存还是省时间」「信调用方还是信自己扫一遍」「语义贴近直觉还是贴近直觉的反面」之间做选择。mitt 的 `on` 把这几条都讲死成了一条规则，使用者照着走就能预测行为：先查表里有没有这一类，没有才建表，有就往后追加，并且永远不查重。

## 2. 核心思想

**先查表里有没有这一类，没有才建表，有就往后追加——并且永远不查重。**

把这句话拆开，每一段都对应一条刻意的取舍。「没有才建表」是惰性初始化（lazily allocate）：只在某类型第一个处理器到来时才为它创建数组，未监听类型零内存。「有就往后追加」是注册顺序被原样保留的保序写入：注册了三个处理器，触发时就按登记顺序叫一遍。「永远不查重」是直接对齐 Node.js 标准 EventEmitter 的语义：把「去重」这件事的责任明明白白甩给调用方。

## 3. 心智模型

那张查找表是 `Map<事件类型, 处理器数组>`（第 1 章已经讲透，本章直接用）。`on(type, handler)` 一次注册的全部动作只有六步：

1. 注册调用到来，带着 `type`（事件类型）和 `handler`（处理器）两个参数。
2. 向那张表查 `type` 当前对应的数组——一次 `get`，同时回答「这个类型存在吗」和「把数组给我」两件事。
3. 查到的是已存在的数组 → 把 `handler` push 到末尾，注册顺序被原样保留。
4. 查到的是 `undefined`（这种类型头一回被注册）→ 新建 `[handler]`，登记进表。
5. 全程不检查 `handler` 是否已经登记过——同一个函数可以在数组里出现 N 次。
6. 净效果：表里每一个被注册过的类型，都持有「按注册顺序排列、允许重复」的处理器序列；从未被注册过的类型，在表里压根不存在。

这套心智模型有一条不变式撑着它：**已存在的类型键，其值永远是一个数组对象，永远是真值**。哪怕后续用 `off` 把某类型的处理器全清空，mitt 也只是把空数组留在那儿（`all.set(type, [])`），不会 `delete` 这个键——所以「拿到真值就追加、拿到 `undefined` 就建表」这条分支永远成立。

## 4. 关键权衡

这一章的高潮不在演示代码里——演示代码只有 8 行。高潮在下面三条权衡上：写入路径上的每一个分叉，mitt 都做了一个明确选择，并把这个选择的代价也一并吃下去了。

### 惰性建表，而非为每个类型预留空数组

**选择**：只在某类型第一个处理器到来时，才为它创建数组；之前对它零分配。

**换来**：表里只出现真正有人监听的类型键。一个事件系统里可能写了几十上百种事件名，实际被用到的往往只有三五类——预分配会让表里堆满「空数组占位」的死键，惰性建表让这些类型零内存、零开销。派发时同样省事：一次 `get` 拿到 `undefined` 即可立刻短路返回，连遍历空数组的开销都省了。

**代价**：相比「为每个事件类型预分配空数组、注册时无条件 `push`」的写法，每次注册要多一次 `get` + 一个 `if` 分支。开销不大但确实存在，mitt 认为换来的「表里零死键」值得付这笔小钱。

**化解的矛盾**：内存占用（表越大越费）与代码简洁（不想写两套分支）之间的矛盾——mitt 选了「写两套分支换零死键」。

### 追加不查重，把去重责任交给调用方

**选择**：拿到已存在的数组就直接 `push`，不做任何「这个 handler 是否已经在数组里」的检查。

**换来**：注册路径严格 O(1)——一次 `get` + 一次 `push`，没有遍历、没有比较。代码也最短，整个 `on` 方法体只有 6 行。语义完全可预测：注册了几次，派发时就响几次，使用者照「我挂了几次」的直觉走就行。

**代价**：重复注册同一函数，会在派发时被多次调用——这是发布订阅库里最常见的「误用源」。React 组件挂载时如果在 `useEffect` 里忘了清掉旧监听又注册了新的，往往会撞上「为什么我的回调被叫了三次」。mitt 的态度是：这种去重我不管，由你调用方负责（可以先 `off` 再 `on`）。测试代码直接引用 Node.js EventEmitter 文档作为契约——同一个 listener 多次注册应被登记多次，这是明文对齐，不是疏忽。

**化解的矛盾**：「调用方希望库帮我把关」与「库希望最小代码、可预测语义」之间的矛盾——mitt 选了后者，把责任划得清清楚楚。

### 用「查到的值」本身做存在性判断，而非先 has 再 get

**选择**：用 `all.get(type)` 的返回值（数组对象或 `undefined`）的真假来分支，而非先 `all.has(type)` 问有没有、再 `all.get(type)` 取数组。

**换来**：一次 `get` 同时回答了「这个类型存在吗」和「把数组给我」两件事，省掉一次冗余的 `has` 查询。在热路径上，省下的一次哈希查询是实打实的。

**代价**：依赖「数组对象恒为真值」这条不变式。一旦某天有人把已存在的键存成了空数组对象以外的判假值（`null`、`0`、`""`），这条分支就崩了。mitt 靠两条规则守住这条不变式：建表时永远存数组、清空时永远存空数组对象（不 `delete`），所以它永远成立。

**化解的矛盾**：「需要知道有没有」与「需要拿到值」这两个查询之间的冗余——用一次查询的两个语义（真值/假值 + 实际内容）一并回答。

## 5. 最小原理演示

下面这段代码就是 mitt `on` 方法的全部灵魂——8 行，只演「惰性建表」和「追加不查重」两条权衡。通配符派发、移除、类型泛型、symbol 私有频道全部故意省略，那些是后面几章的事。

```js
// 唯一状态：事件类型 -> 处理器数组（第 1 章已经讲透）
const table = new Map();

function on(type, handler) {
  // 一次 get 同时回答两件事：类型存在吗？把数组给我
  const list = table.get(type);
  if (list) {
    // 已有数组就追加，不查重，注册顺序被原样保留
    list.push(handler);
  } else {
    // 首次注册才建表，之前对这个类型零内存占用
    table.set(type, [handler]);
  }
}

// 三次注册，看表里的最终形态
const h1 = () => console.log('h1');
const h2 = () => console.log('h2');

on('foo', h1);
on('foo', h2);
on('foo', h1);   // 同一个函数第二次注册，照样追加进去

console.log(table.get('foo'));   // [h1, h2, h1] —— 追加保序 + 不去重
console.log(table.has('bar'));   // false —— 从未被注册的类型零占用
```

跑一遍这段，输出会精确地是 `[h1, h2, h1]` 和 `false`。`h1` 在数组里出现两次——这不是 bug，是明文契约。派发 `foo` 时 `h1` 会被叫两遍。

## 6. 执行轨迹

输入是一张刚建好的空表（`new Map()`），跟着三次注册调用，看表怎么一步步变化：

```
状态0：table = Map {}

注册('foo', h1)
  → table.get('foo') 返回 undefined        // 类型不存在
  → else 支：table.set('foo', [h1])
状态1：table = Map { 'foo' => [h1] }

注册('foo', h2)
  → table.get('foo') 返回 [h1]             // 真值，类型已存在
  → if 支：[h1].push(h2)
状态2：table = Map { 'foo' => [h1, h2] }

注册('foo', h1)                             // 同一函数再次注册
  → table.get('foo') 返回 [h1, h2]         // 真值，类型已存在
  → if 支：[h1, h2].push(h1)               // 不查重，照样追加
状态3：table = Map { 'foo' => [h1, h2, h1] }
```

之后如果触发 `foo` 事件，发射器会按 `[h1, h2, h1]` 的顺序调用三次——`h1` 被叫两次，`h2` 被叫一次。这就是「追加保序 + 永不查重」在运行时的具体长相。

## 7. 教学简化说明

本章演示故意省略了：

- `mitt()` 工厂壳与 `all` 参数注入（属第 2 章「函数工厂与无 this 的方法」）；
- 注册方法的泛型签名 `Key extends keyof Events` 与内部 `as` 断言（属第 7 章「一张 Events 映射派生全 API 类型」）；
- 通配符 `'*'` 在注册端没有特殊待遇——它只是又一个会被惰性建表的普通键，特殊性全在派发端（属第 6 章「通配符星号的第二条派发路径」）；
- 事件类型允许 `symbol`、不做大小写归一化（属第 1 章）；
- 移除/清空逻辑（属下一章「无分支安全移除与重载清空」）。

## 8. 小结

mitt 的 `on` 用 6 行代码把写入策略钉死成一条规则：表里有这一类就追加，没有就建表，永远不查重。这条规则的精妙不在「简洁」，而在它把每一份代价都明明白白地分配出去——内存归零的代价是「每次注册多一次存在性判断」，最短代码和可预测语义的代价是「去重归调用方管」。下一章接着这张表写另一个动作：当你想把某个处理器从表里拿掉、或干脆清空整类事件时，mitt 又用一种位运算的小把戏把分支省掉了。
