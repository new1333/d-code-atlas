# 无分支安全移除与重载清空

> 本章属于 primitive 层。前置：把 pubsub 退化成一张查找表、惰性初始化的追加式订阅。
> 学完你能：讲清「为什么 mitt 的 off 敢于把 `indexOf` 的 -1 直接喂给 splice、以及为什么省略处理器就清空」。

## 1. 为什么需要它

上一章讲了「首次注册即建表、不去重地追加」——既然注册时不挑食地往列表里 push，移除这一侧就立刻要面对两个边界：要删的处理器可能根本没在列表里；更甚者，要删的事件类型压根没注册过。

最朴素的写法会自然长成这样：先 `indexOf`，再 `if (i >= 0) splice(i, 1)`，外层还要包一层 `if (handlers)` 防类型未注册。三个分支、两个临时变量。在普通业务里这是再正常不过的防御式写法；但 mitt 把自己压在 ~200 字节的体量内卖，每个 `if`、每个变量名都是真金白银的 gzip 成本。

更深一层的张力在于：「找不到」在这里压根不是异常情况。你完全可能去 off 一个已经 off 过的处理器、或对一个从没注册过的类型调用 off——这是调用方的合法行为，不该被当作错误处理。一旦承认它是常态，那为它专门写一条 `if` 就显得多余：能不能让代码路径自己「跨过去」？

## 2. 核心思想

把「找不到」这个信号，用一次位运算直接抹平成「无害的越界下标」，让删除退化成一条无分支的直线。

`indexOf` 找不到时返回 -1，而 `-1 >>> 0 === 4294967295`。把这个数当起点喂给 `splice`，运行时会按 ECMA-262 的规定把起点钳到数组长度、删除数量钳到 0——等价于什么都没删。「找不到」就这样被消解掉了，没有 `if`，没有 -1 判断。

## 3. 心智模型

把 off 当成对那张查找表（第 1 章）的一个写者：

1. 从表里取出该类型的处理器数组。
2. 取不到（类型从未注册）→ 整体返回，安全 no-op。
3. 取到了，再看调用方有没有给处理器：
   - 给了 → 在数组里查它第一次出现的位置（与第 3 章「不去重地追加」对称：`indexOf` 只取首个）。
   - 把这个位置——包括「找不到」对应的 -1——做一次无符号右移 `>>> 0`。
   - 用结果当起点 `splice(_, 1)`：找到时正常删一个；找不到时起点是 4294967295，钳到 length 后删 0 个。
4. 没给处理器 → 把该类型的数组整个替换成空数组（清空）。

整张表始终是 `Map<事件类型, 处理器数组>`，off 只是在其上做这两个写动作之一。

## 4. 关键权衡

### 用无符号右移把 -1 抹成必然越界的正整数

`indexOf` 找不到时返回 -1，最直接的防御写法是 `if (i >= 0)`。mitt 改写成 `splice(handlers.indexOf(handler) >>> 0, 1)`——单行表达式，没有任何分支。

换来的是删除路径在源码层只有一条直线，压缩器（gzip、terser）特别喜欢吃这种没有控制流的代码，几个字节就这么抠出来了；读者也少了一个临时变量 `i` 要跟踪。

代价是可读性骤降。读者必须同时知道两条冷知识才有机会看懂这一行：「`-1 >>> 0 === 4294967295`」和「`splice` 的越界起点会被运行时钳到数组长度、从而删 0 个」。任意一条不知道，整行就像在念咒。这条权衡化解的本质矛盾是「体积成本 ↔ 可读性」这对老对头：在 mitt 这种以小为卖点的库里，体积赢了，可读性的债留给注释和文档背。

### 让省略处理器参数重载成清空该类型全部

要让发射器支持清空某类型的所有处理器，常规做法是再开一个方法——`clear(type)` 之类。mitt 选择把这条语义塞进 `off` 本身：带处理器就删一个、不带处理器就清全部。

换来的是对外 API 表面更小：少一个方法名要文档、要导出、要测、要被压缩器收录。对一个 ~200 字节的库，少一个方法名可能就是几个字节。

代价是同一个 `off` 方法承担两种语义，仅靠参数个数区分——读者第一次遇到 `off('foo')`（不带处理器）很容易愣一下：这是删第一个，还是删全部？这是文档而非代码能讲清的事。背后仍是 mitt 一贯的取舍：API 表面小、语义透明度让位。

### 清空时替换成空数组，而不是把键删掉

清空某类型时，mitt 选择 `all.set(type, [])` 而不是 `all.delete(type)`。

换来的是这张表对外的形状更稳。第 1 章里说查找表是公开可窥探的——外部代码可以读到 `all.get('foo')`。清空后这个值稳定是 `[]`，而不是 `undefined`；外部观察者不用每次都判空。同时也与第 3 章「首次注册即建表」的语义对齐：只要类型曾经被注册过，它在表里就一直有一个数组在那里。

代价是表会长期残留空数组键——反复清空多种类型时，每个被清空的类型都留一个空数组在表里，占少量内存。这个代价薄到不展开：一个空数组在 V8 里就几十字节，且事件类型总数通常是个位数。这里化解的张力是「对外形状稳定 ↔ 内存占用」，mitt 选了前者。

## 5. 最小原理演示

下面这十几行只演示一件事：怎样用一个位运算把「找不到」消解掉、并让省略参数自然走清空分支。配上一张 `Map` 当查找表，跑起来就能验证三种调用形态。

```ts
type Handler = (e: unknown) => void;

function makeOff(table: Map<string, Handler[]>) {
  return function off(type: string, handler?: Handler) {
    const list = table.get(type);
    if (!list) return;                        // 类型从未注册 -> 整体 no-op
    if (handler) {
      // indexOf 找不到返回 -1；-1 >>> 0 = 4294967295，必然越界
      // 越界起点会被运行时钳到 length、删 0 个 -> 等价没删
      list.splice(list.indexOf(handler) >>> 0, 1);
    } else {
      table.set(type, [] as Handler[]);       // 省略 handler -> 替换成空数组 = 清空
    }
  };
}
```

这段演示只演「位运算抹平边界 + 重载清空 + 替换而非删键」三件事，刻意省掉了 mitt 真实代码里的 Events 类型映射、通配符 `'*'` 分支、symbol 键（机制等同 string 键）。

## 6. 执行轨迹

拿一个具体输入走一遍。初始表里 `foo → [f, f]`（同一函数被注册了两次，呼应第 3 章的「不去重」）：

```
表: { foo → [f, f] }

off('foo', f)
  → 取到 list = [f, f]
  → handler 真值，进删除分支
  → indexOf(f) = 0；0 >>> 0 = 0；splice(0, 1) 删第一个
  → 表: { foo → [f] }

off('foo', g)         // g 是一个从未注册过的函数
  → 取到 list = [f]
  → handler 真值，进删除分支
  → indexOf(g) = -1；-1 >>> 0 = 4294967295
  → splice(4294967295, 1)：起点钳到 length=1，删 0 个
  → 表: { foo → [f] }      // 什么都没变

off('foo')            // 省略 handler
  → 取到 list = [f]
  → handler 为 undefined，进清空分支
  → table.set('foo', [])
  → 表: { foo → [] }       // 键仍在，值是空数组

off('bar')            // 'bar' 从未注册过
  → table.get('bar') = undefined
  → 整体 no-op
  → 表: { foo → [] }       // 什么都没变
```

四步走下来，没有任何分支被触发为「报错」——三种边界都自然消解成 no-op 或越界钳制。

## 7. 教学简化说明

上面演示故意没演：通配符 `'*'` 的移除（属后续章）、Events 类型映射与泛型（属后续章）、symbol 键（机制等同 string 键、加了只增噪音）。真实 mitt 的 off 还有一层泛型签名 `Key extends keyof Events` 让 `off('foo', handler)` 的 handler 类型自动收窄——那是另一章的故事。

## 8. 小结

off 的全部魔法就是一行：`handlers.splice(handlers.indexOf(handler) >>> 0, 1)`。`>>> 0` 把 -1 变成越界正整数，把「找不到怎么办」这个问题从代码里彻底抹掉——是 mitt 用可读性换体积的极致体现。省略 handler 就是清空、清空就是替换成空数组，这两个决定都在延续同一个偏好：用最少的 API 表面、最稳的对外形状，换调用方一点点学习成本。

但有个细节我们一直绕过去了：如果 off 是在一个事件正在派发的过程中被调用的呢？正在遍历处理器数组时，某个处理器把自己 off 掉、或往里 on 一个新的——这时会发生什么？这正是下一章「快照式派发抵御中途改表」要拆的。
