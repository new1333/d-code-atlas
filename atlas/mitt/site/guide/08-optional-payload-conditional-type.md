# 条件类型区分「可不带数据」的事件

想象你在写一个登录模块。用户点了「退出登录」，你只需要对外广播一句「登录态变了」，并不需要附带任何东西——因为监听这个信号的人，自己会去重新拉取登录状态。这类「信号型事件」在工程里到处都是：任务完成、连接断开、缓存失效。它们的共同点是：**触发就是触发，不带额外信息**。

可如果你的发布订阅库把触发动作的第二个参数写死成「必传」，你就被迫写出 `emit('logout', undefined)` 这种空转调用——明明没东西要传，还得硬塞一个 `undefined` 进去，纯属多此一举。

那把第二个参数改成「一律可选」总行了吧？也不行。因为还有另一类事件是**必须带数据**的，比如 `emit('message', msg)`。一旦把参数设成可选，用户手滑漏写了 `msg`，编译器一声不吭地放行，等运行时处理器拿到一个 `undefined` 直接炸掉。

痛点就在这儿：同一个触发 API，怎么让「不带数据的事件」和「必带数据的事件」**走两条完全不同的类型检查通道**——前者允许你省掉参数，后者强制你必须传？

mitt 的解法是在编译期问一句话。这一章我们就拆开看这句话是什么、靠哪几个零件搭起来、又付出了什么代价。

## 先认三个零件

要搭这个「编译期判分器」，得先认识三个 TypeScript 的基本件。它们都不涉及运行时，全发生在类型层面。

**零件一：条件类型。** 它长得像一个三元表达式：

```ts
T extends U ? A : B
```

读作「如果 `T` 能赋值给 `U`，结果就是 `A`，否则是 `B`」。这是类型层面的分支判断，运行时根本不存在这个东西。

**零件二：可选属性的索引访问，天然多出一个 `undefined`。** 这条规则是整章的地基。当你写下 `{ bar?: number }`，再用 `Events['bar']` 去取这个键的类型时，拿到的不是 `number`，而是 `number | undefined`——多出来的那个 `undefined`，正是「这个键可能压根没值」的类型层印记。换句话说，「可选」这件事，在类型系统里留下了一个可被探测的痕迹。

**零件三：`never`（永不类型）。** 没有任何值能赋值给 `never`，它也赋值不出任何值。在条件类型里把它当成一把筛子：某一项求值结果是 `never`，就等于声明「这一项被删掉了」。

## 把零件拼成「筛键器」

把上面三个零件接到一起，就能筛出「可以省掉参数的键」。思路很直白：对每一个键问一句——`undefined` 能不能赋值给它的数据类型？能，就留下这个键；不能，就变成 `never`。

下面这个类型别名把这件事写清楚了：

```ts
// 对每个键判分：含 undefined 的保留为自身，不含的变成 never，最后拍平成一个联合
type FireableWithoutData<Events> = {
  [K in keyof Events]: undefined extends Events[K] ? K : never
}[keyof Events]
```

把它套到一张混着两种键的事件清单上，效果立竿见影：

```ts
interface Events {
  foo: string;     // 必带数据：索引取值是 string，不含 undefined
  bar?: number;    // 可不带数据：索引取值是 number | undefined
}

type Result = FireableWithoutData<Events>;
//   ^? type Result = "bar"      ——foo 被算成了 never，筛掉了，只剩 bar
```

`foo` 的数据类型是 `string`，`undefined extends string` 不成立，于是 `foo` 这一格变成了 `never`，最后被拍平掉；`bar` 的数据类型是 `number | undefined`，`undefined extends (number | undefined)` 成立，于是 `bar` 被原样保留。

> 顺带一提：mitt 实际并没有把这个判分单独抽成一个类型别名，而是直接内联进了重载签名里（下面会看到）。抽出来只是为了讲清楚，二者语义是一回事。这里还依赖一个 TypeScript 的小特性——当条件类型作用在「裸类型参数」上时，它会**逐个成员地分别判定再合并**（术语叫分布式条件类型）。所以哪怕 `Key` 是个联合，它也会对其中每一个键单独问一遍「含不含 undefined」。这条细节点到为止，知道它能逐键判分就够了。

## 给触发动作开两条通道

筛出了「可省参数的键」这个子集，下一步就是用它。办法是给 `emit` 写**两条重载签名**：

```ts
interface Emitter<Events> {
  // 第一条：带数据通道 —— 键 + 数据，双参必传
  emit<K extends keyof Events>(type: K, data: Events[K]): void;

  // 第二条：不带数据通道 —— 只接受「筛出的可省参数键子集」
  emit<K extends keyof Events>(type: undefined extends Events[K] ? K : never): void;
}
```

调用 `emit` 时，编译器会依次试这两条签名。分流的逻辑是这样的：

```
emit('foo', 'hi')   ──匹配第一条──▶  走「带数据」通道，放行
emit('foo')         ──第一条缺 data 不匹配──▶ 试第二条
                      第二条要求 type: "bar"（foo 已坍缩成 never）
                      'foo' 不能赋值给 "bar"  ──▶ 编译期拒绝 ❌
emit('bar')         ──第一条缺 data 不匹配──▶ 试第二条
                      第二条要求 type: "bar"，'bar' 能赋值 ──▶ 放行 ✓
emit('bar', 1)      ──匹配第一条（data 为 number）──▶ 放行 ✓
```

关键就在第二条签名的那个参数类型 `undefined extends Events[K] ? K : never`。它是一个**就地收缩的筛子**：对每一个具体的键，当场判分——能省参数的键被保留成它自己，不能省的被算成 `never`。于是当你对一个「必带数据」的键（比如 `foo`）发起不带数据的触发时，那个键在第二条签名里根本不存在（被算成了 `never`），`'foo'` 没有任何合法位置可放，编译期直接报错。

> 和上一章的关系：你已经知道，mitt 靠 `Key extends keyof Events` 反向推出了每个 API 的参数类型——那是上一章「一张映射派生全 API 类型」的成果。本章不重讲那套「键反推数据类型」的推导，而是顺着它的一个新侧面往下挖：**数据类型能不能被判定为「可省略」，从而给触发动作单独开一条编译期通道**。

## 对外严格，内部却很宽松

读到这儿你可能有个疑惑：第二条签名说得那么严，可真到了运行时，用户调用 `emit('bar')` 压根没传数据，实现里不会因为拿不到数据而出问题吗？

有意思的地方来了——**对外的类型签名和内部实现签名，是两套东西**。对外接口里，不带数据触发只放行可省参数的事件；但实现签名却是：

```ts
emit<K extends keyof Events>(type: K, evt?: Events[K]) {
  // ...
  handler(evt!);   // evt 对所有键都标了可选，没传就是 undefined，直接传下去
}
```

实现里 `evt` 对**所有**键都标成了可选，还用 `evt!`（非空断言）兜底。说人话就是：**类型层负责「挡住不合法的不带数据触发」，运行时只管「不抛错地把流程走完」**。哪怕某个事件的数据在类型上不可省，运行时就算真没传，也不过是个 `undefined` 被传进处理器，空跑一遍而已，不会崩。

这种「契约归契约，实现归实现」的分离，是读这段代码必须跨过的一道坎。

## 一个能跑的最小复刻

把上面全部串起来，下面是一个可以独立运行、忠实复刻「编译期判分」核心机制的演示。整段没有任何运行时逻辑——它要演示的就是类型系统本身的行为。

```ts
// demo.ts —— 演示：编译期判分「哪些事件可以不带数据触发」

// ① 一张事件清单，故意混着「必带数据」和「可不带数据」两种键
interface Events {
  foo: string;     // 必带数据
  bar?: number;    // 可不带数据（也可能偶尔带个序号）
}

// ② 编译期判分器：含 undefined 的键留下，不含的坍缩成 never
type FireableWithoutData<Events> = {
  [K in keyof Events]: undefined extends Events[K] ? K : never
}[keyof Events];

// ③ 触发的两条重载：带数据通道 + 不带数据通道
interface Emitter<Events> {
  emit<K extends keyof Events>(type: K, data: Events[K]): void;
  emit<K extends keyof Events>(type: undefined extends Events[K] ? K : never): void;
}

declare const emitter: Emitter<Events>;

// ④ 验证：必带数据的键 vs 可不带数据的键，走的是不同的通道
emitter.emit('foo', 'hello');   // ✓ 必带数据键，老老实实带上数据

// @ts-expect-error   —— foo 必须带数据，省掉参数必须在编译期报错
emitter.emit('foo');

emitter.emit('bar');            // ✓ 可不带数据键，省掉参数直接放行
emitter.emit('bar', 1);         // ✓ 想带数据也行

// @ts-expect-error   —— bar 的数据类型是 number，传 string 必须报错
emitter.emit('bar', 'oops');
```

这几行 `@ts-expect-error` 就是断言本身：如果它下面那一行**没**被编译器报错，整个类型测试就失败了。这和 mitt 仓库里 `test-types` 脚本的手法完全一致——靠的不是运行时断言，而是编译器的「报不报错」。

配一个最小的 `package.json`，读者就能本地 `npm run check` 验证：

```json
{
  "name": "conditional-emit-demo",
  "private": true,
  "scripts": {
    "check": "tsc --noEmit demo.ts"
  },
  "devDependencies": {
    "typescript": "^5.4.0"
  }
}
```

> 一个要注意的边界：这套判分成立的前提，是「可选属性的索引访问**必含** `undefined`」。这依赖 `strict: true` 且**未**开启 `exactOptionalPropertyTypes`——后者一旦打开，`Events['bar']` 就不再自动包含 `undefined`，整条判分会当场失效。mitt 自己的 `tsconfig` 没开这个选项，所以行为是稳定的；但若你的项目单独开了它，就得当心。

## 这套设计换来了什么，又付出了什么

把演示看完，原理已经清楚。剩下的就是算账——为什么偏偏要这么设计。本章机制集中在这一个判分器上，下面三条权衡都围着它转。

**权衡一：选「两条重载分流」，而不是「一条可选数据参数」。**
最省事的写法其实是 `emit(type, data?: Events[K])` 一条签名搞定。但这一省，就把「必带数据的事件」也放过了——`data` 一旦可选，漏传就不报错了。mitt 偏要写两条重载，换来的是一条**硬保证**：必带数据的事件，绝对无法在不带数据的情况下被触发，漏传直接编译失败。代价是第二条签名是 `undefined extends Events[K] ? K : never` 这样一段条件类型表达式，初读几乎看不懂，得绕几遍才反应过来它在筛键。

**权衡二：拿「数据类型里含不含 `undefined`」当判分依据。**
判分依据可以是任何东西——本来可以设计一个显式开关或注解来标记「这个事件可省参数」。mitt 偏不，它直接借用了「可选属性 ⇒ 索引取值含 `undefined`」这条 TypeScript 既有的语义约定。换来的是**零额外配置**：用户只要在事件清单里把某个键写成可选属性（`bar?: number`），就同时把「这个事件可以不带数据触发」也表达完了，不用学任何新语法、不用记任何新开关。代价是这个判分**完全是隐式的**——读代码的人看不到「可选属性」和「可省参数触发」之间这座隐含的桥，得自己把语义约定这一步补上才能想通。

**权衡三：对外签名严格，内部实现签名宽松。**
对外的两条重载是「不带数据触发只放行可省参数事件」的严格契约；可内部实现却对所有键都把数据标成可选、还用非空断言兜底。换来的是**运行时极简与类型精确并存**——类型层精确地挡住非法调用，运行时却不用为「数据可不可省」写任何分支、抛任何错误，没传就传个 `undefined` 空跑一遍。代价是**契约与实现的不一致**：同一个方法，给用户看的签名和真正跑起来的实现不是一回事。读者得接受「重载签名是给用户的承诺，实现是另一回事」这个心智模型。

把三条放在一起看，它们其实指向同一个取舍：**把判分的复杂性尽量往类型层、往隐式约定里推，换来的则是用户侧的零负担（不用学开关）和运行时的零负担（不用写分支）**。复杂性没有消失，只是被收进了那一条晦涩的条件重载里。

## 小结

这一章的核心就一句话：**在编译期问一句「这个事件的数据类型里到底允不允许出现 `undefined`」，据此把触发动作劈成两条通道——允许的走「不带数据触发」，不允许的直接拒绝。**

它靠三个零件搭起来：条件类型做判分、可选属性的索引访问留下 `undefined` 痕迹、`never` 当筛子删掉不合格的键。判分的结果喂给 `emit` 的第二条重载签名，让「不带数据触发」这件事对编译器而言可判定——可省参数的事件放行，必带数据的事件编译失败。而对外严格、内部宽松的分离，让类型层的精确保护不必拖累运行时的简洁。

值得记住的是它付出的代价：那条 `undefined extends Events[K] ? Key : never` 的重载签名相当晦涩，判分的依据完全隐式，且当用户漏写数据时，收到的报错是「不能赋值给 `never`」这类拐弯抹角的提示，而不是「这个事件必须带数据」的直白提醒。这是用极简签名换来的可读性成本。

这套纯类型层的把戏，最终要落到一个真实可用的库上——一份 TS 源码，既要能被 Node `require`，也要能被浏览器 `<script>` 直接吃下，还要给打包器喂对的格式。下一章《一源多格式通吃所有 JS 运行时》就来看，mitt 是怎么靠 `package.json` 的条件映射把一份产物路由到所有运行时的。
