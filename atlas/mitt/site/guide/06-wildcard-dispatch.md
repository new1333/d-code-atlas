# 通配符星号的第二条派发路径

> 本章属于 composite 层。前置：快照式派发抵御中途改表。
> 学完你能：用一句话讲清 mitt 怎么靠一个保留键 `'*'` 就拿到了 catch-all 能力，以及为什么它必须是「第二条」派发路径、为什么通配符处理器得用双参。

## 1. 为什么需要它

上一章把 `emit` 内部那一次「先 slice 再遍历」的快照手法讲透了——派发集合在入口那一刻冻结，回调里反手改表不会让本轮出 BUG。但当时为了不分散注意力，第 3 节末尾留了那么一句：「类型匹配的名单跑完后，通配符 `'*'` 名单会用同样的方式再跑一遍。」本章就接这个口子。

事件系统里有一类需求是「横切」的——日志、调试、遥测、把事件转发到另一个总线、做 AOP 式拦截。它们的共同点是：**不在乎刚才是什么事件被触发，只想统统听一遍**。如果发射器不专门支持这种能力，调用方就得为每一个事件类型各订阅一遍（类型一多就忘），或者被迫修改每一次 `emit` 的调用点去塞一段广播逻辑（这与把发布订阅抽象出来的初衷背道而驰）。

使用者真正想要的是：**一处订阅就能收到任意事件，并且能知道刚才到底是什么事件被触发了**。前半句好办，给个「全部事件」的订阅入口就行；后半句才是难点：一个订阅了「全部事件」的处理器，必须能拿到那个「具体是什么事件」的信息，否则它就只是个无意义的 echo。

## 2. 核心思想

约定一个保留键代表「全部事件」，让通配符的订阅、退订、存储**完全复用**已有的那张 Map；派发时在第一路径之外再加一条独立路径，专门把真实事件类型作为第一参补进去。

说人话就是：不引入第二套注册表、也不引入第二套订阅 API，把通配符当成表里的一个特殊键，订阅它跟订阅 `'click'` 走一模一样的代码路径；只在派发那里多走一趟，并把「真实类型」这第一参补上。

## 3. 心智模型

注册表还是上一章那张 `Map<type, handler[]>`，`'*'` 只是其中一个被约定的保留键。数据流是这样的：

1. 订阅 `on('*', g)`——与订阅 `on('foo', f)` **走完全相同的代码路径**：表里没有 `'*'` 这个键就建数组、有就 push。星号在存储层没有任何特殊待遇。
2. 派发 `emit(type, evt)` 时进入第一路径：取出 `type` 这个键的处理器数组，按上一章的快照手法遍历，**单参**调用 `h(evt)`。
3. 第一路径结束（无论是否命中），立刻进入第二路径：取出 `'*'` 这个键的处理器数组，**同样**先 slice 一份快照。
4. 第二路径遍历快照，每个处理器用**双参**调用 `h(type, evt)`——把第一参「真实事件类型」补进去。
5. 两趟各自独立做快照、各自独立 `if (handlers)` 短路，任一趟没注册过就跳过。
6. 结果：同一次派发同时通知「该类型的订阅者」和「全部事件的订阅者」，后者额外知道收到的是什么类型。

不变量是：**通配符处理器永远在类型匹配处理器之后跑**，且固定拿双参；通配符的订阅、退订、存储与普通事件完全等价，差别只在 emit 里多走一趟、参数多一个。

## 4. 关键权衡

### 把通配符当成表里的一个保留键，而非另起一张注册表

**选择**：不新建 `wildcardHandlers: Handler[]` 这种独立结构，而是把 `'*'` 当成 `Map<type, handler[]>` 里的一个普通键。订阅、退订的实现体只有一份，星号与普通事件走完全相同的「查表 → 追加 / 移除」逻辑，没有任何 `if (type === '*')` 的分支特殊对待。

**换来**：零新增代码路径。第 3 章的「惰性建表」（首次注册即建数组）、第 4 章的「无分支移除」（`indexOf >>> 0`），对通配符**全部自动复用**。整条订阅/退订管线只维护一份代码，星号蹭车走完。这是「一张 Map 退化 pubsub」哲学的最纯粹体现——任何特殊语义都靠「保留键」实现，不再加结构。

**代价**：`'*'` 这个名字被永久占用。用户再也不能把星号当普通事件名用——`on('*', ...)` 永远被解释成「订阅全部事件」，而不是「订阅名为星号的事件」。一个事件系统对外的命名空间是有限的，每个保留键都是从用户那里借走的额度。未来若还要加 `'**'`、`'?'` 之类的特殊语义，命名空间会被一步步蚕食。

**化解的本质矛盾**：「机制要支持 catch-all 语义」与「实现要保持极简、不加结构」——这对张力直接落在「是否新增数据结构」上。新建结构换来命名空间干净、语义清晰；复用表换来代码极简但占用一个名字。mitt 一贯选后者，它的价值主张就是「~200 字节、零依赖」，为 catch-all 单独建表违背初衷。这是一类通解：**当一种特殊语义可以靠「约定一个保留值」复用已有结构来表达时，就别新增结构**——API 表面更小、代码路径更少、可维护性更高，代价只是占用了一个原本可用的值。Unix 的 `'-'` 表示 stdin、HTTP 的 `OPTIONS *`、SQL 的 `SELECT *`——同一招的反复应用。

### 通配符处理器用双参把真实类型补进去，而非延续单参签名

**选择**：普通处理器签名是 `(event) => void`，通配符处理器签名是 `(type, event) => void`——多出一个「真实事件类型」作为第一参。

**换来**：catch-all 处理器能区分「刚才到底是什么事件被触发了」。一个日志处理器拿到 `('foo', {a:1})` 就能写 `[foo] {a:1}`；拿到 `('bar', {b:2})` 就写 `[bar] {b:2}`。如果延续单参，通配符处理器只能拿到 `{a:1}` 或 `{b:2}`——根本不知道是哪个事件，等于一个瞎子监听器，毫无用处。这第二参是 catch-all 能用的**充要条件**。

**代价**：同一张表里现在并存两种不同签名的函数。运行时存储必须用一个联合类型把它们塞进同一个数组；派发时两条路径各自做类型断言还原（单参路径当成 `Handler`、双参路径当成 `WildcardHandler`）。更直接的代价是——**手动 `emit('*')` 被刻意禁止**：类型层没有为字面量 `'*'` 提供 emit 重载。这不是任性限制，而是双路径设计的直接推论：若强行 `emit('*', evt)`，第一路径会以**单参**调用星号处理器（把 `'+'` 当成 event，第二参丢失，参数错位）；紧接着第二路径又以**双参**正确调用一次——同一个星号处理器会被触发两次且第一次参数错位。禁止手动触发星号，是这套设计自洽的代价。

**化解的本质矛盾**：「订阅端希望一种签名走天下」与「catch-all 必须能区分类型」——前者要求签名统一、简洁，后者要求多一个参数。无解，只能选一边：mitt 选了「让普通处理器保持单参、让通配符处理器单独拿双参」，于是普通订阅零认知负担，catch-all 多一个参数但能用。读者带走的通解骨架是：**当一组操作里有「特殊的一个」需要额外信息时，给这个特殊操作单独设计签名，而不是给所有操作都加上那个参数**——避免污染大多数。React 的 `key` 只对列表子元素生效、Express 的错误处理中间件多一个 `err` 参数，都是同一招。

### 每次派发都无条件查一次星号槽，而非用标志位短路

**选择**：emit 不维护「是否存在通配符订阅者」这种运行时状态，每次派发跑完第一路径后，**无条件**去 `all.get('*')` 查一次。

**换来**：catch-all 语义的确定性与代码极简。无需在 on/off 里维护「有没有人订阅了通配符」的标志位，也无需考虑标志位与实际订阅状态的同步问题（一个隐蔽的 bug 源）。派发逻辑就是两条直线，查类型槽、查星号槽，读起来毫无心智负担。

**代价**：每次派发都多一次 Map 查找。绝大多数 emit 调用其实根本没有通配符订阅者，这次查找命中 `undefined` 就短路，开销极小，但确实存在。此外，通配符处理器**固定**排在类型匹配处理器之后，**优先级不可配置**——既不能让 catch-all 先于具体处理器跑，也不能在它们之间插队。源码注释明确写明这条规则。需要分阶段拦截（前置 vs 后置）的调用方得自己组装多个处理器，mitt 不在排序上提供灵活性。

**化解的本质矛盾**：「派发要快」与「实现要简单、无状态」——这对张力落在「是否为通配符维护运行时状态」上。维护标志位换来 O(1) 短路，但引入状态同步负担；不维护换来无条件简洁，付出固定查找成本。mitt 一贯选「不维护运行时状态、靠查找兜底」——on/off 是纯数据结构操作、emit 是纯遍历，整个库没有一个隐藏的布尔标志。这是一类通解骨架：**当你不确定是否需要做一件事时，宁可每次都做一次廉价检查，也不要为「省这次检查」维护一份状态**——状态是 bug 的温床，查找是 O(1) 的常数。

## 5. 最小原理演示

下面这段几十行的 TS 从零搭一张查找表，演透三件事：①星号与普通事件共用同一张表、走同一份订阅代码；②派发时两趟独立快照遍历；③第二趟用双参把真实类型补进去。每一行都对应上面某条权衡或某个心智模型步骤。教学简化：不演泛型、不演 symbol、不演退订——它们都不影响「第二条派发路径」这个核心原理。

```ts
// wildcard.ts
type Handler = (event: any) => void;                    // 普通处理器：单参
type StarHandler = (type: string, event: any) => void;  // 通配符处理器：双参

function mitt() {
  // 一张表，'*' 只是其中一个键——没有任何独立结构
  const all = new Map<string, Function[]>();

  function on(type: string, h: Function) {
    // 星号与普通事件一视同仁：查表 → 有就 push、没就建数组
    const list = all.get(type);
    if (list) list.push(h);
    else all.set(type, [h]);
  }

  function emit(type: string, evt: any) {
    // 第一路径：取该类型槽位，借上一章的快照手法遍历，单参调用
    const typed = all.get(type);
    if (typed) typed.slice().forEach((h: any) => h(evt));

    // 第二路径：无条件取星号槽位，同样快照遍历，双参调用——补上真实类型
    const starred = all.get('*');
    if (starred) starred.slice().forEach((h: any) => h(type, evt));
  }

  return { on, emit };
}

const bus = mitt();
bus.on('foo', (e: any) => console.log('foo 收到:', e));
bus.on('*', (t: string, e: any) => console.log('星号收到:', t, e));

bus.emit('foo', { a: 1 });
// foo 收到: { a: 1 }       ← 第一路径
// 星号收到: foo { a: 1 }   ← 第二路径，type 被补进去

bus.emit('bar', { b: 2 });
// 星号收到: bar { b: 2 }   ← 第一路径落空跳过，第二路径仍触发——catch-all 与具体类型是否有人订阅无关
```

两趟派发各自做了一次 `.slice()`，这就是上一章快照手法在通配符路径上的复用——本章不重复讲快照原理，只看它在第二条路径上被原样调用了一次。第二路径的 `h(type, evt)` 把真实事件类型作为第一参注入，这就是 catch-all 处理器能区分事件的原因。

## 6. 执行轨迹

拿上面的 bus，把 `bus.emit('foo', {a:1})` 的内部状态一步步走一遍。

初始：表为空 `{}`。

调用 `bus.on('foo', f)`：表里没有 `'foo'` 这个键，走 `else` 分支建数组，表变成 `{ foo: [f] }`。

调用 `bus.on('*', g)`：表里没有 `'*'` 这个键，**同样**走 `else` 分支建数组，表变成 `{ foo: [f], '*': [g] }`——星号在存储层毫无特殊待遇，与 `'foo'` 走完全相同的代码路径。

调用 `bus.emit('foo', {a:1})`：

1. 进入 emit，先跑第一路径：`all.get('foo')` 拿到 `[f]`，存在，于是 `.slice()` 复制一份得到 `[f]`（冻结名单），遍历它，对唯一的元素调用 `f({a:1})`——单参。控制台输出 `foo 收到: { a: 1 }`。
2. 第一路径结束，立刻跑第二路径：`all.get('*')` 拿到 `[g]`，存在，于是 `.slice()` 复制一份得到 `[g]`，遍历它，对唯一的元素调用 `g('foo', {a:1})`——**双参，第一个位置补上真实类型 `'foo'`**。控制台输出 `星号收到: foo { a: 1 }`。
3. 第二路径结束，emit 返回。

对照 `bus.emit('bar', {b:2})`：`'bar'` 这个键在表里压根不存在，第一路径的 `all.get('bar')` 返回 `undefined`，`if (typed)` 短路跳过，控制台没有 `bar 收到:` 这行。但第二路径照常跑：`all.get('*')` 仍命中 `[g]`，调用 `g('bar', {b:2})`，控制台输出 `星号收到: bar { b: 2 }`。这一步证明：**catch-all 派发独立于具体类型是否有人订阅**——星号槽只要有人订阅，无论被发射的是什么类型（哪怕没人听），都会触发。

## 7. 教学简化说明

本章演示故意省略了：通配符处理器的泛型签名如何由用户那张事件映射反推（属紧邻下一章「一张 Events 映射派生全 API 类型」）；通配符的退订（与普通事件退订同构，第 4 章已讲透）；「可选载荷事件」的条件类型重载（属第 8 章）；通配符处理器手动 `emit('*')` 为何被类型层拒绝的精确签名推导（正文已用双路径矛盾讲透其根本原因）。这些都不是「第二条派发路径」的必要组成。

## 8. 小结

mitt 用一个保留键 `'*'` 复用同一张查找表，给 emit 加上无条件跑的第二条派发路径——通配符的订阅、退订、存储与普通事件完全等价，差别只在派发多走一趟、参数多一个。换来的是「一处订阅即收到任意事件且能区分类型」的 catch-all 能力；代价是占用了 `'*'` 命名空间、同一张表里两种签名并存、以及手动 `emit('*')` 因双路径矛盾被刻意禁止。

到此运行时的派发就闭环了。下一章把镜头切到类型层——看 mitt 怎么让用户只声明一张「事件名 → 数据类型」的 Events 映射，就让整条 on/off/emit 的参数类型自动反推出来。
