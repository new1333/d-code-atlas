# 把 pubsub 退化成一张查找表

> 本章属于 primitive 层。前置：（首章，全书地基）。
> 学完你能：用一句话讲清「为什么 mitt 把整个发射器坍缩成一张『事件类型 → 处理器数组』的查找表」，以及这个选择放弃了什么。

## 1. 为什么需要它

打开 Node 自带的 `EventEmitter`，你能列全它内部到底记了什么吗？默认监听器上限、`once` 包装链、`prependListener` 的插入位置、`rawListeners` 留下的原始引用、可能挂上去的 Symbol 钩子……它是一个对象、又是一坨隐式状态：你既看不全它记了什么，也很难把它的状态整个 dump 出来调试。可绝大多数真实需求其实就这么一句——「我就是要在两个模块之间传个事件」。

全书为什么从这一章开始？因为后面每一章其实都在回答同一个问题——**「围绕这张表，mitt 是怎么做某个具体操作的？」**——订阅的具体写法、退订的位运算技巧、发布的快照防御、通配符的第二派发路径、整条 API 的类型推导……每一章都建立在本章立起来的那张表上。所以全书必须从这一章起步：先把「发射器的状态是什么形态」这件事定下来，后面所有具体操作的取舍才有讨论的舞台。

## 2. 核心思想

**把发射器的全部状态坍缩成一张查找表——表外别无状态。**

「状态形态」是发射器设计里最早需要拍板的一件事，它一旦定下来，所有 API 的行为就都从这张表的形态自然推出来：订阅就是往表里塞、退订就是从表里抹、发布就是查表读出来逐个调用——三件事不再需要三套独立机制，它们都只是同一张表上的三种 CRUD。mitt 不是「先写一个 emitter 再尽量精简」，而是「先承认状态只能是一张表，剩下的全部从这一前提推出来」。

## 3. 心智模型

这张表的结构朴素到一目了然：

```
Map<事件类型, 处理器数组>
```

- **键**：事件类型，取值域是 `string | symbol`。每条记录就是「一个事件名 → 一组监听这个事件的函数」。
- **值**：一个普通数组。没有优先级队列，没有 Set 去重，没有 once 标记位——就是原生 `Array<Handler>`，按订阅顺序排着。

把发射器想成一本**通讯录**：名字（事件类型）对应一串电话（处理器数组）。订阅就是在某名字底下加一条电话，发布就是按名字翻到那一页、把上面所有电话挨个拨一遍。整本通讯录就是发射器的全部，没有第二本暗藏的账。

围绕这张表的三件事：

1. **订阅** = 查表：有这条记录就 push 进去，没有就开一条新记录。
2. **退订** = 查表：从对应数组里抹掉那个函数。
3. **发布** = 查表：取出数组、挨个调用。

注意一个不变量：**派发只是读表，不改表**——发布前后表的内容一模一样。这一点稍后会在执行轨迹里亲眼看到。

## 4. 关键权衡

### 一张表做唯一状态，换极简与可窥探，代价是放弃封装

mitt 没有像传统 emitter 那样把状态拆成 `_listeners`、`_onceWrappers`、`_maxListeners` 等多个实例字段，更没有用优先级队列等富结构。整条 emitter 上**只有一个可变字段 `all`**，它的值就是这张表。

这个选择换来两件实在的东西：

- **极小体积**（README 宣称压缩后约 200 字节）：状态只有一份，操作它的代码也就不需要在多个字段之间来回联动。
- **完全可窥探**：你可以 `console.log(emitter.all)` 直接看见全部订阅关系——哪条事件谁在监听、先后顺序如何，全在一行打印里。

代价是**彻底放弃封装**：`all` 没有用 `readonly` 或 `#` 私有化，谁拿到实例都能 `emitter.all.set(...)` 直接改表。「可窥探」与「可被外部篡改」是同一枚硬币的两面。

> 本质矛盾：**极简内核 ↔ 封装隔离**。传统 emitter 选了后者（私有字段 + getter），mitt 选了前者。

> 这张表被「公开为实例字段、且可从外部注入共享」这一封装取舍，主要属于第 2 章『函数工厂与无 this 的方法』要讲的核心权衡，本章只看它作为「唯一状态容器」这一侧面。

### 键只接字符串与 symbol，且刻意不归一化，换精确匹配与私有频道，代价是一致性责任外推

事件类型的全集被压缩到 `string | symbol`，且全文里**找不到一句** `toLowerCase` / `trim` / 大小写折叠。也就是说，`'FOO'` 和 `'foo'` 是两个互不相干的 key——这是设计，不是 bug。

换来的好处有两条：

- **语义完全可预测**：键相等性就是 JS 原生的 `===`，没有任何隐藏的归一化规则要记。订阅时写的是什么字符串，发布时就得写什么字符串。
- **symbol 天然形成「私有频道」**：外部代码拿不到某个 symbol 引用，就永远无法监听它——靠语言本身的作用域机制就完成了「频道隔离」，库什么都不用做。

代价是把一致性的责任全部推给了调用方——你写 `'FOO'` 订阅、用 `'foo'` 发布，mitt 不会帮你 debug。

> 本质矛盾：**精确可控 ↔ 容错便利**。归一化是「替用户兜底」、不归一化是「让用户自己负责」。mitt 选了后者，因为它的目标是「最小内核」，而不是「替用户操心」。

### 处理器集合就是一个裸数组，换极小与透明，代价是放弃优先级 / once / 异步

某类型的处理器集合就是 `Array<Handler>`，没有任何附加元数据：

- 不内置**优先级**——先注册的先触发，仅此而已；
- 不内置 **once**——想只触发一次，得让处理器在执行体里自己把自己退订；
- 不内置**异步调度**——发布就是同步遍历调用，没有微任务排队。

换来的是：状态语义完全透明（数组什么样、派发就什么样），代码体积也压到最小。

代价是：当真需要这些能力时，调用方得自己在处理器里实现。这是把便利下放给用户的取舍——mitt 假设你的多数场景不需要这些，需要时你自己加，比一开始就强加给所有使用者更合理。

> 本质矛盾：**极简内核 ↔ 内置便利**。Node EventEmitter 选了后者（自带 once / prepend / setMaxListeners），mitt 选了前者。

## 5. 最小原理演示

下面这段代码**只为演透「状态 = 一张表」这一条**，所以写得最朴素：普通 `if` + `push`、普通 `for`、没有任何体积优化。通配符、`.slice()` 快照、`>>> 0` 退订、惰性建数组——这些后续章会逐个讲透的技巧，这里全部不演。

```ts
type Handler = (event: any) => void
type EventType = string | symbol  // 取值域就这两种，刻意不做任何归一化

type Emitter = {
  all: Map<EventType, Handler[]>  // 整个发射器唯一的可变状态：一张查找表
  on: (type: EventType, h: Handler) => void
  off: (type: EventType, h: Handler) => void
  emit: (type: EventType, evt: any) => void
}

function createEmitter(): Emitter {
  // 新建一张空表——这就是发射器诞生时拥有的全部
  const all: Map<EventType, Handler[]> = new Map()

  return {
    all,
    on(type, h) {
      // 订阅 = 查表：有就追加，没有就开一条新记录
      const list = all.get(type)
      if (list) list.push(h)
      else all.set(type, [h])
    },

    off(type, h) {
      // 退订 = 查表：从数组里抹掉那个函数
      const list = all.get(type)
      if (list) {
        const i = list.indexOf(h)
        if (i > -1) list.splice(i, 1)
      }
    },

    emit(type, evt) {
      // 发布 = 查表：取出来挨个调用（本章不演通配符的第二条派发路径）
      const list = all.get(type)
      if (list) {
        for (const h of list) h(evt)
      }
    },
  }
}

// 亲手摸一下「可窥探」
const bus = createEmitter()
bus.on('foo', (e) => console.log('a got', e))
bus.on('foo', (e) => console.log('b got', e))
console.log(bus.all)
// Map(1) { 'foo' => [ [Function (anonymous)], [Function (anonymous)] ] }
// ↑ 整个发射器除了这张表，什么都没有——想看状态，直接打印 all 即可
```

看最后那行 `console.log(bus.all)`——它把「状态即表」这件事直接摆到了眼前。一个传统 emitter 想做到这件事，得专门写一个 `dumpState()` 方法，或者绕到 DevTools 里去翻私有字段；mitt 这里一行 `console.log` 就够了。

## 6. 执行轨迹

拿一个具体输入走一遍。先订阅两次同一类型、再发布一次：

```ts
const a = (e: number) => console.log('a', e)
const b = (e: number) => console.log('b', e)

bus.on('foo', a)   // 表里没有 'foo'：开一条新记录 'foo' → [a]
bus.on('foo', b)   // 表里有 'foo'：直接 push 进去，'foo' → [a, b]
bus.emit('foo', 42)
// → a 42
// → b 42
```

发布时，表的内容是 `'foo' → [a, b]`；`emit` 把数组取出来、按下标 0、1 依次调用 `a(42)` 和 `b(42)`。

注意一件关键的事：**发布前后，这张表本身一字未动**。`emit` 只读、不写。这正是「状态即表」最朴素的证明——派发不是一个会改变状态的动作，它只是把表里早就记下的关系读出来执行一遍。

## 7. 教学简化说明

本章演示**故意省略**了：通配符 `'*'` 的第二条派发路径（第 6 章）、发布时的 `.slice()` 快照防御（第 5 章）、退订的 `>>> 0` 无分支技巧（第 4 章）、订阅时的惰性初始化与不去重语义（第 3 章）、`mitt()` 作为函数工厂与 `all` 可注入（第 2 章）、以及任何 TS 类型推导（第 7～8 章）。这一章只演一件事：**状态 = 一张表**。

## 8. 小结

mitt 在这一层只做了一件事：把发射器的全部状态定调成 `Map<EventType, Handler[]>`，剩下的全部从这个前提推出来。订阅、退订、发布没有第二套机制；换来极小体积与一行 `console.log` 就能窥探的透明，代价是放弃封装与一堆内置便利。下一章顺着这个前提走得更远：**既然状态只有一张表，那 emitter 还需要 `this` 吗？**
