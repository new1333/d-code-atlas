# 编译期宏的本质：运行时不存在的「变换提示」 · 主题精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：
  在声明式组件语法出现之前，要表达「这个组件接收哪些 props、触发哪些事件、暴露哪些方法」，使用者只能写完整的选项对象或 `setup(props, {emit})` 函数，并把模板用到的每个变量手动 return——样板冗长、类型推导差。更隐蔽的痛点是：这些「组件的静态结构信息」其实编译期就能完全确定，却被推迟到运行时用对象字面量去表达，每次渲染都要背着这份本可省掉的开销。使用者撞上的不是「能不能写」，而是「为什么这么确定的东西不能让编译器替我写、还要我在运行时反复声明」。

- **一句话核心思想**：
  宏是写给编译器看的「变换提示」——它假装成一个函数调用，实际只是给编译器一个锚点，让编译器在这个位置把声明式写法原地改写成等价的运行时代码，然后把自己从产物里彻底删掉。

- **设计动机（为什么需要它）**：
  宏要解决的矛盾是『运行时才能表达的约定』与『其实编译期就能确定』之间的错位——把这份约定**前移到编译期**，用一次编译期 AST 变换，换取①零运行时开销（编译期算完、运行时无解析成本）②更声明式的语法（一行替代样板）③类型友好（编译期能读 TypeScript 类型并生成运行时等价物）。
  **承前关系标注**：本章是全书地基章（无前置依赖），建立「编译期变换提示 / 伪函数」这个公理——后续 13 章全部建立在此之上。本章**只讲宏"是什么"**，不讲具体某个内置宏怎么去糖（→ 第 2 章『`<script setup>` 与内置宏的设计动机』），也不讲它靠什么机制识别与改写（→ 第 3 章编译管线 / 第 4 章 AST 识别 / 第 5 章 sourcemap）。

- **关键权衡（本 Atlas 的核心；3 条三段式）**：
  1. **选择「让宏伪装成普通函数调用、由编译器静态识别后擦除」→ 换来了「语法和普通函数一样自然、用户无需 import、且零运行时开销」→ 代价是「宏调用没有真实函数语义：不能赋值给变量、不能嵌套、不能放在条件或回调里、必须在顶层静态地写——因为它根本不是一个能在运行时被求值的函数」**。
  2. **选择「编译期完全确定地擦除并改写」→ 换来了「运行时产物干净、性能可预测、组件结构在编译期就定型」→ 代价是「普通 JS 工具链不认识这个'幽灵函数'：lint 工具会报未定义、纯 TypeScript 编译器不识别这些全局宏，必须额外靠语言服务层的虚拟代码才能获得类型提示与诊断」**。
  3. **选择「宏在运行时彻底消失」→ 换来了「不增加包体积、不增加任何调用栈层级」→ 代价是「可调试性受损：运行时断点、调用堆栈、报错位置都指向编译产物而非用户写的源码，必须依赖 sourcemap 才能还原回用户视角」**。

- **最小心智模型（6 步）**：
  1. 用户在源码里写下一个"宏调用"——它有名字、有参数，看起来和一个普通函数调用一模一样。
  2. 但这个名字在运行时根本不存在：它没有被 import，也不指向任何函数实体。
  3. 编译器在编译期把源码解析成 AST，按"调用名 + 出现位置"识别出哪些节点是宏调用。
  4. 对每个命中的宏调用节点，编译器用一段**等价的、可独立运行的实现代码**原地替换（或移除）它。
  5. 替换完成后，原宏调用的痕迹从 AST 里消失——产物里再也搜不到那个"函数名"。
  6. 最终交付的运行时代码中宏不存在，只留下它被改写后的等价物，因此运行时为零开销。

- **推荐的一个执行轨迹例子（演核心思想，不演全量）**：
  - **输入**：一段源码含 `const greeting = defineConstant('MSG', 'hello')`——一个伪装成函数调用的宏。
  - **关键中间态**：编译器解析后在 AST 上识别到一个调用节点，callee 名 = `defineConstant`；查表得知它是宏；用等价代码 `const MSG = 'hello'` 原地替换该节点，并把 `greeting` 绑定改指向新声明；原调用节点从 AST 移除。

## 概念要点

- **要点 1（官方定义）**：Vue 官方明确定义 `defineProps` / `defineEmits` 等为 **compiler macros（编译器宏）**——只在 `<script setup>` 内可用、**无需 import**、在处理 `<script setup>` 时被 **compiled away（编译擦除）**。这是"宏=运行时不存在的伪函数"这一论断的权威出处。依据: Vue.js 官方文档 `<script setup>`「Macros / defineProps & defineEmits」段。

- **要点 2（运行时无实体）**：宏在运行时**不作为可调用函数存在**。若因嵌套调用等原因导致编译器未能静态识别并改写它，运行时会抛 `ReferenceError: defineProps is not defined`——这是"它根本不是函数"的直接运行时证据。依据: Vue 官方文档 + Stack Overflow「ReferenceError: defineProps is not defined」案例。

- **要点 3（变换提示 / 伪函数本质）**：宏是**只在编译期有意义**的"特殊函数"，其作用是**给编译器一个变换锚点**，编译器据此把声明式写法改写成等价运行时代码，随后宏本身消失。这一定义与 Lisp / Elixir / Rust 宏家族的通用语义一致：宏在编译期展开（macroexpansion）/ 变换 AST，运行时不存在。依据: Vue Vine 官方 macros specification（"macros are special functions that only have meaning at compile time — hints for the compiler"）；Lisp / Elixir `defmacro` 通用宏理论（宏接收并返回 AST、在编译期展开）。

- **要点 4（必须顶层静态使用）**：所有 Vue 编译器宏共享「**必须在 `<script setup>` 顶层静态使用**」的约束——不能放进生命周期钩子、条件分支、回调或辅助函数内。原因是编译器做的是**静态分析 + 变换**，必须能在编译期定位到宏调用；嵌套/条件调用隐含运行时求值，与宏的编译期设计直接矛盾。依据: Vue 官方文档 `<script setup>` + Stack Overflow 相关问答。

- **要点 5（两类声明二选一）**：`defineProps` / `defineEmits` 的「**类型声明（type-based）**」与「**运行时声明（runtime declaration）**」**二选一、不可混用**。这反映了一个深层约束：宏必须在编译期**完整解析**出 props/emits 的结构定义——类型声明要求编译器读出 TS 类型并生成运行时等价物，运行时声明则直接采用对象字面量。依据: Vue.js 官方文档 `<script setup>`「type-based declaration vs. runtime declaration」段。

- **要点 6（换取的能力）**：编译期宏换取三项能力——① **零运行时开销**（编译期算完，运行时无解析成本）；② **声明式语法**（一行宏替代完整 setup 样板）；③ **类型推导**（编译期读 TS 类型生成运行时等价 props/emits，同时供编辑器类型提示）。依据: Vue 官方文档 + Vue Macros 官方博客「Supercharge Your Code with Vue Macros」。

- **要点 7（代价：普通 JS 工具不认识）**：因为宏是不需要 import 的"全局幽灵函数"，普通 JS 工具链默认无法按函数理解它——① lint 工具会报 `defineProps is not defined`，需通过配置 globals 或专用插件消除；② 纯 TypeScript 编译器不识别这些全局宏、Vue 编译器自身也不做类型检查，必须依靠 `vue-tsc` / Volar 语言服务层的虚拟代码才能获得类型与诊断。依据: DEV Community「fix 'defineProps' is not defined'」(ESLint globals)；Reddit / Vue 官方 TypeScript 指南（"Vue compiler does not type-check, run vue-tsc"）。

- **要点 8（Vue Macros 的角色 = 编译器能力的探索性扩张）**：Vue Macros 是一个**社区库**，实现 Vue 官方**尚未采纳**的宏提案——它本质上是对官方编译器「宏集合硬编码、可扩展性受限」的**临时性扩张**（许多宏如 `defineOptions` / `defineModel` 后来被官方吸收）。这一点揭示了"宏 = 编译器能力的扩张"的生态定位，也是后续 Vue Macros 全书主题的立身之本。依据: DEV Community「Collection of Vue Macros in Vue.js 3.3」（"a community library that implements proposals and ideas not yet officially adopted by Vue"）；Vue Core Issue #6392（defineModel/defineOptions 等经由 vite-plugin-vue / vue-loader 的编译期变换实现）。

## 关键流程

用户写宏调用 → 编译器解析源码为 AST → **静态识别**宏调用节点（按"调用名 + 位置"）→ 用**等价运行时代码原地替换**该节点 → 宏调用从 AST 消失 → 产出**干净的运行时代码**（零宏残留、零运行时开销）

补充维度（同一流程的两个观测面）：
- **源码侧**：存在一个伪装成函数调用的宏。
- **产物侧**：该"函数"完全不存在，只剩它的等价改写物。

依据: Vue 官方文档「compiled away」描述 + 通用编译期宏展开流程（Lisp macroexpansion / Elixir 编译期 AST 变换 / Vue 官方对 defineModel 的编译期展开说明）。

## 易混淆 / 边界 / 推断

- **事实**：宏调用在最终产物中**完全不出现**（不像普通函数会被打包保留），这是"运行时彻底擦除"的字面含义。依据: Vue 官方文档「compiled away」。
- **易混淆（编译期的所指）**：Vue 语境下的「编译期」指 **SFC / 模板的构建期编译**（由 vite-plugin-vue / vue-loader 在构建阶段执行），**不是**「JS 引擎的解析期」。宏在构建阶段就被处理完毕。依据: Vue Core Issue #6392。
- **易混淆（类型支持是两层）**：宏的"类型"支持分两层——**编译期**靠 Volar / vue-tsc 的虚拟代码层"假装"宏有类型；**运行时产物**靠编译器从类型声明生成的 runtime props 对象。这两层各自独立、必须语义对齐——这正是后续「双轨制」章（第 11 章）的核心命题，本章只需点明"宏的类型不是普通 TS 函数签名"。依据: Vue 官方 TypeScript 指南 + 社区「Vue compiler does not type-check」讨论。
- **推断（标注为推断）**：宏"伪装成函数调用"（而非用注解 / 装饰器 / 特殊指令语法）是**刻意的设计选择**——为了调用处语法自然、贴近用户既有的"函数调用"心智，降低学习成本。这一点官方未在单一文档里明述，属从语法形态反推的设计意图。
- **推断（标注为推断）**：Vue 宏**不是**完整的 hygienic macro 系统（如 Racket 的 scope-set 卫生展开），更接近"**编译器硬编码 / 可注册的固定变换集合**"——它的"卫生性"靠编译器对每个宏的专门实现保证，而非通用宏展开器。精确边界待进一步核对 Racket / hygienic macro 文献。
- **未理解 / 待查证**：宏调用在「同时存在 `<script setup>` 与普通 `<script>`」的混合 SFC 里，编译器的识别作用域与边界规则细节；以及 `useXxx` 风格的 Composition API 函数与 `defineXxx` 宏在编译器内部走的是否完全不同的代码路径——建议 Writer 在正文回避这两个边角，留作后续章或按需查证。
