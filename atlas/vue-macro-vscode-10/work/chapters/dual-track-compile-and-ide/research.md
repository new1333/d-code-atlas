# 双轨制：编译变换与 IDE 类型支持为何必须并存 · 主题精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：你在 `.vue` 里写了一个 Vue Macros 提供的宏（比如 `defineModels`），`vite build` 跑得好好的、上线没问题。可一回到编辑器，那行代码被红线波浪线标记为「未定义的函数」，补全也出不来。反过来也存在：IDE 给你完美的类型提示和补全，但一构建就报运行时错（宏没被变换，浏览器里它就是个 `undefined`）。同一个特性、两套工具链，认知却对不上——这就是双轨制要解释的根因。

- **一句话核心思想**：一个宏必须在两个**执行时机完全不同、消费者完全不同**的管线里各实现一遍——构建轨**真的改写代码**产出可运行的产物，智能轨**假装改写**生成内存里的虚拟代码骗过语言服务，两条轨语义必须对齐却各自独立。

- **设计动机（为什么需要它）**：宏的本质是「运行时不存在的编译期伪函数」（前置章已讲透）。这带来一个必然裂痕——**消费源码的两类工具看待它的方式完全相反**：
  - 浏览器/打包器**只信运行时**：源码里写宏调用，对它们而言就是个不存在的符号，必须有东西在构建期**真实**把它擦除、注入运行时代码。
  - 编辑器/语言服务**只信源码字面**：它直接看你磁盘上的文件（里面宏调用还在），却不会执行构建变换，于是对原生 TS 而言宏是「未声明的标识符」，必须有人在它眼皮底下**假装**这些宏合法、给出类型签名。
  两条轨都不能省：缺构建轨→运行时崩；缺智能轨→编辑器全红。这就是双轨**必须并存**的动机。
  - **承前关系（跨章去重信号）**：
    - 「unplugin：跨构建工具的统一插件抽象」（第 8 章）已讲透构建轨的**接入机制**（工厂函数把同一份 transform 适配到各打包器）。本章**不重讲**它怎么适配 Vite/webpack，只看它作为「**构建轨执行体**」的新侧面：它产出的是可运行 JS。
    - 「Vue Language Plugin 接口与 SFC 解析扩展点」（第 10 章）已讲透智能轨的**虚拟代码生成管线与扩展点**。本章**不重讲**插件怎么改写 SFC→虚拟代码的映射，只看它作为「**智能轨执行体**」的新侧面：它为什么不产文件、为什么不能被构建轨替代、为什么不能与构建轨合并成一条。

- **关键权衡（机制丰富章，4 条三段式，是正文核心原料）**：
  1. **分成两条独立管线而非一条** → 换来了**各轨可以按自己消费者的最优方式输出**（构建轨输出可运行 JS + sourcemap，串在打包流里；智能轨输出带双向位置映射的虚拟代码，供语言服务查类型）→ 代价是**同一个宏的语义要在两处各实现一次**，且必须人工保持对齐，任一侧更新滞后就割裂。
  2. **智能轨用「虚拟代码假装改写」而非「直接把编译产物喂给语言服务」** → 换来了**诊断位置能精确回映到用户源码**（补全、跳转、红波浪线都对得上你光标所在的位置，而不是变换后产物的位置）→ 代价是**要额外维护一套虚拟代码生成与双向 offset 映射**（这个代价的深度属前置章范围，本章只点明它对双轨对齐的影响：映射一旦失真，IDE 提示本身就不可信）。
  3. **用共享的工具底座承载两轨的「宏定义与识别」层** → 换来了**语义对齐的部分机制化保障**（改一处宏定义/识别规则，两轨都能感知，降低手抄漂移）→ 代价是**对齐仍非编译器级保证**——共享的只是「识别与定义」，两轨各自的「输出变换」（一个产 JS、一个产虚拟代码）无法共享，残留的语义漂移只能靠作者纪律 + CI 门禁兜底。
  4. **把双轨语义对齐当作「契约」而非「自动结果」** → 换来了**两轨可独立演进、独立优化、独立发布**（智能轨不必等构建轨、构建轨可针对性能单独调）→ 代价是用户侧可能遭遇三种割裂——「能跑但红线」「能提示但报错」「不红也能跑但类型与行为暗中不符（最危险，因为无报错信号）」。

- **最小心智模型（7 步）**：
  1. 用户在源文件里写下宏调用（编译期才有效、运行时不存在的伪函数）。
  2. 源码同时进入两条**互不调用**的管线。
  3. **构建轨**：transform 命中宏调用节点 → 真实擦除宏、注入运行时代码 → 产出可运行 JS（带 sourcemap）→ 喂给打包器/浏览器。
  4. **智能轨**：插件识别同一宏调用 → 在内存里生成「虚拟代码」，假装该宏是合法的、并给出类型签名 → 喂给 TS 语言服务。
  5. 语言服务基于虚拟代码产出诊断/补全，再按双向映射**回映到用户源码**的位置上显示。
  6. **契约**：同一宏在两轨的行为/类型语义必须对齐（构建轨注入的运行时行为 ≡ 智能轨声明的类型）。
  7. 一旦某轨滞后或两轨语义不一致 → 割裂；而契约无编译器级强制，靠作者纪律 + 把智能轨搬到命令行做 CI 门禁来兜底（这正是下一章 vue-tsc 的存在理由）。

- **最小原理演示（替代旧「复刻范围」）**：
  - **应演示**：一个极简到只表达「双轨」思想的从零实现（几十行 TS/JS 即可）。核心是一个假宏 `__sayHi(name)`，然后为它**各自**写两条轨：
    - 构建轨：一个 `transform(source)` 函数，识别 `__sayHi("x")` 调用，把它就地替换成 `console.log("hi x")`，返回变换后的可运行代码（模拟「产生物」）。
    - 智能轨：一个 `getVirtualCode(source)` 函数，**不**改源码，而是返回一段「前置类型声明」虚拟片段 `declare function __sayHi(name: string): void;`（模拟「假装改写、给语言服务看」）。
    - 再用一张**四格矩阵**演示状态：① 只配构建轨 → 运行 OK 但 IDE 标红；② 只配智能轨 → IDE 不红但运行时 `__sayHi is not defined`；③ 两轨都开且语义一致（都把入参当 string）→ 既不红也能跑；④ 故意让两轨语义不一致（构建轨按 string 产物、智能轨声明成 number）→ 不红也能跑，但用户拿到错误类型提示（演示最危险的隐性割裂）。
  - **每一行都要对应上面某个原理点**：`transform` = 轨道 A「真改写、产生物」；`getVirtualCode` = 轨道 B「假改写、不产文件」；四格矩阵 = 割裂的三态 + 对齐态；③④的对照 = 「对齐是契约不是自动」。
  - **应故意省略**：真正的 unplugin 工厂、真正的 Volar 插件协议、sourcemap、双向 offset 映射的实现、AST 精确解析（演示里用最简字符串匹配即可，目的不是健壮性而是演「两轨并存」思想）、多打包器适配。
  - **演示载体建议**：**首选 TS/JS**（本 Atlas 产物是 JS 生态站点，TS/JS 对读者最友好）。用纯函数模拟两条轨即可，无需真的接入打包器或起语言服务。

- **正文不宜展开的细节**：unplugin 工厂如何适配各打包器（第 8 章已讲）；Volar 虚拟代码双向 offset 映射的具体实现（前置章已讲）；vue-tsc 如何把智能轨搬到 CLI 做 CI 门禁（下一章主题，本章只点到「这是对齐兜底」）；配置 schema 如何成为两轨唯一真相源（后置「配置系统」章）；各具体宏的语法差异与设计原型分类（前置「宏的设计原型」章）。

- **推荐的一个执行轨迹例子**：输入一个 `.vue`，里头写 `defineModels<{ foo: string }>()`。→ 构建轨：transform 命中 → 注入 `props.foo` 与 `emit('update:foo', …)` → 运行时可双向绑定。→ 智能轨：虚拟代码里声明 `model foo: string` 类型 → IDE 能补全 `v-model:foo`、类型检查通过。→ 对照：若只配构建轨，IDE 把 `defineModels` 标红（未定义符号）；若只配智能轨，`vite build` 时该宏未被变换，运行时抛 `defineModels is not defined`。

## 概念要点
- 宏是「只在编译期有意义、运行时被彻底擦除」的伪函数，它本身不是会在运行时被调用的方法。依据: Vue Macros 官方 Reactivity Transform 文档（明确写 `$ref()` 这类是 compile-time macro，"不会在运行时被调用，而是编译器把它当作提示"）。
- Vue Macros 官方把**集成显式分成两步独立配置**：「打包器/编译变换集成」与「TypeScript Support / Volar Support」是分别给出的两段——前者配 unplugin，后者既要在 tsconfig 加 `types`，又要配 `vueCompilerOptions.plugins: ["vue-macros/volar"]`。依据: Vue Macros 官方 Bundler Integration 指南（该页把 "TypeScript Support" 与 "Volar Support" 作为并列独立小节呈现）。
- 每个宏包**典型地提供两层实现**：bundler 侧的 unplugin transform + 语言工具侧的 Volar 插件。monorepo 内有共享包 `@vue-macros/common`，被两侧共同依赖，承载 AST 辅助/类型解析/宏定义等公共逻辑。依据: vue-macros 官网与 GitHub 仓库描述（同时标注 "Full TypeScript / Volar support" 与 "powered by unplugin"）；@vue-macros/common 与 @vue-macros/volar 的 npm 依赖关系（@vue-macros/volar 依赖 @vue-macros/common）。
- 双轨割裂是**真实可观察的痛点**，而非理论假设：build 期支持与 IDE 期支持会出现不同步，导致「能跑但红线」或「能提示但报错」。依据: DEV Community「Collection of Vue Macros in Vue.js 3.3」指出由于 Vue Macros 实现的是官方尚未采纳的提案，IDE 支持常常落后于 build 支持；Stack Overflow「Volar and vue-tsc are showing different TS errors」与 create-vue #437（type-check reports errors twice）记录了编辑器诊断与构建期/CLI 类型检查不一致的现象。
- **推断（标注为推断）**：智能轨不能直接复用构建轨的编译产物喂给语言服务，因为编译产物的 offset 已与用户源码脱钩，诊断/补全位置会整体错位；这正是前置章「Volar 虚拟代码 + 双向位置映射」存在的根本理由。依据: 基于前置章已建立的「虚拟代码必须保留与源码的双向 offset 映射」原理所作的推断，未在官方文档见到显式论述。
- **推断（标注为推断）**：两轨无法合并为单一变换，因为两轨**消费者本质不同**——构建轨消费者是打包器/浏览器（要可运行 JS），智能轨消费者是 TS 语言服务（要带位置映射的虚拟代码），输出格式与生命周期无法统一。依据: 基于上述两轨消费者差异与官方「两步独立配置」事实所作的架构职责推断。

## 关键流程
用户源码（.vue，含宏调用）分叉进入两条**互不调用**的管线：

```
                         ┌─→ 构建轨: unplugin transform ─→ 擦除宏 + 注入运行时代码 ─→ 可运行 JS(带 sourcemap) ─→ 打包器 / 浏览器
用户源码 (.vue, 含宏) ──┤
                         └─→ 智能轨: @vue-macros/volar ─→ 生成虚拟代码(假装宏合法 + 给类型签名) ─→ TS 语言服务 ─→ 诊断/补全回映到 .vue 源码
                                                          ↑
                                            语义对齐契约: 两轨对同一宏的「行为 / 类型」必须一致
                                            (共享 @vue-macros/common 降低漂移，但非编译器级保证)
```
依据: Vue Macros 官方 Bundler Integration 指南（两步独立配置：unplugin 集成 + TypeScript/Volar 支持）；vue-macros monorepo 结构（每个宏包双层实现 + 共享 common 包）。

## 易混淆 / 边界 / 推断
- **事实**：双轨**不是**「同一个变换被调用两次」，而是「两套独立实现，对同一宏各跑一次、各产各的输出」。
- **事实**：共享 `@vue-macros/common` **不等于自动对齐**。它只共享「宏识别与定义」层；两轨各自的「输出变换」（一个产 JS、一个产虚拟代码）无法被共享，因此对齐仍是契约，不是机制结果。
- **事实**：割裂有三种形态，危险度递增——① 能跑但红线（构建轨新、智能轨旧）；② 能提示但报错（智能轨新、构建轨旧）；③ 不红也能跑但类型与行为暗中不符（两轨都「认识」宏，但语义理解不一致）。第三种最危险，因为没有报错信号提醒用户。
- **推断（衔接下一章）**：vue-tsc 之所以存在，正是为了把「智能轨」搬到命令行、用 CI 门禁倒逼两轨对齐——它构成双轨的「对齐兜底」。但需注意：vue-tsc 复用的是**智能轨（虚拟代码）**而非**构建轨（unplugin transform）**，所以「vue-tsc 通过」并不等价于「构建产物正确」（构建轨若滞后或开关漂移，vue-tsc 查不出来）。依据: 依据下一章主题与前置章 volar-language-plugin 所述「语言插件复用」原理的推断，供 Writer 做与下一章的衔接，正文不必深挖。
- **未理解 / 待查证**：未见官方文档**显式**论述「为什么 transform 与 volar 不能复用同一段代码」这一设计决策（相关结论目前为基于架构职责的推断，非官方原文陈述）。若后续能查到维护者层面的架构说明（如 RFC、设计 issue、会议笔记），可补充为强事实。
