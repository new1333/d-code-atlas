# 双轨制：编译变换与 IDE 类型支持为何必须并存

> 本章属于 system 层。前置：unplugin-abstraction、volar-language-plugin。
> 学完你能：用一句话讲清「为什么同一个宏必须在两条管线里各实现一次、两条轨为什么不能合并成一条、为什么对齐靠契约而不靠机制自动保证」。

## 1. 为什么需要它：能跑但红线，能提示但报错

上一章我们让自定义宏走进了 IDE 的虚拟代码管线，TS 语言服务终于认得 `defineModels` 这类用户宏了。但这只是事情的一半。

设想你刚把 `defineModels<{ foo: string }>()` 写进 `.vue`，跑 `vite build`，产物上线，运行得好好的。回到编辑器，那一行却被红线标了「未定义的函数」，补全也出不来。

反过来也成立：你给项目加了 IDE 支持，光标悬停、补全、跳转一应俱全；可一构建、一上浏览器，控制台就抛 `defineModels is not defined`。

这两种状态都是真实可观察的，它们就是双轨制的根因表象。问题根源在于：**消费你源码的工具分成两类，它们看待宏的方式正好相反**。

- 打包器和浏览器只信运行时。你源码里写宏调用，对它们来说就是不存在的符号，必须有东西在构建期真的把它擦除、把运行时代码塞进去，否则线上必崩。
- 编辑器和语言服务只信磁盘上的源码字面。它直接读你写的文件（里面宏调用还在），但不会跑构建变换，于是对原生 TS 来说宏就是个未声明的标识符——必须有东西在它眼皮底下「假装」这宏合法、给出类型签名，否则满屏红线。

两条轨都不能省。缺构建轨运行时崩，缺智能轨编辑器全红。这一章要回答的是：**它们为什么必须分成两条独立管线，而不是同一段变换被调用两次**。

## 2. 核心思想：同一份源码，两条管线各跑一遍同一个宏

双轨的本质是：一个宏必须在两条消费者完全不同、输出格式完全不同的管线里**各实现一遍**——构建轨真的改写源码产生可运行 JS，智能轨假装改写、只产内存里的虚拟代码骗过语言服务。两条轨语义必须对齐，却各自独立、互不调用。

本章不重讲上一章「虚拟代码 + 双向 offset 映射」本身怎么工作，也不重讲第 8 章 unplugin 怎么适配多打包器。我们聚焦新问题：这两套东西为什么不能合成一条、为什么对齐这件事只能靠契约兜不住靠机制。

## 3. 心智模型：源码的分叉与交汇

源码进来，立刻分叉：

```
                         ┌─→ 构建轨: unplugin transform ─→ 擦除宏 + 注入运行时代码 ─→ 可运行 JS + sourcemap ─→ 打包器/浏览器
用户源码 (.vue, 含宏) ──┤
                         └─→ 智能轨: @vue-macros/volar ─→ 生成虚拟代码(假装宏合法 + 给类型签名) ─→ TS 语言服务 ─→ 诊断/补全回映到源码
                                 ↑
              语义对齐契约: 同一宏在两轨的「行为/类型」必须一致
              (共享 @vue-macros/common 降低漂移，但非编译器级保证)
```

四件事要记住：

1. **两轨互不调用**。构建轨跑完不知道智能轨存在，智能轨也完全不依赖构建轨产物。它们各自从源码出发。
2. **两轨输出格式天差地别**。构建轨产可运行 JS（带 sourcemap），串在打包流里；智能轨产带双向位置映射的虚拟代码，喂给 TS 服务查类型。
3. **共享的只是「识别与定义」层**。同一个 `@vue-macros/common` 包告诉两轨「这个宏叫 `defineModels`、长这样」，但两轨各自的「输出变换」（一个写 JS、一个写虚拟代码）无法共享。
4. **对齐是契约，不是机制结果**。没有任何编译器级保证能让你「改一处自动两轨同步」。改完宏语义、只更新了一侧的包，另一侧就落后了。

这就是后面所有权衡展开的舞台。

## 4. 关键权衡

### 两条独立管线，而非一段变换调两次

最直接的取舍问题：**为什么不把同一段变换写一次，在构建期和 IDE 里各调一次？**

答案是两轨消费者的输出需求根本对不齐。打包器要的是「能跑的 JS 文件」——必须真的把宏调用擦掉、把运行时代码塞进去。语言服务要的是「能查类型的虚拟代码」——它甚至不能让宏消失，反而要让宏「看起来是个合法函数」，否则光标悬停、补全、跳转都出不来。

如果硬要把两轨合成一条，输出格式要么偏向 JS（IDE 拿不到能查类型的代码），要么偏向虚拟代码（浏览器拿到一堆类型声明，没有运行时实现）。**两轨各自按自己消费者的最优方式输出**，这是双轨并存的核心收益。

代价是：同一个宏的语义要在两处各实现一次。`defineModels` 在 unplugin 那侧写一段、在 volar 插件那侧再写一段。两段不能互相校验，只能靠人维护同步。这里化解的本质矛盾是「消费者异构 vs 共享实现成本」——只要两类消费者对输出格式诉求相反，你就必须接受两份实现。

### 智能轨假装改写，而不是把编译产物直接喂给 TS

智能轨这条线还有一个二级选择：**为什么不让 TS 直接看构建轨产的可运行 JS？**

因为 offset 全错。构建产物里宏调用已经被擦除、运行时代码已经塞进去，行号、列号跟用户在编辑器里看到的源码完全对不上。如果 TS 看到第 12 行有错，IDE 把红波浪线画到用户源码第 12 行——可那一行用户写的是别的代码。诊断、补全、跳转全部错位。

所以智能轨不喂编译产物，而是另起一段「虚拟代码」：保留宏调用的位置（让诊断能对齐用户源码），同时把它声明成合法函数（让 TS 认得它）。这就是「假装改写」的意思——产出一份专门给语言服务看的版本，并不真的改源码。

代价是要额外维护一套虚拟代码生成与双向 offset 映射（这个机制的深度是前置章的内容，本章只点它对双轨的影响：映射一旦失真，IDE 提示本身就不可信，红波浪线会画错位置）。化解的本质矛盾是「位置保真 vs 类型合法性」——你既要保住用户源码的位置、又要让 TS 当它是合法代码，唯一的办法是不动源码、另起一份虚拟版本。

### 共享的只是「识别与定义」层

为了降低两轨漂移，Vue Macros 让两轨共享同一个 `@vue-macros/common` 包——承载 AST 辅助、类型解析、宏定义。改一处宏识别规则，两轨都能感知。

但**这只共享了「识别」**，不共享「输出」。识别 `defineModels` 是什么、长什么样可以共享；怎么把它变成 JS、怎么把它变成虚拟代码，这两段无法共享。换句话说，两轨对宏的「理解」可以共享，两轨对宏的「翻译」必须各写一遍。

代价是：**对齐仍然不是编译器级保证**。共享包降低了一类漂移（识别漂移），但另一类漂移（输出语义漂移）完全裸奔——构建轨注入的运行时行为可能跟智能轨声明的类型对不上，编译器查不出来。残留漂移只能靠作者纪律加 CI 门禁兜底。化解的本质矛盾是「DRY 与异构输出不可兼得」——能抽出来的公共部分有限，剩下不能共享的部分才是双轨对齐的真实风险面。

### 对齐是契约，不是自动结果

把上面三条压成一条总取舍：**双轨语义对齐靠人维护，不靠机制保证**。

换来的是**两轨可独立演进、独立优化、独立发布**。智能轨加新特性不必等构建轨，构建轨调性能不必担心影响智能轨。两个包各自的版本号可以错峰。

代价是用户侧可能遭遇**三种割裂**，危险度递增：

- **能跑但红线**：构建轨新、智能轨旧。构建产物没问题，但 IDE 满屏红线。有视觉信号，能发现。
- **能提示但报错**：智能轨新、构建轨旧。IDE 看起来完美，但 `vite build` 一跑就崩。有报错信号，能发现。
- **不红也能跑，但类型与行为暗中不符**：两轨都「认识」宏，但对它的理解不一致——比如智能轨声明 `model: string`、构建轨实际按 `number` 注入。不红、不报错、能跑，但用户拿到的类型提示是错的。**这一种最危险，因为没有信号提醒用户**，bug 会潜伏到运行时崩。

化解的本质矛盾是「演进自由 vs 行为一致性」——你不可能既要两轨独立发布节奏、又要它们语义自动对齐。承认对齐是契约，就是承认这条路有不可避免的维护成本。

## 5. 最小原理演示：双轨并存的玩具模型

下面几十行 TS 演示双轨思想。我们造一个最简宏 `__sayHi(name)`，构建轨把它换成 `console.log("hi " + name)`，智能轨给它一个类型声明。然后跑四格矩阵看会发生什么。

```ts
// 一个最简宏：源码里写 __sayHi("alice")，构建期把它替换成 console.log

// === 源码 ===
const userSource = `
  __sayHi("alice");
`;

// === 构建轨：真的擦除宏、注入运行时代码，产出可运行 JS ===
function transform(source: string): string {
  // 命中宏调用节点（这里用最简字符串匹配，真实场景靠 AST）
  // 把 __sayHi("x") 整体替换为 console.log("hi x")——擦掉宏、塞进运行时代码
  return source.replace(
    /__sayHi\((".*?")\)/g,
    (_, name) => `console.log("hi " + ${name})`,
  );
}

// === 智能轨：不改源码，返回一段「前置类型声明」给 TS 看 ===
function getVirtualCode(source: string): string {
  // 检测源码里是否用了 __sayHi（同样，真实场景靠 AST）
  // 返回的虚拟代码声明这个宏是合法函数——这就是「假装改写」
  // 源码本身没动，TS 读源码 + 读这段虚拟代码，就能不报错地理解 __sayHi
  if (source.includes("__sayHi")) {
    return `declare function __sayHi(name: string): void;\n`;
  }
  return "";
}

// === 模拟两轨被独立开关 ===
type Track = "build" | "ide";
function simulate(
  tracks: Track[],
  buildAssumesString = true,
  ideAssumesString = true,
) {
  const buildOn = tracks.includes("build");
  const ideOn = tracks.includes("ide");

  // 构建轨产物：决定运行时行为
  const built = buildOn ? transform(userSource) : userSource;

  // 智能轨产物：决定 IDE 类型提示
  // 故意加 ideAssumesString 开关，下文用它演示「两轨语义漂移」
  const virtual = ideOn
    ? ideAssumesString
      ? `declare function __sayHi(name: string): void;\n`
      : `declare function __sayHi(name: number): void;\n`
    : "";

  return { built, virtual, buildOn, ideOn };
}

// === 四格矩阵：把双轨对齐的三态 + 对齐态一次性演完 ===

// 状态①：只开构建轨——产物正确，但 IDE 没有 __sayHi 的声明，会标红
const case1 = simulate(["build"]);
console.log("① 只构建轨 →", case1);

// 状态②：只开智能轨——IDE 不红，但产物里 __sayHi 还在，运行时崩
const case2 = simulate(["ide"]);
console.log("② 只智能轨 →", case2);

// 状态③：两轨都开且语义一致——既不红也能跑
const case3 = simulate(["build", "ide"], true, true);
console.log("③ 两轨对齐 →", case3);

// 状态④：两轨都开但语义漂移——不红也能跑，但用户拿到的类型是错的
// 构建轨按 string 注入、智能轨却声明成 number：IDE 提示接 number，运行时却接 string
const case4 = simulate(["build", "ide"], true, false);
console.log("④ 暗中漂移（最危险） →", case4);
// case4 没有任何报错信号——这正是双轨对齐为何必须靠契约、而非自动机制
```

跑一下：状态①产物里 `__sayHi` 已被擦掉换成 `console.log("hi alice")`，但虚拟代码为空，TS 不认这宏；状态②反过来，虚拟代码声明齐全，但产物里 `__sayHi` 原封不动，浏览器一跑就崩；状态③是理想态；状态④最隐蔽——两轨都「认识」宏，但类型与行为对不上，IDE 给出错误提示却毫无警报。

这段演示故意省略了真正的 unplugin 工厂、Volar 插件协议、sourcemap、双向 offset 映射、AST 解析（用字符串匹配代替）——目的不是健壮性，只是把「两轨并存」的思想演透。

## 6. 执行轨迹：defineModels 走两条轨

拿一个真实宏看双轨怎么各自走完一遍。输入：

```vue
<script setup lang="ts">
const models = defineModels<{ foo: string }>();
</script>
<template>
  <input v-model="foo" />
</template>
```

**构建轨**（unplugin transform 命中后）：

1. 拿到 `<script setup>` 的源码 AST。
2. 遍历到 `defineModels` 调用节点，识别成功（共享 `@vue-macros/common` 的识别规则）。
3. 用 magic-string 擦除宏调用，注入等价的运行时代码：声明等价的 `props.foo`、`emit('update:foo', …)`，让浏览器里能双向绑定。简化示意产物大致长这样：

```js
const props = defineProps({ foo: { type: String } });
const emit = defineEmits(['update:foo']);
const models = { get foo() { return props.foo }, set foo(v) { emit('update:foo', v) } };
```

4. 产出变换后的可运行 JS + sourcemap，交给打包器。

**智能轨**（@vue-macros/volar 命中后）：

1. 拿到同一个 `.vue` 源码。
2. 在虚拟代码生成阶段识别出 `defineModels` 调用。
3. **不擦除**宏调用（保住位置），在虚拟代码里追加类型声明：声明 `models.foo` 是 `string` 类型、可读可写；让 TS 知道 `v-model:foo` 绑定的就是这个 model。
4. 把虚拟代码 + 双向 offset 映射喂给 TS 语言服务。
5. IDE 因此能补全 `v-model:foo`、能在类型不匹配时画红线、能光标悬停看类型。

**对照**：如果只配了构建轨，IDE 看到的源码里 `defineModels` 没有任何声明，红波浪线。如果只配了智能轨，`vite build` 时 unplugin 没启用，`defineModels` 原封不动进了产物，运行时抛 `defineModels is not defined`。

## 8. 小结

宏注定要活在两条管线里：一条真改代码产生物、一条假装改写产虚拟代码。它们消费者不同、输出格式不同，所以无法合并，对齐只能靠契约兜。最危险的不是「能跑但红线」或「能提示但报错」，而是两轨都认识宏、语义却暗中漂移——这种 bug 没有信号。
