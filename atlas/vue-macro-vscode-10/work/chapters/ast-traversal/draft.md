# 靠 AST 而非正则识别宏调用节点

> 本章属于 primitive 层。前置：「SFC 编译管线与宏的注入时机」。
> 学完你能：用一句话讲清「为什么宏识别必须靠 AST 的结构化条件而非正则、这种健壮性换来什么、代价是什么」。

## 1. 为什么需要它

上一章把一件事定下来了：宏的变换不能趴在源码字符串上做，得挂到 `compileScript` 的 AST 遍历那一步，因为只有拿到 AST 才谈得上精确识别。但那只回答了「在哪做」，留下了一个更要紧的口子：「具体怎么把一个宏调用节点从整段脚本里挑出来」。本章就接着这个口子往下拆。

先说最朴素的冲动。你盯着 `defineProps({ count: Number })` 这行，心想这不就是「`defineProps` 加个括号」嘛，写个正则到文本里捞不就行了？比如 `/defineProps\s*\(/g`。听起来合理，直到你的脚本长成这样：

```ts
// 用 defineProps() 来声明 props
const tip = "defineProps() in string";
defineProps({ count: Number })
```

拿这个正则去跑，三处命中：第一行注释里的 `defineProps()`、第二行字符串里的 `defineProps()`、第三行真正的调用。可你真正想变换的只有第三行。前两处是纯粹的误命中，但正则分不清，因为在它眼里整段文本就是一串平等的字面字符，它不知道哪里是注释、哪里是字符串。

矛盾就在这：宏调用「写在代码里、长得像函数调用」，可它和注释、字符串里的同名文字在文本层面毫无区别。靠描字面根本分不开。解析器能分开，因为它会把源码拆成一棵带类型的节点树——第一行的内容挂成「注释附件」，第二行变成「字符串字面量的值」，只有第三行才是「调用表达式」节点。换到这棵树上挑，前两行天然就不在候选里。

## 2. 核心思想

区别就在这一步：先让解析器把源码变成一棵带类型的节点树，再用「节点类型 + 被调用者名」这两个结构化条件去精确命中，而不是去文本里描字。

## 3. 心智模型

打个比方：正则像在一张写满字的纸上找某几个墨迹连成的形状，纸上哪是注解、哪是引文它一概不知；AST 像是有人已经把这张纸拆成零件，每个零件都贴了型号标签（节点类型）和位置标签（字节区间），你只要按型号挑就行。

这套识别走六步：

1. 用成熟的 JS/TS 解析器把 `<script setup>` 文本解析成一棵节点树。每个节点都自带它在原文里的字节区间（`start`/`end`）。
2. 遍历这棵树，每碰到一个节点就问第一个问题：「你的类型是调用表达式（CallExpression）吗？」
3. 若是，再问第二个问题：「被调用者是一个裸标识符（Identifier）吗？」这一问顺带把 `obj.defineProps()` 这种成员访问排除了——它的被调用者是 MemberExpression，不是 Identifier。
4. 若是，问第三个问题：「这个标识符的名字，在已注册的宏名单里吗？」
5. 三个问题全「是」，就算命中。把它的参数节点和字节区间取出来，交给后面的变换器。
6. 至于注释、字符串，它们的节点类型压根不是调用表达式，在第二步就被挡掉了，根本不用为它们写任何特殊规则。

注意第二步那个「按型号挑」是整套机制的关键：注释和字符串不是被你「特判」掉的，而是它们的结构注定了过不了「你是调用表达式吗」这一关。这种排除是免费的、必然的，不像正则那样得靠更复杂的规则去补窟窿。

## 4. 关键权衡

（上一章已经讲透了「宏变换挂在 AST 遍历阶段而非字符串阶段」这个时序决策，这里不重复，只看结构化识别本身带来的取舍。）

**权衡一：全量解析换正确性，代价是付不起「带病运行」。**
选择让每个文件都走一遍完整的 Babel 解析（开 typescript、jsx 插件），换来的是 100% 的语法正确性——注释、字符串、嵌套括号、TS 泛型全都被正确归类，匹配结果可以完全信任。代价有两层：一是每个文件都要实打实付一次解析开销，没法像正则那样几乎免费；二是源码一旦有语法错误，解析直接失败，宏变换整个卡住。这背后是对立的两头：一边要「匹配绝对正确」，一边要「对残缺源码也能凑合产出」。正则方案能带病运行、多少捞点东西出来，AST 方案在这个维度上反而更脆——它宁可不跑，也不跑出错的结果。这种「宁缺毋滥」正是它健壮性的另一面。

**权衡二：抽象掉源码格式换健壮性，代价是改写只能认 offset。**
AST 节点里不存空格、换行、注释位置这些排版信息，匹配只看结构。这换来的是对用户写法完全不敏感：你怎么排版、括号换不换行、注释写在哪，识别结果都一样。换句话说，用户改一行排版再也不会让宏识别崩掉。代价是节点看不见自己原来的文本长相，想做就地改写，手里唯一的抓手就是节点带的字节区间（`start`/`end` 这两个数字）。报错定位也得靠这个区间回溯到用户源码。这正是紧邻下一章的入口——光知道在哪个区间改还不够，怎么改了还能还原 sourcemap，是 magic-string 要解决的事。

**权衡三：只认名字不查作用域，换来极简判定，代价是会被局部变量骗。**
三个判定条件只看「名字叫 defineProps」，并不验证这个名字指向的是不是真正的宏。好处很明显：判定是 O(1) 的字符串比较，实现极简，不用理解作用域。代价是它会被人钻空子——要是有人在函数内部写 `const defineProps = () => {}` 然后调用它，纯结构匹配会把它当宏命中。工程上的兜底是再补一道作用域校验：用解析器的绑定信息（scope binding）确认这个标识符解析到的是真正的宏、没被局部变量遮蔽。vue-macros 里就有这么一个校验步骤（复用了官方的 `walkIdentifiers`）。这里的本质矛盾是「判定便宜」和「判定准确到作用域」两头不可兼得：你想用最便宜的名字比对，就不得不放弃追问「这个名字到底指的是谁」。

**权衡四：脚本块认 Babel 的 CallExpression，换来全语种支持，代价是和模板 AST 异构。**
正因为 `<script setup>` 里是 JS/TS 代码，我们用的是 Babel 那套 ESTree 节点类型（`CallExpression`、`Identifier`，`type` 是运行时可见的字符串），而不是 Vue 模板的那套（`JS_CALL_EXPRESSION` 等，还是运行时被擦除的 const enum）。换来的是对 TS 类型标注、JSX、装饰器这些 JS/TS 全语种的成熟支持，识别宏调用的逻辑可以写得非常稳。代价是 `<script>` 和 `<template>` 是两棵结构完全不同的树，跨边界的语义得在管线里手工桥接，没法用同一套访问者一把梭。

## 5. 最小原理演示

下面这段演示只演透一件事：怎么在 Babel 产出的 AST 上，用三个结构化条件精确命中宏调用，并且和朴素正则做对照。每一行都对得上前面的某个原理点。

```ts
import { parse } from "@babel/parser";

const MACROS = new Set(["defineProps"]); // 已注册的宏名单

// 输入：注释里、字符串里都"长得像"宏调用，故意布满干扰
const source = `// 用 defineProps() 来声明 props
const tip = "defineProps() in string";
defineProps({ count: Number })
`;

// 【步骤 1】让解析器把源码变成一棵带类型的节点树
const ast = parse(source, { plugins: ["typescript"] });

// 一个极简访问者：递归访问每个节点，对每个节点跑一次回调
function walk(node, visit) {
  visit(node);
  for (const v of Object.values(node)) {
    for (const k of Array.isArray(v) ? v : [v]) {
      if (k && typeof k.type === "string") walk(k, visit);
    }
  }
}

// 【步骤 2～4】对每个节点问三个结构化问题
const hits = [];
walk(ast, (node) => {
  if (node.type !== "CallExpression") return;     // 问题一：你是调用表达式吗？
  if (node.callee.type !== "Identifier") return;  // 问题二：被调用者是裸标识符吗？
  if (!MACROS.has(node.callee.name)) return;      // 问题三：名字在宏名单里吗？
  hits.push({ name: node.callee.name, start: node.start, end: node.end });
});

console.log("AST 命中数:", hits.length);           // → 1，只有真实调用那行

// 【对照】朴素正则在同一份文本里捞 defineProps(
const regexHits = source.match(/defineProps\s*\(/g);
console.log("正则命中数:", regexHits?.length ?? 0); // → 3：注释、字符串、真实调用各一
```

跑起来你会看到两行输出：`AST 命中数: 1` 和 `正则命中数: 3`。同样的文本，正则多捞了两处根本不是调用的东西，AST 一个不多一个不少。注意 `hits` 里存了 `start`/`end`——这两个字节区间就是节点自带的「在原文哪里」的坐标，留给变换器用。

## 6. 执行轨迹

拿上面那段三行输入，一步步看两边各自发生了什么。

解析阶段，Babel 把三行拆成这样：第一行 `// 用 defineProps() 来声明 props` 整个变成一条注释，作为「注释附件」挂在第二条语句上，它不是任何调用节点的来源；第二行 `const tip = "defineProps() in string"` 变成一个变量声明，里面的 `defineProps()` 只是字符串字面量（StringLiteral）的值，同样不是调用节点；只有第三行 `defineProps({ count: Number })` 变成一个货真价实的调用表达式节点，被调用者是名为 `defineProps` 的裸标识符，带一个对象字面量参数，`start`/`end` 正好框住第三行。

正则那边没有「拆零件」这一步。它在整段文本里逐字符扫 `/defineProps\s*\(/`：第一行注释里的 `defineProps()` 命中，第二行字符串里的 `defineProps()` 命中，第三行真实调用的 `defineProps(` 也命中，共三处。它没法知道前两处一个是注释、一个是字符串，因为在它眼里全是平等的字面字符。

于是访问者只对第三行触发，拿到参数和字节区间；正则对三行全部触发，其中两处是假警报。如果你在这段输入后再加一行 `obj.defineProps()`，正则还会再多捞一处，而 AST 因为被调用者是 MemberExpression、过不了问题二，依旧只命中真实调用那一处——结构匹配的红利在这里白捡。

## 7. 教学简化说明

这段演示故意省了几样东西：真正的就地改写留给下一章 magic-string；宏的完整变换语义（比如 props 的类型推导）属后续章节；作用域遮蔽校验只是点到，没在演示里实现；`walk` 是手写的最小递归，真实工具会用 `@babel/traverse` 或官方的 `walkIdentifiers`，还要处理多文件过滤、unplugin 集成、错误恢复这些工程脚手架。这些都不影响「用结构化条件精确识别」这个核心原理。

## 8. 小结

回到那句话：宏识别认的是结构，不是字面。把源码变成带类型的节点树之后，「调用表达式 + 裸标识符 + 名字命中名单」三个条件就能把宏调用一个不漏、一个不错地挑出来，注释、字符串、成员访问这些正则的噩梦被结构天然挡在门外。代价你也看见了：要付解析开销、容忍不了语法错误、改写只能捏着字节区间。而这个「只能捏着字节区间」恰恰把问题交到了下一章手里——光知道改哪个区间还不够，怎么在区间上动手脚还能让 sourcemap 追回用户源码，就是 magic-string 要解决的事。
