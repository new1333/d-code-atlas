# 宏的设计原型：把什么前移到编译期 · 主题精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：没有这套宏之前，Vue 开发者每天在手写三类本可自动生成的东西——
  写一个组件 `v-model` 要手动凑齐「一个 prop + 一个 emit + 一个带 get/set 的 computed」三件套；
  props 一旦解构就丢响应性，被迫满文件写 `props.foo` 而不敢用解构语法；
  想用 JSX / render 函数就得整体退出 `<script setup>`、退回老式 `setup()` 函数。
  这些都不是「逻辑难」，而是「样板在手写、约定靠人记」。Vue Macros 追问的是：这些手写样板里，
  哪些是编译器能**确定性地**替你推导出来的？能推导出来的，就不该再让人写。

- **一句话核心思想**：判断一个特性该不该做成宏的唯一判据是——**它能否被一段确定性的编译期变换，
  从用户写的简写形式唯一地还原成等价的标准 Vue 代码**；能就是宏，需要运行期信息或外部状态的就不是。

- **设计动机（为什么需要它）**：Vue 官方编译器只内置了一小撮宏，大量社区痛点的解法是「编译器能做但官方还没做」。
  Vue Macros 把这些『能做但没做』的能力收编成可选语法糖，让写法可以比官方激进得多地试错——这是它的生态位。
  承前关系：（**已在第 6 章『Vue Macros 的宏变换流水线』讲透单条流水线的『注册宏→遍历 AST→命中节点→magic-string 注入』
  与多宏改写同一节点的统一 walk 调度**，本章不重演这条机制；本章只看它的新侧面——流水线上承载的『**变换内容**』
  有哪些可归纳的设计原型，即从『一条管线怎么跑』上升到『整张宏目录里的原料只有几类』）。

- **关键权衡（本 Atlas 的核心，4 条）**：
  1. **「确定性可还原」作为收编门槛**：选择只收编那些能被编译期唯一还原成标准代码的特性 → 换来了宏的语义安全
     （生成的代码等价于用户手写、无隐藏运行期副作用） → 代价是凡依赖运行期才能确定的信息的特性，根本无法做成纯编译期宏。
  2. **激进程度 ↔ 心智模型偏离**：原型一（补全能力，如 `defineModels`）只省样板、产物仍是标准 Vue 代码，迁移与理解成本接近零；
     原型三（全新 DSL，如 `setupSFC` / `jsxDirective`）则改变了『怎么写组件』本身 → 换来了极致简洁与表达力 → 代价是
     偏离标准 Vue 心智模型、新人看不懂产物、IDE/工具链需额外支持，且与官方演进可能正面冲突（典型如下文 reactivity transform 被废弃）。
  3. **「补全」vs「发明」的官方吸收张力**：原型一/二往往最终被官方上游吸收（`defineModel` 进官方、reactive props destructure 进官方）
     → 这恰好**证明**了它们是『官方迟早会做的缺口』 → 代价是宏作者要接受『被官方收编后自己退场』的生命周期，
     即宏本质是编译器能力的**临时扩张**；而原型三几乎不会被官方吸收，因为它改的是偏好不是缺口。
  4. **语法糖的单向可逆性**：编译期变换是单向的（源码 → 产物），用激进 DSL（如 `setupSFC` 把整个 SFC 变成纯 script）后，
     产物很难反向还原回用户简写 → 换来了写法上的极致简洁 → 代价是调试/报错指向产物而非源码（呼应第 5 章对 sourcemap 的依赖），
     且一旦想脱离该宏就得整段重写。

- **最小心智模型（3～7 步）——『如何判断一个特性属于哪类原型』**：
  1. 拿到一个候选特性（例如 `defineModels`、props 解构、JSX 指令）。
  2. 问判据一：它的产物，是不是一段标准 Vue 本来就能手写出来的等价代码？是 → **原型一·补全能力**。
  3. 问判据二：它是不是在『改写你对已有数据的访问路径』，从而绕开一个纯运行期的约束？是 → **原型二·运行期约定编译期化**。
  4. 问判据三：它是不是引入了一种 Vue 本来根本没有的写法 / 语法通道？是 → **原型三·全新 DSL**。
  5. 三个都否 → 它不该做成宏（该做运行时工具或组合式函数）。
  6. 越靠后的原型，偏离标准心智越大、被官方吸收的可能性越低、维护与迁移成本越高。
  7. 原型之间**不互斥**：同一特性可能横跨两类（如 reactivity transform 兼具二与三，这正是它最终只被部分保留下来的原因）。

- **最小原理演示（替代旧『复刻范围』）**：
  - **应演示**：一个极小的『三类原型确定性还原器』玩具——给定用户简写片段，演示三类原型各自的还原动作差别，每个原型一个十几行的小函数：
    - 原型一（`defineModels` 风格）：把一句 `defineModels<{count:number}>()` 展开（或用最简对象记录其声明意图）成『一个 prop 声明 + 一个 emit 声明 + 一个可读写的 ref』，演透『**纯样板展开，产物完全等价手写**』——可直接对照官方给出的 `defineModel` 展开形态（prop + emit + computed get/set）。
    - 原型二（reactive destructure 风格）：把 `const { count } = props` 之后所有对 `count` 的裸读，重写为 `props.count` 的属性访问，演透『**不改语义、只改访问路径，从而在解构语法下保住响应性**』。
    - 原型三（`defineRender` 风格）：把 `defineRender(() => <jsx/>)` 变成『把 setup 的返回值设为这个 render 函数』，演透『**引入官方 SFC 里本不存在的表达通道**』。
    - 三段共用一个简陋的『输入字符串 / AST 节点 → 输出标准代码字符串』骨架即可，重点在还原方式的**对照**，不在工程精度。
  - **应故意省略**：真实的 Babel AST 解析与遍历、magic-string 的 sourcemap、unplugin 接入、Volar 类型层、Vue 2.7/3 兼容分支、每个宏的完整选项与边界、任何工程脚手架。变换用纯字符串或简单对象操作表达，**只演『确定性还原』这个判据，不演工程**。
  - **演示载体建议**：**首选 TS/JS**（本 Atlas 产物是 JS 生态 VitePress 站点，对读者最友好，且与 Vue Macros 自身语言一致）。无原仓库语言约束。三类原型各一段纯函数足矣。

- **正文不宜展开的细节**：每个宏的完整 API 与选项表、Vue 2.7 vs 3 的兼容与 Volar 支持矩阵；`betterDefine` / `booleanProp` / `hoistStatic` 等『增强型 feature』的内部类型推断机制（依赖编译期可见的类型信息，较深，点到为止）；`namedTemplate` / `shortBind` / `exportRender` / `chainCall` 等冷门特性的逐一变换规则；`jsxDirective` 支持的每条指令（v-if/v-for/v-slot/v-memo）的逐一规则；**特性开关配置**——那是第 13 章『配置系统』的内容；**reactivity transform 被废弃的完整时间线**——第 14 章『根本权衡』会讲，本章只点一句『激进糖有被官方废弃的风险』；**Volar 类型层如何为各类原型生成虚拟代码**——第 9～10 章内容。

- **推荐的一个执行轨迹例子**（演核心思想，三类原型同台）：以一个『同时用了 props 解构、定义了组件 v-model、并用 JSX 渲染』的 SFC 为输入，展示三类原型各自被确定性还原、互不干扰：
  - 输入（用户简写，三类原型共存）：
    ```ts
    const { count = 0 } = defineProps<{ count?: number }>()          // 原型二·约定编译期化
    const models = defineModels<{ open: boolean }>()                 // 原型一·补全能力
    defineRender(() => <div>{count}{models.open.value}</div>)        // 原型三·全新 DSL
