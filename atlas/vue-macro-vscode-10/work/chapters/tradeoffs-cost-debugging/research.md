# 根本权衡：零运行时 vs 可调试性，以及宏的生态演进 · 主题精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：一个用了编译期宏的开发者会接连撞上三面墙——第一面，线上报错的堆栈指向编译后的 bundle 文件，而不是他写的组件源码，定位问题要先在脑里「反编译」；第二面，某条激进语法糖用了一年，官方宣布把它收敛进核心（或直接废弃），他的全量代码要迁移；第三面，调试器里变量名和控制流被改写得面目全非，就算 sourcemap 把行号对上了，逻辑还是看不懂。这三面墙不是 bug，而是「把运行期工作前移到编译期」这条路线**主动换来的代价**。

- **一句话核心思想**：宏是编译器能力的「临时扩张」——它用编译期的变换复杂度，换取运行时的零开销与更声明式的语法，代价是可调试性让位，而且越激进的语法糖，越要随着官方编译器能力的收敛而逐步退场。

- **设计动机（为什么需要它，含跨章去重标注）**：本章是全书末章，职责不是再教一个新机制，而是把散落在前面各章的单点权衡，提升为「一个宏的完整生命周期取舍」——从引入、到与官方编译器博弈、再到收敛或退场的整条弧线。
  - （已在第 7 章『宏的设计原型』讲透：语法糖越激进、与标准 Vue 心智模型偏离越大——本章**不重演**偏离本身，只看偏离的**长期后果**：双心智模型把激进糖逼到被废弃。）
  - （已在第 11 章『双轨制』讲透：双轨实现成本高、任一侧滞后会出现『能跑但红线 / 能提示但报错』的割裂——本章**不重演**双轨同步成本，只看「宏作为一种维护负担在生态层面」的演进张力。）
  - 本章新侧面：把宏放进**时间轴**看——它不是永恒特性，而是官方编译器尚未提供某能力时的「补丁」，注定要随官方收敛而退场。

- **关键权衡（本章核心，4 条）**：
  1. **用编译期 AST 变换换运行时零开销** → 换来无运行时成本、更贴近用户心智的声明式语法 → 代价是断点 / 堆栈 / 报错都指向编译产物而非用户源码，sourcemap 只能部分回溯（行号可还原，变量名与控制流不可还原）。
  2. **让宏承担官方编译器尚未提供的能力（临时扩张）** → 换来在官方能力收敛之前就能用上新语法的先发优势 → 代价是官方一旦收敛（采纳或废弃），宏要么被删、要么被废，用户面临全量迁移成本（reactivity transform 的历史即此判例）。
  3. **用「双心智模型」（标准 JS 语义 + 编译器增强语义）换语法糖的极致简洁** → 换来少写 `.value`、少写样板 → 代价是开发者必须在两套语义间反复切换，认知负担最终大于收益——这正是 reactivity transform 被废弃的核心论据。
  4. **把实验性激进特性放在第三方（Vue Macros）而非官方核心** → 换来官方核心保持精简稳定、实验失败的成本由社区承担 → 代价是特性的成熟度与官方支持力度存在落差，用户需自担「随时可能被废弃」的风险。

- **最小心智模型（6 步）**：
  1. 用户写下声明式语法糖（如响应式变量糖、解构 props）。
  2. 编译期，宏的 visitor 在 AST 上识别糖语法，用就地改写把它变成等价的运行时代码。
  3. 运行时，糖语法已彻底消失，只剩等价的 ref / props 访问——零额外开销。
  4. 出错时，运行时报错与堆栈指向编译产物（改写后的代码），而非用户源码。
  5. sourcemap 把产物行号回映到源码行号——但变量名 / 控制流已被改写，调试逻辑仍需脑内「反编译」。
  6. 当官方编译器演进：要么采纳该糖（进核心）、要么废弃（删特性），宏随之收敛或退场，用户代码迁移——这是「临时扩张」的终局。

- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个极小编译期宏（如 `defineState`：把 `const x = $(ref(0))` + 函数体里的 `x` 改写为 `const x = ref(0)` + `x.value`），几十行 TS/JS 即可。要在一份代码里演透三件事、且每件事对应上面一个原理点：(a) 编译期糖被擦除为运行时代码 → 对应「零运行时开销」；(b) 故意让运行时抛错，展示堆栈第一帧指向改写后产物而非用户源码 → 对应「断点 / 堆栈错位」；(c) 加上 sourcemap 后行号能回映、但变量语义已变 → 对应「sourcemap 部分回溯」。示意骨架：
    ```ts
    // 用户源码（糖）
    const count = $(ref(0))
    function inc() { count++ }            // 用户写的

    // 编译产物（糖被擦除）
    const count = ref(0)
    function inc() { count.value++ }      // 产物：count.value++

    // 运行时若 count 为 undefined，.value++ 抛 TypeError
    // → 堆栈第一帧指产物的 count.value++，而非用户写的 count++
    // → sourcemap 回映行号，但读者仍须把 count.value++ 反编译回 count++
    ```
  - **应故意省略**：完整的宏注册流水线、双轨 volar 类型支持、多宏冲突调度、工程化脚手架、真实打包器接入——这些前面章节已讲，本章只演示「代价」本身，不追求工程完整。
  - **演示载体建议**：**首选 TS/JS**（本 Atlas 产物是 JS 生态 VitePress 站点，TS/JS 对读者最友好）。无需真实打包器，用一个极简的字符串改写函数 + 一段假运行时来抛错即可演透；sourcemap 部分可用注释 + 行号对照演示，不必生成真实 `.map` 文件。

- **正文不宜展开的细节**：reactivity transform 的 `$()` / `$$()` / `$ref()` 完整语法表（只取「被废弃」这一历史事实即可）；各打包器 sourcemap 传递链的具体差异；Sentry 等监控平台回栈的具体配置；Vue 3.3 → 3.4 → 3.5 逐版本 changelog 细节；JSX 指令等具体 DSL 的迁移步骤；核心团队内部决策的完整讨论记录（公开资料只给结论）。

- **推荐的一个执行轨迹例子**：输入 `const count = $(ref(0)); function inc(){ count++ }` → 编译期中间态：宏 visitor 命中 `$()`，就地改写把 `$(ref(0))` 变成 `ref(0)`、把函数体内 `count` 的读写改写为 `count.value` → 输出产物 `const count = ref(0); function inc(){ count.value++ }` → 运行时抛错时堆栈指向产物的 `count.value++` 而非用户写的 `count++`，sourcemap 仅回映行号、变量语义需读者自行反编译 → 退场弧线（叙述层）：若数年后官方在核心原生支持该能力，本宏被删除，用户用 codemod 把糖改回原生写法——这就是「宏作为临时扩张」的完整生命周期。

## 概念要点

- **编译期宏的根本取舍**：用编译期复杂度换运行时零开销与更声明式的语法——这是全书各章单点权衡的总纲。依据: Vue Macros 官网首页定位描述「Extend more macros and syntax sugar · Type-safe」；本 Atlas 第 1 章『编译期宏的本质』已建立的「编译期擦除」原理。
- **可调试性代价（本章主角之一）**：运行时报错 / 堆栈 / 断点指向编译产物而非用户源码；sourcemap 是部分回溯手段（行号可还原，变量名 / 控制流不可还原），其保真度完全取决于编译插件链在每一步变换中是否正确传递 sourcemap 段。依据: Sentry Vue「Troubleshooting Source Maps」官方文档（`source-map-support` 可能覆盖堆栈导致回栈失败）；Nuxt 官方讨论 #23661（产物 `server.mjs` 堆栈而非 `app.vue`）。
- **Reactivity Transform 生命周期（退场判例）**：实验特性 → Vue 3.3 标记 deprecated → Vue 3.4 从核心移除（因属实验性、不承诺稳定，故**无需 major 版本号**即可删除）→ 此后仅经 Vue Macros 提供。依据: Vue 3.4 官方博客「Announcing Vue 3.4」；vuejs/rfcs 讨论 #369（Dropped）；`@vue/reactivity-transform` npm 包页。
- **被废弃的核心论据（双心智模型）**：解构响应式对象易丢失响应性；引入「双心智模型」——开发者须同时持有标准 JS 语义与编译器增强语义两套理解，认知负担大于收益。依据: Vue 官方文档「Reactivity Transform」页（「It's easy to lose reactivity when destructuring reactive objects」）；vuejs/rfcs #502（「compiler-magic-powered reactive binding」需用户理解编译器内部）。
- **Reactive Props Destructure（收敛判例）**：原为 Reactivity Transform 的一个子能力，被**拆出**独立成 RFC #502，并在 Vue 3.5 进入核心稳定——即「有价值的糖被收敛进核心、其余被废弃」的样本。依据: vuejs/rfcs 讨论 #502；Vue 3.5 发布说明。
- **Vue Macros 的生态定位**：官方核心的实验性 staging ground——激进特性先在 Vue Macros 试水，成熟的（如 reactive props destructure）被收敛进核心，有争议的（如 reactivity transform）被废弃后仍由 Vue Macros 承载。依据: Vue 官方文档「Reactivity Transform」页（被移除后 "now only available via the Vue Macros plugin"）；vue-macros.dev 官网定位。

## 关键流程

宏的完整生命周期弧线：

`用户采用激进糖（先发收益）→ 编译期擦除为运行时代码（零开销）→ 出错时堆栈错位（可调试性代价，sourcemap 部分缓解）→ 官方编译器演进博弈（采纳 / 废弃）→ 宏收敛进核心或被废弃 → 用户代码迁移（长期成本）`

依据: 综合 Vue 3.4 / 3.5 官方博客与 Vue 官方文档「Reactivity Transform」页的演进叙述；reactivity transform（废弃）与 reactive props destructure（收敛）构成这条弧线的两个真实端点。

## 易混淆 / 边界 / 推断

- **事实**：「实验性」标签是 reactivity transform 能在非 major 版本被删除的法理依据——它从未承诺稳定 API。依据: Vue 3.4 官方博客（「does not require a major due to the feature being experimental」）。
- **事实**：sourcemap 的保真度取决于编译插件链每一步是否正确传递 sourcemap 段——任一环节丢失，下游全部错位；这是宏可调试性的硬约束。依据: Sentry Vue sourcemap 官方文档；本 Atlas 第 5 章『magic-string：sourcemap 友好的源码就地变换』已建立的原理。
- **推断（标注为推断）**：宏与官方编译器的「张力」，本质是同一能力的两个实现源头——宏是编译器的超集扩张，官方是子集收敛，二者语义必须对齐，否则复现第 11 章所述割裂；reactivity transform 的废弃可视为官方选择「不再向该方向扩张」的判例。依据: 由 reactivity transform 废弃事件 + 第 11 章双轨对齐原理归纳，属推断。
- **推断（标注为推断）**：把激进特性放第三方而非核心，是「保持核心精简稳定 vs 满足新语法渴望」的组织级权衡——核心团队借此把实验失败的代价外部化给社区（特性被废弃时，维护负担由 Vue Macros 而非核心承担）。依据: 由 Vue Macros 作为 staging ground 的定位 + reactivity transform 下放至 Vue Macros 的事实归纳，属推断性解读。
- **未理解 / 待查证**：reactivity transform 当初被引入核心实验、后又废弃的完整决策时间线（哪些核心成员的论据最终主导、是否有内部投票）——公开资料只给结论与官方理由，未公开完整讨论记录，Writer 不宜虚构细节。
