# 根本权衡：零运行时 vs 可调试性，以及宏的生态演进

> 本章属于 system 层。前置：双轨制（编译变换与 IDE 类型支持为何并存）、宏的设计原型（把什么前移到编译期）。
> 学完你能：用一句话讲清宏是编译器能力的「临时扩张」，为什么注定要随官方演进而退场，以及它替用户欠下了什么账。

## 1. 为什么需要它（设计动机）

上一章把视角放在配置系统：一份配置同时驱动编译变换和 IDE 两条管线，看似把宏这件麻烦事打理得井井有条。但配置系统只回答了「两条管线如何同步」，没回答一个更长远的问题——当宏这种「临时扩张」被官方能力收敛或废弃时，用户和生态要付出什么账？本章就接着这个口子讲。

一个用了编译期宏的开发者，迟早会接连撞上三面墙。

第一面墙是出错的时候。他在浏览器里看到一行红色报错，堆栈顶端是 bundle 里某行 `count.value++`，可他写的代码里压根没有 `count.value`，他写的是 `count++`。要复现 bug，他得先把变换器在脑子里重跑一遍。

第二面墙是某天早上看到官方博客。某个他用了两年的语法糖被宣布废弃，下个版本就删。他的整个代码库要做迁移，而迁移工具不一定覆盖所有边角。

第三面墙是断点和变量观察。就算 sourcemap 把行号对上了，调试器里跳动的变量名和控制流已经被改写得面目全非——他盯着某个内部字段，怎么也想不起它对应自己源码里的什么。

这三面墙不是 bug，而是「把运行期工作前移到编译期」这条路线主动换来的代价。本章作为全书末章，职责不是再教一个新机制——前面 13 章把机制都讲完了——而是把这些散落的单点代价，提升为「一个宏的完整生命周期取舍」：从引入、到与官方编译器博弈、再到收敛或退场的整条弧线。

## 2. 核心思想

宏是编译器能力的**临时扩张**：它替官方编译器暂时背上一些官方还没采纳（或不愿采纳）的语法糖，用编译期的变换复杂度换运行时的零开销和更贴近心智的声明式语法。但既然是「扩张」，它就要么被官方收敛（采纳进核心）、要么被废弃（特性退场），代价是可调试性让位与长期迁移成本。

换句话说，宏不是永恒特性，而是有生命周期的补丁。

## 3. 心智模型：一条生命周期弧线

把宏放进时间轴，它不是一段静态代码，而是一条六步弧线：

1. **用户采用糖**：在源码里写下声明式语法（如 `const count = $(ref(0))`、`const { foo } = defineProps()`）。
2. **编译期擦除**：宏的 visitor 在 AST 上命中糖语法，用就地改写把它替换为等价的运行时代码（`count.value` 访问、底层 `props.foo` 访问）。
3. **运行时零开销**：糖语法彻底消失，运行时只有 ref / 原生 props 访问，没有任何「宏运行时」参与。
4. **出错时堆栈错位**：异常抛出时，第一帧指向产物而非源码——用户得在脑子里反编译。
5. **sourcemap 部分回溯**：sourcemap 把产物行号回映到源码行号，但变量名与控制流已被改写，调试逻辑仍需脑内"反编译"。
6. **官方演进博弈**：几年后官方编译器演进，要么把糖采纳进核心（如 Reactive Props Destructure 在 Vue 3.5 进入稳定），要么废弃掉（如 Reactivity Transform 在 Vue 3.4 被移除）。宏随之收敛或退场，用户代码迁移。

这条弧线的两个端点——采纳和废弃——构成了本章真正要回答的问题：宏的「代价」不是单点的可调试性损失，而是**整条生命周期的维护承诺**。

## 4. 关键权衡

### 4.1 编译期变换换零运行时开销，代价是断点 / 堆栈 / 报错全部错位

宏做了选择：把工作前移到编译期。换来的是运行时绝对干净，没有任何「宏运行时」参与执行，糖语法被擦除为等价的原生写法。

代价是：当产物抛错时，堆栈第一帧指向的是变换后的代码，不是用户写的那一行。sourcemap 只能部分缓解——行号可以回映，但变量名和控制流已经被改写。`count.value++` 可以映射回 `count++` 所在的行，但读者依然要在脑子里把 `.value++` 翻译回 `++`，否则读不懂这段逻辑在做什么。

**本质矛盾**：运行时性能与可调试性，是同一执行链路的两端。编译期变换把「理解代码」的工作从运行时（开销可见）转移到了维护时（认知开销不可见）——前者账单由所有用户平摊，后者账单只压在出问题的那个人头上。

### 4.2 替官方背锅换先发优势，代价是随时被收敛或废弃

宏做了选择：让第三方（Vue Macros）承担官方编译器还没提供的能力。换来的是先发优势——官方能力收敛之前，用户就能用上新语法。

代价是：官方一旦做出选择（采纳或废弃），宏要么被删（特性进核心），要么被废（特性被官方否定）。无论哪条路，用户都面临全量代码迁移。Reactivity Transform 的历史就是这条判例——它从 Vue 3.3 起标记为 deprecated，Vue 3.4 直接从核心移除，因为「实验性」标签从未承诺稳定 API，所以**不需要 major 版本号**就能删；之后该能力完全下放给 Vue Macros 维护，原有用户要么迁移回 `.value`，要么继续依赖第三方插件。

**本质矛盾**：先发优势与稳定性承诺，是没法同时拿满的两个方向。先发意味着搭上一段未定型的轨道，稳定性意味着只能跟在已被采纳的能力后面走。

### 4.3 双心智模型换极致简洁，代价是认知负担终将反噬收益

宏做了选择：在标准 JS 语义之上叠加编译器增强语义，让用户少写 `.value`、少写样板。换来的是源码极致贴近心智模型——`count++` 比 `count.value++` 更像普通变量。

代价是：开发者必须在两套语义之间反复切换。一段代码看起来像普通 JS（`count++`），但它的真实行为是 `count.value++`，遇到响应性丢失的 bug 时，开发者必须先想起「这段被宏改写过」，再回退到编译器增强语义去理解。Reactivity Transform 被废弃的核心论据就是这条：双心智模型的认知负担最终超过了少写 `.value` 的收益。Reactive Props Destructure 反过来——它从 Reactivity Transform 里被拆出来独立成 RFC，在 Vue 3.5 进入核心稳定——证明了「有价值的糖」会被收敛，「引起认知负担的糖」会被废弃。

**本质矛盾**：语法糖的简洁度与心智模型的单一性，是反相关。糖越多，单看代码越舒服；但理解运行行为时，需要记住的「例外」也越多。这一条不是「机制越激进越偏离 Vue 心智模型」的复述（第 7 章讲过的取舍），而是它的长期后果——偏离本身不是问题，问题是偏离会随时间累积成被废弃的理由。

### 4.4 把激进特性放第三方而非核心，代价是把废弃风险外部化给社区

宏做了选择：把实验性激进特性放在 Vue Macros（第三方）而不是 Vue 核心。换来的是官方核心保持精简稳定，实验失败的成本由社区承担——特性被废弃时，维护负担由 Vue Macros 团队而非核心团队扛。

代价是：特性的成熟度与官方支持力度存在落差。用户用 Vue Macros 时享受了官方生态的可靠性预期，但实际上某些特性（如 Reactivity Transform）已经被核心团队判废，用户自担「随时可能被废弃」的风险。这是组织层面的权衡：核心团队通过把激进特性外部化，换取核心的迭代速度与稳定性。

**本质矛盾**：核心的精简性与生态的丰富度，没法同时拿满。把激进特性收进核心，核心就被实验失败拖累；推到第三方，用户就要自己判断哪些糖长期可靠、哪些糖已经走在被废弃的路上。

## 5. 最小原理演示

下面这段最小实现演透三件事：编译期糖被擦除（对应 4.1 的零运行时开销）、抛错时堆栈指向产物而非源码（对应 4.1 的堆栈错位）、sourcemap 行号可回映但变量语义已变（对应 4.1 的部分回溯）。

```ts
// 用户源码（糖）：他希望 count 像普通变量
const userSource = `
const count = $(ref(0))
function inc() {
  count++
}
inc()
`
// 上面 $(ref(0)) 是糖：编译期擦除为 const count = ref(0)
// 上面 count++ 是糖：编译期改写为 count.value++

// 极简编译期变换器：识别 $(REF) 与 IDENT++，用 offset 改写
// （真实 Vue Macros 走 AST，这里用字符串正则只为示意原理）
function compileSugar(src: string): { code: string; map: SourceRange[] } {
  const map: SourceRange[] = []
  const out = src
    .replace(/\$\(ref\((\w+)\)\)/g, (_, v) => `ref(${v})`)
    .replace(/(\w+)\+\+/g, (_, name) => `${name}.value++`)
  // 记下行号映射（演示用：产物第 N 行对应源码第 N 行）
  out.split("\n").forEach((_, i) => map.push({ genLine: i, srcLine: i }))
  return { code: out, map }
}

// 编译产物：糖被擦除
const compiled = compileSugar(userSource)
// 等价于：
//   const count = ref(0)
//   function inc() { count.value++ }
//   inc()

// 运行时（演示抛错：故意让 count 为 undefined）
function runtime() {
  const count = undefined as any
  count.value++   // ← TypeError: Cannot read properties of undefined (reading 'value')
}
try {
  runtime()
} catch (e: any) {
  console.log(e.stack)
  // 堆栈第一帧指 runtime() 里的 count.value++
  // 不是用户写的 count++，用户得在脑里反编译回去
}

// sourcemap 行号回映（演示：行号对得上，但变量语义对不上）
function mapLine(genLine: number, map: SourceRange[]) {
  return map.find((m) => m.genLine === genLine)?.srcLine
}
// 产物第 3 行（count.value++）回映到源码第 3 行（count++）
// 行号对得上，但读者仍需把 .value++ 翻译回 ++

type SourceRange = { genLine: number; srcLine: number }
```

不到 40 行代码，演透了本章核心：糖在编译期被擦除（产物里只剩 ref 与 `.value`），抛错时堆栈指向产物（用户得反向翻译），sourcemap 只能解决「哪一行」而不能解决「这一行在做什么」。

## 6. 执行轨迹

把上面那段演示代码沿弧线走一遍：

1. **输入**：用户源码 `const count = $(ref(0)); function inc() { count++ }; inc()`。
2. **编译期中间态**：变换器命中 `$(ref(0))`，把它改写为 `ref(0)`；命中 `count++`，把它改写为 `count.value++`。sourcemap 记下「产物第 N 行 ↔ 源码第 N 行」。
3. **输出产物**：`const count = ref(0); function inc() { count.value++ }; inc()`——糖被擦除，运行时只有原生 ref 访问。
4. **运行时抛错**：当 count 为 undefined 时，`count.value++` 抛 TypeError，堆栈第一帧指向产物第 3 行的 `count.value++`。
5. **sourcemap 回映**：用户拿到产物第 3 行，通过 map 查到源码第 3 行。**行号对得上，变量语义需自行翻译**——他得把 `count.value++` 在脑里翻回 `count++`，才能想起自己当时写的是什么。
6. **退场弧线**（叙述层）：假设两年后 Vue 核心原生支持了 `$()` 语法，本宏被官方能力替代，从 Vue Macros 删除，用户用 codemod 把 `$ref()` 改回 `ref()` + `.value`；又或者像 Reactivity Transform 那样被废弃，用户迁移到原生 `.value` 写法。无论哪条路，这条糖都走完了「临时扩张」的完整生命周期。

## 7. 教学简化说明

本章演示故意省略了：完整的宏注册流水线（第 6 章已讲）、AST 遍历而非字符串替换（第 4 章已讲）、magic-string 的 sourcemap 生成（第 5 章已讲）、双轨 volar 类型支持（第 11 章已讲）、真实打包器接入（第 8 章已讲）。这里只用字符串正则做一个最小变换器，目的是演透「代价」本身——糖擦除、堆栈错位、sourcemap 部分回溯——这三件事，而不是复刻一个能跑的工程。

## 8. 小结

宏是编译器能力的临时扩张，这句话同时定义了它的价值与终点。它在官方编译器尚未提供某能力时撑起一段过渡，用编译期的复杂度换运行时的干净与语法的贴近心智；它的代价不是单点的可调试性损失，而是整条生命周期的维护承诺——堆栈错位、双心智模型、与官方演进的长期博弈。当官方能力收敛，糖要么进核心、要么被废弃，宏就该退场。这本 atlas 走到这里，把「宏是什么」讲完之后，最后一条原理是：宏有它该退场的时刻。
