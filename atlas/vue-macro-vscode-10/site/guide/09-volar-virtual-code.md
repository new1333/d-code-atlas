# Volar 的虚拟代码生成与位置回映

> 本章属于 composite 层。前置：<script setup> 与内置宏的设计动机。
> 学完你能用一句话讲清：为什么 Volar 不重写一个「懂 Vue 的 TS 服务」，而是用「虚拟代码 + 双向位置映射」这一间接层让现成语言服务读懂 `.vue`；以及这个间接层付出了什么代价。

## 1. 为什么需要它（设计动机）

上一章把构建期的代码变换做到了跨打包器复用——unplugin 一次编写，Vite/webpack/Rollup 都能跑。但那是用户主动跑 build 时才发生的事；IDE 工作在另一个时间维度上：用户敲下 `<script setup>` 那一刻，编辑器就要给出补全、类型报错、跳转定义，根本没有「先 build 一次」的余地。

而 `.vue` 文件是 IDE 眼里的怪物。它把三种语言塞进一个文件——`<script>` 是 TypeScript，`<template>` 是 HTML 再嵌 inline TS，`<style>` 是 CSS。现成的语言服务（tsserver、cssls、htmls）都强假设「一个文件 = 一种语言」，tsserver 压根不会去读 `.vue`，更不会理解里面哪段归它管。

> 第 2 章『<script setup> 与内置宏』讲过：宏是**编译期去糖**——把声明式语法编译成等价的 setup() 返回值。那是构建期的事。本章退一层看一个更底层的地基问题：**IDE 在用户根本还没构建、甚至根本没装构建工具时**就要理解 SFC（连同里面的宏）。第 2 章是「编译器替运行时去糖」，本章是「Volar 替类型检查器去糖」——同一原理在两个不同时间维度的两侧。本章只聚焦虚拟代码 + 位置映射这个底层机制本身，宏的具体去糖不重演。

如果没有中间层，要让 IDE 懂 `.vue` 只剩两条路：要么自己重写一个「懂 Vue 的 TS 服务」（从类型系统到控制流分析全部重造），要么放弃类型智能。两条都不现实。

## 2. 核心思想

把一个多语言混合的源文件**翻译**成一棵由若干「单语言虚拟文件」组成的树，让现成的语言服务各自只读自己那一份虚拟文件；再用一张**位置映射表**，把诊断、补全、跳转的坐标在虚拟坐标系与源坐标系之间双向翻译。

说人话就是：tsserver 永远以为自己读的是个 `.ts`，它不知道这个 `.ts` 是 Volar 现场从 `.vue` 翻出来的，它只对自己看到的字符负责；Volar 在背后做翻译，让用户在 `.vue` 里看到的报错和补全都落在正确的字上。

## 3. 心智模型

最小数据结构：

- **VirtualCode**：一个虚拟文件，持五样东西——`id`（标识，如 root/script/template）、`languageId`（伪装成哪种语言）、`snapshot`（虚拟文件的文本内容）、`mappings`（到父代码的位置映射）、`embeddedCodes`（嵌套的子虚拟代码）。
- **Mapping**：一段「源 offset 数组 ↔ 虚拟 offset 数组 + 每段长度」的对照记录，外加一个 `data` 字段标元数据（这段是否真正可映射、属于哪个 embedded 语言）。
- **LanguagePlugin**：翻译规则的接口——`createVirtualCode`（首次创建）、`updateVirtualCode`（增量更新）、`dispose`（销毁）。

虚拟代码是**树状**的：根虚拟代码代表整个源文件，下面挂着 script/template/style 各自的子虚拟代码；template 这种子虚拟代码内部还可再嵌（模板插值里的 inline-ts 是叶子）。每一层有自己独立的 mappings，是「子 ↔ 父」的局部关系，跨层级位置回映要逐层累加。
