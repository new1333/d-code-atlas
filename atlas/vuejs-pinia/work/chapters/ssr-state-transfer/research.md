# 服务端渲染的状态传递 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：服务端渲染时，组件已经在服务器上把状态算好了（登录态、购物车、首屏数据）。到了浏览器端，如果让组件把这些数据重新请求、重新算一遍，既慢又会闪一下"未登录→已登录"的跳变。使用者真正想要的是：服务器算出的那棵状态树原封不动地"传"到浏览器接着用——但又不能无差别全传（浏览器端要新建的路由实例、第三方有状态对象不该被服务端旧值覆盖，也不该塞进 HTML 白白增大体积）。

- **一句话核心思想**：把整棵集中状态树塞进框架自带的传输载荷里随网页一起下发，客户端再整棵倒回去；不愿下发的字段提前打一个隐式标记，序列化时自动摘掉。

- **设计动机（为什么需要它）**：要解决的矛盾是"服务端与客户端是两个独立运行时，状态不会自动跨过去"。它复用了两个前置设计：状态之所以能"整棵端走"，是因为容器早就把所有仓库的状态聚成了一棵集中树（已在第 2 章『Pinia 容器与集中式状态树』讲透状态为何能聚成单棵可整树序列化的树，本章只看这棵树如何被打包跨网络往返）；而之所以能定位"当前这份状态属于哪个请求"，靠的是那个全局活跃指针（已在第 3 章『活跃实例指针』讲透全局变量的跨请求污染风险，本章只看它在渲染结束后被主动置空这一兑现动作）。换来的能力是零自建传输通道——直接借宿主框架已有的"载荷随 HTML 下发"管道搭车。

- **关键权衡（选择→换来→代价）**：
  1. **借宿主的载荷管道搭车** → 换来完全不必自建一套服务端→客户端的传输通道（不必自己写 script 标签、不必管编码与解析）→ 代价是与宿主的序列化协议强耦合：要按宿主"类型化序列化"的扩展点成对注册降级/还原函数，换框架时这部分要重写。
  2. **整棵状态树一次性端走** → 换来序列化与回填都只需一行（写载荷=读那棵树；回填=把载荷赋回那棵树），不必逐仓库、逐字段搬运 → 代价是必须有第二道细粒度逃逸口，否则要么把不该跨端的庞大有状态对象也序列化出去造成体积膨胀与水合冲突，要么无差别水合导致客户端新建对象被服务端旧值覆盖。
  3. **用一个隐式标记声明"这字段别传"，标记在序列化与装配两道关各设一次** → 换来使用者只需把对象包一下就完成声明、标记跟着对象走不污染数据形状 → 代价是标记是运行时隐式的（控制台看不见），且必须在序列化时用它把对象降级成哨兵、在仓库装配时再用它决定是否灌入服务端值，两道关缺一不可。
  4. **渲染一结束就主动把全局活跃指针置空** → 换来服务端并发处理多请求时，那个被所有请求共享的模块级全局变量不会把 A 请求的状态漏给 B 请求 → 代价是必须卡准"渲染完成、载荷已收尾"这个钩子时机去清空，漏一次就跨请求串状态（这是第 3 章欠下的债，本章兑现）。

- **最小心智模型（3～7 步）**：
  1. 构建期，集成模块注册两个运行时插件：一个负责"建容器 + 跨端搬运状态"，一个负责"序列化时摘掉免水合字段"。
  2. 服务端启动，第一个插件建好容器、装进应用、把全局活跃指针指向它。
  3. 服务端渲染期间，各仓库正常读写，状态全落在那棵集中树上。
  4. 渲染完成钩子触发：把整棵集中树写进传输载荷；紧接着把全局活跃指针置空，断开对这份状态的引用。
  5. 载荷随 HTML 下发（其中打了免水合标记的字段已在序列化时降级成哨兵，真实数据并未传输）。
  6. 客户端启动，同一个插件再跑一遍：发现载荷里已有状态树，就整棵赋回新建容器的集中树。
  7. 客户端装配各仓库时逐字段查免水合标记：没标记的灌入服务端值（跨端一致），有标记的保留客户端自己新建的对象。

- **最小原理演示**：
  - 应演示：一个"集中状态树"对象（普通对象包一层 ref）；一个模拟"载荷"的中间载体；一个打标记函数（往对象上埋一个不可见标记，如 Symbol）+ 一个判定函数（查这个标记）；一对"降级/还原"函数（序列化时把带标记对象换成哨兵、反序列化时还原成空）；一个"装配仓库时逐字段过滤"的函数。演的核心思想是"整树端走 + 标记摘字段 + 双端配合"。演第 3 条权衡时，故意让某字段被打标，观察它在载荷里变成哨兵、客户端被还原成空、装配时被跳过。
  - 应故意省略：宿主框架真实的载荷线路格式、HTML 注入与解析、集成模块的自动导入与目录扫描、构建期转译、类型声明生成、多请求并发的真实调度——这些都不参与"演透原理"。
  - **演示载体建议：首选 TS/JS**。本章核心是"序列化协议（降级/还原）+ 隐式标记位 + 整树搬运"，全是纯数据变换与控制流，无任何 Vue/Nuxt 特有运行时语义（不依赖响应式系统、不依赖组件树），几十行 TS/JS 配最小 package.json 即可 `node` 跑通，对读者最友好。无需退回原仓库语言。

- **正文不宜展开的细节**：宿主"类型化载荷"的具体线路格式（降级函数为何要返回 truthy 才算匹配）；为何读状态前要先剥一层代理（容器自身被冻结为原始对象，但经宿主注入后可能被代理包裹）；插件为何要排在路由插件之前（排序不当会导致状态尚未就绪，对应上游 issue #9130）；构建期集成模块的自动导入、目录扫描、转译与类型声明生成；开发模式额外的热更新插件注册。

- **推荐的一个执行轨迹例子**：
  - 输入（服务端）：某仓库状态 = `{ 访问次数: 5, 路由器: 打标(路由实例) }`。
  - 服务端渲染完成：载荷 = `{ 访问次数: 5, 路由器: <带标记的路由实例> }`；随即全局指针置空。
  - 序列化降级：载荷改写为 `{ 访问次数: 5, 路由器: 哨兵 }`（路由实例真实数据未进入传输）。
  - 客户端反序列化还原：载荷变回 `{ 访问次数: 5, 路由器: 空 }`。
  - 客户端装配仓库：访问次数无标记 → 灌入 5；路由器有标记 → 跳过，保留客户端新建的路由实例。
  - 输出：访问次数跨端一致为 5，路由器两端各自独立、互不串扰。

## 概念要点
- 集成模块在 `modules:done` 钩子里注册两个运行时插件（先状态搬运插件、后载荷摘字段插件），注释引用上游 issue #9130 说明插件排序的必要性。源码位置: packages/nuxt/src/module.ts:57-62
- 集成模块同时把 defineStore / acceptHMRUpdate / storeToRefs / usePinia 注册为自动导入，并按 storesDirs 扫描仓库目录纳入自动导入，免去手写 import。源码位置: packages/nuxt/src/module.ts:64-86
- 运行时插件 setup 阶段：新建容器 → 装进 Vue 应用 → 把全局活跃指针指向它；服务端与客户端都会执行这段。源码位置: packages/nuxt/src/runtime/plugin.ts:9-11
- 客户端水合：若载荷中已有状态，直接整棵赋值给集中状态树——这是"整树端走"的回填侧。源码位置: packages/nuxt/src/runtime/plugin.ts:13-15
- 服务端序列化：在渲染完成钩子里把整棵集中状态树写入载荷，随后把全局活跃指针置空，注释明确"避免在服务器上持有该变量"。源码位置: packages/nuxt/src/runtime/plugin.ts:25-30
- 免水合标记是一个（开发期带描述的）Symbol；打标记=给对象定义该 Symbol 属性，判定=查该 Symbol 是否存在。源码位置: packages/pinia/src/store.ts:115-140
- 序列化侧（降级函数）：宿主遍历载荷时对每个对象调判定函数，若不该水合则返回 truthy 值（1）使其被识别为该自定义类型，从而真实对象不进入传输。源码位置: packages/nuxt/src/runtime/payload-plugin.ts:14-18
- 反序列化侧（还原函数）：客户端遇到该自定义类型时无条件还原成 undefined，使该字段在客户端为空，让仓库装配时走客户端默认值。源码位置: packages/nuxt/src/runtime/payload-plugin.ts:19
- 仓库装配（Setup Store）时逐字段判定是否水合：仅当字段未被标记才把服务端初值灌入用户创建的 ref/reactive，否则保留客户端对象——这是免水合标记的第二道关卡（第一道在序列化）。源码位置: packages/pinia/src/store.ts:514-533

## 关键调用链
服务端：
集成模块注册插件 → 状态插件.setup() 建容器 + 设活跃指针 → 组件渲染（各仓库写集中状态树）→ 渲染完成钩子 → 写载荷 + 清空活跃指针 → 宿主序列化载荷（经摘字段插件的降级函数剔除免水合字段）→ HTML 下发

客户端：
HTML 解析 → 宿主反序列化载荷（经摘字段插件的还原函数把哨兵还原成空）→ 状态插件.setup() 建容器 + 读载荷整树回填 → useStore 装配时逐字段判定过滤 → 仓库就绪

源码位置: packages/nuxt/src/module.ts:59-62; packages/nuxt/src/runtime/plugin.ts:8-31; packages/nuxt/src/runtime/payload-plugin.ts:13-20; packages/pinia/src/store.ts:516

## 易混淆 / 边界 / 推断
- 事实：整树赋值是设置初值的源头、逐字段判定是装配时的细粒度关卡，两层互补。整树赋值仅对 Options Store 直接生效（它装配时直接从集中树读自己的分支）；Setup Store 装配时则走逐字段判定路径，把初值灌进用户自建的 ref/reactive。源码位置: packages/nuxt/src/runtime/plugin.ts:14; packages/pinia/src/store.ts:514-533
- 事实：降级函数返回 `1` 而非 `true`——宿主的类型化序列化协议要求返回 truthy 才视为"匹配该类型"，返回 falsy 则跳过本函数继续尝试其他类型；源码注释 "We need to return something truthy to be treated as a match" 直接佐证。源码位置: packages/nuxt/src/runtime/payload-plugin.ts:16-17
- 事实：写载荷前用 toRaw 剥代理，因容器自身被 markRaw，但经宿主 provide 注入后 `$pinia` 可能被代理包裹，toRaw 确保读到真实容器的状态字段。源码位置: packages/nuxt/src/runtime/plugin.ts:27
- 推断：渲染完成钩子在"服务端渲染完成、载荷即将被序列化进 HTML 之前"触发——从命名与用途（写载荷 + 清指针）推断，未读宿主源码确认精确时机。
- 推断：宿主的"类型化载荷"是一种按类型标签序列化的协议（降级函数打标签、还原函数按标签还原）；具体线路格式未读宿主源码，仅从成对注册的用法推断。
- 未理解：客户端首次装配时，若某字段在服务端被免水合、客户端还原成 undefined，而用户在 setup 内对该字段又有默认初值——最终客户端该字段是"用户默认值"还是"空"——初步判断应为用户默认值胜出（因用户在客户端新建的对象同样不带标记，装配走保留分支），但未跑实测验证，Writer 撰写此细节前建议补实测。
