# 测试替身：借插件实现 Mock

> 本章属于 system 层。前置：插件扩展总线。
> 学完你能：用一句话讲清"为什么 `@pinia/testing` 能用一个独立 npm 包完成 mock，而核心不用开任何测试后门"。

## 1. 为什么需要它

上一章讲的是服务端渲染：状态在服务端拍好照、序列化进 payload，再在客户端水合回来。那是 Pinia 跑在生产环境里要过的最后一道关。本书走到最后一章，换一个完全不同的场景——不在生产，而在测试：怎么反过来把状态管"死"，让一个组件从整棵应用里干净地切出来单测。

想象你在单测一个购物车组件。组件一挂载就调 `cart.addItem()`，而这个动作会真的去发请求、写状态、触发一连串订阅。你的测试本来只想验证"点击加购按钮后角标 +1"，结果却被拖进整条后端链路里：请求要 mock、订阅的副作用要清理、网络时序要等。测试又慢又脆，被测的对象反而淹没在噪音里。

你真正想要的是把动作变成"哑炮"——它不发请求、不改状态，但你能断言"它被调过、参数是什么"；初始状态能预设成某个固定值；计算属性能钉死成定值。换句话说，把组件或单个 store 从整棵应用里隔离出来测。

矛盾在于怎么做到。最直白的办法是给 Pinia 核心开一个测试分支，比如 `if (isTest) skipAction()`。可那意味着核心要背上一个跟生产无关的负担，testing 包也没法独立成包发布。能不能在不碰核心、不开后门的前提下，劫持每一个 store？

## 2. 核心思想

把 mock 实现成一个普通的 pinia 插件，确切说，一个排在插件链最末尾的插件。

前置章已经把"插件扩展总线"建好了：每个 store 组装完，总线会按注册顺序逐个调用插件，插件的返回值合并进 store。这条总线本来是给 devtools、持久化这类扩展用的。testing 包要做的事，就是往这条总线的最末尾再插一个插件，让它拥有最终决定权——前面所有人装上的动作，它都能换掉。

插件链像一条流水线，store 是被加工的工件，从第一个插件传到最后一个。最后一个插件下笔的地方盖在所有人上面：它能把前面任何插件装上去的动作整个换成哑炮。整章围绕的就是这一句——不开后门，借总线。

## 3. 心智模型

容器内部维护着一个插件数组 `_p`。组装一个 store 时，`setup` 先跑（这一步把状态和动作挂到 store 上），随后总线遍历 `_p`、按顺序逐个调用插件，插件的返回值会合并进 store。谁后跑，谁就能改掉先跑的人留下的东西。

`createTestingPinia` 拿一个普通容器，按固定顺序往 `_p` 里追加四个插件：

1. **初始状态注入**——按 store 的 id 从测试预设的 `initialState` 取初态，盖到 store 自带的初态上。
2. **用户的业务插件**——测试方传入的应用插件，照常生效。
3. **计算属性可覆写**——让计算属性能被手动钉死成定值。
4. **动作替身**——把动作换成（或包成）spy。

替身排在第四位、最后一个被追加。因为总线按追加顺序执行，它也就最后生效，能覆盖前面三个插件装上去的一切。

要说"替身稳稳排末尾"，得圈定一下范围。在 testing 能直接 push 进 `_p` 的这四个插件里，替身确实是最后一个。但有一条漏网之鱼：`createPinia` 自己会注册一个 devtools 插件，而这个插件比较特殊——容器还没装进应用之前，它先被搁在一个等候区（`toBeInstalled`）里；等到 `app.use(pinia)` 真正触发安装的那一刻，它才被搬进 `_p`。这一刻晚于 testing 直接追加替身的时刻，所以 devtools 反而排在替身后面。换句话说，testing 直接控制不了、却能越过替身的，就只有这个容器自带的可观测性插件。

这本来会是个麻烦：devtools 为了做时间线分组，会把每个动作再包一层代理，正好盖掉 testing 装的替身。所以 testing 还得额外在容器上设一个 `_testing = true` 标志，让 devtools 看到就主动收手。这条让位协议是下一节要讲的第二条权衡。

替身插件拿到 store 之后，对每个动作做一个判断：要不要替死。要替死，就调 `createSpy()`（不传原函数）造一个空 spy 盖上去，动作变成哑炮；不替死，就调 `createSpy(store[action])`（把原函数传进去）造一个包裹，原逻辑照跑，只是外面包了一层可断言的壳。同一个造 spy 的工厂，参数传不传，就区分了"替换"和"包裹"两种测试策略。默认全部替死，也就是动作一律哑炮；`$patch` 和 `$reset` 默认不替死，只包一层用于观察。

## 4. 关键权衡

### 复用总线、不碰核心，换来 mock 随组装自动生效

testing 选择完全不碰核心、不开任何测试分支，把自己实现成一个排在链尾的普通插件。

这一选择换来的好处很实在。mock 随 store 组装自动生效：被测代码里只要照常调 `useStore()`，store 一组装、替身就自动就位，测试不用手动给每个 store 打补丁。mock 和业务插件天然共存：大家都是插件，挂在同一条总线上，彼此不需要知道对方存在。testing 因此能独立打包发布，核心一行代码都不用为它改。

代价是，mock 的生死完全系于插件顺序。替身插件必须排在 `_p` 的最末尾。一旦它先于某个业务插件注册，那个业务插件的返回值就会在替身之后把真动作装回去，盖掉替身，mock 当场失效。源码里那句注释说得很直白：绕过"等应用安装"这一步，就是为了确保动作替身发生在最后。这条代价不是偶发的边界情况，而是这套设计的结构性前提——testing 把自己绑在了"我必须是最后一个"这个约定上。

这条权衡化解的本质矛盾是：**测试要隔离（动作得变哑炮）vs 复用核心装配管线（动作由总线统一装上、谁都能改）**。testing 不另起炉灶造一套测试专用 store，而是挤进已有的装配管线、抢到最后一个位置。读者抓住这个本质，就能在别的框架里认出同一类问题：只要一个系统提供了"按顺序执行的扩展链"，把测试替身排到链尾都是通解；反过来，只要你在扩展链里发现了顺序敏感的 bug，先怀疑的就是谁抢了谁的位置。

### 一道跨包的"正在测试"暗号，换来 mock 与开发者工具共存

testing 在容器上设 `pinia._testing = true`；devtools 在给动作做时间线分组之前先看这个标志，为真就跳过分组逻辑。

这道暗号换来的是两个都想改 store 动作的插件能共存：testing 把动作换成哑炮，devtools 不会再用自己的代理把它冲掉。

代价是两个独立的包之间多了一条隐式协议。devtools 必须知道 testing 会设这个标志、并主动尊重它；任何一方不认账——比如某个旧版 devtools 不认这个标志——替身就会被冲掉、或者 devtools 的时间线分组就缺了一块。这种跨包耦合不像类型契约那样有编译器兜底，只能靠注释里引用的 issue 编号维系。说人话就是，这两个包互相使了个眼色，没有合同。

这条权衡背后的本质矛盾是：**同一份 store 动作，两个插件都要动手脚（testing 要换成哑炮、devtools 要包代理做时间线分组）vs 它们不能互相覆盖**。解法是给其中一方一个优先级标记，另一方主动让位。这同样是通解骨架：多个扩展都要改同一个对象时，总得有人定先后，要么靠注册顺序，要么靠一个显式的优先级标志。本章恰好同时展示了这两种——替身靠注册顺序赢过业务插件，devtools 靠显式标志输给 testing。

## 5. 最小原理演示

下面的演示只演一条原理：插件总线按注册顺序执行、后跑者覆盖先跑者。两个对照用例分别演"替身排最后"和"替身排最前"，看出顺序怎么决定 mock 生死。

```ts
// 最小插件总线容器：演"后装者覆盖先装者"这一条原理
function createMiniPinia() {
  const plugins = []
  return {
    use(plugin) { plugins.push(plugin); return this },
    assemble(setup) {
      const store = setup()                  // setup 先跑：动作此刻已挂在 store 上
      for (const plugin of plugins) {        // 总线按注册顺序逐个跑插件
        const ext = plugin(store)            // 插件可以直接改 store
        if (ext) Object.assign(store, ext)   // 也可以返回值、合并进 store；后者覆盖前者
      }
      return store
    },
  }
}

// 真动作：发请求落库（测试时想让它变成哑炮）
const realAddItem = (item) => `已落库 ${item}`

// 业务插件：模拟应用里"会往 store 上装动作"的普通插件，靠返回值合并进 store
const businessPlugin = () => ({ addItem: realAddItem })

// 替身插件：遍历 store，把每个动作直接赋值换成 spy（哑炮、可断言被调）
function stubPlugin(spy) {
  return (store) => {
    for (const key in store) {
      if (typeof store[key] === 'function') {
        store[key] = (...args) => spy(key, args)   // 直接赋值，盖掉真动作
      }
    }
  }
}

// 用例 A：替身排最后（createTestingPinia 的正确做法）
const spyA = []
const cartA = createMiniPinia()
  .use(businessPlugin)        // 先注册业务插件
  .use(stubPlugin(spyA))      // 最后注册替身：它最后跑，盖掉前面装上的动作
  .assemble(() => ({ count: 0, addItem: realAddItem }))
cartA.addItem('apple')        // 命中替身，真逻辑没跑
console.log(spyA)             // => [['addItem', ['apple']]]

// 用例 B：替身排最前（反面教材）
const spyB = []
const cartB = createMiniPinia()
  .use(stubPlugin(spyB))      // 替身先跑：把真动作换成了 spy
  .use(businessPlugin)        // 业务插件排在其后：返回值把真动作装回，盖掉 spy
  .assemble(() => ({ count: 0, addItem: realAddItem }))
cartB.addItem('apple')        // 命中真逻辑，替身被覆盖了
console.log(spyB)             // => []，替身虽跑过，却白跑一趟
```

两个用例里 `setup` 返回的对象都带着真动作 `addItem`，对应真源里"动作在总线跑之前已由核心组装挂上"这一前提。区别只在注册顺序：用例 A 把替身放在最后，它是最后一个改 store 的人，哑炮留到了最后；用例 B 把替身放在最前，业务插件排在其后，业务插件通过返回值把真动作装回去，替身就被盖掉了。这就是"mock 生死系于插件顺序"的活教材。

## 6. 执行轨迹

拿一个会发请求的购物车 store，配上 `createTestingPinia({ stubActions: true })`，看一次调用是怎么走完装配、变成哑炮的。

输入：测试里渲染被测组件，组件内部调 `useCart()`。此时 `addItem` 还是那个会发请求落库的真动作。

第一步，`createTestingPinia` 先拿到普通容器，往 `_p` 按顺序追加四个插件，替身压在最后；接着设 `_testing = true`，把自己设为当前活跃实例（这样组件外也能直接 `useCart()`）。

第二步，组件调 `useCart()` 触发 store 组装。`setup` 先跑，store 此刻长成 `{ count: 0, addItem: <真动作> }`。

第三步，总线遍历 `_p` 依序跑。初始状态插件没找到这个 store 的预设初态，不动；没有业务插件；计算属性可覆写插件发现没有计算属性；最后轮到替身。替身判断 `addItem` 要替死，调 `createSpy()` 造一个空 spy，`store.addItem = spy`。此时 store 变成 `{ count: 0, addItem: <空 spy> }`。

第四步，组件里 `cart.addItem({ id: 1 })` 命中那个空 spy。不发请求，不改状态，但 spy 把这次调用记了下来。

输出：测试可以断言"addItem 被调了一次、参数正是 `{ id: 1 }`"，组件和真实后端被干净隔离。一次调用从会落库的真动作，变成了可观测、零副作用的哑炮。

## 7. 教学简化说明

本章演示故意省略了几样东西。计算属性可覆写那段是直接改响应式库内部缓存字段（缓存值、脏标记、计算函数）的 hack，目的是把计算属性钉死成定值、赋空再还原，但它强耦合底层私有实现，本章只在心智模型里提了存在、没有演。初始状态深合并的边界、`$patch` 合并逻辑的同源差异（合并管道在前置章已经讲过）也没有展开。造 spy 工厂对 jest / vitest 全局变量的运行时探测、两条错误码校验（没找到工厂、误把已调用的 spy 实例当工厂传进来）、`fakeApp` 触发安装的分支，都是工程边角，演示不追求。第二条权衡里 `_testing` 标志和 devtools 让位的代码实现也只讲了原理、没有落成代码。这些都是裁剪过的原理模型，不是工程完整度。

## 8. 小结

全书走到这里，从状态树的聚合、动作的拦截，到上一章 SSR 的状态搬运，讲的都是核心怎么把状态管好。这一章正好反过来用同一套机制：testing 一行核心都没改，它只是站在"插件总线"那块地基上，往队尾挤进了一个插件。能这么轻巧地完成 mock，恰恰说明那条总线设计得够通用——它本来是为了让核心不被各种扩展需求掏空，结果连测试隔离这种看起来"理应开后门"的事，也能靠"排到最后一个位置"解决。
