# 插件扩展总线 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：一个状态管理库不可能预置好所有部署期才需要的能力——调试面板、测试替身、持久化、日志、权限……如果都塞进核心，核心会臃肿到无法维护；可若不提供入口，使用者只能 fork 改源码。使用者真正需要的是：「在每个 store 诞生完毕的那一刻，让我有机会再往它身上挂自己的能力」。

- **一句话核心思想**：把「每个 store 诞生完毕」这个时刻，变成一条按注册顺序逐个通知的回调列表，让回调往新生的 store 上添东西——一条围绕 store 生命周期的有序扩展总线。

- **设计动机（为什么需要它）**：核心想保持精简、但部署又需要大量横切能力，这对矛盾不可调和；解法是把「诞生后钩子」标准化为「收集 + 按序调用 + 合并返回值」的总线，把所有非核心能力移出核心。
  - 承前关系：这条总线是前置章「运行时自动分流组装引擎」的直接下一个动作——组装引擎负责把用户声明的状态/计算/动作三类成员装进 store（已在第 5 章『Setup Store 的运行时自动分流』讲透，本章只看它的新侧面：装配完成之后留下的对外扩展点）；总线还复用了第 2 章建立的「用一个副作用作用域托管所有副作用」这一容器底座（本章只看它的派生结论：插件副作用落在 store 自己的子作用域内）。Writer 切勿重讲分流引擎本身或容器作用域本身。

- **关键权衡（选择→换来→代价）**：
  1. **按注册顺序串行调用、后注册者覆盖先注册者同名属性** → 换来了可预测的叠加语义（先注册的插件加的属性，后注册的插件既看得到、也能覆盖）→ 代价是**插件顺序敏感**：同一组插件注册顺序不同，store 上的最终扩展就不同（例如「测试替身」插件必须排在链尾才能真正替换掉动作）。
  2. **让每个插件在 store 自己的副作用作用域内执行** → 换来了插件建立的自动依赖追踪、监听、计算都随 store 一并回收（store 销毁即扩展清理，不留泄漏）→ 代价是**插件副作用的生命周期被绑死在单个 store 上**，想做跨 store 的全局副作用，插件得自己另开作用域。
  3. **插件返回的对象直接合并进 store** → 换来了极简的扩展 API（`return { foo }` 即把 `foo` 挂到 store 上）→ 代价是 store 本身是响应式对象，**返回的普通对象会被深响应化、且「提取状态为独立引用」的工具会忽略非响应式属性**，故开发模式必须对「非响应式、也未显式标记为原始值」的返回值发诊断警告，逼作者用响应式包装或显式标记。
  4. **用一个暂存表处理「容器挂载前」就注册的插件** → 换来了插件可在应用挂载前的任意时刻注册（含核心自带的调试插件）→ 代价是多一条「挂载时把暂存表整体转正」的两阶段细节。

- **最小心智模型（7 步）**：
  1. 容器创建时备两张表：一张「已就位」插件表、一张「待转正」暂存表；核心自带的调试插件先进暂存表。
  2. 用户注册插件：若应用尚未挂载 → 进暂存表；否则 → 直接进就位表。
  3. 应用挂载容器那一刻，暂存表按原顺序整体转入就位表。
  4. 某 store 首次被使用时，组装引擎先把状态、计算、动作三类成员装配进 store、定义好集中状态入口、并把半成品登记进实例表。
  5. 装配尾部，按顺序遍历就位插件表，把 `{ store, 应用, 容器, 定义选项 }` 交给每个插件。
  6. 每个插件在 store 自己的副作用作用域内执行；其返回的对象被合并进 store，扩展立即生效。
  7. store 销毁时其副作用作用域停止，插件在该作用域内建立的所有副作用一并回收。

- **最小原理演示（替代旧「复刻范围」）**：
  - 应演示：一个几十行、纯表达「收集 + 诞生即按序通知 + 返回值合并 + 作用域绑定回收 + 顺序覆盖」的最小骨架。每一行都要对应上面某个原理点：两阶段收集演权衡④；按序回调 + 合并演权衡①；给每个 store 配一个可 `stop()` 的「作用域」对象、插件在该作用域内建的清理钩子随 stop 触发演权衡②。
  - 应故意省略：真正的响应式系统（用普通对象即可演顺序与合并）、诊断警告、调试属性登记、热更新、SSR、完整类型系统。
  - 演示载体建议：**首选 TS/JS**。本章核心是「收集 + 按序回调 + 合并返回值 + 作用域回收」，纯属数据结构与回调的组织，纯 JS 即可忠实演透，无需 Vue 运行时；用一个极简的「作用域」对象（持有一个清理钩子列表、`stop()` 时逐个调用）模拟副作用作用域的回收语义足矣。**无需退回原仓库语言**。演示演的是权衡①（顺序覆盖）和权衡②（作用域回收）这两条最硬的原理。

- **正文不宜展开的细节**：诊断警告的具体文案与「标记为原始值」的内部标记机制（点到「非响应式返回值会被警告」即可，文案留给代码注释）；调试模式下把扩展属性登记进自定义属性集合的逻辑；定义选项里的动作列表是如何为「装配式 store」运行时收集出来的（这是第 5 章分流引擎的副产物）；应用挂载时往全局属性与依赖注入里塞容器的那些装配细节（第 2 章已讲）；销毁容器时清空插件数组的细节。

- **推荐的一个执行轨迹例子**：
  - 输入：容器创建 → 自带调试插件进暂存表 → 用户注册插件 A（返回 `{ x: 某响应式状态 }`）→ 用户注册插件 B（返回 `{ x: 覆盖值, y: 某响应式状态 }`）→ 应用挂载 → 首次使用某 store。
  - 中间态：挂载时暂存表 `[调试]` 转入就位表；就位表 = `[调试, A, B]`；store 装配完毕。
  - 顺序通知：调试先跑；A 给 store 加 `x`；B 覆盖 `x`、再加 `y`。
  - 输出：最终 store 同时带「被 B 覆盖后的 `x`」和「`y`」；store 销毁时，三个插件在该 store 作用域内建的副作用全部被回收。

## 概念要点

- 容器同时持有一份「已就位插件表」与一份「待转正暂存表」；二者都是数组，按注册顺序排列。源码位置: packages/pinia/src/createPinia.ts:18-20,47
- 注册方法：若应用尚未挂载（应用引用为空）→ push 进暂存表；否则 → push 进就位表；返回容器自身以支持链式注册。源码位置: packages/pinia/src/createPinia.ts:38-45
- 应用挂载（install）时：设置活跃指针、把容器塞进依赖注入与全局属性，然后把暂存表逐项转入就位表并清空暂存表。源码位置: packages/pinia/src/createPinia.ts:23-36（转正动作见 34-35）
- 容器自带调试插件在容器构造末尾就注册（此时应用尚未挂载，故落入暂存表，挂载时第一批转正，从而总是插件链最前）。源码位置: packages/pinia/src/createPinia.ts:58-60
- 销毁容器时停掉总作用域、清空实例表，并 `splice(0)` 清空就位插件表、置空应用引用。源码位置: packages/pinia/src/createPinia.ts:72-79
- 插件执行点位于「装配式 store 构造函数」尾部：在「装配引擎把三类成员 `assign` 进 store」「定义 `$state` 访问器」之后，在「打开状态监听开关」之前——即插件拿到的是一个组装完毕、但尚未对外发出任何状态变更通知的 store。源码位置: packages/pinia/src/store.ts:716-754（前置装配见 573-595，监听开关打开见 778-779）
- 执行方式：遍历就位插件表，**每个插件都在 store 自己的副作用作用域内运行**（`scope.run(() => extender(...))`）；该作用域是在容器总作用域之下、为这个 store 专门 `effectScope()` 新建的。源码位置: packages/pinia/src/store.ts:500-502（建作用域）,718-725（在该作用域内跑插件）
- 传给插件的上下文固定为 `{ store, app, pinia, options }`。源码位置: packages/pinia/src/store.ts:719-724；类型契约见 packages/pinia/src/rootStore.ts:132-157
- 插件返回值被 `assign(store, extensions)` 整体合并进 store；数组按顺序遍历 + 对象赋值，意味着**后注册插件的同名属性覆盖先注册者**。源码位置: packages/pinia/src/store.ts:717,753
- 调试构建下，扩展返回值的每个 key 会被登记进 store 的「自定义属性集合」，供开发者工具识别为非内置属性。源码位置: packages/pinia/src/store.ts:728-732
- 开发模式下对扩展返回值做诊断：凡值为对象、又不是响应式引用、又不是响应式对象、又未带「标记为原始值」标记的，发警告——因为「把 store 状态转成独立引用」的工具会忽略这类属性。**检查必须在合并之前做**（注释明确：合并进响应式 store 后，响应式对象会被解包，就再也区分不出「原本是响应式对象」还是「普通对象」了）。源码位置: packages/pinia/src/store.ts:734-751；警告文案见 packages/pinia/src/diagnostics.ts:38-43
- 传给插件的「定义选项」对象自带一份动作清单：声明式 store 直接继承用户声明的动作；装配式 store 的动作清单则是装配引擎在分流时逐个累加进去的——两条路都让插件能拿到完整动作集。源码位置: packages/pinia/src/store.ts:232-235,540-554
- 插件类型契约：接收上下文，返回「自定义属性 / 自定义状态属性」的部分对象，或什么都不返回。源码位置: packages/pinia/src/rootStore.ts:159-172

## 关键调用链

注册链：`createPinia()` → `pinia.use(plugin)` →（应用未挂载）暂存表 /（已挂载）就位表；`app.use(pinia)` 触发 `install` → 暂存表整体转入就位表。

源码位置: packages/pinia/src/store.ts:716-754（执行点），packages/pinia/src/createPinia.ts:23-45（收集与转正）

## 易混淆 / 边界 / 推断

- **事实**：诊断检查必须早于合并——合并进响应式 store 后响应式对象会被解包，与普通对象不可区分，注释直接写明这一点。源码位置: packages/pinia/src/store.ts:734-737
- **推断（顺序敏感的根因）**：插件按数组顺序串行执行，每轮 `assign(store, extensions)` 累加；后注册插件的上下文里的 `store` 已含先注册插件加的属性，且其返回值同名 key 会覆盖前者。故「测试替身」类插件须排在链尾才能真正拦截动作。源码位置: packages/pinia/src/store.ts:717,753
- **事实**：插件副作用落在 store 的子作用域上，而非容器总作用域；`$dispose`（停该 store 子作用域）只回收本 store 内插件建的副作用，而 `disposePinia`（停容器总作用域）会连锁回收所有 store 的子作用域。源码位置: packages/pinia/src/store.ts:349-354,500-502；packages/pinia/src/createPinia.ts:72-79
- **推断（调试插件为何总在最前）**：核心在构造容器末尾就注册自带调试插件，此刻应用未挂载、故进暂存表；挂载时暂存表按序转入就位表，调试插件成为就位表首项，从而能先于任何用户插件建立观察。源码位置: packages/pinia/src/createPinia.ts:58-60,34-35
- **事实**：插件返回 `undefined`（即 `void`）时安全——`for...in undefined` 跳过、`Object.assign(store, undefined)` 为 no-op，不报错。源码位置: packages/pinia/src/store.ts:738,753
- **未理解**：无明显不可解之处。
