# 随作用域清理的发布订阅

> 本章属于 primitive 层，是全书的地基章之一（无前置依赖）。
> 学完你能用一句话讲清：为什么订阅机制的注销要绑在"注册那一刻所在的作用域"上，以及 detached 这个开关为了换什么、付出了什么。

## 1. 为什么需要它

用过状态库的人都熟悉一种订阅：在组件里监听某个 store 的状态变化，或者监听每次动作的执行。写一句订阅本身不难，真正让人头疼的是另一件事——**什么时候该把它收掉**。

忘了收的后果很具体：组件都卸载了，回调还在跑；回调里碰的响应式数据早就没了，访问就报错；组件实例被回调引用着，垃圾回收收不掉，内存就这么一点一点漏出去。于是你被迫给每一条订阅都配一句注销，再挂到组件的卸载钩子上。每订阅一次就得手写一遍这套样板，啰嗦，而且容易漏——漏一条就是一个潜在的泄漏。

更麻烦的是，两种合理的诉求会打架。绝大多数时候你希望订阅**跟着组件一起死**：组件没了，这条订阅就没意义了，自动收掉最省心。但偶尔你恰恰需要它活得比任何组件都久——比如在应用根上挂一个全局监听，把每一次动作上报到埋点系统。这种时候"跟着组件死"反而是错的。

所以这个机制要同时摆平两件事：让"随作用域自动收"成为默认，省掉那套手写样板；又得留个口子，让少数订阅能脱离作用域、自己活下去。

本章是全书第一章，也是地基章。后面所有跟"状态变更通知"有关的机制，最后都会落到这套订阅骨架上。先把它讲透，后面每次再见到它，你都能一眼看穿那只是同一套原理换了个名字。

## 2. 核心思想

把"这条订阅到底该活多久"这个决定，从调用方手里的样板代码，挪到**订阅注册那一刻所在的作用域**身上。

订阅函数在登记回调的同时，顺手问一句"你现在身处哪个作用域"，然后把注销动作挂到那个作用域的离场清单上。作用域销毁时清单统一结清，订阅就跟着一起死了。再给一个 detached 开关，让它可以选择"我不属于任何作用域，自己活"。

## 3. 心智模型

这套机制由三件套拼成，理解了它们就理解了全章。

**第一件：一个订阅簿。** 用一个集合存这一类事件的所有回调。集合的好处有两点：同一份回调注册两次只算一份（靠引用去重）；遍历时按插入顺序来，触发顺序可预期。它本身不记任何状态，谁要监听就把回调塞进来，所以同一个订阅簿能被状态订阅、动作订阅、动作的 after 回调等反复复用。

**第二件：一个注销闭包。** 每次注册都当场产出一个"注销函数"，它闭包记住自己要删哪个回调。这个闭包是全章的关键道具——后面两条注销路径执行的**是同一段代码**。

**第三件：作用域的离场清单。** 可以把作用域想象成一块带"离场清单"的区域：你在这块区域里登记的清理动作，都被记在它的清单上；区域销毁时，清单上的事被逐个结清。订阅要利用的就是这张清单。

完整的生命周期是这样的：

```
注册：回调进订阅簿
      → 产注销闭包
      → 若「未声明 detached」且「当前身处某个作用域」
        → 把注销闭包推进该作用域的离场清单
      → 无论上面走没走，都把注销闭包返回给调用方

触发：遍历订阅簿，把事件参数逐个透传给每个回调，同步调

注销（两条路走同一闭包）：
  · 自动——作用域销毁 → 跑离场清单 → 执行注销闭包
  · 手动——调用方主动调返回的注销函数
  闭包做的事：从订阅簿删掉这个回调；只有真删掉了，才顺带跑一个"清理钩子"
```

这里有个细节值得记住：清理钩子**只有真删掉回调时才触发**。于是注销闭包天生是幂等的——先手动注销一次，作用域销毁时再触发一次，第二次发现回调早已不在，删不掉，钩子就不会重复跑。这让你不用操心"会不会注销两次"。

（顺带一提：为什么用集合做订阅簿、用最朴素的同步遍历来触发？因为这套东西要被各处复用，它必须薄到几乎不携带任何自己的逻辑——加防抖、加微任务、加批处理都会把它和"什么时候触发"绑死，而触发时机恰恰是调用方的事。保持"只是一存一遍历"，它才能保持通用。触发时机的那些讲究，留给后续专门讲状态变更的章节。）

## 4. 关键权衡

这一节是全章的重头戏。这套机制之所以这么设计，核心就在下面两条取舍里。它们其实是同一个本质矛盾的两面：**资源回收想要自动化、省心，但"这份资源到底该活多久"本质上是个语义判断，没法一概而论。** 这对矛盾不只出现在这里——React 的 `useEffect` cleanup、定时器、事件监听器、`ResizeObserver`，凡是"注册时留了把柄、用完要回收"的东西，都得在"自动随生命周期回收"和"回收时机由语义决定"之间找平衡。Pinia 的解法是：默认绑最近的作用域，把不常见的"我想活更久"留给一个开关。

### 把注销挂到"注册那一刻所在的作用域"

| | |
| --- | --- |
| **选择** | 注册时探测当前作用域，把注销闭包推进它的离场清单 |
| **换来** | 调用方完全不用写卸载样板。在组件里写一句订阅，就等于同时写好了注销，几乎不可能泄漏 |
| **代价** | 订阅的生死被**隐式**绑到"注册那一刻所处的那个作用域"上。你在组件 setup 里订阅，它绑组件作用域；你在某个嵌套作用域里订阅，它绑那个嵌套作用域 |

这条权衡换来的是一种"零成本的安全"：开发者根本不需要意识到注销的存在，它就自己发生了。但隐式绑定有它的认知税。哪天你遇到"为什么这个组件卸载了，订阅还在？"或者反过来"为什么这个订阅莫名其妙没了？"，调试的第一步必须是先想清楚"注册那一刻，我到底站在哪个作用域里"。作用域这个上下文是隐式的——代码里没有任何一行写着"这条订阅属于组件 A"，它的归属完全取决于**调用的时机和位置**。这种隐式性在大多数时候是福利（不用写），在出 bug 时就成了需要你主动还原的隐藏状态。

### detached 开关配上"永远返回手动注销函数"

| | |
| --- | --- |
| **选择** | 即便已经挂了自动清理，订阅函数也永远把注销闭包返回出来；再加一个 detached 参数，传 true 就跳过自动清理 |
| **换来** | 同一套 API 既能随作用域死、又能跨作用域活。全局埋点监听、跨组件的事件总线这类"活得比任何组件都久"的场景，只要传个 `detached: true` |
| **代价** | detached 这条路完全靠调用方自觉。框架不再帮你兜底：你必须自己把返回的注销函数存起来，在合适的时机调掉。忘了存、忘了调，就一定会泄漏，而且因为是脱离作用域的，没有任何东西会替你善后 |

这条权衡化解的本质矛盾是："资源要随某个生命周期集体回收"与"个别资源需要脱离任何生命周期独立存活"天然打架。任何事件总线、全局监听系统都会撞上它：强制所有订阅都随作用域死，就做不了全局监听；全都不自动回收，又退回到手写样板的老路。detached 开关本质是给"集体回收"开了一个"个人请假"的口子——代价是请了假的这笔账，得调用方自己记、自己销。

> 这两条权衡不是孤立的。第一条让"随作用域死"成为默认的省心选择；第二条给这个默认开了一个可控的例外。两者合起来，才同时满足了开头说的那两种打架的诉求。

## 5. 最小原理演示

下面这段从零实现的代码，只为演透一件事：**自动清理换便利、detached 换长生命周期**这对全章灵魂。它包含三块——一个订阅簿总线、一个自造的迷你作用域、一个把两者粘起来的订阅函数。命名是教学化的，不追求和真实代码一致。

```ts
// 订阅簿总线：一个集合存回调，触发时遍历调用
type Callback = (...args: any[]) => void

function createBus() {
  const callbacks = new Set<Callback>()

  function on(
    callback: Callback,
    detached = false,
    onCleanup: () => void = () => {}
  ) {
    callbacks.add(callback)

    // 注销闭包：无论手动调、还是作用域代为调，跑的都是这一段
    const remove = () => {
      const deleted = callbacks.delete(callback)
      // 只有真删掉了才收尾 —— 先手动注销、作用域销毁再调一次，钩子也不会重复触发
      if (deleted) onCleanup()
    }

    // 灵魂一句：没声明 detached、且此刻正身处某个作用域 → 把注销交给它
    if (!detached && getCurrentScope()) {
      onScopeDispose(remove)
    }

    // 不管有没有自动清理，注销函数都还给调用方，允许提前手动收
    return remove
  }

  function emit(...args: any[]) {
    // 最朴素的同步广播：按插入顺序逐个调，不防抖、不排队
    for (const cb of callbacks) cb(...args)
  }

  return { on, emit }
}
```

要让上面那句"灵魂一句"生效，得有一个能被探测、能记账的作用域。下面这个迷你作用域就是干这个的——一根全局指针记住"当前在哪个作用域"，每个作用域随身带一张离场清单：

```ts
// 自造作用域：全局指针记"当前在哪儿"，每个作用域带一张离场清单
type Scope = { cleanups: Array<() => void> }
let activeScope: Scope | null = null

function getCurrentScope() {
  return activeScope
}

function onScopeDispose(fn: () => void) {
  // 谁是当前作用域，清理动作就记在谁的账上
  if (activeScope) activeScope.cleanups.push(fn)
}

// 开一个作用域：进入时把自己设为当前，结束时把离场清单逐个结清
function beginScope() {
  const scope: Scope = { cleanups: [] }
  const prev = activeScope
  activeScope = scope
  return function end() {
    activeScope = prev
    for (const cleanup of scope.cleanups) cleanup()
    scope.cleanups = []
  }
}
```

现在跑两条对比轨迹，看那对灵魂权衡怎么落地：

```ts
// 轨迹一：在作用域内订阅（默认随作用域死）
{
  const bus = createBus()
  const endScope = beginScope()
  const log: string[] = []

  bus.on(() => log.push('命中'))   // 注册那一刻，当前作用域 = 刚开的这个
  bus.emit()                        // log: ['命中']
  endScope()                        // 作用域结账 → 注销被连带触发 → 回调消失
  bus.emit()                        // log 仍是 ['命中']，没人再响应
}

// 轨迹二：detached 订阅（脱离作用域活，手动注销才死）
{
  const bus = createBus()
  const endScope = beginScope()
  const hits: number[] = []

  const off = bus.on(() => hits.push(1), /* detached */ true) // 跳过自动清理
  endScope()                                                  // 作用域结账，也动不了它
  bus.emit()                                                  // hits: [1]，回调还在
  off()                                                       // 必须自己调返回的注销函数
  bus.emit()                                                  // hits 仍是 [1]
}
```

轨迹一里，回调的生死完全交给了作用域，调用方连注销函数都没存——这就是"自动清理换便利"。轨迹二里，同一个 `on` 只是多传了一个 `true`，回调就脱离了作用域、得自己管——这就是"detached 换长生命周期"。两段代码共用同一份 `on`，差别只在那一个开关上。

> Pinia 里这套东西的订阅函数叫 `addSubscription`、触发函数叫 `triggerSubscriptions`，被 `$subscribe`（监听状态变化）和 `$onAction`（监听动作执行）共用同一份实现。Vue 自身的作用域清理（`getCurrentScope` / `onScopeDispose`）背后也正是上面这套"指针 + 离场清单"的机制。

## 6. 执行轨迹

拿一个最常见的情况走一遍：某个组件在 setup 里调用了 `$onAction` 监听动作，没传 detached。此刻当前作用域就是该组件的作用域。

注册瞬间，依次发生：

1. 回调被塞进"动作订阅簿"这个集合。
2. 注销闭包产出，它记着要删的就是刚才这个回调。
3. 探测当前作用域——返回的是组件作用域，且没传 detached，**两个条件都满足**，于是把注销闭包推进组件作用域的离场清单。
4. 注销闭包同时返回给调用方（这一例里调用方没存它，无所谓）。

接着某个动作被调用，触发侧遍历动作订阅簿，把 `{ args, name, store, after, onError }` 透传给回调，回调命中。

然后组件卸载，组件作用域销毁，离场清单开始结账：执行注销闭包 → 从集合里删掉这个回调 → `delete` 返回 true → 清理钩子跑（动作订阅这里通常没有外部资源要收尾；如果是状态订阅，这个钩子负责停掉背后的 watcher）。一切归零。此后再有动作触发，订阅簿里已经没这个回调，遍历自然跳过。

换一个参数，结果完全不同，对比如下：

| 注册方式 | 组件卸载后回调还在？ | 谁负责最终清除 |
| --- | --- | --- |
| `$onAction(cb)`（默认） | 不在，随作用域一起没了 | 作用域的离场清单 |
| `$onAction(cb, true)`（detached） | **还在**，下次动作照样命中 | 只能是调用方手动调 `off()` |

detached 那一行之所以"还在"，是因为注册瞬间第 3 步的探测被那个 `true` 挡掉了，注销闭包根本没进任何离场清单。组件作用域销毁时无从触及它，于是它就这么悬空地留着，直到调用方自己想起手里还攥着那个 `off`。

## 7. 教学简化说明

上面的演示是一个裁剪过的原理模型，故意省略了这些东西：完整的类型泛型（真实代码用 `Parameters<T>` 从回调类型反推触发参数）；多事件通道（这里只演了单一总线，真实场景下动作订阅和状态订阅是两本不同的订阅簿）；偏函数技巧（真实代码用 `bind` 把订阅簿预先"焊"好，对外只暴露回调和 detached 两个参数）；以及开发期的重复订阅诊断码、生产构建下被裁掉的告警分支。还有一件最重要的事刻意没讲：**什么时候触发**遍历、怎么和 `nextTick` 配合、怎么把多次修改合并成一次事件——那属于后续专门讲状态变更的章节，不是订阅原语本身的职责。

## 8. 小结

这套订阅机制关心的只有两件事：回调怎么存、怎么随作用域一起死。它刻意不碰"谁在改状态、改了之后该怎么通知"——那是把它拿去用的 store 的职责。而那些 store，又全部住在一个更大的容器里。下一章我们就造那个容器：看 Pinia 怎么用一个作用域托管所有 store 的响应式副作用，又怎么把每个 store 的状态聚成一棵统一的集中状态树。
