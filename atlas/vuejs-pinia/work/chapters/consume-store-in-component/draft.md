# 在组件中消费 Store：解构与映射

> 本章属于 composite 层。前置：Setup Store 的运行时自动分流、Options Store：声明式三分与统一组装。
> 学完你能：用一句话讲清「为什么直接解构 store 会丢响应性，以及消费入口靠什么把响应性找回来」。

## 1. 为什么需要它

上一章把「怎么改状态」讲透了——动作拦截和 `$patch` 批量合并两条管道，解决了状态怎么变的问题。这一章换个方向，看组件里「怎么把状态拿出来用」。

使用 store 的人，最自然想这么写：

```js
const { count, double } = useCounterStore()
```

把要的字段解构出来，按名字直接用，干净利落。但跑起来你会发现：改了 `count`，界面纹丝不动。原因不在写法，而在 store 的形状。它内部是一个被响应式代理包裹的整体对象，`count` 的响应性是「代理对象」赋予的；一旦你把它解构出来，等于把值「拷」成了一份普通变量，和代理对象之间的联系当场断开。直接解构，必然丢响应性。

第二个痛点来自另一类组件。Options 风格的组件没有 `setup` 这个时机去调用工厂函数拿 store，开发者想要的是 Vuex 时代那种声明式铺开的写法：把状态铺进 `computed`，把动作铺进 `methods`，像填表一样用。

本章讲的两个消费入口，就是为这两个痛点分别而生：`storeToRefs` 解决「解构不丢响应性」，`mapState`/`mapActions` 一族解决「没有 `setup` 时机也能用 store」。它们看着是两套 API，对着的是同一个事实——store 是个被代理的统一对象，状态、计算属性、动作三类成员已经摊平挂在它上面。

## 2. 核心思想

把上面两个痛点放一起看，会发现它们其实是同一个底层问题的两面：**响应性是「代理对象」的属性，不是单个值的属性；任何「把值拷出来」的用法都会把它弄丢。**

打个比方，store 的响应性像水管里的水压，是整条管网维持的属性，不是单个水龙头自带的。直接解构，等于把水龙头从管网上卸下来——水压当场没了。所以无论解构还是映射，解法都是同一招：**读值的时候绕回那个统一代理对象，永远不拷贝值**。解构助手不把值交给你，而是给每个「会变」的成员套一层壳，壳的读法是「回 store 上取当前值」；映射助手生成的也不是值，而是一个个函数，函数体每次执行都重新访问 store。包装的形态不同，底层都是「转发，不拷贝」。

## 3. 心智模型

先记住 store 成品长什么样。组装完成后，状态、计算属性、动作三类成员被摊平挂在同一个被代理的对象上——这套三分结构怎么「建立」起来的，第 5 章已经讲透，本章只管「消费」。从消费侧看过去，它是一个扁平的同构对象：光看形状，你分不清某个字段原本是状态、计算属性还是动作。

可两个入口偏偏需要区分。于是它们都做了一件事：**在运行时对每个字段再跑一遍特征探测**，把已经混在一起的三类重新认出来。这正是第 5 章「运行时自动分流」的消费侧镜像——同一套探测手法（是不是 ref、是不是 reactive、身上有没有副作用标记），建立侧跑一遍用来分类挂载，消费侧再跑一遍用来分拣消费。

两条路径的流转：

**解构路径**（Composition 风格，`setup` 里一次性调用）：

```text
成品 store
  → 穿透代理拿到原始对象，遍历每个字段
  → 特征探测分三路：
       带副作用标记        → 计算属性 → 新建一层转发壳（读写都回 store）
       是 ref 或 reactive  → 状态     → 在 store 上建一个属性引用
       其余                → 动作等   → 丢弃
  → 返回一个只装「会变成员」的扁平引用对象
```

**映射路径**（Options 风格，铺进 `computed`/`methods`）：

```text
给一组键名
  → 为每个键生成一个普通函数（不是箭头函数）
  → 函数体：取当前组件实例的 $pinia → 调工厂拿 store → 读对应字段
  → 状态/计算属性铺进 computed 槽位，动作铺进 methods 槽位
  → 渲染期 Vue 调用函数时，上面那串才真正执行
```

有个支撑性细节顺带交代：store 组装时，成员被同时挂到了代理对象和穿透后的原始对象两份上（这恰是为了让解构助手穿透代理后还遍历得到它们）。所以解构路径第一步才敢先穿透、再遍历。

## 4. 关键权衡

### 把会变的成员包成转发壳，而不是拷贝值

解构这条路的根本抉择在这里。

**选择**：解构助手不把字段值拷给你，而是给每个会变的成员套一层「读值时绕回 store」的引用壳——计算属性套一个 `computed` 壳，读时回 store 取、写时回 store 写；状态用一个指向 `store[key]` 的属性引用。

**换来**：解构后每个字段仍是独立引用，响应性一根没断，可以放心地 `const { count, double } = storeToRefs(store)`。而且读写都落回同一个 store，整个对象保持着单一数据源，状态变更、序列化、写回计算属性都指向同一份。顺带一个干净的心智：解构助手主动跳过动作，所以「解构出来的全是会变的引用」，跟你「解构状态」的直觉完全对齐，代价是动作得另从原对象取。

**代价**：多了一层读取间接，每次读 `count` 都要先穿过壳再回 store。更要紧的是，要认出计算属性，得靠「这个值身上挂着副作用标记」这一实现细节。框架当时没有官方的 `isComputed` 判定方法，只能伸手去摸 `value.effect`，等于依赖了 Vue 的内部约定，多了一层脆弱的间接。

**背后的本质矛盾**：这是「想按字段单独使用」和「响应性依附于整体代理对象」之间的冲突。解构天生是「拷值」，可响应性偏偏是代理对象的群体属性，一拷就断。这条权衡的通解骨架是：**解构出来的不该是值，而该是「读值时绕回代理」的引用**。抓住这一点，你在 Vue 自身的 `toRefs`、在 React 里「别解构 props、别解构 state 对象」的告诫中，都能认出同一个问题。

### 把取 store 这件事推迟到渲染期，从组件实例身上拿 Pinia

映射这条路要解决的是另一道难题：Options 组件没有 `setup`，调用工厂拿 store 的时机从哪来？

**选择**：映射函数不立即拿 store，而是给每个键生成一个普通函数闭包。函数体里不引用任何模块级全局变量，而是从当前组件实例的 `$pinia`（插件安装时挂上去的全局属性）拿到所属的 Pinia，再调工厂取 store，最后读字段。真正执行被推迟到渲染期——Vue 渲染组件、需要某个计算属性的值时，才会调用这个函数。

**换来**：Options 风格组件完全没有 `setup` 也能用 store，像填表一样把字段铺进 `computed`/`methods`。更关键的是，它不依赖任何全局单例，Pinia 是从组件实例的注入点取的，这意味着同一个应用可以同时存在多个 Pinia 实例（测试隔离、SSR 同构多请求），互不污染。

**代价**：每次读属性都要重新走一遍「取 `$pinia` → 调工厂 → 读字段」。工厂内部对已建 store 只是查表返回，不会重复装配，所以开销可控，但调用路径确实更长。另一个代价是写法受限：这些函数必须写成普通 `function` 而不是箭头函数（要靠 `this` 拿组件实例），且整体依赖「Pinia 被挂成了组件实例的全局属性」这一注入约定。

**背后的本质矛盾**：这是「没有合适的时机去拿 store」和「工厂必须被调用才有实例」之间的冲突。通解骨架是经典的惰性求值——**把『拿』这个动作推迟到真正『用』的那一刻，并让闭包从自己的执行上下文里取依赖，而不是依赖全局**。任何「定义时依赖还不存在、运行时才齐备」的场景，都能套用这个骨架。

## 5. 最小原理演示

下面这段演示只演透两件事：解构侧「特征探测 + 转发回代理、绝不拷值」，映射侧「延迟到渲染期 + 从实例取 Pinia」。类型推导、后缀定制、写回细节一律略去。

```ts
import { computed, isReactive, isRef, toRaw, toRef } from 'vue'

// 解构助手：演「特征探测 + 转发回代理、绝不拷值」
function storeToRefs(store: any) {
  // 先穿透代理。直接在代理上遍历，每个嵌套对象都会被判成 reactive，
  // 分不清谁天生是响应式子对象；穿透到原始对象，特征探测才准。
  const raw = toRaw(store)
  const refs: Record<string, any> = {}

  for (const key in raw) {
    const value = raw[key]
    if (value?.effect) {
      // 计算属性：身上挂着副作用标记。套一层转发壳，读写都绕回 store，
      // 不拷贝它当前的值——惰性求值与缓存因此都还在。
      refs[key] = computed({
        get: () => store[key],
        set(v) { store[key] = v },
      })
    } else if (isRef(value) || isReactive(value)) {
      // 状态：在 store 上牵一根属性引用，跟着 store 走。
      refs[key] = toRef(store, key)
    }
    // 动作、插件加的普通字段：既无 effect 标记也不是引用，直接跳过。
  }
  return refs
}

// 映射助手：演「延迟到渲染期 + 从组件实例取 Pinia」
function mapState(useStore: (pinia: any) => any, keys: string[]) {
  return keys.reduce((mapped: Record<string, () => any>, key) => {
    // 普通函数而非箭头函数——要靠 this 拿到组件实例。
    mapped[key] = function (this: any) {
      // 写下 mapState 的这一刻这串还没执行；渲染期 Vue 把组件实例绑成 this
      // 来调用它，此刻才取 $pinia、调工厂、读字段，并顺手建立响应式依赖。
      return useStore(this.$pinia)[key]
    }
    return mapped
  }, {})
}

// 用法：mapped.count 此刻只是一个函数，store 连影都没有，但不耽误
const mapped = mapState(useCounterStore, ['count'])
// 渲染期：拿一个组件实例当 this 去调它，延迟的那串此刻才跑
const fakeInstance = { $pinia: currentPinia }
mapped.count.call(fakeInstance) // → store.count
```

## 6. 执行轨迹

拿一个具体的成品 store 走一遍。它上面挂着：数值状态 `count`（当前为 1）、由 `count` 派生的计算属性 `double`（当前为 2）、动作 `inc`。

**解构路径**：`storeToRefs(store)` 先穿透代理拿到原始对象，开始遍历。读到 `count`，它是个 ref、身上没有副作用标记，命中「状态」分支，于是 `toRef(store, 'count')` 牵一根引用，`refs.count` 跟着 store 走。读到 `double`，它是个 ref 且身上挂着 `effect`，命中「计算属性」分支，新建一个 `computed`，读它时回 `store.double` 取、写它时回 `store.double` 写。读到 `inc`，是个普通函数，既不是 ref 也没副作用标记，三路都不收，丢弃。最终 `refs` 长成 `{ count: 引用, double: 转发壳 }`，没有 `inc`。解构出 `count` 再改它，走的是转发壳回 store 的那条路，响应性没断，界面照常从 1 更新到 2。

**映射路径**：调用 `mapState(useCounterStore, ['count'])`，reduce 出 `{ count: ƒ }`。此刻 `ƒ` 只是一个被定义好的函数，`useCounterStore` 还没被调用，store 尚不存在。把它铺进组件的 `computed`。到了渲染期，Vue 需要渲染用到 `count` 的地方，于是调用这个函数：`this` 是当前组件实例，从 `this.$pinia` 取到所属的 Pinia，调 `useCounterStore(pinia)` 拿到（或查表拿到已建好的）store，读 `store.count`——响应式依赖就在这一刻建立。动作 `inc` 走的是 `mapActions`，铺进 `methods`，调用时函数体同样回 store 取 `inc`，再把参数原样转发过去。

## 7. 教学简化说明

本章演示故意裁掉了一批东西：只读与可写计算属性的精细类型推导、`mapWritableState` 的写回 `set` 细节、对象形式 `mapState` 里「值是函数时绑定组件实例」的 `this` 用法、`mapStores` 的后缀定制、开发期对参数误传的诊断，以及映射相关的整套 Options API 类型体操。它们都是工程与类型完备性内容，不影响「转发不拷贝」和「延迟到渲染期」这两条核心原理。

## 8. 小结

消费 store 的诀窍落在一点上：读值时绕回那个统一代理对象，别把值拷出来。解构助手靠运行时特征探测，把会变的成员重新打包成转发壳，动作直接丢弃；映射助手靠生成延迟到渲染期的闭包，从组件实例取 Pinia 再回访 store。两条路包装不同，底子都是「转发，不拷贝」。下一章会把镜头从消费侧移开，去看 store 还能怎样被「扩展」——插件扩展总线。
