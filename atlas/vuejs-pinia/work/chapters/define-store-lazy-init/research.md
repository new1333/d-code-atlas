# defineStore 的懒装配与循环引用破解 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：状态库常见的两个坑。其一，启动时把所有 store 全量实例化，结果哪怕从没被用到的 store 也进了内存、还无法被打包器裁掉。其二，两个 store 互相依赖（A 用 B、B 用 A）时实例化顺序无解——先造 A 则 A 装配时要的 B 还没造，先造 B 同理，甚至直接栈溢出死循环。使用者只想「定义好 store、需要时拿到实例」，根本不想操心初始化顺序。

- **一句话核心思想**：**先占位登记一个半成品，再去懒装配它的内容**——用「同一个对象引用、分两步填满」破解循环，用「工厂延迟到首次调用」换取按需创建。

- **设计动机（为什么需要它）**：这个机制同时解两个矛盾——「相互引用的 store 谁先实例化」的死结，以及「未使用的 store 不该进产物」的体积负担。承前关系：本章站在前置章搭好的两块地基上——容器（一个托管所有副作用的根作用域 + 一棵集中状态树）和活跃指针（在任意上下文找回当前容器）。这两条原理（已在第 2 章『Pinia 容器与集中状态树』、第 3 章『活跃实例指针』讲透），本章只看它们的新侧面：容器里的「实例注册表」如何与「集中状态树」「根作用域」三者协作完成单例的懒装配；活跃指针如何保证在跨 store 的装配链路上始终指向正确容器。

- **关键权衡（本 Atlas 的核心）**：
  1. **先登记半成品、后运行装配** → 换来「相互引用的 store 不会陷入无限递归」（对方 store 哪怕只装配了一半，也能从注册表拿到同一个引用，递归就此终止）→ 代价是「装配期间被引用的自身 store 还是半成品」，所以跨 store 取值必须延迟到 getter/action 真正调用时（懒取），而不能在装配顶层同步解构对方的字段。
  2. **定义阶段只造工厂、首次调用才实例化** → 换来「未被调用的 store 可被摇树优化、且实例化推迟到真实需要的那一刻」→ 代价是「实例化时机交给调用方决定」，调用方必须能提供或注入容器，否则拿不到实例。
  3. **按 id 缓存的单例注册表** → 换来「同一容器下任意位置拿到的都是同一个实例、天然跨组件共享」→ 代价是「实例生命周期绑在容器上」，服务端渲染下容器若跨请求复用就会污染，必须主动重建/清理（承接第 3 章活跃指针的 SSR 风险）。

- **最小心智模型（7 步）**：
  1. 定义阶段只记下「配方」（id + 装配函数或配置），返回一个工厂，不创建实例。
  2. 工厂被首次调用时，先从注册表按 id 查；命中就直接返回，查不到才进入创建。
  3. 创建第一步：造一个只含内置方法（改状态、订阅、销毁等）的「半成品」实例。
  4. 立即把半成品按 id 写进注册表（先登记）——这是破解循环的关键一步。
  5. 在容器的根作用域下开一个子作用域，运行装配函数，产出用户的状态/计算属性/动作。
  6. 装配期间若引用了别的 store（哪怕对方也正在装配、只到半成品），递归创建在注册表层终止，不会死循环。
  7. 装配结果原地合并进那个已登记的半成品（对象引用始终不变），它就此「填满」；此后所有工厂调用都命中注册表，返回同一个单例。

- **最小原理演示**：
  - 应演示：一个约 30 行的从零实现，演透「先登记半成品 → 后运行装配 → 循环在注册表层终止 → 原地合并填满」这条核心链，以及「工厂延迟创建」。每一步对应一个原理点：注册表 = 单例缓存；先写入注册表 = 权衡 1 的占位；运行装配 = 装配阶段；原地合并 = 「引用不变地填满」。
  - 应故意省略：响应式、副作用作用域、插件、热更新、Options/Setup 两种风格的分流、订阅与批量合并、devtools、所有错误处理。
  - 演示载体建议：**首选 TS/JS**。本章核心是「注册表 + 工厂 + 占位符 + 惰性求值」这套与框架无关的纯语言机制，用 JS 几十行即可忠实演透，配最小 `package.json` 可直接 `node` 跑，对读者最友好；完全无需退回原仓库语言，也不依赖 Vue 运行时语义。

- **正文不宜展开的细节**：打包器 `__NO_SIDE_EFFECTS__` 注解对摇树的静态分析语义（提一句即可，不展开打包器原理）；热更新分支（hot 参数与 `__hot:` 临时 id）；测试模式忽略传入容器参数的特殊分支；把 store 缓存进组件实例供 devtools 读取的逻辑；Options Store 把声明式配置翻译成装配函数的过程；装配产物按响应式特征自动分类入库；插件按注册顺序应用——以上都属于后续章节或工程化旁路。

- **推荐的一个执行轨迹例子**：输入——定义两个互相引用的 store A、B（A 的装配里调 B 的工厂，B 的装配里调 A 的工厂），首次调用 A 的工厂。关键中间态：A 不在注册表 → 造 A 半成品 → 注册表写入 A → 运行 A 装配 → 内部调 B 工厂 → B 不在注册表 → 造 B 半成品 → 注册表写入 B → 运行 B 装配 → 内部调 A 工厂 → A 已在注册表（半成品）→ 直接返回、递归终止 → B 装配完成原地合并进 B 半成品、返回 B → A 装配完成原地合并进 A 半成品、返回 A。输出：A、B 各自持有对方的引用且都是完整实例，全程无死循环；再次调用任意工厂都直接命中注册表返回同一对象。

## 概念要点

- 定义阶段不创建实例：三个重载签名（id+options、id+setup+options、统一实现），实现里仅用 `isSetupStore = typeof setup === 'function'` 区分两种风格，构造一个 `useStore` 闭包并设 `useStore.$id = id` 后返回。源码位置: packages/pinia/src/store.ts:828-864, 879, 951-953
- 工厂内部的容器解析顺序：测试模式特殊处理 → 有注入上下文则 `inject(piniaSymbol)` → 回退到参数 → 再 `setActivePinia(pinia)` → 最终用模块级 `activePinia`（即活跃指针）兜底；无容器则抛错。源码位置: packages/pinia/src/store.ts:883-900
- 懒创建门槛：`if (!pinia._s.has(id))` 才进入创建，否则跳过；创建分两条路（Setup / Options）。源码位置: packages/pinia/src/store.ts:902-908
- 创建后统一从注册表取回实例（单例）。源码位置: packages/pinia/src/store.ts:917
- 「先登记」：组装函数先构造 `partialStore`（仅含 `$id`、`_p`、`$patch`、`$reset`、`$subscribe`、`$onAction`、`$dispose` 等内置成员），用 `reactive()` 包成 `store`，**随即** `pinia._s.set($id, store)`。源码位置: packages/pinia/src/store.ts:431-494
- 「后装配」：登记之后，才在应用上下文 + 容器根作用域 `pinia._e` 内开新 `effectScope` 运行 `setup`，产出 `setupStore`。源码位置: packages/pinia/src/store.ts:496-502
- 「原地合并填满」：装配产物经分类后用 `assign(store, setupStore)` 合并进**同一个** reactive store 引用——这正是半成品最终变完整、且注册表里引用无需更新的关键。源码位置: packages/pinia/src/store.ts:573-578
- 摇树支持：定义工厂前标注 `/*! #__NO_SIDE_EFFECTS__ */`，并注释「allows unused stores to be tree shaken」；配合「工厂不被调用就不创建」，未使用的 store 可被打包器整体裁掉。源码位置: packages/pinia/src/store.ts:857-858
- 销毁即注销：`$dispose` 调 `scope.stop()` 并 `pinia._s.delete($id)`，把实例从注册表移除。源码位置: packages/pinia/src/store.ts:349-354
