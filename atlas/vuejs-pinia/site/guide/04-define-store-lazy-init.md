# defineStore 的懒装配与循环引用破解

> 本章属于 composite 层。前置：Pinia 容器与集中式状态树、活跃实例指针：在任意上下文找回 Pinia。
> 学完你能：讲清 store 实例是何时被造出来的、两个互相引用的 store 为什么不会陷入死循环，以及为什么跨 store 取值必须"懒"。

## 1. 为什么需要它

上一章解决了"在任意上下文找回 pinia"——store 的工厂不管在组件里被调用，还是在另一个 store 的装配过程里被调用，都能定位到所属容器。可定位到容器只是起点，真正的问题是：实例到底在哪个瞬间被造出来？又是怎么造出来的？

你写 `defineStore(...)` 的时候，可能一口气写了十几个 store，但这次页面只用到其中两个。如果定义的那一刻就把它们全部实例化，剩下八个从没被用到的 store 也进了内存，更糟的是打包器没法把它们裁掉，体积无谓变大。使用者只想"定义好、需要时再拿"，根本不想操心初始化时机。

更棘手的是 store 之间的相互引用。A 的装配过程里要用到 B，B 又要用到 A。不管先造哪一个都卡住：先造 A，A 装配到一半要 B，可 B 还没造；先造 B 同理。要是老实地"A 装配时去造 B、B 装配时又回头造 A"，直接栈溢出。这是个典型的鸡生蛋死结。

这套机制就是同时解这两个矛盾：用按需创建避免无谓实例化，用一种特殊的装配顺序破解循环依赖。

## 2. 核心思想

把"造一个 store"拆成先后两件事：先在容器的注册表里给它挂上门牌号，拿到一个稳定的对象引用；再回过头慢慢把状态、计算属性、动作装配进这个引用里。门牌号一旦挂上，谁按这个号来取，拿到的都是同一扇门——哪怕门里的家具还没搬齐。

配合"工厂延迟到首次调用才触发整个过程"，就既不提前实例化、又能在装配链路里随时拿到那个已经挂了号的半成品引用。

一句话：**先登记半成品，再懒装配它的内容**——靠"同一个引用、分两步填满"破解循环。

## 3. 心智模型

容器身上挂着一张实例注册表，就是一个按 id 存取的映射。`defineStore` 调用时只做一件事：记下"配方"（这个 store 的 id 和装配函数），返回一个工厂函数，不创建任何实例。

等到工厂第一次被调用，装配流程才启动，分这么几步：

1. 先查注册表。命中就直接返回那个已存在的实例，查不到才往下走。
2. 造一个半成品：只有改状态、订阅、销毁这些内置骨架，还没有用户写的任何字段。
3. 立刻把半成品按 id 写进注册表。这一步是破解循环的关键，先记住。
4. 在容器托管的作用域里运行装配函数，产出用户的状态、计算属性、动作。
5. 装配期间如果引用了别的 store，就去调它的工厂。对方哪怕也正在装配、只到半成品，注册表里也已经有了它的引用，递归在这一层停下，不会无限套娃。
6. 装配产出的字段原地合并进那个已经登记的半成品。注意是"原地"——往同一个对象上塞属性，引用始终不变，注册表里的记录也无需更新。半成品就此填满，此后所有工厂调用都命中注册表，返回同一个填满了的实例。

全程最关键的不变量是：注册表里那个引用，从登记的那一刻起就不变了。它只是从一个空壳子，逐步被填满。

## 4. 关键权衡

### 先登记半成品，再运行装配

这条权衡把"半成品写进注册表"这一步，挪到了运行装配函数之前，而不是"装配完了再把完整实例存进去"。

换来的是循环安全。A 装配到一半去拿 B，触发了 B 的创建；B 装配到一半又回头拿 A，此刻 A 在注册表里已经有了，虽然只是半成品，B 直接拿到这个引用就返回，递归当场终止。要是改成"装配完才登记"，B 回头拿 A 时 A 还没造好，只能再触发一次 A 的创建，A 又去拿 B，死循环就起来了。

代价是：装配期间被别人引用到的那个 store 还是个半成品，用户写的字段一个都没装配上去。所以跨 store 取值必须懒——只能把"读对方的某个字段"这件事推迟到计算属性或动作真正被调用的时候，而不能在装配函数的顶层就同步去读。在装配顶层同步读 `otherStore.someField`，拿到的是 `undefined`，因为那一刻 `someField` 还没合并进去。本节的演示会把这个 `undefined` 实打实地演出来。

这条权衡化解的本质矛盾，是"循环依赖"和"实例化必须有先后顺序"之间的死结：只要双方互相需要、且各自一开工就要对方在场，任何线性的初始化顺序都安排不下来。把"拿到引用"和"填满内容"拆开，"谁先谁后"就不再重要——先开工的那个，总能先拿到对方的空壳子引用，等内容各自补齐，引用自然就指向了完整对象。这套解法骨架在任何需要"互相引用 + 延迟初始化"的场景里都认得出来。

### 定义阶段只造工厂，首次调用才实例化

这条权衡让 `defineStore` 只返回一个工厂函数，把真正的实例化推迟到工厂第一次被调用。

换来的是按需创建。从没被调用的 store 不会进内存，配合打包器对工厂函数的"无副作用"标注，未使用的 store 能被整体裁掉，产物体积只包含真正用到的部分。

代价是实例化的时机交给了调用方：调用方必须能提供或注入一个容器，工厂才知道往哪个注册表里存。真实代码里这个容器由上一章的活跃指针负责找到（组件内走依赖注入、组件外走那个模块级变量），所以使用者几乎感知不到；可一旦在没有任何容器在场的情况下调用工厂，就拿不到实例。这条权衡背后是"声明即就绪"和"资源延迟分配"的拉扯：定义时立刻就绪当然省心，可那意味着所有声明都得在启动期付出实例化的代价；把就绪推迟到首次调用，是用"调用方需自带容器"这个小责任，换掉了"启动期无差别实例化"的大包袱。

> 关于"按 id 缓存的单例注册表"在服务端渲染下的跨请求污染风险——实例生命周期绑在容器上，容器若跨请求复用就会串数据。这恰是上一章活跃指针那条权衡的同源问题，渲染结束后必须主动清空，这里不重复展开。

## 5. 最小原理演示

下面这段几十行的 JS，去掉了响应式、副作用作用域、插件、热更新、Options 与 Setup 两种风格的分流等一切旁路，只演透一件事：先登记半成品、再懒装配、循环在注册表层终止、最后原地合并填满。真实代码里工厂内部"怎么找到 pinia"由上一章的活跃指针负责，这里直接把 pinia 当参数传进来，不展开。

```js
function createMiniPinia() {
  // 容器身上挂一张实例注册表：id -> store
  return { _s: new Map() }
}

function defineStore(id, setup) {
  // 定义阶段：只记下配方，返回工厂，不创建实例
  function useStore(pinia) {
    // 懒门槛：注册表里没有才创建
    if (!pinia._s.has(id)) {
      createSetupStore(id, setup, pinia)
    }
    // 不管刚创建还是早就有，统一从注册表取回单例
    return pinia._s.get(id)
  }
  useStore.$id = id
  return useStore
}

function createSetupStore(id, setup, pinia) {
  // 造半成品：此刻只有骨架，没有用户的任何字段
  const half = { $id: id }
  // 先登记：引用在这一刻固定下来，破解循环就靠这一步
  pinia._s.set(id, half)
  console.log(`[${id}] 半成品已登记`)
  // 运行装配：此刻去拿别的 store，对方哪怕也是半成品，也能从注册表拿到同一个引用
  const produced = setup()
  // 原地合并：往同一个对象塞属性，引用不变，注册表记录也无需更新
  Object.assign(half, produced)
  console.log(`[${id}] 装配完成`)
  return half
}
```

演透循环破解：定义两个互相引用的 store，A 的装配里调 B、B 的装配里调 A，然后首次调用 A。

```js
const pinia = createMiniPinia()

const useA = defineStore('A', () => {
  console.log('  A 装配：准备引用 B')
  const b = useB(pinia)              // A 装配里引用 B
  return { aCount: 1, aSeeB: () => b.bCount }
})

const useB = defineStore('B', () => {
  console.log('  B 装配：准备引用 A')
  const a = useA(pinia)              // B 装配里引用 A，此刻 A 还是半成品
  return { bCount: 2, bSeeA: () => a.aCount }
})

console.log('--- 首次调用 useA ---')
const a = useA(pinia)

console.log('a.aCount   =', a.aCount)
console.log('a.aSeeB()  =', a.aSeeB())                       // A 能完整看到 B
console.log('B.bSeeA()  =', pinia._s.get('B').bSeeA())       // B 也能完整看到 A
console.log('再次 useA 命中注册表：', useA(pinia) === a)
console.log('再次 useB 命中注册表：', useB(pinia) === pinia._s.get('B'))
```

运行后整条轨迹长这样：

```text
--- 首次调用 useA ---
[A] 半成品已登记
  A 装配：准备引用 B
[B] 半成品已登记
  B 装配：准备引用 A
[B] 装配完成
[A] 装配完成
a.aCount   = 1
a.aSeeB()  = 2
B.bSeeA()  = 1
再次 useA 命中注册表： true
再次 useB 命中注册表： true
```

重点看 B 装配里那行 `useA(pinia)`：它没有再触发一次 `[A] 半成品已登记`，因为 A 早就登记过了，注册表直接把那个半成品引用还给了 B，递归就在这一层停下。再看最后的验证：`aSeeB()` 拿到 2，`bSeeA()` 拿到 1，说明 A 和 B 各自都持有了对方的完整实例。这之所以成立，是因为 `a`、`b` 两个闭包变量抓住的是对方的引用，而原地合并是在同一个对象上发生的——B 当初拿到的虽然是 A 的空壳子，可等它真正调用 `a.aCount` 的时候，壳子早被填满了。

演透代价：跨 store 取值懒不懒，结果截然不同。下面这对 store，Y 在装配顶层同步读 X 的字段，而 X 用方法把读取推迟到调用时。

```js
const useX = defineStore('X', () => {
  console.log('  X 装配：准备引用 Y')
  const y = useY(pinia)              // X 装配里引用 Y，触发 Y 的创建
  return { x: 1, seeY: () => y.y }   // 正确：把读 y.y 推迟到方法被调用时
})

const useY = defineStore('Y', () => {
  console.log('  Y 装配：准备引用 X')
  const x = useX(pinia)              // X 此刻还在装配中，注册表里只有半成品 {$id:'X'}
  const snapshot = x.x               // 反面：装配顶层同步读，x.x 还是 undefined
  console.log('  Y 同步读 X.x =', snapshot)
  return { y: 2, snapshot }          // snapshot 被永久冻结成 undefined
})

console.log('--- 首次调用 useX（触发 X 与 Y 的互相引用链）---')
const x = useX(pinia)
console.log('x.seeY()      =', x.seeY())             // 推迟到调用时，Y 已填满，读得到
console.log('Y 的 snapshot =', useY(pinia).snapshot) // 装配期偷跑，拿到空
```

运行结果：

```text
--- 首次调用 useX（触发 X 与 Y 的互相引用链）---
[X] 半成品已登记
  X 装配：准备引用 Y
[Y] 半成品已登记
  Y 装配：准备引用 X
  Y 同步读 X.x = undefined
[Y] 装配完成
[X] 装配完成
x.seeY()      = 2
Y 的 snapshot = undefined
```

X 和 Y 同样互相引用、同样经过了半成品登记，但 Y 在装配顶层同步读 `x.x` 的那一刻，X 还是 `{$id:'X'}` 这个空壳子，`x` 字段压根没合并进去，`snapshot` 于是被冻成 `undefined`，再也不会变。反观 X 的 `seeY()`，它把读取推迟到自己被调用的那一刻，那时 Y 早已填满，自然读得到 2。拿到对方的引用可以很早，但读对方装配产出的字段，必须等装配链路全部走完——这就是"跨 store 取值必须懒"这条代价的实打实后果。

## 6. 执行轨迹

把上面 A、B 那次调用放慢，盯住注册表 `_s` 这个映射在每个关键节点的样子，循环是怎么断的就一目了然：

| 时刻 | 正在发生 | 注册表 `_s` 的内容 |
| --- | --- | --- |
| 调用 useA | 查不到 A，开始造 A | `{}` |
| A 半成品登记 | 写入空壳子 A | `{ A: {$id:'A'} }` |
| 运行 A 装配 | A 装配函数里调 useB | `{ A: {$id:'A'} }` |
| B 半成品登记 | 查不到 B，造 B，写入空壳子 | `{ A: {$id:'A'}, B: {$id:'B'} }` |
| 运行 B 装配 | B 装配函数里调 useA | 同上 |
| useA 命中注册表 | A 已在表里，直接返回半成品引用，递归终止 | 同上，未新增 |
| B 装配完成 | 装配结果原地合并进 B | `{ A: {$id:'A'}, B: {$id:'B', bCount:2, bSeeA} }` |
| A 装配完成 | 装配结果原地合并进 A | `{ A: {$id:'A', aCount:1, aSeeB}, B: {…已填满} }` |

关键就是"运行 B 装配 → useA 命中注册表"这一行：B 想要的 A 此刻只是空壳子，但注册表有求必应、原样返回，递归就此打住。等各自装配完成、原地合并之后，壳子都成了完整实例，而注册表里的引用从头到尾没换过——这正是再次调用任何工厂都返回同一对象的原因。

## 7. 教学简化说明

本章演示故意省略了这些：响应式（真实 store 用 reactive 包裹、状态同步进集中状态树）、副作用作用域的回收、插件管线、热更新分支、Options 与 Setup 两种风格的运行时分流、订阅与批量合并、devtools 接入，以及工厂内部解析容器的完整顺序（这一步是上一章活跃指针的职责）。这里只保留"注册表 + 工厂 + 半成品登记 + 原地合并"这条与框架无关的纯逻辑骨架。

## 8. 小结

defineStore 把"造 store"拆成了挂号和填空两步：工厂第一次被调用，先把一个半成品写进注册表固定引用，再去运行装配、把结果原地合并进同一个对象。两个 store 不管怎么互相引用，递归都会在"对方已挂号"这一层停下，循环就这么破了；代价是装配期间大家手里捏着的都可能是空壳子，所以跨 store 取值必须懒。下一章会走进装配函数内部，看 setup 返回的那么多字段，是怎么被自动归类成状态、计算属性和动作的。
