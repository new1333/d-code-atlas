# URL 分段编码与查询串

> 本章属于 primitive 层。前置：无（全书地基章之一）。
> 学完你能：用一句话讲清「URL 编码为什么必须按段细分、查询串为什么要有两种空值」。

## 1. 为什么需要它（设计动机）

整本讲 Vue Router 的书为什么从「URL 编码」开始？因为路由器这个程序，本质就是不停做两件事：把内存里的「路径段、路径参数、查询键值、哈希」拼成 URL 字符串推进浏览器地址栏，再把地址栏里的 URL 字符串拆回来还原成内存里那几段。这一推一拉贯穿了后续每一章：匹配、导航、守卫、恢复滚动，全都默认「URL 这个东西已经被搞定了」。所以本章是全书的地基，先把「URL 怎么安全地编/解」一次讲透，后续章节只看自己的新侧面。

听起来只是 `+` 拼接和 `split` 切分，但只要上手写就会撞上两个挥之不去的麻烦。

第一个麻烦是「我拼出的串」和「地址栏实际显示的串」对不上。你按标准把空格编成 `%20`、把方括号编成 `%5B%5D`，浏览器一看：这俩我本来就留着不编，反手把你写的还原回去；又或者你在路径里写了个 `?`，浏览器要判断这是「路径里的字面量问号」还是「查询串的起始符」，结果往往和你想的不一样。来回几次，调试器里的 URL 和代码里拼出来的 URL 像两个不同的东西，浏览器每次升级行为还可能微调。

第二个麻烦出在查询串。`?darkMode` 这种「只有键、没有值」的标志型参数，和「压根不传 darkMode」语义上完全不同：前者是「我要开」，后者是「我没意见」。可如果用普通字符串类型表示查询值，你拿什么表达「这个键存在、但没有值」？空字符串、`null`、`undefined` 三个候选各代表什么、序列化时分别变成什么样的 URL 片段，全靠开发者口耳相传。

这两件麻烦都不是「再写一个工具函数」能糊弄过去的，需要从设计上专门处理。

## 2. 核心思想

**把 URL 的领域规则（各段语法不同）显式地带进编码层，让每段都有自己的字符策略，并贴着浏览器的实际行为走。**

这句话的分量在于它放弃了「找一个完美编码函数」这条看似更优雅的路。代码里没有 `universalEncode`，只有 `encodePath / encodeParam / encodeQueryValue / encodeQueryKey / encodeHash` 五个函数，每个都为自己负责的那一小段 URL 定制「保留谁、编码谁」。换句话说，路由器把「这是个什么段」这个上下文信息，从调用方一路带进了编码实现里。

## 3. 心智模型

可以把 URL 想成一份多栏表格：路径栏、参数栏、查询键栏、查询值栏、哈希栏，每一栏对同一个标点的态度可能不一样。比如花括号 `{` 在路径栏里要编成百分号串，到了哈希栏却被浏览器原样保留。

一段文本从「原始值」变成「可以安全贴进 URL 的片段」，要经过三步：

1. **过宽松基底**：用平台 `encodeURI` 把非 ASCII 字符和通用不安全字符编掉，得到起点串。
2. **还原基底误编、但本段该保留的符号**：比如方括号、竖线这些浏览器实际不编码、但 `encodeURI` 会顺手编掉的的东西，要在这里还原回来。
3. **补编码会破坏本段语法的符号**：路径段里的 `#` `?` 会让解析器误以为是「哈希」「查询开始」，必须补编成 `%23` `%3F`；查询值里的 `&` 会切断键值对，必须编成 `%26`；查询键里的 `=` 会混淆 `键=值` 结构，必须编成 `%3D`；路径参数里的 `/` 会让参数穿越段边界，必须编成 `%2F`。

三步之后产出的字符串就是「浏览器地址栏会原样显示的样子」。

解码走反方向，但有一个关键设计：**容错优先于严格**。`decodeURIComponent` 一旦遇到畸形的百分号串会抛异常，路由器选择 catch 住、退回原文，不让一个坏字符把整个导航打断。

查询串走另一条流水线，因为它的「存在性」本身就是信息：

- **解析**（URL → 对象）：按 `&` 切段，每段先把 `+` 还原成空格，按第一个 `=` 拆键值；没有 `=` 的段记为 `null`（标志型空值）；同名键累积成数组。
- **序列化**（对象 → URL）：`null` 只输出键（无 `=`）、`undefined` 整个跳过、有值则 `键=值`。

## 4. 关键权衡

### 按段细分字符策略，而不是一刀切编码

路由器为每一段单独写一个编码函数：路径里编 `#` `?`、查询值里编 `#` `&`、查询键再额外编 `=`、路径参数再额外编 `/`、哈希段则把花括号等浏览器实际保留的符号还原。

换来的是各段都贴合浏览器的实际行为，生成的 URL 可读、且不会被浏览器二次改写。代价是要维护一组分层编码函数，以及多条「先编码、再还原」的替换链：`encodeParam` 内部先调 `encodePath`、`encodePath` 内部先调 `commonEncode`，每一层都叠加一组正则替换，顺序敏感、不直观。

这条取舍化解的是**通用性与精确性**的矛盾。一个函数搞定一切当然优雅，但 URL 不是「一个东西」，它是几个语义不同的段拼起来的复合体，通用性越高、对每一段就越不精确。

### 对齐浏览器实际行为，而不是 RFC 标准

代码注释里写着：浏览器在做宽松编码时本就不编码 `!'()*` 等字符，且不同浏览器在哈希段对 `"<>{}` 的处理还不一致。作者选择观察浏览器实际怎么干、就怎么写编码，而不是严格按 RFC 3986 来。

换来的是「编码结果与地址栏一致、跨浏览器可预测」这个对路由器来说生死攸关的性质：路由器生成的 URL 是要给人看到、复制粘贴、来回分享的，地址栏就是它的事实裁判。代价是与严格标准工具的互操作不可预期，必须靠注释维护一张「各浏览器差异表」。

本质上，路由器在这里选了**事实**这一边而非**规范**那一边。RFC 给的是规则，浏览器给的是事实，两边不一致时跟着事实走，因为用户在地址栏里看到的，是事实。

### 宽松基底 + 按段补丁，而不是从零实现

作者没有自己写一个完整的百分号编码器，而是直接拿平台的 `encodeURI` 当基底，再在上面按段做「还原误编 + 补编码漏编」的修正。

换来的是实现极短：核心 `commonEncode` 只有 4 行，非 ASCII 处理完全复用平台能力。代价是写法和直觉相反：不是「挑出该编码的字符编掉」，而是「先把所有可疑的都编码、再把不该编码的百分号串还原回来」，读代码的人容易在「为什么这里在 unencode」这一步卡住，新增字符规则时也容易漏改顺序。

这是**实现经济性**与**可读性**之间的取舍。从零写编码器读起来直白但要几百行、还要自己处理 UTF-8 字节序列；站在平台函数肩膀上只要几十行，代价是读起来像在拆别人干完的活。作者选了短。

### 用两种空值二分查询参数的存在语义

查询参数的「存在性」其实有两种：`?flag`（键存在、但没值）和「干脆不出现这个键」。路由器选择把这两种语义都搬进类型层：`null` 表示「键存在但无值」（序列化只输出键、无 `=`），`undefined` 表示「完全省略」（序列化整个跳过）。

换来的是用类型精确描述两种 URL 形态，序列化和解析双向无损。代价是序列化与归一化逻辑因为多了一个空值判断而分支增多，调用方必须理解两种空值的细微差别：`null` 和 `undefined` 在 JavaScript 里本来就长得像，这里却要它们承载完全不同的语义。

如果只用一种空值（比如只用 `null`），那 `?flag` 和「不出现」就没办法在同一个对象里共存；如果都用空字符串，那 `?flag=` 和 `?flag` 又会被混淆。两个对立需求都逼着路由器把空值拆成两种，代价是把这份「哪个是哪个」的认知负担转嫁给了调用方。

## 5. 最小原理演示

下面这段几十行的代码只演两件事：按段细分字符策略、以及两种空值的二分。它不是工程完整版，省略了哈希段对花括号、`^` 的还原规则，省略了数组值与归一化等细节。

```ts
// 每个段独立的「补编码集」：同一字符在不同段命运不同
const SEGMENT_EXTRA_ENCODE = {
  path:       /[#?]/g,
  param:      /[\/#?]/g,
  queryValue: /#&/g,
  queryKey:   /#&=/g,
}

// 按段编码：先过宽松基底、再按本段补编码
function segEncode(
  text: string | number | null | undefined,
  segment: keyof typeof SEGMENT_EXTRA_ENCODE,
): string {
  if (text == null) return ''
  // 宽松基底：交给平台 encodeURI 处理非 ASCII 与通用不安全字符
  let s = encodeURI(String(text))
  // 按本段规则，把破坏段语法的字符编成百分号串
  s = s.replace(
    SEGMENT_EXTRA_ENCODE[segment],
    m => '%' + m.charCodeAt(0).toString(16).toUpperCase(),
  )
  return s
}

// 查询值段的特殊处理：真实加号先编、空格编成加号
// 真实 + 编成 %2B，避免和「空格编成的 +」混淆；这是查询段独有，路径段无此处理
function encodeQueryValue(text: string | number | null | undefined): string {
  return segEncode(text, 'queryValue')
    .replace(/\+/g, '%2B')
    .replace(/%20/g, '+')
}

// 序列化查询对象：null 只输出键（无 =）、undefined 完全跳过、有值则 键=值
function stringifyQuery(query: Record<string, string | null | undefined>): string {
  let search = ''
  for (const key of Object.keys(query)) {
    const value = query[key]
    if (value == null) {
      // null 和 undefined 在这里分家
      if (value !== undefined) {
        search += (search.length ? '&' : '') + segEncode(key, 'queryKey')
      }
      continue
    }
    search +=
      (search.length ? '&' : '') +
      segEncode(key, 'queryKey') +
      '=' +
      encodeQueryValue(value)
  }
  return search
}

// 反向：URL 查询串 → 对象，无 = 的段记为 null
function parseQuery(search: string): Record<string, string | null> {
  const query: Record<string, string | null> = {}
  if (!search) return query
  for (const segment of search.split('&')) {
    const restored = segment.replace(/\+/g, ' ')
    const eq = restored.indexOf('=')
    const key = decodeURIComponent(eq < 0 ? restored : restored.slice(0, eq))
    query[key] = eq < 0 ? null : decodeURIComponent(restored.slice(eq + 1))
  }
  return query
}
```

注意 `stringifyQuery` 里 `value == null` 这一行同时拦住了 `null` 和 `undefined`，紧接着用 `value !== undefined` 把两者分家：这是把两种空值塞进一个 `==` 的写法，紧凑但读起来要慢半拍。

## 6. 执行轨迹

拿三个具体输入走一遍。

**输入 A：路径段文本 `a b?c#d`，过 `segEncode(text, 'path')`。**

第一步宽松基底 `encodeURI('a b?c#d')` 得到 `a%20b?c#d`：空格被编成 `%20`，但 `?` 和 `#` 因为是 URL 通用分隔符被 `encodeURI` 保留。

第二步按 path 段规则补编码 `?` 和 `#`，`?` 变成 `%3F`、`#` 变成 `%23`，最终结果是 `a%20b%3Fc%23d`。这个串贴进路径里，浏览器解析时就不会误以为是「查询开始」「哈希开始」。

**输入 B：查询值 `x+y z`，过 `encodeQueryValue`。**

先过 `segEncode('x+y z', 'queryValue')`：基底 `encodeURI` 得 `x+y%20z`（`+` 是 URL 安全字符、保留，空格被编成 `%20`）；queryValue 段的补编码规则是 `#&`，这里没有命中。

接着两步特殊处理：先把真实 `+` 编成 `%2B`，得 `x%2By%20z`；再把 `%20` 换成 `+`，得 `x%2By+z`。

注意顺序很关键：如果反过来，先把 `%20` 换成 `+`，再把所有 `+` 编成 `%2B`，那原来真实的 `+` 和原本的空格就都被编成 `%2B` 了，信息丢失。最终 URL 里看到 `x%2By+z`，`%2B` 是字面量加号、`+` 是空格，解析时先把 `+` 还原成空格、再把 `%2B` 解码回 `+`，双向无损。

**输入 C：查询对象 `{ flag: null, gone: undefined, q: 'a&b' }`，过 `stringifyQuery`。**

- `flag: null` → 命中 `value == null` 分支，`value !== undefined` 为真，只输出键 → `flag`
- `gone: undefined` → 命中 `value == null` 分支，但 `value !== undefined` 为假，整个跳过 → 不输出任何片段
- `q: 'a&b'` → 正常走 `键=值`，值里的 `&` 被 `encodeQueryValue` 补编码成 `%26` → `q=a%26b`

最终拼成 `flag&q=a%26b`。

反向解析 `flag&q=a%26b`：按 `&` 切成 `['flag', 'q=a%26b']`；`flag` 没有 `=`，记成 `{ flag: null }`；`q=a%26b` 拆出键 `q`、值 `a&b`。结果 `{ flag: null, q: 'a&b' }`，与原输入语义一致。`gone` 在反向结果里也不出现，和原输入里被整个省略的状态完全对应。

## 7. 教学简化说明

上面的演示故意省略了这些：哈希段对花括号、`^` 等符号的还原规则；路径参数段叠在路径段之上再编 `/` 的层级实现；查询键里等号编码的细节；数组值的累积与归一化；解码失败时的诊断码报告；以及查询对象用普通对象字面量（而非 `Object.create(null)`）带来的原型链边界——这是源码里已知的待改进项，TODO 标记在下一个 major 版本处理。

## 8. 小结

URL 在路由器手里不是一个字符串，而是五段各有字符规则的复合体：按段细分、贴着浏览器实际行为走，是兼顾可读性与可预测性的唯一办法；查询参数的存在性本身承载信息，所以需要两种空值把「有键无值」和「干脆省略」分开。
