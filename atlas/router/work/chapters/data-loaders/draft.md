# 导航期数据加载器

> 本章属于 system 层。前置：Router 核心与导航主循环、导航守卫管线。
> 学完你能讲清：为什么数据请求要绑在导航而不是组件挂载上，以及它为此付出的代价。

## 1. 为什么需要它

上一章讲的是构建期——怎么把一坨文件按约定编成一张路由表。这一章把视线拉回运行时：导航发生了，但页面要显示的数据还没到。

最朴素的写法是把数据请求塞进组件的 `onMounted`：路由切了→新组件挂载→发请求→等响应→画面跳一下。用户先看到新页面的骨架与转圈，几百毫秒后数据回来，画面再跳一次。如果页面上多个组件各自发请求、各自到达，画面会闪好几下。

更头疼的是连点导航。用户从首页跳到 `/users/1`，请求还没回来又改跳 `/users/2`。第二条快、先返回，画面正确显示 2 号用户；可第一条慢请求之后才到，把 1 号用户的旧数据盖回了已经显示 2 号的页面上。

两个问题合起来指向同一件事：**数据请求本质上是「为这次导航服务」的，可传统写法把它绑在了「组件挂载」这个错误的生命周期上**——组件挂载晚于导航、且各组件各自为政，可见性散乱，没有一个统一的提交点。

## 2. 核心思想

把数据获取从组件树挪到导航管线里：让请求在导航解析阶段就并行跑起来，用「**先暂存、等导航确认后统一提交**」把数据的可见性与导航的生命周期绑死。

换句话说，数据不是组件挂载的副产物，而是导航的副产物——导航完成的那一刻，本页所有数据就应该已经就绪、且原子地一起出现。

## 3. 心智模型

整套机制挂在三个守卫 + 一个跨导航复用的条目缓存上。

**条目缓存**：每个加载器函数（是的，函数对象本身）对应一个跨导航复用的条目，里面有三个关键字段：

- `data`：组件真正能读到的可见数据；
- `staged`：暂存区，加载器刚跑完时把结果写在这里，组件看不到；
- `pendingNav`：当前在飞的导航标识。

**三段时序**——这里只看本章新接的那道缝。守卫串联的严格顺序、`next` 回调 promise 化、可取消异步状态机的取消检查，都是前置章已经讲透的主题，本章不重演；我们只看「解析前 → 导航确认后」这道天然接缝是怎么被当成「并行加载 → 统一提交」的挂载点用的。

1. **导航开始**（beforeEach）：建一个中止信号挂在本次导航上；同时宣告「当前待定导航」就是这次，旧待定导航的中止信号随即触发。
2. **解析前**（beforeResolve）：收集本次路由涉及的全部加载器（来自路由元信息和组件具名导出的 Symbol 鸭子判定），把中止信号交给它们并行启动；加载器跑完不写 `data`、只写 `staged`。
3. **导航确认后**（afterEach）：所有非懒加载器都完成、导航放行，每个加载器把 `staged` 提交进 `data`。因为提交统一发生，组件看到的不是「数据一个个到位」，而是「同一瞬间全部到位」。

中止信号、`pendingNav` 标识、暂存区，三件东西合起来构成了下面要讲的几条关键权衡。

## 4. 关键权衡

### 把加载挂在导航守卫上、而不是组件树或 Suspense

这是整套设计最根本的取舍。

**选择**：把数据获取的时机从「组件挂载」前移到「导航解析阶段」，让它跟守卫跑在同一个时序里。

**换来**：组件挂载时数据已就绪、多个加载器天然并行、且拥有一个统一的提交点（导航确认）——这些都是组件树给不了的。

**代价**：加载器必须和路由强耦合（这套插件必须挂在路由上），而且本来可以靠 Suspense 声明式 async 组件解决的简洁性没了，得自己接管暂存、提交、取消、父子同步的整套生命周期。

这里要专门说一下为什么不是 Suspense。Suspense 把异步绑在组件树**渲染**上：它在组件开始渲染之后才等待，没法在组件挂载前就并行启动；而且它没有跨多个并行加载器的统一提交点，每个 async 子组件各自 settle。换不来「导航即数据就绪」+「原子可见」这两条核心语义。这是一条「换不来、所以不走」的刻意绕开。

**本质矛盾**：数据的导航生命周期与组件挂载的生命周期，本来就是两条不同的时间线——硬要绑在一起就会闪烁、回滚；本机制把数据从组件挂载那条线抽出来，绑到导航那条线。

### 暂存→提交两阶段 + 「我这次导航是否仍是最新」的身份校验

第一条权衡解决了「数据从哪里来」；这一条解决「数据什么时候可见、过期数据怎么挡住」。

**选择**：加载器跑完不直接写 `data`，先写 `staged`；只有导航真正确认那一刻（所有守卫过、未被新导航取消），才把 `staged` 一次性提交进 `data`。同时每个条目维护一个 `pendingNav` 标识，加载器写 `staged` 之前先问一句「我还在为最新导航服务吗」，不是就丢弃。

**换来**：

- **原子可见**——多个并行加载器到达时间不一，但可见性统一压到「确认后」那一刻，组件看到的总是「一起到位」；
- **防回滚**——连点导航时，第一条慢请求晚到，但因为它的 `pendingNav` 已不是最新，结果直接丢弃，不会盖回已显示的新数据。

**代价**：每个条目多一对暂存字段（`staged` / `stagedError`）和一个待定导航槽位（`pendingNav` / `pendingTo`），提交时机也得拆成「立即」与「加载后」两条分支（前者用于手动 reload 这类非导航场景，后者是默认），状态机变复杂。一个 `STAGED_NO_VALUE` Symbol 哨兵也得专门发明，因为 `=== undefined` 区分不出「暂存了 undefined」和「根本没暂存」。

**本质矛盾**：异步加载的完成时机不可控（请求什么时候回来由网络决定），但用户对「画面的确定性」有强期待（一次跳转就该看到一整页一致的数据）。两阶段提交把这两件事剥开——加载随便什么时候完成都不影响可见性，可见性只跟导航的生命周期绑定。

### 「对象即 Promise」的双面返回值

这条权衡藏得最深，但最能体现设计意图。

**选择**：加载器的返回值是一个被「把结果字段拍到一个 promise 上」拼出来的对象——它既是个 promise（可以 `await`），又挂着 `data` / `error` / `isLoading` / `reload` 这些响应式字段。

**换来**：同一个返回值在不同语境里以不同姿态出现：

- 在组件 `setup` 里调，解构出 `data` 字段，做响应式渲染；
- 在另一个加载器体里 `await` 它，拿到父加载器的原始数据——子加载器依赖父加载器就这么自然成立。

**代价**：类型层得发明「既是对象又是 Promise」的交叉类型（`_PromiseMerged = RawType & Promise<T>`）；错误处理也得分流——只有「作为嵌套被 await」时才把错误向上 reject，作为顶层在 setup 里调时反而吞掉错误（错误已经进了 `error` 字段，再 reject 会变成未捕获的 promise 拒绝）。

**本质矛盾**：同一份数据有两个身份——「给模板用的响应式状态」和「给其他加载器用的可等待值」。硬拆成两个 API 会割裂心智（同一个东西在两个地方用法完全不同），所以干脆合二为一。

## 5. 最小原理演示

下面这段几十行代码演透前两条权衡的核心——暂存隔离可见性 + 身份校验防回滚 + 并行启动 + 统一提交。错误分类、嵌套加载器的父子同步、SSR、类型层全部省略。

```ts
// 一个条目 = 一份跨导航复用的状态
function makeEntry() {
  return {
    data: undefined,        // 组件真正能看到的可见数据
    staged: null,           // 暂存区——加载器刚跑完写这里，组件看不到
    hasStaged: false,       // 区分「暂存了 null」与「没暂存」
    pendingNav: null,       // 当前在飞的导航标识
  }
}

// 导航开始 → 解析前 → 确认后 的极简三段
async function navigate(navId, entries, fetch) {
  // 抢占：宣告最新导航。旧待定导航的慢请求之后回来时，
  // 会因为身份校验不通过而被丢弃
  for (const e of entries) e.pendingNav = navId

  // 解析前：所有条目并行启动；任何一条慢请求期间都可能已被新导航取代
  await Promise.all(entries.map(async e => {
    const d = await fetch(navId)
    // 身份校验：我还在为最新导航服务吗？不是就丢弃，绝不回写暂存
    if (e.pendingNav !== navId) return
    e.staged = d
    e.hasStaged = true
  }))

  // 确认后：统一提交——所有暂存一次性写进可见数据
  for (const e of entries) {
    if (e.hasStaged) {
      e.data = e.staged
      e.hasStaged = false
    }
  }
}

// 连点导航演示：A 慢、B 快
const a = makeEntry()
const b = makeEntry()
const slowFetch = () => new Promise(r => setTimeout(() => r('A 的数据'), 100))
const fastFetch = () => new Promise(r => setTimeout(() => r('B 的数据'), 10))

navigate('A', [a, b], slowFetch)              // 不 await，让它在飞
await navigate('B', [a, b], fastFetch)        // B 先完成、先提交
// 此时 a.data 与 b.data 都是 'B 的数据'

await new Promise(r => setTimeout(r, 200))    // 等 A 的慢请求回来
// A 因 pendingNav 已是 'B'，结果被丢弃；a.data 仍是 'B 的数据'，没有被回滚
console.log(a.data)                            // → 'B 的数据'
```

三个细节对回上面的原理：

- `pendingNav` 抢占那一行演的是「身份校验防回滚」——加载器跑完先问自己有没有过气；
- `staged` 字段全程不给组件看，演的是「暂存隔离可见性」；
- 最后那个 `for` 循环统一提交，演的是「原子可见」——所有暂存一起变成可见数据。

中止信号（让用户在请求里取消）省略了，它只在外部用户函数里需要、对核心时序没有影响。

## 6. 执行轨迹

输入：用户从首页跳到 `/users/1`，目标页有两个并行、互不依赖的加载器——一个取用户信息、一个取文章列表。

| 时刻 | 系统状态 | 组件看到 |
|---|---|---|
| 用户点击 | 触发 `router.push('/users/1')` | 仍是首页 |
| 导航开始 | 建中止信号；置待定导航 = `/users/1`；旧待定（首页）的中止信号触发 | 仍是首页 |
| 解析前 | 收集两个加载器，并行启动；各自的请求在飞 | 仍是首页 |
| 用户信息先到 | 身份校验通过（仍是最新），写入 `staged`；**不写 `data`** | 仍是首页 |
| 文章列表到 | 身份校验通过，写入 `staged`；**不写 `data`** | 仍是首页 |
| 所有非懒完成 | 导航放行 | 仍是首页 |
| 导航确认后 | 两个条目把 `staged` 统一提交进 `data` | **同时**显示新用户信息和文章列表 |

整个过程中组件只经历一次「画面更新」，就在导航确认那一刻。

连点场景的对比：用户在「用户信息先到」之后、还没确认就改跳 `/users/2`。此时 `pendingNav` 被改成 `/users/2`，第一条导航的中止信号触发；当 `/users/1` 的慢文章列表请求终于回来时，加载器一查 `pendingNav` 已不是 `/users/1`，结果丢弃；最终用户看到的是 `/users/2` 的全套数据，没有被 `/users/1` 的迟到响应盖回。

## 7. 教学简化说明

本章演示故意省略了：

- **嵌套加载器的父子同步**——靠一份模块级全局上下文，加载器 `await` 另一个加载器时自动建立父子依赖、父提交时递归提交子；
- **错误分类与 `errors` 选项**——本地与全局两层「期望错误」判定，命中的错误不中止导航；
- **中止信号传入用户函数**——`AbortController` + `signal.throwIfAborted()`，让长请求能真正取消；
- **SSR 首屏同步注入**——服务端把数据序列化、客户端首次渲染时同步写入并短路本次 load；
- **「对象即 Promise」的类型层**——`_PromiseMerged = RawType & Promise<T>` 的交叉类型；
- **高阶实现里用代理追踪加载器读了路由的哪些字段**——按需重取（只读了 `id` 就只在 `id` 变化时重取，query 变了但加载器没读 query 就不重取）。

这些不展开，不是因为不重要，是因为它们都建在上面那套「暂存→提交 + 身份校验」的地基上。

## 8. 小结

数据加载器把数据获取从「组件挂载的副产物」改写成「导航的副产物」——这一笔挪位，让暂存区、提交时机、身份校验成为必要的代价，换来的是「导航完成即数据就绪、原子可见、连点不被回滚」这三条核心语义。
