# 路径模式编译与优先级评分

> 本章属于 primitive 层。前置：无（全书地基章之一）。
> 学完你能：用一句话讲清「为什么路由匹配的优先级靠模式自己算分、不靠声明顺序」，以及这套评分体系做了哪几个关键取舍。

## 1. 为什么需要它

上一章把 URL 拆成了 path、query、hash 三段并解析了相对路径——你已经知道「现在在哪个 URL 上」。可这只是单边的事实：路由表的另一头是一堆「模式」，每个模式都说自己想接管什么样的 URL。问题是，同一个 URL 往往同时撞上好几个模式。

举个例子：你写了用户详情页 `/users/:id`，又写了「新建用户」页 `/users/new`。访问 `/users/new` 时，两个模式都成立——`new` 既符合静态字面量 `new`，也符合 `:id` 占位。该让谁赢？

早期路由库的答案是「按声明顺序」：谁先写谁优先。听起来简单，实际上把正确性外包给了人的记忆——你必须记得「更具体的写在前面」。一旦把 `/users/:id` 写到 `/users/new` 前面，`new` 就被当成 `id="new"` 吞下去，路由进了详情页组件，详情页拿 `id="new"` 去请求数据，回来一堆莫名其妙的报错。这类 bug 极难排查，因为路由表本身看起来「完全正确」。

本章要解决的就是这件事：把「谁更该匹配」从「用户写的顺序」彻底拿走，换成一个由模式自身派生、与声明顺序无关的量。

## 2. 核心思想

具体性，本就该写在模式里。

`/users/new` 比起 `/users/:id`，「更不容易匹配」也就意味着「一旦匹配更珍贵」——一个写死的字符串只能匹配它自己，一个 `:id` 能匹配任意片段。把这种「具体程度」量化、编译进每个模式的产物里，再按这个量从高到低匹配，赢家就自动浮现。用户怎么排声明顺序，都不再影响结果。

这个想法的关键一步，是把「具体性」用一种和 URL 结构同形的层级来表达——先比段、再比段之内——而不是压扁成一个数字。下面几节会围绕这点展开。

## 3. 心智模型

整体是一条「编译期三步走 + 运行期一次 test」的流水线：

1. **词法切段**：把模式字符串逐字符喂给状态机，遇到 `/` 就切段；每一段产出一组词法单元。单元有三种：静态串（`users`）、参数（`:id`）、带自定义正则的参数（`:id(\d+)`）。修饰符 `? + *` 紧跟在参数尾巴上，分别表示「可选」「可重复」「可选且可重复」。
2. **编译正则**：把每个单元翻译成一段正则片段，首尾加锚、段间补斜杠，拼成一条完整的正则，同时按顺序登记每个参数对应的捕获组。运行期只靠这一次 `test` 决定匹配与否。
3. **同步算分**：每个单元按尺度打分，写进一个与段结构同形的二维数组 `Array<number[]>`——外层每项对应一个段，内层是该段各单元的得分。
4. **注册排序**：把新路由插进一张「高分在前」的有序表（具体怎么插是后续章节的事，本章只关心分数怎么来、怎么比）。
5. **匹配**：URL 来了，从高到低依次 `test`，第一个命中的模式就是赢家——它也就是「最具体」的那一个。
6. **双向**：命中的模式还能用捕获组反向抽出参数（`parse`），或者把参数拼回成 URL（`stringify`）。

这里最关键的设计是第 3 步的「二维分数」。它不是一锅炖的一个数，而是镜像 URL 的层级：先按段排，段内再按子片排。这个选择换来什么、又付出了什么，是下一节的重头戏。

## 4. 关键权衡

### 用二维分数镜像 URL 层级，而不是压扁成一个数

每一段一个分数组、段内每个单元一个分——这种 `Array<number[]>` 的二维结构是本章最重要的选择。

换来的是「段级优先于段内」这种层级化比较语义。考虑 `/a/b` 和 `/a-:b` 这两个模式：如果分数被压扁成一个数字，两者对同一个 URL 的具体性可能算出同样的总分，无法区分。但用二维分数，前者是「两段、每段一个静态」，后者是「一段、段内两个单元」——外层先比段数，段数不同就立刻分胜负，根本不用纠结段内细节。

背后化解的本质矛盾是：URL 是天然分段的，而「谁更具体」这种判断需要逐段对比才能成立。一维分数会把段间和段内的差异混在一起，让对比失真；二维分数让对比顺序直接镜像 URL 的层级结构，逐层下沉。

代价是比较器变复杂。它要写成一个字典序比较：外层先逐段比，第一段同分才看第二段；段内再逐单元比。更要命的是，还要处理段数不等的边界（一方只有一段静态、另一方有多段；或者一方末尾是负分），这些场景下「先比段」这个朴素规则不够用，得特判。后面几条权衡会逐个消化这些特判。

### 公共乘数 + 刻意取整，把浮点误差挡在门外

所有分数都是同一个乘数（10）的倍数，各种微调项被注释硬性约束在「不足以撼动主体排序」的量级——例如「是否严格」「是否大小写敏感」这两项，特意取了不到 0.1 个乘数的小数。

换来的是整数级别的精确比较，绝不出现 `0.1 + 0.2 === 0.30000000000000004` 这种浮点坑。两个模式如果只在「严格性」上有差异，那它们确实只在末位差那么一丝——主排序完全由段结构、静态/动态、参数修饰符这些大头来定，微调项只在最后一公里起作用。

代价是分数体系失去了「按重要性任意加权」的灵活性。你想临时给某个新特性一个高分来插队？办不到，它会冲乱既有的主排序。这套体系的设计者是认了这条限制的：他们宁可让分数体系「窄而硬」，也不愿冒「主排序被微调项污染」的风险。

背后化解的本质矛盾是：评分体系既需要容纳「主体差异」（段结构、静态/动态）这种粗粒度，又需要容纳「末位微调」（严格性、大小写）这种细粒度，而这两层在同一个数字尺度上无法共存。解法是人为指定一个尺度阶梯——大头按乘数的整倍数跳，微调按乘数的小数位跳——两者永远不交叉。

### 通配用负分，刻意抵消正则的加分

通配（`:rest(.*)*` 这种「匹配任意路径」的形态）是整个体系里唯一产生负分的单元。它的负分大到注释里直白写着「我们顺手扣掉了自定义正则本应加的分」。

换来的是一条极稳固的语义：**通配永远垫底**。不管通配后面挂多复杂、多花哨的自定义正则，它就是最不具体的——因为「匹配任意」本来就是具体的反面。靠负分硬扣，而不是靠「我写代码时记得让通配垫底」，让这条规则在评分体系里自洽，而不是依赖某个分支的判断。

代价是分数可正可负，比较器必须额外处理这种异常——比如特判「某方末尾单元得分为负」时的先后关系，否则就会出现「通配模式被错误地排到前面」这种诡异情况。

背后化解的本质矛盾是：自定义正则「本来应该让参数更具体」（毕竟多了一个约束），但通配里的 `.*` 又是最宽泛的匹配。这两个属性在同一个单元上打架。靠「先加正则分、再由通配硬扣回去」的负分设计，让通配在「正则很厉害」和「通配很宽泛」两层语义冲突中，最终服从后者。

### 用手写字符级状态机做词法，而不是一个巨型正则

词法器是一个五状态、逐字符推进的小状态机：静态、参数、参数正则、参数正则收尾、转义下一字符。靠 `buffer` 和 `customRe` 两个累加器交接。

换来的是对三种麻烦场景的精确控制：模式里的转义字符（让静态段也能容纳字面量的特殊符号）、自定义正则的边界（`(` 配 `)`、且 `)` 前一个字符是 `\` 时不结束）、修饰符的「回退一字符」回看（看到 `*+?` 时要把刚刚吃进去的字符吐出来，再去判定前一个参数的语义）。

代价是状态分支多、可读性下降——一段看起来朴素的模式字符串，背后要走十几个分支才能切对。源码注释也承认这是「添加路由时最慢的一步」，但又说「已经足够快，故未加缓存」。选择状态机的真正动机不是性能，而是控制力：用一个吞掉整段路径的正则来做这些事，转义、嵌套括号、修饰符回看每一项都得在同一个正则里表达，最后会变成读不懂也改不动的怪物。

背后化解的本质矛盾是：路径模式本身是一个有结构的小语言（段、参数、修饰符、自定义正则），而正则表达式虽然强大，却不是「解析小语言」的好工具。一旦把词法外包给正则，所有边界情形只能塞进同一个模式串里互相打架。手写状态机把每类边界拆成独立状态，让每条规则单独可读、可改。

## 5. 最小原理演示

下面这段代码只演透两件事：**二维分数的字典序比较**，以及**通配负分如何让通配垫底**。词法器、正则编译都做了大量简化（不处理转义、不处理嵌套正则、不区分大小写敏感等微调项），只保留演原理必需的最小骨架。

```ts
// 单元类型：静态片段、动态参数、带正则的参数、通配
type Token =
  | { type: 'static'; value: string }
  | { type: 'param'; name: string }
  | { type: 'regexp'; name: string; re: string }
  | { type: 'wildcard'; name: string }

// 极简词法：只识别「按 / 切段、段内 :param 与 :param(re) 与 .* 通配」
function tokenize(pattern: string): Token[][] {
  return pattern
    .split('/')
    .filter(Boolean)
    .map((seg) => {
      if (seg.startsWith(':')) {
        const m = seg.match(/^:([^()]+)(?:\(([^)]*)\))?$/)!
        const [, name, re] = m
        if (re === '.*') return [{ type: 'wildcard', name }]
        return re ? [{ type: 'regexp', name, re }] : [{ type: 'param', name }]
      }
      return [{ type: 'static', value: seg }]
    })
}

// 与段结构同形的二维分数
const SCORE = {
  static: 40,
  regexp: 30, // 带自定义正则的参数，比普通参数更具体
  param: 20,
  wildcard: -50, // 通配：唯一产生负分的单元
}

function scoreOf(tokens: Token[][]): number[][] {
  return tokens.map((seg) => seg.map((t) => SCORE[t.type]))
}

// 字典序比较：先逐段比（外层），段内再逐单元比（内层）
function compare(a: number[][], b: number[][]): number {
  const len = Math.max(a.length, b.length)
  for (let i = 0; i < len; i++) {
    const ai = a[i],
      bi = b[i]
    // 段数不等：一方只含一个静态段则短者前；否则长者前
    if (!ai) return bi!.length === 1 && bi![0] === SCORE.static ? 1 : -1
    if (!bi) return ai.length === 1 && ai[0] === SCORE.static ? -1 : 1
    for (let j = 0; j < Math.max(ai.length, bi.length); j++) {
      const diff = (bi[j] ?? -Infinity) - (ai[j] ?? -Infinity)
      if (diff !== 0) return diff
    }
  }
  return 0
}

// 三个对照模式
const routes = [
  { name: '/users/:id', tokens: tokenize('/users/:id') },
  { name: '/users/new', tokens: tokenize('/users/new') },
  { name: '/users/:rest(.*)', tokens: tokenize('/users/:rest(.*)') },
]

const ranked = routes
  .map((r) => ({ ...r, score: scoreOf(r.tokens) }))
  .sort((a, b) => compare(a.score, b.score))

console.log('按具体性从高到低：')
for (const r of ranked) {
  console.log(`  ${r.name.padEnd(20)} score = ${JSON.stringify(r.score)}`)
}
```

跑一遍，输出会长这样：

```
按具体性从高到低：
  /users/new           score = [[40],[40]]
  /users/:id           score = [[40],[20]]
  /users/:rest(.*)     score = [[40],[-50]]
```

第一段都是 `[40]`（都是静态 `users`），打平。胜负在第二段：静态 `new` 拿 40，动态 `:id` 拿 20，通配 `(.*)` 直接 −50。字典序下沉到第二段就分出胜负。**注册时这三个模式无论以什么顺序写入路由表，最终命中 `/users/new` 这个 URL 的赢家永远是 `/users/new`**——这就是「与声明顺序无关」在代码层面的落地。

## 6. 执行轨迹

把上面那个例子拆开走一遍，看「分数怎么把歧义解掉」：

1. **注册 `/users/:id`**：词法切成两段 `[static users]`、`[param id]`。算分得 `[[40],[20]]`。插进有序表（此时表里只有它）。
2. **注册 `/users/new`**：词法切成两段 `[static users]`、`[static new]`。算分得 `[[40],[40]]`。比较器拿它和已有的 `/users/:id` 比：外层段数都是 2，进第一段，`[40]` 对 `[40]` 同分；进第二段，`[40]` 对 `[20]`，`b[j]-a[j] = 20 > 0`，意味着 `/users/new` 应该排前。表变成 `[/users/new, /users/:id]`。
3. **注册 `/users/:rest(.*)`**：算分得 `[[40],[-50]]`。和 `/users/:id` 比：第一段同分；第二段 `−50` 对 `20`，`20 − (−50) = 70 > 0`，通配模式排到最末。表变成 `[/users/new, /users/:id, /users/:rest(.*)]`。
4. **运行期，URL `/users/new` 进来**：从高到低依次 test 正则。先测 `/users/new`，命中。赢家确定，后面两个模式根本没机会跑。

如果用户偏偏把 `/users/:id` 写在 `/users/new` 之前会怎样？答案是，毫无影响。注册时的「二分插入」是按分数排，不是按到达顺序排。声明顺序在这套体系里只是「决定哪一行先被编译」，再无其它作用。

## 7. 教学简化说明

本章演示故意省略了：转义字符的状态分支、嵌套自定义正则（如 `:p(?:prefix_([^/]+))`）的边界处理、严格 / 末尾 / 大小写三个选项对正则锚与分数末位的微调、可选参数拼回 URL 时的斜杠去重，以及「分组」单元类型（类型层已定义但词法器不会产出）。这些都不影响「具体性评分」这条主轴。

## 8. 小结

这一章把「谁更该匹配」从「用户写的顺序」搬到了「模式自身的具体性」——编译每个模式时同步算出二维分数，按字典序比较，最高分赢。代价是一个看起来复杂、其实只做「逐段、逐单元、特判边界」的比较器，加上一套刻意取整、刻意让通配变负的分数体系。
