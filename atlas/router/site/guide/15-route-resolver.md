# 新一代路由解析器

> 本章属于 system 层。前置：路由匹配表（沿父链反推 matched 链 + 评分排序树）、URL 分段编码与查询串（按段细分编码）。
> 学完你能：用一句话讲清「为什么这个解析器把『不匹配』做成异常、为什么参数校验失败会让整条路由落选」。

## 1. 为什么需要它

上一章把数据获取从组件树提到导航管线，让导航链变成带 staged→commit 两阶段的复杂管线。但这条链的最前端（URL 拿到后怎么找到对应的路由记录）还停在为「运行时动态增删路由」设计的旧解析器上。

具体矛盾摆在 file-based routing 使用者面前特别刺眼：

- 路由表是构建期扫描目录 + 代码生成出来的静态清单，运行时根本不会增删；可旧解析器却背着一套为运行时增删准备的评分排序系统。
- 路径参数 `:id` 拿到手永远是字符串，组件里要自己 `Number()`、自己校验，校验不过还得自己处理。
- 路径匹配失败和「参数值不合法」返回的是同一种 null，调用方分不清是「这条 URL 没有对应路由」还是「值不对」。

使用者被迫在匹配层之外再叠一层类型转换与校验。矛盾的核心是：**路由表已经静态化，可参数语义却越来越丰富（带类型、带校验）**。旧解析器是给「会变」的路由表设计的，对新场景下「参数该怎么处理」毫不在意；新场景需要一个匹配器，把参数类型转换和校验一并接管，而不是把这件事甩给组件层。

## 2. 核心思想

把「不匹配」做成一个可抛出的异常，让参数类型校验失败等价于「这条路由落选」。匹配的过程本身就是筛选的过程。

这里换了个角度：不是「让匹配器多承担一点校验工作」，而是把两层判断折叠成一层。旧解析器里「能不能匹配」是第一层、「参数合不合法」是第二层；新解析器让它们走同一个出口，只要任意一层失败，就抛同一个 `MatchMiss`，外层循环自动 try/catch 试下一条。校验成了匹配的一部分，而不是匹配之后还要做的另一件事。

## 3. 心智模型

想象一组按构建期固定顺序排好的记录，每条记录身上挂着三段独立的匹配器：路径段、查询段、哈希段。每段匹配器内部又挂着参数解析器，负责把捕获到的字符串换成目标类型。

解析一个 URL 时：

1. 先把 URL 拆成 path / query / hash 三段。
2. 按数组顺序取出第一条记录，让它的路径匹配器去试 path 段。匹配不上，匹配器内部就抛 `MatchMiss`。
3. 路径过了，再让哈希匹配器试哈希段（只看最深那条记录）。
4. 沿记录的 `parent` 链一路反推，拼出 matched 链（这一点和第 6 章「路由匹配表」一致，本章只复用、不重演）。
5. 把 matched 链上每条记录的查询匹配器结果合在一起（query 是非排他的，下面权衡里专门讲）。
6. 任何一处匹配中的参数解析器，把字符串转成目标类型；转换或校验失败，同样抛 `MatchMiss`。
7. 整条记录全程不抛就是命中；只要中途抛过，循环 try/catch 试下一条。
8. 全部试完都不行，返回一个「无匹配」哨兵位置（带 Symbol 作 name、空 params、空 matched）。

关键不变量：**「不匹配」只有一个控制流出口，就是抛 `MatchMiss`**；调用方看到的「无匹配哨兵」是循环走完没人接住之后的兜底。

## 4. 关键权衡

### 异常即不匹配：把「未命中」做成专用异常

匹配器内部任何一处「不通过」——路径静态段大小写不符、必填 query 缺失、参数类型解析失败、Standard Schema 校验给出 issues——都抛同一个 `MatchMiss`。外层循环用一个 try/catch 接住，自动试下一条。

换来的是逻辑高度统一：不用为每种失败写不同的判断分支；参数校验失败天然等价于「这条路由落选」；调用方不需要再区分「路径没匹配」还是「值不合法」。

代价真实存在：异常对象要带调用栈，构造它不是免费的，高频匹配路径上每次落选都付一次。异常控制流对第一次接触的调试者也不直观——单步调试会突然跳进 catch。这是用运行时性能和直观性，换「匹配 + 校验」在概念上的合并。

化解的本质矛盾：「检查失败」与「记录不匹配」是两种语义上的「不通过」；把它们合并到同一个控制流出口，才能让「匹配即筛选」成立，否则就得在匹配之外再叠一层判断。

### 固定有序表 + 顺序试错，而非评分排序树

旧解析器（第 6 章「路由匹配表」）为了支持运行时 `addRoute`，要在记录里维护评分、二分插入保持有序、resolve 时按分数挑最优。新解析器直接收下一张构建期定下来的数组，运行时顺序遍历，第一个全程不抛的就是命中。

换来的是大幅简化：不需要评分系统、不需要二分插入、记录之间用 `parent` 指针就能表达嵌套（matched 链直接 walk 父链），和代码生成天然契合——codegen 生成的就是数组。

代价是放弃运行时增删路由的能力（动态性被推到构建期）；命中优先级隐式依赖数组顺序（生成器必须保证更具体的记录排在更通用的之前）；匹配是 O(n) 而非 O(log n)。源码里 `TODO: test performance` 的注释暗示作者知道这里有边界，但选择了简单性。

化解的本质矛盾：「路由表是否会变」决定了匹配数据结构的最优形态——能变就要排序树，不会变就可以用线性表。file-based routing 把「变」推到构建期之后，运行时就不必再付树的复杂度。这是和第 6 章最直接的对照。

### path 排他、query 非排他合并

选哪条记录由 path 段排他决定——路径正则命中的那条就赢；但 query 段不排他，会沿 matched 链把每条祖先记录的查询匹配结果合并进 params。

换来的是「分组记录」这种用法：把分页参数（`?page=`）、筛选参数（`?filter=`）抽成一条无 path、无 name、只能匹配 query 的「分组记录」，挂在多条路径记录的祖先位置，让它们各自独立声明类型、跨路径复用。

代价是 path 与 query 的匹配语义不对称——一个排他、一个合并，心智模型需要额外接受这个不对称；多出「只能匹配 query 的分组记录」这一概念，初见会问「为什么会有没有路径的记录」。

化解的本质矛盾：「排他选择」（路径只决定一条）与「跨记录共性提取」（查询参数可被多条路径共享）是两种对立的组织需求。让 path 走一条、query 沿链合并，是同时满足两者的折中。

### 类型转换下沉到匹配层 + 标准校验协议

参数解析器（`ParamParser`）就长这样：`get` 把 URL 字符串值换成强类型、`set` 反向序列化。匹配阶段就会调用 `get`——任何校验库只要实现 Standard Schema 协议（zod、valibot 等都符合），就能被自动适配成 `ParamParser`：校验通过就返回强类型值，有 issues 就 `miss()`。

换来的是 `route.params` 直出强类型——`/users/42` 命中后 `params.id` 就是 `number` 42，不是字符串 `"42"`；组件层不必再 `Number()`、再校验；zod/valibot 等校验库零适配接入。

代价是匹配路径承担了类型转换职责（关注点从「挑记录」扩展到「挑并验证」）；解析器里的错误必须走「未命中」语义而非普通异常（你抛一个普通 `Error` 不会被外层 try/catch 当成 miss）；并且显式拒绝异步校验，匹配必须是同步的，整个解析才能是同步的。

化解的本质矛盾：「类型校验」与「路由匹配」在概念上是分离的两件事，但把它们在匹配层合并，才能让「参数非法」等价于「路由落选」，避免组件层再叠一层校验。

## 5. 最小原理演示

下面这段从零实现的解析器，只演示三件事：「未命中是可抛异常」「参数校验失败即落选」「构建期固定表顺序试错」。其余能力（哈希段、别名、分组记录的 query 合并、相对路径、编码、正则编译、HMR）一律省略。

```ts
// "未命中"是一个专用异常——路径不符、参数非法都抛它
class MatchMiss extends Error {}
const miss = (): never => { throw new MatchMiss() }

// 参数解析器：把"字符串→强类型+校验"下沉到匹配层
const numberParser = {
  get: (v: string | null) => {
    if (v == null) miss()
    const n = Number(v)
    if (Number.isNaN(n)) miss()      // 非法值当作不匹配，而不是抛错给上层
    return n
  },
  set: (n: number) => String(n),
}

// 一条记录：路径正则 + 携带参数解析器
function defineRoute(
  re: RegExp,
  parsers: Record<string, { get: (v: string | null) => any }>,
) {
  return {
    match(path: string) {
      const m = path.match(re)
      if (!m) miss()                  // 路径不匹配 → 抛
      const params: Record<string, unknown> = {}
      let i = 0
      for (const k of Object.keys(parsers)) {
        params[k] = parsers[k].get(m[++i])
      }
      return params                   // 拿到的就是强类型
    },
  }
}

// 构建期固定清单：顺序试错，首个全程不抛即命中
function createFixedResolver(records: ReturnType<typeof defineRoute>[]) {
  return {
    resolve(path: string) {
      for (const r of records) {
        try {
          return { path, params: r.match(path), ok: true }
        } catch {
          // 这条落选，试下一条
        }
      }
      return { path, params: {}, ok: false }   // 全部落选 → 无匹配哨兵
    },
  }
}

const resolver = createFixedResolver([
  defineRoute(/^\/users\/([^/]+)$/, { id: numberParser }),
])

resolver.resolve('/users/42')
// { path: '/users/42', params: { id: 42 }, ok: true }   ← id 直出 number
resolver.resolve('/users/abc')
// { path: '/users/abc', params: {}, ok: false }          ← numberParser 校验失败自然落选
```

## 6. 执行轨迹

路由表只有一条记录：`{ name: 'users', path: '/users/:id' }`，`id` 的参数解析器是 `numberParser`。

**输入 `/users/42?page=3`**：

1. parseURL 拆段：`{ path: '/users/42', query: { page: '3' } }`（query 此例不影响结果，先放着）。
2. 顺序遍历，取出 users 记录，让它的路径匹配器试 `/users/42`。
3. 路径正则 `/^\/users\/([^/]+)$/` 命中，捕获到字符串 `'42'`。
4. 路径匹配器把 `'42'` 交给 `numberParser.get`：`Number('42')` 是 `42`，校验通过，返回数字 `42`。
5. 沿记录 `parent` 链反推 matched 链（此例只有 users 自己）。
6. 全程没人抛 `MatchMiss`，记录命中。
7. 输出：`{ name: 'users', params: { id: 42 }, ... }`，`id` 直出 `number`。

**对比输入 `/users/abc`**：

1. 拆段：`{ path: '/users/abc' }`。
2. 取出 users 记录，路径正则命中，捕获 `'abc'`。
3. `numberParser.get('abc')`：`Number('abc')` 是 `NaN`，触发 `miss()`，抛 `MatchMiss`。
4. 外层 try/catch 接住，试下一条记录（没有了）。
5. 全部落选，返回无匹配哨兵：`{ name: Symbol(no-match), params: {}, matched: [] }`。

同一条路径 `/users/:id`，仅仅因为参数值不同（`42` vs `abc`），会命中或落选。这就是「类型校验即筛选」的直接推论：参数的类型决定了 URL 能否落到这条路由。

## 7. 教学简化说明

本章演示故意省略了：哈希段、别名记录（`aliasOf`）、分组记录的 query 沿链合并、相对路径（`./`、`../`、`?page=2`）解析、可重复/可选参数、trailingSlash 三态、子段编码细节、正则编译、HMR 替换解析器、与 history / 守卫 / 滚动恢复的集成。这些都是工程化脚手架，原理主角始终是上面那四条权衡。

## 8. 小结

新解析器的灵魂就一句话：把「不匹配」做成异常，让「参数校验失败」和「路由落选」共用同一个出口。匹配器于是从「挑记录」扩展成「挑并验证」，校验库通过 Standard Schema 协议即插即用，组件层再也拿不到非法参数。代价是把动态性推到构建期、放弃运行时增删，这正好对上 file-based routing 的现实。下一章「文件路由：类型生成与构建期集成」就接着讲构建期这一侧：怎么扫目录、生成这张固定表，再把类型一路前移到 `typed-router.d.ts`。
