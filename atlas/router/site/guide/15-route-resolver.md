# 新一代路由解析器：把"没匹配上"做成一次异常

## 用文件路由的人，到底在烦什么

想象你用文件路由搭一个后台：`src/pages/users/[id].vue`、`src/pages/users/index.vue`……这些路由不是你手写的，是构建期扫目录、生成出来的一张**静态清单**。程序跑起来之后，这张清单不会增、不会删——它生来就是定死的。

可旧的解析器偏偏背着一套为"运行时随时增删路由"准备的复杂系统：每加一条路由要算一个具体性分数，再二分插进一张有序表里维持排名。这套东西我们在第 6 章「路由匹配表」里讲透了，它对付的是"路由表会变"的世界。但文件路由的世界里路由表根本不变——这套动态排序的 machinery 就成了纯负担。

更让人烦的是参数。路径里的 `:id` 从 URL 里捞出来永远是字符串 `"42"`，你在组件里得自己 `Number()`、自己校验。万一传进来 `/users/abc`，旧解析器照样把 `"abc"` 当成 id 返回给你，你还得在业务代码里判断它是不是合法数字。查不到记录时更含糊：返回一个 null，你分不清到底是"这条路径压根没匹配上"，还是"匹配上了但参数不合法"。

这一章讲的解析器，就是为治这两个烦而生的。它干了两件颠覆性的事：**第一，把"没匹配上"做成一个可以抛出的异常；第二，把"字符串转强类型 + 校验"这一步，从组件层搬进匹配层。** 这两件事其实是同一件事的两面。

## 最底层那块：没匹配上，就抛出去

先从最基本的问题问起：一个匹配函数，"没匹配上"该怎么表达？

最直觉的答案是返回 `null` 或者 `false`。但这条路有个麻烦：一条记录的匹配分好几步——路径正则要对上、参数要能解析、必填的 query 不能缺……任何一步出问题都算"这条记录没中"。如果你用返回值表达"没中"，每一步都得写成"先判断、再决定要不要继续"，代码会被 if/else 塞满，而且每一步的"没中"含义还不一样，散落在各处。

这个解析器换了个思路：**"没中"不返回，直接抛。** 它定义了一个专门的异常类型 `MatchMiss`，再加一个小助手 `miss()`——任何一处觉得"这条不对"，就调一下 `miss()`，控制流立刻跳出当前记录。

说人话就是：匹配像一条流水线的质检，每一道工序都有权直接把不合格的零件踢下线，不用等所有工序做完再回头判断合格不合格。踢下线这个动作，就是抛 `MatchMiss`。

这个决定看似不起眼，其实是整章的魂。它带来一个统一的结果：**路径对不上、参数不是数字、必填 query 缺失、静态段大小写不符……这些原本八竿子打不着的"没中"原因，全走同一个 `miss()` 出口。** 外层只需要一个 try/catch 就能接住所有情况，根本不用关心是哪一步没中的。

## 再上一层：校验失败，等于这条路由落选

光有"没中就抛"还不够。真正有意思的，是把参数的类型转换也塞进这条抛出通道里。

每条记录在声明自己的路径模式时，可以给每个参数配一个**解析器**（ParamParser）。解析器就两个动作：`get` 把 URL 里的字符串转成你要的类型，`set` 反过来把你的类型变回字符串。关键是，`get` 就跑在匹配阶段——也就是说，类型转换发生在"判断这条路由中没中"的过程里，而不是之后。

拿 `/users/:id` 配一个数字解析器举例。URL 是 `/users/42`：正则捕获到字符串 `"42"`，解析器的 `get` 把它转成数字 `42`，整个过程没抛异常，这条记录命中，你拿到的 `route.params.id` 直接就是 `number` 类型的 `42`，不用再 `Number()`。URL 换成 `/users/abc`：`get` 发现 `"abc"` 不是合法数字，调 `miss()` 抛出去——这条记录就这么自然落选了，外层会去试下一条。

这一下，类型校验和路由筛选就合二为一了：**一个值过不了类型校验，跟"这条路由本来就不该匹配它"是同一件事。** 你再也不用在组件里写 `if (isNaN(id))` 这种防御代码，因为根本到不了组件——校验不过的路由压根进不来。

这里还有个特别聪明的设计：任何遵循 Standard Schema 的校验器（zod、valibot 这些），都能零适配地插进来当解析器。做法很轻——解析器收到一个对象，就用鸭子类型摸一下它身上有没有 `~standard` 这个标记，有就把它的 `validate` 包成 `get`：校验通过返回值，校验有 `issues` 就调 `miss()`。**Standard Schema 在这里就像一个 USB-C 接口**，谁遵守这个规范谁能插，路由器完全不关心你用的是哪个校验库。

顺带一提：这个解析器显式拒绝了异步校验。因为整个匹配必须是同步的——一次 resolve 要当场给出结果，不能 await。

## 把记录装进一张固定表，顺序试错

有了"抛 MatchMiss = 没中"这条通道，剩下的问题就简单了：一堆记录摆在那，怎么挑出命中的那条？

答案是整章最朴素的一句话：**挨个试，第一个全程不抛的就是它。**

构建期，代码生成把所有记录排成一个**固定数组**交给解析器，解析器顺手再建一张"名字 → 记录"的快查表（别名记录不进表，按名查总是落回原记录）。运行时要解析一个 URL，就拿到这个数组从头遍历，对每条记录调一次 `validateMatch`，套在 try/catch 里：不抛就 break、就是命中；抛了就 catch 掉、接着试下一条。全试完都没中，返回一个"无匹配"的位置。

这里要跟第 6 章做个对照。第 6 章的匹配表为了对付"路由会动态增删"，给每条记录算分数、二分插入维持一张按具体性排序的表，匹配时靠分数保证最具体的那条优先命中。这一章的前提变了——路由表是构建期定死的、不会变——所以它**直接放弃了整套评分和二分插入**，改用最直白的数组顺序。命中优先级就隐含在数组的排列里（代码生成时已经排好）。同样是"沿父链反推出 matched 链"（这个第 6 章讲透了，本章原样复用，不重复），但维持表有序的那套 machinery 整个被砍掉了。

> 顺便补一句第 1 章的编码：路径参数捕获到字符串后要先 decode，再交给解析器。这里有个新出现的细节——同一个动态段，段内部（子段）用一种保留 `/` 的编码 `encodeParam`，整段用另一种编码 `encodePath`，两种编码在同一条路径上分工协作。第 1 章把"按段细分编码"讲透了，本章只看它在这个解析器里的这个新侧面，不展开编码本身。

## 三段各管各的：path 排他，query 合并

一条 URL 拆成 path、query、hash 三段。这三段在匹配时的脾气**完全不一样**，这是本章最容易绕晕的地方，得分开说。

**path 是排他的。** 它决定"选哪一条记录"——数组里只有一条记录的 path 能命中，命中之后别的记录就不再考虑了。这是上面"挨个试、第一个不抛的就 break"的基础。

**query 是非排他的，它会沿 matched 链合并。** 命中一条记录后，解析器会沿着父链把这条记录和它所有祖先记录的 query 匹配结果**合并**到一起（用一个 `Object.assign` 把链上每条记录的 query 结果并进同一个 params 对象）。换句话说，query 参数不属于某一条路径记录独有，而是"这一组记录共享"的。

这个设计是有现实动机的。分页参数 `?page=2`、筛选参数 `?status=active` 这类东西，往往是一整组路由都要用的，跟具体路径没关系。所以解析器允许一种**分组记录**：它没有 name、没有 path、没有 hash，**只能匹配 query**。你把一组公共的 query 参数声明在分组记录上，挂到多条路径记录的父链里，这些路径记录就都能复用同一份 query 类型声明，彼此独立。

**hash 只看最深的那条记录。** 它既不像 path 那样排他地挑记录，也不像 query 那样沿链合并——就是匹配命中记录自己的 hash 而已。

> 文字流程图概括一下 `validateMatch` 这一步在干什么：
>
> `record.path.match(path)`（排他，不中就抛）
> → `record.hash?.match(hash)`（只看命中的这条）
> → `buildMatched(record)`（沿父链反推 matched 数组，第 6 章讲过）
> → 把链上所有记录的 `query.match(query)` 结果合并进 params
> → 返回 `[matched, { ...path参数, ...query参数, ...hash参数 }]`

## 两条解析路，和一个"无匹配"哨兵

对外暴露的 `resolve` 其实有两条路，看你给它的是字符串还是带名字的对象。

**给字符串或纯路径对象**（比如 `/users/42`）：先把它拆成 path/query/hash 三段，然后就是上面说的——遍历记录、try/catch 试、第一个不抛的命中。全没中？返回一个特殊的"无匹配"位置。这个位置很讲究：它的 name 是一个 Symbol，params 是空对象，matched 是空数组。用一个 Symbol 当 name，是为了让"无匹配"也有一个稳定的标识可比较，同时允许 path/query/hash 这些字段照常变化。

**给带名字的对象**（比如 `{ name: 'user', params: { id: 42 } }`）：走的是另一条路。先从快查表里按名字捞出记录，用参数把 URL **build** 出来（路径、query、hash 都拼好），然后再拿拼好的 URL 调一次 `validateMatch` 复算。你可能会问：参数都是我给的，干嘛还要复算一遍？因为参数可能来自好几个地方——path、query、hash 各自声明了同名参数时，build 出来的 URL 里它们可能对不上。复算一遍就是为了消除这种不一致，保证最后交出去的 params 是自洽的。

## 原理演示：40 行演透两条核心权衡

下面这段从零写的 TS 演示，只演两件事——"异常即不匹配"和"类型校验即筛选"。哈希、别名、query 合并、相对路径、编码细节这些都故意省略了，为的是让那两条原理一根线贯穿到底。

```ts
// resolver-demo.ts
// 原理①：没匹配上不返回 null，而是抛一个专用异常
class MatchMiss extends Error {}
const miss = (): never => { throw new MatchMiss() }

// 原理②：参数解析器把「字符串 → 强类型 + 校验」下沉到匹配层
const numberParam = {
  get(v: string | null): number {
    if (v == null) miss()        // 没值 → 当作不匹配
    const n = Number(v)
    if (Number.isNaN(n)) miss()  // 不是数字 → 当作不匹配
    return n
  },
  set: (n: number) => String(n),
}

// 一条记录：路径正则 + 它携带的参数解析器
function defineRoute(
  re: RegExp,
  parsers: Record<string, { get: (v: string | null) => unknown }>,
) {
  return {
    match(path: string) {
      const m = path.match(re)
      if (!m) miss()             // 路径对不上 → 不匹配
      const params: Record<string, unknown> = {}
      let i = 0
      for (const key of Object.keys(parsers)) params[key] = parsers[key].get(m[++i])
      return params              // 拿到的已经是强类型
    },
  }
}

// 原理③：构建期收下一张固定清单，运行时顺序试错，第一个全程不抛的就是命中
function createResolver(records: ReturnType<typeof defineRoute>[]) {
  return {
    resolve(path: string) {
      for (const r of records) {
        try {
          return { path, matched: true, params: r.match(path) } // 不抛 = 命中
        } catch {
          // 这条没对上，试下一条
        }
      }
      return { path, matched: false, params: {} } // 全部落选 → 无匹配
    },
  }
}

const resolver = createResolver([
  defineRoute(/^\/users\/([^/]+)$/, { id: numberParam }),
])

console.log(resolver.resolve('/users/42'))
// { path: '/users/42', matched: true, params: { id: 42 } }   ← id 直出 number
console.log(resolver.resolve('/users/abc'))
// { path: '/users/abc', matched: false, params: {} }         ← 校验失败，自然落选
```

配套最小 `package.json`，`bun run demo` 或 `npx tsx resolver-demo.ts` 即可跑：

```json
{
  "name": "resolver-demo",
  "private": true,
  "type": "module",
  "scripts": { "demo": "tsx resolver-demo.ts" },
  "devDependencies": { "tsx": "^4.0.0" }
}
```

把演示稍微扩成完整的"三段 + 命名"场景，跑一遍推荐轨迹：路由表里有一条 `{ name: 'users', path: '/users/:id', id 解析器 = number }`，再挂一个分组记录声明了 query 参数 `page`（也是 number）。请求 `/users/42?page=3`：

```
拆段 → { path: '/users/42', query: { page: '3' } }
→ 试 users 记录，路径正则命中、捕获 '42'
→ number 解析器把 '42' 转成 42（若捕获到 'abc' 则解析器抛、该记录落选）
→ 沿父链合并分组记录的 query，page 解析器把 '3' 转成 3
→ 输出 { name: 'users', params: { id: 42, page: 3 } }，两个参数都是 number，直出强类型
```

这条轨迹一次演透了"类型校验即筛选"和"直出强类型"两点。

## 关键权衡

这一章的机制不算少，但都围绕同一个魂打转。这里把四条最关键的权衡摊开。

**① 异常即不匹配（全章灵魂）**。做了"匹配不上就抛专用异常、循环里 try/catch 试下一条"的选择。换来的是：参数类型校验失败、必填 query 缺失、静态段大小写不符……全部用同一套 try/catch 自然落选，类型校验即匹配筛选，逻辑高度统一。代价是：每次落选都要构造一个异常对象（带调用栈），在频繁匹配的热路径上是一笔实打实的开销；而且异常这种控制流，对不熟悉的人调试起来不如返回值直观——你看到一堆被 catch 掉的 `MatchMiss`，第一反应未必能马上反应过来"这是正常的落选，不是 bug"。

**② 固定有序表 + 顺序试错，而非评分排序树**。做了"构建期收下一张有序清单、运行时顺序遍历首个全程不抛的即命中"的选择。换来的是：彻底砍掉评分系统与二分插入、记录可以直接用 parent 指针表达嵌套、跟代码生成天然契合。代价是：彻底放弃了运行时增删路由的能力（动态性被推到了构建期），命中优先级隐式依赖数组顺序（你得相信代码生成排得对），匹配复杂度是 O(n) 而非 O(log n)。这是跟第 6 章评分排序树最直接的对照——前提从"路由表会变"变成了"路由表定死"，整套维持有序的 machinery 也就没有了存在理由。

**③ path 排他、query 非排他合并**。做了"路径段排他决定选哪条记录、但查询段沿 matched 链把所有祖先记录的查询结果合并"的选择。换来的是：能把分页、筛选这类"分组级查询参数"抽成无路径的分组记录，跨多条路径记录复用、各自独立声明类型。代价是：path 和 query 的匹配语义不对称（一个排他、一个合并），心智模型要稍微拧一下；而且多出了"只能匹配 query 的分组记录"这么个新概念，初见会觉得绕。

**④ 类型转换下沉到匹配层 + 标准校验协议**。做了"在匹配阶段就用参数解析器把字符串转成目标类型并校验、任何校验库只要实现 Standard Schema 协议就能即插即用"的选择。换来的是：`route.params` 直出强类型、校验失败即落选无需组件层再校验一遍、zod/valibot 这类校验库零适配接入。代价是：匹配路径承担了类型转换这个新职责（关注点变多了）、解析器的错误必须走"未命中"语义而不能当普通异常抛、而且显式拒绝了异步校验——你没法在参数解析里做需要 await 的校验。

## 小结

这一章的解析器，骨子里就是用两个互相支撑的决定撑起来的：**把"没匹配上"做成一次可抛的异常**，再**把类型校验塞进匹配阶段**。前者让所有"不中"的原因共用一个出口，后者让校验失败等价于路由落选——两者一合，匹配的过程本身就是筛选的过程，组件层从此不必再背类型转换和防御校验的包袱。再加上"路由表构建期定死"这个大前提，整套为动态增删服务的评分排序 machinery 被干净利落地砍掉，换成了最直白的固定表顺序试错。

这套"路由表构建期固定 + 参数类型下沉到匹配层"的设计，恰好是下一章「文件路由：类型生成与构建期集成」要接的另一头——代码生成器扫目录、生成的不只是 routes 数组，还包括这套解析器要的记录清单和每个参数的解析器。两章拼起来，才是一个完整的"把动态性推到构建期、把类型前移到编译期"的闭环。
