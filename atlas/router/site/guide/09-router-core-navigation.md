# Router 核心与导航主循环

前面几章，我们把一台导航机器的零件一个一个造好了：怎么把配置编译成匹配表、怎么把 URL 抽象成可导航可监听的接口、怎么把守卫串成一条 promise 链、怎么给失败分类、怎么恢复滚动、怎么解析和判等位置。零件齐了，但还差一台总装线——**谁来按顺序叫它们开工？谁在异步的空窗里判定一条导航已经过期？谁在一切就绪后把结果真正落到 URL、状态和视图上？** 这一章就是这台总装机器。

## 先看一个会出 bug 的场景：幽灵导航

想象你在写一个后台系统。某个页面的进入守卫要等接口返回才放行，于是你这么写：

```ts
beforeEnter: async () => {
  await fetch('/api/permission')   // 这一下要 200ms
}
```

用户性子急，点了「用户管理」（/users），200ms 还没过，又点了「订单」（/orders）。这时候会发生什么？

导航本质上是异步的。守卫可以 `return fetch(...)`，组件可以是 `() => import('./Orders.vue')` 的懒加载 chunk，这些都要 `await`。而 `await` 会**让出执行权**——在等待的这段空窗里，用户完全可以再点一次链接、再触发一次导航。

如果没有专门机制，那条还在 `await` 的旧导航（/users），在恢复执行后会**继续往下走**，最后把 /users 的 URL、滚动、组件，一股脑覆盖到屏幕上。可用户明明最后点的是 /orders。屏幕闪一下跳回 /users——这就是「幽灵导航」。重定向、被守卫中止、重复点同一个链接，也都是同一个调度问题。

这章要解决的，就是**怎么把一条又长又异步、随时可能被打断的导航，变成一个随时能被取消的状态机**。

## 一块谁都能看到的公共白板：在途令牌

要说怎么取消，得先回答：**怎么知道「我自己这条导航，是不是已经过期了」？**

答案简单得有点反直觉：**用一个谁都能看到的、可变的公共变量，记下「当前正在途的那条导航」**。每来一条新导航，就把它写进去。这就像一块挂在墙上的公共白板，上面写着「现在在处理哪一单」——

- 你新来一单，第一件事就是把白板擦了、写上自己的名字；
- 你干完一段活回来，第一件事也是去看白板：上面写的还是我吗？是，继续干；已经被别人改成别人的名字了，那我就是过时的，立刻停手走人。

这个「白板」在代码里就是一个闭包里的可变变量，记作「在途位置」（`pendingLocation`）。它初始是一张空白票——一个叫 `START_LOCATION` 的哨兵，表示「还没发生过任何导航」。

一条导航进入主循环的第一步，就是把目标 resolve 成完整位置，然后**把白板上的名字改成自己**——这一刻起，它宣告「现在在途的是我」。后面所有的取消判断，都是一句话：**白板上写的还是不是我**。

## 在每两个阶段之间插一道闸门

光有白板还不够，你还得**主动去看**。导航不是一步走完的，它是一串阶段：离开旧页 → 全局前置守卫 → 更新守卫 → 进入前守卫 → 进入守卫 → 解析前守卫，最后才是收尾落地。这串阶段怎么串成 promise 链、`next` 回调怎么 promise 化，**第 7 章（导航守卫管线）已经展开过**，这里不重复。我们只看一个新的侧面：**主循环怎么在这条链的每两段之间，插一道「闸门」。**

闸门干的事很简单——读一眼白板，比对一次引用：白板上写的还是我吗？不是，就立刻抛一个「取消」失败，整条 promise 链当场短路，后面的阶段一段都不跑。

关键在于：这道闸门是**手动**塞进去的。每跑完一个守卫阶段，下一段开始之前，都显式地 push 一个检查函数进队列。一共六个阶段，就插六次；最后收尾之前，还再查一次——这是第七次。

说人话就是：取消不是靠什么高级的 `AbortController` 或者到处传递的取消信号实现的，而是靠**一个公共变量 + 一堆散落在各处的、一次引用比较**。这是这章最核心、也最反直觉的设计，下面用一段几十行的代码演透它。

## 最小演示：一条随时能被取消的异步导航

这段演示只演一件事——**「公共白板 + 阶段之间的闸门」怎么让任何阶段都能被新导航作废**。守卫真实的 arity 切换、重定向、滚动、URL 编解码，全都故意省略，因为它们跟「取消」原理无关。

```ts
// pending 就是那块公共白板：全局唯一的「在途导航」令牌
let pending: string | null = null

// 闸门：只要白板已被别人改写，当前这条导航立刻作废
const check = (self: string) => {
  if (pending !== self) throw Error(`CANCELLED：${self} 已被 ${pending} 取代`)
}

// 一条导航 = 一串异步阶段，每两个阶段之间插一次闸门
async function runPhases (self: string, phases: Array<() => Promise<void>>) {
  for (const phase of phases) {
    await phase()      // 跑当前阶段（内部可能 await，让出执行权）
    check(self)        // ← 关键：阶段之间手动比对一次白板
  }
}

async function navigate (to: string, phases: Array<() => Promise<void>>) {
  pending = to         // 进门第一件事：把白板改成自己
  try {
    await runPhases(to, phases)
    check(to)          // 收尾前最后一次闸门
    console.log(`✅ commit ${to}`)     // 全过了，才真正落地
  } catch (e) {
    console.log(`⚠️ ${e.message}`)     // 被取消，整条链短路，不再收尾
  }
}

// 一个故意很慢的阶段，模拟守卫 await 拉取懒加载 chunk
const slow = () => new Promise<void>(r => setTimeout(r, 50))

navigate('/a', [slow, slow])                  // A 启动，两个慢阶段
setTimeout(() => navigate('/b', [slow]), 10)  // 10ms 后 B 抢占白板
```

跑一下，输出是：

```
⚠️ CANCELLED：/a 已被 /b 取代
✅ commit /b
```

A 的第一个慢阶段跑完（50ms），回到闸门一看，白板早在 10ms 时就被 B 改成 `/b` 了——A 当场短路，连第二个阶段都不跑，更不会 commit。B 顺利走完所有阶段、最后再查一次闸门（还是它自己），于是 commit /b。屏幕最终停在 /b，A 的那套慢活全被丢弃，没有幽灵。

整段代码没有 `AbortController`、没有到处传的 cancel token、没有给每个 promise 包一层取消逻辑——**就是一个可变变量加几次引用比较**。把上面 `pending` 和 `check` 拿掉，立刻就回到「幽灵导航」。

配一个最小 `package.json` 就能用 `node`（或 `bun`）跑：

```json
{ "name": "cancelable-nav", "type": "module" }
```

## 把零件总装成四段式主循环

演示里的 `navigate` 是玩具，真实的总装线由四个函数接力，从外到内一层包一层：

```
push(to)                      薄封装：记下 { replace } 标记
  → pushWithRedirect(to)      递归入口：resolve、写白板、判重定向、判重复、调度守卫、收尾、afterEach
    → navigate(to, from)      守卫执行器：抽离开/更新/进入三组记录，跑六段守卫，每段后插闸门
    → finalizeNavigation()    收尾：最后一次闸门、改 URL、替换状态、滚动、宣告就绪
```

几个值得点破的接线细节：

**`replace` 不是独立的路。** 它的实现就是 `push(to, { replace: true })`，整个主循环只有 `push` 一条路，靠一个 options 标记区分是压栈还是替换。少一条路就少一处要维护取消逻辑的地方。

**进 `pushWithRedirect` 的第一件事是 resolve + 写白板。** 先把目标（可能是个 `{ name, params }` 或相对路径）resolve 成完整位置，顺手把白板改成它。**怎么 resolve、matched 链怎么反推、params 怎么来，第 6 章（路由匹配表）讲透了**，这里只看：resolve 完的结果，就是白板上写的那个「在途位置」。

**重定向就是递归回 `pushWithRedirect` 自己。** 两种来源：路由配置末尾带了 `redirect`，由 `handleRedirectRecord` 算出新目标、递归回去；或者某个守卫返回了一个重定向（这是一种被分类好的「失败」）。两种都带着一条「我是从哪里被重定向来的」链（`redirectedFrom`）一路传下去，方便事后追溯。为防配置写出一个 A→B→A 的死循环，递归时偷偷数次数，超过 30 次就判定「无限重定向」直接拒绝。

**重复导航走捷径，但保留锚点滚动。** 如果新目标和当前位置判等（matched 链引用相等 + params 结构 + query/hash 字符串一致——**这套判等第 2 章讲过**），又没强制跳，主循环直接构造一个「重复」失败短路返回，**不**再跑守卫、**不**改 URL。但有个反直觉的细节：它仍然调用一次滚动处理。为什么？因为用户可能点的是同页面的一个锚点 `#section-2`，URL 没变（所以判等），但你确实想让页面滚到那个锚点。**滚动怎么保存恢复、为什么要在 nextTick 后才应用，第 8 章讲透了**，这里只看这一个调用时机。

## 拿到失败之后怎么分支

守卫跑挂了、被拦了、或者干脆被别的导航挤掉了——这些「失败」落到主循环手里，并不是一刀切地当错误处理。第 4 章（导航失败的语义化分类）已经讲透了：失败不是笼统的 reject，而是用位标志 + Symbol 鸭子判定，建模成「中止 / 取消 / 重复 / 重定向」几种**可按位查询、可跨 realm 的可恢复值**。这里只看主循环拿到这些值之后，怎么分别对待：

```
重定向  → 不是失败，是「换目标」：递归回 pushWithRedirect，带上 redirectedFrom
取消    → 整条链短路，不收尾、不改 URL、不替换状态（新导航会自己来收尾）
重复    → 短路返回，但仍触发一次滚动（同锚点跳转）
中止    → 守卫主动说不去，短路返回，上层按需报错
```

注意「取消」是最安静的：它不该被当成错误抛出去吓到上层（毕竟取消是正常的、用户连点导致的），所以它被特意建模成一种「可恢复值」而不是抛异常——这也是第 4 章那位「避免把正常取消误报成未捕获异常」的权衡在本章的体现。

## 收尾：一切就绪后的落地点

六段守卫全过、最后一次闸门也通过了，就进 `finalizeNavigation`。这是整台机器的落地点，按固定顺序做五件事：

1. **最后一次查取消**——守卫跑完了，但万一在跑守卫的最后一刻又来了新导航？再比对一次白板，确认还是自己，才继续。
2. **判断是不是首次导航**（起点是不是那个 `START_LOCATION` 哨兵）。首次导航强制走 `replace` 而不是 `push`，因为这时候历史栈还没有这条记录可压。
3. **改 URL**：按 push/replace 调底层 history 的 `push` 或 `replace`。**history 那套 push/replace/go/listen 接口、html5/hash/memory 三实现怎么透明可换，第 5 章讲透了**——这里只把它当成一个「能改 URL 的小盒子」用。
4. **整体替换当前路由**：`currentRoute.value = 目标位置`。就这一句，是驱动视图更新的唯一动作。
5. **处理滚动 + 宣告就绪**。

至于浏览器的前进/后退按钮，是通过 history 的 `listen` 回调接进来的，它最终也走 `navigate` + `finalizeNavigation` 同一条收尾路，只是标记成「不是 push」。如果这条前进/后退导航失败了（比如被守卫拦下），监听器会按方向信息用 `history.go(-delta)` 把栈退回去——浏览器地址栏已经变了，得退回原样。

## 关键权衡

### 权衡 1（全章灵魂）：用「一个可变变量做在途令牌 + 手动散布检查点」，换来「无需 AbortController、一次引用比较即作废整条链」

**选择**：取消机制不引入 `AbortController`、不定义取消 token、不在每个 promise 上包取消逻辑，而是用**闭包里一个可变的 `pendingLocation` 变量 + 在六个守卫阶段之间各手动 push 一个检查函数**。

**换来**：整套取消逻辑极其薄——取消判断永远是一次 `pendingLocation !== to` 的引用比较，不需要把一个 abort signal 一路穿透六段守卫、穿透那些被 `guardToPromiseFn` promise 化的旧式 `next` 回调。要知道，旧式回调的签名根本没有地方塞 signal，硬塞就得改 API、改类型、改所有第三方守卫。公共白板绕开了这一切：不管守卫是新 API 还是旧回调，它只要是个 promise，主循环就能在它后面插一道闸门。

**代价**：闸门是**手动**塞的，不是自动包的。没有 `withCancel(guard)` 这种高阶函数帮你统一处理——每新增一个守卫阶段，维护者必须记得在那个阶段之后补一次检查。漏掉一个，那个阶段和下一段之间的空窗就成了幽灵的温床：旧导航在那个漏掉的空窗里恢复了，没人拦它，它会一路跑到收尾、把旧页面盖到新页面上。另外，这个令牌是**闭包里的可变变量**，它是 router 实例私有的，外部、跨 realm（比如另一个 iframe 里的代码）都没法强制取消你——它只能被「同一条主循环里的新导航」改写。

一句话：它用「手动 + 显式」换来了「极薄 + 兼容旧 API」，代价是把「记得插闸门」的责任交给了人。

### 权衡 2：用「浅响应承载当前路由、只在最外层整体替换」，换来「matched/params 的内部变更不触发深重渲染」

**选择**：`currentRoute` 用 `shallowRef` 包，收尾时只做一句 `currentRoute.value = toLocation`，整体替换引用。

**换来**：当前路由对象里有深结构——`matched` 是一串带组件实例的记录数组，`params` 是个对象。如果用深响应（`ref` 或 `reactive`），用户在某个地方 `route.params.id = 5` 这种内部字段变更，会触发所有用到路由的组件重新渲染。换成浅响应后，**只有整个路由切换**（引用变了）才触发更新，组件实例和 params 对象的内部变化完全不引起重渲染。这对一个「一次导航只该刷新一次视图」的系统来说，是更贴语义的粒度。

**代价**：消费者**不能**直接 mutate 当前路由的内部字段（`route.params.id = 5` 不会触发更新），必须走「整体替换引用」的路子。而且 Options API 的 `$route` 还需要额外一层代理对象：构造一个空对象，给它的每个字段定义一个 getter 指向 `currentRoute.value[该字段]`，再用 `shallowReactive` 包一层——这样 `$route.params` 才能既保持响应式、又自动跟随 `currentRoute` 的浅替换。

### 权衡 3：把「历史监听器的挂载」推迟到首次导航成功之后，换来「初始导航不被二次触发、多 app 不重复 push」

**选择**：不在创建 router 时就挂 `history.listen`，而是把它塞进 `markAsReady`——只在**首次导航收尾**（或失败）时，才第一次挂监听器。

**换来**：如果监听器在构造期就挂上，那 `install` 阶段触发的初始 `push(routerHistory.location)` 就可能被自己挂的监听器当成一次「浏览器前进/后退」再处理一遍——一次初始导航被触发两次。把挂载推迟到首次导航落定之后，就保证了「先有 URL 落定，监听器才开始监听」的顺序。多个 app 共用同一个 router 时，也不会因为每个 app 都 install 而重复 push。

**代价**：在「就绪」之前，浏览器的前进/后退按钮不会被捕获。但这个窗口期本来就不该有用户交互（app 还没初始化完），而且 `router.isReady()` 返回一个 promise，给了上层一个明确的「现在可以交互了」的时间点——首次导航失败时它也会 reject，让上层能捕获到启动错误。

### 权衡 4：诊断信息用「稳定码目录 + why/fix 严格分离 + 裸表达式调用点」，换来「可 tree-shake、码号稳定可断言」

**选择**：所有运行时警告集中在一个 `defineDiagnostics({ codes })` 目录里。每条诊断有三个固定部分：一个永久稳定的码（`VUE_ROUTER_R####`）、一个 `why`（只讲出了什么问题，不提怎么补救）、一个 `fix`（只讲怎么补救，不重复问题）。而调用点全写成裸表达式 `diagnostics.R0008({ ... })`，而不是 `if (cond) return diagnostics.R0008(...)`。

**换来**：`why` 和 `fix` 互补不重复，读者看一眼问题、再看一眼方案，信息不冗余。裸表达式调用没有返回值依赖，整个调用语句能被生产构建直接 tree-shake 掉——线上包不带任何诊断字符串。码号永远不变，测试可以稳定地断言「这个场景触发了 R0008」。

**代价**：每加一条诊断，都得维护「码号 + 双字段 + 文档链接」三样东西；调用语法被约束成不能依赖返回值（你想 `return` 点什么就得另写）。

## 小结

这章没有发明任何新零件。它的全部贡献，是把前面造好的零件**编排成一条可取消的主循环**，并补上三样「零件之间」的东西：一块记录在途导航的公共白板（在途令牌）、散布在守卫阶段之间的取消闸门、以及一个把「改 URL + 换状态 + 滚动 + 就绪」串到一起的收尾函数。核心就一句话：**用一个可变变量加几次引用比较，把又长又异步的导航变成随时能被取消的状态机**——这是整台机器得以不出现幽灵导航的根本。

导航主循环把结果落到了 `currentRoute.value`，并且整体替换它来驱动视图。那么，视图那头——`RouterView`——是怎么读这个 `currentRoute`、又怎么凭 matched 链自动选出该渲染哪一层组件、实现零配置的嵌套渲染的？这就是下一章《RouterView 嵌套渲染》要拆的。
