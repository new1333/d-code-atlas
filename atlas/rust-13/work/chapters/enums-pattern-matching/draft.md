# 代数数据类型：枚举与穷尽模式匹配

> 本章属于 primitive 层。前置：Rust 的设计哲学与编译模型总览。
> 学完你能：用一句话讲清「为什么 Rust 用 `enum` + `match` 把『漏处理一种状态』从运行时崩溃前移成编译期错误，以及为此付出了什么代价」。

## 1. 为什么需要它（设计动机）

上一章讲数据该放栈还是堆、该 Copy 还是 Clone，通篇拿 `struct` 当例子——它把若干字段「一起」摆好。可 `struct` 只会表达「同时拥有这些字段」这种关系：一个用户既有名字又有邮箱，一个矩形既有宽又有高。

现实里的状态常常不是「都有」，而是「非此即彼」：一次登录要么登录中、要么已登录、要么已登出；一次请求要么成功、要么失败；一个值要么有、要么没有。硬要用 `struct` 去装这种互斥状态，你就得写一堆可空字段再加一串 `if` 去猜「现在到底是哪种情况」——字段之间该同时为空、还是恰好一个有值，全靠注释和人脑约定撑着。

写过 JS/TS 的人对这种坑更熟：你用一个带 `kind` 字段的对象、或者一个联合类型配 `switch` 去描述「几种形态之一」。然后某天给类型加了一种新形态，某个角落里的 `switch` 忘了处理。因为你顺手写了 `default` 兜底，运行时静默走进默认分支，产出一份谁也解释不了的离谱数据。又或者你用 `null`/`undefined` 表示「没有」，于是任何引用「可能」是空的，忘了判空就在用户脸上炸成一个 `TypeError`。

这两类 bug 的共同点是：**「漏处理某一种情况」要到运行时才暴露**。Rust 想把这件事往前挪。这和第 1 章讲的那条主轴是同一个哲学——把 JS 里由运行时兜底的问题前移到编译期——只不过前几章前移的是内存（所有权、借用、生命周期），本章前移的是**状态合法性与控制流分支**这条全新的轴。

## 2. 核心思想

`enum` 是真正的**求和类型**（sum type）：变体之间是「或」的关系，与 `struct` 这个「积类型」（「与」的关系）正好对偶。「代数数据类型」的名字就是这么来的——类型的代数里，积对应 `struct`，和对应 `enum`。

光有求和类型还不够。灵魂在于：`enum` 是一个**封闭集合**，编译器认识它全部的变体；于是 `match` 分支时，编译器能逼你把每一种变体都处理掉——**把「漏掉一种情况」从运行时崩溃，变成编译期就过不去的错误**。

## 3. 心智模型

把 `enum` 想成一个「带标签的盒子」，盒子里同一时刻只放得下一种形状的东西。

- **定义**：用 `enum` 列出若干互斥变体，每个变体可以带不同类型、不同数量的负载（也可以什么都不带）。编译器据此生成一个「判别式（tag）+ 负载」的求和类型。tag 就是一个小整数，记录「现在激活的是哪个变体」。
- **构造**：你想造一个值，只能用某个变体的名字精确地造。值一造出来，它的 tag 就钉死了——「它是谁、带了什么」就此确定，运行时不可能凭空变成另一个变体。
- **解构访问**：想读变体里的负载，必须用 `match`（或 `if let`）把它「拆开」。编译器先看 tag 选分支，进入分支后才把负载绑定到你起名的变量上。你不能像 `struct` 那样直接 `obj.field` 点出来——因为别的变体根本没这个字段。
- **穷尽校验**：编译器要求分支覆盖所有变体，或者你显式用 `_` 兜底。漏掉任意一个，编译失败。
- **演进闭环**：给 `enum` 加一个新变体，所有没覆盖它的 `match` 立刻编译报错，编译器逐个指给你看该补哪儿。
- **没有 `null`**：「可能缺失」这件事，标准库用一个叫 `Option<T>` 的 `enum`（`Some(T)` 或 `None`）来表达。它不是什么新机制，就是上面这套的一个标准库应用。

整个流程可以串成一条线：

```
定义 enum（列变体 + 各自负载）
  → 用变体名构造值（tag 钉死）
  → match 按 tag 选分支、解构绑定负载
  → 编译器校验穷尽（漏了就编译失败）
  → 新增变体 → 所有未覆盖点重新编译报错，逐一补齐
```

## 4. 关键权衡

### 让变体携带异构负载，换一个类型精确建模多形态值

变体可以各带各的负载：`Move` 带两个坐标、`Write` 带一段文字、`Quit` 什么都不带。换来的是你能用**一个**类型精确刻画「一个消息可能是这几种形状之一」——事件系统、AST 节点、`Option`、`Result` 全是这个套路。没有它，你得为每种形态各起一个类型，再用 `struct` + 标志位勉强拼到一起，字段何时有效全靠约定。

代价有两条。第一，运行时整个值必须留出一个 tag 来记录当前是哪个变体（一个变体无负载也照样占位，因为值的大小要按「最大那份负载 + tag」来定，所有变体共用同一个大小）。第二，访问负载之前**必须先 match 解构**，不能直接点字段——这恰好也是它安全的来源：你不可能误把 `Write` 的字符串当成 `Move` 的坐标读出来，因为不先解构根本碰不到负载。

这里化解的本质矛盾是：「想让一个值在不同时刻是不同形状的数据」撞上「类型系统需要一个确定的大小和访问方式」。`enum` 用「一个 tag 在同一时刻只激活一份负载」把两者都照顾到了。

### 强制穷尽，换一张重构安全网

`match` 漏一个变体就编译不过。换来的是一张实打实的重构安全网：你给 `enum` 加变体，编译器会**主动**把所有该改没改的调用点揪出来，绝不让你偷偷漏掉一个。

代价是当你只想关心一种情况时，也得显式把其余情况打发掉——要么写 `_` 兜底，要么改用 `if let` 只看你关心的那一个分支。比起 JS 里「只写一个 `if`、其余爱怎样怎样」，确实啰嗦。

这里打架的两个需求是「想让代码安全地演化」和「想让日常代码尽量简洁」。Rust 一边倒选了前者：把「忘了改某处」这个最容易在重构里漏掉的 bug，变成编译器主动来找你，而不是等到线上崩了才回头查。

### 封杀 `null`，换「缺失」进入类型签名

Rust 语言层没有 `null`。一个值「可能缺失」，由 `Option<T>` 的 `None` 来表达。换来的是「这个值可能没有」直接写进了类型签名，编译器盯着你必须处理 `None`，再没有「随手忘了判空」这回事——被 Tony Hoare 自己称为「十亿美元错误」的空指针崩溃，在 Rust 的安全子集里从根本上无处发生。

代价是所有可能缺失的值都得 `Option` 包一层、用的时候再解包一层，和 JS「万物随时可能是 null，写代码时自己当心」的直觉正好相反，初学者会有一阵别扭。好消息是这层安全常常**真的是零开销**：编译器会做 niche 优化，复用类型里「不可能出现的位模式」来表示 `None`，比如引用永远不为空，于是空指针这个位刚好拿来当 `None` 的标记，`Option<&T>` 和一个裸指针占一样大的内存。（niche 优化的位级细节是实现行为，不是语言保证，这里知道「常常零开销」就够了。）

这里要调和的是「缺失是再正常不过的事」和「空指针崩溃必须消灭」。Rust 的做法是把「缺失」升级成一个普普通通的值（`None`），让它走和所有别的值一样的 `match` 流程——判空不再是随手可省的步骤，而是编译器盯着你做的那一步。

### 封闭集合，换穷尽性成立

`enum` 是封闭的：你没法跨 crate 给别人的 `enum` 追加变体。想扩展，只能自己定义一个新 `enum` 把人家的包一层。

换来的是穷尽性检查这件事**才有可能成立**——编译器之所以能逼你覆盖所有变体，前提就是它知道「全部」变体是什么；要是谁都能往里塞新变体，「全部」就无从谈起。

代价是与面向对象「随时子类化扩展」的思路完全相反。跨团队复用一个 `enum` 时，你只能消费它、不能扩张它。

这里对立的是「想让编译器替你守住完整覆盖」和「想随时扩展类型」——这俩本质上互斥。编译器要能穷尽，就必须知道所有可能性；而「随时扩展」恰恰意味着可能性是开放的。Rust 选了封闭，把扩展能力换成了编译期的完整性保证。

## 5. 最小原理演示

本章核心特性 TS 演不透——它的判别式联合配 `switch` 只能靠 `never` 旁路「近似」穷尽，一旦写了 `default` 兜底就不再强制，而且运行时数据还可能偏离类型。所以这里用双载体对照：先拿 TS 把它的缺陷演给你看，再用 Rust 原生 `enum` + `match` 重写同一份逻辑，让编译器亲自证明差别。

先看 TS 版，刻意暴露问题：

```ts
// 一个带 kind 标签的联合，模拟「消息可能是这几种形态之一」
type Message =
  | { kind: "quit" }
  | { kind: "move"; x: number; y: number }
  | { kind: "write"; text: string };

function handle(m: Message): string {
  switch (m.kind) {
    case "quit": return "bye";
    case "move": return `->(${m.x},${m.y})`;
    // 写了 default 兜底之后，漏掉 write 也不会报错
    default: return "unknown";
  }
}
```

这段代码在 TS 里能编译通过，运行时遇到 `write` 消息就静默返回 `"unknown"`——正是开头说的那种「漏处理走默认分支、产出离谱数据」。就算你不写 `default`、改用 `never` 做穷尽检查，只要数据是从 JSON 边界进来的，运行时仍可能冒出一个类型没列出的 `kind`。

再看 Rust 版，同样的逻辑：

```rust
// enum 列出全部互斥变体，各自带不同负载
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
}

fn handle(m: Message) -> String {
    match m {
        // 每个分支解构出负载，产出同一个类型（String）
        Message::Quit => String::from("bye"),
        Message::Move { x, y } => format!("->({},{})", x, y),
        Message::Write(text) => text,
    }
}
```

不写 `_` 兜底、也没法写默认分支漏过去——编译器要求这三个变体一个不落。想读 `Write` 的字符串，必须先 match 进这个分支把它解构出来，旁分支碰不到它。

现在演本章最有说服力的一刻：**演进闭环**。需求变了，要加一种 `Send` 消息：

```rust
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    Send(String),   // 新增的变体
}

fn handle(m: Message) -> String {
    match m {
        Message::Quit => String::from("bye"),
        Message::Move { x, y } => format!("->({},{})", x, y),
        Message::Write(text) => text,
        // 编译失败：non-exhaustive patterns，`Send(_)` 未被覆盖
    }
}
```

编译器直接拒绝编译，并告诉你 `Send(_)` 没有被任何分支覆盖。在 TS 那版，加一个 `send` 成员，那个忘了改的 `handle` 照样安安静静跑进 `default`；在 Rust 这版，编译器主动把每个该补的调用点指给你看。这就是「漏掉一种情况」从运行时 bug 前移成编译期错误的实感。

最后点一下「无 `null`」这同一机制的特例：标准库的 `Option<T>` 本质就是个双变体 `enum`。

```rust
enum Option<T> {
    Some(T),
    None,
}

// 用之前必须 match，把 None 打发掉——编译器逼你判空
fn length(s: Option<String>) -> usize {
    match s {
        Some(text) => text.len(),
        None => 0,
    }
}
```

`Option` 不是什么新东西，就是把上面那套「求和类型 + 穷尽匹配」用在「有值 / 没值」上。

## 6. 执行轨迹

拿一个具体的 `Message::Move { x: 3, y: 4 }` 走一遍。

1. **构造**：你写下 `Message::Move { x: 3, y: 4 }`，编译器生成一个值，它的 tag 被钉成「`Move`」，负载区里存着 `3` 和 `4`。从这一刻起，这个值运行时只能是 `Move`，不可能是 `Quit` 或 `Write`。
2. **进入 match**：`handle` 收到这个值，`match m` 先读 tag，发现是 `Move`，跳过 `Quit` 分支、跳过 `Write` 分支，选中 `Message::Move { x, y }` 这条臂。
3. **解构绑定**：在选中的臂里，模式 `Move { x, y }` 把负载区里的 `3` 绑定到变量 `x`、`4` 绑定到 `y`。现在这个分支里 `x` 就是 `3`、`y` 就是 `4`，可以直接用。
4. **求值返回**：执行 `format!("->({},{})", x, y)`，得到字符串 `"->(3,4)"`。因为 `match` 是个表达式，这条臂的值就是整个 `match` 的值，函数把它返回。所有臂产出的都是 `String`，类型一致。
5. **演进时刻**：现在有人给 `enum` 加了 `Send(String)`。你重新编译，编译器重新做穷尽校验，发现 `handle` 里的 `match` 没有覆盖 `Send`，于是报 `non-exhaustive patterns: 'Send(_)' not covered`，拒绝编译。你照着提示补上一条 `Message::Send(content) => content`，编译才通过。

整条轨迹演的是「解构 + 穷尽 + 演进闭环」这三件事，没碰 tag 的位级表示——那是 `unsafe` 才需要关心的。

## 7. 教学简化说明

本章演示故意省略了这些：判别式的位宽与具体内存布局、niche 优化的多缺口情形、`#[repr(C)]`、递归 `enum` 为什么需要 `Box`（点到「变体大小需编译期已知」为止）、`match` 的 binding modes 完整规则、`#[derive]` 如何为 `enum` 生成代码、以及 `enum` 与泛型/trait bound 的结合。最后这一项正是下一章的主题。

## 8. 小结

`enum` 把「一个值非此即彼的几种形态」连同各自负载一起封进一个类型里，`match` 的穷尽性检查再把「漏掉一种」变成编译期过不去的坎——你用封闭集合换来编译器替你守完整性，代价是写分支时不能再随手 `default` 掉不想理的情况，遇到「可能缺失」也得老老实实包一层 `Option`。

到这里你手里的工具是「按**值是什么**分叉」。可有时候你想抽象的不是「是什么」，而是「**能做什么**」——同一种能力，能不能让不同类型共用一段代码？这正是下一章「Trait 与泛型」要打开的另一条轴。
