# Rust 编译到 WebAssembly：前端工程师的落地接口

> 本章属于 system 层。前置：生命周期、unsafe 与 FFI。
> 学完你能：讲清为什么 Rust 是编译到 wasm 的理想源语言、wasm-bindgen 这层胶水在边界上做了什么，以及什么场景下才值得为 wasm 付出跨边界的拷贝与体积代价。

## 1. 为什么需要它

上一章讲了 unsafe 与 FFI：Rust 跟 C 之间的那条互操作边界，把安全保证从编译期证明降级为一份人工契约。那道边界一头是 C，一头是 Rust。但前端工程师遇到的边界形状不太一样：一头还是 Rust，另一头不是 C，而是跑在浏览器里的 JavaScript。

起点是一个很具体的痛点。当你在浏览器里做图像处理、视频编解码、大数组运算、复杂状态机这类**计算密集**的活时，JavaScript 哪怕有 JIT 也会力不从心，更要命的是 GC 暂停会在你最不希望的时候插一脚，带来不可预测的卡顿。换 C/C++？得拖上一个庞大运行时，再面对手动内存管理的老问题。读者真正想问的是：能不能把那 5% 真正吃性能的 hot path，用一种「没有 GC、内存行为确定、又能被浏览器原生执行」的语言来写，剩下 95% 还是 JS？

WebAssembly（wasm）就是浏览器给的这个「原生执行」的口子：一套沙箱化的字节码，可移植、不挑平台。但它出生时被设计得极其朴素，只规定了**一块连续的字节内存（线性内存）**加上**只能传几种标量（i32/i64/f32/f64）的函数调用约定**。它不认识字符串，不认识对象，不认识数组，更没有任何 DOM 或浏览器 API。

矛盾就在这儿冒出来。你在 Rust 里写一个再普通不过的 `pub fn greet(name: String)`，原生 wasm 根本表达不出「String」这个东西，它只懂两个数字。所以一定得有人**在 JS 和 wasm 之间写胶水**：把 JS 字符串编码成字节、拷进线性内存、把「指针 + 长度」这两个数字交给 wasm。手写这套胶水极其痛苦而且极易出错。`wasm-bindgen` 就是来把这件事自动化的工具，也是本章真正的主角之一。

## 2. 核心思想

wasm 这套执行模型里有一条贯穿始终的裂缝：**JS 的 GC 堆和 wasm 的线性内存是两个物理隔离的世界**，而它们之间唯一的通讯渠道是「只能传几个标量」的函数调用。核心思想就是在这条裂缝上铺一层**自动生成的翻译层**，让 Rust 侧能继续写 `String`、`Result`、甚至直接持有 JS 对象这种自然签名，由工具在编译后生成对应的 JS 胶水，把高级类型翻译成「拷贝进线性内存、再传两个数字过去」的底层动作。

而 Rust 之所以是铺这层翻译的理想源语言，关键在于它**无 GC、靠所有权加确定性析构管内存**。这意味着编译出来的 wasm 模块不必拖一个垃圾回收运行时，产物紧凑；它的内存模型又恰好能严丝合缝地落在 wasm 那块「自管线性内存」上。换个源语言（比如把 Go、C# 编到 wasm），就得把各自的 GC 运行时一起塞进 .wasm，体积和复杂度都上去了。

## 3. 心智模型：一条字符串过边界的旅程

理解本章，先在脑子里立住一个画面：**两个互不相通的世界**。一边是 JS 引擎管的 GC 堆，你平时的对象、字符串、数组都在那儿；另一边是 wasm 的线性内存，它在 JS 侧看就是一个 `WebAssembly.Memory`，底下是个 `ArrayBuffer`，一块光秃秃的连续字节。两边谁也不能直接指对方的东西，函数调用时也只能传少数标量。

记住这个画面，一条 JS 字符串要进 wasm，就得走这样一段旅程：

1. Rust 侧用 `#[wasm_bindgen]` 宏标了一个 `pub fn greet(name: String)`，宏在编译期记下「这个导出函数想要一个字符串参数」这条描述。
2. `cargo build` 以 wasm 为目标编译，产出的 .wasm 里既有这条描述，也有 greet 的真实实现，而那个真实实现只接受 `(指针, 长度)` 两个 i32。
3. `wasm-bindgen` 工具来后处理这个 .wasm：读出描述，照着生成一个 JS 胶水函数 `greet(arg)`，再把描述段剥掉。
4. JS 调 `greet("Atlas")`：胶水把 "Atlas" 按 UTF-8 编码成字节，在线性内存里分配一块、把字节拷进去，记下指针 `ptr` 和长度 `len`。
5. 胶水去调 wasm 里那个原始的 `greet(ptr, len)`；Rust 侧用 `(ptr, len)` 在线性内存里**重建**出 `String`，跑业务逻辑。
6. 返回值若也是字符串，就反过来走一遍：Rust 把结果写进线性内存、返回 `(ptr, len)`，胶水读出字节解成 JS 字符串，再调 wasm 的 dealloc 把那块内存还回去。

每一个来回，都是「分配、拷贝、释放」的三件套。这就是跨边界成本的来源。

## 4. 关键权衡

这一节是全章重点。Rust 编到 wasm 不是免费的午餐，它是一连串清醒的取舍。

### 只在 hot path 上 wasm，是这套方案的总开关

最该让读者带走的，是一个产品判断而不是一个 API。你选择把**计算密集、性能敏感**的那块模块交给 Rust + wasm，换来的是相对纯 JS 大约 2 到 6 倍的加速（任务越重差距越大），更重要的是**没有 GC 暂停、性能可预测**，这对动画、音频这类对卡顿零容忍的场景是质变。代价是实打实的：.wasm 的下载体积（里面链着堆分配器、panic 处理等一坨东西）、模块编译与实例化的冷启动开销、以及每一次跨边界的序列化成本。

这里化解的本质矛盾，是「专用引擎的极致性能」和「通用引擎的低启动成本」之间的老对立。任何「把热点切出来用更专用、更重的引擎跑」的架构都要付这个过路费。结论不是「全场用 wasm」，而是 **hot path 值得，I/O 密集或轻量任务 JS 仍然更优**。首屏着陆页这种对首次加载延迟极度敏感的场景尤其要保守，因为下载、编译、实例化是一段串行的冷启动；而在线编辑器、游戏、音视频处理这种「长会话、反复算」的场景才真正划算。具体倍数随任务和引擎版本波动，要拿自己的负载去量。

### 用胶水生成器，而不是手写原始 FFI

你可以选择手写那种「传两个数字、自己管内存」的原始 FFI，但 `wasm-bindgen` 选择的是**自动生成胶水**。换来的是你能在 Rust 里写极其自然的函数签名，心智负担大幅下降，这正是它存在的全部理由。代价是它**把跨边界的真实成本藏起来了**：一个写得像普通函数的调用，底下其实是一次 UTF-8 编码、一次内存分配、一次拷贝、一次释放。

这里化解的本质矛盾，是「人想要自然的高级接口」和「底层 ABI 只认标量」之间的鸿沟。凡是「机器生成翻译层、把高级接口降到底层 ABI」的方案，从 RPC 的 stub 生成、protobuf，到 TypeScript 的 `.d.ts`，都在解决同一件事，也都背同一个坑：**便利会让人误以为无开销**。最典型的翻车，是把一个细粒度函数放进循环里反复跨边界调用，每一次都付出一次拷贝，最后可能比等价的纯 JS 实现还慢。正确用法是「在 wasm 侧把一整块计算做完，只跨边界传一次大输入、收一次大输出」。

得点一句这里的承前关系：这条 wasm→JS 边界，骨子里就是一条 FFI 边界。上一章讲透了 FFI 会把安全保证从「编译期证明」降级为「人工契约」，wasm-bindgen 并没有打破这件事，它只是把那些 `unsafe` 收窄、藏进了工具内部，让普通使用者看不见。但边界「靠序列化加契约、而不是靠类型系统来保证」的本质，一点没变。

### 线性内存 + 自管分配器，换来无 GC 的确定性

wasm 的堆就是那一块 JS 侧的 `ArrayBuffer`，由 wasm 模块自己分配、自己释放。换来的是**没有 GC、内存行为确定、可预测**，这正是 Rust 的所有权模型能完美映射上去的原因：谁拥有、何时析构，编译期就定死了，不需要运行时再来收。代价是 Rust 必须把一个堆分配器（默认是 dlmalloc 之类）链进 .wasm，体积因此变大；而且 JS 和 wasm **始终不能共享对象**，跨边界要么拷贝、要么走间接表。

这里化解的本质矛盾，是「想要无 GC 的可预测」和「内存总得有人管」之间的张力。手动管内存换确定性，是 C/C++ 走了几十年的老路，但 Rust 的所有权让它不必重蹈「内存泄漏、悬垂指针」的覆辙。顺带一提，跨 wasm 边界时，上一章的生命周期武器是失效的：你没法用编译期生命周期去证明一段跨边界的引用有效，所以这条边界上能用的只剩**拷贝换安全**这一招，这也是为什么旅程里的每一步都在拷贝。

### 整型索引 + JS 侧对象表，换在 Rust 里持有 JS 对象

有时候你需要在 Rust 里直接操作 `window`、`document`，或者任意一个 JS 对象。可线性内存里存不下 JS GC 对象的稳定地址，GC 随时会搬动它们。`wasm-bindgen` 的解法是：在 JS 侧维护一张对象表（一个数组），把真对象挂在表里，Rust 侧的 `JsValue` 内部只是一个 u32 索引。把它想象成寄存处的号码牌：Rust 拿着号码，真东西在 JS 侧的寄存处。换来的是在 Rust 里像用普通值一样用任意 JS 对象，自然得几乎让人忘了边界存在。

代价有两条，都很真。第一，每一次属性读写、每一次方法调用，都要拿号码去 JS 侧查表、再跨一次边界，这很贵，密集调用会非常肉。第二，**Rust 侧忘了 drop 一个 `JsValue`，JS 侧那张表里的槽位就永远不会被清空，对应的 JS 对象也就永远没法被 GC 回收**，这是一条静悄悄的内存泄漏路径。这里化解的本质矛盾，是「wasm 内存存不下 GC 对象」和「想在 Rust 里把 JS 对象当一等公民用」之间的硬冲突；而解法，也就是「句柄表加不透明令牌」，是跨 GC/非 GC 边界的通解骨架，JNI 的全局引用表、Emscripten 的对象表都是同一个套路。

## 5. 最小原理演示

把上面两条最关键的原理，**跨边界拷贝**和**对象索引表**，用 TypeScript 演一遍，不必真的去编译 Rust。第一段演「高级字符串签名如何被翻译成拷贝加 (指针, 长度)」：

```ts
// 用 Uint8Array 模拟 wasm 的「线性内存」：一块光秃秃的连续字节
const memory = new Uint8Array(64 * 1024);
let heapPtr = 1000; // 极简分配器：只往前推，演原理够用

// 这是 wasm 里 greet 的真实面目：只认 (指针, 长度)，根本不认识字符串
function __greet(ptr: number, len: number): [number, number] {
  const name = new TextDecoder().decode(memory.subarray(ptr, ptr + len));
  const reply = `hello, ${name}`;
  // 结果也得写回线性内存，再把 (指针, 长度) 还给 JS
  const out = new TextEncoder().encode(reply);
  const outPtr = heapPtr; heapPtr += out.length;
  memory.set(out, outPtr);
  return [outPtr, out.length];
}

// wasm-bindgen 生成的胶水：把 greet(string) 翻译成上面的 (ptr, len)
function greet(name: string): string {
  const bytes = new TextEncoder().encode(name); // JS 字符串 → UTF-8 字节
  const ptr = heapPtr; heapPtr += bytes.length;
  memory.set(bytes, ptr);                       // 关键一步：拷进线性内存
  const [outPtr, outLen] = __greet(ptr, bytes.length); // 跨边界，只传两个数字
  const out = new TextDecoder().decode(memory.subarray(outPtr, outPtr + outLen));
  return out; // 真实工具还会调 dealloc 释放 ptr 和 outPtr 两块
}
```

第二段演 `JsValue` 的索引表，看为什么 Rust 持有的只是个号码牌：

```ts
// JS 侧的「寄存处」：真 JS 对象挂在这里，wasm 只拿号码牌
const slab: unknown[] = [undefined]; // 0 号留空，避免和「空」混淆

function __wbindgen_object_push(obj: unknown): number {
  slab.push(obj);
  return slab.length - 1; // 返回给 Rust 的，就是一个 u32 索引
}

function __wbindgen_object_drop_ref(idx: number): void {
  // Rust 侧 drop JsValue 时调它：清空槽位，JS GC 这才能回收
  slab[idx] = undefined;
}

// Rust 侧的 JsValue，在我们的模拟里就是这个形状
type JsValue = { readonly idx: number };

function getWindow(): JsValue {
  return { idx: __wbindgen_object_push(globalThis) }; // Rust 拿到的只是个号码
}

function drop(v: JsValue): void {
  __wbindgen_object_drop_ref(v.idx); // 忘了这步 = 寄存处常驻 = 内存泄漏
}
```

两段加起来四十来行，每一行都对应上面讲过的一个原理点：拷贝、指针加长度、反向回收、号码牌、drop 通知。

## 6. 执行轨迹

把 `greet("Atlas")` 这一次调用从头走到尾，看清「拷贝、指针加长度、反向回收」三件事怎么串起来：

- **输入**：JS 调 `greet("Atlas")`。
- **编码**：胶水把 "Atlas" 按 UTF-8 编码，得到 5 个字节 `[65, 116, 108, 97, 115]`。
- **写入内存**：把这 5 字节拷进线性内存偏移 `1000` 处，`heapPtr` 推进，记下 `ptr=1000, len=5`。
- **跨边界**：胶水调原始的 `__greet(1000, 5)`，只传了两个数字过界。
- **Rust 侧重建**：用 `(1000, 5)` 从线性内存读回那 5 字节，重建出 `name = "Atlas"`，拼出 `reply = "hello, Atlas"`（11 字节）。
- **写回**：把 11 字节写进偏移 `2000` 处，返回 `(2000, 11)`。
- **反向解码**：胶水读 `memory[2000..2011]`，解成 JS 字符串 `"hello, Atlas"`。
- **回收**：胶水通知 wasm 释放偏移 `1000` 和 `2000` 这两块（演示里省略了这步，原理上必须有）。
- **输出**：JS 拿到 `"hello, Atlas"`。

一次最简单的字符串往返，背后是两次分配、两次拷贝、两次回收。这就是「写得像普通函数」的真实账单。

## 7. 教学简化说明

本章演示故意省略了一堆东西，免得它们遮住原理：真实的 .wasm 二进制和它的段结构、`wasm-bindgen` 完整的代码生成细节、`wasm-opt` 的体积优化、多线程与 SIMD、`wasm-pack` 从 build 到打包的完整流程、TypeScript 类型定义的生成，以及 `serde-wasm-bindgen` 这类序列化方案的对比。它们都是值得单独深挖的工程话题，但都不是理解「为什么跨边界要拷贝、为什么 JS 对象要用索引表」的必要前提。

## 8. 小结

走到这里，全书的那条主线终于落地了。Rust 那套「所有权加借用加生命周期加确定性析构」的机制，加上 `unsafe` 这道可审计的逃逸舱，最后在前端工程师最熟悉的浏览器里，变成了 wasm 模块那块自管的线性内存和一层自动生成的胶水。hot path 用 Rust + wasm 换来无 GC 的可预测性能，其余仍是 JS，这个判断比任何 API 都值得记住。边界没消失，它只是被工具收进了内部，而你现在知道那层胶水底下，每一次调用都在付着拷贝的账单。
