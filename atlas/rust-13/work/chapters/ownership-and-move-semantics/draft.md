# 所有权与移动语义：取代 GC 的核心机制

> 本章属于 primitive 层。前置：Rust 的设计哲学与编译模型总览。
> 学完你能用一句话讲清：Rust 怎么靠「每个值只有一个主人、主人走了就回收」这套规则，在不要垃圾回收器的前提下把内存管好，以及这个选择换来什么、又付了什么代价。

## 1. 为什么需要它

上一章把 Rust 的整体打法摆了出来：把 JS 里交给运行时和垃圾回收器兜底的事，前移到编译期做静态检查。那是一张总图。它还没回答最具体的一问——一块数据在内存里，到底归谁管、什么时候回收？本章就接着这一问往下拆。

如果你从 JS 过来，最先撞的墙大概是这样的：

```rust
let s = String::from("hi");
let t = s;                // 看起来只是把 s 赋给 t
println!("{}", s);        // error[E0382]: borrow of moved value: `s`
```

在 JS 里，把一个对象赋给另一个变量，是让两个名字共享同一份引用，谁都能读写，等所有人都放手了 GC 才把它收走。你从来不需要想「这块数据现在归谁」。而 Rust 在第二行就给 `s` 判了「死刑」：它被移走了（moved），再读 `s` 就是编译错误。初学者的本能反应往往是到处加 `.clone()` 把数据复制一份来消掉报错，但这恰恰绕开了 Rust 要你做的判断——「这份数据到底该归谁」。

为什么 Rust 要这么较真？因为内存回收这件事，现有的两条路都不让人满意：

- **GC 的路**：回收被推迟到「某个不确定的未来」。你不知道它什么时候来、会停顿多久，对延迟敏感的场景（游戏帧、实时响应）总像头顶悬着个不确定因素。
- **C/C++ 手动管理的路**：自由过了火，`free` 同一块内存两次（double-free）、释放完再去访问（use-after-free）是养活了一大批安全漏洞的经典错误。

Rust 选了第三条路：把「这块数据归谁」和「何时回收」这两件事，钉死在两个完全确定的事实上——它有唯一的主人，以及主人在一个确定的时刻离场。于是「什么时候回收」从一个运行时才知道的随机事件，变成了一件一开始就有确定答案的事。

## 2. 核心思想

每个值都有唯一的主人；主人一换，所有权就跟着转移；主人一离场，值就被销毁。转移和销毁这两件事，编译器在编译期全程追踪。于是 Rust 不需要任何运行时的回收器插手，就能保证每个值被释放、且只被释放一次。

## 3. 心智模型

Rust 的所有权建立在一个简短到像公理的规则上：

1. 每个值都有唯一的所有者（owner）。
2. 同一时刻只有一个所有者。
3. 所有者离开作用域，值就被自动销毁（drop）。

这三条是整套机制的根。下面看它们怎么长出 move 语义和析构。

**赋值和传参默认是「转移」（move）。** 当你写 `let t = s;`，或把 `s` 传进一个函数，`s` 的所有权就交出去了，`s` 此后不可再用：

```rust
fn greet(name: String) {       // name 接管传入值的所有权
    println!("Hello, {name}");
}

let s = String::from("Ada");
greet(s);                       // s 的所有权 move 进 greet
// println!("{}", s);           // 这行会报错：s 已被移出
```

所有权也能反着传回来：函数把值返回，所有权就从函数内部 move 回调用者。所以「谁拥有它」是在函数签名里就写死了的——拿走还是借走，看一眼签名就知道。

**有一个例外：`Copy` 类型。** 整数、布尔、浮点这些「按位复制就完整」的类型实现了 `Copy` trait，赋值时是老老实实复制一份，原变量照常可用：

```rust
let a = 5;
let b = a;            // i32 是 Copy，按位复制
println!("{}", a);     // 正常：5
```

而 `String`、`Vec` 这类「自己管着堆上一块数据」的类型不是 `Copy`，赋值只能 move。为什么不能让它们也 Copy？因为按位复制会把「指向同一块堆数据的指针」复制成两份，两个主人各自离场时就会释放同一块内存，正好是 double-free。`Copy` 的完整判定规则（哪些类型能 Copy、`Copy` 和 `Clone` 的关系）留到「栈与堆」一章细讲，这里只要记住这个结论。

**离场即析构，且只析构一次。** 当一个值的主人走到它作用域的末尾，编译器自动给它插一个析构调用，释放它拥有的资源：

```rust
{
    let s = String::from("hi");   // s 进入作用域，成为主人
}                                  // s 离场 → 自动 drop，堆内存释放
```

关键在「主人」两个字：析构只发生在**此刻仍是主人的那个名字**身上。如果值在离场前已经被 move 走了，原名字就不再是主人，离场时什么也不会发生：

```rust
{
    let s = String::from("hi");
    let t = s;        // s 被移出
}                      // t 离场 → drop 一次；s 已不是主人 → 静默跳过
```

这就是「无 double-free」的直接来源：每个值有且只有一个主人，所以析构必然恰好一次。

## 4. 关键权衡

这是本章的重头戏。所有权不是一个孤立的语法点，它是一连串设计取舍的结果。

### 默认移动，把「归谁」写进每一次赋值

Rust 让赋值和传参默认 move，而不是像 JS 那样默认共享引用、也不是默认深拷贝。换来的是：每一次值的传递都明确表达了「所有权交给你了」，数据归属一目了然，而且大对象不会在你不知情的情况下被整份复制。

代价是真实的心智冲击。从 JS「对象赋值就是共享同一份引用」的直觉里出来，你得重新建立「值语义」的反射，什么时候会 move、move 之后哪个变量作废，全要在脑子里过一遍。而最容易掉进去的坑，是用 `.clone()` 把每个报错都糊过去：它能消掉编译错误，却也替你掩盖了「这份数据到底该归谁」这个本该由你做的设计判断，还顺带付了一笔真实的深拷贝开销。

这条权衡化解的本质矛盾，是**「数据共享的便利」和「数据归属的清晰」**在打架。JS 选了前者，把回收丢给运行时的 GC；Rust 选了后者，把判断还给程序员，换回编译期的内存安全。

### 单一主人加确定离场，换「可预测」的回收

把回收时机钉死在「主人离场那一刻」，换来的是回收完全可预测：没有 GC 的停顿，没有不可控的内存峰值。更妙的是，这套机制不只管内存——锁、文件句柄、网络连接，凡是实现了析构的资源，都能在确定的那一刻被立即释放。这就是 RAII（资源获取即初始化）在 Rust 里自然落地的方式。

代价是，你必须时刻想清楚「现在谁拥有它」。这件事甚至会渗透到函数签名里：一个参数是 `String` 还是 `&String`（下一章的主角），传达的是完全不同的意图，要么「我要拿走它」，要么「我只是借来用」。在 JS 里你从不需要在函数签名上做这种表态。

这条权衡化解的本质矛盾，是**「回收时机的可预测」和「使用时的灵活共享」**在打架。GC 用不确定的时机换来了随时共享的自由；Rust 用确定的离场换来了可预测的回收，把共享的灵活性往后推给了借用机制。

### move 在内存层是「复制栈表示」，不是物理搬迁

move 这个词很容易让人以为运行时真的「搬」了一下数据。其实没有。move 在内存层面做的是：把值在栈上的那份表示（比如 `String` 的「指针、长度、容量」三元组）按位复制到目标位置，再把源绑定在编译期标记为不可用。堆上的数据本身一个字节都没动。

打个比方：move 不是搬家，而是房产证过户——房子（堆数据）还立在原地，只是房产证上的名字（合法主人）从 `s` 换成了 `t`。

换来的是 move 几乎零成本（不复制堆数据），同时又安全（析构只跑一次）。代价薄到几乎不用展开：move 是一个编译期的语义概念，运行时看不到任何「搬迁」动作，所以在调试器里你不会看到一次迁移发生，得理解「值的表示」这层抽象，才能解释清楚变量的生死。

这条权衡化解的本质矛盾，是**「想要转移所有权」和「不想付出复制成本」**在打架。C++ 的 move 还得靠 move 构造函数这种运行时机制；Rust 把整件事变成「按位复制栈表示加编译期作废旧绑定」，把成本压到了零。

## 5. 最小原理演示

下面用一个极简的 JS 小模型，演透前面三件事：值身上记着主人、move 怎么换主人、离场怎么只析构一次。这不是真实的 Rust 编译器，而是把所有权的几条规则建成一个你能在脑子里跑一遍的玩具。

```ts
// 极简所有权模型：用 JS 演透「单一主人 + 转移 + 离场析构恰好一次」
let nextId = 0;

// 一个带「主人标记」的值：id 标识它持有的那份数据，alive 表示这个名字还是不是合法主人
type Boxed = { id: number; data: string; alive: boolean };
const makeBox = (data: string): Boxed => ({ id: nextId++, data, alive: true });

// move：把值的表示复制给新主人，再让旧名字失效
// 这正对应 Rust 里「源绑定在编译期不可再用」
const move = (src: Boxed): Boxed => {
  const dst: Boxed = { ...src };   // 新主人拿到值的表示（堆数据概念上未复制）
  src.alive = false;               // 旧主人在编译期失效（真实 Rust 里是编译错误，这里用标志模拟）
  return dst;
};

// 离场析构：只对「仍是合法主人」的值触发一次
const endScope = (v: Boxed) => {
  if (v.alive) {
    console.log(`drop #${v.id}（释放 "${v.data}"）`);
    v.alive = false;               // 析构后标记，防止重复释放
  }
  // 已被 move 走的（alive===false）什么都不做，这就是「无 double-free」的来源
};

const a = makeBox("hi");   // a 成为 #0 的主人
const b = move(a);         // a 失效，b 接管 #0；堆上的 "hi" 一字未动

endScope(a);               // a 已不是主人：静默跳过
endScope(b);               // b 是当前主人：drop #0，恰好一次
// 控制台输出：drop #0（释放 "hi"）
```

跑完这段，你会看到析构只发生了一次，落在那个还活着的主人 `b` 身上。`a` 因为早就不是主人了，离场时被安静地跳过。整套机制要保证的，就是这么一个朴素的性质：**每个值恰好被析构一次**。

## 6. 执行轨迹

把一段真实的 Rust 代码掰开，看每一步到底发生了什么：

```rust
let s = String::from("hi");
let t = s;
```

第一步，`String::from("hi")` 执行：在堆上分配一块内存存下 `"hi"` 这几个字节；栈上的 `s` 绑定拿到一个三元组 `(指针, 长度=2, 容量)`，其中指针指向那块堆内存。此刻 `s` 是这块数据的唯一主人。

第二步，`let t = s;` 执行 move：

- `s` 在栈上的三元组被按位复制到 `t`，于是 `t` 的指针也指向同一块堆内存；
- `s` 被编译器标记为「已移出」，此后任何对 `s` 的读取都是编译错误（`borrow of moved value: s`）；
- 堆上的 `"hi"` 一个字节都没动。

接下来如果再写 `println!("{}", s)`，编译期就过不去；而 `t` 可以正常用。

最后到了作用域末尾：`t` 是当前主人，离场时被析构一次，那块堆内存随之释放；`s` 虽然也声明在这个作用域里，但它早就不是主人了，离场时被跳过。这块堆内存最终被释放了恰好一次，double-free 在编译期就被排除掉了。

## 7. 教学简化说明

本章演示故意省略了这些东西：借用与引用（下一章）、生命周期标注（第 4 章）、`Copy`/`Clone` 的完整对比与栈堆存储全景（第 5 章）、结构体的部分移动、自定义 `Drop` 的写法、`std::mem::drop` 提前释放、析构逆序的边角。玩具模型用布尔标志模拟了编译期的「移出」判定，真实 Rust 里这是编译期完成的，没有任何运行时开销。

## 8. 小结

Rust 用「每个值只有一个主人、主人走了就回收」这么几条近乎公理的规则，把内存回收从一个运行时的不确定事件，变成了一件编译期就能证明的确定事实。代价是你得重新建立「数据归谁」的反射，并在函数签名上明明白白地表态。

但这套规则有个直接的后坐力：如果每次想用一下数据都得交出所有权，写起代码来会非常啰嗦。于是很自然地就有了一个需求——能不能「借」来用，而不夺走它？这正是下一章「借用与引用」要解决的问题。
