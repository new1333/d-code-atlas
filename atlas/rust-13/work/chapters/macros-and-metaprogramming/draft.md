# 宏系统：编译期代码生成

> 本章属于 composite 层。前置：Rust 的设计哲学与编译模型总览。
> 学完你能：讲清为什么 Rust 在「函数 + 泛型 + trait」之外还需要第三类抽象工具——宏，以及它用「极强的表达力」换来了什么代价。

## 1. 为什么需要它（设计动机）

上一章讲智能指针，是把借用规则从编译期「降级」到运行期——当编译器证明不了某种共享与可变的组合时，用 `RefCell` 在运行时再检查一遍，给类型系统开了一个**运行时的逃生舱**。本章要讲的是另一个方向的口子：类型系统**本身**表达不了的抽象，靠编译期「生成」代码来解决。

具体到写代码的场景。你写过 `vec![1, 2, 3]` 吧？这一行想要展开成「先建一个空容器，再挨个 push 进去，最后返回它」。这里头的 push 语句**数量不固定**——三个元素就三条、十个就十条。你又写过 `#[derive(Debug, Clone)]`，加这一句就想让编译器替你的 struct 凭空写出两个 `impl` 块。

现在你手上只有三种抽象工具：函数、泛型、trait。挨个试一遍：

- 函数做不到。函数调用是一次求值，它没法「在调用点凭空变出 N 条语句」，更没法在调用者的作用域里插入变量声明。
- 泛型做不到。泛型是「同一个函数适配多种类型」，它能换类型，但不能凭空新增一个 item（比如一个新的 `impl` 块）。
- trait 做不到。trait 声明的是能力契约，它要求你**已经写好**了实现，并不能替你把实现变出来。

这就是矛盾所在：你需要「生成代码结构本身」的能力，但 Rust 现有的抽象工具全都只能组合已有的代码，不能生产新的代码骨架。于是遇到这类需求，你只能手写大量长得一模一样的样板。

宏就是为了填这个空洞而存在的第三类工具。第 1 章讲过 Rust 把问题前移到编译期这个大方向，但前面十几章——所有权、借用、生命周期、trait——前移的都是编译期「**检查**」。本章看的侧面不同：编译期「**生成**」。检查是你写好代码编译器来验证，生成是编译器替你写。

## 2. 核心思想

一句话：**宏是在类型检查之前的解析阶段，对代码的 token 流做变换的代码生成器。**

这里有个关键的不寻常之处：宏处理的既不是运行时的值，也不是已经组装好的语法树，而是代码本身的「零件」——token。函数吃进去的是值，吐出来的也是值；宏吃进去的是一段还没做完类型检查的代码碎片，吐出来的是另一段代码碎片，再交给后面的类型检查器去校验。

打个比方点透这层区别：如果说写函数像是在算账（输入数字算出数字），那写宏更像是排版——你摆弄的是活字（token）本身，把一组活字按模板排成另一组活字，排完才送进印刷机（类型检查）。

## 3. 心智模型

### 3.1 token 树：宏的统一数据结构

编译器拿到源码后，先切成一个个 token（标识符、字面量、符号）。但宏不是在一个扁平的 token 序列上干活，而是在 **token 树**上。token 树的递归定义很简洁：

- 要么是一个叶子 token；
- 要么是一组被 `()` / `[]` / `{}` 包起来的子树，子树内部又是一片 token 树。

括号必须配对这件事，由树结构本身保证，宏的匹配规则因此不需要自己去数括号。声明宏和过程宏都工作在这一层，**而不是**在抽象语法树上。这是个常被忽略的事实：宏看到的代码比 AST 要「生」得多，它连「这是一个表达式」都还不确定，只看到一堆 token。

### 3.2 两套引擎

Rust 有两套宏引擎，共享同一个时机（类型检查前）和同一个数据层（token 树），但变换方式截然不同：

- **声明宏**（`macro_rules!`）：你写一组「模式 → 模板」的替换规则，编译器照着做模式匹配替换。`vec!`、`println!`、`format!` 这些你天天用的都是声明宏。
- **过程宏**：你写一个普通的 Rust 函数 `fn(TokenStream) -> TokenStream`，把输入 token 流变换成输出 token 流，图灵完备。它分三种入口：`#[derive(Foo)]` 给 struct/enum 追加 trait 实现、`#[my_attr]` 注解并可能替换整个 item、`foo!(...)` 像函数一样调用但吃任意 token 流。Serde 的 `#[derive(Serialize)]` 就是典型。

注意一个易混点：声明宏**不是函数**。它不参与类型签名、不能当 trait 方法、不能作为值传来传去，它只在解析期做 token 替换。过程宏虽然是一个真函数，但它跑在编译器进程里，吃的是 token 流而非运行时值——把它当「编译期执行的普通函数」只对了一半。

### 3.3 展开在编译流水线里的位置

宏的时机可以用一条流水线讲清楚：

```
词法分析 → 解析（含未展开的宏调用节点）→ 宏展开（反复直到没有宏）→ 完整 AST → 名称解析 → 类型检查 → ...
```

关键在于：宏展开是解析阶段的一部分，发生在类型检查**之前**。展开可能反复进行——宏生成的代码里如果还有宏调用，就继续展开，直到整份代码里一个宏都不剩。此时才得到完整的 AST，类型检查器才进场。

这意味着宏的变换逻辑本身**见不到任何类型信息**。它瞎着眼睛在 token 层搬弄，搬完了，类型检查器才睁开眼检查搬出来的结果。

## 4. 关键权衡

### token 层操作换任意结构生成，代价是宏对类型检查隐身

宏之所以能干函数和泛型干不了的事（注入任意条语句、批量生成 `impl`、在编译期解析格式串），根本原因就是它选了一个比类型系统更底层的工作层——token 流。在 token 层，它不受类型规则的约束，能拼出任何结构合法的代码。

换来的是覆盖三大场景的能力：自定义语法（写 DSL）、自动派生（`#[derive]`）、消除重复样板。

代价是真实且扎手的：**宏本身不参与类型检查，只有展开后的结果参与**。这带来一连串后果。错误被延迟到展开后才暴露；宏内部写错了，报错往往指向展开后的那行代码而不是你的宏调用点，你看着一个陌生的行号根本对不上自己写了什么；调试时你不得不借助 `cargo-expand` 把展开结果打印出来，才能看到宏到底生成了什么。对比泛型在单态化之前就会按 trait bound 做检查，宏是彻底的「事后检查」，可见性差了一大截。

这条权衡化解的本质矛盾，是「**表达力**」与「**可静态分析的透明度**」之间的对立。你越是想要绕过类型系统去生成代码结构，类型系统就越看不见你在干什么；反过来，凡是类型系统能直接表达的抽象，就根本不需要付出这个代价。

### 声明宏用模式匹配替换换零解析器成本，代价是受困于固定片段分类符

声明宏定义一个宏只要写「匹配什么 → 替换成什么」，编译器替你完成匹配和替换，你不用手写解析器。定义本身就是文档：读 matcher 就知道它接受什么形状的输入。对绝大多数常见场景，这套机制足够强——`vec!` 和 `println!` 这种标准库主力都是声明宏。

代价藏在「匹配」的能力边界里。matcher 里的「洞」只能按固定的几种**片段分类符**来匹配——`expr`（表达式）、`tt`（单个 token 树）、`ty`（类型）、`ident`（标识符）等等。你不能凭空发明一种新的匹配类别。更折磨人的是 follow set 限制：某些分类符（如 `expr`）之后，matcher 里只能紧跟特定的 token（如 `=>` / `,` / `;`），否则编译器没法判断这个片段该在哪结束。于是一些略复杂的自定义语法你根本写不出来，只能退回去用过程宏。声明宏递归展开时的调试也以痛苦著称。

本质矛盾是「**机制简单性**」与「**语法表达力**」之间的取舍。模式匹配替换足够机械、足够可预测，所以才能被编译器廉价地实现、让宏作者免写解析器；但机械的代价就是不能灵活地描述任意语法。

### 过程宏用普通函数换图灵完备生成，代价是工程负担与编译开销

当声明宏的表达力不够时，过程宏给出了终极方案：它就是一个普通的 Rust 函数，输入 token 流、输出 token 流，你想怎么算就怎么算，图灵完备。它能解析任意的自定义 DSL，能一次派生多个 item（Serde 靠它一个 derive 同时生成 `Serialize` 和 `Deserialize`）。

代价分两层。工程层：过程宏**必须**拆成一个独立的 crate（在 `Cargo.toml` 里标注 `proc-macro = true`），不能在定义它的 crate 内部使用它——因为它要在编译期被先编译成可执行代码、由编译器加载去运行，跟使用方混在一起会产生先有鸡还是先有蛋的引导问题。所以你几乎一定得依赖 `syn`（把 token 流解析成语法树）、`quote`（用类 Rust 语法反向拼回 token 流）这套工具链，错误诊断还得自己手写 `Span` 去定位。性能层：过程宏会显著拖慢编译。

本质矛盾是「**生成能力**」与「**工程纪律**」之间的对立。能力越接近「随便写程序」，就越要求你把它当成一个独立的小工程来对待——单独的 crate、专门的解析与拼接库、自己处理报错定位。这正是为什么 Rust 社区有个强惯例：能用 trait/generics 解决就别上宏，宏是最后手段。

### 卫生性换免于变量捕获，代价是注入标识符要绕路

如果你用过 C 的宏，多半被坑过：宏体里的某个变量名意外地「捕获」了调用点的同名变量，或者反过来，因为 C 宏就是纯文本粘贴，对作用域毫无知觉。

Rust 宏从根上治掉了这个病。它给宏展开产生的每个标识符打上一个看不见的「语法上下文」标记。两个标识符要被认为是同一个，光名字相同不行，连语法上下文也得相同。于是宏内部起的临时变量名，和调用点碰巧同名的变量，处于不同的上下文，互不干扰。这就是卫生性（hygiene）。

代价是当宏**确实想**往调用点注入一个由自己定义的变量名时（比如想做一个能被调用方引用的 `it` 变量），卫生性反而成了拦路虎，得绕路实现。而完整的那一档卫生语义（让标识符始终解析到宏定义处）至今还没在稳定 Rust 里全部提供，目前稳定的只有 call-site 和 mixed-site 两档。

本质矛盾是「**隔离**」与「**协作**」之间的张力。卫生性通过把宏内外划成两套命名空间来杜绝意外的名字串扰；可一旦宏的设计意图本来就是「送一个名字给调用方用」，这种隔离就成了需要刻意打破的屏障。

> 一条贯穿性的配套惯例：**能用 trait/generics 就不用宏，宏留作最后手段**。因为每用一个宏，都是在拿类型检查、可读性、IDE 支持、编译速度去换那一份表达力。只有当类型系统真的表达不了（自定义语法、批量派生、消除大量同构样板）时，这个交换才划算。

## 5. 最小原理演示

下面这段 TypeScript 把声明宏的核心机制——token 树、模式匹配、元变量绑定、模板渲染——压缩到几十行里演一遍。它不追求工程完整，只演透一件事：**一次宏调用，如何在 token 层被模式匹配、再渲染成一段数量不固定的代码**。

每一行的用意写在注释里，对应上面讲过的原理点。

```ts
// token 树：要么是单个 token（字符串叶子），要么是一组带括号的子树（数组）
type TT = string | TT[]

// 一条宏规则 = 一个 matcher（带「洞」$name 的匹配模式）
//            + 一个 transcriber（用同名占位符渲染的输出模板）
type Rule = { matcher: TT[]; transcriber: TT[] }

// 绑定表：洞名 → 匹配吃到的片段；序列用数组收集
type Bindings = Map<string, TT[]>

// 匹配：拿 matcher 逐位对比输入 token，把洞里吃到的东西记进绑定表
function match(pattern: TT[], input: TT[], b: Bindings): boolean {
  let i = 0
  for (const tok of pattern) {
    if (tok === '$list*') {
      // 重复洞，演的是 macro_rules 里的 $($x:expr),*
      // 贪婪吃掉剩余片段，顺手跳过分隔逗号
      b.set('$list', input.slice(i).filter(t => t !== ','))
      return true
    }
    if (typeof tok === 'string' && tok.startsWith('$')) {
      b.set(tok.slice(1), [input[i]])   // 单个洞：吃掉当前位置一个片段，绑到名字上
    } else if (tok !== input[i]) {
      return false                       // 字面量对不上：这条规则宣告失败，编译器会去试下一条
    }
    i++
  }
  return true
}

// 渲染：拿 transcriber 模板，把占位符换成绑定表里的片段，产出新的 token 流
function render(template: TT[], b: Bindings): TT[] {
  const out: TT[] = []
  for (const tok of template) {
    if (tok === '$list*') {
      // 序列展开，演的是 $(...$x...)*：序列里有几个元素，内层模板就印几份
      for (const frag of b.get('$list')!) {
        out.push('v', '.', 'push', '(', frag, ')', ';')
      }
    } else if (typeof tok === 'string' && tok.startsWith('$')) {
      out.push(...b.get(tok.slice(1))!)   // 单个占位：把绑到的片段填回这个位置
    } else {
      out.push(tok)                       // 字面量：原样搬到输出
    }
  }
  return out
}

// 展开：识别宏调用 → 匹配 → 渲染 → 生成的新 token 流顶替原宏调用的位置
function expandVec(callArgs: TT[]): TT[] {
  const b: Bindings = new Map()
  match(['$list*'], callArgs, b)          // 教学简化：直接匹配参数子树内部，省略编译器认出“这是 vec!”的部分
  return render(
    ['{', 'let', 'mut', 'v', '=', 'Vec::new', '(', ')', ';', '$list*', 'v', '}'],
    b,
  )
}

// 跑一遍等价于 vec![1, 2, 3] 的调用：参数是 [1, 2, 3] 子树内部的 token 流
const expanded = expandVec(['1', ',', '2', ',', '3'])
console.log(expanded.join(' '))
// 输出：{ let mut v = Vec::new ( ) ; v . push ( 1 ) ; v . push ( 2 ) ; v . push ( 3 ) ; v }
```

注意输出的形态：一次 `vec![1, 2, 3]` 调用，被渲染成了一段「建空容器 + 三条 push + 返回容器」的代码。push 的条数完全由 `$list` 序列里有几个元素决定——这正是函数做不到、宏能做到的「注入数量不固定的语句」。而这段刚生成的 token 流，此刻还没经过类型检查；它会被送回解析管线，等整份代码里再没有宏调用时，类型检查器才会睁眼去看它。

## 6. 执行轨迹

拿 `vec![1, 2, 3]` 一步一步走一遍，看清 token 在中间态经历了什么。

调用进入编译器，括号里的内容先被解析成 token 树。`[1, 2, 3]` 是一棵子树，内部是三个被逗号分隔的叶子 token：`1` `2` `3`（逗号是分隔符，不算叶子内容）。

编译器在类型检查之前，把这个 token 树交给 `vec` 宏的规则表。规则从上往下试，`vec!` 的 matcher 形如 `$($x:expr),*`：它把子树内部逐个吃进 `$x`，遇到逗号就当分隔符跳过，最后绑定到 `$x = [1, 2, 3]` 这个序列。第一条规则命中，结束匹配。

接着渲染 transcriber。模板大意是「建一个空容器；`$(容器.push($x);)*`；返回容器」。那个 `$(...)*` 看到 `$x` 序列里有三个元素，就把内层模板印三遍：

```
let mut v = Vec::new();
v.push(1);
v.push(2);
v.push(3);
v
```

这段新 token 流顶替掉原来 `vec![1, 2, 3]` 的位置。扫描发现已经没有剩余的宏调用，展开结束，得到完整 AST。

直到这一刻，类型检查器才第一次看到这段代码。它检查 `Vec::new()` 返回的是不是 `Vec<_>`、`push` 的参数类型对不对、最终 `v` 的类型能不能作为整个表达式的结果。如果有错，报错指向的是这条展开后的 `push` 语句，而不是你写 `vec![1, 2, 3]` 的那一行——这就是前文说的「宏错误定位难」的由来。

## 7. 教学简化说明

本章演示故意省略了不少东西：真实的片段分类符全集（`expr`/`tt`/`ty`/`ident`/`pat`/`stmt`/`item`/…）以及每种分类符背后的 follow set 规则；卫生性「语法上下文」的具体实现；过程宏必须拆独立 crate 的脚手架、`syn`/`quote` 的真实用法；属性宏、派生宏、函数式宏三套注册流程的细节；以及 `cargo-expand`、IDE 集成这些工程化配套。这些都属于「知道了原理之后再去查文档就能补上」的细节，不影响理解宏为什么这样设计。

## 8. 小结

宏是 Rust 在类型系统之外补上的第三类抽象工具，用「在类型检查之前的 token 层做变换」换来了类型系统给不了的表达力——注入任意语句、批量派生、自定义语法。这份能力不便宜：宏对类型检查隐身、调试要靠展开、声明宏受片段分类符约束、过程宏要独立 crate 还拖慢编译，于是社区把宏列为最后手段。它和泛型各管一层：泛型是类型层的编译期多态，宏是 token 层的编译期生成。

带着「编译期能生成代码」这个新视角，下一章会看到 Rust 怎样把另一件更吓人的事也在编译期办妥——多线程的数据竞争。下一章讲无畏并发，看 `Send`/`Sync` 如何在编译期就证明类型能不能跨线程传递。
