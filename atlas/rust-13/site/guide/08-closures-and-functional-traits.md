# 闭包与 Fn/FnMut/FnOnce：捕获方式即类型

> 本章属于 composite 层。前置：借用与引用、Trait 与泛型。
> 学完你能用一句话讲清：Rust 为什么要把闭包拆成 Fn / FnMut / FnOnce 三类——它把「回调能对外部状态做什么」直接编码进类型，让高阶函数在签名层就能精确约束回调，且不花一分运行时开销。

## 1. 为什么需要它（设计动机）

上一章把 trait 当能力契约、配合泛型在编译期单态化，办成了「静态多态 = 零成本」。但它留了个口子：高阶函数（迭代器的回调、排序比较器、事件处理器）经常要接收的不是一个干干净净的函数，而是一段「带着外部状态」的回调，也就是闭包。问题随之而来：类型系统怎么描述「这个回调能对它捕获的外部状态做什么」？

想象你写一个调度器，把一堆回调塞进集合里反复执行。在 JS 里闭包就是闭包，一类搞定：随便传、随便反复调、随时改外面的变量。但到了 Rust，同样是回调，能量等级天差地别：有的只是读一眼外部变量，有的要改外部变量，有的干脆要把一个外部变量「吃掉」（move 走，用一次就没了）。

如果语言不区分这三者，灾难是实在的。一个「把变量吃掉」的闭包被你塞进集合反复调用，第二次调用时那个变量早就不在了，这正是 Rust 要在编译期消灭的内存不安全。所以 Rust 必须有一种办法，让「这个回调到底能对环境做什么」在类型层面看得见，编译器才拦得住滥用。

这三种「对外部状态做什么」并非新东西。第 4 章讲借用与引用时，共享借用 `&T`、唯一可变借用 `&mut T`、移动 `move` 这三种操作就已经定下来了。本章只看它们的下一个侧面：编译器怎么把这三种操作自动套到闭包捕获上，并据此把闭包分成三类可调用 trait。

## 2. 核心思想

Rust 的办法浓缩成一句：**捕获方式即类型，类型决定可调用性**——你不必声明一个闭包属于哪一类，编译器看你怎么用捕获变量就推出来了。

再往上看一层，这套设计取向是「能力从用法中浮现，而不是靠人手标注」。闭包实现哪个 trait，完全由它的函数体决定：只读就归 `Fn`，会改就归 `FnMut`，要消耗就只够 `FnOnce`。写的人不用操心分类，而这个被推断出来的类型，随即成了高阶函数 bound 求解的硬事实。它没有为闭包另立一套安全规则，只是让所有权的三种操作顺着捕获这件事，自然流进了函数式抽象里。

## 3. 心智模型

先建立画面：每个闭包表达式，编译器都会在背后生成一个你看不见的匿名 struct，字段就是它从外层捕获到的那些变量。你写不出这个 struct 的类型名，它是「唯一且不可名状」的。捕获方式决定了这些字段怎么存（共享借用、可变借用，还是把值整个搬进来），进而决定了闭包实现哪个 trait。

从写出闭包到被调用，编译期走的是这样一条流水线：

```
闭包表达式 |...|
   │
   ├─ 识别捕获 ──→ 找出引用了哪些外层变量
   ├─ 脱糖     ──→ 生成匿名 struct，字段 = 捕获变量（按 &/&mut/own 存）
   ├─ 推断 trait ──→ 只读→Fn / 可改→FnMut / 消耗→FnOnce
   └─ 使用     ──→ 作 trait bound 单态化，或翻译成对应的 call 方法
```

三个 trait 的差别，全部落在「self 以什么形式接收」上，这恰好对应三种捕获方式：

| trait | 接收者 | 怎么拿到捕获 | 能改 | 能消耗 | 能否反复调 |
|-------|--------|------------|------|--------|-----------|
| `Fn` | `&self` | 共享借用 `&T` | ✗ | ✗ | 能 |
| `FnMut` | `&mut self` | 可变借用 `&mut T` | ✓ | ✗ | 能 |
| `FnOnce` | `self`（按值） | 所有权（move） | ✓ | ✓ | 仅一次 |

别误读这张表：`FnOnce` 不是最弱的一档，恰恰相反。它按值拥有捕获变量，能改也能消耗，是三档里能力最强的；代价是它以 `self` 为接收者，调一次就把闭包自身消耗掉了，所以叫 Once。三档真正的分界线是最左那列——靠哪种方式拿到捕获变量，而非能力上限。

三档还构成层级 `Fn : FnMut : FnOnce`（`Fn` 是 `FnMut` 的子 trait，`FnMut` 又是 `FnOnce` 的子 trait）。意思是：凡是 `Fn` 闭包，自动也是 `FnMut` 和 `FnOnce`；实现 `FnMut` 的也是 `FnOnce`。越只读、越能反复调，越通用。一个只读闭包可以塞进任何接收 `Fn`/`FnMut`/`FnOnce` 的位置，反过来则不行，消耗型闭包只能去 `FnOnce` 的位置。

## 4. 关键权衡

### 用三类 trait 把回调的能力写进签名

Rust 选择把「捕获方式」编码成三个独立的 trait，而不是像 JS 那样一类通吃。换来的是：高阶函数能在签名层精确表达「我要的回调只能读 / 可以改 / 只能调一次」。调度器要往集合里塞反复执行的回调？签名写 `F: Fn()`，消耗型闭包根本塞不进来，编译期就拦住。前面那个「吃掉变量的闭包被反复调」的灾难，在类型层就没机会发生。

代价是三类 trait 的概念负担。初学者得先建立「为什么不是一类」的直觉，还会踩一些坑：最常见的是误以为 `FnMut` 会「消耗」变量（其实它只是可变借用，可反复调），真正的消耗只有 `FnOnce`。这里化解的本质矛盾是**安全表达力与认知负担**：把回调能力分得越细，编译器替你拦住的越多，但读者要先学会这套分类语言。

### 闭包脱糖成匿名 struct，而不是堆上的环境对象

JS 的闭包背后是一个挂在堆上的环境对象，捕获的变量是其中的引用。Rust 走了另一条路：每个闭包脱糖成一个匿名的 struct，字段就是捕获到的变量，按需以借用或所有权存。换来的是：捕获数据可以原样躺在栈上，每个闭包是独立的具名（但对程序员不可名状）类型，被单态化后内联进调用点，整条函数式链路零运行时开销，和手写循环一个价。

代价是这个匿名类型你写不出来。它有类型，但你写不出它的名字。于是想把闭包存进 struct 字段、或从函数里返回时，没法直接写具名类型，得绕一层：用 `impl Fn`（返回位置，静态、单态化）或 `Box<dyn Fn>`（堆上、动态派发，下一章细讲）间接表达。另一个连带后果是，返回一个引用了外层栈帧的闭包会悬垂，所以返回闭包常常要加 `move`，让它把需要的变量搬进自己体内、自洽地活下来。这里化解的本质矛盾是**零成本与可名状性**：不藏任何堆分配、不做运行时包装，类型就得亲自承载捕获的布局，于是它必然具体到写不出来。

### 最小捕获：能少借，就少借

编译器不会傻乎乎地把整个环境搬进来。它只捕获闭包体真正用到的变量；只用一个字段，就只借那个字段（自 Rust 2021 起精确到字段级，即 RFC 2229 的 disjoint capture）。换来的是更细的捕获粒度：只读某个字段就不会把整个 struct 的可变借用锁死，闭包和外面的可变操作能并存，少跟借用检查器打架。

代价是这套行为对 edition 敏感。同一段代码从 2018 切到 2021，闭包捕获的范围可能变，历史上这确实是个会咬人的坑，后来才被修平。这里化解的本质矛盾是**捕获精度与行为稳定性**：借得越精确、越少挡路，但精确的规则越依赖编译器的版本演进，跨 edition 时行为可能悄悄变。

## 5. 最小原理演示

下面这段 Rust 演透「捕获方式即类型」这一条核心：三个看着同类的闭包，因为对待捕获变量的方式不同，被编译器分进不同的 trait，进而只能被对应的 bound 放行。

```rust
// 三种 bound，各对应「回调能对环境做什么」的一档
fn run<F: Fn()>        (f: F) { f() }       // 要求回调只读捕获
fn run_mut<F: FnMut()> (mut f: F) { f() }   // 要求回调可改捕获
fn run_once<F: FnOnce()>(f: F) { f() }      // 允许回调消耗捕获

fn takes_vec(_: Vec<i32>) {}

fn main() {
    let n = 10;
    let mut v = vec![1, 2, 3];
    let u = vec![4, 5, 6];          // 消耗型闭包用独立变量，不和改写型争 v 的借用

    let a = || println!("{n}");     // 只读 n        → 捕获 &n       → Fn
    run(a);                         // ✓  Fn bound 放行

    let b = || v.push(0);           // 改写 v        → 捕获 &mut v   → FnMut
    // run(b);                      // ❌ 去掉注释：b 不满足 Fn bound
    run_mut(b);                     // ✓  FnMut bound 放行

    let c = || takes_vec(u);        // 消耗 u(move) → 拿走 u 的所有权 → FnOnce
    // run(c);                      // ❌ c 不满足 Fn bound
    // run_mut(c);                  // ❌ c 不满足 FnMut bound
    run_once(c);                    // ✓  FnOnce bound 放行
}
```

三段闭包之所以依次构造、依次消耗，是因为它们各自对环境持有实打实的借用：两个改写 `v` 的闭包若同时存活就会触发借用冲突，这本身也印证了「闭包的捕获是真的持有环境」。`❌` 注释都放在该闭包被消耗之前，去掉注释只会触发「trait bound 不满足」，正好让你亲眼看编译器怎么拒绝。

把放行结果合起来看，就是核心思想的落地：

| 闭包 | 捕获 | 实现 | `run` (Fn) | `run_mut` (FnMut) | `run_once` (FnOnce) |
|------|------|------|------------|-------------------|---------------------|
| a 只读 | `&n` | Fn(+Mut+Once) | ✓ | ✓ | ✓ |
| b 改写 | `&mut v` | FnMut(+Once) | ❌ | ✓ | ✓ |
| c 消耗 | move `u` | FnOnce | ❌ | ❌ | ✓ |

右下三角全是 ✓（层级关系：越只读越通用），左上三角全是 ❌。这条对角线就是「捕获方式即类型」刻在编译器里的形状。

给 JS 背景的读者一段十行对照，体会 Rust 为什么要拆三类：

```ts
let counter = 0
const list: number[] = [1, 2, 3]

const cb = () => {
  console.log(counter)   // 读
  counter++              // 改
  list.length = 0        // JS 没有所有权，「消耗」无从谈起
}
cb(); cb(); cb()         // 同一个闭包，想调几次调几次，类型上毫无区分
```

JS 里同一个闭包既能读又能改又能（伪）消耗，三类合一，因为根本没有所有权，也就没有「用一次就没了」的危险。Rust 必须拆三类，正是因为它有所有权——「消耗」在 Rust 里是真实的、不可逆的，类型系统必须把这件事记下来。

## 6. 执行轨迹

拿一个具体输入，走一遍编译期的内部状态变化。

输入：环境里 `let n = 10;`、`let mut v = vec![1,2,3];`、`let u = vec![4,5,6];`，写三段闭包 a / b / c。

第 1 步，识别捕获。a 的体里用了 `{n}`（只读），b 的体里 `v.push(0)`（要改），c 的体里 `takes_vec(u)`（要按值用）。

第 2 步，脱糖成匿名 struct。编译器给 a 生成一个内含 `&n` 的 struct，给 b 生成一个内含 `&mut v` 的 struct，给 c 生成一个把 `u` 整个搬进来的 struct——此刻 `u` 的所有权已经从外层 move 进了 c，外层再也碰不到 `u`。

第 3 步，推断 trait。a 的体只读捕获，实现 `Fn`（顺带 `FnMut`/`FnOnce`）；b 的体写入捕获，实现 `FnMut`（顺带 `FnOnce`）；c 的体消耗捕获，只实现 `FnOnce`。

第 4 步，bound 放行。`run(a)` 通过（Fn ✓），`run_mut(b)` 通过（FnMut ✓），`run_once(c)` 通过（FnOnce ✓）。若把 `run(b)` 写出来，编译器在第 4 步的 trait 求解阶段就报 `b: FnMut` 不满足 `F: Fn`。整个过程不产生任何运行时检查，全部在编译期完成，零运行时开销。

## 7. 教学简化说明

本章演示故意省略了这些：把闭包存进 struct 字段的工程用法、`Box<dyn Fn>` 的动态派发与 vtable（下一章主角）、返回闭包时的生命周期标注、async 闭包、精确捕获在 edition 边界的 corner case、`impl Fn` 与 `Box<dyn Fn>` 的汇编级对比，以及 `fn` 指针与闭包在 FFI 下的差别。它们都不影响「捕获方式即类型」这条主线。

## 8. 小结

Rust 把闭包拆成三类，本质是把所有权的三种操作（共享借用、可变借用、移动）原样搬到捕获上，让回调的能力落在类型里，编译期就能挡掉误用，且不花一分运行时。代价是你写不出闭包的类型名：想存进字段或返回，就得借助 `impl Fn` 静态绕过，或 `Box<dyn Fn>` 动态绕过。后者正是下一章的主角——当回调要塞进同一个集合、类型各不相同时，单态化就不够用了，得请 vtable 出场。
