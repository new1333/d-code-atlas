# 无畏并发：Send/Sync 与编译期线程安全

> 本章属于 composite 层。前置：借用与引用、智能指针与内部可变性。
> 学完你能：用一句话讲清 Rust 为什么能让多线程代码"在跑起来之前就被证明不会数据竞争"——靠两个运行期完全不存在的 marker trait，加上一道把线程安全写进类型签名的闸门。

## 1. 为什么需要它

上一章讲宏系统，Rust 用编译期代码生成换更强的表达力，那是"把活儿前移到编译期"的又一处。但编译期还能干一件更狠的事：在你的程序跑起来之前，就证明它的多线程部分**不可能出现数据竞争**。这正是本章的主题。

先说数据竞争为什么难。多个线程真正并行地跑，只要"一个线程在写、另一个线程同时在读写同一块内存、中间没有任何同步"，数据竞争就发生了：轻则读到半新半旧的脏值，重则 double-free、use-after-free，表现成最折磨人的"偶发崩溃、换台机器就消失"。各语言的应对分两类：要么让程序员自觉加锁（C/C++/Java，错了就 race），要么干脆上运行时大锁（Python 的 GIL），用牺牲多核性能换省心。

如果你是从 JS 过来的，这件事其实离你很远。JS 是单线程事件循环，回调之间只是时序问题，根本不存在两段代码同时摸同一个变量。要真并行只能开 Worker，而 Worker 之间数据靠拷贝或 `Transferable`，**不共享内存**，用"不共享"绕开了竞争。

Rust 想要的是第三条路：**既允许多个线程真共享内存并行跑，又把数据竞争在编译期彻底消灭**，而且不为此付任何运行时税。这听起来像许愿，但 Rust 真做到了，靠的是把前面几章那套"编译期证明"再往前推一步。

> **承前去重**：把"运行时安全检查前移成编译期证明"这个大模式，已经在第 3 章"借用与引用"和第 4 章"生命周期"讲透了——那两章解决的是"单线程里，引用会不会悬垂、会不会别名冲突"。本章不重讲它，只看新侧面：把同一条"别名 XOR 可变"的规则**从单线程推广到跨线程**，再配一个能在类型层机械判定的判据。同样，第 12 章讲过"把借用检查推迟到运行期"的内部可变性；本章只补它的并发半边：运行期检查**带不带同步**，直接决定类型是 `!Sync`（`Cell`/`RefCell`，无锁）还是 `Sync`（`Mutex`，带锁）。这两条回指够用，本章专注"跨线程"这个新维度。

## 2. 核心思想

用两个**不含任何方法、运行期完全不可见**的 marker trait——`Send` 和 `Sync`——给类型盖"线程安全"的章，让编译器在编译期就能证明"这个值搬去别的线程、或被多个线程同时引用，都不会引发数据竞争"。

它的本质，是把借用检查器那一套"谁能在什么时刻读写一块内存"的别名分析，**从线程之内推广到线程之间**。数据竞争的根因就是"无同步的并发读写"，而借用规则恰好管的就是读写权限——只要这条规则能跨线程生效，数据竞争在编译期就自己消失了。

## 3. 心智模型

想象类型要办"出国签证"。一个值想跨线程，无非两种诉求：要么**把所有权搬过去**（move，从此归那个线程独占），要么**让多个线程同时持有它的引用**（share `&T`，大家只看不动）。编译器对应问两个问题：

- `T: Send` 吗？——把 `T` 的所有权搬到别的线程，安全吗？
- `T: Sync` 吗？——让多个线程同时持有 `&T`，安全吗？

这两个问题其实是一枚硬币的两面，靠一条对偶定义焊在一起：

> `T: Sync` 当且仅当 `&T: Send`。

也就是说，"能不能共享一个只读引用"被折合成"能不能把这个引用搬过去"——共享，本质上就是搬运一个引用。这条对偶让整套线程安全体系直接复用了所有权章的 move 直觉，不用另起炉灶。

签证是怎么发的？靠 auto trait 的两条规则：

- **结构派生**：编译器自动展开一个类型的全部字段，**所有字段都 Send，这个类型才 Send**（Sync 同理）。所以随手写个 `struct Point { x: i32, y: i32 }`，不用写一个字的 trait 声明，它自动就是 `Send + Sync`，因为 `i32` 是。
- **默认盖章、可拒签**：auto trait 默认就给你发签证；但类型可以主动 `impl !Send` / `!Sync` 声明"我不安全"，这就是 opt-out。`Rc` 就这样拒了 `Send`，因为它内部是非原子引用计数，两个线程同时 clone 会并发改同一个计数器。

光有签证还不够，得有海关查。那些跨线程的 API——`thread::spawn`、`Arc`、channel 的 send——都在签名上挂了类型闸门。最典型的是 `spawn`：

```rust
fn spawn<F, T>(f: F) -> JoinHandle<T>
where F: FnOnce() -> T + Send + 'static, T: Send + 'static
```

`F: Send` 这道闸要求"闭包连同它捕获的所有值都能搬到新线程"。`'static` 要求"闭包不借用任何比整个程序还短的引用"——注意这**不是**"值要活到程序结束"，而是"它持有的东西都是自己的，不是借来的"（第 4 章那个生命周期的复用），一个 move 进来的拥有值天然满足。

整个流程串起来就七步：

1. 一个值要么想搬走（move），要么想被共享（`&T`）。
2. 编译器据此问：它 `Send` 吗？`Sync` 吗？（二者是对偶）
3. 这两个属性按字段结构自动派生——全满足才满足。
4. 某些类型主动 opt-out，如实声明"我不安全"。
5. 跨线程 API 在签名上挂 `Send + 'static`（或 `Sync`）这道闸。
6. 不满足 → 编译失败，根本进不了运行期；满足 → 生成跨线程搬运的机器码。
7. 运行期**没有任何**"检查这个值是不是 Send"的代码——盖章是纯类型层行为，所以叫"零成本"。

## 4. 关键权衡

这一节是本章重头戏。Rust 的并发安全不是免费的，它的每一个设计选择都在拿一样东西换另一样。

### 用类型层证明换零运行时开销

数据竞争的检测，主流语言要么不做（C/C++），要么在运行期做（解释器锁、运行时插入的检查）。Rust 选了第三条路：把整件事做成一个**编译期证明**——`Send`/`Sync` 是无方法的 marker trait，运行期一行相关代码都没有。

换来的是"无畏并发"这个硬承诺：在 safe Rust 范围内，**你写不出**一段会引发数据竞争的代码，不是"写了可能出错"，是"根本编不过"。多核并行不再需要提心吊胆。

代价是这套约束会沿字段和 API 像传染一样扩散，而且和 `'static` 紧耦合。一个函数要跨线程，它的所有参数、捕获值、字段都得是 `Send`，少一个就全盘编译失败。最折磨新手的实战场景：拿 `Rc` 跨线程被拒，被迫改写成 `Arc`，顺带把 `RefCell` 换成 `Mutex`——你得一砖一瓦重建"这个值到底能不能跨线程"的类型直觉，而这在 JS 里从来不是问题。这条权衡化解的，是"安全检查要严"和"并发性能要好"两头在打架：检查越严越安全，可运行期检查越多，多核的收益就越被吃掉；Rust 把检查整个搬到编译期，让两头都不牺牲，代价是这个成本转嫁成了学习成本和编译期斗争成本。

### 结构派生换零样板，代价是隐式难审计

第二条选择：线程安全属性按字段结构**自动派生**，默认就有、不用写。你写一百个普通业务 struct，没有一个需要写 `impl Send`，它们全都自动拿到了正确的属性。

换来的是近乎零样板的开发体验。绝大多数自定义类型，编译器替你做了证明，你不用操心。

代价是这个属性是**隐式**的——它不写在源码里，你肉眼扫一遍代码看不出某个类型到底 Send 不 Send。当自动派生的结论恰好是错的（最常见：结构体里塞了一个裸指针 `*const T`，或一个 FFI 句柄），自动派生会直接判整个类型 `!Send`/`!Sync`，这时程序员必须用 `unsafe impl Send` 亲手接过那个证明义务，告诉编译器"我相信它跨线程安全，责任我担"——这正是后面 unsafe 章的入口。这里打架的两头是"让人少写代码"和"让人能看清属性"：Rust 偏向少写，把罕见的"属性判错"留给 `unsafe` 显式接手，把风险压缩进一个可审计的小口子。

### 把 Sync 定义成 &T: Send，换复用 move 直觉

第三条是很精巧的类型设计：没有为"共享"单独发明一套语义，而是用对偶定义 `T: Sync ⟺ &T: Send` 把它折合成"搬运"。共享一个引用，本质上就是搬运那个引用。

换来的是整套线程安全体系**直接复用所有权章的 move 直觉**，读者不用学第二套模型。"搬过去"这个动作你早就懂了，"共享"现在也只是搬一个 `&T` 而已。

代价是两条轴——"搬走一份独占的所有权"和"共享一个只读引用"——在初学时极易搅在一起。最反直觉的组合是 `Cell<T>`：它是 `Send` 但 `!Sync`，意思是"能搬过去独占用，但不能让多个线程同时持有引用看"。新手常误以为"不 Sync 就一定不 Send"，撞上 `Cell` 这种"能搬不能共享"的就会卡壳。这里拧着的是"概念要少而统一"和"两类操作语义其实不同"：Rust 用对偶把它们焊成一个概念，换来学习路径短一截，代价是那道焊缝（move vs share）偶尔让人绊一下。

### 默认偏向线程安全，换多线程代码天然安全

第四条是标准库的默认值取向：`thread::spawn` 索要 `Send + 'static`、跨线程引用计数默认推 `Arc`、文档里到处是并发友好的 API。换句话说，**写多线程代码是顺手且安全的，想写单线程极致优化的代码反而要主动 opt-out**（显式挑 `Rc` 而不是 `Arc`、挑 `RefCell` 而不是 `Mutex`）。

换来的是"无畏并发"落地为默认体验：你随手写的多线程程序就是线程安全的，不用特意维持加锁纪律。

代价是这个默认值和大多数语言**正好相反**——C/Java/Python 都是"默认单线程，想并发自己加锁"。于是单线程场景下的新手常被"为什么 `Rc` 不能跨线程"卡住，以为 Rust 在刁难，其实 Rust 只是把默认值取在了另一头：它假设你随时可能并发，把单线程那点零开销便利留给你主动认领。这里取舍的两头是"默认要安全"和"默认要省开销"：Rust 选了安全优先，理由是数据竞争的代价（诡异的并发 bug）远大于单线程那点同步开销，但这对于从"默认单线程"语言过来的读者是一次默认值的整体翻转。

## 5. 最小原理演示

下面用 TypeScript 把"安全证明住在类型层、运行期完全无感"这件事演透。核心三件事：印章是纯类型标记、闸门靠类型约束生效、运行期盖章值和不盖章值毫无差别。

先做一个诚实的交代：Rust 的 auto trait 是"默认盖章、显式拒签"（opt-out），但 TS 的结构类型天然是"必须显式带字段才匹配"（opt-in）。为了让 `Rc` 在 TS 里**真的**被拒（而不是像可选字段那样谁都过得去），下面用"必填品牌字段"来等效表达"印章 + 闸门"。auto trait 的"默认满足 + 字段传染"是 Rust 编译器内部的派生规则，TS 无法忠实模拟，已在上一节心智模型里讲清。

```ts
// 印章：纯类型层标记，运行期不占一个字节
interface Send {
  readonly __sendBrand: true   // 必填品牌：缺它的类型一律过不了闸
}

// 闸门：把 Send 写进 spawn 的类型约束
// 对应 Rust: fn spawn<F>(f: F) where F: FnOnce() + Send + 'static
function spawn<T extends Send>(f: () => T): T {
  return f()   // 运行期什么都不查——证明已经在类型层做完
}

// 盖了章的普通类型：一个简单计数器
class Counter implements Send {
  readonly __sendBrand!: true   // 仅类型断言，运行期不会真出现这个字段
  constructor(public value = 0) {}
}

const counter = new Counter(0)
spawn(() => counter)   // 通过：Counter 带着印章，满足 T extends Send

// 故意不盖章的 Rc：非原子引用计数的替身
// 对应 Rust 里 Rc 主动声明 !Send 的拒签
class Rc<T> {
  refcount = 1                    // 没有 __sendBrand 字段
  constructor(public value: T) {}
  clone(): Rc<T> { this.refcount++; return this }
}

const rc = new Rc(42)
// spawn(() => rc)
// 报错：类型 "Rc<number>" 中缺少属性 "__sendBrand"，
//       但类型 "Send" 中需要该属性 —— 不满足约束 T extends Send

// 运行期对照：印章从不现身
console.log(counter)   // { value: 0 }         —— 没有 __sendBrand
console.log(rc)        // { value: 42, refcount: 1 }
// 两者都是普通对象，谁也没多出一个"安全位"——证明只活在类型里
```

几个对应关系值得看清。`__sendBrand!: true` 用的是 TS 的"确定赋值断言"，它只在类型层宣称"有这个字段"，运行期根本不产出这个字段，所以 `counter` 实例只剩 `{ value: 0 }`——这就是 marker trait "零运行时占用"的 TS 映射。而 `Rc` 之所以被拒，不是因为它运行期做了什么危险动作，**仅仅是因为它的类型里缺了那个字段**：拒签发生在类型层，运行期的 `rc` 和 `counter` 长得一样普通。

## 6. 执行轨迹

拿新手最容易踩的那个坑走一遍。假设你写了：

```rust
let rc = Rc::new(RefCell::new(0i32));
std::thread::spawn(move || {
    *rc.borrow_mut() += 1;   // 想在新线程里改这个值
});
```

你想做的事很自然：把一个可变的共享值搬进新线程去改。编译器审查这次调用的过程：

1. `spawn` 的签名挂着 `F: FnOnce() + Send + 'static` 这道闸。
2. 编译器推断闭包 `F` 的类型，逐一展开它 `move` 捕获的值——这里捕获了 `rc: Rc<RefCell<i32>>`。
3. 对 `Rc<RefCell<i32>>` 查 `Send`：按字段结构派生，先看最外层的 `Rc`——命中 `Rc: !Send`（非原子引用计数，标准库主动 opt-out）。
4. 派生链在最外层就断了：`Rc<...>` 整个 `!Send`，闭包捕获了它，闭包 `F` 也跟着 `!Send`。
5. `F: !Send` 不满足 `spawn` 的 `F: Send + 'static` 闸 → **编译失败**，错误精准指向 `move ||` 那一行捕获了 `Rc`。

注意全程没有运行期：程序还没跑起来，错误就堵在编译期。修法是把 `Rc` 换成 `Arc`、`RefCell` 换成 `Mutex`——`Arc` 用原子引用计数换到了 `Send + Sync`，`Mutex` 用带锁的内部可变性换到了 `Sync`。改完重编通过，运行期没有任何多余的"是否 Send"检查。这条轨迹把两个核心演透了：**错误发生在类型层**（不是运行期崩），**自动派生沿字段传染**（一个 `!Send` 字段拖垮整个闭包）。

## 7. 教学简化说明

本章演示故意省略了不少东西：真正的 OS 线程创建、`Arc`/`Mutex` 背后的原子操作和内存序、`Sync` 的对偶在编译器内核里怎么和借用规则耦合、negative impl（`impl !Send`）的精确语法与稳定化进度（目前主要还是标准库专属）、`MutexGuard` 离开作用域自动解锁的 RAII 细节。这些都是"原子与锁"或 unsafe 章的专题，本章只演透"安全证明住在类型层"这一个原理，不追求把并发整座大山一次搬完。

## 8. 小结

Rust 的并发安全，说白了就是把"这个值能不能跨线程"做成一个**类型问题**而不是运行期问题：两个空壳 marker trait 给类型盖章，跨线程 API 在签名上挂闸门，编译器替你查一遍，查不过就编不过。你为此付出的是一套新的类型直觉和偶尔的 Rc→Arc 改写，换回的是多核并行不必再提心吊胆。这套静态证明只覆盖 safe Rust 能表达的部分，一旦跨进 unsafe、FFI 的世界，证明义务就从编译器交还给了人。下一章会把"线程"换成更轻的"任务"，看 Future 怎么沿用同一套 `Send` 思路，把异步也纳入类型层约束。
