# Cookie 凭证的清洗与校验 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：用户从浏览器把知乎 Cookie 整段复制过来，但这串字符里往往混着百度统计、Google Analytics 等第三方站点的跟踪项，有时还缺最关键的签名/登录凭证，甚至已经过期。如果原样发出去：轻则被知乎以 403 拒绝，重则被静默重定向到别处、或撞上一面登录墙——爬到的全是空壳。使用者完全不知道是 Cookie 出了问题，还是程序坏了。

- **一句话核心思想**：Cookie 不是一份静态凭证，而是一个**会脏、会缺、会失效的活动状态**；所以入口处必须做「清洗 → 静态校验 → 动态探测」三道预处理，把不可用的 Cookie 在真正发请求之前拦下或修正。

- **设计动机（为什么需要它）**：知乎反爬把 Cookie 当作主战场之一，而一份"从浏览器扒下来的 Cookie 字符串"天然不可信——它混合了多个域名、无法从字符串本身看出有效期。这个机制要解决的矛盾是：**用户给的输入脏且不可校验，但下游每个请求通道都对 Cookie 的"干净度"有不同且严苛的要求**。它换来的是：下游的爬虫、API 客户端、浏览器引擎都不必各自处理 Cookie 卫生，统一在这一层收敛。
  - 承前关系（跨章去重）：本章持有的 Cookie 字符串、以及"内存槽 + 持久化"的双写约定，其**存放容器**来自第 1 章『全局共享状态容器』建立的模块级单例；本章只关注"往这个槽里放什么、放之前怎么清洗、怎么判断它坏了"，不重复讲容器本身。

- **关键权衡（本章核心原料）**：
  1. **黑名单前缀过滤，而非白名单**：理论上"只保留知乎域 Cookie"最稳妥的做法是白名单（列出所有已知知乎 Cookie 名），但知乎 Cookie 名多且会随版本变动 → 改用黑名单（只列已知第三方前缀如百度统计、GA）→ 换来"新增知乎自有 Cookie 时无需改代码即可保留" → 代价是"出现一个未列入黑名单的新第三方跟踪项时，它会被原样放行，需持续维护这张表"。
  2. **完整性校验只查"有没有"，不查"对不对"**：校验只判断关键安全项（请求签名 + 登录凭证）的 **key 是否存在**，完全不校验其值是否仍有效 → 换来"纯本地、零网络、毫秒级"的快速预检 → 代价是"key 在但值已过期"这种最常见失效，必须由下游的动态探测兜底。这把校验刻意拆成**静态存在性（本地、快）+ 动态有效性（联网、慢）**两层。
  3. **失效判定靠"副作用"反推，而非主动校验**：Cookie 字符串里没有可靠的有效期字段，无法主动判断是否失效 → 于是采用"先发一次真实请求，再看返回页面里有没有冒出登录按钮"来反推失效 → 换来"完全不必理解知乎的会话协议/加密" → 代价是"必须承受一次失败请求、且反推准确性强依赖于那个登录按钮的 DOM 选择器不被知乎改版"。
  4. **清洗策略按传输通道分化**：原始 HTTP 通道（热榜/列表/API）对第三方 Cookie 零容忍——发了就 403，所以走"全量过滤"；真实浏览器通道（详情页爬取）对第三方 Cookie 容忍度高，真正会惹麻烦的只是一个会导致"被重定向到热榜"的特定项，所以只做"定向移除" → 换来"按各通道的真实威胁模型精准处理" → 代价是"存在两套清洗逻辑、调用方必须知道该用哪套"，调用点甚至出现"两种都调一遍"的防御性重复。

- **最小心智模型（Cookie 从输入到被判失效的生命周期，7 步）**：
  1. **入库**：Cookie 来自三个入口之一——用户手粘、扫码登录回传、或旧格式历史配置的兼容迁移。
  2. **入库即清洗**：用黑名单前缀过滤掉已知的第三方统计项。
  3. **双写**：同时写入内存槽（供运行时各处读取）与持久化配置（供重启后恢复）。
  4. **用前静态校验**：检查两个关键安全项是否存在；缺则弹窗引导用户重新登录，绝不带着残缺 Cookie 继续。
  5. **按通道按需再清洗**：发请求前，原始 HTTP 通道再过一遍全量过滤；真实浏览器通道则只定向移除那个会触发重定向的项。
  6. **请求发出**。
  7. **动态探测兜底**：若返回 403、或返回的页面里冒出登录按钮，则反推 Cookie 已失效，触发去抖提示（短时间内只提醒一次，避免刷屏）。

- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个纯脚本，演透"清洗 → 静态校验 → 动态探测"三件套骨架——给定一段含杂质、缺关键项的 Cookie 字符串：(a) 用一张黑名单前缀表做过滤（演权衡 1）；(b) 检查关键项 key 是否存在（演权衡 2：快但只查存在性）；(c) 用一个 stub 的"返回 HTML"模拟请求结果，靠"是否含登录按钮选择器"反推失效（演权衡 3：靠副作用反推）。每一步都要对应上面某条权衡。
  - **应故意省略**：VSCode 配置持久化与弹窗 UI、扫码登录回传链路、旧格式 JSON 迁移、真实网络请求、真实浏览器注入、去抖定时器的工程化包装。
  - **演示载体建议**：本章虽是 VSCode 扩展的一部分，但"清洗/校验/探测"三件套是**纯字符串处理 + 一个选择器匹配**，与宿主无关。建议写成一段**可直接 `node`/`bun run` 的独立 TS 脚本**：把"动态探测"用一段写死的假 HTML 字符串代替真实请求，照样能演透"静态校验"与"动态探测"的分层。**不必、也不应该**为了演示去启动真的 VSCode 扩展或真发知乎请求——那只会把"原理"埋进"工程脚手架"。
  - 一句话原则：**载体服务于"演透原理"，不是服务于"能跑"。**

- **正文不宜展开的细节**：双写存储中"内存优先于配置"的读取顺序细节、旧格式 JSON 自动迁移的正负样例、第三方前缀表的完整清单（举几个代表性即可）、去抖提示的具体毫秒数、清除 Cookie 后触发各列表刷新的命令清单——这些是工程化包装，点到为止，不展开。

- **推荐的一个执行轨迹例子**：
  - 输入 Cookie（用户粘的）：`登录凭证=AAA; 请求签名=BBB; 百度统计项=ccc; GA项=ddd; 重定向项=eee`
  - 清洗后：`登录凭证=AAA; 请求签名=BBB`（第三方全去；"重定向项"在黑名单里也被一并去掉）
  - 静态校验：两个关键项都在 → 通过（注意：通过只代表"存在"，不代表"有效"）
  - 假设其实已过期 → 发请求 → 返回页面里冒出登录按钮 → 动态探测反推"已失效" → 去抖提示用户更新。
  - 这条轨迹演的是核心思想：**通过了静态校验的 Cookie，依然可能被动态探测判失效——两层缺一不可。**

## 概念要点

- **核心抽象是"Cookie 作为一个活动状态的三种病"**：脏（含第三方）/ 缺（缺关键项）/ 失效（过期）。三种病对应三种不同处理：清洗 / 静态校验警告 / 动态探测反推。这是本章的主线分类法。源码位置: src/core/zhihu/cookie/index.ts:5-309（整文件围绕这三类操作组织）

- **黑名单前缀过滤（清洗第三方）**：维护一张"已知第三方 Cookie 前缀"数组（百度统计 `Hm_lvt`/`HMACCOUNT`、百度搜索 `BAIDUID`/`BDUSS`/`BIDUPSID` 等、Google Analytics `_ga`/`_gid` 等），匹配规则为「key 等于前缀，或以前缀加 `_`/`.` 开头」即剔除。注释明确说明动机：这些第三方 Cookie 若一起发给知乎会导致 403。源码位置: src/core/zhihu/cookie/index.ts:211-266（前缀表 217-242，过滤谓词 244-257）

- **命名语义偏差（推断）**：该过滤方法的命名是"只保留知乎 Cookie"（白名单语义），但实现是黑名单（剔除已知第三方）。偏差的证据是：那个会引起重定向的"重定向项"本身是知乎域的 Cookie，却被额外塞进了第三方黑名单里——说明命名描述的是"目标"而非"实现手段"。源码位置: src/core/zhihu/cookie/index.ts:237（"BEC"被列入第三方前缀表）

- **定向移除"重定向项"是独立方法**：存在一个专门只移除单个项（BEC）的方法，且其唯一调用点的注释点明了动机——"避免重定向到热榜页面"。它出现在真实浏览器（Puppeteer）打开详情页的路径上。源码位置: src/core/zhihu/cookie/index.ts:187-203；调用与动机注释: src/core/zhihu/puppeteer/index.ts:440-442

- **通道分化（核心权衡的事实依据）**：原始 fetch 通道（热榜）调用全量过滤；真实浏览器通道（Puppeteer）只调用定向移除。两类调用点处理 Cookie 的"力度"不同，对应各通道对 Cookie 杂质的容忍度差异。源码位置: 全量过滤调用 src/core/zhihu/sidebar/hot.ts:152-154；仅定向移除调用 src/core/zhihu/puppeteer/index.ts:441

- **静态完整性校验只查 key 存在性**：校验函数解析出所有 key，判断"请求签名项"与"登录凭证项"是否**都存在**，返回布尔；不校验值的合法性。注释说明：前者是请求签名必需，后者是登录凭证。源码位置: src/core/zhihu/cookie/index.ts:177-180（key 解析 166-172）

- **静态校验失败后的引导**：在加载 Cookie 时若发现不完整，会计算出具体缺失项，弹出带两个动作按钮的警告，引导用户走"扫码登录"或"手动设置"。源码位置: src/core/zhihu/cookie/index.ts:42-65

- **动态失效探测——DOM 登录墙反推**：用 `.SignFlow-submitButton` 这个选择器去页面里找登录按钮，找到即认定 Cookie 已失效/未设置。该探测在 Puppeteer 页面上下文里用 `page.$(selector)` 完成。源码位置: src/core/zhihu/cookie/index.ts:296-308

- **同一探测原理的两种载体**：原始 fetch 通道里没有 Puppeteer page 对象，于是用 cheerio 在返回 HTML 里内联查**同一个选择器** `.SignFlow-submitButton` 来反推失效——原理一致，载体不同。源码位置: src/core/zhihu/sidebar/hot.ts:204（fetch+cheerio 内联探测）；对照 src/core/zhihu/cookie/index.ts:301-303（Puppeteer page 探测）

- **失效提示带去抖**：静态类上有一个"正在提醒"布尔标志，提示时置真，5 秒后自动复位，避免多个列表并发失效时刷屏弹窗。源码位置: src/core/zhihu/cookie/index.ts:6,148-161

- **双写 + 读取时"内存优先"**：Cookie 同时写入内存单例槽与 VSCode 持久化配置；判断"是否已设置"时优先看内存槽（注释理由：扫码登录可能刚写入内存但配置尚未落盘完成），内存空才回落到读配置。源码位置: 写入 src/core/zhihu/cookie/index.ts:72-79；内存优先读取 src/core/zhihu/cookie/index.ts:137-145

- **入口触发点**：Cookie 加载/清洗发生在知乎服务构造时（即扩展激活组装期），确保下游任何请求发出前 Cookie 槽已就绪。源码位置: src/core/zhihu/index.ts:7-9
