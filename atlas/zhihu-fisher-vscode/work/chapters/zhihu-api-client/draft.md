# 第 4 章 知乎 JSON API 写操作客户端

## 为一个"赞同"，你要启动一台浏览器吗？

想象你在编辑器里打开了一条知乎回答，点了一下"赞同"。

最直觉的实现是什么？开一台真实 Chrome，导航到那条回答，注入 Cookie，等页面渲染完，模拟点击那个"赞同"按钮，再等它的状态翻过来。每点一下赞同，都要把这一整套重型机械跑一遍。

但你想过没有——知乎网页前端自己点"赞同"的时候，它到底做了什么？它其实就是往服务器发了一次带 Cookie 的 JSON 请求，一次 HTTP 而已。页面根本没有重新渲染任何内容，按钮高亮只是前端自己改的。

那问题就来了：你用一个完整的浏览器渲染管线，去发一个本质上只是一次 HTTP 的动作，这不是杀鸡用牛刀吗？每次都要启动 Chrome、烧一份 Cookie、等上几秒。本章讲的就是怎么把这件事做轻。

## 核心思想：写操作就是一次状态翻转，别用浏览器去发它

"赞同、收藏、关注、不感兴趣"这些动作有一个共同点：**它们不产生需要渲染的内容，只是把服务器上某个状态翻一下**。赞同就是把"投票态"从无翻到有，收藏就是把"是否在收藏夹里"从假翻到真。

既然只是翻转状态，它就没有理由走"渲染页面 → 提取内容"那条读操作的路线。读操作之所以非得用真实浏览器，是因为知乎把内容藏在一堆反爬后面，必须渲染才看得见；而写操作没这个需求。

所以这一章的做法一句话：**别爬页面，把自己伪装成知乎前端，直接复刻它本该发出的那条 XHR**。

"伪装"这个词很关键。知乎服务器不会因为你说自己是浏览器就信你，它要看一整套"浏览器才会发的请求头"。你可以把这想象成混进公司收发室的快递——你得有正确的快递公司马甲（User-Agent）、正确的收发室编号（Origin、Referer）、还有一枚正确的内部签收章（Cookie）。这一套全对上了，门禁才放行；少一件，保安（反爬）就把你拦下来。

至于那枚"内部签收章"——Cookie——从哪来？它不是本章要操心的事。**前置章（第 2 章《Cookie 凭证的清洗与校验》）在写入 Cookie 时，就已经把第三方统计项洗掉、把签名和登录凭证校验齐全、把会惹麻烦的重定向项去掉了**，存下的是一条干净的字符串。本章要做的，只是把这条字符串原样塞进请求头。所以接下来你不会看到任何 Cookie 清洗或校验的代码——那套逻辑第 2 章已经讲透，这里不重复。

## 从最底下那块零件说起：请求头工厂

既然要"伪装成浏览器"，那伪装的活儿谁来干？最底下有一块专门干这个的零件：一个请求头工厂。给它一个 Cookie，它吐出一整套"假装我是从知乎自家页面发出的同源 XHR"的请求头。

这套头里都有什么？粗分三类：

- **身份类**：`User-Agent`（我是 Chrome 122）、`Sec-Ch-Ua` / `Sec-Ch-Ua-Mobile` / `Sec-Ch-Ua-Platform` 这套"客户端提示头三件套"（更细地交代浏览器和系统）。这是浏览器指纹的主干。
- **来路类**：`Origin: https://www.zhihu.com`、`Referer: https://www.zhihu.com/`、`Sec-Fetch-Site: same-origin`——宣称"我是从知乎自己的页面发出的，不是跨站来的"。
- **XHR 标记类**：`X-Requested-With: XMLHttpRequest`——传统上标示"这是前端发的 Ajax 请求"的头。

Cookie 单独占一项。如果这次请求带请求体，工厂再按需追加一个 `Content-Type`。

这段逻辑写成代码很短，但它是整章的基石：

```ts
// 请求头工厂：给个 Cookie，吐出一整套"我是浏览器同源 XHR"的头
function getCommonHeaders(cookie: string, contentType?: string) {
  const headers: Record<string, string> = {
    Accept: "application/json, text/plain, */*",
    Cookie: cookie,
    Origin: "https://www.zhihu.com",
    Referer: "https://www.zhihu.com/",
    "Sec-Ch-Ua": '"Chromium";v="122", "Google Chrome";v="122"',
    "Sec-Ch-Ua-Mobile": "?0",
    "Sec-Ch-Ua-Platform": '"Windows"',
    "Sec-Fetch-Site": "same-origin",       // 宣称"我从知乎自家页面发出的"
    "User-Agent": "Mozilla/5.0 ... Chrome/122.0.6261.95 ...",
    "X-Requested-With": "XMLHttpRequest",
  };
  if (contentType) headers["Content-Type"] = contentType;
  return headers;
}
```

注意这套头里**没有一个跟具体操作有关**——不管赞同还是收藏，发出去的"外壳"长得一模一样。操作的差异全在 URL、HTTP 方法、请求体那三样里，跟头无关。这就是为什么头工厂能被所有写操作共用。

## 把零件装成一条管线：统一请求出口

光有头还不够，得有人把"取 Cookie → 拼头 → 发请求 → 看结果"这一串步骤串起来。这个角色叫**统一请求出口**。所有十几个写操作，不管赞同、收藏、关注还是不感兴趣，最后都从这同一个方法发出去。

它干四件事，顺序固定：

1. **取 Cookie**：找凭证管理器要那条前置章清洗好的字符串。
2. **判空**：如果 Cookie 是空的（用户根本没登录），弹个错误提示，直接抛异常中断——没法继续。
3. **拼头发请求**：用头工厂拼出整套伪装头，把 Cookie 和内容类型塞进去，发起这次 fetch。
4. **处理结果**：HTTP 层失败（非 2xx）就统一抛出；成功的话，删类请求通常没有响应体，直接判成功，其余的解析 JSON 返回。

这里有个容易被一句话带过的细节，值得单独拎出来：**出口只看 Cookie 在不在（非空就放行），并不在这里再校验一遍签名和登录凭证齐不齐**。为什么？因为那份完整校验在前置章（第 2 章）写入 Cookie 时就已经做完了。换句话说，走到这里能拿到的 Cookie，要么是空（没登录），要么是已经过关的合格品，没必要在发请求的关口再查一遍。所以这一步是轻量的"在不在"判断，而不是沉重的"合不合格"判断——这也正好回应了为什么本章不需要重复第 2 章那套校验。

把上面四步写成代码，就是整条管线的样子：

```ts
// 统一请求出口：所有写操作都从这里发出去
async function makeRequest(url, { method, body, contentType }, opName) {
  const cookie = getCookie();                                   // 1. 拿前置章清洗好的 Cookie
  if (!cookie) throw new Error(`没有 Cookie，无法${opName}`);    // 2. 只判非空

  const res = await fetch(url, {                                // 3. 拼头 + 发请求
    method,
    headers: getCommonHeaders(cookie, contentType),
    body,
  });

  if (!res.ok) throw new Error(`${opName} HTTP 错误: ${res.status}`); // 4. 失败统一抛
  if (method === "DELETE") return { success: true };             // 删除通常没响应体
  return await res.json();                                      // 其余解析 JSON
}
```

一个细节藏在第 4 步：为什么 DELETE 要特判？因为 REST 风格里，删除一个资源成功后，服务器经常**只回一个状态码、没有响应体**。如果无脑去 `res.json()` 解析空体，会直接报错。所以出口对 DELETE 网开一面——只要 HTTP 成功，就当作 `{success: true}` 返回，不去碰响应体。

整条管线画成图就是这样：

```
写方法把动作翻译成 (URL, 方法, 请求体, 操作名)
            │
            ▼
       makeRequest（统一出口）
            │
   ┌────────┼──────────┐
   ▼        ▼          ▼
 取Cookie   判空?       拼头工厂
（前置章    空→抛        伪造全套
 清洗好）   非空→放行    浏览器头
                        │
                        ▼
                     发 fetch
                        │
                ┌───────┴────────┐
                ▼                ▼
            非2xx→抛          2xx
                            DELETE→{success:true}
                            其余→解析JSON
```

## 同一个出口，三套不同的"成败交代"

走到这里，请求怎么发、怎么判 HTTP 成败，已经彻底统一了。但有意思的地方来了：**请求构造层统一，业务成功判定层却故意不统一**。

什么意思？同样是"调 makeRequest 拿到结果"，不同写操作对"失败怎么办、成功返什么"的处理，分成了三派：

**第一派：吞掉异常，只回一个布尔。** 收藏、不喜欢这类操作属于这一派。它们的界面（比如列表上一个"收藏"按钮）只关心"成没成"——按钮要么变成"已收藏"，要么没变。失败原因是什么，界面根本不关心。所以这类方法在内部 `try/catch` 把异常吃掉，成功返 `true`、任何闪失返 `false`。调用方拿到的永远是一个安安稳稳的布尔，不用自己 try/catch。

**第二派：异常原样上抛，返回完整对象。** 投票、关注、评论点赞属于这一派。为什么它们不能学第一派？因为它们的界面要的不止是"成败"。你点完"赞同"，详情页要拿返回体里的最新投票态去刷新那个按钮的高亮——它需要完整的返回对象。要是异常被吞成 `false`，界面就拿不到"当前到底是赞同还是不赞同"了。所以这类方法把异常原样抛上去、把对象原样返回来，让调用方自己决定怎么处理。

**第三派：返回一个带细节的结构体。** 创建收藏夹、删除收藏夹属于这一派。它们要区分两种不同的"失败"：一种是网络/HTTP 层炸了（请求没发出去），另一种是请求发出去了但业务上被拒（比如收藏夹重名）。所以它们返一个 `{success, error?, collection?}` 结构体，把失败原因也带回来，让界面能告诉用户"是网络问题还是名字撞了"。

这三派的差异，从一个对比就能看清楚：

```ts
// 第一派：收藏——界面只要"成败"，吞异常、回布尔
async function addToCollection(colId, contentId, contentType) {
  try {
    const r = await makeRequest(
      `.../collections/${colId}/contents?content_id=${contentId}&content_type=${contentType}`,
      { method: "POST", contentType: "application/x-www-form-urlencoded" },
      "收藏内容"
    );
    return r.success === true;            // 只要成败信号
  } catch {
    return false;                         // 任何闪失都吞成 false
  }
}

// 第二派：投票——界面要拿返回体刷新按钮，异常原样抛、对象原样返
async function voteAnswer(answerId, voteType) {
  return await makeRequest(
    `.../answers/${answerId}/voters`,
    { method: "POST", body: JSON.stringify({ type: voteType }),
      contentType: "application/json" },
    `回答投票(${voteType})`
  );   // 不 try/catch，异常直接冒泡，对象原样返
}
```

顺带一提，"点赞 / 取消点赞"在客户端里是同一个方法：传一个布尔，`true` 走 POST、`false` 走 DELETE，用 HTTP 方法本身来表达状态翻转。不过这个布尔翻转的写法**只用在评论点赞和想法点赞两处**；至于**关注 / 取消关注，仍然是两个独立方法**（`followUser` 走 POST、`unfollowUser` 走 DELETE），并没有合并成带布尔参数的一个。这也呼应了上面说的——本章里的"统一"是有选择的，不是一刀切。

## 一段能跑的演示：亲眼看看伪造的头和塞进去的 Cookie

光讲原理容易虚。我们起一个本地的桩服务（mock server）假装是知乎，让它把"收到的所有请求头"原样打印出来。这样你就能亲眼看到：客户端伪造的那套头到底长什么样、Cookie 是怎么被塞进去的。比真的去连知乎更安全，也更聚焦"伪装"这件事本身。

先起桩服务，它只做一件事——收请求、打印头、回个假的成功：

```ts
// 桩服务：假装是知乎，把收到的请求头打印出来
import http from "node:http";

http.createServer((req, res) => {
  let body = "";
  req.on("data", (c) => (body += c));
  req.on("end", () => {
    console.log("---- 桩服务收到请求 ----");
    console.log(req.method, req.url);
    console.log("收到的请求头：");
    for (const [k, v] of Object.entries(req.headers)) {
      console.log(`  ${k}: ${v}`);      // 重点看 Cookie 是不是真发出去了
    }
    res.setHeader("Content-Type", "application/json");
    res.end(JSON.stringify({ success: true, voting: 1 }));   // 假装赞同成功
  });
}).listen(9000, () => console.log("桩服务跑在 http://localhost:9000"));
```

然后用上面的客户端去点一次"赞同"，执行轨迹是这样走的：

```
输入：用户在详情页点"赞同回答 12345"
   │
   ▼
voteAnswer('12345', 'up')
   │  翻译成三要素：URL=.../answers/12345/voters, 方法=POST, 体={type:'up'}
   ▼
makeRequest(...) 走统一出口
   │  1. getCookie() → "__zse_ck=...; z_c0=..."（前置章清洗好的，非空，放行）
   │  2. getCommonHeaders() 拼出整套伪装头，Cookie 塞进 headers.Cookie
   │  3. fetch 发出
   ▼
桩服务打印收到的头（你亲眼看到）：
   Cookie: __zse_ck=...; z_c0=...      ← 真的发出去了
   User-Agent: Mozilla/5.0 ... Chrome/122 ...
   Sec-Fetch-Site: same-origin
   X-Requested-With: XMLHttpRequest
   ...
   ▼
桩服务回 {success:true, voting:1}
   │  2xx + 非 DELETE → 解析 JSON
   ▼
voteAnswer 原样返回 {success:true, voting:1}（不吞异常）
   │
   ▼
详情页拿 voting:1 去把"赞同"按钮高亮起来

输出：投票态翻转，按钮高亮
```

如果你把 `getCookie()` 改成返回空字符串，出口会立刻在第 2 步抛出"没有 Cookie"——这就是判空那道闸在工作。

## 关键权衡

这一章真正值得记的，是下面这几条"做了什么选择、换来什么、付出什么代价"。本章机制不算多但很集中，所以把这三条一次讲透。

**权衡一：选择"重放前端 XHR（伪造全套请求头 + Cookie）"，而不是"用真实浏览器操作页面"。**

换来的是写操作**极轻量**：一次 HTTP 就完事，不启动 Chrome、几乎不烧 Cookie（每次只是带着 Cookie 发个轻请求，远比开浏览器渲染一整页温柔）、毫秒级返回。十几个写操作叠在一起，这套轻量化的收益非常可观——你不用为每一个"赞同""收藏"都背上一台浏览器的开销。

代价是**必须手工伪造一套完整且自洽的浏览器指纹请求头**——客户端提示头三件套、User-Agent、Origin、Referer、Sec-Fetch 系列、X-Requested-With，一个都不能少，而且彼此要"对得上"（比如 UA 说自己是 Chrome 122，客户端提示头的版本号也得是 122）。任何一个头缺失或自相矛盾，都可能被反爬识破为非浏览器流量。更深一层：这些指纹是**硬编码**的，浏览器版本会随时间过时（今天写 Chrome/122，过两年就是古董了），需要人定期去更新。这笔代价之所以值得付，是因为写动作天生没有"要渲染的内容"，用渲染管线去发它纯粹是浪费——轻量化的收益压倒了手工维护指纹的麻烦。

**权衡二：选择把十几个写操作全做成"无状态的静态方法、共用同一个请求出口"。**

换来的是**请求构造、凭证拼装、HTTP 错误处理在一处统一**。要加一个新写操作，你只要填三样东西——接口地址、HTTP 方法（增还是删）、请求体——再起个操作名，剩下的（取 Cookie、拼头、发请求、判 HTTP 成败）全自动复用。这套出口相当于把所有写操作共有的"脏活"抽干了，新操作只写自己独有的那点差异。

代价有三条。第一，这些方法**隐式依赖全局共享的 Cookie**，而不是把 Cookie 当参数显式传进来——想单独测某个写操作，得先把全局状态喂饱，没法当纯函数测。第二，**失去了按操作类型定制策略的余地**：比如投票被限流了，你想给它单独加个退避重试，对不起，出口里没有这个钩子，所有操作共用同一套（也就是没有）重试逻辑。第三，没有实例状态，就没法在对象上挂"当前会话"之类的信息，灵活性受限。这三条代价换回的是"加新操作极省事"，对十几个高度同质的写操作来说，这笔账划算。

**权衡三（这条最值得琢磨）：选择"请求构造层彻底统一，但业务成功判定层刻意分裂"。**

这听起来矛盾——既然前面那么强调统一，为什么到这里反倒要分裂？因为**该统一的地方统一了，就该让不该统一的地方各自为政**。这条划的就是"该统一"和"该不统一"的分界线。

换来的是**每种操作都能按自己界面的实际需要，选最省事的错误传播方式**。收藏/不喜欢的界面只要"成没成"，用布尔最省事，调用方连 try/catch 都不用写；投票/关注的界面要拿返回体刷新按钮态，必须拿到完整对象，那就让它原样返；创建收藏夹要分辨"网络失败"和"业务被拒"，那就返个带原因的结构体。如果硬把它们统一成一种（比如全返布尔，或全抛异常），每种操作的界面都得自己再翻译一次，反而更累。

代价是**调用方必须记住每个方法的契约**：这个返布尔、那个返对象、另一个返结构体、还有的会抛异常——不能无脑统一处理。新人最容易在这里踩坑，比如对投票方法不写 try/catch，异常就一路冒泡炸到界面。换句话说，这条权衡把"记住契约"的心智负担从框架内部挪到了调用方。它换来的"每种操作都恰到好处"是否值得这份负担，取决于这些写操作彼此的差异是不是真的够大——在本章这个场景里确实够大，所以分裂是赚的。

## 小结

这一章讲的是怎么把"改变知乎服务器状态"的那类动作做轻。核心就一句：**写操作不爬页面，伪装成知乎前端、复刻它本该发的那条 XHR**。

为此它搭了三块东西，自下而上：最底下是一个**请求头工厂**，负责伪造一整套"我是浏览器同源 XHR"的指纹头；中间是一个**统一请求出口**，把取 Cookie、拼头、发请求、判结果串成一条所有人共用的管线；上面是十几个**写操作方法**，各自只填"地址 / 方法 / 请求体"三要素的差异。而到了业务成败这一层，它故意分成三派（吞异常回布尔 / 原样抛返对象 / 返结构体），让每种操作按自己界面的需要选最省事的方式——这是"该统一就统一、该分裂就分裂"的一次干净示范。

写操作客户端就位了，但它是被人调用的底座，自己不挑起任何界面。下一章《侧边栏内容列表》会把知乎的推荐、热榜搬进编辑器侧边栏——你在推荐列表里点的那一下"不感兴趣"，最终就是落到本章这个客户端发出去的。
