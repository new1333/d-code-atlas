# 评论父子树的游标分页

你点开一个几万赞同的热门回答，往下滑，评论区赫然挂着「1352 条评论」。你点「加载评论」，它先给你 20 条；你继续翻，第 2 页、第 3 页……翻到第 5 页某条评论底下，你还顺手展开了它的 60 条回复。这时老板走过来，你把评论区一收。等老板走了，你再展开——

要是按「翻页就重刷」的笨办法，你刚一展开，它又退回第 1 页，那 60 条回复也全没了，你得一页页重新点回来。

这一章要解决的，就是这种「深翻页 + 反复展开收起」场景下的状态保真：怎么让人往深处翻很多页都不偏移、收起再展开还在原地、翻页交界处还不把同一条评论显示两次。

说人话就是：**每翻一页，把新拉回来的评论增量攒进一棵一直活着的评论树；翻页只换「当前页那一片」，靠一个随页推进的续读书签（游标）让深翻不偏移，靠 id 去重让交界处不重复。** 下面从最底层的那块讲起。

## 一、游标续传：为什么不能只靠页码

先抛一个问题：为什么「翻到第 3 页」这么简单的需求，在评论区会变得麻烦？

想一下偏移分页（offset pagination）。你跟接口说「给我第 3 页、每页 20 条」，接口内部换算成「跳过 40 条、取 20 条」。静态数据上没问题。可评论区是活的：你翻到第 2 页的功夫，可能有 3 条新评论被顶上来、插到了最前面。等你请求第 3 页时，接口跳过的那 40 条里已经混进了新评论，结果你这页和「刚才那页」接不上缝——某条评论重复了，或者漏了。

游标分页（cursor pagination）换了个思路。它不要你报页码，而是给你一个「续读书签」：第一页拉回来时，接口附一句「下次想继续，带上这个书签」；你翻下一页，把书签原样递回去，接口就知道从哪接着给。书签永远指向「上一页最后一条的确切位置」，中间有谁插队、谁被删，都不影响这条缝。

打个比方：偏移分页像翻字典说「给我第 3 个抽屉」——可要是有人趁你不注意往第 1 个抽屉塞了东西，第 3 个抽屉里装的就不是原来的东西了；游标分页像在一卷长卷上夹一枚书签，书签夹在「你读到的那一格」，谁来动这卷都不影响你接着读。

这套机制在知乎评论里，因为接口历史包袱，落地成了三种续法（这正是本章最值得讲的地方）：

- **专栏评论**：接口直接回传一个「下一页 URL」，代码把这个 URL 原样存下来当书签，下次翻页直接请求它。这是最干净的游标续传——接口替你把「从哪续」全算好了。
- **子评论**：接口也回传「下一页 URL」，但代码没存整个 URL，而是用一句正则把 URL 里的 `offset` 参数抠出来，当成一个不透明的小书签存着，下次翻页原样回传。为什么「不透明」？因为这个值被当成字符串处理、从不做加减——它可能根本不是个数字，而是一串 token，代码不敢假定它的结构。
- **问题评论**：走的是一套老接口，**既没给可靠游标，也没给可靠分页信息**。代码只能退而求其次，用「页码 × 每页大小」自己反算 offset 去请求——这其实退化回了偏移分页，只能靠后续的去重和自估来兜底。选这个接口的唯一理由写在注释里：它没有反爬。

三种续法、三种可靠程度，背后是三个不同年代的接口。同一套「翻页」需求，被硬接成了三套实现。

## 二、累积列表 + id 去重：让「收起再展开」不发请求

游标解决了「往深处翻不偏移」。但还差一个问题：怎么保住你已经翻过的内容？

设想只存「当前页」会怎样：你翻到第 5 页，看到的是第 81～100 条；你收起评论区，再展开——当前页数据没了，要么重发请求从头翻，要么干脆什么都不显示。

所以评论区在「当前页」之外，还偷偷攒着一份**累积列表**：每翻一页，把新拉回来的评论按 id 和这份全集比对，重复的丢掉、新的追加进去。这份全集不为显示服务，它的全部职责就三个——去重、算总数、回看上一页。

这套手法你大概眼熟：第 7 章讲「相关问题」时，也是用 Set 按 id 去重后增量合并。**那里是合并两批一次性数据；这里的关键差别在于，累积列表要跨很多页长期活着**——它不是「这次请求完就丢」的临时变量，而是一路从第 1 页攒到末页的持久数据。也正因为要长期活着，去重的作用从「合并两批」升级成了「让一页页往深处翻时，交界处永远不重复」。

有了这份全集，「收起再展开」就变得几乎免费：

```
收起 / 展开
  ├─ 翻一个状态标记（collapsed ↔ expanded）
  ├─ 从累积列表里重新切出「当前页那一片」
  └─ 重新渲染
  ✗ 全程不发任何网络请求
```

翻页才请求，切换状态不请求——这就是为什么你收起评论区、过会儿再展开，它还稳稳停在第 5 页。

## 三、存储与显示必须分开：累积的必然代价

把内容攒成全集听起来很美，但它逼出一个硬约束：**你存的，和你显示的，不能是同一份。**

为什么？全集是「从第 1 页到当前页的所有评论」，而读者这一刻只想看「当前页那 20 条」。你图省事直接把全集全渲染出来，翻到第 5 页时会看到 100 条评论糊在屏幕上。所以渲染时，永远要从全集里切出「当前页那一片」再画。存全集、显示当前页——这是「累积」策略绕不开的代价。

但这套「累积 + 切片显示」并非唯一解。专栏评论就走了完全相反的路：

```ts
// 专栏：书签 = 接口回传的「下一页 URL」，翻页直接替换列表，不攒
const url = direction === "next" ? nextUrl : prevUrl;
list = await fetch(url);          // 直接替换，不 push 进全集
```

它用接口回传的 URL 当游标续传，但**翻页时直接把整个列表替换成本页结果，根本不攒全集**。为什么？因为 URL 游标和「累积」一旦配对，反而会错位——你攒着上一页，再用 URL 游标续传拉下一页，接口可能因为数据变动给你回了重叠或跳号的内容，攒出来的全集是乱的。专栏接口的 URL 游标足够可靠，干脆放弃累积，换「书签绝对准、但没法回看上一页」。

这是一个漂亮的对照：**问题/子评论接口的游标不可靠 → 攒全集 + 自己去重兜底，付出存储/显示分离的代价；专栏接口的游标可靠 → 直接替换、不攒，省了分离的复杂度，却丢了回看上一页。** 同一个「翻页」问题，因为接口可靠度不同，长成了两个相反的样子。

子评论则更特殊。它既攒全集（为了去重和算总数），**显示却又只给当页新拉的那批**，不从全集里切片：

```ts
// 子评论：全集照攒（为去重/算总数），显示只给当页新拉的
const seen = new Set(replies.map(r => r.id));
replies.push(...fresh.filter(r => !seen.has(r.id)));   // 全集照攒
display = fresh;                                       // 显示却只给当页这批
```

为什么子评论不敢像父评论那样「从全集按页码切片」？注释给了一句很实在的理由：**「知乎 API 返回的评论顺序可能和页码不完全对应。」** 既然顺序都对不上号，按页码切片切出来的就可能是乱的，干脆只显示当页新拉的那批，全集纯粹退化成「去重池 + 计数器」。

一张表把四种翻页实现理清楚（父评论的三个内容源，外加第二层的子评论）：

| 翻页实现 | 游标怎么续 | 翻页怎么存 | 显示给什么 |
|---|---|---|---|
| 问题评论 | 页码反算 offset（退化为偏移） | 累积合并 + id 去重 | 全集按页切片 |
| 专栏评论 | 接口回传的 next URL | 直接替换，不攒 | 本页结果 |
| 想法评论 | 页码反算 offset | 直接替换，不攒 | 本页结果 |
| 子评论 | 从 next URL 抠出的 offset | 累积合并 + id 去重 | 只给当页新拉的 |

注意一个反直觉的点：用没用游标，和攒不攒全集，是**两个独立的维度**。专栏用了最可靠的游标却不攒；子评论用了游标也攒，但攒了不切片显示；问题评论几乎没游标可游（退化成偏移），却攒得最全、还切片显示。接口靠不靠谱，决定了每一行怎么填。

## 四、父子两层，各自一套书签

到此讲的都是「一层评论」的翻页。可知乎评论区其实是**两层树**：

- 第一层是**父评论**（根评论），挂在「当前回答」底下，自己有一个累积列表；
- 第二层是**回复**，每条父评论内部又能开出一串回复。每条父评论自己有一个「已加载回复累积列表」，外加接口首屏附带的那几条 `child_comments` 和一个回复总数 `child_comment_count`。

既然是两层，就各自需要一套书签。父评论的游标管父评论往深处翻；回复的游标管回复往深处翻。两层互不干扰，可以各自独立地一页页往深处走。

这带出一个关键设计：**回复的「查看全部 N 条」走独立弹窗 + 独立游标。** 父评论首屏只附带几条回复（够你扫一眼），真要把 60 条回复看完，才点「查看全部」打开弹窗——弹窗里用的是回复自己的游标续传，跟父评论那一套完全分开。

这个设计说白了是为了「首屏轻」：大多数评论底下你只想瞄两眼回复，没必要一进来就把 60 条全拉回来烧请求；只有真要深翻回复的人，才在弹窗里一页页付这个代价。代价当然是——回复的存储、展示、游标都得跟父评论各做一套，弹窗里翻页用的还是字符串型游标（可能是非数字 token），不能简单按页码算术。

## 五、亲手跑一遍：游标分页状态机骨架

说了这么多机制，我们把最核心的几个——游标推进、累积去重、切片显示、状态持久——写成一个能直接 `node` 跑的最小状态机。它演的是「问题评论」这一型（累积 + 切片 + 状态持久），因为这一型把最多的原理揉在了一起：

```ts
// ===== mock：一个会回传「下一页游标」的评论接口 =====
type Comment = { id: string; text: string };
type Page = { comments: Comment[]; cursor: string | null }; // cursor=null 表示末页

const LIMIT = 20;
const all = Array.from({ length: 95 }, (_, i) => ({ id: `c${i}`, text: `第${i + 1}条` }));

function fetchPage(cursor: string | null): Promise<Page> {
  const start = cursor ? Number(cursor.replace("after-", "")) + 1 : 0;
  const slice = all.slice(start, start + LIMIT);
  const next = start + LIMIT < all.length ? `after-${start + LIMIT - 1}` : null;
  return Promise.resolve({ comments: slice, cursor: next });
}

// ===== 状态机：累积 + 游标 + 当前页 + 收起态 =====
const state = {
  accumulated: [] as Comment[],   // 全集：去重 / 算总数 / 回看上一页都靠它
  cursor: null as string | null,  // 续读书签（游标）
  page: 0,                        // 当前页码（只为切片显示用）
  collapsed: true,                // 收起态标记
};

async function loadNext() {
  if (state.page !== 0 && state.cursor === null) return; // 已到末页，不请求
  const { comments, cursor } = await fetchPage(state.cursor);
  const seen = new Set(state.accumulated.map(c => c.id));
  state.accumulated.push(...comments.filter(c => !seen.has(c.id))); // ① 游标续传 + id 去重
  state.cursor = cursor;
  state.page += 1;
  state.collapsed = false;
  render();
}

function toggle() {
  state.collapsed = !state.collapsed;
  render(); // ② 只翻状态标记，不调 fetchPage，不发请求
}

function render() {
  if (state.collapsed) return console.log("[收起] 显示「加载评论」按钮");
  const start = (state.page - 1) * LIMIT;
  const display = state.accumulated.slice(start, start + LIMIT); // ③ 存全集、显示当前页切片
  console.log(
    `[第${state.page}页] 书签=${state.cursor ?? "末页"} 已攒${state.accumulated.length}条 显示:`,
    display.map(c => c.id).join(",")
  );
}

// ===== 跑一遍执行轨迹 =====
(async () => {
  await loadNext(); // 第1页
  await loadNext(); // 第2页
  toggle();         // 收起（无请求）
  toggle();         // 展开 → 仍在第2页（无请求！）
  await loadNext(); // 第3页
  await loadNext(); // 第4页
  await loadNext(); // 第5页，书签=末页
  await loadNext(); // cursor=null，已末页，直接 return 不请求
})();
```

跑出来的轨迹：

```
[第1页] 书签=after-19 已攒20条 显示: c0,c1,...,c19
[第2页] 书签=after-39 已攒40条 显示: c20,...,c39
[收起] 显示「加载评论」按钮
[第2页] 书签=after-39 已攒40条 显示: c20,...,c39   ← 展开后仍在第2页，无请求
[第3页] 书签=after-59 已攒60条 显示: c40,...,c59
[第4页] 书签=after-79 已攒80条 显示: c60,...,c79
[第5页] 书签=末页   已攒95条 显示: c80,...,c94
（再次 loadNext：cursor=null，已末页，不请求）
```

对着轨迹看四个原理点：`loadNext` 每次把上一页留下的书签递回去续传、新拉的评论靠 id 进集合去重后并入全集（①）；`toggle` 全程不碰网络，只翻个标记（②）；`render` 永远只切当前页那一片（③）；收起再展开，`accumulated` 还在、`page` 还在，所以位置原封不动。专栏的「直接替换不攒」和子评论的「攒了但不切片显示」是这个骨架的两个变体——骨架没画，但上一节已说清各自的取舍。

（这里故意省略了三种内容源的 URL 差异、反爬请求头、HTML 渲染、点赞的乐观 UI、弹窗样式、错误处理，以及「评论区已关闭」的判定。它们都不服务于「演透游标分页」这个目标。）

## 六、关键权衡

这一章机制多，挑四条最实在的讲透。

**权衡一：用接口回传的「下一页 URL」当游标续传，换「翻多深都不偏移」。**
专栏评论这么干：代码不自己算偏移量，直接拿接口给的 next URL 当书签。换来的是无论数据怎么变动、翻到第几页，缝都接得准——偏移分页那种「中间有人插队就错位」的问题根本不存在。代价是这条 URL 游标必须随每一页持久化存好，而且它**只能配「直接替换列表、不做缓存」**——一旦你想既用 URL 游标又攒全集，攒出来的东西反而会错位（上一节专栏那段已展开）。可靠的游标和「累积」天然排斥，得选一个。

**权衡二：攒全集 + id 去重，换「收起再展开、回看上一页都不重发请求」。**
问题和子评论接口的游标靠不住（问题接口压根没有可靠游标），代码不敢把「续读位置」全托付给接口，于是自己攒一份全集兜底。换来的是切换收起态、回到上一页都几乎免费——状态全在本地，不用再求接口。代价是**「存储」和「显示」必须强行分离**：存的是全集，显示的只能是当前页那一片；子评论因为「接口返回顺序和页码对不上」更极端——全集攒着只为去重和算总数，显示却只敢给当页新拉的那批。攒全集换来了状态免费，却把「该显示哪一片」甩给了渲染层去头疼。

**权衡三：父评论与子评论各维护一套独立游标，换「两层各自独立往深处翻」。**
父评论用 next/previous URL 续传，子评论用从 URL 里抠出的 offset 续传，两套书签互不干扰。换来的是父评论翻父评论的、回复翻回复的，互不阻塞；回复还能按需在弹窗里懒加载。代价是分页状态结构相当臃肿——「是不是末页」「是不是首页」「上下游标 URL」「续传偏移」「当前页/每页大小/已加载数/总数」十来个字段都得存；而且四种翻页实现各写一套，连「是不是最后一页」都得用好几种不同判法（专栏看 next URL 在不在、子评论看本页够不够 limit、问题评论只能自己估算 loadedTotals 是否到顶）。多一层、多一种接口，分页状态就多膨胀一圈。

**权衡四：子评论「查看全部」走独立弹窗 + 独立游标，首屏只附带几条，换「首屏轻」。**
父评论底下首屏只给几条回复，够你扫一眼；真要看完全部 60 条，才点「查看全部」打开弹窗，用回复自己的游标一页页深翻。换来的是大多数「只想瞄两眼回复」的人，根本不用为那 60 条付请求代价。代价是子评论的存储、展示、游标都跟父评论完全分离，弹窗里翻页用的还是字符串型游标（可能是非数字 token），没法按页码做算术——又是多出来的一套独立分页逻辑。

## 七、小结

回到开头那个场景：你翻到第 5 页、展开了一串回复，收起、再展开——它还稳稳停在第 5 页，回复也还在。这靠的不是什么黑魔法，而是三件事一起发力：一个随页推进的续读书签（游标）让你往深处翻不偏移；一份一直活着的累积列表加 id 去重让交界处不重复、收起展开不丢内容；以及「存全集、显示当前页」的刻意分离。

评论区之所以长出三种续法、四种存储策略、两套独立游标，根子在一个朴素的事实：知乎的评论接口是不同年代拼出来的，靠不靠谱各不相同。代码没假装它们一样，而是对每种接口的可靠度做了不同取舍——可靠的就信书签、直接替换；不可靠的就自己攒全集兜底。同一套「翻页」，被接成了几种不同的样子，每一种都是在「这个接口到底能信几分」这个约束下能做到的最好。

至于另一个同样需要分页、同样靠本地缓存、却长成完全不同形状的场景——收藏夹，我们下一章再讲。
