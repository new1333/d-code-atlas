# 一次编写、六套构建器适配的 unplugin 模式 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：一个 Vue 宏（比如 `defineModels`）本质只是「把源码里的某些写法改写成另一种写法」。但前端构建器有六套（vite/rollup/webpack/esbuild/rspack/rolldown），它们的插件 API 形态各不相同。如果没有一层抽象，宏作者要么只支持一个构建器、要么把同一份改写逻辑抄六遍——每加一个宏就乘以六。使用者则会因为自己用的构建器不在支持列表里而无法用这个宏。

- **一句话核心思想**：把「改源码」写成与构建器无关的纯函数，再用一层适配壳把它分发成六套构建器各自认识的原生插件。

- **设计动机（为什么需要它）**：这个机制是为了解决「转换逻辑」与「构建器差异」之间正交增长、却被迫耦合的矛盾——宏的数量 × 构建器的数量本该是乘法爆炸，靠这层适配把它压成加法（写一份转换、零成本获得六套入口）。它换来的是「宏只管语义改写、构建器适配一次性解决」的清晰分层。
  - **承前**：（已在第 1 章『SFC 解析与增量 AST 编辑』讲透 magic-string-ast 的增量编辑与 setupOffset 偏移；本章**不关心**那个纯函数内部怎么改 AST，只看它「如何被包成一个与构建器无关的纯函数、再分发到六套构建器」这一新侧面。）

- **关键权衡（核心原料，4 条）**：
  1. **选择**「所有构建器统一走 unplugin 库的适配抽象、宏只写一份转换」→ **换来**一次编写、六套构建器原生入口自动生成、聚合层按当前构建器分发 → **代价**被锁死在该抽象暴露的 API 面里，用不到抽象未暴露的构建器私有特性；且每个宏包要维护六个近乎一行式的入口文件。
  2. **选择**「不在工厂内部按构建器 if-else 写六份代码，而是让同一个工厂在运行时拿到当前构建器名、就地分支」→ **换来**构建器相关的怪癖（如某构建器把单文件拆成多个虚拟子模块、文件 id 长得不一样）能在同一份逻辑里被内联处理，无需复制插件 → **代价**构建器差异会「漏」进文件过滤逻辑，抽象并不完全透明。
  3. **选择**「用一个统一的『特性门控 + 按构建器分发』函数作为聚合层与每个宏之间的唯一接口」→ **换来**聚合插件的主入口是一张扁平的「宏 × 开关」清单，新增或禁用一个宏只改一行、特性开关与分发共用同一机制 → **代价**要求每个宏都长得一样（同一个适配器形状）；少数不符合形状的宏只能被强转塞进去、且只能跑在部分构建器上。
  4. **选择**「把跨宏通用职责（文件过滤、找 vue 插件拿编译器 api、HMR 读改写）集中收在 common 公共层」→ **换来**宏自身只剩语义改写、可读性高、可独立维护 → **代价**同一套公共设施要同时伺候两种异形宏（「改 script 的纯转换宏」与「改 template、需往 vue 编译器里塞节点 transform 的宏」），后者甚至不走适配抽象，造成约定上的破口。

- **最小心智模型（3～7 步）**：
  1. 宏作者写一个纯函数「拿到源码、吐改写后的源码」，它不知道自己在哪个构建器里跑。
  2. 用一个适配器工厂把纯函数包起来：工厂在运行时收到「当前是哪个构建器」，据此算好该构建器需要的过滤规则，并声明插件名/过滤/转换。
  3. 适配库自动给这个工厂挂上六套「按构建器物化成原生插件」的方法。
  4. 每个宏包写六个一行式入口文件，分别 re-export 对应构建器的方法，供消费者按构建器 import。
  5. 聚合插件统一拿到当前构建器名，对每个宏调一次分发函数：开关关 → 不产出插件；开关开 → 按构建器物化出原生插件。
  6. 物化出的原生插件，其「过滤」决定改哪些文件、「转换」把活全委托回第 1 步的纯函数。
  7. 通用职责（过滤、拿 vue 编译器 api、HMR 读改写）从 common 取用，宏只挑自己需要的。

- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个几十行的脚本，演透三条原理——① 转换是纯函数；② 一个工厂同时给出多套构建器的适配形态（用真实库的六适配器简化成 2～3 个手写适配器即可）；③ 分发函数 = 「按构建器选适配器」+「开关门控」。每一行都对应上面某个原理点。
  - **应故意省略**：真实 unplugin 库的完整 API、虚拟模块（resolveId/load，那是下一章）、HMR hack、构建期宏生成插件名、类型泛型、webpack 虚拟子模块正则的完整细节。
  - **演示载体建议**：本仓库是 TS/JS，建议写成一段**能 `bun run`/`node` 直接跑的脚本**（能跑最好，非硬要求）。因为本章原理与 Vue 无关、纯是「插件分发」机制，一段不依赖任何构建器的独立脚本最能演透；不要去真的起一个 vite/webpack，那会淹没原理。
  - 建议骨架（供 Writer 落地时参照，演的是「权衡 1/2/3」）：
    ```js
    // 原理点①：转换是纯函数，与构建器无关
    function transformFoo(code) { return code.replaceAll('defineFoo(', 'defineBar(') }

    // 原理点②：一个工厂给出多套构建器适配形态（真实库自动挂 6 个，这里手写 2 个演示）
    function makeFooFactory() {
      return {
        vite: () => ({ name: 'foo', enforce: 'pre', transform(c) { return transformFoo(c) } }),
        rollup: () => ({ name: 'foo', transform(c) { return transformFoo(c) } }),
      }
    }

    // 原理点③：分发函数 = 特性门控 + 按构建器选适配器
    function resolve(factory, framework, enabled) {
      if (!enabled) return undefined        // 开关门控
      return factory[framework]()           // 按构建器物化
    }

    const framework = 'vite'
    const plugins = [
      resolve(makeFooFactory(), framework, true),
      resolve({}, framework, false),         // 关 → undefined
    ].filter(Boolean)                        // 抹掉 undefined，聚合层是 flat list
    console.log(plugins[0].name, plugins.length)  // → foo 1
