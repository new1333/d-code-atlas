# 编译期注入虚拟 helper 模块 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）

- **用户痛点 / 场景**：宏在编译期把一个新调用注入进了你的源码，而这个调用依赖一个「磁盘上根本不存在的模块」。如果没有专门的机制，构建器在解析这行新插入的 import 时会直接报「找不到模块」，宏注入的运行时帮手就永远落不了地。换句话说，宏想「凭空」给用户塞一段运行时实现，却无处可塞。

- **一句话核心思想**：编译期只往源码插一句指向虚构路径的 import，运行时由插件自己冒充这个模块、把实现代码当场交出来。

- **设计动机（为什么需要它）**：这个机制要解决的是「注入的帮手代码到底该住哪」的矛盾。住进用户项目会污染源码树、版本难以和宏同步；完全内联到每一处调用点又会让产物膨胀且无法复用。于是用「虚拟模块」把「注入点」与「实现」彻底分开——编译期只认一行指向虚构路径的 import，真正的运行时实现集中住在宏自己的包里，由插件在加载阶段交出。其中承前部分：（已在第 2 章『一次编写、六套构建器适配的 unplugin 模式』讲透插件外壳与构建器解耦，本章只看它新暴露的『模块解析拦截』这一侧面）。而帮手内部如何把属性与事件粘成可写引用，是第 5 章『defineModels：从类型合成 props/emits 双向绑定』的主题——本章只管「这段实现如何被装载进产物」，不展开其内部语义。

- **关键权衡（本 Atlas 的核心）**：
  - 用「磁盘上不存在的虚构路径」当 import 目标 → 换来帮手代码集中维护、不污染用户源码树、还能被多个特性（结构扩展、命名模板等）复用 → 代价是必须实现一整套模块解析拦截（认领解析、声明可加载、交出代码三步），且这套拦截要适配不同构建器的差异。
  - 把「帮手的源文件」直接当作「被加载的模块内容」自我引用 → 换来实现与被加载内容永不漂移（改一处即同步生效） → 代价是依赖构建器对「以原始字符串形式导入文件」这一约定的支持，且帮手文件里不能含仅编译期有效、运行期会塌掉的语法。
  - 给注入的标识符统一加一段内部前缀，并用缓存按「来源+名字」去重 → 换来同一帮手被多处引用时只插一条 import、且绝不与用户代码撞名 → 代价是用户在产物里看到的变量名是被改写过的、对人类不可读。

- **最小心智模型（3～7 步）**：
  1. 宏在转换用户源码时，在 setup 顶部插入一行 import，目标是一个带统一前缀的虚构路径。
  2. 同时把原来对宏的调用，改写成调用这个 import 进来的帮手。
  3. 构建器尝试解析这行新 import，逐个询问插件「谁能认领这个路径」。
  4. 本插件认领，把该虚构路径固定为一个确定的模块标识，从而阻止构建器再去磁盘找文件。
  5. 构建器随后要加载这个标识；本插件把预先以字符串形式备好的帮手源码作为模块内容交出。
  6. 帮手代码由此进入正常打包流程，与用户代码一起被打进产物、一起运行。

- **最小原理演示（替代旧"复刻范围"）**：
  - 应演示：一个极简的「假构建器 + 插件」流水线，演透「import 一个磁盘上没有的模块，靠插件拦截并交出代码」这件事。大约几十行即可：定义一个虚构路径常量；在转换阶段往一段示例用户代码顶部插一行 import 并把调用改写掉；在「解析」阶段由插件认领该路径返回标识；在「加载」阶段由插件返回一段自造的实现字符串；最后把交出的代码与用户代码拼装、求值，验证调用确实命中了帮手。这段演示演的正是「用虚拟模块桥接编译期与运行时」这条核心权衡——注入点与实现解耦。
  - 应故意省略：多构建器适配（vite/webpack/rspack 的差异）、帮手内部的双向绑定语义（留给第 5 章）、多个帮手的分派、source map、HMR、内部前缀去重的全部工程细节。
  - 演示载体建议：本仓库主语言是 TS/JS，建议写成一段能被 `node`/`bun` 直接跑的独立脚本——手写一条「转换 → 认领 → 加载 → 字符串拼装 → 求值」的最小流水线，**不依赖真实 vite/rollup**，这样能把「虚构模块如何被认领和交出」演到肉眼可见；不要套任何工程化脚手架。一句话原则：载体服务于「演透原理」，这里重点是让读者看见 import 一个不存在的路径却没有报错、反而拿到了实现。

- **正文不宜展开的细节**：「以原始字符串导入文件」的约定在不同构建器的差异、为何某些构建器必须额外声明「可加载」过滤器、帮手内部用响应式库粘合属性与事件的具体走法（属第 5 章）、赋值即触发事件那种模式下赋值表达式的改写细节（属第 5 章）、内部前缀与增量字符串编辑的去重实现。

- **推荐的一个执行轨迹例子**：
  - 输入：setup 里一句声明双向绑定的宏调用。
  - 转换后：顶部多出 `import 帮手 from "<虚构路径>"`，原调用被改写为 `帮手([...])`。
  - 构建器解析该 import → 插件认领 → 加载 → 交出帮手的源码字符串。
  - 输出：帮手函数被打包进产物，运行时把对应的属性与 update 事件粘成可写引用。

## 概念要点

- **虚构路径的统一前缀来自一个全局常量**：所有 vue-macros 虚拟模块共享同一前缀 `/vue-macros`，define-models 在其下挂自己的命名空间 `/vue-macros/define-models`，再派生两个具体帮手路径。这种「前缀分层」让任何插件都能用 `startsWith` 一眼认领属于自己的虚拟 id。源码位置: `packages/common/src/constants.ts:38`、`packages/define-models/src/core/helper/index.ts:3-8`

- **帮手源文件即被加载内容（关键巧思）**：声明虚构 id 的同时，用 `?raw` 把同目录下的运行时实现文件以**字符串**形式导入（`emitHelperCode`/`useVmodelHelperCode`）。于是「帮手的实现」与「load 时要交出的模块内容」是同一份文本，改实现即改被加载内容，永不漂移。源码位置: `packages/define-models/src/core/helper/index.ts:6,9`

- **运行时帮手之一（双向绑定粘合剂，内部语义留第 5 章）**：默认导出一个函数，借助响应式库的 `useVModel` + `getCurrentInstance`，把组件 props 与对应的 `update:` 事件粘成一组可写 ref；支持「单个键名」与「[键名, 属性名, 事件名, 选项] 元组」两种入参。源码位置: `packages/define-models/src/core/helper/use-vModel.ts:4-28`

- **运行时帮手之二（赋值改写的发射器，内部语义留第 5 章）**：默认导出 `(emitFn, key, value, ...args)`——先发射事件，再返回传入值（若有额外参数则返回第一个额外参数，用于保留原赋值表达式的求值结果）。它服务于「赋值即触发事件」模式，让被改写的赋值表达式在语义上仍返回新值。源码位置: `packages/define-models/src/core/helper/emit-helper.ts:3-11`

- **模块解析拦截三件套**：在 unplugin 实例里同时实现三个 hook——① 认领解析：id 以前缀开头则返回 id 本身，把虚构路径固化为模块标识、阻止磁盘查找；② 声明可加载：同样以前缀做过滤器（某些构建器需要它才知道哪些 id 该进 load）；③ 加载：按精确 id 匹配，返回对应的 `?raw` 源码字符串。三者合起来才能在多构建器下都成立。源码位置: `packages/define-models/src/index.ts:56-68`

- **编译期 import 注入器（公共能力）**：一个公共函数负责「在指定偏移处插入一行 import 并返回可用的本地名」。它给本地名统一加 `__MACROS_` 前缀避免与用户代码冲突，并用一个以 magic-string 实例为键的 WeakMap 按「来源@导入名@前缀@本地名」去重——同一帮手在一处源码里被多次引用也只插一条 import。注入时区分默认导入与命名导入两种形态。源码位置: `packages/common/src/ast.ts:151-178`

- **注入处如何串起虚构路径**：在改写运行时调用时，调用上述注入器，把 `from` 参数直接传成虚构 id；注入器据此生成 `import __MACROS_useVModel from "<虚构路径>"`，并把宏调用改写为对该导入名的调用。reactivity-transform 模式下赋值改写也用同一注入器指向另一个帮手 id。源码位置: `packages/define-models/src/core/index.ts:286-311,326-335`
