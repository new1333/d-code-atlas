# 订阅原语：回调集合与作用域自动清理

## 你为什么会需要一套「订阅原语」

用 Pinia store 的人，最常见的两类通知需求是：

- **状态一变就告诉我**（`$subscribe`）：store 的 state 改动后，把「这次变了什么 + 最新状态」回调给我。
- **某个 action 被调用了，且让我挂它的成功/失败回调**（`$onAction`）：每次调用一个 action 前后，分别给我一个插入点。

这两类需求看似不同，但剥到骨头里，它们的骨架完全一样：

```
注册：把回调收进某个容器 → 广播：遍历容器逐个调用 → 卸载：从容器移除回调（并顺带释放资源）
```

如果各自单独造一套「容器 + 广播 + 卸载」，会出现高度重复的三份代码，而且每份都得自己处理「同一个回调被重复注册」「在组件外（store 互引、SSR、独立脚本）订阅时到底什么时候该取消」这些繁琐问题——啰嗦、重复、极易内存泄漏。

Pinia 的做法是：把这套与业务无关的骨架抽成一个**订阅原语**，让 `$subscribe` 和 `$onAction` 各自只在它之上补上「卸载时还要顺手释放什么」这一笔尾巴。

## 一句话核心思想

> **订阅 = 往集合里塞一个回调 + 立刻返回一个「注销闭包」+ 默认把这个闭包绑到当前作用域的销毁时机。**

记住这一句，整章就迎刃而解。

## 四个原子（纯概念）

原语只由四个不可再分的「原子」组合而成。

**原子一：用集合持有回调。** 每一类订阅各持有一个 `Set`。状态订阅一个集、action 订阅一个集。`Set` 天然去重（同一回调引用只能入一次），天然支持遍历删除。容器问题一句话解决。

**原子二：返回一个幂等的注销闭包。** 注册时不只是「塞进集合」，还要当场造一个**捕获了这个回调**的闭包返回给调用方。这个闭包只做两件事：从集合里 `delete` 该回调；如果 `delete` 确实删掉了（返回 `true`），再调一次「清理回调」。注意是「删掉成功才清理」——因此这个注销闭包**天然幂等**：无论被调用多少次，资源只会被释放一次。手动注销、作用域自动注销，都走这同一个函数体。

**原子三：默认绑作用域销毁。** 注册时若满足两个条件——**没声明脱离**（`detached` 为假）且**当前正处在某个 effect scope 内**——就把那个注销闭包挂为该作用域的销毁钩子（`onScopeDispose`）。这一笔是「零样板防泄漏」的关键：你在组件 `setup` 里订阅，组件的 effect scope 被销毁时，注销闭包自动触发。组件外（全局监听、store 互引）若没有作用域，则不挂——此时注销完全交还调用方。

**原子四：按回调签名透传广播。** 广播原语只负责「遍历集合、把触发时的实参原样透传给每个回调」。状态订阅的回调是双参（变更对象 + 新状态），action 订阅的回调是单参（action 事件对象）——广播原语不关心签名差异，谁注册时是什么签名，触发时就照那个签名传。一个广播原语喂两种业务。

## 关键权衡（为什么这样设计）

每个原子背后都是一次取舍。

**① 把注销做成「捕获回调的闭包」并返回它**
- 换来：手动注销、作用域自动注销、额外资源释放，三种卸载语义共用同一个函数体（都走这一个闭包）。
- 代价：每次订阅多分配一个闭包对象。

**② 默认在「非脱离 且 正处于某作用域内」时，把注销闭包挂为作用域销毁钩子**
- 换来：组件内订阅零样板、自动防泄漏。
- 代价：想让订阅**跨作用域长期存活**（如全局监听），必须显式声明 `detached`，并自己持有注销函数、记得手动调。

**③ 把「卸载时要顺带释放的外部资源」做成一个可选清理回调参数（缺省为何也不做）**
- 换来：同一个原语既服务**没有尾巴**的 action 订阅（不传该参数），又服务**带尾巴**的状态订阅（传「停掉对应侦听器」）。
- 代价：资源释放职责被劈成两半——集合成员资格归原语管，外部资源释放归调用方用清理回调表达。

**④ 广播时按回调自身的签名做可变参数透传**
- 换来：一个广播原语同时喂给「双参状态订阅」和「单参 action 订阅」。
- 代价：所有回调须符合同一可调用类型；集合里元素的签名在注册那一刻就定死。

## 生命周期心智模型（七步）

把四个原子串成一条完整的生命周期：

```
1. 装配：上层各持一个空 Set 作为「某一类回调的容器」
2. 注册：回调入集合，立刻造好捕获它的注销闭包
3. 绑生命周期：若「非脱离 且 当前在作用域内」，把注销闭包挂为作用域销毁钩子
4. 返回：把注销闭包交给调用方，作为「手动取消」的通道
5. 广播：遍历集合，按注册时的签名把实参原样透传给每个回调
6. 卸载（三种触发源之一）：手动调返回的注销函数 / 所在作用域被销毁 / 整个 store 被销毁
   → 注销闭包内部：从集合删除该回调；删成功则调清理回调（释放外部资源）
7. （边界）整店销毁：见末节「$dispose 的分工」
```

一条执行轨迹例子：在组件 `setup` 里 `const stop = store.$subscribe(cb)`——

```
cb 进状态订阅集
  → 因当前正处在组件作用域内，注销闭包被挂到该作用域
  → 组件存活期间，每次状态变更都遍历集合调 cb
  → 组件卸载 → 作用域销毁 → 触发注销闭包
  → 集合删除 cb 成功 → 调清理回调 → 停掉为 cb 创建的侦听器
```

对照组：若写成 `store.$subscribe(cb, { detached: true })`，则**不挂作用域**，组件卸载后 cb 仍留在集合里持续被广播（泄漏）——除非你自己保留 `stop` 并在合适时机手动调。

## 最小原理演示

下面用几十行从零实现，演透四个原子。它不追求工程完整（省略了完整 TS 泛型标注、去重、业务包装），只演「集合 + 注销闭包 + 作用域绑定 + 可选清理尾巴」这条主线：

```ts
import { getCurrentScope, onScopeDispose, effectScope, ref } from 'vue'

// —— 原语：四个原子 ——
function addSubs(set, cb, detached, onCleanup = () => {}) {
  set.add(cb)                              // 原子一：入集合

  const remove = () => {                   // 原子二：捕获 cb 的幂等注销闭包
    if (set.delete(cb)) onCleanup()        //   删成功才清理 → 幂等
  }

  if (!detached && getCurrentScope()) {    // 原子三：非脱离 且 当前在作用域内
    onScopeDispose(remove)                 //   挂为作用域销毁钩子
  }

  return remove                            // 返回 → 手动取消通道
}

function triggerSubs(set, ...args) {       // 原子四：按签名透传广播
  set.forEach((cb) => cb(...args))
}

// —— 跑通「注册 → 广播 → 卸载自动清理 → 清理尾巴被触发」——
const subs = new Set()
const state = ref(0)

const scope = effectScope()
scope.run(() => {
  // 在作用域内订阅，附带一个「清理尾巴」
  addSubs(
    subs,
    (payload, s) => console.log('收到', payload, s),
    false /* 非脱离 */,
    () => console.log('清理尾巴被触发：停侦听器 / 释放资源')
  )
})

// 广播：双参原样透传给回调
triggerSubs(subs, { type: 'patch' }, state.value)   // → 收到 { type: 'patch' } 0

// 卸载自动清理：销毁作用域 → onScopeDispose 触发 remove
//   → 删除 cb 成功 → onCleanup() 被调 → 打印「清理尾巴被触发」
scope.stop()
```

注意演示里 `onCleanup` 是可选的：不传它时（action 订阅就是这样），卸载只是把回调从集合删掉，没有任何尾巴要释放。

## 原语如何被上层消费

原语本身只有「注册 + 广播」两个出口，上层各取所需：

- **`$onAction`**：把 action 订阅集合偏应用绑死给原语的第一个参数。注册 action 订阅时**不传清理回调**（走默认的「何也不做」）——因为 action 订阅不持有需释放的资源。
- **`$subscribe`**：注册状态订阅时**传入清理回调** `() => stopWatcher()`——状态订阅背后挂着一个 `watch`，订阅被移除时要连带把这个侦听器停掉。这正是清理回调参数存在的理由。它还在注册前先检查「同一回调是否已注册」：命中则直接返回一个空函数当「假 remove」（调了也无害），避免重复订阅。
- **状态广播**：`$patch` 因为中途暂停了监听侦听器，需**手动**调一次广播，保证「一次 patch = 一次状态订阅事件」而非每属性一事件。
- **action 广播**：action 包装器在每次调用前后多次广播——调用前广播事件对象，执行后按同步返回 / Promise 成功 / 失败分别广播对应回调。具体的「每次调用临时新建 after/onError 订阅集」细节，留给后续「状态及动作订阅」一章展开。

## $dispose 的分工：作用域销毁负责成员归零，clear 负责清尾巴

整店销毁（`$dispose`）演示了原语边界处最微妙的一段。它的真实执行顺序是：

```
1. scope.stop()                  ← 先停作用域
2. subscriptions.clear()         ← 再清空状态订阅集
3. actionSubscriptions.clear()   ← 清空 action 订阅集
4. pinia._s.delete($id)          ← 从实例字典移除该 store
```

**关键在「先 stop 后 clear」这个顺序带来的因果分工：**

`scope.stop()` 先执行——此时集合成员**仍在集合中**。对所有「非脱离、在作用域内」的订阅，它们的注销闭包当初正是经 `onScopeDispose` 挂在这个 scope 上的。scope 一停，这些注销闭包被逐个触发：`delete(cb)` 成功（成员还在，删得掉）→ `onCleanup()` 被调 → 状态订阅的 `stopWatcher()` 被执行。**也就是说，作用域销毁这一步，把正常订阅连同它们的外部资源（侦听器）一并正确释放了。**

随后 `clear()` 执行——但它只能扫到**剩余成员**：即那些当初声明了 `detached`、或注册时本就不在任何作用域内、因而**没有**注册 `onScopeDispose` 的订阅。`clear()` 是直接对 `Set` 操作，**绕过了注销闭包**，因此**不会**触发这些剩余成员的 `onCleanup`。

于是分工清晰了：

- **作用域销毁（`scope.stop`）**：负责「正常成员归零 + 顺带释放它们的外部资源」。
- **`clear()`**：只负责清扫「脱离 / 不在作用域内的剩余成员」，但**不**替它们释放外部资源——这部分本就由声明 `detached` 的调用方自行负责。

这也回扣了权衡②的代价：声明脱离换取了跨作用域存活，代价就是即便整店销毁，原语也不会替脱离订阅善后。
