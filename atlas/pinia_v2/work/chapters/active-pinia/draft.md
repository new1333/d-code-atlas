# 全局活跃指针与 Pinia 实例契约

> 本章是整个 Pinia 取用体系的地基（layer: primitive，无前置依赖）。它只建立在两个 Vue 基础概念上——依赖注入（`provide` / `inject`）与插件钩子（`app.use` 的 `install`）。后续所有章节——store 的懒实例化、装配、订阅、插件——都建立在「如何拿到当前该用的那个 pinia 实例」之上。本章只回答一个问题：**组件之外，pinia 实例从哪里来？**

## 一、问题：组件之外，pinia 实例从哪来？

在组件的 `setup()` 内部取用一个 store 很自然——Vue 的依赖注入会把 `app.use(pinia)` 时注册的实例递送进来。可一旦脱离组件上下文，这条路就断了。典型场景有三类：

- **跨 store 互引**：在 store A 的 getter 里取用 store B，此刻并不处于任何组件的 `setup()` 中。
- **SSR**：在 `fetch` / `setup` / `serverPrefetch` 这类服务端顶层函数里取用 store。
- **模块顶层**：在没有任何组件包裹的纯模块代码里直接 `useStore()`。

注入是「按组件作用域精确」的，但它只在组件内可用；要穿越这些边界，需要另一种机制。Pinia 的选择是：**用一个模块级的全局指针记住「此刻正在被使用的那个 pinia」**。两条路最终汇成一个统一的取用入口。

矛盾与权衡就藏在这里——注入精确但受限；全局指针无视边界但不精确。本章的核心，就是把这两条路径叠在一起的方式讲透。

## 二、底层原语：一个模块级可变指针

整条「组件外取用路径」的唯一载体，是一个**模块级的、可变的**变量——把它叫做「活跃指针」。它初始为空（`undefined`），代表「此刻还没有任何 pinia 被确立为活跃」。改写它靠一个**设置函数**，读取它靠一个**取用函数**以及 store 装配链。

**设置函数**被刻意写成「赋值即返回」：函数体只有一行赋值表达式 `activePinia = pinia`。赋值表达式的求值结果就是被赋的值，于是这个函数既改写了指针（副作用），它的返回值又是被设置的实例本身。这种形态让它能直接嵌进赋值表达式里被当作值使用；配套的三重重载类型签名只是让这种用法类型顺滑的 TypeScript 技巧，不影响行为，本章不展开。

一句话概括底层原语：**一个可写的全局槽位 + 一个「写下即返回」的赋值器**。指针本身是空的，它的意义要在下文两个「组合机制」里才显现。

> **权衡 1（贯穿全章的核心代价）**：用一个可变的全局模块指针，换来「无需层层把 pinia 当参数传」的便利。代价是——它是一份隐式可变的模块级全局状态。服务端多个并发请求共享同一份模块状态时，指针会被互相覆盖，造成跨请求串污染。正因如此，使用者必须在每个请求入口显式重置指针（或把 pinia 显式传进取用调用）来隔离。这条代价会在第八节具体演。

## 三、组合机制一：安装时同时建立两条路径

指针本身是空的，必须有人在「正确的时机」把它指向正确的实例。第一个时机，就是安装 pinia 的时候。

`createPinia()` 返回的实例是一个 Vue 插件（带 `install` 钩子）。`app.use(pinia)` 触发安装，**在同一刻做两件事**：把全局指针指向自己（建立「组件外取用」路径），同时把实例 `provide` 进应用注入上下文（建立「组件内取用」路径）。源码里那条英文注释说得直白——这套机制就是为了让「安装 pinia 之后，即使不在组件 `setup()` 里也能取用 store」。

```
app.use(pinia)
      │
      ├─① 设置指针 = pinia          ──► 组件外取用路径（全局指针）
      │
      └─② app.provide(sym, pinia)  ──► 组件内取用路径（依赖注入）
```

同一刻两件事，是「双路径取用」的源头：设置指针那一步解释了「为什么安装之后、即便不在组件内也能取到 pinia」；`provide` 那一步解释了「为什么组件内 `inject` 能命中它」。一旦安装完成，两条路都已就绪。

## 四、组合机制二：取用函数的双路径归一

对外暴露给用户的取用入口是取用函数。它的实现把两条路径归一成一个判断：**有注入上下文就注入，否则读指针**。逻辑是三段拼接——先问「现在有没有注入上下文」（即是否在组件 `setup()` 内）；有，就 `inject` 取注入的 pinia；没有，这一段为空；最后兜底 `||` 读全局指针。

这就是「注入优先、指针回退」的字面语义：**组件内拿到最精确的注入实例，组件外拿到兜底指针**。其字面实现见文末「源码对照」。

这里还藏着一个开发 / 生产双版本的设计：

> **权衡 3**：取用函数在开发构建里多了一段诊断——当「服务端（非客户端）且注入落空」时上报一条 error 级提示，因为这种情况极可能意味着 SSR 顶层函数忘了显式设置指针。而生产构建把这段检查整段裁掉，直接静默回退。换来的是生产包更小、取用路径更短更快；代价是生产环境里取用失败时不再有任何报错提示。

> 一个容易看错的事实：对外 API 取用函数与 `useStore()` 内部装配链是**两套分离的实现**。`useStore()` 并不调用取用函数，而是直接读取那个模块级指针变量。两者逻辑等价，但实现分家——取用函数面向外部用户，装配链为了性能和上下文直接读变量。

## 五、取用链细节：刷新指针与统一读指针

`useStore()` 内部对 pinia 的取用，把双路径逻辑写得更细，并暴露两个容易被忽视的细节。

**第一个细节：只有真正取到 pinia，才顺手刷新指针。** 取用时的优先级是——显式传入的 `pinia` 参数优先，其次注入；只要取到了实例，就把全局指针刷新成它（测试模式下还有一条「忽略传入 pinia、改走 testing pinia 指针」的旁路，属测试替身机制，本章略）。若这一步什么都没取到，则**不刷新**——指针维持上一次的值，继续靠兜底。

**第二个细节：无论走哪条路，最终都统一从指针读取。** 也就是说，三条路径的分歧只用于「决定把哪个实例刷新进指针」，刷新之后一律以 `pinia = 指针` 收口。这是双路径在装配链里的真正归一点。

```
useStore(pinia?)
   │
   ├─ 显式传入 pinia?  ──┐
   ├─ 测试旁路?         ──┤ 任一取到 ──► 刷新指针 = 该实例
   └─ 注入命中?         ──┘
                            都没取到 ──► 不刷新，保持指针现状
                                                      │
                                                      ▼
                                            pinia = 指针   ← 统一出口
```

## 六、嵌套互引：求值前的指针刷新

为什么需要一个「可被反复刷新」的指针？答案在跨 store 互引。设想 store A 的 getter 内部取用了 store B：取用 B 的那一刻，注入上下文早已不在（getter 在装配期求值，不在组件内）。要保证此刻指针指向 A 所属的那个 pinia，必须在**求值 A 的 getter 之前**先把指针刷回 A 的 pinia。

源码正是这么做的——在装配 getter、执行 action 之前，各插入一次「把指针刷成当前 store 的 pinia」，注释点明动机正是「允许跨 store 互引」。这样，无论 getter / action 里嵌套地二次取用别的 store，指针始终指向「当前正在被求值 / 执行的这个 store 所属的 pinia」，嵌套取用就能拿到正确实例。

> 这一节是「指针刷新」的消费端。刷新的完整机制（装配、getter、action 如何协作）属于「store 装配机器」章；本章只点明：**可变指针之所以必须可变，正是为了支撑这条嵌套互引链**。

## 七、最小原理演示：从零实现「全局指针 + 注入回退」

抛开 Pinia 的工程细节，本章核心思想用几十行就能演透。下面的迷你实现只表达一件事——**一个可变全局指针，加上「注入优先、指针回退」的取用入口**。它自洽、不依赖原仓库，与真实源码非逐字雷同，只为演透「双路径取用 + 全局指针」这一核心思想：

```ts
import { inject, hasInjectionContext, type App } from 'vue'

// ① 底层原语：模块级可变指针
let active: PiniaLike | undefined

// ② 设置函数：赋值即返回
const setActive = (inst: PiniaLike | undefined) => (active = inst)

// ③ 安装时同时建立两条路径
function install(this: PiniaLike, app: App) {
  setActive(this)                 // 指针路径
  app.provide(PINIA_KEY, this)    // 注入路径
}

// ④ 取用入口：注入优先，指针回退
function getActive(): PiniaLike | undefined {
  return (hasInjectionContext() && inject(PINIA_KEY)) || active
}

interface PiniaLike { install(app: App): void }
const PINIA_KEY = Symbol('pinia')
```

每一行都对应到前面的某个原理点：第 ① 行是模块级指针；第 ② 行是「赋值即返回」；第 ③ 行是安装时建立双路径；第 ④ 行是双路径归一。

> 这段演示有意**省略**了：求值 / 执行前的指针刷新（属装配章）、开发 / 生产双版本与 SSR 诊断、测试旁路、`Pinia` 接口的其余字段、Symbol 的调试差异。它们都不影响「双路径取用 + 全局指针」这一核心思想。

## 八、SSR 串污染：代价的具体剧本

权衡 1 的代价，用两个并发请求的执行轨迹最直观。服务端 Node 进程只有**一份**模块状态，活跃指针是所有请求共享的：

```
请求 A: setActive(piniaA)        // 指针 = piniaA
请求 A: await fetch(...)         // A 让出执行权
            │
            ▼  （此时指针仍是 piniaA）
请求 B:        setActive(piniaB) // 指针被覆盖 = piniaB
请求 B:        ... 读 store ──► 拿到 piniaB ✓
            │
            ▼
请求 A 恢复:    读 store ──► 读到 piniaB ✗（串污染！）
```

请求 A 恢复执行时，指针已被 B 覆盖，于是 A 取到了 B 的状态字典。正解有两条，本质都是把「全局指针」这条不精确路径重新收窄回本请求：

- **每请求入口显式重置指针**：在 `fetch` / `setup` / `serverPrefetch` 顶部把指针设为本请求的 pinia；
- **或把 pinia 显式传进取用调用**：`useStore(pinia)` 直接绕开指针。

开发构建里的那条 error 级诊断正是为这条代价兜底——它在「SSR 注入落空」时大喊一声，提醒你检查时序。

## 九、Pinia 实例契约：一眼带过

最后，被指针化、被注入的那个「pinia 实例」到底长什么样？本章只把它当作背景交代，其余字段归各专题章。一个 pinia 实例大致是这样一组东西：

- **install**：Vue 插件钩子，本章的主角之一——安装时同时挂上注入路径与指针路径。
- **state**：根状态字典（一棵扁平的状态树）——归 createPinia 章。
- **use / _p**：注册插件与插件数组——归插件系统章。
- **_a**：所属 app——归 createPinia 章。
- **_e**：副作用作用域（所有 store 响应式副作用的容器）——归 createPinia 章。
- **_s**：store 注册表（id → store）——归装配章。
- **_testing**：测试旁路标志——归测试替身章。

本章只关心一条事实：**pinia 实例是这样一个「可被注入、可被指针化」的对象**，`install` 把它同时挂到注入上下文和全局指针上。其余字段，后续章节逐个展开。

至于注入用的那个 Symbol，也是开发 / 生产双形态（开发用带描述的 `Symbol('pinia')` 便于调试，生产用无名 `Symbol()` 更小），并标注为内部 API——它是 storybook 等多 app 场景下需手动 `inject` 的边界点，本章仅作背景记录。

## 小结

| 机制 | 作用 | 源码定位 |
|---|---|---|
| 模块级指针 + 设置函数 | 组件外取用载体；赋值即返回 | `rootStore.ts:27, 36` |
| 取用函数双版本 | 注入优先 `\|\|` 指针回退；生产裁掉诊断 | `rootStore.ts:47–58` |
| 安装建立双路径 | 设置指针 + `provide` 同步建立 | `createPinia.ts:24–28` |

**核心概念一句话**：用一个可变的全局模块指针记住「当前该用的 pinia」，组件内走注入、组件外走指针，两者在取用入口归一为「能注入就注入，否则读指针」。

**四条关键权衡**：

1. 全局指针换「无需层层传 pinia」的便利 → 代价是 SSR 跨请求串污染，须显式重置指针。
2. 取用函数「注入优先、指针回退」→ 兼顾精确与兜底 → 代价是组件外拿到的是「最后一次被设置的指针」，调用时序敏感。
3. 生产构建 tree-shake 掉诊断 → 包更小、路径更快 → 代价是生产环境取用失败静默兜底，无报错。
4. 设置函数做成「赋值即返回」+ 三重重载 → 可在表达式里当值用、类型顺滑 → 代价是核心状态是隐式可变全局变量，封装性弱。

掌握了这一章，「pinia 实例如何被持有与取用」的地基就铺好了——后续章节的所有 store，都从这个被指针化、被注入的实例上生长出来。

## 附：源码对照

正文用迷你演示承载了原理。若要对照真实实现，下面三段是核心源码（定位见上方小结表）。

**① 设置函数与模块级指针**（「赋值即返回」：函数体即赋值表达式，返回值就是被设置的实例）：

```ts
export let activePinia: Pinia | undefined

export const setActivePinia: _SetActivePinia = (pinia) => (activePinia = pinia)
```

（三重重载类型签名与 `@ts-expect-error` 属 TypeScript 技巧，此处略。）

**② 取用函数的开发 / 生产双版本**（注入优先、指针回退；开发版含 SSR 诊断，生产版裁掉）：

```ts
export const getActivePinia = __DEV__
  ? (): Pinia | undefined => {
      const pinia = hasInjectionContext() && inject(piniaSymbol)
      if (!pinia && !IS_CLIENT) {
        diagnostics.PINIA_R1004({}, { method: 'error' })
      }
      return pinia || activePinia
    }
  : (): Pinia | undefined =>
      (hasInjectionContext() && inject(piniaSymbol)) || activePinia
```

**③ 安装时同时建立两条路径**（注释点明「组件外取用」动机）：

```ts
install(app: App) {
  // this allows calling useStore() outside of a component setup after
  // installing pinia's plugin
  setActivePinia(pinia)
  pinia._a = app
  app.provide(piniaSymbol, pinia)
```

三段合起来，就是「安装建立双路径 → 取用注入优先回退指针 → 设置函数随时刷新指针」的完整闭环。
