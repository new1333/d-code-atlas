# HMR：保留状态的就地热更新

## 改一行 store，凭啥要我重头来过

调试到一半，你已经把登录态点出来了、表单填了一半、计数器也调到了 `count = 5`。这时你想给 store 里的 `inc` 改个小逻辑，存盘——开发服务器贴心地热更新了页面。结果一刷新，状态全归零：登录没了、表单空了、`count` 回到 0。你只能重新点登录、重新填表、重新调到那个状态。

这不该是热更新（HMR）该干的事。可 store 的热更新偏偏藏着一个坑：如果你图省事，直接拿一个新 store 实例去顶替旧的——

## 换逻辑可以，换对象不行

store 实例是个对象，它的"身份"被到处攥着：组件 setup 里那句 `const user = useUserStore()` 拿到的引用、别的 store 里 `useCartStore().user` 这种跨 store 引用、还有 `store.$subscribe(...)` 注册进来的订阅回调，全都是同一栋房子。

你若直接换掉这个对象（拿新实例顶上去），所有旧引用瞬间指向了那个被抛弃的旧实例——页面看着是更新了，组件里实际还在跑老 store。

打个比方：对象是房子，组件、跨 store、订阅就是住在里面的人和接好的水电管线。你想翻新，不能把人赶出去、把房子拆了重建——那身份就没了，地址作废。只能在原房子里换家具、换管线。人不用搬家，住进去就是焕然一新的家。

Pinia 的选择就是这套"原地翻新"：再请一个**替身演员**进场，让它照着新代码把整个 store 原样演一遍，再把演出来的新家具、新管线逐个搬进老房子。老房子还是那栋老房子，但里面的逻辑已经是新的了。一句话——

> 热更新不换掉正在用的那个对象，而是另起一个替身跑出新代码，再把替身的内容原样搬进旧对象：对象身份不变，运行时状态不丢。

造替身用的那套"装配流程"，第 4 章已经讲透了（它在那儿是拿来造第一个 store 的）。本章只看它的一个新用法——造**第二个、用完即弃的临时产物**。搬运期间要短暂关掉监听，那套"暂停监听再恢复"的批处理套路第 5 章也讲透了，这里只是再用它一次，不重复展开。

## 七步走完一次热更新

把整件事拆成七步，从你按下保存那一刻说起。

**1. 注册回调。** store 文件末尾通常有这么一行：

```js
if (import.meta.hot) {
  import.meta.hot.accept(acceptHMRUpdate(useStore, import.meta.hot))
}
```

你把一个热更新回调挂到了打包器（Vite 之类）的模块热替换接口上。这里的 `acceptHMRUpdate` 不是回调本身，而是一个"回调工厂"——它吞下旧的 `useStore` 和打包器的 `hot` 对象，吐出一个准备好接新模块的回调。

**2. 改动触发。** 你改了 store 源码、存盘。打包器编译新模块，回头调用你注册的那个回调，把全新的模块对象递给它。

**3. 认领并校验。** 回调在模块里找到名为 `useStore` 的导出，确认它是个 store 定义函数；再确认这个 store 已经被实例化过（在 pinia 的注册表里有它）。如果这个 store 从来没人 `useStore()` 过，直接返回——还没本体可热更，等首次使用时自然就拿到新代码。如果新模块里这个 store 的名字（`$id`）跟旧的对不上（你重构改了 store 名），那就没救了，身份都变了，只能让打包器整页刷新。

**4. 进入热更分支。** 回调把既有 store（本体）当成 `useStore` 的第二个参数传进去——`useStore(pinia, existingStore)`。`useStore` 一看"第二参数是个 store"，就明白这是热更新：不再实例化，改走热更分支。

**5. 造替身。** 用新代码装配一个临时 store，它的 id 加上 `__hot:` 前缀。它跑的是和正常 store 一模一样的装配流程，所以 state、action、getter 自动按新代码分好类、装进一份"新版本清单"。唯一不同的是：它的状态被收进一个独立容器（`hotState`），**绝不写回真实状态树**——替身是临时的，不能弄脏本体的状态。

**6. 就地搬运。** 对本体执行搬运，照着替身的清单逐项搬家：

- **状态**：保留旧的运行时值（旧 `count = 5` 不丢）。选项式 store 按新形状逐字段调和，组合式 store 整值迁移。
- **动作**：用新代码重新包一层，绑到本体的订阅集合上。
- **计算属性**：选项式重新包成 computed 并把 `this` 绑到本体，组合式直接搬用。
- **增删**：新加的成员补上、删掉的成员清掉。
- 在状态树整体改指向新容器的那一瞬间，短暂关掉监听（否则这次切换会被订阅当成一次用户操作记下来），下一个 tick 再恢复。

**7. 清理替身。** 把替身从状态树和注册表里删掉，用完即弃。本体的对象身份从头到尾没变，但里面已经是全新逻辑 + 保留下来的旧状态。

一次完整的执行轨迹长这样：

```
输入：你把 inc 从 +1 改成 +2、新增了 triple getter、删掉了 double getter；此刻本体里 count = 5。
   ↓
中间态：替身装配完，清单写着 { state: [count], actions: [inc], getters: [triple] }；
       本体开始搬运——旧值 5 搬进新状态容器；inc 被重包、绑到本体；triple 被新增；double 被删；
       状态树整体改指向新容器，此刻监听短暂关闭，下一个 tick 恢复。
   ↓
输出：本体对象的地址没变，但它现在持有 "inc = +2、有 triple、没 double、count 还是 5"。
       组件里早先 const s = useStore() 拿到的旧引用，啥都不用做，自动看到新行为。
```

## 原理演示：把搬运函数从零写一遍

七步里最核心、也最值得亲手摸一遍的，是第 6 步的"就地搬运"。我们抛开打包器集成、计算属性重包、暂停监听这些周边，只把 `hotUpdate(本体, 替身)` 这个搬运函数从零实现出来。它得同时办成三件事：**状态保留**、**逻辑焕新**、**身份不变**，外加**成员增删**。

```js
// 旧版 store（v1）：inc 每次 +1，带一个 double getter
function makeStore() {
  const s = {
    _state: { count: 0 },
    inc() { s._state.count += 1 },
    get double() { return s._state.count * 2 },
  }
  return s
}

const store = makeStore()
for (let i = 0; i < 5; i++) store.inc()   // 用户已经把状态用到 count = 5
const externalRef = store                  // 模拟"组件里早就拿到的引用"

// 新版 store（v2）：inc 改成 +2、新增 triple、删掉 double
function makeStoreV2() {
  const s = {
    _state: { count: 0 },
    inc() { s._state.count += 2 },
    get triple() { return s._state.count * 3 },
  }
  return s
}

// 就地搬运：本体身份不变，只逐个换成员
function hotUpdate(oldStore, neo) {
  // ① 状态保留：新容器里和旧容器同名的键，用旧值覆盖
  for (const k in neo._state) {
    if (k in oldStore._state) neo._state[k] = oldStore._state[k]
  }
  // ② 逻辑焕新：动作换新版（neo.inc 的闭包绑的是 neo._state）
  oldStore.inc = neo.inc
  // ③ 成员增：在本体上补一个新 getter，读本体自己的状态
  Object.defineProperty(oldStore, 'triple', {
    get() { return oldStore._state.count * 3 },
    configurable: true, enumerable: true,
  })
  // ④ 成员删：清掉已移除的旧成员
  delete oldStore.double
  // ⑤ 状态树整体改指向新容器（此后 oldStore.inc 改的就是新容器）
  oldStore._state = neo._state
}

hotUpdate(store, makeStoreV2())

console.log(externalRef._state.count)  // 5      身份没变，旧状态值保留
externalRef.inc()
console.log(externalRef._state.count)  // 7      新逻辑（+2）已生效
console.log(externalRef.triple)        // 21     新成员就位
console.log('double' in externalRef)   // false  旧成员已清
console.log(externalRef === store)     // true   自始至终同一个对象
```

这段脚本把核心权衡演透了：`hotUpdate` 自始至终没有把 `store` 指向别处，`externalRef === store` 一直是 `true`——身份没动；可它身上跑的已经是 v2 的逻辑、留着 v1 的状态、成员也按新版增删过。说人话就是：**对象不动，动的是对象身上的成员**。真实实现里这个搬运函数会照着替身装配时攒下的"清单"去精确对账 state / action / getter 三个集合，演示版只留下了"就地变异"这一个最关键的思想。

## 关键权衡

### 权衡 1（核心）：就地变异既有对象，而不是替换它

**选择**：不动 store 对象的身份，而是在它身上逐个换成员——动作换新的、getter 重新绑、state 指向改一改、多余的成员删掉。

**换来**：运行时状态不丢（旧的 `count = 5` 被原样搬进新容器）；更关键的是，因为对象身份没变，组件里早就拿到的旧引用、别的 store 对它的引用、已经注册的 `$onAction` / `$subscribe` 订阅，全都继续指向同一个活着的对象，**自动看到新行为**，谁都不用重新 `useStore()`。

**代价**：搬运逻辑必须把"状态 / 动作 / 计算属性"三个集合的增、删、改逐个精确同步。新加的成员要补上、删掉的成员要清掉、改了的要换上——任何一处漏了，本体上就会留下**幽灵成员**（源码里已经没有了，但对象身上还赖着）或**残留旧逻辑**（源码改了，对象上跑的却还是老动作）。这正是为什么替身要老老实实攒一份"清单"：搬运时照清单逐项对账，少一项都会留下不一致。

### 权衡 2：让替身完整跑一遍既有装配，而不是另写一套重建逻辑

**选择**：不为热更新单独写一套"从新源码直接重建 store"的并行逻辑，而是原样复用造 store 的那套装配流程，只是给替身一个带 `__hot:` 前缀的临时 id。

**换来**：零分叉——第 4 章讲的那套"返回值分类"机制（ref/reactive 当 state、function 当 action、computed 留作 getter）原样复用，新版本的"清单"自动生成，搬运时照着清单对账就行，不用担心自己漏认了某个返回值类型。

**代价**：每次热更新都得完整重跑一次 setup（重新包装动作、重建 computed），哪怕你只改了一个字符；而且替身的状态必须**严格隔离**进那个独立容器——替身装配期间它的 `$state` getter 读的是隔离容器、setter 直接抛错（"不能写热状态"），装配结束才被一次性搬走。替身的动作在装配时也故意先不包追踪、留到搬运时才重新包，目的是让新动作的追踪器绑到**本体**而不是替身上——否则热更后动作触发的是随替身一起被删掉的订阅。

### 权衡 3：状态迁移分两路——选项式按新形状调和、组合式整值迁移

**选择**：选项式 store 的 state 形状在定义时就是确定的（`state()` 返回什么就是什么），所以用 `patchObject` 把旧值按新形状逐字段调和；组合式 store 的 state 是命令式创建的（`ref({})` 这种），运行时还可能动态加属性，所以直接把整个旧值原样搬过去（整值迁移）。

**换来**：选项式 store 能优雅处理字段增删——新形状缺的字段自然消失、新加的字段自然出现、共有的字段保留旧值；组合式 store 不会因为调和而丢掉运行时动态加进去的属性（这是一条真实踩过的坑：issue #2611，整值迁移就是为了堵住它）。

**代价**：两条路径要分别维护，迁移语义略有差异。这里还藏着一个容易绊倒人的细节：`patchObject` 的注释写着"会删掉 newState 没有的键"，但它真正实现时只遍历旧 state、对共有键做合并，**并不删除**任何键；真正的"删除被移除字段"是搬运逻辑另外单独做的。注释描述的是热更新的整体组合效果，不是这个函数单看的行为，光看注释很容易被骗。

### 权衡 4：整套机制只活在开发期，生产构建里入口退化为空函数

**选择**：`acceptHMRUpdate` 一开头就是一句 `if (!__DEV__) return () => {}`，把整个函数体直接砍掉。

**换来**：生产构建里热更新逻辑被彻底摇除（tree-shake），零体积、零运行时开销——因为生产环境根本没有模块热替换接口，这套机制从一开始就只为打包器的开发服务器服务。

**代价**：它纯粹是开发期产物，生产环境没有任何对应物。开发时你享受的这套"改一行、状态不丢"的魔法，上线后凭空消失，不能指望它在线上也生效。

## 小结

热更新的本质矛盾是"想换逻辑、又不能换对象"。Pinia 的解法很干脆：请替身演新代码、再就地把内容搬进老对象——身份不变、状态不丢、订阅不断。这套机制的精妙之处全在"就地变异"四个字上，代价则是搬运逻辑要精确同步三个集合的增删改，且整套机制只活在开发期。

这套"就地焕新"还会和外部观测层打交道：状态树的大切换、动作的重新包装，都需要被开发工具正确感知、又不能被误记成用户操作。下一章《DevTools 集成：作为 Pinia 插件的可观测层》会展开这部分——而热更新期间的那些"短暂关闭监听"的小动作，正是为了和那套观测层和平共处。
