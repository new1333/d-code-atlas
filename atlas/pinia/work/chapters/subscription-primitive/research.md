# 订阅原语：回调集合与作用域自动清理 · 源码精读

## 给 Writer 的教学钩子（必填，8 子项缺一不可）
- **用户痛点 / 场景**：在组件里订阅一个 store 的状态变化或动作调用，组件卸载时若忘记手动取消订阅，回调会泄漏——轻则继续被触发、重则操作已销毁的 store 报错。没有统一原语时，「状态订阅」和「动作订阅」要各写一套注册 / 取消 / 清理逻辑，重复且极易在作用域生命周期面前出错。
- **一句话核心思想**：订阅就是把回调塞进一个集合并返回一个取消函数；默认把它跟当前作用域绑死、随作用域自动回收，想跨作用域长存就显式脱离。
- **设计动机（为什么需要它）**：状态订阅与动作订阅这两类**完全不同**的订阅，共用同一副「往集合加回调 → 广播参数 → 清理」的骨架。把这副骨架抽成一个最小原语，换来的能力是：任何新订阅类型只要能写成「加回调 + 广播」，就自动获得「作用域安全清理」这一契约，无需各自重造。本章是全书地基章，**无前置依赖**；它供应的这副骨架，会在后续「动作订阅」「状态订阅」相关章节被直接装配——那些章只看「在骨架之上搭了什么（动作包裹器、深度监听协调）」，**不重讲骨架本身**（骨架已在本次讲透，Writer 写后续章时复用即可）。
- **关键权衡（本 Atlas 的核心）**：
  1. **默认绑作用域、显式脱离出逃**：选择「默认把每次订阅挂到当前作用域的销毁钩子上」→ 换来「组件 / store 卸载即自动回收订阅，零样板、无泄漏」→ 代价是「想跨作用域（全局、模块级）长期订阅，必须显式传一个『脱离』标记，否则当前作用域一结束订阅就随之消失」。
  2. **自动清理与手动取消并存**：选择「既挂销毁钩子、又把取消函数返回给调用方」→ 换来「声明式（靠作用域）与命令式（手动调返回值）两种清理方式按场景任选」→ 代价是「同一个取消闭包被两个持有者引用（作用域 + 调用方），需靠集合删除的幂等性兜底，确保重复清理不产生重复副作用」。
  3. **附带清理以「真删成功」为闸门**：选择「只有当回调确实从集合移除时，才执行附带清理（如停掉对应的监听器）」→ 换来「重复调用取消函数不会重复停监听器、不会重复释放」→ 代价是「附带清理的语义被绑死在『从集合移除』这一刻，调用方需理解此契约」。
  4. **触发即原位广播、不快照**：选择「触发时直接遍历集合、不在触发前拷贝」→ 换来「零分配、最快路径」→ 代价是「回调内部若同步增删集合，迭代行为依赖语言规范（已删未访问的会被跳过、新增未访问的会被跑到），属边界情形」。
- **最小心智模型（3～7 步）**：
  1. 每个持有人各自备一个「回调集合」（一个 store 通常持两个：状态集合 + 动作集合）。
  2. 订阅：把回调加进集合，造一个「取消闭包」。
  3. 若未声明脱离、且当前正处在某个作用域内：把取消闭包登记到该作用域的销毁钩子。
  4. 把取消闭包同时返回给调用方（手动取消入口）。
  5. 触发：遍历集合，把同一批参数广播给每个回调。
  6. 清理（任一路径触发）：取消闭包从集合删回调；只有真删成功才跑附带清理。
  7. 幂等：重复清理安全，附带副作用只发生一次。
- **最小原理演示（替代旧"复刻范围"）**：
  - **应演示**：一个几十行的从零实现，演透权衡 1（默认绑作用域自动回收 vs 显式脱离长存）与权衡 3（附带清理受删成功闸门保护）。关键是造一组**对照执行轨迹**：同一段订阅代码，默认形态下「作用域结束 → 订阅自动消失、附带清理被触发」；显式脱离形态下「作用域结束 → 订阅仍存活、附带清理不触发，需手动取消」。再补一个「对同一订阅连调两次取消函数，附带清理只跑一次」的小验证。
  - **应故意省略**：泛型与参数类型推导、动作包裹器（before/after/onError、Promise 感知）、状态订阅的深度监听与监听协调开关、补丁期暂停、重复订阅去重告警、HMR 分支——这些都不属于「订阅原语」本身，是建在原语之上的能力。
  - **演示载体建议**：本仓库主语言为 TS，且机制灵魂正是「借宿主的作用域模型实现自动清理」，故建议写成**依赖 Vue 作用域原语（`effectScope` + `onScopeDispose`）的可运行脚本**（`bun run`/`node` + vue 依赖均可跑），让读者亲眼看到「作用域 stop → 订阅自动回收」。若读者环境不便装 Vue，可退化成「自手搓一个最小作用域栈 + dispose 钩子」模拟，但会在「为什么必须借宿主作用域而非自己管生命周期」这一层失真——故首选真 Vue 作用域。一句话原则：载体服务于演透原理，这里原理正包含「借宿主作用域」，故不宜替换。
- **正文不宜展开的细节**：泛型约束与回调参数沿 `Parameters` 自动对齐（纯编译期，无运行时影响）；用 `bind` 预填集合生成「动作订阅」公开方法的柯里化手法；状态订阅里整套「深度监听 + 监听协调开关 + 补丁期暂停」；同回调重复订阅的去重保护与 dev 告警；空函数占位符在「无重置能力」等无关场景的复用。
- **推荐的一个执行轨迹例子**：输入——在组件 setup 内对某 store 做一次**默认**状态订阅。中间态——回调入集合 → 造取消闭包 → 因当前在组件作用域且未声明脱离 → 登记到作用域销毁钩子 → 返回取消闭包。触发——一次状态补丁在内部广播 → 集合内回调被调用、收到变更描述与新状态。卸载——组件作用域销毁 → 销毁钩子触发取消闭包 → 回调从集合移除 → 附带清理（停掉深度监听器）执行。输出——订阅随组件自动消失，集合与监听器均无残留。

## 概念要点
- 要点 1：整文件仅导出 3 个东西——一个空函数占位符（默认附带清理、多处兜底用）、一个注册函数、一个触发函数；外加从 Vue 引入「取当前作用域」「登记销毁钩子」两个原语。源码位置: packages/pinia/src/subscriptions.ts:1-4,6,26
- 要点 2：注册函数把回调加进**外部传入**的集合（不自带集合），造取消闭包，按「是否脱离 + 是否在作用域内」决定是否挂销毁钩子，最后返回闭包——集合由调用方持有，原语本身无状态。源码位置: packages/pinia/src/subscriptions.ts:12-23
- 要点 3：挂销毁钩子的条件是 `!detached && getCurrentScope()`——脱离标记与「当前有无作用域」同时成立才不挂；模块顶层等无作用域场景下，即便不传脱离标记也不会挂，只能靠返回值手动清。源码位置: packages/pinia/src/subscriptions.ts:19
- 要点 4：取消闭包先 `delete` 回调，**删成功才**调附带清理；删失败（已被清过）则什么都不做——这是幂等性与「不重复副作用」的关键。源码位置: packages/pinia/src/subscriptions.ts:14-17
- 要点 5：触发函数用 `forEach` 原位遍历，**不在触发前拷贝集合**；回调参数类型靠泛型 + `Parameters<T>` 对齐回调签名，编译期保证、无运行时校验。源码位置: packages/pinia/src/subscriptions.ts:26-33
- 要点 6：两函数的泛型约束 `_Method` 极宽松（任意参、任意返），类型安全完全在编译期；触发时直接 spread，运行期对参数个数 / 类型不设防。源码位置: packages/pinia/src/types.ts:414
- 要点 7：两类消费者各取所需——**动作订阅**用 `bind` 预填回调集合后暴露成 store 方法（调用方拿到的是 `(callback, detached?, onCleanup?)` 形态，默认走非脱离）；**状态订阅**手动调注册函数，把「停掉监听器」作为附带清理传入，并按 `options.detached` 透传脱离标记。源码位置: packages/pinia/src/store.ts:435,448-453
- 要点 8：状态订阅额外做「同回调重复订阅」去重——集合已有该回调时直接返回空函数占位符（dev 下告警），既防重复又复用了本文件的空函数。源码位置: packages/pinia/src/store.ts:441-446
- 要点 9：动作订阅的触发发生在 action 包裹器内，每次动作被调时广播 `{ args, name, store, after, onError }` 给全体订阅者；after/onError 又是两个**临时新建的小集合**，分别承载成功 / 失败回调，由包裹器在动作结束后自行触发。源码位置: packages/pinia/src/store.ts:372-373,382-388,402,406,412
- 要点 10：状态订阅的触发有**两条路**——补丁路径在 `$patch` 内手动广播（因补丁期间暂停了深度监听，需手动补这一刀）；直接改 state 路径则由一个深度 watch 在变更时直接调回调（不经触发函数）。源码位置: packages/pinia/src/store.ts:323-327,454-471
- 要点 11：store 销毁时直接 `clear()` 两个集合，与作用域自动清理形成双保险——即便某条订阅是脱离的，store 整体销毁时也会被清空。源码位置: packages/pinia/src/store.ts:349-353

## 关键调用链
- 注册侧（动作订阅）：外部调 store 的动作订阅方法 →（经 `bind` 预填集合）→ 注册函数(集合, 回调, 脱离?, 附带清理?) → 集合.add + 登记销毁钩子 → 返回取消闭包。源码位置: packages/pinia/src/store.ts:435 → packages/pinia/src/subscriptions.ts:6-24
- 注册侧（状态订阅）：外部调 store 的状态订阅方法 → 去重预检 → 手动调注册函数(集合, 回调, options.detached, () => 停监听器) → 同上 → 另起一个深度 watch 监听根 state。源码位置: packages/pinia/src/store.ts:441-471 → packages/pinia/src/subscriptions.ts:6-24
- 触发侧（动作）：action 包裹器每次被调 → 触发函数(动作集合, 事件对象) → forEach 广播 → 各订阅者的 after/onError 由包裹器在动作结束后触发临时小集合。源码位置: packages/pinia/src/store.ts:382 → packages/pinia/src/subscriptions.ts:26-33
- 触发侧（状态·补丁）：$patch 改完 state → 触发函数(状态集合, 变更描述, 新状态) → forEach 广播。源码位置: packages/pinia/src/store.ts:323-327 → packages/pinia/src/subscriptions.ts:26-33
- 清理侧：作用域销毁 → 销毁钩子 → 取消闭包 → 集合.delete(回调) → 成功则 onCleanup()；或调用方手动调返回的取消闭包，走同一路径。源码位置: packages/pinia/src/subscriptions.ts:14-23

## 源码摘录（带行号，全文累计 ≤ 30 行）
```ts
// packages/pinia/src/subscriptions.ts:6-33（注册 + 触发两个核心原语；空函数占位符 noop 见 L4）
export function addSubscription<T extends _Method>(
  subscriptions: Set<T>,
  callback: T,
  detached?: boolean,
  onCleanup: () => void = noop
) {
  subscriptions.add(callback)

  const removeSubscription = () => {
    const isDel = subscriptions.delete(callback)
    isDel && onCleanup()
  }

  if (!detached && getCurrentScope()) {
    onScopeDispose(removeSubscription)
  }

  return removeSubscription
}

export function triggerSubscriptions<T extends _Method>(
  subscriptions: Set<T>,
  ...args: Parameters<T>
) {
  subscriptions.forEach((callback) => {
    callback(...args)
  })
}
```

## 易混淆 / 边界 / 推断
- 事实：取消闭包有两条持有路径——作用域销毁钩子（自动）+ 调用方返回值（手动）；靠 `Set.delete` 幂等 + `isDel && onCleanup` 闸门，保证重复清理只触发一次附带清理。源码位置: packages/pinia/src/subscriptions.ts:14-23
- 事实：触发函数**不拷贝快照**、原位 forEach。若回调在触发期间同步增删集合，迭代行为依语言规范——已被删且尚未访问的元素会被跳过，迭代期间新增的元素也会被访问到。实际订阅回调极少在触发时变异集合，属边界情形。源码位置: packages/pinia/src/subscriptions.ts:30-32
- 事实：脱离标记 + 当前作用域**共同**决定是否自动清理——`getCurrentScope()` 为空（全局脚本顶层、或非 setup 上下文）时，即便不传脱离标记也不会挂销毁钩子；脱离的订阅则无论是否有作用域都不挂。两种情形下订阅都只能靠返回值手动清，或等 store 整体销毁时 clear。源码位置: packages/pinia/src/subscriptions.ts:19
- 事实：用 `Set` 而非数组，同引用 `add` 两次只存一份，配合状态订阅的 `has` 预检能廉价防重复订阅；代价是无序、无索引，但订阅本不需要顺序。源码位置: packages/pinia/src/subscriptions.ts:7,12 + packages/pinia/src/store.ts:441
- 推断（标注为推断）：泛型 `_Method` 极宽（`(...args:any[])=>any`）且触发时直接 spread 无校验，故类型安全完全依赖 TS 编译期，运行期对参数个数 / 类型不设防——这是「原语尽量薄」的有意取舍，把校验责任留给类型系统与调用方。依据：types.ts:414 定义 + subscriptions.ts:30-32 无校验直跑。
- 推断（标注为推断）：原语不自带集合、自身无状态，是「让调用方持有集合、原语只提供 add/trigger/remove 行为」的显式设计——这让同一个原语能同时服务「每 store 两个集合」乃至动作包裹器里「每次调用两个临时集合」，复用面最大化。依据：subscriptions.ts:6-7 集合由参数传入 + store.ts:372-373 在包裹器内临时 new 集合。
- 未理解：无重大未理解点；本文件仅 33 行、逻辑直白，全部行为已被源码字面与调用方交叉印证。
