# 订阅原语：回调集合与作用域自动清理

> 本章属于 primitive 层，是全书地基章之一。前置：上一章的「Pinia 实例」立起了容器（根状态盒子、注册表、一根脱离组件树的作用域）。
> 学完你能：用一句话讲清为什么 Pinia 把「状态订阅」和「动作订阅」这两类看似不同的东西，统一成同一副「回调集合 + 取消函数 + 作用域自动清理」的骨架，以及这副骨架做了哪些关键取舍。

## 1. 为什么需要它

上一章把容器立起来了：根状态盒子、注册表、一根脱离组件树的作用域。容器只是装东西的壳，本章往里头看一个甚至比单个 store 还要底层的小块——「订阅」本身。

写 Vue 应用时，你大概率在组件里写过 `store.$subscribe((mutation, state) => {...})` 监听状态变化，或 `store.$onAction(({ after, onError }) => {...})` 观察 action 调用。这两件事听起来八竿子打不着：一个是状态变了被通知，一个是函数被调了被通知。可它们骨子里干的是同一件事——你递给 store 一个回调，store 在某个时机把它叫起来。

问题就在「回调」这两个字上。回调本身是一个引用，谁拿着它谁就得负责还回去。在组件里订阅一个 store，组件卸载了忘取消订阅——回调会继续被触发，更糟的是它可能去操作一个已经销毁的 store。每一次泄漏都是「我加进去了，但没人帮我拿出来」。

如果「状态订阅」和「动作订阅」各自写一套注册、触发、清理逻辑，每个新订阅类型都得重造一遍轮子，更糟的是每个都得各自处理「随作用域回收」这件最易出错的事。Pinia 的做法是把这套骨架抽成一个最小原语——任何只要能写成「加回调 + 广播参数」的订阅，都自动获得「作用域安全清理」的契约。本章就是讲这副骨架。

## 2. 核心思想

订阅就是把回调塞进一个集合、并返回一个取消函数；默认把这个取消函数挂到当前作用域的销毁钩子上，想跨作用域长存就显式说一声「我脱离」。

这层原理的重点不在「集合」也不在「回调」，而在「把取消函数挂到作用域销毁钩子」这一下借力——订阅的生命周期从此不必由调用方记得管，而是顺着宿主的作用域模型自然收回。

## 3. 心智模型

这个原语本身没有状态，连「集合」都不是自己的。它只提供两个函数，外加调用方各自备的一个 `Set<回调>`：

- **持有人各自备集合**：一个 store 通常持两个集合——一个状态订阅集合、一个动作订阅集合。原语只负责往里加、往里触发、往里删。
- **注册（`addSubscription`）**：把回调塞进集合；造一个取消闭包；若不脱离且当前正处在某个作用域内，把这个闭包登记到该作用域的销毁钩子上；最后把闭包返回给调用方。
- **触发（`triggerSubscriptions`）**：遍历集合，把同一批参数广播给每个回调。
- **取消闭包**：从集合里 `delete` 这个回调；只有真删成功，才调一次附带清理函数（比如停掉对应的 watcher）。

数据流就一条线：

```
订阅：回调 → 集合.add → 造取消闭包 →（视情况）挂作用域销毁钩子 → 返回闭包
触发：参数 → 集合.forEach → 每个回调(...参数)
清理：取消闭包（任一来源触发）→ 集合.delete → 删成功才 onCleanup
```

为什么用 `Set` 而不是数组？因为同引用 `add` 两次只存一份（廉价防重复订阅），`delete` 是幂等的（删第二次返回 `false`），这两个特性正好对上原语需要的契约；订阅本就不需要顺序，无序无索引的代价可以忽略。

## 4. 关键权衡

### 默认绑作用域，显式脱离出逃

注册函数拿到回调后做的第一件要紧事，是看一眼「现在有没有作用域」和「调用方有没有声明脱离」。两个条件同时满足——`!detached && getCurrentScope()`——就把取消闭包塞给 `onScopeDispose`。

换来的是「组件 / store 卸载即自动回收订阅，零样板、无泄漏」：你在组件 setup 里写一行 `$subscribe(...)`，组件卸载时 Vue 自动触发该作用域的销毁钩子，钩子里跑取消闭包，回调从集合里消失。整条链路你完全不用管。这条契约太重要了，它把「我忘了取消订阅」这种最常见的人为泄漏彻底堵死。

代价是「想跨作用域长期订阅，必须显式传一个『脱离』标记」。比如在路由守卫、模块顶层、或某个全局单例里订阅一个 store、又希望这个订阅活一整个应用周期，你得明确说 `detached: true`，否则当前作用域（很可能是某个临时作用域）一结束订阅就跟着没了。本质矛盾是「随组件生命周期自动回收」与「跨作用域长存」这两个对立需求在打架——任何「自动资源管理」系统都得选个默认值，Pinia 选了更安全的「默认回收」，把跨作用域长存留作需要明示的逃生口。这条本质矛盾在 React 的 `useEffect` cleanup、任何带生命周期的资源管理里都看得见，只是这里把「默认绑当前作用域」做成了开关。

### 自动清理与手动取消并存

取消闭包不只有「作用域销毁钩子」一个持有者。注册函数同时把它 `return` 给调用方，调用方随时可以手动调它来提前取消。

换来的是「声明式（靠作用域）与命令式（调返回值）两种清理方式按场景任选」。组件里靠作用域自动清就够了，路由守卫里拿到的返回值则在切换时手动调一下更直接。

代价是同一个取消闭包被两个持有者引用，二者可能在生命周期里先后都被触发——组件卸载跑了一次，调用方又手动调一次。这就要求清理必须是幂等的：跑两次只产生一次副作用。这个保证来自下面那条权衡。

### 附带清理以「真删成功」为闸门

取消闭包里只有两行：先 `delete` 回调，**删成功才**调附带清理（比如 `$subscribe` 里的「停掉那个深度 watcher」）。`Set.delete` 在回调还在时返回 `true`、已被删过时返回 `false`，这个布尔值天然就是一道闸门。

换来「重复调取消函数不会重复停监听器、不会重复释放资源」。配合上面那条权衡的双持有者，整条机制稳稳地满足「同一订阅最多被清理一次」的契约。

代价是附带清理的语义被绑死在「回调刚从集合移除」这一刻，调用方需理解这个契约：你不能假设「每次调取消函数都会触发 onCleanup」，它只在「真删成功」那一刻跑。这条代价很薄：现实里调用方从不在意 onCleanup 跑了几次，只在意「订阅最终被清干净」。

化解本质矛盾的是「双持有者要安全」与「副作用要可重复触发」之间的对立——这里选了前者：把幂等性放进原语本身，让任何调用方都自动获得「重复清理只生效一次」的保证，而不必每个调用方各自实现幂等。

### 触发即原位广播，不快照

`triggerSubscriptions` 只有一行：`subscriptions.forEach(cb => cb(...args))`。它不复制集合、不缓存参数。

换来「零分配、最快路径」。订阅广播是热路径——一个繁忙应用的 action 一秒可能被调上百次，每次都拷贝一份集合、构造一个 args 数组是无谓开销。

代价是回调内部若同步增删集合，迭代行为依赖 JavaScript 语言规范（已删未访问的会被跳过、新增未访问的会被跑到），属边界情形。订阅回调极少在触发期间变异集合——它们只是「观察者」，应当只读不写。这条权衡量级很小，权衡本身只在边角情形上有代价，但「广播时不复制」是高频路径上最朴素的选择。

## 5. 最小原理演示

下面这段几十行的脚本演透核心思想：一个回调集合、一个取消闭包、作用域自动清理、显式脱离、幂等的附带清理。**直接依赖 Vue 的 `effectScope` 与 `onScopeDispose`**——这正是本章原理的内核：订阅机制不自己管生命周期，而是**借宿主 Vue 的作用域模型**来完成自动回收。

```ts
import { effectScope, onScopeDispose } from 'vue'

// 注册原语：往外部传入的集合加回调，造取消闭包，视情况挂作用域销毁钩子
function addSubscription(subs, callback, detached = false, onCleanup = () => {}) {
  subs.add(callback)

  const remove = () => {
    // 删成功才跑附带清理——幂等性的闸门
    const deleted = subs.delete(callback)
    if (deleted) onCleanup()
  }

  // 默认绑当前作用域；显式脱离、或当前不在任何作用域内，则不绑
  if (!detached && currentScopeExists()) {
    onScopeDispose(remove)
  }

  return remove
}

// 触发原语：原位 forEach，不快照
function triggerSubscriptions(subs, ...args) {
  subs.forEach((cb) => cb(...args))
}

// 演示对照：默认订阅随作用域自动回收；脱离订阅需手动清
const scope = effectScope()   // 造一个父作用域，用来模拟「组件 setup 作用域」
scope.run(() => {
  const subs = new Set()

  // 默认形态：绑当前作用域
  const remove1 = addSubscription(
    subs,
    (msg) => console.log('[默认订阅] 收到:', msg),
    false,
    () => console.log('[默认订阅] 附带清理触发（停监听器等）')
  )

  // 脱离形态：不绑作用域，得自己管
  const remove2 = addSubscription(
    subs,
    (msg) => console.log('[脱离订阅] 收到:', msg),
    true,                     // 显式脱离
    () => console.log('[脱离订阅] 附带清理触发')
  )

  triggerSubscriptions(subs, 'hi')
  // → [默认订阅] 收到: hi
  // → [脱离订阅] 收到: hi

  // 演示幂等：连调两次取消，附带清理只跑一次
  remove1()
  remove1()
  // → [默认订阅] 附带清理触发（停监听器等）   ← 只跑一次
  console.log('[取消后集合大小]', subs.size)   // → 1（只剩脱离那个）

  // 父作用域结束时：默认订阅已被手动清，集合里只剩脱离那个；脱离订阅仍存活
})

// 父作用域 stop：默认订阅即使没被手动调，也会被 onScopeDispose 拉走
// —— 但这里它在 scope.run 内已经被手动清掉了，所以 onScopeDispose 时集合里已没它
scope.stop()

function currentScopeExists() {
  // 真源里是 getCurrentScope()；这里简化成「恒为 true」便于演示
  return true
}
```

每行都对应上面讲过的原理点：`subs.add` 落实「回调集合」、`deleted && onCleanup` 落实幂等闸门、`!detached && onScopeDispose` 落实「默认绑作用域」、`triggerSubscriptions` 的 `forEach` 落实「原位广播不快照」、对照演示把「默认绑 vs 显式脱离」直接演给读者看。

## 6. 执行轨迹

拿一次真实场景走一遍。假设你在某个组件 setup 里写了一行 `store.$subscribe(callback)`——本章只看「订阅原语」这一层，先不管 `$subscribe` 内部如何另起深度 watcher（那是后续章节的事）。

**订阅时刻**：`addSubscription(subscriptions, callback, false, stopWatcher)` 被调。
- 第一步：`subscriptions.add(callback)`——集合里多了一个回调引用。
- 第二步：造取消闭包 `remove`，它内部记着「删 callback + 删成功才 stopWatcher」。
- 第三步：判断 `!detached && getCurrentScope()`——你在组件 setup 里，作用域存在，`detached` 默认 false，条件成立，调 `onScopeDispose(remove)`。Vue 把 `remove` 登记到当前作用域的销毁回调列表里。
- 第四步：把 `remove` 返回给 `$subscribe` 的调用方（你组件 setup 里可以接住它，也可以不接）。

此时集合里有一个回调，作用域销毁钩子上有一份 `remove`，调用方手里有一份 `remove`——同一个闭包被两处持有。

**触发时刻**：用户某次改了 state（走 `$patch` 路径），`triggerSubscriptions(subscriptions, mutation, newState)` 被调。`forEach` 遍历集合，把 `mutation` 和 `newState` 广播给回调。回调里你拿到变更描述与最新状态，做你自己的事。

**卸载时刻**：组件卸载，Vue 触发该作用域的销毁钩子，依次跑 `onScopeDispose` 登记过的回调。轮到 `remove`：先 `subscriptions.delete(callback)` 返回 `true`（回调确实在集合里），再 `stopWatcher()` 停掉那个深度监听。集合恢复空、监听器释放、回调引用断开。

**幂等兜底**：假设你组件 setup 里既接住了 `remove`，又在 `onUnmounted` 里手动调了一次。Vue 卸载时作用域钩子也会调 `remove`——但第二次 `subscriptions.delete(callback)` 返回 `false`，`stopWatcher` 不会重复跑。整条清理只产生一次副作用。

## 7. 教学简化说明

本章演示故意省略了：泛型与 `Parameters<T>` 的编译期类型对齐（运行时无开销）、`bind` 预填集合生成 `$onAction` 这类公开方法的柯里化手法、状态订阅里的「同回调重复订阅」去重告警、动作包裹器内部临时新建的 after/onError 小集合。这些都不属于「订阅原语」本身——原语就两个函数、一个集合、一个取消闭包；剩下的全是建在原语之上的能力，会在后续 `$onAction` / `$subscribe` 专门章展开。

## 8. 小结

Pinia 把「状态订阅」和「动作订阅」两类看似不同的事，统收进同一副骨架：一个由调用方持有的回调集合、一对 add/trigger 函数、一个默认挂作用域的取消闭包。这副骨架自己没状态，所以能同时服务每 store 两个长期集合、以及 action 包裹器里每次调用临时新建的小集合。最关键的一笔是「默认把取消函数借给 Vue 作用域的销毁钩子」——订阅的生命周期从此不必由调用方记得管，而顺着宿主作用域模型自然收回。

下一章会讲 `defineStore`：那才是真正「造 store」的入口——但你会发现它本身也不立即造，而是返回一个 `useStore` 闭包，把创建推迟到首次调用。订阅原语先讲透，正是因为 `useStore` 装配出来的那个 store 对象上，`$subscribe` 与 `$onAction` 的契约都长在本章这副骨架上。
