# 订阅原语：回调集合与作用域自动清理

你大概写过这样的组件：在 `setup` 里 `store.$subscribe(...)` 监听了一段状态，组件卸载之后就把这事忘干净了。结果线上偶发报错——用户反复进出这个页面，每进一次就多挂一个监听，旧的回调还活着、还在被触发，最后去操作一个早该销毁的 store，炸了。

「订阅了就忘了取消」是状态库最经典的内存泄漏。Pinia 想一次性解决它，而且不只是给状态订阅解决，连「动作订阅」也一起解决。有意思的是，这两类**完全不同**的订阅——一个监听状态变化，一个监听动作调用——背后共用同一套短到离谱的机制。这章就看它怎么用核心只有两个函数的代码，把「订阅 + 自动清理」这件麻烦事做干净。

## 先看这副骨架能抽到多薄

把「订阅」拆到最底下，其实就三个动作：把回调塞进一个地方存着；要通知的时候，挨个把回调叫醒；不想要了，把它从那个地方拿掉。

Pinia 存回调的地方，就是一个最普通的 `Set`。下面是从零写的最小版本，对照着看就行：

```ts
const noop = () => {}

// 集合不是它自己的——谁传进来，谁拥有。
function addSubscription(subscriptions, callback, detached, onCleanup = noop) {
  subscriptions.add(callback)

  const removeSubscription = () => {
    const removed = subscriptions.delete(callback)
    removed && onCleanup()        // 只有真删成功，附带清理才跑
  }

  // 没声明脱离、且当前正处在某个作用域里 → 把取消挂到作用域的销毁清单上
  if (!detached && getCurrentScope()) {
    onScopeDispose(removeSubscription)
  }

  return removeSubscription
}

// 触发：当场遍历集合，把同一批参数广播给每个回调
function triggerSubscriptions(subscriptions, ...args) {
  subscriptions.forEach((cb) => cb(...args))
}
```

就这么点。说人话就是：**订阅 = 往集合里加一个回调，顺手给你一张「取消单据」；触发 = 对着集合喊一嗓子**。`onCleanup` 是个可选的附带清理（比如「停掉那个深度监听器」），默认给一个什么都不做的空函数。

注意一个设计细节：集合是外部传进来的，这个函数自己不持有任何状态。这一点很关键——后面你会看到，正因为「集合归调用方、行为归函数」，同一个函数既能服务状态订阅的集合，也能服务动作订阅的集合，复用面做到最大。

到这里机制本身已经讲完了。真正让这段代码值钱、也是这章要啃的重点，全在那个 `if (!detached && getCurrentScope())` 里。

## 让订阅「寄居」在作用域上

回到开头那个泄漏场景。问题根源是：组件知道自己的生死（setup 开始、卸载结束），但订阅不知道——它被创建出来之后，就跟组件断了联系，没人会在组件卸载时顺手把它带走。

Pinia 的解法很巧：**不去自己管订阅的生死，而是借 Vue 已有的「作用域」机制**。

打个比方。Vue 的 `effectScope` 像是一个「租期盒子」：组件 `setup` 时打开一个盒子，组件卸载时整个盒子被丢掉，盒子里登记的每件事（响应式 effect、watch、还有这里说的订阅清理）都会被自动办掉。`onScopeDispose` 就是往这个盒子的「销毁清单」上记一笔。

所以默认情况下，订阅一被创建，`addSubscription` 就检查「我现在是不是正待在某个作用域里？」如果是，就把取消单据抄一份登记到那个作用域的销毁清单上。等作用域销毁（也就是组件卸载），订阅自动跟着消失，零样板、不用你写一行清理代码。

跑一段看看（用 Vue 的 `effectScope` 当宿主，`bun run` / `node` 都能跑）：

```ts
import { effectScope, getCurrentScope, onScopeDispose } from 'vue'

const log = []
const push = (...a) => log.push(a.join(' '))

// ── 场景 A：默认形态，订阅「寄居」在作用域上 ──
const setA = new Set()
const scopeA = effectScope(true)                 // 模拟一个组件的 setup 作用域
scopeA.run(() => {
  addSubscription(
    setA,
    () => push('回调收到一次变更'),
    false,                                       // detached = false：默认绑作用域
    () => push('附带清理：停掉深度监听器')
  )
})
triggerSubscriptions(setA)
push('卸载前集合大小', setA.size)

scopeA.stop()                                    // ← 组件卸载，作用域销毁

push('卸载后集合大小', setA.size)
console.log(log.join('\n'))
```

预期输出：

```
回调收到一次变更
卸载前集合大小 1
附带清理：停掉深度监听器        ← 作用域一 stop，销毁清单自动执行，附带清理跟着跑
卸载后集合大小 0               ← 订阅被自动带走，集合干干净净
```

你看，从头到尾没人手动调过取消函数，订阅就是自己消失了。这就是「寄居」的威力。

> **这条权衡**：选择「默认把每次订阅挂到当前作用域的销毁钩子上」→ 换来「组件 / store 卸载即自动回收订阅，零样板、无泄漏」→ 代价是「想跨作用域长期存活（比如全局、模块级的订阅），不能靠默认行为，得显式开口要这个特权，否则当前作用域一结束订阅就没了」。

## 想活过这个作用域？显式说一声

上条的「代价」是真实存在的。有些订阅就不该跟某个组件绑死——比如你想在应用层面一直监听某个 store，组件来了又走，订阅得一直活着。这时候把 `detached` 传成 `true`，`addSubscription` 就跳过「登记到作用域」那一步，订阅成了「脱离」的野孩子，作用域销毁也不碰它。

把场景 A 的代码原样照抄，只把 `detached` 改成 `true`，对照着看：

```ts
// ── 场景 B：显式脱离，订阅活过作用域 ──
const setB = new Set()
const scopeB = effectScope(true)
let stopB
scopeB.run(() => {
  stopB = addSubscription(
    setB,
    () => push('回调收到变更'),
    true,                                         // ← 唯一改动：detached = true
    () => push('附带清理：停掉深度监听器')
  )
})

scopeB.stop()                                     // 作用域结束
push('作用域结束后集合大小', setB.size)            // => 1，订阅还活着！
triggerSubscriptions(setB)                        // 仍在广播
push('手动取消前', setB.size)

stopB()                                           // 必须自己动手取消
push('手动取消后', setB.size)
console.log(log.join('\n'))
```

预期输出：

```
作用域结束后集合大小 1
回调收到变更
手动取消前 1
附带清理：停掉深度监听器        ← 脱离的订阅，附带清理只在手动取消时才跑
手动取消后 0
```

两组执行轨迹摆在一起，差别一目了然：默认形态靠作用域自动收尾，脱离形态必须你自己收尾。同一个函数、同一个参数位，把「跟组件同生共死」和「独立长存」两种语义都给了你。

补充一个容易被忽略的点：挂销毁钩子的条件是 `!detached && getCurrentScope()`——脱离标记和「当前有没有作用域」**共同**决定。如果你在模块顶层、或者任何非 setup 上下文里调（这时 `getCurrentScope()` 是空的），就算不传 `detached`，也不会挂上钩子。这种场景下订阅同样只能靠返回值手动清。

> **这条权衡的另一半**：用 `detached` 这一个布尔位，把「自动清理」从强制契约降级成可选项 → 换来「声明式（靠作用域）和命令式（手动调返回值）两种清理方式按场景任选」→ 代价是「调用方得明白默认会绑作用域，跨作用域的订阅必须显式声明脱离，否则会遭遇『作用域一结束订阅莫名消失』的困惑」。

## 一张取消单据，为什么有两个主人

到现在你应该发现一件事：取消函数 `removeSubscription` 被**返回给了调用方**，**同时**（在默认形态下）也被**登记进了作用域的销毁清单**。也就是说，同一个取消闭包，被两个持有者攥着。

这就引出一个现实问题：组件卸载时作用域会调它一次，如果你代码里也手动调过一次，那岂不是会取消两次？取消两次会不会把附带清理（停监听器、释放资源）也跑两遍？

Pinia 用两行代码把这个坑堵死了。再看一眼取消闭包：

```ts
const removeSubscription = () => {
  const removed = subscriptions.delete(callback)   // Set.delete：删掉了返回 true，本来就没有返回 false
  removed && onCleanup()                           // 只有真删成功，才跑附带清理
}
```

`Set.delete` 的语义是「真删掉了才返回 true，本来就不在集合里就返回 false」。所以第一次调用，`delete` 成功，附带清理跑；第二次调用，回调早就没了，`delete` 返回 false，附带清理被闸门挡住，什么都不做。**幂等性是白送的**，重复清理绝对安全。

跑个最小验证：

```ts
// ── 场景 C：同一份取消闭包被两条路径各调一次，附带清理只跑一次 ──
const setC = new Set()
const scopeC = effectScope(true)
let stopC
scopeC.run(() => {
  stopC = addSubscription(
    setC, () => {}, false,
    () => push('附带清理执行了一次')
  )
})

stopC()            // 路径一：调用方手动取消
scopeC.stop()      // 路径二：作用域销毁，又调同一份闭包
console.log(log.join('\n'))
```

预期输出只有一行：

```
附带清理执行了一次
```

尽管被两个主人各按了一次，附带副作用只发生一次。

> **这条权衡**：选择「既挂销毁钩子、又把取消函数返回给调用方」→ 换来「自动与手动两种清理路径可以并存、谁先触发都行」→ 代价是「同一个取消闭包被两个持有者引用，必须靠 `delete` 的幂等 + `removed && onCleanup` 这个闸门兜底，把契约定死在『从集合真正移除的那一刻才执行附带清理』」。这个契约调用方得理解：附带清理不是「调取消就跑」，而是「回调被真正拿掉才跑」。

## 触发就是当场喊一嗓子，不点名册

最后看触发侧。`triggerSubscriptions` 的实现就一句 `forEach`，没有任何花活。但这里藏着一个刻意的取舍：**它在触发前不拷贝集合**。

很多广播实现会先 `Array.from(set)` 拍一张快照再遍历，为的是「遍历期间就算有人增删集合，我遍历的还是原来那批」。Pinia 不这么做，直接对着集合本身 `forEach`。好处是零分配、最快路径；代价是边界情形——如果某个回调在被触发时同步地去增删集合，迭代行为就交给 JS 语言规范了：已被删且还没轮到的元素会被跳过，遍历期间新加进去的元素反而会被访问到。

实际中，订阅回调极少在触发的一刻去变异集合，所以这基本是个理论边界。Pinia 选择了「不为几乎不发生的情形付拷贝的税」。

> **这条权衡**：选择「触发时直接遍历集合、不预先拷贝」→ 换来「零内存分配、最快广播路径」→ 代价是「回调内部若同步增删集合，迭代行为依赖语言规范，属边界情形——但靠『订阅回调不该在触发时变异集合』这条使用约定来规避」。

## 把这几条权衡钉死

这章机制集中，但内核就一副骨架，所以真正值得带走的是下面这几条「选择 → 换来 → 代价」，记牢了，后面看到 `$subscribe` / `$onAction` 你就知道它们站在什么地基上：

1. **默认绑作用域、显式脱离出逃**：默认挂销毁钩子 → 换来卸载即回收、零样板 → 代价是跨作用域长订阅必须显式传 `detached`。
2. **自动清理与手动取消并存**：取消闭包既给作用域、又返回给调用方 → 换来声明式与命令式两种清理任选 → 代价是靠 `delete` 幂等兜底重复清理。
3. **附带清理以「真删成功」为闸门**：只有 `delete` 返回 true 才跑 `onCleanup` → 换来重复取消不产生重复副作用 → 代价是附带清理的语义被绑死在「回调从集合移除那一刻」。
4. **触发即原位广播、不拍快照**：直接 `forEach` → 换来零分配最快路径 → 代价是触发期间变异集合属边界情形，靠使用约定规避。

一句话收束：**Pinia 没有自己发明订阅的生命周期管理，而是把这件事整个托付给了 Vue 的作用域**——能用宿主已有的机制，就不重造一遍。这套「往集合加回调 + 借作用域自动清理」的骨架，会在后面的「Store 装配」和「订阅系统」两章被直接装配上去，用来支撑 `$subscribe` 和 `$onAction`，到那时候只看「在骨架之上搭了什么」，骨架本身不再重讲。
