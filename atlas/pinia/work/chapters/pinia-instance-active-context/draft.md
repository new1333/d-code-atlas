# Pinia 实例：根状态、注册表与全局活跃上下文

## 写在最前面：没有这套机制，日子会怎么过

想象你在写一个 Vue 应用。你在登录组件里放了一个用户状态库，结果路由守卫里也想读"当前登录用户"，某个工具函数里也想读它。如果缺了本章要讲的这套东西，你会陷入一种很累的写法：把状态库当成参数，一层一层往下传；组件树里还能靠 props 挣扎一下，出了组件树就只能手动从某个全局角落去捞。

更头疼的是：你有十几个 store，它们互相调用。用户 store 要读权限 store，购物车 store 要读用户 store。如果每个 store 在创建时就得先拿到"对方"，立刻就是先有鸡还是先有蛋的死循环。

Pinia 用一个看起来很"魔法"的招数化解了这一切：你在任何地方写一行 `useUserStore()`，它就给你那个唯一的用户 store，不传参、不分场合。这一章就来拆开这个魔法——它其实只靠两样东西：一个全局的"当前活跃"指针，和一个脱离组件树的作用域。

## 一句话点透

状态库不靠参数传来传去，而是靠一根全局指针隐式"被找到"；所有 store 的状态都收进一个独立于组件树的盒子里，方便哪天不要了，一键清空。

下面自底向上，一块一块搭。

## 第一块：根状态盒子，住在一个独立的作用域里

先看最底层。一个 Pinia 应用启动后，所有 store 的状态最终都汇总到同一个对象里，我们叫它"根状态盒子"。这个盒子本身就是一个普通的 Vue `ref({})`，里面按 store 名字分格子：`{ user: {...}, cart: {...} }`。

为什么要把所有状态汇总到一处？因为这样在做服务端渲染时，序列化整个应用状态只需要序列化这一个对象，客户端再把它整体灌回来。这件事后续 SSR 章会展开，这里你只要记住：**有一个统一的状态根，是后面很多便利的源头**。

但这个盒子住在哪里很讲究。Pinia 把它放进了一个特殊的作用域——`effectScope(true)`。这个 `true` 是 Vue 的 `detached` 参数，意思是"脱离父作用域"。换句话说，这个作用域不挂在任何组件下面，谁也不会自动回收它，除非你亲手喊停。

这是为什么？因为组件树会随用户操作不断创建、销毁。如果根状态住在某个组件的作用域里，那个组件没了，你的全局状态也跟着没了。把它独立出来，它的生命周期就和组件树解耦了。

## 第二块：store 注册表，一张 Map

光有根状态盒子还不够。每个 store 本身是个挺复杂的对象（有状态、有计算属性、有方法），Pinia 要保证"不管你调多少次 `useUserStore()`，拿到的都是同一个用户 store"。怎么保证？用一张普通的 `Map`，key 是 store 的名字，value 是那个 store 实例。第一次用到某个 store 时创建它、塞进 Map；之后每次都直接从 Map 里取同一个出来。

这就是单例最朴素的做法——不搞花哨，一张 Map 足矣。

## 第三块：挂载——库怎么"被找到"

现在你有了一个库（根状态盒子 + 注册表 + 一些内部字段），但组件还不知道它的存在。应用启动时你写 `app.use(pinia)`，这会触发库里那个 `install` 函数，它干四件事：

1. 把自己设为"当前活跃"的库（这根指针马上细说）。
2. 记下"我挂在哪个 app 上"。
3. 通过 Vue 的依赖注入把库 provide 进应用，挂在一个特殊的 Symbol 键下。
4. 把库挂到全局属性 `$pinia` 上，给 Options API 用。

前两步好理解。第三步是关键之一——依赖注入，可以理解为"按地址精准投递"：只要组件在这个 app 的树里，它就能 inject 出那个库。第四步是给老式 Options API 写法留的口子。

## 第四块：解析——免传参的秘密

这是全章最关键的一块，也是"魔法"真正发生的地方。

当你写 `useUserStore()` 时，它怎么知道该用哪个库？Pinia 的解析规则是两步走：

**第一步，先看依赖注入里有没有。** 如果是在组件的 setup 里调用的，inject 大概率能命中——拿到属于当前 app 的那个库。拿到后顺手把它设为"当前活跃"。

**第二步，注入没有，就用那根全局指针兜底。**

这根全局指针是什么？它是模块级别的一个变量，相当于**一块谁都能看到的公共留言板**——不管你在哪个组件、哪个工具函数里，读到的都是同一块板子。install 的时候往板子上写一次，之后只要没注入，大家就都看这块板子。

说人话就是：组件里有注入就用注入（精准、安全），出了组件树没注入，就看那块全局板子（方便，但所有人共享）。

这套设计换来的人体工学非常爽——你永远不用把库当参数传，一行 `useXxxStore()` 走天下。但它埋着一个雷，这正是本章最重要的权衡，下面专门讲。

## 第五块：store 之间的无参互引

有了活跃指针，还有个意外收获。假设用户 store 的某个 action 里要读权限 store：

```ts
// 用户 store 内部
actions: {
  async fetchProfile() {
    const perms = usePermsStore() // action 里再取别的 store
    this.profile = { ...(await api.get()), perms: perms.list }
  }
}
```

action 执行前，Pinia 会重新把当前库设为活跃。所以哪怕你在 action 深处、没有任何组件上下文，那根全局指针依然指向正确的库，`usePermsStore()` 照样无参解析成功。store 之间互引不死循环，靠的就是这个——不是创建时就互相握住对方，而是运行时各取所需。

## 第六块：一键销毁

还记得那个 detached 作用域吗？它的价值在这里兑现。当你要回收整个库（测试结束、多实例应用切换），调一个 dispose 函数：

> 停掉 detached 作用域 → 所有 store 的全部响应式（state、getter、订阅）一次性清空 → 清掉注册表 → 清掉插件列表 → 根状态置空 → 解除 app 引用。

**一句话：喊一声停，全部清掉。** 这就是一开始选择 detached 作用域换来的东西。

## 一条完整轨迹，串起来看

把上面六块接成一条真实运行链路：

```
app.use(pinia)
  → install：setActivePinia(pinia) / 记 app / provide 注入 / 挂 $pinia
  → 用户在组件 setup 里写 useUserStore()
  → inject 命中，拿到库，再 setActivePinia 一次
  → 查注册表 _s：没有 user？
  → 创建 user store，登记进 _s，状态镜像进根状态盒子的 user 格
  → 从 _s 取出返回（此后任意地方再调，都拿这同一个）
  → 在 user 的 action 里再写 usePermsStore() → 仍靠活跃指针无参解析到同一个库
```

输入 `app.use(pinia)`，输出一个"任何地方都能无参取到、且全局唯一"的 store 生态。

## 最小演示：从零搭一个状态库

下面这段用 Vue 的 `effectScope` 和 `ref`，几十行演透两件事：detached 作用域的可一键销毁，和全局活跃指针的免传参便利（以及它埋下的串态风险）。每一行都对应上面某块原理。

```ts
import { effectScope, ref } from 'vue'

// ---- 第一块：detached 作用域托管根状态（兑现权衡①的销毁面）----
function createPinia() {
  const scope = effectScope(true)         // true = 脱离父作用域，不会被自动回收
  const state = scope.run(() => ref({}))  // 根状态盒子，住在 scope 里
  return {
    scope,
    state,            // state.value 就是那个统一的状态根
    _s: new Map(),    // store 注册表：name -> store
  }
}

// ---- 第四块：模块级活跃指针（权衡②的核心）----
let activePinia                           // 全局"公共留言板"
const setActivePinia = (p) => (activePinia = p)

// 解析：注入优先、全局兜底
function getActivePinia(injected) {
  return injected || activePinia          // 有注入用注入，否则看全局板子
}

// ---- 跑一遍，看便利，也看串态 ----

// 请求 A：正常设活跃库
setActivePinia(createPinia())
const piniaForA = activePinia

// 请求 B：忘了注入，直接兜底
const piniaForB = getActivePinia(null)

console.log(piniaForA === piniaForB)      // true ← B 错拿到了 A 的库！
// 这就是服务端下跨请求串态的根：一根全局指针被并发请求共享。

// 缓解：组件里永远走 inject 拿"自己的"库，全局只兜底；
// 且开发期对"服务端走到了兜底"主动发警告（对应权衡②的代价面）。

// ---- 兑现权衡①：一键销毁整库响应式 ----
piniaForA.scope.stop()                    // 喊一声停
// 此刻 piniaForA 名下的所有响应式一次性失效。
```

把这段脑内执行一遍：A 设了板子，B 没注入就去读板子，结果读到 A 的库——这就是代价的活体演示；然后 `scope.stop()` 一调，A 的全部响应式归零——这就是当初选择的兑现。

## 关键权衡

机制本身并不复杂，难的是每个选择背后的取舍。本章机制集中，下面把三条核心权衡讲透。

### 权衡①：把根状态放进一个 detached 作用域

**选择**：根状态盒子不在某个组件的作用域里创建，而是在一个传入 `true`（脱离父作用域）的 `effectScope` 里创建。

**换来**：对这个作用域调一次 `stop()`，就能一次性销毁所有 store 的全部响应式——每个 store 的 state、getter、订阅都托管在这个作用域下（具体怎么托管是后续 store-assembly 章的事），停掉它就全停了。不必逐个 store 去销毁，也不会因为某个组件卸载而误伤全局状态。同时根状态的生命周期和组件树解耦，组件随便建随便毁，全局状态稳如磐石。

**代价**：这个状态库的生命周期独立于组件树，**不会随组件自动回收**。你必须在合适的时候（测试结束、多实例切换）主动调 dispose，否则它一直占着内存和响应式开销。测试场景和多实例应用尤其要注意——忘了销毁，状态就会在用例之间或实例之间残留。

> 说白了：换来"一键清空 + 不被组件卸载误伤"，代价是"你得自己记得按销毁按钮"。

### 权衡②：引入一根全局可变的活跃指针（本章最重的权衡）

**选择**：用模块级变量 `activePinia` 记录"当前活跃的库"，并规定解析规则是"注入优先、全局兜底"。

**换来**：调用 store 时不必显式传库——这是 Pinia 最招牌的人体工学。组件里靠 inject 命中、组件外（路由守卫、工具函数、action 内部）靠全局指针兜底，一行 `useXxxStore()` 走天下。store 之间也无参互引，不必在创建时互相握手，从而绕开循环依赖。

**代价**：在服务端渲染下，这根全局单例指针会被**并发请求共享**。请求 A 设了板子，请求 B 没注入就去读板子，结果错拿到 A 的库——这就是臭名昭著的"跨请求串态"。客户端单用户没事（一根指针就一个库），服务端多请求并发时就是定时炸弹。

**怎么缓解**：解析时注入永远优先——只要在组件 setup 里调用，inject 就能拿到属于当前请求的库，全局指针根本没机会上场。全局指针纯粹是兜底，主要服务于"组件树之外"的调用。而且开发期会对一种危险情形主动告警：一旦检测到"既没注入、又跑在服务端"，直接报错级提示，告诉你这会暴露在跨请求串态风险下，并给出修复建议（在 setup 顶部调用，或显式把库传进去）。

> 说白了：换来"免传参的爽"，代价是"服务端有一根会被共享的全局针"，缓解靠"注入优先、全局只在客户端兜底、服务端兜底就报警"。

这条权衡是 Pinia 整个 API 表面的根基——后面章节你会看到，store 的惰性创建、按调用解析库，全都建立在这根指针之上。

### 权衡③：把库实例本身标为非响应式

**选择**：用 Vue 的 `markRaw` 把状态库实例本身标记为非响应式。

**换来**：这个实例会被到处引用（挂在 app 上、存在全局指针里、被 inject 来 inject 去），如果它是响应式的，每次被引用都会触发 Vue 的响应式代理、递归包裹，既无意义又有开销。标成非响应式，它就是一个干干净净的普通对象，被引用时没有任何额外成本。

**代价**：实例自身的字段变化不会有响应式。但这其实不是损失——因为**实例本身不是数据源**。真正的状态数据住在那个根状态盒子里（那个 `ref({})`），响应式是在盒子上、在 store 的 state 上。实例只是个"管家"，管家的名片不需要响应式。所以这个代价几乎无实质损失。

> 说白了：换来"管家被到处引用时不触发响应式开销"，代价是"管家自己不响应式"——但管家本来就不存数据，不响应式正好。

## 收束

这一章是全书的地基。它交付了一件最朴素的东西：**一个挂载到 app 上的单例容器**，里面有根状态盒子、有注册表、有一根全局活跃指针。后面所有花活——store 怎么惰性创建、怎么装配、怎么变更、怎么订阅、怎么做 SSR——全都是往这个容器里装东西。

记住两件最关键的事：

- **detached 作用域**让整库响应式可以一键回收，代价是生命周期独立、需主动销毁。
- **全局活跃指针**让调用免传参，代价是服务端串态风险，靠"注入优先 + 服务端告警"缓解。

这两块都是"容器层面"的机制。容器造好了，下一步就该往里头装第一个真正的零件了。紧邻的下一章会拆开一个最小的"回调集合 + 作用域自动清理"机制——它是后面 `$subscribe`、`$onAction` 这些监听能力共同的底层零件。
