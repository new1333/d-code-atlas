# defineStore：惰性 useStore 闭包与注册表缓存

你大概写过很多次这样的代码：

```ts
const useUserStore = defineStore('user', () => ({ name: ref('') }))
const user = useUserStore()
```

两行写完，顺得像呼吸。但你停下来想一下会发现一件怪事：`defineStore` 看名字像「定义并创建」，可它返回的 `useUserStore` 居然是个**函数**，得再调用一次才拿到真正的 store。为什么要套这么一层？这一层薄薄的「函数套函数」，正是 Pinia 把「定义」和「实例化」分开的关键，也是「store 本质上是一个可组合 hook（composable）」这句话的落点。

## 一、先想清楚：为什么「定义」不能直接给你一个实例

假如 `defineStore` 直接返回一个 store 实例，三件糟心事会立刻冒出来：

- **用没用都会被创建。** 只要你在某处 `import` 了这个 store 模块，它就被实例化了——哪怕你这次根本没调用它。打包器没法把它当作「没用到」剔除掉；在 SSR 下还会白跑一遍 setup，凭空多花一份开销。
- **同一份代码没法服务多个容器。** 你的项目里可能挂了不止一个 app、不止一个 Pinia 容器（测试、微前端、多端共用一份逻辑都很常见）。如果定义即实例，那这个实例归谁？没法各取各的。
- **store 之间互相引用会撞上顺序问题。** 模块一加载就实例化，A 引用 B、B 又引用 A 时，谁先谁后就成了噩梦。

Pinia 的解法反直觉但一招治三病：**定义时不创建实例，而是返回一个「调用入口函数」**。定义这一步被做成了纯粹的、零副作用的声明——什么都没发生；真正的实例化被推迟到你第一次调用那个入口函数的时候。

## 二、定义阶段：把信息夹进菜单，厨房还没开火

打个比方：定义一个 store，就像把一道菜的**食谱**写下来、夹进菜单里。写食谱不等于做出菜——厨房还没开火、食材还没下锅。只有等客人**点单**（调用 `useStore()`）的那一刻，厨房才会照着食谱真正做出这一份来。

照着这个比方看 `defineStore` 在定义阶段到底干了什么，就一目了然了：

```ts
function defineStore(id, setup, setupOptions) {
  const isSetupStore = typeof setup === 'function'   // 定义时一次性判断作者用哪种写法
  const options = isSetupStore ? setupOptions : setup // 把两种写法的「材料」整理成一种形状

  function useStore(pinia?, hot?) {
    // 真正的实例化逻辑都在这里，但现在一行都不执行
  }

  useStore.$id = id    // 入口函数自己也是个「数据载体」：挂着 id 供别处用
  return useStore      // 注意：返回的是函数，不是 store
}
```

就这么几件事：判断一下作者用的是「setup 写法」还是「option 写法」（`typeof setup === 'function'`），把材料整理成同一种形状，然后把 `id`、`options`、`isSetupStore` 这几样东西**闭包**进一个名叫 `useStore` 的函数里，原样返回。**没有创建实例，没有碰全局，没有产生任何副作用。**

正因为它在定义阶段是「干净」的，源码在这个函数上方特地标了一句注解，告诉打包器「调用它没有副作用，没被用到的 store 可以安全剔除」。这就是「定义零副作用」直接换来 tree-shake 能力的证据——食谱没人点，整张食谱都能从菜单上撤掉。

> 这里出现的「注册表 `_s`」和「全局活跃容器 `activePinia`」，是第 1 章已经讲透的两块基础设施：每个 Pinia 容器都有一个 `_s`（一个 `Map`）当缓存，还有一个模块级的 `activePinia` 记住「当前该用哪个容器」。本章不再重讲它们本身，只看 `defineStore` 怎么把它们组织成一个「返回函数」的 API。

## 三、调用阶段：点单那一刻才解析容器、查缓存

那真正的实例化发生在什么时候？答案简单得有点反直觉：**发生在你写下 `useStore()` 的那一行**。

入口函数被调用时，它要做三件事——解析容器、推为活跃、查缓存。我们一件件看。

**第一件：按这次调用解析出「该用哪个 Pinia 容器」。** 这是按一套优先级走的：

```
测试旁路 → 显式传参 → 注入(provide/inject) → 全局活跃兜底
```

也就是说：测试模式下会强制忽略你传的参数；否则只要你调用时显式传了一个容器，就用它；没传但有注入上下文（比如在组件 setup 里），就从注入里取；都没有，就退到那个全局活跃容器上。

这里有个要留意的点：入口**没有**直接复用第 1 章那个「取活跃容器」的函数，而是把解析逻辑内联了进来。原因很实在——那个函数既不接受参数、也不会把自己的结果推为活跃，而本入口恰恰需要这两样。第 1 章那条「注入优先、全局兜底、dev 下告警」的取舍这里不重复，本章相对它**多出来**的，正是最前面的「显式传参优先」和紧跟其后的「推为活跃」。

**第二件：把解析到的容器推为全局活跃。** 一句 `setActivePinia(pinia)`。为什么要这么做？因为接下来真正装配这个 store 时，它内部的 getter、action 还要去取「当前容器」，得保证它们取到的是正确的那个。把刚解析到的容器设为活跃，就是给后续链路铺好路。

**第三件：查注册表，决定创建还是复用。**

```ts
if (!pinia._s.has(id)) {
  // 创建：调用对应的装配函数（它自己负责把实例塞进注册表）
}
const store = pinia._s.get(id)
return store
```

注册表里已经有这个 `id`？直接取出来。没有？调一次装配函数把它造出来——而装配函数会负责把自己造好的实例写进注册表（这一步的内部细节是下一章的主题，本章把它当黑盒）。最后无论如何都从注册表里取一下返回。

把这三件事串起来，整个调用流程长这样：

```
useStore(pinia?)
  ├─ 解析容器：测试旁路 → 显式传参 → 注入 → 全局活跃兜底
  ├─ 把解析到的容器推为全局活跃
  ├─ 注册表里有这个 id？
  │     ├─ 有：跳过创建
  │     └─ 没有：调装配函数（装配函数负责把自己登记进注册表）
  └─ 从注册表取出该 id 的实例返回
```

**心智模型可以浓缩成 7 步**：

1. **定义**：把 `id`、整理好的 `options`、`isSetupStore` 闭包进入口函数，立即返回它；不创建实例、不产生副作用。
2. **首次调用**：拿到一个可选的「显式容器」参数，按优先级解析容器。
3. **推为活跃**：把解析到的容器设为全局活跃容器。
4. **查注册表**：看该容器里有没有这个 `id`——有就直接跳到第 6 步。
5. **创建并登记**：没有就调装配函数，它会先把半成品塞进注册表（这一步的深意留给下一章）。
6. **取出返回**：从注册表取出这个 `id` 的实例。
7. **再次调用**：从第 2 步重复，但第 4 步这次命中缓存——所以同一个入口反复调用，拿到的是**同一个实例**。

## 四、把入口函数从零写一遍

说再多不如自己写一遍。下面这段剥离了响应式、effect scope、两种语法的差异处理，只把「返回函数而非实例」「按调用解析容器」「注册表缓存」这三件事演透。它是能直接用 `node` 跑的：

```js
// ===== 模拟第 1 章提供的基础设施 =====
function makePinia(name) {
  return { name, _s: new Map() }       // _s 就是注册表
}
let activePinia = null                 // 全局活跃容器（第 1 章的 activePinia）
let injectedPinia = null               // 模拟 Vue 的 provide/inject

// ===== 本章的主角：defineStore =====
function defineStore(id, setup) {
  const isSetupStore = typeof setup === 'function'   // 定义时一次分流

  function useStore(pinia) {
    // ① 按调用解析容器：显式传参 > 注入 > 全局活跃兜底
    pinia = pinia || injectedPinia || activePinia
    if (pinia) activePinia = pinia                    // ② 把它推为全局活跃
    // ③ 注册表里有就复用，没有才创建
    if (!pinia._s.has(id)) {
      const store = setup()                           // 真正的「装配」细节留给下一章
      pinia._s.set(id, store)                         // ——装配函数负责把自己登记进注册表
    }
    return pinia._s.get(id)
  }

  useStore.$id = id
  return useStore
}

// ===== 演示：惰性、缓存、按调用选容器 =====
const useCount = defineStore('count', () => ({ n: 0, inc() {} }))
const app = makePinia('app')
injectedPinia = app                                    // 相当于 app.use(pinia) 之后

console.log('定义后，注册表为空：', app._s.has('count'))        // false（惰性：还没造）
const s1 = useCount()
console.log('首次调用后：', app._s.has('count'), s1.n)         // true  0
const s2 = useCount()
console.log('再次调用是同一实例：', s1 === s2)                 // true（缓存）
const app2 = makePinia('app2')
const s3 = useCount(app2)                                         // 显式传另一个容器
console.log('换容器得到的是另一个实例：', s3 !== s1)            // true（按调用选容器）
```

对应的**执行轨迹**是这样的：

- 定义 `const useCount = defineStore('count', ...)`：此刻**没有任何 store 被创建**，`useCount` 只是个挂着 `$id='count'` 的函数，注册表里没有 `'count'`。
- 首次 `const s1 = useCount()`：解析容器（经注入拿到 `app`）→ 推为活跃 → 注册表无 `'count'` → 装配并写入注册表 → 返回实例。
- 再次 `const s2 = useCount()`：注册表命中 `'count'` → 直接取出 → `s1 === s2`。
- 换容器 `useCount(app2)`：这次显式传了 `app2`，于是解析到 `app2`、在它的注册表里另造一份 → `s3 !== s1`。

一句话：**定义是写食谱，调用是点单，点过一次的单会被记下来复用。**

## 五、三个关键权衡

把上面这套机制拆成「做了什么选择、换来什么、又付了什么代价」，能看出 Pinia 为什么长成这样。

**权衡一（全章灵魂）：用「返回调用入口函数而非实例」，换取惰性创建 + 定义零副作用 + 解耦的初始化顺序，代价是每次调用都要做一次「解析容器 + 查注册表」。**
选择不在定义时实例化，换来的是三件好事打包到手：没被用到的 store 能被 tree-shake 掉（零副作用）；实例化推迟到真正需要的那一刻（惰性，SSR 下也不会白跑）；store 之间互相引用时不再有「谁先实例化」的顺序难题（因为都是调用时才造）。说人话就是——把「定义」做成了纯声明，把麻烦全部推迟到「调用」。代价也很清楚：每调用一次入口，都得现解析一次容器、现查一次注册表。好在注册表查询是 `Map` 的 `has/get`，几乎不花什么钱，这笔账很划算。

**权衡二（相对第 1 章的新侧面）：在入口里按优先级解析容器、并把解析结果推为全局活跃，换取「同一个入口在不同容器下能取到不同实例」的多容器能力，代价是入口必须在「有活跃上下文」时调用。**
第 1 章那条「注入优先、全局兜底」的取容器路子，本入口不仅继承了，还在前面加了「显式传参优先」、在后面加了「解析后推为活跃」。换来的是什么？是同一个 `useCount`，在 app A 里调用拿到 A 的实例、在 app B 里调用拿到 B 的实例，甚至测试时还能被旁路重塑——这就是「按调用选容器」带来的多容器隔离能力。代价是：调用入口必须发生在「存在活跃容器」的时候；若没有，开发环境下会直接抛错（提示你是不是在 `app.use(pinia)` 之前就用了 store），生产环境下则可能拿到错误的实例。换句话说，这套人体工学的前提是「调用发生在有上下文的地方」。

**权衡三：在定义阶段就凭「setup 参数是不是函数」一次性分流两种作者语法，换取「一个入口同时服务 option 与 setup 两种写法」，代价是实例化时要分派到两条装配路径。**
`defineStore` 支持两种写法：传一个选项对象（option 写法），或传一个 setup 函数（setup 写法）。它没有为这两种写法各搞一套定义 API，而是在定义的那一刻用一个 `typeof setup === 'function'` 的布尔判断分流，把材料整理成同一种形状，让**同一个** `useStore` 入口都能服务。代价是：到了真正实例化时，入口得根据那个布尔标记把活儿分派给两条不同的装配路径（option store 走 `createOptionsStore`、setup store 走 `createSetupStore`）。这两条装配路径内部到底怎么把返回值分类、怎么托管响应式——那是下一章的事，这里只点到：**分流发生在定义时，分派发生在实例化时，二者被这个布尔标记串起来。**

## 六、小结

回到开头那两行代码，现在你能看透它了：`defineStore` 是写食谱，`useUserStore()` 才是点单。定义阶段零副作用、可 tree-shake；调用阶段按优先级解析容器、推为活跃、查注册表——没造就造、造过就复用。这套「返回函数而非实例」的设计，用一个反直觉的 API 形状，一次性治好了「用没用都创建」「没法多容器」「初始化顺序」三件糟心事，代价无非是每次调用多一次轻量的解析与查表。

入口把活儿干到「调装配函数」就停了。装配函数内部怎么在一个 effectScope 里跑 setup、怎么把返回的 ref/computed/函数分类、为什么要先把自己半成品塞进注册表再跑 setup——这些正是下一章《Store 装配：effectScope 托管的返回值分类与状态镜像》要拆开讲的。
