# 约定胜配置的插件注册机制

## 你最怕的三件事

想象你在维护一个能下载上千个网站的工具。每周都有人发 PR：「我加了对 X 站的支持」「我写了个下完自动转 MP3 的后处理」。作为维护者，你最怕看到的是什么？

不是新代码，而是这件事变成「三连」：**改源码、改注册表、改配置**。每加一个能力，都得先在某个中心清单里手写一行登记——「YouTube 提取器，登记；B 站提取器，登记；转码后处理器，登记……」这个清单会无限膨胀，而且和源码死死绑在一起。外部贡献者也做不到「丢一个文件就走」，因为他还得求你在清单里给他留个位置。

本章要解决的正是这个矛盾：**既要能无限扩展，又不能有任何中心化的登记动作。**

答案是六个字——**约定即配置**。你不用告诉系统「我这有个新插件」，只要把文件放到约定的目录、给类起个约定的名字，系统自己就会发现并接管。说人话就是：**不用登记，放对地方就行。**

这一章是全书靠它打底的章节之一。它建立的「先发空盒子、按约定发现、插件盖过内置」这套手法，后面讲数据总线、讲后处理流水线的章节都会反复用到——各阶段都要往同一份共享注册表里各取所需。

## 第一个基本件：先发空盒子，后填值

我们先看最底层的那块。

整个注册系统有个尴尬的时序问题：很多模块在**程序一启动、导入阶段**就想拿到「插件注册表」（比如提取器要查「有哪些提取器可用」），但注册表真正被填满，要等到**程序真正用起来、去扫描插件目录**的时候——而扫描插件，又可能反过来引用到提取器本身。

这就是循环依赖：A 导入时需要 B 的结果，B 的结果又依赖 A。如果注册表是个普通字典，谁先导入谁就抓瞎——拿到的要么是还没建好的字典，要么是填了一半的。

破局的手法很朴素：**把字典装进一个盒子里。**

```ts
// 一个只包了 value 的可变盒子
class Box<T> {
  value: T;
  constructor(initial: T) { this.value = initial; }
}
```

盒子本身是个稳定的小对象，程序一启动就能建好。模块在导入阶段只要拿到**盒子的引用**就行——至于盒子里面装什么字典，那是后面的事，等准备好再把字典塞进 `.value`。

打个比方：这就像一个贴了门牌号的空房间。**钥匙（盒子引用）早就分发到每个人手里了，家具（注册表内容）等货到了再搬进去。** 大家先记住「那个房间在哪儿」，不用等家具到齐才能开工。

这一招把「拿到引用」和「填进内容」拆成了两个时刻，循环依赖就被绕开了。

## 第二个基本件：后缀就是身份证

现在盒子有了。但系统怎么知道，散落在用户目录里的某个类，到底是个提取器，还是个后处理器，还是根本不算插件？

答案还是约定——**看类名的尾巴**。

- 类名以 `IE` 结尾（Information Extractor）→ 它是个提取器
- 类名以 `PP` 结尾（Post-Processor）→ 它是个后处理器

这就像邮编系统：你不用给每封信单独登记路由，只要信封上写了正确的邮编（后缀），系统就知道往哪送。**类名后缀就是邮编**，系统按后缀把类分拣到对应的注册表。

（顺带澄清一个容易混的点：有些文档会把请求处理器 `RH` 也算进来，说「IE/PP/RH 三类同构」。但 RH 其实**不走这套机制**——它用显式的装饰器登记，是另一套独立的东西，属于「可插拔传输层」那一章的主题。本章只讲提取器和后处理器这两类真正靠约定发现的插件。）

光认后缀还不够，系统还顺手做了一道筛选，把混进来的「不像插件的东西」剔除：

- 必须是个类（不是普通函数、不是常量）
- 必须是 `IE` 或 `PP` 结尾
- 不能以下划线开头（下划线 = 私有约定，跳过）

于是上下划线开头的辅助类、忘加后缀的普通工具函数，统统被静默丢掉。注意「静默」这两个字——这是后面要重点讲的代价：**类名起错了不会报错，只是悄悄不生效**。用户以为注册了，其实没有。

## 组合起来：发现，然后前置合并

有了盒子、有了后缀约定，现在把两个基本件拼起来。整个流程的节奏是这样的：

```
程序启动（导入期）
  ├─ 给每类插件建好空盒子（IE 一对、PP 一对）
  └─ 把一个「自定义查找器」顶到导入链最前面
        ↓  此时盒子里还没东西

用户把插件文件丢进约定目录
  └─ 系统只记下「那个目录在那儿」，先不碰

程序真正用起来（首次构造主编排器）
  └─ 触发「全量加载」——盒子第一次被填满的时刻
        ├─ 查找器把用户目录算成一个「虚拟包」
        ├─ 枚举里面的每个模块，真正读进来
        ├─ 按后缀把合规模件里的类挑出来
        └─ 塞进盒子
```

最关键的一步在最后：**插件不是简单加进注册表，而是被「前置」进去。**

合并的规则是「**第一个非空值胜出**」。插件排在前面，内置排在后面。所以——**只要插件和内置类同名，插件就盖过内置。**

这意味着什么？意味着用户可以不动一行源码，只丢一个 `BilibiliIE.py`，就把官方那个 B 站提取器整个换成自己写的版本。这就是「打补丁」式的扩展：你不用等官方修，自己盖一层就行。

内置类自己呢？它们最后也填进**同一个盒子**。消费方（要查「有哪些提取器」的代码）根本不用区分哪个是内置、哪个是用户插件——读同一个盒子就行。**内置和插件，走的是同一条路。**

## 「发现」在 Python 里靠什么落地：虚拟命名空间包

上面那张流程图里有一句「查找器把用户目录算成一个虚拟包」。这步是整个机制最巧、也最难移植的部分，值得单独说透。

问题是：怎么让 Python 自己去扫描用户目录里的 `.py` 文件，又不让我们手写文件遍历？

Python 的导入系统留了个口子：你可以在导入链最前面插一个**自定义查找器**。正常情况下，当你写 `import yt_dlp_plugins.extractor`，Python 会按默认规则去找这个包。但顶进去的查找器抢在前面说：「这个名字我来管。」

它怎么管？它返回一个**假的包描述**，告诉 Python：「`yt_dlp_plugins.extractor` 是个包，它的搜索位置是用户那几个插件目录。」——这个包根本没有真实的 `__init__.py` 文件，它纯粹是「一组搜索位置」的代名词。

这么一来，Python 自带的工具就会像对待真包一样，去那些目录里枚举子模块。我们一行文件扫描代码都不用写，借用 Python 的导入系统就完成了发现。

> 这一段是 Python 专有的手法，没有 TypeScript 的等价物——TS/JS 没有这种能被外部接管的全局导入钩子。所以下面的演示里，我会用「遍历一组模块对象」来**模拟**这一步，把「发现」这个动作简化掉，重点演透另外三件事：后缀约定、空盒子延迟、前置覆盖。

## 第二种扩展：override，直接替换内置类

除了「新增一个类」，还有种不太一样的扩展方式，顺便提一下。

前面讲的插件，都是往注册表里**加**新东西。但还有一种玩法：用户写一个类，继承自某个内置提取器，并打上 `plugin_name` 标记。系统一旦发现这样的类，就会**就地替换**掉内置类在它自己模块里的名字——也就是说，任何人再去 `import` 那个内置类，拿到的其实已经是用户的包装版本了。

这叫 override，是「打补丁」的另一种姿势：不是和内置同名盖一层（那是前置合并），而是**直接钻进内置类所在的模块，把它的名字换掉**。

这两种扩展方式互补：前置合并适合「我加个新的」或「我同名盖一个」；override 适合「我要包装、增强某个具体的内置类」。它们最终都让用户能在不改源码的前提下改造行为。

## 原理演示：三十行演透三件事

下面用 TypeScript 从零搭一个最小骨架，演透**后缀约定 + 空盒子延迟 + 前置覆盖**这三件事的合奏。「扫描目录发现插件」这一步用遍历模块对象来模拟（上一节说过，真正的发现机制是 Python 专有的）。

```ts
// ① 延迟绑定盒子：先发空盒子，后填值（破循环依赖的那个基本件）
class Box<T> {
  value: T;
  constructor(initial: T) { this.value = initial; }
}

// ② 插件规格卡：一类插件 = 一个后缀 + 两张查表（主查表 + 插件专用查表）
type Spec = {
  suffix: string;
  destination: Box<Record<string, any>>;        // 主查表：内置+插件合并后供消费方读
  pluginDestination: Box<Record<string, any>>;  // 仅插件查表：兼容旧式「from … import X」
};
const specs: Record<string, Spec> = {};
const register = (name: string, suffix: string) =>
  (specs[name] = { suffix, destination: new Box({}), pluginDestination: new Box({}) });

register('extractor', 'IE');     // 提取器
register('postprocessor', 'PP'); // 后处理器

// ③ 约定过滤：从模块里挑出「以指定后缀结尾、非私有」的类
function getClasses(mod: Record<string, any>, suffix: string) {
  const out: Record<string, any> = {};
  for (const [name, value] of Object.entries(mod)) {
    if (typeof value !== 'function') continue;   // 不是函数/类，跳过
    if (!name.endsWith(suffix)) continue;        // 后缀不对，跳过
    if (name.startsWith('_')) continue;          // 私有，跳过
    out[name] = value;
  }
  return out;
}

// ④ 前置合并：每个键取「第一个非空值胜出」，插件排前面 → 同名盖过内置
function mergeDicts(...ds: Record<string, any>[]) {
  const out: Record<string, any> = {};
  for (const d of ds)
    for (const [k, v] of Object.entries(d)) {
      if (!(k in out)) out[k] = v;                            // 第一次见，收下
      else if (out[k] == null && v != null) out[k] = v;       // 已收的是空，用新非空顶上
    }
  return out;
}

// ⑤ 全量加载：扫所有插件模块，前置合并进主查表（首次使用才触发）
let allLoaded = false;
function loadAll(kind: string, pluginModules: Record<string, any>[]) {
  const spec = specs[kind];
  const plugins: Record<string, any> = {};
  for (const mod of pluginModules)
    Object.assign(plugins, getClasses(mod, spec.suffix));
  spec.pluginDestination.value = plugins;                               // 插件专用表整体替换
  spec.destination.value = mergeDicts(plugins, spec.destination.value); // 主表前置合并
  allLoaded = true;
}
const ensureLoaded = (kind: string, mods: Record<string, any>[]) => {
  if (!allLoaded) loadAll(kind, mods);
};
```

现在用一批「模块」来跑它。这些模块对象就模拟「Python 导入系统扫到的那些文件」：

```ts
// 内置提取器（模拟官方自带的提取器包）
const builtinModule = {
  YoutubeIE:  class { id = 'youtube' },
  BilibiliIE: class { id = 'bilibili' },
  GenericIE:  class { id = 'generic' },
  _HelperIE:  class { id = 'helper' },   // 私有，应被约定过滤
  someUtil:   () => {},                  // 没 IE 后缀，应被忽略
};

// 用户丢进约定目录的插件（模拟 yt_dlp_plugins/extractor/mysite.py）
const userPlugin = {
  MySiteIE:   class { id = 'mysite' },         // 合规：新站点提取器
  BilibiliIE: class { id = 'bilibili-patch' }, // 同名！要盖过内置
  broken:     () => {},                        // 忘加后缀，静默忽略
};

// —— 跑一下 ——
// ① 导入期刚结束：盒子建好了，但空的
console.log(specs.extractor.destination.value);                       // {}

// ② 内置填进同一个盒子（内置和插件走同一条路）
Object.assign(specs.extractor.destination.value, getClasses(builtinModule, 'IE'));
console.log(Object.keys(specs.extractor.destination.value));
// [ 'YoutubeIE', 'BilibiliIE', 'GenericIE' ]   ← _HelperIE、someUtil 被过滤掉

// ③ 首次使用才触发全量加载，用户插件被前置合并进来
ensureLoaded('extractor', [userPlugin]);
const table = specs.extractor.destination.value;
console.log(Object.keys(table));
// [ 'MySiteIE', 'BilibiliIE', 'YoutubeIE', 'GenericIE' ]
console.log(new table.BilibiliIE().id);                              // 'bilibili-patch'  ← 插件盖过内置
```

合并这一步的内部轨迹值得盯一眼——这是「前置覆盖」真正发生的地方：

```
mergeDicts( { MySiteIE, BilibiliIE(插件) } , { YoutubeIE, BilibiliIE(内置), GenericIE } )
   插件排第一个参数                              内置排第二个参数
   ├─ MySiteIE      第一次见   → 收插件
   ├─ BilibiliIE    第一次见   → 收插件（插件排第一，胜出！）
   ├─ YoutubeIE     第一次见   → 收内置
   ├─ BilibiliIE    已有(插件) → 内置值被忽略
   └─ GenericIE     第一次见   → 收内置
   ⇒ { MySiteIE:插件, BilibiliIE:插件, YoutubeIE:内置, GenericIE:内置 }
```

所以最后查出来的 `BilibiliIE` 是插件版，官方那个被悄悄盖掉了。配一个最小 `package.json` 就能用 `node`（或 `bun run`）跑出来亲眼看：

```json
{
  "name": "plugin-registry-demo",
  "private": true,
  "type": "module"
}
```

## 关键权衡

演示演透了「怎么做」，但「为什么这么做」更值得记住。这套机制做了四个互相纠缠的选择，一个一个拆。

### 权衡一：后缀即类型，换来零注册表，代价是错名静默失效

**选择**：用类名后缀（`IE`/`PP`）来判定一个类属于哪一类插件，而不是维护一张显式的「类名 → 类型」登记表。

**换来**：完全没有中心化的注册表。不管是官方写的内置类，还是用户随手丢进目录的外部插件，**走的是同一条发现路径**——同一个盒子、同一套过滤规则、同一次合并。外部贡献者真的能「丢一个文件就走」，不需要任何人帮他改登记表。这正是无限扩展和零中心配置之间的桥。

**代价**：类名被硬约束在一个命名规则里。更难受的是——**起错名字不会有任何报错**。一个类忘加 `IE` 后缀、或者打成了小写，它就被「约定过滤」静默丢弃。用户满心以为插件生效了，实际根本没注册进来，而且系统一个字都不提醒。这种「以为装好了其实没有」的故障，排查起来非常折磨人。

### 权衡二：先发空盒子，换来打破循环依赖，代价是读早了拿空表

**选择**：跨模块共享的注册表不直接用字典，而是套一层可变盒子。

**换来**：各个模块在程序一启动的导入阶段，就能拿到「将来才填充」的同一份注册表引用。导入期拿到盒子、运行期再填值——这两件事被拆开了，循环依赖就此瓦解。这是整个机制能跑起来的前提，没有这层间接，导入顺序就会卡死。

**代价**：注册表真正被填满的时刻，被推迟到了「首次使用」。这就埋下一个时序陷阱：**谁要是读早了**（在全量加载触发之前就去查表），会拿到一张空表，而且照样没有报错。插件「没生效」和「读得太早」在现象上一模一样，都是空，非常容易误判。

### 权衡三：借用语言导入系统，换来「丢个文件夹即装好」，代价是绑死宿主语言

**选择**：不自己写文件扫描器，而是把一个自定义查找器顶到 Python 导入链最前面，让用户目录被当成一个无 `__init__.py` 的命名空间包，借用 Python 自己的工具去枚举模块。

**换来**：插件可以散落在多个用户级、系统级配置目录，甚至压缩包里，系统都能无差别发现。对用户而言，安装一个插件真的就是「丢个文件夹」那么简单，不用解压、不用改路径、不用跑安装脚本。

**代价**：这一招深度依赖 Python 导入机制的内部细节（子模块搜索位置、空操作加载器）。它不可移植——换个语言就没有等价物（这正是上面演示只能用遍历模块对象来模拟的原因）。而且它向后兼容脆弱：源码注释里明说这套插件 API 不保证兼容，Python 升级一个版本，这套靠内部行为撑起来的发现机制就可能要跟着修。

### 权衡四：前置合并加同名覆盖，换来就地打补丁，代价是覆盖隐晦难调

**选择**：插件类按「第一个非空值胜出」排到内置类之前，再配上 override 那一路直接替换内置类在模块里的名字。

**换来**：用户插件能按同名覆盖或包装内置实现。某个站点的官方提取器有 bug，用户不用等官方修，丢一个同名的插件就能打补丁；想增强某个内置类，写个 override 包装一层就行。这种「不改源码也能改造行为」的能力，是整个生态能长期被社区维护的关键。

**代价**：覆盖是**隐式**的。同名即覆盖，和加载顺序强相关。调试的时候，你很难一眼看出「这个内置类其实早被某个插件悄悄换掉了」——表面上代码指向的是内置，实际跑的是插件。一旦覆盖行为不符合预期，排查链路很长，得把所有插件目录翻一遍才能定位是谁盖了谁。

## 小结

回到开头那个矛盾：既要无限扩展，又不能有中心化登记。这一章给的解法是三件套的合奏——

- **后缀当身份证**，让系统靠类名尾巴自己分拣，省掉登记表；
- **空盒子延迟填值**，把「拿引用」和「填内容」拆开，绕开循环依赖；
- **前置合并**，让插件盖过同名内置，实现不改源码的打补丁。

这三件套配合起来，换来的就是「丢个文件、起对名字」即可扩展的体验。代价也都摆在明面上：错名静默失效、读早了拿空表、绑死 Python 导入机制、覆盖隐晦难调。这是一组典型的「用隐式约定换零配置」的取舍——你接受了约定带来的约束和静默风险，换回了极致的扩展便利。

这套「延迟盒子 + 约定发现」建立起来的共享注册表，是后面很多章节的底座。紧接的下一章会讲**浏览器指纹伪装**——它也是一种「作为扩展叠加的能力」，只不过它叠加在传输层之上，靠给处理器打偏好分（而不是靠命名约定）来决定谁接管请求。
