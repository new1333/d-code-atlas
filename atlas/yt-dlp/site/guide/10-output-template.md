# 输出模板引擎：命名即元数据投影

## 一、同一份元数据，要变成多少种字符串

想象你在批量下载一个频道的三百个视频，顺手写下一行：

```
%(upload_date)s - %(title)s.%(ext)s
```

然后期待每个文件都按「上传日期 - 标题.扩展名」自动落盘。

但这只是你看得见的那一种字符串。同一份视频元数据，背后还偷偷变出了好几种：下载时终端标题栏实时滚动的百分比、控制台里打印的那行进度、下载完自动跑的一条 `--exec` 命令……它们全都是「从视频元数据派生一段字符串」这件事。

如果没有一个统一的机制，这几处就得各写一套取值逻辑——文件名那套、进度条那套、命令那套——更糟的是，某个字段一缺失就直接崩，而命令那一路的 shell 注入风险也无处集中防御。

说人话就是：系统需要一台「投影机」，喂给它一条模板和一份元数据，它就吐出对应的字符串。这一章讲的就是这台投影机。

> 它吃进去的那份元数据，正是第 4 章讲过的那条胖 info_dict——那一章把「字典当万能数据总线」讲透了，本章只看它的一个新侧面：怎么把这条字典投影成一串输出文字。

## 二、核心思想：编译，不是解释

这台投影机最反直觉的一点是：它**不解释模板**。

「解释」是什么意思？就是拿到 `%(title)s` 后，边扫边查字典边拼字符串，扫一个占位符查一次、拼一段。这听起来最直觉，但有个大麻烦——你想给标题做精度截断 `%(title).30s`、想让它右对齐补零，这些都得自己写一套格式化逻辑。等于从零造一个文本代入器，宽度、精度、对齐全得重新发明一遍。

它选了另一条路：**编译**。把那条富模板，在「正式输出之前」就预先处理成一个扁平的取值表 + 一段宿主语言（这里是 Python）自己就认的格式串。难活——取值、取负、算数学、做日期格式化、做各种类型转换——全在这一步做完，把结果老老实实存进那张扁平表。等到真正要输出字符串的那一刻，剩下的事就交给宿主语言自带的格式化去干，引擎自己几乎什么都不做。

打个比方：这像开卷考试。真正费脑的解题（取值、转换）都在考前就做完了，抄成一张小抄（扁平取值表）带进考场；考场上你只剩一件事——把小抄上的答案，照着题面（改写后的格式串）填进去。考场上的动作平庸到不需要动脑。

「编译」换来的是：宿主语言格式化里那一整套宽度、精度、零填充、左右对齐的能力，引擎**一分钱不花就继承过来**——你写 `.30s`，引擎连看都不看，原样塞回给宿主，让宿主在最后那步替你截断。引擎自己永远只负责「取值与转换」这一件事。

## 三、自底向上：一条占位符要过的两关

把上面那句话落成一条占位符的命运，它从头到尾要过两关。

**第一关：编译期（取值 + 转换）**。引擎用一条「外层」正则扫模板，每扫到一个 `%(...)` 占位符，就交给一个编译回调。回调里，再用一条「内层」正则，把括号里那一串表达式拆开——里面可能藏着取负号、字段路径（还能用点遍历 `a.b.c`）、数学运算、日期格式（`>格式`）、备选字段、替换、默认值。拆完之后沿路径去字典里取值、取负、算数学、做日期格式化，最后按类型字符做一次转换。算完的标量结果，塞进那张扁平取值表；同时，把模板里原来那个复杂的占位符，**改写**成一个只引用扁平表某一条的纯占位符。

**第二关：代入期（宿主格式化）**。所有占位符都过完第一关后，模板已经被改写成「宿主认得的格式串 + 一张扁平表」。这一关就一件事：让宿主做格式化代入，宽度、精度、对齐全在这里生效。

一条占位符的生命周期，用流程图看就是：

```
模板 %(upload_date>%Y-%m-%d)s          ──外层正则命中──▶  编译回调
   │
   │  内层正则拆出：字段=upload_date, 日期格式=%Y-%m-%d
   │  沿路径取值 → '20230101' → 按日期格式化 → '2023-01-01'
   ▼
扁平表 { '\0k0': '2023-01-01' }   ＋   改写后占位符 %(\0k0)s
   │
   └──────────── 代入期：宿主照扁平表填进去 ────────────▶  '2023-01-01'
```

用一个完整的执行轨迹走一遍，你会看得更清楚。输入是一条模板和一份字典：

```
模板：%(upload_date>%Y-%m-%d)s - %(title).30s.%(ext)s
字典：{ upload_date: '20230101', title: 'This Video Title Is Deliberately Very Long', ext: 'mp4' }
```

过第一关，三个占位符分别被处理：

- `%(upload_date>%Y-%m-%d)s`：取值 `'20230101'`，按日期格式化成 `'2023-01-01'`，塞进扁平表；占位符改写成 `%(\0k0)s`。
- `%(title).30s`：取值那个长标题，**原样**塞进扁平表——注意那个 `.30` 引擎根本没处理，它被原样透传；占位符改写成 `%(\0k1).30s`。
- `%(ext)s`：取值 `'mp4'`，塞进扁平表；改写成 `%(\0k2)s`。

于是第一关产出的中间态长这样：

```
改写后模板：%(\0k0)s - %(\0k1).30s.%(\0k2)s
扁平取值表：{ '\0k0': '2023-01-01', '\0k1': 'This Video Title Is Deliberately Very Long', '\0k2': 'mp4' }
```

过第二关，宿主拿着这张表去填改写后的格式串。`.30` 这时候才派上用场——它把标题截到 30 个字符（`This Video Title Is Deliberate`），日期和扩展名直接照填。最终输出：

```
2023-01-01 - This Video Title Is Deliberate.mp4
```

整条轨迹的妙处就在 `title` 那一项：**日期格式化是引擎在第一关算好的，但精度截断是宿主在第二关才做的。** 引擎清楚地知道，哪些活该自己干（取值、类型转换这些它自定义的语义），哪些活该甩给宿主（宽度、精度、对齐这些宿主本来就有的能力）。

## 四、四十行演透两阶段

空讲不如跑一遍。下面这段 JavaScript，从零实现了上面那条流水线，你能在 `node` 里直接跑通。它故意把能省的都省了——不碰文件名净化、不碰那些自定义类型转换字母、不碰数学和备选链——只保留「拆字段 → 取值 → 塞扁平表 → 改写成宿主占位符 → 代入」这条主干，好让你看清两阶段的分界线到底画在哪。

```js
// outtmpl.mjs —— 最小输出模板引擎：编译期 + 代入期
const OUTER = /%\(([^)]+)\)(\d*\.?\d*)?([a-zA-Z])/g   // 外层：拆 %(...) 占位符
const INNER = /([\w.]+)(?:>(.+))?/                    // 内层：字段路径 / >日期格式

// 沿点路径从字典取值：a.b → dict.a.b（本章简化，不展开切片与备选）
const lookup = (dict, path) =>
  path.split('.').reduce((d, k) => (d == null ? d : d[k]), dict)

// 日期格式化（演示版：把 YYYYMMDD 按占位重组）
const fmtDate = (raw, fmt) =>
  /^\d{8}$/.test(raw)
    ? fmt.replace('%Y', raw.slice(0, 4)).replace('%m', raw.slice(4, 6)).replace('%d', raw.slice(6, 8))
    : raw

// ───── 第一关：编译期。把 模板+字典 → { 改写模板, 扁平表 } ─────
function prepare(tmpl, dict) {
  const table = {}
  let n = 0
  const template = tmpl.replace(OUTER, (_all, expr, size, type) => {
    const [, field, dateFmt] = expr.match(INNER)         // 拆表达式
    let value = lookup(dict, field)                      // 沿路径取值
    if (value == null) value = 'NA'                      // 缺失兜底
    value = dateFmt ? fmtDate(String(value), dateFmt) : String(value)  // 编译期就算完
    const key = `\0k${n++}`                              // NUL 打头，防与模板正文撞车
    table[key] = value                                  // 标量塞进扁平表
    return `%(${key})${size || ''}${type}`              // 改写成纯宿主占位符，size 原样透传
  })
  return { template, table }
}

// ───── 第二关：代入期。JS 没有 %(...)s，自己写个 ~5 行的「宿主代入器」 ─────
// 它的存在恰恰证明：代入期平庸到只需 String.replace。
function hostSubst(template, table) {
  return template.replace(/%\(([^)]+)\)(\d*\.?\d*)?s/g, (_all, key, size) => {
    let v = table[key] ?? ''
    if (size?.startsWith('.')) v = v.slice(0, Number(size.slice(1)))  // 精度截断，留到代入期
    return v
  })
}

// ───── 跑一遍：和上面执行轨迹完全对应 ─────
const tmpl = '%(upload_date>%Y-%m-%d)s - %(title).30s.%(ext)s'
const info = { upload_date: '20230101', title: 'This Video Title Is Deliberately Very Long', ext: 'mp4' }

const { template, table } = prepare(tmpl, info)
console.log('改写后模板:', template)   // %(\0k0)s - %(\0k1).30s.%(\0k2)s
console.log('扁平取值表:', table)      // 三个 key 都 NUL 打头，值在编译期已算好
console.log('最终输出 :', hostSubst(template, table))  // 2023-01-01 - This Video Title Is Deliberate.mp4
```

配一个最小的 `package.json`，`node outtmpl.mjs` 就能跑：

```json
{ "name": "outtmpl-demo", "type": "module", "version": "1.0.0" }
```

盯住那行 `if (size?.startsWith('.'))`——它不在第一关的 `prepare` 里，而在第二关的 `hostSubst` 里。这就是整章的精髓：**`.30` 这种宿主语义，引擎在第一关只管透传，到第二关才由宿主解释。** 而日期格式化那种自定义语义，则必须、也只能在第一关就处理掉，因为宿主根本不认识 `%Y-%m-%d`。引擎对每个字符该归谁管，分得清清楚楚。

## 五、关键权衡：三个不能不说的选择

本章机制集中，下面挑三条最值得记住的展开——其中前两条是原理核心和安全命门，第三条呼应开头「一处投影、多处复用」的动机。

### 权衡一：编译而非解释——换来宿主能力，代价是急切求值 + NUL 隔离

**选择**：不边扫边查字典（解释），而是先把每个字段在编译期**全部求值**完，结果塞进一张扁平表，模板改写成只引用这张表的纯格式串，最后一步交给宿主格式化。

**换来**：宿主语言自带的那一整套格式化能力（宽度、精度、零填充、左右对齐），引擎一分钱不花就继承下来——`fmt` 片段原样透传，第二关宿主替你生效。引擎因此永远不用自己写「文本代入器」，只写「取值器」就够了。

**代价**：既然要预编译成扁平表，模板里每个字段就**没法惰性求值**——不管这条字段最后用不用得上，都得在编译期老老实实算好塞进表里。模板里若引用了一个会触发副作用的取值，或是代价昂贵的派生字段（比如要把整段字幕拼出来），就算最终输出根本不需要它，这笔账也已经付了。而且为了把「字段值」塞进「宿主格式串」这套机制，源码用了一个相当 hacky 的技巧：拿 NUL 字符（`\0`）给扁平表的 key 打头做隔离，key 里若出现 `%` 还要替换成 `%\0` 防止和外层宿主的 `%` 语法打架——演示代码里那行 `` `\0k${n++}` `` 就是它的缩影。这套字符把戏能跑，但头一次读的人保准得愣一下。

### 权衡三：exec 安全门——命令模板只许少数转换类型

**选择**：当模板是给 `--exec` 命令用的（即最终要交给 shell 执行），引擎在**后处理器注册期**就跑一次带安全标记的编译：只允许 `difq` 这少数几种安全的转换类型；占位符里的默认值，也不得包含引号、空白、`;&|$<>()` 这类 shell 元字符。任何一条违例，立刻抛错并附上安全公告链接，整个命令直接拒发。

**换来**：这条模板可以**放心地交给 shell 执行**——你不用担心视频标题里夹个 `;rm -rf` 就被 shell 解释成两条命令。安全检查集中在注册期做完一次，运行期解析命令时不再重复校验，开销也低。

**代价**：命令模板的表达力被**刻意削掉一截**。你想在命令里用 `%(title)S`（文件名净化）或 `%(formats)j`（JSON 序列化）这类转换？不行，它们不在 `difq` 白名单里。要解禁，必须显式开启一个标了「不安全」的兼容项，等于主动放弃这层保护。换句话说，它把「默认安全」摆在「默认好用」前面——对一个会把字符串喂给 shell 的功能，这个取舍是站得住的。

### 权衡五：一处引擎，投影出七种字符串

**选择**：上面这台「编译 + 代入」的投影机，只写了一份，却被文件名、控制台打印、下载进度行、终端标题栏、后处理进度、元数据解析、章节标题、exec 命令**七个地方**复用。它们喂给引擎的都是同一条 info_dict，要的只是不同的模板和不同的后处理开关。

**换来**：「命名、进度、命令其实都是同一种元数据投影」这种一致性。你学会了 `%(title)s` 这套语法，就同时学会了怎么定制文件名、怎么改进度条格式、怎么写下载后命令——一套语法走天下。第一节里说的「几处各写一套取值逻辑」的灾难，被这单一入口彻底化解。

**代价**：这台引擎因此**同时背负了好几种彼此正交的模式**——做文件名时要按平台净化非法字符、限制字符集；做命令时要过 exec 安全门；做进度时还要处理一层嵌套子字典（进度模板靠 `progress._default_template` 这种点路径取默认模板）。这些模式本可以拆成独立模块，却挤在同一个求值入口里，单函数体膨胀到数百行。好处是入口统一、行为可预测；坏处是，你想读懂其中任何一种模式，都得起把整台机器过一遍。

## 六、小结

回到开头那台投影机。它最该被记住的，不是那套复杂到吓人的模板语法，而是一个干净的二分：**自定义的语义（取值、取负、数学、日期、类型转换）在编译期做完，宿主原生的语义（宽度、精度、对齐）在代入期交给宿主。** 引擎只写取值器、不写代入器，宿主的能力一分钱不花就继承过来——代价是急切求值和一套 NUL 字符把戏。命令那一路额外加了道白名单安全门，宁可削能力也要保证能安全喂给 shell。
