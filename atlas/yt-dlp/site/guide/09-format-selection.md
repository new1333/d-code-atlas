# 格式选择 DSL：从 `-f` 串到选择器 AST

## 当你有几十种格式，却只想说一句话

打开一个视频站点，它往往同时甩给你几十种格式：纯视频轨、纯音频轨、预合并好的整体文件、各种分辨率和编码、还掺着带 DRM 的和预览用的 storyboard 图。你心里其实只有一句话：

> 「我要 720p 以下最好的，音视频分开下，下载完合并；实在不行，就给我一个整体文件得了。」

如果没有专门的语言，你得为这一句话写一段命令式的代码：遍历所有格式、逐个比分辨率和码率、判断有没有视频轨、再处理「没有分离轨就退而求其次」的回退……而且每个站点对「最好」的定义还都不一样。本章要讲的就是：yt-dlp 怎么用一行声明式的 `-f` 串，把「挑格式」这件高度条件化的事讲清楚。

先点一句定位（这点上一章讲透了，不重复）：格式选择是对那条 info_dict 数据总线做的一次纯变换——读字典里的 `formats` 列表，返回一个子列表或一个合成出来的新格式，全程不改外部状态。本章只盯它的新侧面：**这一行字符串是怎么被编译成对列表的「位置运算」的，以及为什么「选格式」被刻意做成「只取下标、从不比较」**。

## 一个反直觉的事实：选择器自己从不比较

打个比方。想象超市货架已经被理货员按「从差到好」摆好了，最差在左、最好在右。这时候来个顾客，他说「给我最好的那个」「给我最差的那两个」「给我中等偏上的」——他全程没自己掂量过任何一件商品的好坏，他只是在已经排好的货架上**指位置**。

yt-dlp 的格式选择就是这套思路。整套机制可以浓缩成一句可能反直觉的话：

**选择器自己从来不比较任何两个格式。** 它先让一个独立的排序器把所有候选排成唯一的基准序，然后只做「取第 N 个」的位置运算。门外汉以为在选择器里发生的所有「比较分辨率、比较码率、比较编码」，其实全部发生在排序器里；选择器拿到货时，货架已经摆好了。

记住这个拆分，后面每一段都在讲它怎么落地。

## 基准序：货架是怎么摆的

排序器的活是按大约 19 个键把候选排成一条唯一的「从差到好」升序——索引 0 是最差的，末尾是最好。注意这个方向：**升序、最差在前**。它决定了后面所有「取下标」的方向，是全章最容易看反的地方。

这 19 个键里有：有没有视频轨、提取器自己的偏好、语言、分辨率、帧率、是不是 HDR、编码偏好（哪种编码算更好）、总码率、协议、扩展名……其中有些是直接比大小（分辨率），有些是查一张人为排好的「有序表」——比如编码偏好不是比数值，而是查顺序表（av01 排在 vp9.2 前面，再排在 h265 前面），按「在表里的位次」打分。这让「哪种编码更好」变成一张可配置的表，而不是硬编码的数字。

这里有个很巧的设计：这 19 个键语义五花八门——有的要大、有的要小、有的要「最接近某个限值」、有的缺失值要排最后。但它们全被编码成同一种东西，一个元组。比如「最接近限值」被编成 `(0, -abs(值 - limit))`（离限值越近、负数的绝对值越小、排得越靠后即越好），「缺失值排最后」编成 `(-10, 0)`。于是最后只需要一个 `sort()`，就能同时处理所有键各自的语义，不用为每种语义写一段比较逻辑。

这一步发生在很早，**在任何选择动作开始之前**。它要是没跑、或者候选格式缺了字段（协议、扩展名、码率这些得提前补全），后面取的所有下标都是错的。

## 原子选择：过一道筛子，然后取第 N 个

货架摆好了，最底层的选择动作长什么样？用户说一个「规格符」，比如 `best`、`bestvideo`、`worstaudio`、`best.2`（第二好）。选择器对它只做三件事：

1. **过筛子**：用一个过滤函数把不满足的候选剔掉。`bestvideo` 的筛子是「视频轨有、且音频轨为 none」（纯视频轨）；`best` 的筛子是「视频音频都得有」（预合并的整体文件）；`best.2` 和 `best` 用同一把筛子，只是取的下标不同。
2. **按方向决定要不要把列表反过来**：因为基准序是升序（最差在前），取「最好」就要先把列表倒过来再取第 0 个；取「最差」就直接取第 0 个。代码里就是 `best` 把方向标志置真、列表 `[::-1]` 反转。
3. **取第 N 个**：`best` 取下标 0，`best.2` 取下标 1（下标从 1 开始数，所以是「第 N 个减 1」）。

这三步里**没有一处比较**。它过筛子、它反转、它取下标——就是几个机械动作。「哪个更好」是排序器在第一步已经替它定好的。

`best` 和 `bestvideo` 的区别，全在筛子的宽松度上：`b`（写成 `best`）默认要求同时有视频和音频；`bv`（`bestvideo`）要求「视频轨有、音频轨是 none」，只挑纯视频轨；`bv*`（加个星号）表示「容错」——视频轨有就行，站点没有纯视频轨时可以退回去匹配预合并的整体文件。星号改的不是排序逻辑，而是筛子松不松。

## 把一行串拆成一棵小树

原子选择只能表达「取一个」。但用户要的是组合：「要分离的最好视频 + 最好音频，否则退回单个最好」。这需要 `+`（合并）和 `/`（兜底）两个运算符。

那么这一行串，比如 `bestvideo+bestaudio/best`，是怎么变成可执行的东西的？分两步：先切成 token（词法），再拼成一棵 AST（语法）。

**词法上，这里借了宿主语言自带的切词工具。** 这是个挺取巧的选择——不自己写词法器，直接拿 Python 标准库的 `tokenize` 来切。`tokenize` 本来是给 Python 代码切词用的，它本来就能识别「这是个名字」「这是个数字」「这是个运算符」，还能告诉你每个 token 在第几列——错误信息能带光标定位，白捡。但代价是这工具是为另一种语言做的，得打补丁修补语义偏差（下面权衡会细说）。

**语法上，用「嵌套层次」天然表达优先级。** 解析器产出的 AST 只有四种节点：原子（SINGLE）、合并（MERGE）、兜底（PICKFIRST）、分组（GROUP），每种节点上还能挂一串过滤器。解析函数分三层嵌套，最内层处理 `+`（合并），外层处理 `/`（兜底）。内层函数遇到不属于自己这层的运算符（比如碰到了 `/`），就把刚读的那个 token「吐回去」（退一个计数器）、让自己 break，留给外层处理。于是 `a+b/c` 会被理解成「先合并 a 和 b，再和 c 兜底」——`+` 自然比 `/` 结合得更紧，不需要单独维护一张优先级表。

`bv+ba/b` 解析完是这样一棵树：

```
            兜底(/)
           /        \
      合并(+)        原子(b)
      /     \
原子(bv)  原子(ba)
```

## 把每个节点编译成一个闭包

AST 拿到了，怎么执行？这里又是一个取巧的选择：**不写一个运行时边走树边解释的解释器，而是在构造期把 AST 的每个节点编译成一个闭包**。求值时，就是对最外层闭包的一次普通调用，没有「遍历树」的开销。

每种节点的闭包干的事很直接：

- **原子**：就是上一节那三步——筛子、反转、取第 N 个。
- **合并（`+`）**：把左右两路选择的结果做笛卡尔积，对每一对凭空造一个「合成格式」。
- **兜底（`/`）**：把几个分支依次试一遍，第一个返回非空的就采用，后面不再试。
- **分组**：透传，把括号里的选择器原样交给上一层。
- **逗号列表**：逐个把每个选择器的结果吐出来（这是「下载多个格式」的来源）。

过滤器作为最外面的一层包裹：在真正调原子闭包之前，先用所有过滤条件一道道把候选收紧。比如 `[height<=720]` 就先把高于 720 的全删掉，剩下的才进原子去取下标。换言之，**筛子收紧候选，是在取下标之前完成的**。

## 合并不是真下载，是凭空造一个「假格式」

这里有个特别容易误解的点：用户写 `bestvideo+bestaudio`，看起来像「下载视频、下载音频、把它们合起来」。但在选择阶段，**合并一个字节都没下载**。

`+` 的闭包做的事是：把「最好的视频轨」和「最好的音频轨」这两个格式，在内存里拼出一个全新的格式字典——给它在两路之间挑一个兼容的输出容器扩展名、把两路的码率加起来、记下「这两路是它的原始来源」。这个拼出来的字典是个「虚构格式」，它假装自己是一个真格式，混在结果里往下游走。真正的合并下载，是被推迟到很后面的后处理阶段才做的。

说白了，选择阶段只负责「定下来要哪几路」，合并动作本身被刻意推走，让选择逻辑保持干净。

## 一段从零实现的演示

下面这段 TS 把前面三条原理演透：①排序产出基准序、选择只取下标；②三种 AST 节点编译成闭包；③筛子在取下标前先收紧候选。每一处标注它演的是哪条权衡。为了保持小巧，词法用一个 4 行正则手写（真实实现借了 `tokenize`，这点下面权衡会讲），并省略了 `*` 容错修饰符和约 19 键的完整排序。

```ts
// format-selector.ts
type Fmt = {
  id: string;
  vcodec: string; // 'none' = 无视频轨
  acodec: string; // 'none' = 无音频轨
  height: number;
  tbr: number;    // 总码率 kbps
};

// ──【权衡①】排序器：独立产出「从差→好」升序基准序 ──
// 真实实现是约 19 个键；这里用「有视频优先 + 分辨率 + 码率」演示多键排序。
// 升序 ⇒ 索引 0 = 最差，末尾 = 最好。
function sortFormats(fs: Fmt[]): Fmt[] {
  const hasVideo = (f: Fmt) => (f.vcodec !== 'none' ? 1 : 0);
  return [...fs].sort(
    (a, b) =>
      hasVideo(a) - hasVideo(b) // 1. 有视频的排后面（更好）
      || a.height - b.height    // 2. 分辨率高的排后面
      || a.tbr - b.tbr,         // 3. 码率高的排后面
  );
}

// ──【权衡③】AST 三种节点（真实有四种，演示省略分组 GROUP）──
type Node =
  | { t: 'single'; spec: string }        // 原子：best / bv / ba / worst
  | { t: 'merge'; a: Node; b: Node }     // 合并：A + B
  | { t: 'fallback'; a: Node; b: Node }; // 兜底：A / B

// 极简词法（真实实现借 tokenize，这里用正则只为保持演示小巧）
function tokenize(s: string): string[] {
  return s.match(/[^+/]+|[+/]/g) ?? [];
}

// 递归下降解析：嵌套层次天然编码优先级——
// 内层 merge() 处理 +，外层 expr() 处理 /，故 + 比 / 结合更紧。
function parse(tokens: string[]): Node {
  let i = 0;
  const atom = (): Node => ({ t: 'single', spec: tokens[i++] });
  const merge = (): Node => {
    let n = atom();
    while (tokens[i] === '+') { i++; n = { t: 'merge', a: n, b: atom() }; }
    return n;
  };
  const expr = (): Node => {
    let n = merge();
    while (tokens[i] === '/') { i++; n = { t: 'fallback', a: n, b: merge() }; }
    return n;
  };
  return expr();
}

// 原子的「筛子」：best 要音视频都有；bv 要纯视频轨；ba 要纯音频轨。
function sieve(spec: string): (f: Fmt) => boolean {
  if (spec.startsWith('bv')) return (f) => f.vcodec !== 'none' && f.acodec === 'none';
  if (spec.startsWith('ba')) return (f) => f.acodec !== 'none' && f.vcodec === 'none';
  return (f) => f.vcodec !== 'none' && f.acodec !== 'none'; // best / worst
}

// ──【权衡①落地】求值：每节点编译成闭包，取值是纯位置运算 ──
// ──【权衡④】合并：笛卡尔积 + 凭空造合成字典（一个字节都没下载）──
function compile(node: Node) {
  const run = (n: Node, ctx: { formats: Fmt[] }): Fmt[] => {
    if (n.t === 'single') {
      const fs = ctx.formats.filter(sieve(n.spec));               // 1. 筛子收紧
      const ordered = n.spec.startsWith('b') ? [...fs].reverse() : fs; // 2. best 反转
      return ordered.slice(0, 1);                                 // 3. 取第 1 个
    }
    if (n.t === 'merge') {
      const a = run(n.a, ctx), b = run(n.b, ctx);                 // 左右各选一路
      return a.flatMap((v) =>                                     // 笛卡尔积 → 合成字典
        b.map((au) => ({
          id: `${v.id}+${au.id}`, vcodec: v.vcodec, acodec: au.acodec,
          height: v.height, tbr: v.tbr + au.tbr,
        })),
      );
    }
    // fallback：依次试，第一个非空即返回（用户感知到的「优雅降级」就在这）
    const a = run(n.a, ctx);
    return a.length ? a.slice(0, 1) : run(n.b, ctx).slice(0, 1);
  };
  return (ctx: { formats: Fmt[] }) => run(node, ctx);
}

// ── 跑一遍：选择器对「更好」一无所知，全靠 sortFormats 先把序排好 ──
const candidates: Fmt[] = [
  { id: '137', vcodec: 'h264', acodec: 'none', height: 1080, tbr: 3000 }, // 纯视频
  { id: '140', vcodec: 'none', acodec: 'mp3', height: 0, tbr: 128 },      // 纯音频
  { id: '22', vcodec: 'h264', acodec: 'aac', height: 720, tbr: 1500 },    // 预合并整体
];
const sorted = sortFormats(candidates); // 排成「从差→好」
console.log('基准序(差→好):', sorted.map((f) => f.id)); // → 140, 22, 137

const select = compile(parse(tokenize('bv+ba/b')));
console.log('选中:', select({ formats: sorted }).map((f) => f.id)); // → 137+140
```

跟着求值走一遍：候选排成 `[140, 22, 137]`（最差在前）。AST 是 `fallback(merge(bv, ba), b)`。先试左支合并——`bv` 筛子留下纯视频轨 `[137]`、`best` 方向反转后取第 1 个得 `137`；`ba` 筛子留下纯音频轨 `[140]`、取第 1 个得 `140`；两者笛卡尔积拼出一个合成格式 `137+140`。左支非空，兜底直接返回它，右支 `b` 根本没机会跑。真正的合并下载被推迟到后处理。

换个站点，假设它只有 `22` 这一个预合并整体文件、没有任何纯轨：`bv` 筛子筛完是空列表、取第 1 个得空、合并左支整体为空 → 兜底走右支 `b`（筛子要音视频都有）→ 留下 `[22]` → 取第 1 个得 `22`。这就是 `/` 表达「实在不行就退而求其次」的真正落点。

## 关键权衡

这一章机制集中，但所有设计都围绕一个核心思路展开，下面把四条权衡讲透。

**① 排序与选择彻底分离（全章灵魂）。** 选择「用一个独立排序器产出基准序、选择器只做位置取值」，换来的是选择器逻辑极简——它根本不需要懂「什么算更好」，十几个排序键、正着排还是反着排、要不要逼近某个限值、缺失值怎么处理，全部归排序器一个 `sort()` 管。选择器只会三件事：过筛子、反转、取下标。这套拆分还顺带让两种本质独立的事各归各：排序器管的是「什么算更好」（这是一次性、全局成立的），选择器管的是「我要哪种组合」（这是用户每次都不同的）。要是把它们揉进同一段代码，会得到一个既不懂偏好、又不懂语法的怪物。

代价是：正确性强依赖「排序必须先跑」这个前置条件。选择器拿到的下标对不对，全看基准序对不对；如果跳过了排序，或者运行前没给每个格式补全缺失字段（协议、扩展名、码率这些得提前回填），那么取出来的「第 N 个」就毫无意义。换句话说，这套设计把所有正确性的重量都压在了「先把序排对」这一根柱子上。

**② 复用宿主语言自带的词法器。** 选择「不自己写词法器，直接拿 Python 标准库的 `tokenize` 切词」，换来的是立刻拿到现成的词类型识别（名字、数字、运算符）和列位置信息——错误信息能带光标定位，也不必自己维护一套独立文法。这是一个典型的「能借就不造」的取舍。

代价是借来的工具是为另一种语言（Python 代码）做的，语义对不上时得用 hack 修补。真实代码里留了两个补丁和一个 TODO：其一，Python 3.12 换了底层解析器，会把 `7_a` 这种串判为非法，于是给所有数字串前面加一串 32 位随机字母前缀来骗过解析器、切完词再剥掉；其二，得把「非特殊运算符」重新粘回相邻字符串，让 `mp4-baseline-16x9` 成为一个完整的名字原子而不是三个 token。代码注释里甚至直白地写着 TODO，希望有一天换掉 `tokenize`、自己写一个不依赖它的解析器。换句话说，省下来的工作量，被慢慢偿还成了对这些补丁的长期维护。

**③ 先建 AST 再把每个节点编译成惰性闭包。** 选择「解析阶段产出一棵固定的小树，求值阶段把每个节点编译成一个生成器闭包，选择时就是原生迭代、没有运行时树遍历解释器」，换来的是求值零分发开销——求值时不会反复判断「现在这个节点是什么类型」，每个节点在编译期就已经决定了自己怎么跑。而且生成器是惰性的，配合「格式探测下载」（带 DRM 或没测过的格式，只在真正被取到时才发起网络探测），昂贵的探测天然只跑到「被选中的那个下标」为止，没被取到的候选根本不会被探测。

代价是调试困难。运行时是一摞嵌套闭包，出问题时栈不直观——你看到的是一连串内部闭包帧，而不是「这棵树的第几层第几个节点」。这种把控制流提前固化进闭包结构的写法，读起来比一个直白的解释器要费劲。

**④ 合并格式是「虚构字典」而非真实文件。** 选择「音视频合并在选择阶段不下载任何东西，而是凭空造一个合成格式字典（带兼容输出扩展名、累加码率、标注两路原始来源），交给下游阶段当真格式处理」，换来的是选择逻辑保持纯函数、与真正的混流阶段彻底解耦——选择只回答「要哪几路」，不碰任何下载细节。

代价是这个虚构格式得「骗得过」下游：它的 `protocol` 字段是两路协议用 `+` 拼出来的、`ext` 是在两路之间挑的兼容容器，下游的下载器和混流器都得容忍这种合成字段、把它当真格式对待。真正的合并动作被推迟到后处理，也就是说「合并」这个词在用户心里是一件事，在代码里却被劈成了两半——选择阶段造个占位的假格式，后处理阶段才真正动手合并。

## 小结

一行的格式选择串，背后是两层清晰的分工：排序器先把几十种格式排成一条唯一的「从差到好」基准序，选择器再在这条序上做纯位置运算——过筛子、反转、取下标，外加合并与兜底两种组合方式。它看起来在「比较」，其实从来不比较；它看起来在「合并下载」，其实只是造了个假格式。把「什么算更好」和「我要哪种组合」拆开，是这套 DSL 能用一行串表达复杂意图的根因。

定下来要哪几路之后，下一个问题自然就是：这些下载下来的文件，该叫什么名字、放到哪？这正是下一章「输出模板引擎：命名即元数据投影」要讲的——同一个 info_dict，这次被投影成文件名和进度串。
