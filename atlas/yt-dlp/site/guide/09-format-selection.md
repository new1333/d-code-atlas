# 格式选择 DSL：从 -f 串到选择器 AST

> 本章属于 composite 层。前置：info_dict 数据总线与提取器骨架。
> 学完你能：用一句话讲清"为什么这门选格式的小语言自己从不比较任何两个格式——它把『什么算更好』整个外包给了一个独立的排序器，自己只做取下标、合成、兜底"。

## 1. 为什么需要它（设计动机）

上一章把后处理写成了一条声明式流水线：每个 PP 接收 info、返回 info，链式传递。这条流水线的入口必须回答一个问题——**到底把哪一路或哪几路格式喂进去**？这个问题不解决，下游再多 PP 都是在加工一个不知道从哪选出来的东西。

打开任何一个视频站点的格式列表，几十条候选扑面而来：纯视频轨、纯音频轨、预合并的整体文件、不同分辨率/编码/容器、带 DRM 的、甚至连 storyboard 预览图都算一路。用户的意图却往往只是一句人话——"我要 720p 以下最好的，音视频分开下然后合并，实在不行给个整体文件也行"。

如果没有这门小语言，用户就得写一段命令式的代码：先按某种标准给候选排序，再判断是不是想要的类型，再处理想要的两路能不能合并，再想"实在不行"的回退该怎么写……而且每个站点的"最好"定义还不一样。把这段命令式代码硬塞进 CLI 里既不优雅也无法复用。

yt-dlp 的回答是设计一门**一行的声明式查询语言**：用户写 `bestvideo+bestaudio/best`，系统把这一行编译成一棵小 AST，对候选列表求值，挑出最终格式。**门外人以为这门语言在做格式比较，其实它从不比较**——这是本章要讲清的最关键的设计选择。

## 2. 核心思想

这门语言之所以能做到"看起来在做比较、其实从不比较"，是因为它把整个问题切成两段独立的事：**排序器先产唯一的基准序，选择器只做位置运算**。两个职责彻底拆开，排序器不懂语法、选择器不懂好坏。

## 3. 心智模型

整条链路分两段：

**排序段**——`FormatSorter` 给每个格式算一个多键元组作为 sort key，再 `formats.sort(key=...)` 把候选排成"从差→好"升序（索引 0 = 最差，末尾 = 最好）。这个方向很反直觉，但记住这一点后面所有"取下标"才看得懂。

**选择段**——用户的 `-f` 串经过三步变换：

```
串 → tokenize 切词 → 递归下降建 AST → 编译成生成器闭包 → 对 ctx 求值
```

AST 只有四种节点，全章就靠它支撑：

| 节点类型 | 写法 | 求值行为 |
|---|---|---|
| SINGLE | `best` / `worst` / `bv*` / 扩展名等原子 | 过滤候选 → 在基准序里取第 N 个 |
| MERGE | `A+B` | 两路做笛卡尔积，每对**造一个合成格式字典** |
| PICKFIRST | `A/B` | 依次试每个分支，首个非空即返回 |
| GROUP | `(A,B,C)` | 透传 / 逐个 yield |

每个节点上还能挂一串过滤器（如 `[height<=?720]`），在取下标之前先收紧候选集。

求值入口 `ctx` 是一个小字典，装着当前候选列表 `formats` 和两个开关：`has_merged_format`（有没有预合并格式）和 `incomplete_formats`（候选是不是全纯音或全纯视频）——这两个开关是后面"容错回落"的钥匙。

## 4. 关键权衡

### 把"什么算更好"整个外包给排序器

用户感受的痛点是"我要 720p 以下最好的视频"，这句话里其实藏着两件本质独立的事：**一是"什么算更好"**（涉及十几个互相冲突的排序键——有没有视频、提取器偏好、语言、分辨率、帧率、HDR、编码偏好、码率、协议、扩展名）；**二是"我要哪种组合"**（单路？音视频合并？多个兜底？）。

把它们耦合在一起写，会得到一个既不懂偏好又不讲语法的怪物：每比较两个格式都得重新跑一遍偏好逻辑，每个用户的不同组合意图都得从头算一次。

yt-dlp 的选择是**把两者彻底拆开**——排序器一次性算好基准序，选择器只管在序上做位置取值。换来的是选择器逻辑极简：它根本不懂"更好"是什么意思，无论用户要 best 还是 worst、要第几好、要带什么过滤器，本质都只是"在已排序列表里取下标 N"。代价是正确性强依赖排序必须先跑、且依赖运行前给每个格式回填缺失字段（协议、扩展名、码率），否则取的下标全是错的。

这条权衡化解的本质矛盾是**全局成立的多键排序 vs 每次都不同的声明式意图**——前者算一次复用所有人，后者用最薄的位置运算表达即可。

### 借宿主语言的词法器，给数字串打补丁

写 DSL 的人第一反应往往是"我得自己写个词法器"。yt-dlp 直接拿了 Python 标准库的 `tokenize`：把选择串当 Python 表达式切词，立刻拿到 NAME / NUMBER / OP 词类型和列位置，错误信息能带光标定位。

但 `tokenize` 是为 Python 代码设计的，不是为格式选择串。比如 `mp4-baseline-16x9` 在 Python tokenize 看来会被切成三个 token；又比如 Python 3.12 的解析器会拒收 `7_a` 这类数字串。yt-dlp 用两个 hack 修补这种语义偏差：`_remove_unused_ops` 把"非特殊运算符"（如 `-`）重新粘回相邻字符串让原子保持完整；给所有数字串加 32 位随机字母前缀绕过 3.12 解析器，tokenize 后再剥掉（代码注释里直接标了 `HACK` 和 `TODO 将来换掉它`）。

选择"借"换来的是不必维护一套独立文法，错误位置开箱即用；代价是借来的工具是为另一种语言做的，得用 hack 修偏差，而且代码作者自己都觉得这条路长久走不通。**化解的本质矛盾是 DSL 解析的复杂度 vs 不愿为了一门小语言重新发明词法轮子**。

### AST 先建好、再编译成惰性生成器闭包

求值阶段没有"运行时树遍历解释器"。解析阶段产出一棵四种节点的 AST，构造期（或首次选择时）每个节点被 `_build_selector_function` **编译成一个 Python 生成器闭包**，选择时就是原生生成器迭代。

这个设计带来两个红利。第一个是**求值零分发开销**：运行时没有 `switch(node.type)` 的解释循环，每个节点直接是一段 Python 代码。第二个更妙——**生成器的惰性天然把昂贵的格式探测藏了起来**：候选列表是 `LazyList`，配合 `_check_formats` 的"探测下载"，只有真正被取到的下标才会触发对带 DRM / 未测格式的网络探测；用户写 `bestvideo/best`，如果 `bestvideo` 命中，`best` 那一路根本不会被探测。

代价是调试困难：运行时是一摞嵌套闭包，错误栈不直观，断点打不到树节点上。**化解的本质矛盾是 DSL 的可读结构 vs 高频求值的性能要求**——用编译期换运行时，结构只在解析阶段存在。

### 合并格式是"虚构字典"，不是真实文件

用户写 `bestvideo+bestaudio` 时，他以为系统当场把两路下载下来合并了。其实没有。MERGE 节点的求值只是对左右两路做笛卡尔积，对每对**凭空造一个合成格式字典**：`requested_formats=[视频, 音频]`、扩展名由 `get_compatible_ext` 选一个兼容容器（比如 mp4）、tbr 累加、视频字段从视频轨取、音频字段从音频轨取。

这个虚构格式被原封不动地塞回 info_dict.formats，让下游阶段当真格式处理——真正的混流动作被推迟到后处理流水线（上一章那条 PP 链里的 `FFmpegVideoConvertor` / `FFmpegMergerPP`）。选择阶段不下载任何东西、不做任何 IO，是 info_dict 上的纯变换。

换来的是选择逻辑彻底纯化、与下载和混流阶段完全解耦；代价是这个虚构格式要"骗得过"下游——`protocol` 字段是两路协议用 `+` 拼接、扩展名是兼容容器，下游必须容忍这种合成字段。**化解的本质矛盾是用户视角的"合并"（一步到位）vs 内部架构的阶段分离**（选择、下载、混流必须可独立测试与调度）。

## 5. 最小原理演示

下面几十行 TS 把上面四条权衡各演一段：排序器独立产基准序、四种 AST 节点编译成生成器闭包、过滤器在取下标前先收紧候选、合并是笛卡尔积 + 合成字典。词法分析这里**故意手写极简版**以保持小巧——真实实现借了 Python 标准库的 `tokenize`，但那是 Python 特有便利，TS 演示不必复刻。

```ts
type Fmt = {
  id: string;
  vcodec: string;   // 'none' 表示无视频轨
  acodec: string;   // 'none' 表示无音频轨
  height: number;   // 0 表示无视频
  tbr: number;      // 总码率 kbps
};

// 排序器：独立产出「从差→好」升序基准序；选择器后续只信它，自己从不比较。
// 真实实现是 ~19 键的多键元组比较；这里用「有视频优先 + 分辨率 + 码率」演示多键排序的方向
function sortFormats(fs: Fmt[]): Fmt[] {
  return [...fs].sort((a, b) =>
    Number(a.vcodec !== 'none') - Number(b.vcodec !== 'none') ||
    a.height - b.height ||
    a.tbr - b.tbr,
  );
} // 升序 ⇒ 索引 0 = 最差，末尾 = 最好

// 四种 AST 节点（演示用三种：single / merge / fallback；GROUP 透传同理省略）
type Node =
  | { t: 'single'; spec: string; filter?: (f: Fmt) => boolean }
  | { t: 'merge'; a: Node; b: Node }
  | { t: 'fallback'; a: Node; b: Node };

// 极简手写词法 + 递归下降：merge 比 fallback 结合更紧，由嵌套层次天然表达。
// 真实实现借 tokenize 切词——这里刻意简化以聚焦解析结构
function parse(tokens: string[]): Node {
  let i = 0;
  const atom = (): Node => ({ t: 'single', spec: tokens[i++] });
  const merge = (): Node => {
    let n = atom();
    while (tokens[i] === '+') { i++; n = { t: 'merge', a: n, b: atom() }; }
    return n;
  };
  const expr = (): Node => {
    let n = merge();
    while (tokens[i] === '/') { i++; n = { t: 'fallback', a: n, b: merge() }; }
    return n;
  };
  return expr();
}

// 把每个 AST 节点编译成惰性闭包：返回 formats[] → Fmt[]
// single 节点先按过滤器收紧候选、再在基准序里取下标（位置运算，非比较）
function compile(n: Node) {
  const run = (n: Node) => (formats: Fmt[]): Fmt[] => {
    if (n.t === 'single') {
      // 过滤器作为最外层包裹：取下标前先收紧候选
      const fs = n.filter ? formats.filter(n.filter) : formats;
      // best 反转后取末尾的「末尾」= 最好；worst 直接取末尾的「开头」= 最差
      const rev = n.spec.startsWith('best');
      const ord = rev ? [...fs].reverse() : fs;
      return [ord[0]].filter(Boolean);
    }
    if (n.t === 'merge') {
      // 笛卡尔积 + 凭空造合成字典（不下载、不 IO）
      const a = run(n.a)(formats);
      const b = run(n.b)(formats);
      return a.flatMap(v =>
        b.map(au => ({ ...v, ...au, id: `${v.id}+${au.id}`, tbr: v.tbr + au.tbr })),
      );
    }
    if (n.t === 'fallback') {
      // 兜底：左支非空就返回它；否则走右支（用户用 / 表达优雅降级的地方）
      const a = run(n.a)(formats);
      return a.length ? a.slice(0, 1) : run(n.b)(formats).slice(0, 1);
    }
    return [];
  };
  return run(n);
}

// 演核心思想：选择器对「更好」一无所知，全靠 sortFormats 给的序
const sorted: Fmt[] = sortFormats([
  { id: '137', vcodec: 'h264', acodec: 'none', height: 1080, tbr: 5000 }, // 纯视频
  { id: '140', vcodec: 'none', acodec: 'mp4a', height: 0,    tbr: 128  }, // 纯音频
  { id: '22',  vcodec: 'h264', acodec: 'aac',  height: 720,  tbr: 1500 }, // 预合并
]);
// 用户的选择串：bv + ba / b ——「尽量要分离的最好视频 + 最好音频，退化到单个最好」
const selector = compile(parse('bestvideo + bestaudio / best'.split(' ')));
console.log(selector(sorted));
// 预期：一个合成字典 { id: '137+140', vcodec: 'h264', acodec: 'mp4a', tbr: 5128, ... }
```

跑一下你能看到：选择器从头到尾没出现一次 `a.height > b.height` 这样的比较——所有"哪个更好"的判断都藏在 `sortFormats` 里，`compile` 只是按 AST 结构在已排序的数组上做"反转、取下标、笛卡尔积、首非空返回"这几样位置运算。

## 6. 执行轨迹

拿用户写 `bv*+ba/b`（"尽量要分离的最好视频 + 最好音频，退化到单个最好"）走一遍。假设站点返回三个格式，排序器已经把它们排成升序：

```
候选（已按基准序升序，从差→好）：
  [0] 140  纯音频 mp4a 128kbps
  [1] 22   预合并 720p h264/aac 1500kbps
  [2] 137  纯视频 1080p h264 5000kbps
```

**第一步——解析**：递归下降把串切成一棵 AST。`+` 在更内层处理、`/` 在更外层处理，于是 `+` 结合更紧。得到的结构是：

```
fallback(
  merge(
    single('bv*'),   // 容错最好视频：视频轨有即可，可回落到预合并
    single('ba'),    // 最好音频
  ),
  single('b'),       // 兜底：单个最好
)
```

**第二步——编译**：每个节点变成一个生成器闭包。

**第三步——求值**：从根节点 fallback 开始。

- 先试左支 merge：
  - 左支的 `single('bv*')` 在基准序里反转后取下标 0——拿到 137（纯视频，1080p）。`*` 的容错作用此时没用上，因为有纯视频轨；如果只有 22 这一种预合并格式，`bv*` 会因为"视频轨有"匹配上它（这就是用户感受到的"自动容错"的真正实现处）。
  - 右支的 `single('ba')` 反转后取下标 0——拿到 140（纯音频）。
  - merge 笛卡尔积：`[(137, 140)]`，对每对造合成字典 `requested_formats=[137, 140]`、扩展名取兼容容器（mp4）、tbr = 5000 + 128 = 5128。
- merge 返回非空，fallback 不再试右支，直接返回这个合成字典。
- 若站点只有 22 这一种预合并格式、没有任何纯轨：左支 merge 里 `bv*` 落到 22、`ba` 也落到 22，merge 笛卡尔积给 `[(22, 22)]`——但这种"自己跟自己合并"的合成字典下游通常不接受，得靠 `incomplete_formats` 标志在更上层把它判为空，从而触发 fallback 走右支 `single('b')` 拿到 22。

真正的混流（用 ffmpeg 把 137 和 140 合成一个 mp4）本章不展开——那是上一章那条 PP 链里 `FFmpegMergerPP` 的活。

## 7. 教学简化说明

本章演示**故意省略**了这些东西，它们是工程上的真实复杂度但不影响理解原理：

- 排序器的完整 ~19 键多键元组（含 ordered 类型按正则位次排名、closest 限值、字段缺失档位）
- 借 tokenize 切词的 3.12 兼容 HACK（给数字串加随机字母前缀）和 `_remove_unused_ops` 把 `-` 粘回字符串
- `bv*` / `ba*` / `b*` 三种 `*` 修饰符与 `incomplete_formats` / `has_merged_format` 标志联动的回落矩阵
- 过滤器的字符串算子族（`^=` `$=` `*=` `~=` 正则、`!` 取反、`?` none-inclusive、文件大小后缀 `1M`）
- 运行前给每个格式回填缺失字段（协议、扩展名、码率互相推算、HEVC-over-FLV 特例罚分）
- 默认选择串如何依 ffmpeg 可合并性 / is_live / 输出到 stdout 自动决定
- `LazyList` + `_check_formats` 的"探测下载"惰性触发（这条对真实性能很关键，但演示层面看不出来）

## 8. 小结

把"什么算更好"外包给排序器、自己只做位置取值——这是这门小语言的全部门道。四种 AST 节点足够把"取下标、笛卡尔积合成、首非空兜底"这几样位置运算拼成用户能写的所有组合意图；合并是造字典、不是下文件，真正的混流留给了上一章那条 PP 链。

格式选好了，info_dict 的 `requested_formats` 字段也就定了。下一章「输出模板引擎：命名即元数据投影」就接着讲这个定下来的格式如何通过 `%(title)s-%(id)s.%(ext)s` 这样的模板投影成最终的文件名和进度串。
