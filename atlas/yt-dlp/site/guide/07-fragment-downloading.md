# 分片化下载：把长流拆成可恢复的工作单元

下载一部两小时的 HLS 视频，你以为是在传「一个文件」。但在网络那一层，它根本不是一个文件——它是几百段各自独立的小分片，每段就是一个普普通通的 HTTP 请求。

这件事的后果很烦人：连接要是断在第 89%，你下的那 89% 和剩下 11% 之间并没有一个「半截文件」能接着往下写；任意一段返回 503 或超时，整条流就宣告失败；中间还可能夹着广告段、被加密的段、甚至字幕段，各有各的处理方式。

用户要的其实是「下完能播的一个文件」，但网络只肯给你「一堆易碎的小段」。这一章要填的，就是这两者之间的鸿沟。

填法一句话点透：**把一条不可靠的长下载，看成一组可以一片一片处理的小任务——每片独立下载、独立重试、下坏可以跳过、加密可以就地解开、下完就追加进总文件并记一笔账；崩了就翻账本，从下一片接着干。**

先把这个「逐片循环 + 记账」拆开看，再用一段从零写的代码演透它，最后是四个真正决定这套设计好不好的权衡。

## 一、先把「一条长流」重新想象成「一片一片」

想象你在通关一个很长的游戏。如果中间断了只能从第一关重来，没人受得了。正常的做法是：每过一关，存一次档；下次开机，读档，从上一关继续。

分片下载干的就是这件事——**那条长长的流，被拆成了一段一段的分片；每下完一段、追加进总文件之后，就「存一次档」**。这个「档」，是一个小小的 JSON 簿记文件，里面只记一个最关键的信息：**当前已经下到第几片了**。

整个流程长这样：

```
准备阶段
  ├─ 读簿记  → 得到「已下到第几片」
  ├─ 按数据文件已有大小 → 决定 覆写 / 追加 打开
  ├─ 派生一个「被静音」的子下载器（专管抓单片）
  └─ 挂一个「把单片进度翻译成总进度」的钩子

逐片循环（核心）
  对每一片 i：
    下 → 读出字节 →（解密）→（变换钩子）→ 追加进总文件 → 把片号写回簿记 → 删掉这片临时文件
    └─ 失败？独立重试 N 次；还不行就按策略 跳过 或 中止整流

收尾
  关流 → 临时文件改名为最终文件 → 删除簿记 → 报告完成
```

说人话就是：循环每跑一圈，处理一片；每片都走一遍「下、读、解密、变换、追加、记账」；下完整条流，把临时文件扶正、把账本删掉。

这套循环有个特别好的性质：**进度是按「片」算的，不是按「字节」算的**。这听起来是小事，但它是后面所有权衡的根。下面这段代码会把这件事演透。

## 二、从零实现：一个能断点续传的分片下载器

这段 TypeScript 演示聚焦三件事：① 每追加一片就持久化「片号」簿记，中断重启后靠它跳过已下片；② 每片独立重试，实在不可得就按策略跳过；③ 用一个共享的可变标志在片边界「礼让」退出（协作式中断）。

为了把话说实，我们故意造一个刁钻场景：一条 4 片的流，**第 3 片（索引 2）第一次会失败、重试后才成功**；而且**在下完第 2 片之后，进程会被「中断」**，随后重新启动。我们要看到它从中断处续传，而不是从 0 重来。

```ts
// fragment-download.demo.mjs
import { existsSync, readFileSync, writeFileSync, appendFileSync, statSync, unlinkSync } from 'node:fs'

const DATA_FILE = 'stream.part'   // 最终拼接的总文件（临时名）
const BOOK_FILE = 'stream.ytdl'   // 簿记文件：记录当前已下到第几片

// ---- 模拟网络：拉一片。第 3 片（索引 2）首次失败、重试后成功 ----
const FETCH_TRIES = new Map<number, number>()
function fetchFragment(index: number): string {
  const n = (FETCH_TRIES.get(index) ?? 0) + 1
  FETCH_TRIES.set(index, n)
  if (index === 2 && n === 1) throw new Error('HTTP 503 Bad Gateway')
  return `<frag-${index} />`        // 假装是这一片的字节
}

// ---- 簿记：{ downloader: { current_fragment: { index } } } ----
type Book = { downloader: { current_fragment: { index: number } } }

function readBook(): { index: number; clean: boolean } {
  if (!existsSync(BOOK_FILE)) return { index: 0, clean: true }
  try {
    const b = JSON.parse(readFileSync(BOOK_FILE, 'utf8')) as Book
    return { index: b.downloader.current_fragment.index, clean: true }
  } catch {
    return { index: 0, clean: false }   // 解析失败 → 簿记损坏
  }
}
function writeBook(index: number) {
  writeFileSync(BOOK_FILE, JSON.stringify({ downloader: { current_fragment: { index } } }))
}

function dataBytes(): number {
  return existsSync(DATA_FILE) ? statSync(DATA_FILE).size : 0
}

// ---- 变换钩子：解密、字幕合并都插在这里。默认恒等（啥也不改）----
function pack(content: string, _index: number): string {
  return content
}

// ---- 逐片下载 + 独立重试。首片致命；其余片失败则返回 null（表示「跳过」）----
function downloadOne(index: number, retries: number): string | null {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return fetchFragment(index)
    } catch (err) {
      console.log(`    [片 ${index}] 第 ${attempt + 1} 次失败：${(err as Error).message}`)
      if (attempt === retries) {
        if (index === 0) throw err     // 首片致命：直接抛
        return null                     // 其余片：交给调用方按策略跳过
      }
    }
  }
  return null
}

// ---- 核心：下载一条分片序列 ----
// interrupt 是一个被外部翻转的可变标志 —— 这就是「协作式中断」
function downloadStream(
  total: number, retries: number, skip: boolean,
  interrupt: { stop: boolean }, stopAfter?: number,
): void {
  const { index: saved, clean } = readBook()
  let bytes = dataBytes()

  // 病态检测：簿记说下到第 N 片，但数据文件却空着 → 状态不一致
  const inconsistent = saved > 0 && bytes === 0
  const dirty = !clean || inconsistent
  let start = saved
  if (dirty) {
    console.log(`  [簿记] ${!clean ? '损坏' : '状态不一致'} → 从 0 重新开始`)
    if (existsSync(DATA_FILE)) { unlinkSync(DATA_FILE); bytes = 0 }
    start = 0
  }

  let append = bytes > 0   // 数据文件已有内容 → 追加；否则首片覆写
  console.log(`  [准备] 从片 ${start} 开始，${append ? '追加' : '覆写'}模式`)

  for (let i = start; i < total; i++) {
    // 片边界检查中断标志：被外部置停就在这片之前退出
    if (interrupt.stop) { console.log('  [中断] 片边界检测到停止标志，退出循环'); return }

    const content = downloadOne(i, retries)
    if (content === null) {
      if (skip) { console.log(`  [片 ${i}] 不可得，按策略跳过`); continue }
      throw new Error(`片 ${i} 不可得，整流中止`)
    }

    // 追加 → 落盘刷新 → 把片号写回簿记 → 删掉这片临时文件
    const body = pack(content, i)
    if (!append) { writeFileSync(DATA_FILE, body); append = true }   // 首片覆写，之后都追加
    else appendFileSync(DATA_FILE, body)
    writeBook(i + 1)              // 簿记记的是「已下完几片」
    console.log(`  [完成] 片 ${i} 已追加，簿记更新到 {index: ${i + 1}}`)

    if (stopAfter === i) interrupt.stop = true   // 演示用：下完这片就假装被打断
  }

  unlinkSync(BOOK_FILE)          // 收尾：删簿记
  console.log(`  [收尾] 全部完成，最终内容 = "${readFileSync(DATA_FILE, 'utf8')}"`)
}

// ---- 演示执行轨迹 ----
console.log('==== 第一次运行：下完片 1 后被中断 ====')
downloadStream(4, /*retries*/ 2, /*skip*/ true, { stop: false }, /*stopAfter*/ 1)

console.log('\n==== 第二次运行：从中断处续传 ====')
downloadStream(4, 2, true, { stop: false })
```

配一个最小的 `package.json`，`node fragment-download.demo.mjs`（或 `bun run`）就能跑：

```json
{
  "name": "fragment-download-demo",
  "private": true,
  "type": "module"
}
```

运行这段代码，你会看到：

```text
==== 第一次运行：下完片 1 后被中断 ====
  [准备] 从片 0 开始，覆写模式
  [完成] 片 0 已追加，簿记更新到 {index: 1}
  [完成] 片 1 已追加，簿记更新到 {index: 2}
  [中断] 片边界检测到停止标志，退出循环

==== 第二次运行：从中断处续传 ====
  [准备] 从片 2 开始，追加模式
    [片 2] 第 1 次失败：HTTP 503 Bad Gateway
  [完成] 片 2 已追加，簿记更新到 {index: 3}
  [完成] 片 3 已追加，簿记更新到 {index: 4}
  [收尾] 全部完成，最终内容 = "<frag-0 /><frag-1 /><frag-2 /><frag-3 />"
```

盯住这两次运行之间发生了什么：第一次下完了片 0、片 1，簿记停在 `{index: 2}`，然后被打断——**注意它没有删掉数据文件，也没删簿记**。第二次启动，读到簿记说「已下到片 2」，就直接从片 2 开始，而且数据文件以**追加**模式打开。最妙的是片 2：它第一次抓失败（模拟 503），重试一次才成功，但**这丝毫不影响总文件**——失败的只是那一片的临时抓取，重试成功后照样正常追加。

最终结果：片 0、1、3 各只下了一次，片 2 下了两次（一次失败、一次成功），总文件却是完整正确的四片拼接。这就是「把不可靠的长下载拆成可恢复的工作单元」最直接的回报。

## 三、四个关键权衡

代码不长，但藏着四个真正值钱的设计选择。挨个拆。

### 权衡一：续传记「片号」，而不是记「字节数」

你可能觉得奇怪：单文件断点续传，记一个「已下字节数」、下次发个 `Range: bytes=N-` 不就行了吗？为什么还要单独搞一个簿记文件、记「片号」？

因为分片流的「逻辑进度」不是字节数，是片数。这片是广告、要跳过；那片是加密的、要解密；还有一片是字幕、要和上一段去重合并——这些「片段级」的语义，字节数根本表达不了。而一旦你接受了「进度按片算」，就得为每一片记账：下到第几片了、这片是不是该跳过、解密信息有没有变。

**选择**：每追加完一片，立刻把「当前片号」写进那个 JSON 簿记文件。

**换来**：按「逻辑片边界」精确续传——哪怕分片是各自独立抓取再拼接的，重启后也能准确跳过已下片；而且这个簿记还能顺手承载额外状态（比如解密相关的中间量），给后面的变换钩子留接口。演示里 `writeBook(i + 1)` 就是这一步，记的是「已下完几片」。

**代价**：磁盘上多了一份必须和数据文件保持一致的簿记状态。它一坏，整个续传就不可信了。所以代码里专门检测两种病态，命中就一律从 0 重来：

- **簿记损坏**：簿记文件存在，但 JSON 解析失败（写了一半就崩了）。演示里 `readBook` 的 `catch` 就是兜这个。
- **状态不一致**：簿记说「下到第 3 片」，但数据文件是空的——账和货对不上。演示里 `inconsistent = saved > 0 && bytes === 0` 兜这个。

这两种情况都说明「账本不可信」，与其将就着用错账，不如清盘重来。这恰恰是「多一份簿记状态」这个代价的直接体现。

> 顺带一提，字节级续传其实**并没有被丢掉**：准备阶段会看数据文件已有多少字节，决定用覆写还是追加打开（演示里 `append = bytes > 0`）；单片内部也还能做字节级续传。也就是说，**字节续传（细）和片号续传（粗）是叠在一起用的**，片号决定从哪片开始，字节决定从哪个位置接着写。

### 权衡二：每片用一个「被静音的子下载器」去下

演示里 `fetchFragment` 是个模拟函数，直接就「拉到一片」。真实代码里，抓单片这件事没那么简单——它要走 HTTP、要支持 Range、要会重定向、要限速、要断点续传。这些能力第 6 章讲过的那个单文件下载器（`HttpFD`）全都有。

**选择**：不为分片另起炉灶写一套抓取逻辑，而是派生一个**关掉屏幕输出和进度条、重置各种 sleep、强制单跑**的子下载器实例，由它逐片抓到独立的临时文件里。

**换来**：完整继承既有单文件下载器的断点、Range、重定向、限速能力——这些能力是反复打磨过的成熟件，直接复用，不重新发明。同时，**屏幕和进度条的「发言权」完全归父下载器独占**：子下载器只闷头干活、不出声，父下载器负责把所有片聚合成一条总进度条。否则你会看到几百片各自刷一条进度条，屏幕直接糊掉。

**代价**：多了一层「嵌套下载器」，以及一层「进度翻译」——得把子下载器的字节级进度，映射、平滑、外推成「分片级 + 总量估算」的总进度。这层翻译不简单（要按已下片均摊估算总量），但比起把抓取逻辑重写一遍，还是划算得多。

### 权衡三：解密、字幕合并，都是插在循环里的「钩子」

回头看演示里的这一行：

```ts
const body = pack(content, i)
```

`pack` 默认啥也不改，直接返回原内容。但这个位置就是整个循环里最关键的一个「插槽」。

**选择**：核心循环对每片的字节，先过一个变换钩子（`pack`）再追加；全部结束时，再过一个收尾钩子（`finish_func`），允许最后再补写一段。

**换来**：同一条循环，既能干「原始字节拼接」的活（音视频分片），也能干「碎片化字幕合并去重 + 时间戳溢出修正」的活——而**循环本身一行都不用改**。AES-128 解密也是同一个位置：抓下来的密文，过一遍「就地解密」，再追加。换句话说，解密从来不是循环的特例，它就是「途中的一次变换」。演示里 `pack` 就是这个钩子的恒等版本，把它换成解密或字幕合并逻辑，循环骨架纹丝不动。

**代价**：当变换复杂起来（比如字幕合并要跨片去重、要维护一个滑动窗口、要修正 MPEG-TS 的时间戳溢出），这个钩子会变成一个需要跨片状态的小状态机，正确性保证起来不轻松。好在这些复杂状态可以塞进簿记的「额外状态」字段（见权衡一），跟着片号一起持久化、一起恢复。

### 权衡四：用户按 Ctrl+C，靠一个共享标志「礼让」退出

下到一半用户想停，怎么办？最粗暴的办法是直接把工作线程强杀掉。但强杀既不可靠也不安全——文件可能写了一半、资源没释放、状态没保存。

**选择**：用一个**被所有工作线程共享的可变标志位**，在每一片的边界处检查它；用户中断时，只是把这个标志「翻成假」，工作线程跑完手头这一片、自然就会察觉并退出。

**换来**：线程池能干净收尾，无需强杀；而且对**直播流**特别友好——直播被中断时，可以直接返回「已经下到的中间结果」，而不是抛异常、什么都丢掉。

**代价**：取消是**协作式**的、有延迟的。工作线程正在抓的那一片没法立刻打断，得等它跑完（甚至多跑一片）才会检查到标志、退出。演示里这个标志就是 `interrupt` 对象，循环顶部的 `if (interrupt.stop) break` 就是那个片边界的检查点；`stopAfter` 模拟的就是「外部把标志翻掉」这个动作。

## 小结

这一章的主线很单纯：**把一条不可靠的长下载，拆成一组可恢复的工作单元**。每一片独立下载、独立重试、可跳过、可解密、可变换，下完就追加进总文件并记一笔账；崩了翻账本接着干。围绕这个主线，四个权衡层层叠加：用簿记文件记片号换精确续传（代价是要维护账货一致）、用静音子下载器换能力复用（代价是多一层进度翻译）、用可插拔钩子换「一条循环多种用途」（代价是复杂变换要管跨片状态）、用共享标志换干净的中断与直播容错（代价是取消有延迟）。

还有一条线索值得点一下：本章的两个下载器（HLS、DASH），本身正是被第 6 章那个「协议字段驱动分派」机制按 `m3u8` / `dash` 协议选中的；而一旦 native 下载器发现自己搞不定（比如遇到非 AES-128 的 DRM 加密），它会主动「自报不足」，把整条下载**转交给外部工具**——这是分派机制在本章内的又一次反向应用，但本章的主角始终是架在分派之上的「分片序列」这一层抽象。
