通配符星号的第二条派发路径 ​

想监听“所有事件”，该怎么办？ ​

假设你正在排查一个诡异的 bug，想搞清楚这条事件总线上一整天到底飞了哪些事件——做日志、做调试埋点、或者干脆把所有事件原样转发到另一条总线去做 AOP 式拦截。这类需求有一个共同点：它们是“横切”的，不关心具体是 click 还是 submit，只想在任意一个事件发生时都被通知一下。

如果没有对应的能力，你就只剩两条难看的路：要么把每一个事件类型各订阅一遍（漏一个就漏一类，新增类型还得记得补），要么去改每一处派发代码，手动塞一段广播逻辑进去。读者真正想要的是——一处订阅，收所有事件，并且能知道“刚才到底是什么事件被触发了”。

前两点好懂，第三点才是关键：一个监听全部的处理器，如果收不到“这次是哪个类型”，那它基本是个瞎子，只能看见事件数据，却不知道这数据属于谁。这个诉求，决定了本章几乎所有的设计。

星号不是新东西，它是表里的一个保留键 ​

这个发射器的做法很省：不新建第二张注册表，也不新增第二套订阅接口，而是约定一个特殊的键 '*'，让它的语义就是“全部事件”。 订阅、退订、存储，全走老路，星号只是这张 Map 里的又一个普通键而已。

打个比方：这张查找表就像一块公共留言板，谁都能往上贴条；星号只是其中一块贴了“我全要”标签的格子，处理它的方式，和处理格子里写着 foo、bar 的格子没有任何两样。换句话说——想实现“监听所有事件”，作者没有为它专门盖一栋楼，而是在已有的楼里钉了个写着 * 的信箱。

这一节是全文的根。后面你会看到，正因为它“就是个普通键”，所以订阅、退订能零成本复用；也正因为它“只是个键、没有自己的独立通道”，所以派发时必须额外加一条路径去主动喊它。

订阅：对星号和普通事件一视同仁 ​

先看订阅最薄的样子。星号处理器和普通处理器，走的注册逻辑完全相同：

ts
on(type: string, h: Function) {
  const list = all.get(type);
  if (list) list.push(h);      // 已有：追加
  else all.set(type, [h]);     // 首次：建数组
}

on('foo', f) 和 on('*', g) 在这里看不出任何区别：都是“按 type 查槽位，有就 push，没有就建”。星号没有特殊的 if 分支，没有独立的存储。这一件事换来一个实打实的好处：前面讲过的惰性建表、无分支移除，星号这一路全都白用了，一行新代码都不用写。

但这里埋着一个伏笔：foo 的处理器是 f(event)，只拿事件本身；而 g 作为一个“监听全部”的处理器，光拿事件是不够的——它得知道这次到底是哪个类型。所以两种处理器的签名不一样。这个差异在订阅时不显眼，到了派发那一步就会变成主线。

派发：一趟走完，再补一趟 ​

现在到重头戏。派发 emit('foo', evt) 时，事情分两趟走，两趟各自独立、各自短路：

emit('foo', evt)
  ├─ 第一趟：all.get('foo') → 复制快照 → 每个处理器用单参 handler(evt) 调用
  └─ 第二趟：all.get('*')  → 复制快照 → 每个处理器用双参 handler('foo', evt) 调用

第一趟是老朋友：取出 foo 对应的处理器，复制一份再遍历调用。这个“先复制再遍历”的快照手法，第 5 章已经讲透——它保护你不受“处理器在派发中途自己 on/off/clear 改动当前数组”的干扰，本章不重复那个原理。我们只看它在本章的新侧面：同一次派发里，这个快照手法被调用了两次，形成两条互不干扰的派发路径。

新东西在第二趟：无论第一趟有没有命中，派发都会紧接着去查一次 '*' 这个槽位。 命中就把星号处理器也复制一份、遍历调用——但注意参数变了：每个星号处理器拿到的是 handler(type, evt)，被触发的真实类型 'foo' 被作为第一个参数补了进去。

这就是开头那个“瞎子”问题的答案：星号处理器靠这多出来的第一个参数，知道自己收到的是什么类型的事件。一处订阅、收所有事件、还能区分类型——三个诉求在这一趟里一次性满足。

两趟各自独立做快照、各自独立短路（没处理器就跳过）。于是同一次派发，会同时通知到“该类型的订阅者”和“全部事件的订阅者”；后者额外知道自己收到的是什么类型。

上手跑一遍 ​

把上面这些揉成一个能跑的最小实现：

ts
// demo.ts —— 用 bun run demo.ts 或 npx tsx demo.ts 运行
type Handler = (event: any) => void;                   // 单参：普通处理器
type StarHandler = (type: string, event: any) => void; // 双参：通配符处理器

function mitt() {
  const all = new Map<string, Function[]>();           // 一张表，星号只是其中一个键
  return {
    on(type: string, h: Function) {                    // 星号与普通事件一视同仁
      const list = all.get(type);
      if (list) list.push(h); else all.set(type, [h]);
    },
    emit(type: string, evt: any) {
      all.get(type)?.slice().forEach((h: any) => h(evt));        // 第一路径：单参
      all.get('*') ?.slice().forEach((h: any) => h(type, evt));  // 第二路径：双参，补类型
    },
  };
}

const bus = mitt();
bus.on('foo', (e: any) => console.log('foo:', e));
bus.on('*', (t: string, e: any) => console.log('star:', t, e));

bus.emit('foo', { a: 1 });  // → foo: { a: 1 } / star: foo { a: 1 }
bus.emit('bar', { b: 2 });  // → star: bar { b: 2 }

配套一份 package.json，让 npm start 也能跑：

json
{ "name": "wildcard-demo", "scripts": { "start": "tsx demo.ts" }, "devDependencies": { "tsx": "^4" } }

跟着执行轨迹走一遍，三条权衡就全活过来了：

  • 起初表是空的。订阅 foo 和星号之后，表长这样：{ foo: [f], '*': [g] }。注意它们肩并肩躺在同一张表里，没有任何分家。
  • emit('foo', {a:1})：第一趟查到 [f]，单参调用 f({a:1})；第二趟查到 [g]，双参调用 g('foo', {a:1})。一次派发，两趟各跑一次。
  • emit('bar', {b:2})：第一趟查 bar，落空，直接跳过；第二趟照样查到 [g]，调用 g('bar', {b:2})。

最后这一行最值得品：bar 根本没人订阅，但星号处理器照样被触发，还准确拿到了 'bar' 这个类型。 这正是 catch-all 的语义——它和“某个具体类型有没有人订阅”完全无关。

三个权衡，环环相扣 ​

这块是这个设计的精华。三件事，每一件都讲清了“为什么这么选”。

权衡一：复用一张表 + 保留键，而不是单建一套通配符注册表 ​

  • 选择：让星号就当表里的一个普通键。
  • 换来：通配符的订阅、退订完全复用已有的惰性建表和无分支移除逻辑，零新增代码路径。
  • 代价：占用了 '*' 这个命名空间——从此用户再也不能把星号当一个普通事件名来用，on('*', ...) 永远被解读成通配符。

说白了，作者用一个几乎零成本的约定，换掉了一整套本可以独立存在的注册、退订、遍历代码。

权衡二：通配符处理器用双参 (类型, 事件)，普通处理器用单参 (事件) ​

  • 选择：给星号处理器多塞一个“事件类型”参数。
  • 换来：监听全部的处理器能区分“是什么事件被触发了”——否则一个收所有事件的处理器拿不到类型信息，等于没用。
  • 代价：同一张表里现在并存两种签名的函数，类型层只能用联合类型把它们塞进同一个数组，派发时再分别还原。

这个代价还顺带牵出一个有趣的推论——为什么手动 emit('*') 被刻意禁止？ 想想双路径会怎样：如果你硬要触发星号类型，第一趟会拿星号处理器用单参调用一次（把类型当成事件、第二个参数直接丢了，参数全错位），紧接着第二趟又用双参正确地调用一次。同一个星号处理器被触发两次，第一次还是歪的。这不是作者任性的限制，而是“双路径 + 两种签名”这两个选择叠加后的必然结果。

权衡三：第二趟无条件执行 ​

  • 选择：每次派发都老老实实去查一次星号槽，不管有没有人订阅星号。
  • 换来：catch-all 语义确定、代码极简——不用维护“现在到底有没有人订阅了通配符”这么个标志位，也不用每次 on/off 都去更新它。
  • 代价：每次派发多一次 Map.get('*')（命中为空就立刻短路，开销小到可忽略）；以及通配符处理器固定排在类型匹配处理器之后触发，优先级不可配置。

第三点的“固定顺序”是刻在源码注释里的规则：星号处理器永远在类型匹配的处理器之后被调用。你不能让它先跑。

小结 ​

一句话收束：这个发射器用“一个保留键”和“派发时多走一趟”，零成本地长出了 catch-all 能力。 没有新数据结构，没有新订阅接口，只有一张表、两条路径、两种签名。三者的关系很干净——复用一张表，决定了“星号怎么存”；双参签名，决定了“星号处理器怎么被调用”；无条件第二趟，决定了“星号什么时候被调用”。

你可能会接着好奇：通配符处理器那个双参签名，它的类型（type 允许取哪些值、event 到底是什么类型）是怎么从用户给的那张事件映射里精确推出来的？这正是下一章《一张 Events 映射派生全 API 类型》要拆解的——一处定义，全 API 的类型都从这里长出来。
