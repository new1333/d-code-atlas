快照式派发抵御中途改表 ​

本章属于 composite 层。前置：惰性初始化的追加式订阅、无分支安全移除与重载清空。 学完你能：用一句话讲清 emit 为什么在派发前先复制一份处理器数组——为什么这么做、换来了什么、代价是什么。

1. 为什么需要它 ​

上一章讲透了 off 的两种改表方式：splice 删一个、set([]) 把整张数组换成空。当时我们看的是「派发之外」调用 off 的常规场景——先注销、下一次 emit 时新名单生效，干净利落。但还有一个一直被绕开的口子：如果一个处理器在自己的函数体里反手调用 on 或 off，也就是在派发进行到一半时改这张表，会发生什么？

想象一个表单。你写了 on('change', validator)，又写了 on('change', logger)。validator 跑完一遍发现数据干净，觉得自己可以下班了，于是在函数体里 off('change', validator) 把自己注销；又或者更隐蔽——validator 内部 off('change', logger)，因为某些场景下不该再打日志。这一刻 emit('change') 还在遍历过程中，validator 后面本来该轮到 logger。注册表是同一张可变数组，validator 一反手把它改了，遍历器的脚下地板就动了。

矛盾的根源在于发布订阅这件事的结构本身。注册表（第 1 章那张 Map<type, handler[]>）是一张可变的活动数组，而「派发」恰恰是要遍历这张数组、并把控制权交给用户回调。on 的 push 追加、off 的 splice 删除，第 3、4 章已经讲透；回调里天然可以反手改这张表。这就构成了「一边遍历一边被改」的根本矛盾，本章机制正是为化解它而生。

2. 核心思想 ​

派发前先把处理器名单冻结一份副本，本次遍历只认这份快照，外界对原表的任何改动都影响不到正在跑的这一轮。

说人话就是：遍历器和改表者本来在抢同一个可变引用。把它们拆开：遍历器走手里那份拍下来的快照，改表者继续改注册表里的原表。两份引用各跑各的，矛盾就消解了。

3. 心智模型 ​

注册表是一张会被原地改写的「活动表」。emit(type, evt) 时的数据流是：

  1. 从注册表里取出该类型的活动数组——拿到的是一个引用，外界随时可能改写它。
  2. 立刻对这份引用拍一份浅拷贝（.slice()），手里这份就是本轮的「冻结名单」。
  3. 遍历这份冻结名单，依次把 evt 传给每个处理器，把控制权交出去。
  4. 某个处理器在执行中调用 on/off/clear，改的都是注册表里那份原表，不是手里这份快照。
  5. 于是本轮从头到尾只跑「入口那一刻」的名单：中途被删掉的仍会跑（不漏触发），中途新加的不会跑（不重复触发）。
  6. （旁路）类型匹配的名单跑完后，通配符 '*' 名单会用同样的方式再跑一遍。通配符为何单独成一路是下一章的事。

不变量是：本轮派发的处理器集合，在 emit 被调用的那一刻就冻结了，外界后续任何动作都改不了它。

4. 关键权衡 ​

入口处拍一份快照，换本轮集合的强确定性，代价是每发一次都多一次数组分配 ​

选择：emit 取出某类型的活动数组后，第一件事不是遍历，而是 .slice() 复制一份再遍历副本。

换来：本次派发的处理器集合在 emit 被调用的那一刻就被冻结，对中途任意 on/off/clear 完全免疫。使用者在回调里改注册表这件事，从「会让本轮派发出 BUG」降级为「会反映在下一次 emit」。你随时可以放心地推理「我这次 emit 到底会调到谁」——就调入口那一刻名单上的人，仅此而已。这种可推理性是写复杂事件流（处理器之间互相依赖、互斥、自注销）的前提。

代价：每次 emit 都多一次 O(n) 的数组分配与拷贝，无论本次中途有没有改表。绝大多数 emit 其实根本没人改表，这一次 slice 是「白花」的——对一个高频触发的事件系统，这是实打实的 GC 压力，且无法用惰性策略规避（你不知道哪次 emit 会改表，所以必须每次都拍）。

化解的本质矛盾：遍历者要「按某一刻的名单办事」，而注册表天然「随注册/注销持续演化」——这两者争抢同一份可变引用就一定撞车。快照把「派发期间表是什么样」从「运行时可变」里剥出来，让「派发集合」变成一个不可变快照，注册表本身继续保留随时可改的灵活性。这是一类通解：凡是「遍历一个会被并发/回调改写的集合」的场景（DOM NodeList 的 live vs static、数据库的 MVCC 快照、不可变数据结构的版本隔离），本质上都在用同一种「拷一份再走」的招数。读者一旦抓住这个本质矛盾，在别的语言、别的框架里看到类似设计就能立刻认出来。

移除延迟一拍生效，换与 Node EventEmitter 的语义对齐，代价是直觉相悖 ​

这是上面那条权衡的直接推论，但因为容易让人踩坑，单独拎出来讲透。

选择：快照语义意味着——中途被 off 掉、但还没轮到的处理器，本轮依然会被触发；移除真正生效要等到下一次 emit。

换来：与 Node.js EventEmitter、浏览器 EventTarget 的行为完全一致。一个工业级 pubsub 库的「可预测」几乎都建立在这个延迟上：派发是原子的，中途改表反映在「下一次」，而不是「本轮剩下半截」。

代价：这个语义和「我立刻把它移除了，它就不该再跑」的直觉相悖。如果文档不写明，使用者会觉得 off 失败了——「我都注销了它怎么还在跑」。代价是认知负担：调用方必须知道，想让某个处理器在「当前这次 emit 的后续处理器」看来已经消失，是不能靠在它前一个处理器里 off 实现的——必须改用标志位、或干脆把派发顺序重新设计。这是一份需要文档化的语义债。

化解的本质矛盾：注册端希望「我此刻消失，立刻对所有人可见」，派发端已经按入口名单发出去了，认这个「中途状态」就要付出遍历一致性崩盘的代价。这是一对方向相反的预期，无解，只能选一边并文档化——快照方案选了「派发的可推理优先」，把「立刻生效」让渡给「下一轮」。任何「遍历过程中允许反手改集合」的设计都会撞上这对矛盾，差别只在选了哪边。

选用 .map 当遍历器而非 .forEach，换更短的方法名，代价是语义错位 ​

这条是体积优先的小注脚，前两条才是主角。

选择：遍历快照时用 .slice().map(h => h(evt))，丢弃 map 的返回数组，而不是语义更贴切的 .slice().forEach(h => h(evt))。

换来：方法名从 7 字符（forEach）压到 3 字符（map），契合整个库 ~200 字节的体积定位。（这是基于体积目标的推断，源码无注释佐证。）

代价：把「映射」语义错用为「副作用循环」，map 本该用来生成新数组，这里却把新数组扔了。此外 map 还会再分配一个结果数组（slice 已经分配过一份），等于每次 emit 多一次内存开销。这是一个「为了几个字节牺牲语义贴合」的轻微技术债，读者若在大项目里看到这种写法，要明白它只在「字字必争」的库里才划算。

化解的本质矛盾：可读性/语义贴合 vs. 体积压缩，一个追求极简库的常态取舍，没什么深意，但能解释为什么源码读起来「怪怪的」。

5. 最小原理演示 ​

下面这段几十行的 TS，从零搭一张查找表，演透「快照 vs 不快照」的差异。构造两个处理器 a、b（a 注册在前），让 a 在自己函数体里当场把 b 注销掉，然后触发事件。对比两版：有快照版里 b 仍然被调用，无快照版里 b 被跳过。这一组对比演的就是上面主权衡——「冻结名单」到底换来了什么、代价是什么。

ts
// snapshot.ts
type Handler = (e?: unknown) => void;

// 注册表：Map<type, handler[]>（第 1 章已讲透，这里直接用）
const table = new Map<string, Handler[]>();

// 注册：不去重地追加（第 3 章已讲透）
function on(type: string, h: Handler) {
  const list = table.get(type);
  if (list) list.push(h);
  else table.set(type, [h]);
}

// 移除：indexOf + splice（第 4 章已讲透）
function off(type: string, h: Handler) {
  const list = table.get(type);
  if (list) list.splice(list.indexOf(h) >>> 0, 1);
}

// 版本 A：有快照（本章主角）。入口先 slice 复制，再遍历副本
function emitSnapshot(type: string, evt?: unknown) {
  const live = table.get(type);
  if (!live) return;
  const frozen = live.slice();      // 入口冻结名单，外界后续改的是 live，不是这份
  for (const h of frozen) h(evt);
}

// 版本 B：无快照（对照）。直接遍历 live，中途 splice 会让下标漂移
function emitNaive(type: string, evt?: unknown) {
  const live = table.get(type);
  if (!live) return;
  for (const h of live) h(evt);
}

跑一次「a 在自己函数体里 off 掉 b」的对照实验：

ts
let trace: string[] = [];

const a: Handler = () => {
  trace.push('a');
  off('foo', b);                     // a 执行中顺手把 b 从活动数组里删了
};
const b: Handler = () => trace.push('b');

function run(emit: (t: string) => void, label: string) {
  trace = [];
  table.clear();
  on('foo', a);
  on('foo', b);
  emit('foo');
  console.log(label, '->', trace.join(','));
}

run(emitSnapshot, '有快照');         // 输出: 有快照 -> a,b
run(emitNaive,    '无快照');         // 输出: 无快照 -> a

有快照版：emit 入口拍了一份 [a, b]，遍历这份；a 调用时改的是 live，但 frozen 不变，所以 b 仍被调用，共触发 2 次。无快照版：直接遍历 live = [a, b]，i=0 调 a，a 里 splice 把 b 删掉后 live 变 [a]、长度 1，循环结束，b 被跳过，只触发 1 次。

6. 执行轨迹 ​

拿上面的对照场景，把「有快照版」的内部状态一步步走一遍，看核心思想是怎么落到每一行的。

输入：on('foo', a) → on('foo', b) → 在 a 里 off('foo', b) → emit('foo')。

注册之后的初始状态：注册表 { foo → [a, b] }，其中那个数组就是 live——外界随时能改写它。

调用 emitSnapshot('foo')：

  1. 进入 emit，从表里取出 live = [a, b]。此刻手里拿的是 live 数组的引用。
  2. 立刻 frozen = live.slice()，复制出一份新数组 frozen = [a, b]——本轮的「冻结名单」就此与 live 分家。这一步发生在调用任何处理器之前。
  3. 进入 for 循环，取 frozen[0] = a，调用 a()，把控制权交出去。
  4. 在 a 的函数体里执行 off('foo', b)：off 找到 live 里 b 的位置（1），splice 删一个，live 变成 [a]。
  5. 注意：frozen 不受影响，仍是 [a, b]——这就是「拍快照」换来的隔离。
  6. a 返回，循环继续，取 frozen[1] = b，调用 b()。
  7. b 返回，循环结束。trace = ['a', 'b']。

对照无快照版走同一条输入：

  1. 进入 emit，取出 live = [a, b]，直接对 live 进 for-of。
  2. 取 live[0] = a，调用 a()。
  3. a 里 splice 后 live 变 [a]、长度 1。
  4. a 返回，循环试图前进，发现已经到末尾（length=1），结束。
  5. trace = ['a']，b 被跳过。

差别全在第 2 步那一次 .slice()——它把「派发期间表是什么样」从「运行时可变」剥成了「入口那一刻冻结」，遍历器从此和外界改表各跑各的。

7. 教学简化说明 ​

本章演示故意省略了：通配符 '*' 的第二条派发路径（下一章专门讲）、泛型与类型签名、事件载荷的多种形态、symbol 私有频道、生产级的错误隔离（单个 handler 抛错如何不影响其他处理器）。§4.3 点出的 .map 当遍历器的体积权衡，演示里没用源码那种写法，而是用了更直观的 for-of——目的是演透快照原理本身，不背体积压缩的额外包袱。这些都不是「快照原理」的必要组成。

8. 小结 ​

快照并不是 mitt 的独创——Node.js EventEmitter、浏览器 EventTarget 都在派发入口克隆 listeners 数组。工业级 pubsub 的「可预测」几乎都建立在这一拍上：派发是原子的，中途改表反映在「下一次」而不是「本轮剩下半截」，代价是 O(n) 拷贝和一份需要文档化的「移除延迟一拍」语义债。

到此，单条类型路径的派发就完整了：注册、移除、派发三件套对单一事件类型已经闭环。但事件系统里还有一种「不管什么类型都想听一耳朵」的需求，也就是通配符。下一章就看 mitt 怎么用一个保留键 '*'，给 emit 加上第二条独立派发路径。
