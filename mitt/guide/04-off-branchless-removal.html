无分支安全移除与重载清空 ​

想象你在维护一个事件系统，用户注册了一堆监听器，现在想移除其中一个。最直白的写法是什么？先查它到底在不在列表里，在才删：

ts
const i = list.indexOf(handler);
if (i >= 0) list.splice(i, 1);

这两行谁都能看懂，一个 if、一个临时变量 i，清清爽爽。可如果这个库的卖点是「整个打包下来不到 200 字节」，那这一个分支、这一个变量名，就全是实打实的体积成本。更要命的是，「移除」这件事天然带着两个让人忍不住写 if 的边界——只要老老实实处理它们，代码就会膨胀。

本章讲的就是：怎么把这两个边界各用一个巧妙的招数抹平，让「删一个处理器」退化成一行没有分支的直线，顺手再把「清空全部」也塞进同一个方法里。

先把两个边界摊开看 ​

移除一个处理器时，有两件「倒霉事」随时可能发生，它们都会诱惑你写分支：

  • 边界一：这个事件类型压根没人注册过。 你对一张空表说「移除 foo 的处理器」，表里根本没有 foo 这个键。
  • 边界二：类型注册过，但你要移除的那个处理器不在列表里。 比如它早就被移走了，或者你记错了——indexOf 会老老实实返回 -1，表示「没找到」。

注意，这两件事都不是异常。在一个事件系统里，「去移除一个根本没注册过的东西」是再正常不过的调用，绝不该报错。难点在于：怎么让这两种「扑空」都安静地变成「什么也没做」，又不在代码里堆满 if。

下面两个招数，分别对付这两个边界。

边界一：用一次真值判断挡在门外 ​

边界一最好处理。移除方法的第一行就是去那张全局查找表里把该类型的处理器数组取出来（这张表是整个发射器的唯一状态，第 1 章「把 pubsub 退化成一张查找表」已经讲透，本章只把它当成一个现成的 Map 来读写）：

ts
const list = table.get(type);
if (!list) return;   // 这个类型从没注册过 -> 直接返回，什么都不做

取不到，说明这个类型从没人注册过，那就整体返回，连后面的逻辑都不用走。这一个 if 是挡在最外面的守卫，把边界一变成一个廉价的「安全空操作」。

真正被抹平成无分支的，是边界二——也就是「删一个处理器」的那条热路径。下面这才是本章的灵魂。

边界二：用一个位运算把「-1」变成无害的越界下标 ​

走到这里，说明类型是注册过的，list 是个实打实的数组，而且调用者给出了具体要删的处理器。现在要做的，是在数组里找到它、删掉它。

最朴素的写法你已经在开头见过了：indexOf 找位置，判断 >= 0 再删。这里的 if (i >= 0) 就是为了应付边界二——万一是 -1，就别删了。这个分支能不能省掉？

能。关键在于认识到一件事：「找不到」对应的 -1，与其用 if 把它挡回去，不如直接把它改写成一个「无害的下标」，让删除动作自己扑个空。

这就用到了一个位运算的小知识：-1 >>> 0。>>> 是无符号右移，它会把左侧操作数当成一个 32 位无符号整数来处理。-1 在 32 位里是一串全 1，右移 0 位后还是全 1，作为正整数读出来就是 4294967295——约 42.9 亿。

说人话就是：-1 经过这一次无符号右移，被改写成了一个巨大到不可能存在的位置——「列表第 42.9 亿号」。这个位置当然不存在，于是接下来要从这儿删东西的删除动作，必然扑空。

把这个数当成「起点」喂给数组的 splice，会发生什么？这里用到第二条冷知识：按规范，splice 会先把越界的起点钳制到数组长度（actualStart = min(start, length)），再在这个钳制后的起点上删指定个数；当起点已经被钳到数组末尾时，可删的元素数自然就是 0。于是这次 splice 删了 0 个元素，数组原封不动。

把这两步合起来，删除单个处理器就退化成了一行没有 if 的表达式：

ts
list.splice(list.indexOf(handler) >>> 0, 1);

我们顺着这条直线把两种情况都走一遍：

  • 找到了（比如位置是 0）：0 >>> 0 还是 0，从 0 号位删 1 个——正常删除，删的是第一个匹配项。
  • 没找到（indexOf 返回 -1）：-1 >>> 0 变成 4294967295，这个起点被钳到数组长度，删 0 个——什么也没删。

一个 >>> 0，把「找不到」和「找到了」两条原本要走分支的路，合并成了一条无分支的直线。妙就妙在它把 indexOf 的 -1 信号，直接复用成了「一个必然越界的下标」，让运行时自带的钳制规则替你做完了那个判断。

关于「只删第一个匹配项」：因为用的是 indexOf（取首次出现位置），所以同一个函数如果被注册了多次，一次移除只会清掉一个。这和注册侧「不去重地追加」严格对称——注册时加几次，移除时就要调几次才清得干净。这个对称性第 3 章「惰性初始化的追加式订阅」已经讲透，这里不重复。

还要能清空：让「不传处理器」表示「全部清掉」 ​

除了删单个，用户还经常需要「把这个类型的处理器全清掉」。最直觉的做法是再加一个 clear(type) 方法。但这个库没有，它选择了另一条路：让 off 不传第二个参数时，就表示「清空该类型的全部处理器」。

ts
if (handler) {
  // 删一个
} else {
  table.set(type, []);   // 没传 handler -> 清空全部
}

外层用 if (handler) 来区分两路（处理器只能是函数、恒为真值，所以这里和显式判断「有没有传」实际等价）。传了处理器，走删一个的直线；没传，就把这个类型对应的数组整个换成一个空数组，等于清空。

注意这里的清空是 table.set(type, [])——换一个新空数组，而不是把键从表里删掉。这个选择有讲究，留到下面权衡里细说。

把整条移除流程串起来 ​

到这里，「移除」就只剩两种行为，没有尴尬的第三种「找不到怎么办」：

off(type, handler?)
  ├─ table 里没有这个 type？  → 直接返回，安全空操作（边界一）
  └─ 有这个 type：
        ├─ 传了 handler？  → indexOf 取首个位置 → >>> 0 抹平 → splice 删一个（边界二在此被抹平）
        └─ 没传 handler？  → set(type, [])  清空该类型全部

「找不到」这件事，从头到尾没有以 if (i >= 0) 的形式出现过。

原理演示 ​

下面这段几十行的 TS，从零搭一张查找表，演透「位运算抹平边界 + 重载清空」。注册侧（on）只是为了配合演示，逻辑极简：能取到数组就 push，取不到就建一个（注册不去重这件事第 3 章已讲透）。

ts
// off.ts
type Handler = (e: unknown) => void;

// 一张查找表，就是整个发射器的全部状态（第 1 章已讲透）
const table = new Map<string, Handler[]>();

// 注册侧：不去重地追加（第 3 章已讲透，这里只作配合）
function on(type: string, handler: Handler) {
  const list = table.get(type);
  if (list) list.push(handler);
  else table.set(type, [handler]);
}

// 本章主角：移除
function off(type: string, handler?: Handler) {
  const list = table.get(type);
  if (!list) return;                       // 边界一：类型从没注册过 -> 安全空操作
  if (handler) {
    // 边界二：indexOf 找不到返回 -1；
    // -1 >>> 0 === 4294967295（必然越界），splice 会把越界起点钳到长度、删 0 个
    list.splice(list.indexOf(handler) >>> 0, 1);
  } else {
    table.set(type, []);                   // 省略 handler -> 清空该类型全部
  }
}

配一个最小 package.json，用 npx tsx off.ts 即可跑通：

json
{
  "name": "off-demo",
  "private": true,
  "type": "module",
  "scripts": { "start": "tsx off.ts" },
  "devDependencies": { "tsx": "^4.0.0" }
}

把三种情况都跑一遍，对照每一步的表内容：

ts
const f: Handler = () => {};
const g: Handler = () => {};

on('foo', f);
on('foo', f);                     // 同一个函数注册两次（不去重）
console.log(table.get('foo'));    // [f, f]

off('foo', f);                    // 删第一个 f -> 位置 0，抹平后仍 0，删一个
console.log(table.get('foo'));    // [f]

off('foo', g);                    // g 从没注册过 -> -1 抹成 4294967295 -> 越界删 0 个
console.log(table.get('foo'));    // [f]  （什么也没删）

off('nope', f);                   // 'nope' 这个类型根本不存在 -> 边界一 -> 直接返回
console.log(table.has('nope'));   // false

off('foo');                       // 省略 handler -> 清空
console.log(table.get('foo'), table.has('foo'));   // [] true（键还在，值是空数组）

最后一步值得留意：清空之后，foo 这个键仍然在表里，只是它的值变成了一个空数组。这正是下面第三条权衡要说的取舍。

关键权衡 ​

本章的机制其实集中在「抹平两个边界 + 重载清空」这一处，下面把三条最核心的「选择 → 换来 → 代价」讲透。

权衡一：用 >>> 0 把 -1 改写成越界下标，换删除路径零分支，代价是可读性骤降。

选择：不写 if (i >= 0)，而是直接把 indexOf 的结果（可能是 -1）经一次无符号右移喂给 splice，靠运行时的钳制规则让「-1」变成「删零个」。

换来：删除单个处理器的那条热路径上零分支、零临时变量，整段是一个单行表达式。没有 if/else 结构、没有中间变量名，对 gzip 压缩极度友好，牢牢咬住「整个库约 200 字节」的定位。对一个以体积为卖点的库，这是实打实的收益。

代价：这一行的可读性是断崖式下降的。要读懂它，读者必须同时知道两条冷知识——其一，-1 经无符号右移会变成 4294967295 这个巨大正整数（而不是停留在 -1）；其二，splice 会把越界起点钳制到数组长度、再把删除数量钳成 0。这两条缺任何一条，读者都会完全不明白这一行在干嘛。换句话说，这个设计把「这里有个边界要处理」的认知负担，从写代码的人转移到了读代码的人头上。这是一个典型的「用可读性换体积」的取舍，在一个追求极简的库里是站得住脚的，但换到追求可维护性的大项目里就不一定值得。

权衡二：让「不传处理器」的重载表示「清空全部」，换更小的对外 API，代价是同方法名承担两种语义。

选择：不单独做一个 clear(type) 方法，而是让 off(type)（不传第二个参数）直接表示「清空该类型的全部处理器」。

换来：对外 API 表面更小，少一个方法名要记、要导出、要写文档。用户只需要认得一个 off，清空不过是它「不传参数」的形态，注册和注销的动词统一在 on/off 这一对上，心智负担更低。

代价：同一个方法名现在背着两种语义——「删一个」和「清全部」，只靠「有没有传第二个参数」来区分。这种「参数个数决定行为」的重载并不自明：光看签名 off(type, handler?)，你未必会立刻反应过来「不传 handler 居然是清空而不是报错」。它必须靠文档点明，否则第一次用的人很可能踩坑（以为不传只是「移除失败」而意外清空了全部）。这是用「一个方法干两件事」换「少一个方法名」的常见代价。

权衡三：清空时换成新空数组而非删掉键，换稳定的可窥探性，代价是表里残留空数组键。

选择：清空执行 table.set(type, [])——把这个键对应的数组整个换成一个新空数组，而不是用 table.delete(type) 把这个键从表里抹掉。

换来：这个类型在表里的键始终存在。这个库的注册表是对外公开、谁都能读的（第 1 章那张完全可窥探的查找表），所以外部代码去 table.get(type) 时，会稳定地拿到一个空数组，而不是 undefined。配合「整张表是唯一状态」的设计，外部观察者可以无差别地读 .length、做遍历，不必每次先判一下 undefined，对外契约更一致、更不容易写出空指针。

代价：表会长期残留这些空数组键。如果反复注册又清空很多种类型，内存里会攒下一堆「键 → 空数组」的条目，它们不会随着清空而自动回收。空数组本身很轻，这个代价通常可以忽略，但它确实存在——尤其在一个本该「用完即走、不留痕迹」的事件清理动作里，却选择留下一个永久的空壳键，多少有点反直觉。这是一个「对外一致性」优先于「内存整洁」的选择。

顺带一提，清空选「整体替换成新数组」而不是「原地截断（list.length = 0）」，两者对本库自身没差别，但对外部已经持有旧数组引用的代码可见性不同：替换后，旧引用还保留着原来的内容，表内则指向新空数组。这只是从代码风格反推的合理猜测，库本身没有明说，了解即可。

小结 ​

「移除」这件事的难点不在删除本身，而在两个让人想写分支的「扑空」边界。本章用一个外层的真值守卫挡住「类型从没注册过」，再用一个 >>> 0 把「处理器不在列表里」的 -1 改写成必然越界的下标、让 splice 自己扑空，于是删除单个处理器退化成一行无分支的直线；顺带让「不传处理器」表示「清空全部」，省掉一个独立方法。代价是把可读性、方法语义清晰度、内存整洁度都让渡了一部分，换来极致的体积友好和 API 简洁——这对一个 ~200 字节的库是划算的。

这里还埋着一个伏笔：移除方法因为这两层抹平，从不抛异常，无论怎么调用都是安全的空操作。这正是它能被一个正在执行中的处理器自己调用的前提——但「移除之后，会不会影响当前正在进行的那一轮派发」？这就引出了下一章「快照式派发抵御中途改表」要回答的问题。
