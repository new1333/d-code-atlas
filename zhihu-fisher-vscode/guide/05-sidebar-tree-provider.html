第五章 侧边栏内容列表：把网页列表变成一棵「状态驱动的树」 ​

你装好这个摸鱼扩展,满怀期待地打开侧边栏,想看看今天知乎热榜都有什么。结果映入眼帘的是一片空白——没有列表,没有报错,也没有提示你该干什么。你点了一下「刷新」,还是空白。

这一章要解决的就是这种尴尬。说得直白点:把知乎的「热榜 / 推荐 / 搜索 / 关注」四份列表搬进编辑器侧边栏,真正的难点不是「列表拉不拉得下来」,而是「不管现在处于什么状态——加载中、没登录、浏览器没配好、拉取出错——侧边栏都得给使用者一个看得懂、点得动的下一步」。

这一章要讲透的核心就一句话:侧边栏的内容不是「存进去」的,而是「按当前状态现算出来的」。加载中、未登录、出错、有数据,各自长成不同的样子;想换内容,只要改一份共享状态、再敲一下「内容变了」的事件,侧边栏自己会重新映照。

一、先看懂编辑器侧边栏的脾气:它只在需要时「来问一次」 ​

要理解为什么侧边栏是这样设计的,得先明白编辑器平台是怎么对待侧边栏内容的。

平台并没有给你一个「往侧边栏里 push 数据」的接口。它给你的是一个回答问题的契约——TreeDataProvider。平台只在它需要画侧边栏的时候,来问你一个问题:

「现在这一层,该显示哪些节点?」

这个问题由一个叫 getChildren 的回调来回答。你返回一串节点,平台就拿去画。除此之外还有两个配套约定:

  • getTreeItem(element):给定一个节点,告诉平台它长什么样(图标、文字、点开会怎样)。
  • onDidChangeTreeData:一个事件。当你觉得内容变了、希望平台重新来问一遍时,就 fire() 一下。

打个比方:侧边栏不是你往里塞东西的「容器」,更像是平台举着一张空表格站在你门口。每次它要展示时,就敲门问一句「现在该填什么?」;你平时往屋里(共享状态)搬东西,搬完了就冲外面喊一声「变啦!」,它才会再敲一次门重新问。

这个「你只负责回答,由平台来问」的回合制,就是后面所有机制的底色。

二、这棵树里只有一种节点:数据项和「动作入口」共用一副皮囊 ​

如果你第一次想这个问题,多半会想成两套东西:数据节点(一条知乎内容)是一类,「点我登录」「点我重试」这种动作按钮是另一类。

但这个扩展偏不。它让「加载中」「点我登录」「点我重试」「打赏作者」这些动作入口,也长成树节点的样子,和数据项共用同一种节点类型。

具体来说有两层:

  • TreeItem:一个数据节点的全部呈现都集中在这里。构造时根据配置决定图标(有远程图就用图片地址,没有就用主题图标),拼一段悬浮提示(热度、摘要、预览图),并且把 command 设成「打开详情」——于是点一下节点就触发详情爬取。它还带一个 contextValue(比如 TreeItem、ThoughtItem、FollowedQuestion),用来控制右键菜单该显示哪些项。
  • StatusTreeItem:这是「占位 / 动作」节点。它的取巧之处在于——它继承自 TreeItem。构造时先造一份假的 LinkItem(一个带随机 id、空 url 的对象),拿去喂父类构造函数,从而白嫖了父类全部的呈现逻辑;然后再把图标、提示、点击命令覆写成自己想要的样子。

说人话就是:它不想为「加载中」「去登录」这些动作单独发明一套节点,而是让它们伪装成一条数据项,搭便车复用现成的节点机制。

这个选择换来什么、代价是什么,留到后面的权衡里细说。这里你只要记住:整棵侧边栏树,自始至终只有一种节点类型。

三、把「取子节点」回调写成一台状态机 ​

回到平台那个问题:「现在该显示哪些节点?」

一个最朴素的回答是:返回数据数组。但这个回答顶不了用——因为「现在」可能是没登录、可能是浏览器坏了、可能是正在加载。一个只懂「返回数据」的函数,在这些时候要么报错、要么返回空、要么卡死,使用者完全不知道发生了什么。

所以这个扩展把 getChildren 写成了一台按状态优先级分支的状态机。它一层一层往下问,哪一层命中就当场返回对应的一组节点,后面都不看了。四个列表的优先级几乎一模一样:

① 自定义浏览器路径无效?   → 返回「路径无效,点我重新设置」
② 不能创建浏览器?         → 返回「点我配置爬虫浏览器」
③ 还没设置 Cookie?        → 返回「扫码登录」+「手动设置 Cookie」
④ 正在加载?               → 返回「正在加载知乎热榜...」
⑤ 有数据?                 → 返回「打赏入口 + 数据项 + 尾部动作」
⑥ 都不是(说明加载失败)?   → 返回「获取失败,点击刷新重试」

注意每一层返回的都不是「错误码」,而是一组实实在在的、能点动的节点。「路径无效」配一个跳到设置页的命令,「没登录」配扫码登录的命令,「失败了」配重试的命令。

换句话说,使用者在任何状态下看到的侧边栏都是有意义的,而且总能点出一个下一步。这就是把回调做成状态机,而不是数据容器,真正想换来的东西。

四、事件驱动重渲染:改完状态,再敲一下「内容变了」 ​

状态机知道「该怎么画」,但平台不会主动来问。你得在内容变化时主动通知它——这就是 onDidChangeTreeData 这件事的用处。

整个刷新的套路是一个固定的循环:

改共享内存里的 list / isLoading  →  _onDidChangeTreeData.fire()  →  平台重新调用 getChildren

fire() 不带任何参数,意思就是「整棵树都算变了,你重新问一遍吧」。

这里有三件套要分清:

  • refreshView():只发事件、不重新拉数据。适合「我改了显示配置,只需要重画」。
  • refresh():重新拉数据,拉完自然也会发事件。
  • reset():先把数据清空,再发事件——立刻让侧边栏变成「空 / 加载中」的样子。

这里要回指一下前置内容:被改的那个共享内存,正是第一章讲透的那个模块级可变单例。它的「谁都能读写、模块一加载就存在」的特性,在这一章里被当成「视图数据源」来用——侧边栏读它、加载逻辑写它,彼此不直接认识,只通过这份共享内存和 fire() 这个信号间接沟通。那个单例是怎么做到的、为什么这么设计,第一章已经展开过,这里不重复。

五、加载编排:触发 → 闸门 → 防重入 → 拉取 → 写回 → 发事件 ​

把状态机、事件、共享内存拼起来,就是一次完整的「加载编排」。它的步骤是固定的(以热榜为例):

① 某个时机触发(构造时 / 用户点刷新 / 提交搜索词)
② 先问「浏览器能不能创建」——不能就清空数据、发事件、停下
③ 用「是否正在加载」做防重入闸门,避免并发重复拉取
④ 置「加载中」状态、发事件  →  此刻 getChildren 返回「加载中」占位节点
⑤ 真正拉取(热榜走轻量 HTTP,其余走真实浏览器)
⑥ 拉到的结果写回共享内存对应列表,置「非加载中」,再发事件
⑦ getChildren 被重新询问,按当前状态返回「打赏 + 数据项 + 尾部按钮」

四个列表(热榜、推荐、搜索、关注)共用这一套骨架,内部结构几乎逐字相同:一个事件发射器、一个状态栏加载项、一个浏览器可用性标志、refresh / reset / refreshView 三件套、一个加载编排私有方法、一个真正拉取的方法。它们的差异只体现在三个地方:

  • 用什么拉取:热榜用一次轻量 HTTP 请求 + HTML 解析;推荐 / 搜索 / 关注用真实浏览器开页、模拟滚动、在页面上下文里提取。
  • 解析什么 DOM:各自依赖知乎页面上不同的选择器(这一层极易随知乎改版失效,不在本章展开)。
  • 何时自动加载:热榜、推荐构造时即自动加载;搜索和关注构造时不加载,得等用户输入关键词 / 手动点「加载」。

这里再回指两处前置成果,本章只看它们被复用的方式,不重讲内部原理:

  • Cookie 清洗与失效探测(第二章):列表在请求前复用那套清洗(去掉会惹 403 的第三方项、去掉会被重定向到热榜的 BEC),在请求后用「登录墙 DOM 是否出现」反判 Cookie 是否已失效。这套清洗和探测怎么做、为什么要这么做,第二章已展开。
  • 防反爬浏览器引擎(第三章):那台真实 Chrome 在本章被当成两重角色复用——既是「详情能不能点开」的前置闸门(下面权衡会讲),又是动态 Feed 流的拉取手段。引擎怎么启动、怎么伪装、怎么模拟滚动,第三章已展开。

六、原理演示:一段能跑的脚本,演透「状态投影 + 事件重算 + 轻重闸门」 ​

下面这段脚本没有第三方依赖,node 直接就能跑。它把编辑器那套契约抽到最简:自己 mock 一个事件发射器 + 一份共享状态 + 一个写成纯函数的 getChildren,然后跑一遍「改状态 → 发事件 → 节点列表变了」的轨迹。

它演的是三条原理,不是爬虫细节——

  • ① getChildren 是「状态 → 节点」的映射函数,状态不同,返回的整棵树就不同;
  • ② 外部改完状态只要 fire() 一下,监听者就会重新调用它,节点列表随之刷新;
  • ③ 数据本身可以「轻量拉取」,但展示前仍要先过「浏览器可用」这道闸门。
js
// side-tree-state-machine.js   ——   node 直接运行,无第三方依赖
// 演透:① 状态机渲染  ② 事件驱动重渲染  ③ 轻量拉取仍过「重」闸门

// ---------- 1) 极简事件发射器(对应平台里的 EventEmitter) ----------
class Emitter {
  constructor() { this.listeners = new Set(); }
  event(cb) { this.listeners.add(cb); return () => this.listeners.delete(cb); }
  fire() { for (const cb of this.listeners) cb(); }
}

// ---------- 2) 共享内存:就是第一章那个模块级单例,这里只当「视图数据源」 ----------
const Store = { hot: { list: [], isLoading: false } };

// ---------- 3) 决定分支的状态 ----------
const State = {
  isUserChromePathValid: true,   // 自定义浏览器路径是否有效
  canCreateBrowser: false,       // ★ 浏览器闸门
  isCookieSet: false,            // 是否已登录
};

// ---------- 4) 统一的节点类型:数据项 / 动作项 共用一种 ----------
function node(label, { icon = '📄', command = null } = {}) {
  return { label, icon, command };
}

// ---------- 5) 状态机:getChildren 是「按状态优先级返回节点」的纯函数 ----------
function getChildren() {
  if (!State.isUserChromePathValid)
    return [node('自定义浏览器路径无效,点我重新设置', { icon: '⚙️', command: 'setCustomChromePath' })];
  if (!State.canCreateBrowser)
    return [node('点我配置爬虫浏览器', { icon: '⛔', command: 'configureBrowser' })];
  if (!State.isCookieSet)
    return [
      node('扫码登录知乎', { icon: '🔑', command: 'qrLogin' }),
      node('手动设置 Cookie', { icon: '🍪', command: 'setCookie' }),
    ];
  if (Store.hot.isLoading)
    return [node('正在加载知乎热榜...', { icon: '⏳' })];
  if (Store.hot.list.length > 0)
    return [
      node('💖 打赏作者', { icon: '💖', command: 'sponsor' }),
      ...Store.hot.list.map(t => node(t.title)),
    ];
  return [node('获取热榜失败,点击刷新按钮重试', { icon: '🔁', command: 'refreshHotList' })];
}

// ---------- 6) 渲染:把当前状态投影出的树打印出来 ----------
function render(reason) {
  console.log(`\n— ${reason} —\n  侧边栏:`);
  for (const n of getChildren())
    console.log(`    ${n.icon} ${n.label}${n.command ? `   ⟶ [${n.command}]` : ''}`);
}

// ---------- 7) 事件驱动重渲染:平台订阅了 onDidChangeTreeData,fire 即重算 ----------
const onChange = new Emitter();
onChange.event(() => render('平台收到 fire(),重新调用 getChildren'));

// ===================== 演示轨迹 =====================
render('扩展刚激活,浏览器还没配好');          // → 「点我配置爬虫浏览器」

console.log('\n# 用户配好了浏览器,但还没登录');
State.canCreateBrowser = true;                  // 闸门打开
onChange.fire();                                // → 扫码登录 / 手动设置 Cookie

console.log('\n# 用户登录成功,触发加载编排');
State.isCookieSet = true;
Store.hot.isLoading = true;
onChange.fire();                                // → 「正在加载知乎热榜...」

console.log('\n# 轻量 HTTP 拉到 3 条热榜(先过浏览器闸门)');
if (State.canCreateBrowser) {                   // ★ 轻重闸门
  Store.hot.list = [
    { title: '如何看待某新兴语言爆火?' },
    { title: '日常有哪些好用到哭的工具?' },
    { title: '为什么没人提这个冷知识?' },
  ];
}
Store.hot.isLoading = false;
onChange.fire();                                // → 打赏 + 3 个内容节点

console.log('\n# 失败支线:HTTP 返回 403 → 判定 Cookie 失效');
Store.hot.list = [];
State.isCookieSet = false;                      // 登录态被反判失效
onChange.fire();                                // → 回到「扫码登录」

跑一遍你会看到侧边栏的「长相」随状态一路变化:配置提示 → 登录入口 → 加载中 → 打赏加三条内容 → 又退回登录入口。节点从没被「塞进去」过——每一次都是 getChildren 根据当时的状态现算出来的。

七、关键权衡 ​

权衡一(核心反差):列表用最轻的 HTTP 拉取,却要先过最重的浏览器闸门 ​

选择:热榜列表本身,用一次轻量 fetch 请求 + HTML 解析就够了,完全不必动用那台昂贵的真实 Chrome。

换来:不占用那台唯一的浏览器实例(也就不会和「推荐页」抢同一个浏览器),列表加载快、机器负担轻。

代价却很有意思,而且分三层:

  1. 即便列表本身根本不需要浏览器,加载的第一步仍必须是「校验浏览器能否创建」,通不过就直接清空、停下。
  2. 这一次 HTTP 请求不能裸发——必须手动伪造一整套浏览器请求头(Sec-Ch-Ua、Sec-Fetch-*、User-Agent、Referer、Cookie),否则照样被反爬挡掉。
  3. 最根本的代价藏在一句源码注释里(大意):「虽然热榜是用 fetch + 解析加载的,但最好还是等浏览器能正常启动再去加载……因为加载文章也需要浏览器,只加载了列表却点不开,加载列表就没意义了。」

这条权衡是全章最具反差感的地方:「轻」无法脱离「重」独立存在。 你可以为了省资源用最轻的方式拉列表,但只要点开详情必须靠那台重浏览器,你就被迫让列表也守着同一道闸门——否则使用者会看到「列表好好的,却什么都点不开」这种最迷惑的半成品状态。

权衡二:把「取子节点」回调做成状态机,而不是数据容器 ​

选择:getChildren 不再是「返回数据数组」的简单函数,而是一长串按优先级排列的条件分支,每层返回不同的占位 / 动作节点。

换来:侧边栏在任何状态下都有意义,使用者总有可点的下一步(去配置、去登录、去重试),再也不会面对一片空白无所适从。

代价:

  • 回调本身变成了一长串条件分支,可读性不如「一个返回数组的函数」那么直白。
  • 这套分支在四个列表里几乎逐字重复,却没有抽取公共基类——维护时要四处同步,改一处漏了别处就行为不一致。
  • 还有个隐蔽代价:像「浏览器能否创建」这种判断,热榜是在加载编排时存进一个实例字段的,getChildren 只是读它。这意味着如果用户在加载之后才配好浏览器,热榜视图不会自动反映,得手动 refresh 才行——而搜索列表的 getChildren 是每次现去校验,就能即时反映。同一个设计取舍,在不同列表上落出了不同的体验瑕疵。

权衡三:用同一种节点类型同时扮演「数据项」和「动作项」 ​

选择:让「加载中」「点我登录」「点我重试」「打赏」这些动作入口,也长成树节点的样子,和数据项复用同一种节点类型(靠 StatusTreeItem 继承 TreeItem、用一份伪数据搭便车实现)。

换来:整棵树只有一种节点类型,平台契约保持单一;而且动作入口天然就能带一个「点击命令」,点一下就跳设置页 / 弹登录 / 触发重试,不用为动作按钮另搭一套机制。

代价:

  • StatusTreeItem 的构造函数因此变得很重——它得先造一份假的 LinkItem 去喂父类构造,再逐个覆写图标、提示、命令,弯弯绕绕。
  • 那份假数据的 id 是用「时间戳 + 随机数」现造的。这就意味着每次 fire() 之后 getChildren 重建占位节点,都会产生一个全新的 id,平台很难按 id 复用它已经画好的 DOM,表现为占位节点每次刷新都是从零重建,而不是平滑更新。这是为了「复用类型」在渲染效率上付出的小代价。

本章机制集中在这三条权衡上,它们共同回答了一个问题:当平台只给你一个「按需来问」的回合制契约时,怎么把它做成一个在任意状态下都站得住、还顺手能承载各种动作的界面。

八、执行轨迹:热榜的一天 ​

把上面所有东西串起来,以热榜为例走一遍真实生命周期:

① 扩展激活,热榜 provider 被构造,自动触发加载编排
② 浏览器闸门校验通过 → 置「加载中」、发事件
   → 侧边栏显示:正在加载知乎热榜...(一个占位节点)
③ Cookie 清洗后发一次轻量 HTTP 请求(带全套伪造头)
   → 解析回 50 条 → 写回共享内存 → 置「非加载中」→ 再发事件
   → 侧边栏变成:打赏入口 + 50 个内容节点
④ 使用者点某节点 → 触发「打开详情」命令 → 把该节点交给下一章去爬详情

失败支线同样清晰:第 ③ 步 HTTP 返回 403(或登录墙 DOM 出现)→ 判定 Cookie 失效 → 弹更新提示、发事件 → 侧边栏显示「获取热榜失败,点击刷新按钮重试」,使用者一点即可重试。注意失败时使用者拿到的仍然是一个能点动的节点,而不是一个红色错误条。

小结 ​

这一章的核心,是认清编辑器侧边栏的本质:它不是容器,而是状态的一面镜子。 平台只在需要时来问「现在该显示什么」,你的全部功夫就花在两件事上——把「该怎么画」写成一台按状态优先级分支的状态机,以及,在状态变化时记得喊一声「变了」。共享内存提供状态、fire() 提供信号、getChildren 提供映射,三者一咬合,侧边栏就能在任何状态下都站得住。

而那条最具反差的权衡也值得记牢:列表可以很轻,但只要详情必须很重,列表就得替详情守住同一道闸门。 因为一个点不开详情的列表,对使用者毫无意义。

顺着这个逻辑往下走:既然侧边栏点开一个节点就要「打开详情」,那详情页到底是怎么从知乎反爬的爪子底下把内容掏出来的?这正是下一章「详情页爬取与反爬内容提取」要展开的——同一台真实 Chrome,在页面上下文里提取结构化数据、模拟滚动、递归去重,以及在「加载体验」和「别把 Cookie 烧到失效」之间反复取平衡。
