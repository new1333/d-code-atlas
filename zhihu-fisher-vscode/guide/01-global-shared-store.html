全局共享状态容器 ​

本章属于 primitive 层。前置：无（全书地基章之一）。 学完你能：用一个模块级可变单例对象充当扩展全生命周期的共享内存，让命令、侧边栏、详情面板三条战线零胶水互相通信——同时清楚这套"全局可变"换来的是什么、付的代价是什么。

1. 为什么需要它（全书的地基） ​

本书讲的是一个 VSCode 扩展，它要在编辑器里塞下知乎的大部分功能：热榜侧边栏、推荐流、关注、搜索、详情面板、收藏夹、评论、扫码登录，还要在老板走过来时一键伪装成代码编辑器。这些功能跑起来后会同时存在好几条独立战线：

  • 命令处理：几十个 registered command，分散在不同文件，被 VSCode 在用户点按钮时回调。
  • 侧边栏 provider：四个 TreeDataProvider，各自管一份列表，按需刷新。
  • 详情面板：用户点开几篇文章，每篇一个 webview panel，互不阻塞。
  • 反爬浏览器：一台真实 Chrome 进程，按需为某篇文章开页面、跑 JS 提数据。
  • 状态栏项：状态栏上若干按钮，被 webview 切换时刷新。

这些战线彼此要找对方。点开详情要知道点的是哪条；投票命令要知道改的是哪个面板；反爬浏览器要知道现在为哪个面板服务；登录流程要把凭证交给侧边栏刷新用。

最朴素的解法是构造函数逐层传：构造 service 时把 panel map、browser、cookie、provider 全传进去；构造命令组时把 service 再传进去。这条路走得下去，但扩展每加一个子系统，就要改一串构造签名——命令注册表慢慢就长成了一个手写的依赖注入容器，胶水代码淹没业务逻辑。

本书后续几乎所有章节都站在这个矛盾的某一侧。本章作为第一章，先把这块地基摆出来：用一个模块级导出的可变对象，当扩展全生命周期的共享内存。后续章节（浏览器、侧边栏、详情、伪装、命令编排）都只往这个容器里塞自己的实例/数据，不再讲"为什么用全局容器"这件事。

2. 核心思想 ​

把扩展全生命周期的资源和数据都挂在一个模块级 export const 可变单例对象上，谁需要谁 import。

任何文件 import { Store } from "./stores" 拿到的都是同一个引用——单例性在 ES 模块层就保证了，无需任何 IoC 容器。

3. 心智模型 ​

容器是一个对象字面量，导出时所有字段都是空的：

text
Store = {
  context: null          // 扩展上下文槽位
  webviewMap: Map        // id → 详情面板实例
  browserInstance: null  // 反爬浏览器实例槽位
  pagesInstance: Map     // id → 浏览器页面实例（与面板共享同一 id）
  statusBarMap: Map
  Zhihu: {
    hot:   { list: [], isLoading: false }   // recommend/follow/search 同构
    cookie: ""                              // 凭证：一处写入，全局可读
    // ...
  }
}
