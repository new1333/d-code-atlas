详情页 HTML 渲染与双向消息 ​

你在 VSCode 里读一篇知乎长文，已经往下滚了很远，顺手展开了几条评论，评论框里还打了一半字；与此同时 AI 总结面板在转圈，你正等结果。就在这个节骨眼上，后台又加载出一批新回答。

如果每次后台一来数据，都把整个页面从头到脚重画一遍——你的滚动会弹回顶部，刚展开的评论重新收起，评论框里那半句话没了，AI 面板的转圈也没了。这一闪，阅读体验就塌了。

本章要解决的就是这件事：数据变了，但页面的阅读状态不能丢。

办法其实很朴素——结构性的大改动（换一篇回答、首次铺开页面）就用整页重画，运行时的小更新（导航计数变了、AI 出结果了）就只发一条点对点的消息，改哪个点就动哪个点。 两条更新路径并存，按「会不会打断阅读连续性」来选边。这一句话点透之后，后面我们用具体场景反复印证它，不再复述。

一个只有两个口子的前端 ​

先说清楚大背景：这个扩展把知乎文章渲染进 VSCode 的 WebView 里。WebView 就是一个被关进沙箱的浏览器页面，扩展端能改它的方式只有两种——这也是本章最底层的那两块基本件：

  • 整页重画：扩展端重新写一遍整份 HTML 文档，塞给 WebView，前端整套 DOM 被推倒重建。
  • 增量消息：扩展端发一条小消息过去，前端收到后自己动手，只改局部某个节点。

打比方：整页重画像是撕掉整张画布重画一幅；增量消息像是只往画上贴一张小纸条，原有的内容原封不动。

数据从哪儿来？真实 Chrome 在页面里爬回答、模拟滚动、批次加载，这一套已经在第 6 章「详情页爬取与反爬内容提取」讲透了，本章只关心爬到手的数据怎么变成页面、之后变了怎么不闪地推给前端。至于爬到的数据和渲染逻辑共同读写的那个共享内存（一条 webview 对应的文章对象、计数、相关问题列表，都挂在全局的 Store 上），它的来历第 1 章「全局共享状态容器」也讲透了——本章只看它如何同时充当「整页重画的输入」和「增量消息的数据来源」，被两条路径共用。

整页重画：把整篇文档一次性拼出来 ​

讲增量消息之前，得先看整页重画是怎么干的——因为这是 DOM 骨架唯一成型的方式。

扩展端有一个纯静态的渲染器，它不存任何状态，就是几个方法，分别拼出「加载中」「Cookie 过期」「出错」「文章正文」四种完整 HTML 文档。拼文章正文时，它从共享内存读出当前文章对象和当前那一条回答，再读七项用户配置（媒体怎么显示、字号大小之类），然后把十来个组件——回答正文、作者信息、投票按钮、导航条、相关问题图标——一个个拼成 HTML 片段，最后和 CSS、脚本一起替换进一个总模板里，得到的就一整份完整文档，一次性塞进 WebView。

这个拼装过程值得单独拎出来讲一个权衡。

权衡 2（服务端字符串拼装，而非前端框架）：这里选择在扩展端用「模板字符串 + 占位符替换」把整份文档拼好注入，前端不装 React、不装 Vue、不做任何打包。

  • 选择：扩展端当服务端渲染器，前端只收一份现成的 HTML 字符串。
  • 换来：渲染逻辑全在扩展端、看得见摸得着；配置项想注入就直接写进模板；十来个组件各自拼一段 HTML，能复用；最关键的是——前端零工程链，不用维护一套打包工具。
  • 代价：占位符替换很脆，替换有先后顺序、同名串要小心区分「只换一次」还是「全部换」，踩坑不易察觉；而且没有虚拟 DOM 帮你算 diff，所以任何运行时的动态变化都退不回这套拼装——只能走下面要讲的增量消息，手写。

换句话说，这套字符串拼装负责「骨架一次性成型」，但它天生不擅长「骨架不变、只是某块数据变了」的运行时更新。这正是为什么需要第二条路径。

灵魂权衡：什么时候重画，什么时候只贴纸条 ​

现在两条路径都摆出来了，真正的难题是：一次更新来了，该走哪条？

答案藏在一个叫 isLoaded 的开关里。首次把文章解析出来铺到屏幕上时，isLoaded 还是假，此时 DOM 骨架根本还没建，必须走整页重画，把骨架立起来；重画完才把它置真。从此之后，后台批次加载到新回答、用户关注了作者、AI 总结出结果，这些运行时小更新——因为骨架已经在那了——就统统只走增量消息，绝不再重画。

这就是本章的灵魂权衡。

权衡 1（两条更新路径并存）：

  • 选择：把更新明确分成两类。结构性变化——首屏、切换上一条/下一条回答、投票、批次加载结束——走整页重画；运行时高频小更新——导航计数、加载态、关注态、AI 结果、相关问题——走点对点的增量消息。
  • 换来：只要走的是增量消息那条路，用户的滚动位置、评论框里的半句话、已展开的评论、AI 面板的转圈状态，全数原样保留。长文阅读的连续性保住了。
  • 代价：两套更新逻辑并存，每个新来的更新点都得有人拍板「这条走哪条路」，心智负担不轻；增量消息这一头更麻烦——前端必须为每一条命令各写一段「找到对应节点 → 改它」的逻辑，几十条命令串成一条长长的判断链。而且重画那条路（比如投完票）照样会丢状态——这是被主动接受下来的代价，不是缺陷。

「数据变了却不动页面状态」到底是怎么发生的？下面这个几十行的脚本把两条路径并排演给你看。它用两个对象分别冒充「宿主侧（扩展）」和「页面前端侧」，前端维护一份当前 HTML、滚动位置和输入框内容，宿主侧只暴露 setHtml（整页重画）和 postMessage（点对点）两个方法。同一份导航计数更新，分别用两条路跑一遍，看滚动和输入框的存留差异。

ts
// 两条更新路径的最小对比：整页重画 vs 增量消息
// 宿主侧（扩展）只能通过两个口子改前端

// ---------- 前端侧：维护一份简化的 DOM + 滚动位置 + 输入态 ----------
const frontend = {
  html: '',        // 当前整页 HTML 字符串
  scrollTop: 0,    // 滚动位置
  inputValue: '',  // 评论框里的内容
  navText: '',     // 导航条文字（会被增量更新的那一小块）

  // 浏览器收到整份新 HTML 时：DOM 重建，连带清零滚动和输入
  render() {
    this.scrollTop = 0
    this.inputValue = ''
    console.log('  [前端] DOM 重建，滚动归零，输入框清空')
  },
}

// ---------- 宿主侧（扩展）：两个改前端的口子 ----------
const host = {
  // 口子一：整页重画 —— 重写整份 HTML 文档
  setHtml(nextHtml: string) {
    frontend.html = nextHtml
    frontend.render()          // 重建 DOM，滚动和输入被一起清零
  },
  // 口子二：增量消息 —— 发一条命令，前端自己改对应节点
  postMessage(msg: { command: string; loadedCount?: number; totalCount?: number }) {
    if (msg.command === 'updateNavInfo') {
      frontend.navText = `已加载 ${msg.loadedCount} / ${msg.totalCount}`
      // 只改这一处文字，不动 scrollTop、不动 inputValue
      console.log('  [前端] 局部改导航文字，滚动与输入框纹丝不动')
    }
  },
}

// ---------- 先铺一个有内容的页面 ----------
host.setHtml('<div>回答正文…<input/><div class="nav">0/0</div></div>')
frontend.scrollTop = 800          // 假装用户往下滚了很远
frontend.inputValue = '我正在写一条评论…'
console.log('用户当前状态：', { scrollTop: frontend.scrollTop, inputValue: frontend.inputValue })

console.log('\n=== 路径 A：整页重画更新导航计数 ===')
host.setHtml('<div>回答正文…<input/><div class="nav">10/30</div></div>')
console.log('重画后：', { scrollTop: frontend.scrollTop, inputValue: frontend.inputValue })

// 把用户状态恢复成「滚到 800、写了半句评论」，再走第二条路
frontend.scrollTop = 800
frontend.inputValue = '我正在写一条评论…'

console.log('\n=== 路径 B：增量消息更新导航计数 ===')
host.postMessage({ command: 'updateNavInfo', loadedCount: 10, totalCount: 30 })
console.log('增量后：', {
  scrollTop: frontend.scrollTop, inputValue: frontend.inputValue, navText: frontend.navText,
})

跑出来的对照一目了然：路径 A 重画之后，scrollTop 归零、inputValue 变成空串；路径 B 增量之后，scrollTop 还是 800、inputValue 还在，只有 navText 被更新了。「数据变了、状态不丢」就是这么来的——不是什么魔法，只是增量那条路压根不碰 DOM 的整体，只改那一个节点。

把两条路径并到一张图里看分工：

结构性变化                            运行时小更新
(首屏 / 切回答 / 投票 / 批次结束)      (导航计数 / 加载态 / 关注态 / AI结果 / 相关问题)
        │                                    │
        ▼                                    ▼
  isLoaded 为假（首屏）                isLoaded 为真
        │                                    │
        ▼                                    ▼
  updateWebview()                      postMessage({ command: ... })
  重写整份 webview.html                发一条小消息
        │                                    │
        ▼                                    ▼
  DOM 整体重建                          前端按 command 找到对应节点
  滚动归零 · 输入清空                    就地改它的文字或样式
  （接受的代价，因为主体整个换了）        滚动 / 输入 / 评论展开 / AI转圈 全保留

最后用一个并列的执行轨迹收束这一节。同一个时刻，两件事可以同时发生，却走截然不同的路：

  • 轨迹 A（结构性）：用户点「下一条回答」 → 前端发 loadNextAnswer → 扩展把当前回答索引加一 → 走整页重画 → DOM 重建、滚动归零。这里主动接受丢状态，因为回答主体整个换了，重画本就是合理的。
  • 轨迹 B（运行时，同一时刻）：后台批次加载又解析出 10 条新回答 → 扩展只发一条「导航计数 +10、加载完成」的增量消息 → 前端仅更新导航条那一行文字。此时用户滚到的位置、正在展开的评论，纹丝不动。

两条轨迹并列，正好把「按会不会打断连续性来选边」演透了：同样是「数据变了」，要不要重画，看的不是数据本身，而是这一变会不会把用户正捧着的阅读状态摔碎。

相关问题：边滚边加，却不刷屏 ​

你读得越深，知乎在侧栏露出的「相关问题」就越多。扩展希望把它们收集起来，攒成一个可点的列表。问题是这些问题是随着滚动一段段冒出来的，每滚一次就解析一次、加一次，怎么做到既越攒越全、又不在你正读着的时候突然闪一下？

答案是三个动作拧在一起：滚动后重复解析、按问题 id 去重、确有新增才发消息。

具体来说，每次批次加载新回答之后，扩展都在真实的页面上下文里重新解析一遍「相关问题」卡片，取出标题、链接、回答数、关注数，并用 URL 末尾那段当问题 id。解析回来的新问题，先拿一个集合装下所有已知 id，过滤掉重复的，只把没见过的合并进列表。最后判断一下：这一轮到底有没有真新增？有，才给前端发一条消息；没有，就一个字都不发。

权衡 3（相关问题：增量解析 + 去重 + 有变化才推）：

  • 选择：滚动后重复解析，用集合按 id 去重，只吸收新问题，且仅当确实有新增时才发消息。
  • 换来：相关问题列表随着你的阅读自动越攒越全，却不会重复刷屏；没新增时是零消息开销，前端完全无感。
  • 代价：发出去的那条消息，装的是去重之后的整份列表，而不是「这一轮多了哪几条」的差异。所以前端的活儿是「整体替换数据、重渲染那个区块」，并非字面意义上的「只追加新项」。

这里有个特别容易讲错的点，要专门点一句：消息里的负载是全量列表，不是差异清单。「增量」体现在三处——解析是滚动后增量触发的、合并时只吸收新增、没有新增就不发——而不是说消息里只装新条目。前端收到消息后，直接拿整份列表替换自己手里的数据，刷新图标上的计数；如果相关问题的弹窗此刻正开着，就连弹窗内容也整体刷新一遍（贴心的是，刷新时还记得你之前在弹窗里滚到哪儿）。

换句话说，权衡 3 做的是「发送侧省心」：扩展那边只管「有新增就推一份最新的全量」，把「和旧的合不合」这件事在发送前用集合去重解决掉；至于前端收到后要不要整体重画那一个区块，那是前端自己的事，不影响页面其它部分的阅读连续性。

AI 直答：先说「我在想」，再说结果 ​

点一下「AI 总结」按钮，会发生什么？后台其实要去真实浏览器里跑一趟两阶段的活儿（这趟轮询的细节第 6 章已展开，这里不重复），是耗时操作，可能要等好几秒。如果一声不吭地等结果出来再回，用户盯着一个毫无反馈的按钮，会以为卡死了。

于是这里定下一条三态的消息协议。收到 AI 总结或关键词解释请求的瞬间，扩展立刻先回一条 state: "loading"，前端马上让 AI 面板转起圈来。之后真正耗时的获取在后台进行，拿到结果了再回一条 state: "success"（带上关键词和回答内容），中途出错了就回 state: "error"（带上错误信息）。哪怕是「页面已经被关了」这种异常分支，也照样补发一条 error 态，不会让前端永远转下去。

前端那边维护着一个迷你状态机：面板里有三个区域——转圈、回答、报错——收到 loading 就亮转圈、藏另两个；收到 success 就藏转圈、亮回答、把回答内容塞进去；收到 error 就藏前两个、亮报错、写上错误原因。同一个面板、三套内容，按 state 字段切换显隐，整页一次都不刷。

权衡 4（AI 直答：加载 → 成功/失败 三态协议）：

  • 选择：对耗时异步操作，先立刻回一条「加载中」，拿到结果再回「成功/失败」。
  • 换来：异步操作变得可感知，前端能按状态分三种方式渲染（转圈 / 结果 / 报错），整个过程整页不刷新，用户不会被踢出阅读状态。
  • 代价：消息协议得提前约定好状态字段的含义，前端要为这一个面板维护一个三态的小状态机；而且只要协议里多出一种状态，前端就得跟着加一个分支，是一种约定换来的灵活性。

三态协议本质上是把「一次耗时调用」拆成了「先应答、后兑现」两步，让前端永远知道现在处于哪个阶段。这是增量消息这条大路径下的一个精细子模式：连「还在等」本身，也可以是一条消息。

小结 ​

这一章我们看清了一件事：在一个装不了前端框架、只能整页重画或发消息的 WebView 沙箱里，要保住长文阅读的连续性，靠的不是某一种更新方式，而是两条路径的分工——结构性大改动整页重画、运行时小更新走点对点增量消息，按会不会打断阅读来选边。

围绕这条主线，我们顺带看清了四个权衡：服务端字符串拼装换来前端零工程链，代价是没 diff、动态变化只能手写；两条路径并存换来状态不丢，代价是每个更新点都要人工判路、前端一条长判断链；相关问题靠去重和「有新增才推」换来不刷屏，代价是负载仍是全量列表；AI 直答靠三态协议换来异步可感知，代价是前端多一个状态机。它们都服务于同一件事：数据随时在变，但你捧着的那页书不能抖。

不过有一类「运行时变化」我们一直刻意绕开了——评论区。评论是父子两层结构，自己分页、自己展开收起，它用的不是本章这种「导航计数变了发一条」的简单增量，而是一套更讲究的游标续传。这正是下一章「评论父子树的游标分页」要拆的事。
