详情页 HTML 渲染与双向消息 ​

本章属于 composite 层。前置：详情页爬取与反爬内容提取、全局共享状态容器。 学完你能：在 WebView 这种「不能装前端框架」的沙箱里，把一份会变的数据交给前端，做到「数据变了」却「页面状态不丢」。

1. 为什么需要它 ​

想象一个具体场景：用户在 VSCode 里读一篇知乎长文，往下滚了大半页、展开了两条评论、刚点了「AI 总结」正在等结果。这时后台的批次加载又拉出了 10 条新回答。如果每次有新数据就把整个 webview 页面重画一遍，滚动条会弹回顶部、评论全部收起、AI 面板状态没了，用户立刻会想摔键盘。

上一章已经讲透了「在真实 Chrome 的页面上下文里爬回答、模拟滚动、批次上限、AI 直答两阶段轮询」这套数据获取流程。但那些被爬到的数据交给谁、变了之后怎么不闪地推给前端，正是本章要接的口子。

WebView 这个沙箱给扩展只留了两个口子改前端：要么把整个 HTML 文档整体重写（DOM 重建，一切归零），要么发一条消息让前端脚本自己改某块 DOM（局部，状态保留）。前者简单粗暴，后者精细但每个更新点都得手写。本章就是要把这两条路径拧成一套分工。

还要提一句：那块被两条路径共同读写的共享内存（Store.webviewMap），第 1 章「全局共享状态容器」已讲透。本章只看它作为「渲染输入 + 消息负载源」被两条路径共用的新侧面，不重讲它怎么成为扩展全生命周期的共享内存。

2. 核心思想 ​

结构性大改动用整页重画，运行时小更新走点对点增量消息。两条更新路径并存，按「会不会破坏阅读连续性」来选边。

什么叫结构性 vs 运行时？骨架本身要换的（首屏构建、切回答、投票后整片改）就是结构性；骨架不动、只是某块数据变了的（导航计数、加载态、关注按钮态、AI 结果）就是运行时。前者不在乎清掉状态，后者必须保住滚动位置、输入框、展开态。

3. 心智模型 ​

整条链路可以这样想：爬取层（前置章）把结构化数据写进 Store.webviewMap[id].article。从这个共享对象出发，有两条路可走：

  • 首屏或结构性变化时，HtmlRenderer 读这个对象 + 7 项用户配置，字符串拼出一份完整 HTML 文档，整体注入 webview。DOM 重建，状态归零。
  • 运行时小更新时，直接读这个对象的某个字段（比如计数、关注态），用 postMessage 把字段值点对点推给前端。前端按命令名找节点就地改，状态保留。

几个关键点：

  • HtmlRenderer 是个纯静态服务端渲染器：不持状态，4 个静态方法分别产出「加载中 / Cookie 过期 / 错误页 / 文章正文」四类完整 HTML 文档。文章正文那条按当前 article 状态（answerList[currentAnswerIndex]）和配置，把约 11 个组件的 HTML 拼成一份完整文档；整个产物是字符串，最终一次性塞给 webview。
  • WebView 的两个口子：扩展侧用 webview.html = ... 整页重画，或 webview.postMessage(...) 点对点；前端侧反向也是两个口子，acquireVsCodeApi().postMessage(...) 发给扩展，window.addEventListener('message', ...) 收扩展推过来的。
  • isLoaded 门控：第一次爬完时 isLoaded=false，走整页重画把骨架建起来；之后 isLoaded=true，再来的批次加载只走增量消息。这是「首次全画、之后增量」的总开关。
  • 前端消息处理按域拆分到多个脚本：core.ts 处理导航计数、问题详情、关注态、评论、导出弹窗等；相关问题、AI 直答各有专门脚本。每个脚本一段 addEventListener('message')，按命令名找到对应节点就地改。

4. 关键权衡 ​

两条路径并存，按「是否破坏连续性」来选边（灵魂权衡） ​

做了什么选择：让两条更新路径同时存在，每个更新点人工判断该走哪条。首屏、切回答、投票、批次结束这种「DOM 骨架本身要换」的，走整页重画；导航计数、加载态、关注按钮、AI 结果、评论这种「骨架不动只是数据变了」的，走增量消息。

换来什么：长文阅读的连续性。运行时高频小更新发生时，用户的滚动位置、正在展开的评论、正在输入的回复框、AI 面板的转圈状态全部保留。这是 webview 这种「页面即应用」场景里最关键的不变量。

代价是什么：两套更新逻辑并存，每个更新点都要人工判断该走哪条路；增量消息还得在前端为每条命令各写一段「找元素→改 DOM」的逻辑（一条长长的 if-else 链分散到各脚本里）。而且重画路径仍会丢状态，比如投票成功后会触发整页重画，用户当前的滚动位置就清零了。这是被主动接受的代价，不是缺陷。

这条权衡化解的本质矛盾是：「想让页面像桌面应用一样状态稳定」与「数据来源（真实 Chrome 异步爬取）一直在变」之间的冲突。任何把页面当应用用的宿主里（不只是 VSCode webview，Electron、浏览器扩展弹窗都是）都会撞上同一对矛盾，「骨架/数据」的二分法是通解。

服务端字符串拼装 HTML，而非前端框架 ​

做了什么选择：渲染逻辑全在扩展端，用「模板字符串 + 占位符替换」把 CSS、各组件 HTML、脚本一次性拼成完整文档注入 webview。前端不装框架、不打包、不跑 npm。

换来什么：整个渲染管线对扩展端透明可控。配置项可以就地注入（脚本块也通过占位符拿到当前回答索引、已加载数、相关问题数据等运行时参数），十来个组件可独立复用，完全没有前端工程链负担。改一个组件直接改 TS 函数返回字符串即可，不需要重新打包。

代价是什么：占位符替换本身很脆，替换顺序敏感、同名字符串要区分「替换一次」还是「替换全部」，踩坑了不会有编译错误，只会让某个区块莫名空白。更根本的代价是没有虚拟 DOM diff，任何动态变化都只能退回到上面那条增量消息手写。换句话说，这条权衡把「动态性」这个球彻底踢给了前一条的两条路径机制。

化解的本质矛盾是：「想把渲染逻辑集中可控」与「webview 沙箱不许装前端框架」之间的冲突。在受限宿主里，"服务端拼装"是唯一既不破约束又能复用组件的解。

相关问题的「解析时机增量 + Set 去重 + 有变化才推」 ​

做了什么选择：相关问题这块把"增量"做到了三层。① 解析时机：每次滚动加载新回答后再重复解析整张「相关问题」卡片，而不是只解析一次。② 合并：用 Set 按「问题 id」（从 URL 末端取）过滤，只 push 没见过的新问题。③ 发送门控：仅当 hasChanges 为真时才发消息，无新增则零消息开销。

换来什么：相关问题列表随阅读深入自动丰富，且不重复刷屏（同一个问题不会被加两次），无变化时前端完全无感。

代价是什么：消息负载仍然是「去重后的全量列表」，不是严格 diff。这一点容易被 outline 的措辞误导：代码里 notifyWebViewUpdateRelatedQuestions 推的是 article.relatedQuestions 整个数组，不是只含新增项的小数组。所以前端拿到后仍需整体重渲染该区块，并非字面意义的「只推新增项」。「增量」只体现在解析时机、Set 去重、hasChanges 门控这三处，不在负载形态上。

化解的本质矛盾是：「数据源（同一张卡片每次解析都可能多出几项）天然带增量特性」与「消息通道本身只支持整块替换」之间的冲突。当数据源天然增量、但消息通道是粗粒度时，"在发送侧做去重 + 门控"是让"增量"在"整块"通道上仍然有效的通用手法。

异步耗时操作用「加载→成功/失败」三态消息协议 ​

做了什么选择：对 AI 直答这类耗时异步操作（前置章已讲：ZhidaManager 要两阶段轮询，先等面板出现、再等"思考中"变成"完成"），约定一个三态协议。收到请求后立刻先回一条 state:"loading"，让前端马上显示 spinner；拿到结果后再回 state:"success" 带回答 HTML，或 state:"error" 带错误信息。多个失败分支（页面已关、异常）都补发 error 态。

换来什么：异步操作可感知。用户点了「AI 总结」按钮后立刻看到转圈，而不是盯着一个毫无反应的按钮怀疑扩展卡死。前端可以按状态分支渲染（转圈/结果/报错），整页不刷，其他状态（滚动、评论）纹丝不动。

代价是什么：消息协议必须约定状态字段语义（哪些命令有三态、loading 何时发、error 谁来补），前端要维护一个迷你的状态机：每个支持三态的命令都要记录「我现在在 loading / success / error 哪一态」，避免乱序消息把 UI 搞错乱。

化解的本质矛盾是：「宿主侧的耗时异步操作天然有"开始-中间-结束"三段」与「点对点消息本身是 fire-and-forget、无回执无状态」之间的冲突。把"三段性"显式编入消息协议，是让无状态通道承载有状态操作的标准做法，任何 RPC 风格的消息系统都会演化出这套。

5. 最小原理演示 ​

下面这段脚本不依赖真扩展，只演透权衡 1 的核心：同一份页面数据要更新时，整页重画会清掉输入态和滚动位置，增量消息不会。两个对象分别模拟宿主侧（扩展）和页面前端侧。

ts
// 模拟前端:维护「当前 DOM 字符串 + 滚动位置 + 输入框内容」
// 这三项一起代表"用户阅读连续性",是演示要保住的对象
class FakeFrontend {
  dom = "<div id='count'>0</div><input id='reply' value=''>";
  scrollY = 0;
  inputText = "";

  // 整页重画入口:扩展侧 webview.html = ... 触发
  // DOM 被整个换掉,scrollY 和 inputText 在新 DOM 上无处挂载,等于清零
  setHtml(newDom: string) {
    this.dom = newDom;
    this.scrollY = 0;
    this.inputText = "";
  }

  // 增量消息入口:扩展侧 postMessage 触发
  // 命令名告诉前端要改哪块,只动那块
  onMessage(msg: { command: string; data?: number }) {
    if (msg.command === "updateCount") {
      // 局部改 textContent,滚动位置和输入框都不动
      this.dom = this.dom.replace(
        /<div id='count'>\d+<\/div>/,
        `<div id='count'>${msg.data}</div>`
      );
    }
    // 真实前端里这里会有几十条 if-else,按命令名分支改不同节点
  }
}

// 模拟宿主侧(扩展):只有两个口子改前端
class FakeExtension {
  constructor(private frontend: FakeFrontend) {}

  // 路径一:整页重画,由"结构性变化"触发
  repaintAll(count: number) {
    this.frontend.setHtml(
      `<div id='count'>${count}</div><input id='reply' value=''>`
    );
  }

  // 路径二:增量消息,由"运行时小更新"触发
  postMessage(command: string, data: number) {
    this.frontend.onMessage({ command, data });
  }
}

// --- 演透两种路径的差异 ---

const fe = new FakeFrontend();
const ext = new FakeExtension(fe);

// 用户已经滚下去、正在打字
fe.scrollY = 800;
fe.inputText = "这段我想回复";

// 场景 A:扩展拿到新计数,误走"整页重画"
ext.repaintAll(10);
console.log(fe.scrollY, fe.inputText);
// => 0 ""    阅读连续性被打回原形

// 重置用户态
fe.scrollY = 800;
fe.inputText = "这段我想回复";

// 场景 B:同样拿到新计数,走"增量消息"
ext.postMessage("updateCount", 10);
console.log(fe.scrollY, fe.inputText);
// => 800 "这段我想回复"    连续性完整保留
console.log(fe.dom);
// => <div id='count'>10</div><input id='reply' value=''>

两段输出对比一目了然：同样的「数据变了」事件，走不同路径，用户的阅读状态存留完全相反。这就是 webview 渲染机制要在每个更新点反复掂量的那一下。

6. 执行轨迹 ​

把同一个时刻、两个不同性质的更新并列走一遍，这正是「按是否破坏连续性来选边」的活样本。

轨迹 A（结构性，走整页重画）：

  1. 用户点「下一条回答」按钮 → 前端 vscode.postMessage({command: "loadNextAnswer"})。
  2. 扩展收到，把 Store.webviewMap[id].article.currentAnswerIndex 加 1。
  3. 因为是切回答，DOM 骨架整个要换：调 updateWebview → HtmlRenderer.getArticleHtml 读新回答、读配置、拼组件 → webview.html = 新文档。
  4. DOM 重建，滚动归零。这是被主动接受的代价，因为新回答主体整个换掉了，旧的滚动位置本就没意义。

轨迹 B（运行时，走增量消息，与 A 同时发生）：

  1. 同一时刻后台批次加载又解析出 10 条回答 → article.loadedAnswerCount 从 5 变 15。
  2. 因为 isLoaded=true，只走增量：updateNavInfoViaMessage(false) → postMessage({command:"updateNavInfo", loadedCount:15, totalCount:30, isLoading:false})。
  3. 前端 core.ts 的 message 监听器按 updateNavInfo 分支找到导航条节点，改文字。
  4. 用户当前的滚动位置、正在展开的评论、AI 面板状态全部不受影响。

两条轨迹并列就演透了选边规则：「DOM 骨架换不换」是分水岭。骨架换，重画可接受；骨架不换，必须走增量。

7. 教学简化说明 ​

本章只演示了两条更新路径的骨架对比，故意省略：三十多条消息命令的逐条清单（只举 updateNavInfo、zhidaResult 几类代表）；HtmlRenderer 约 11 个组件的具体拼装顺序与占位符替换细节；媒体显示模式切换后已开 webview 的同步回路（由前端 storage-sync 脚本承担，超出本章 sourceFiles）；错误页/Cookie 过期页的模板内容；HTML→Markdown 导出的转换正则。

8. 小结 ​

webview 渲染机制的全部巧妙就在那一下选边：DOM 骨架换不换。骨架换，重画可接受，反正旧的滚动位置已经没意义；骨架不换，必须走增量，否则就把用户读了一半的状态全打回原形。这个二分法不依赖 VSCode，任何把页面当应用用的宿主里都成立。

骨架建好之后，下一章接评论区：评论是父子两层结构，每层各自维护一套游标（next/previous/offset），按需懒加载子评论并与已加载列表增量合并，又是"增量"思想在另一种数据形态上的落地。
