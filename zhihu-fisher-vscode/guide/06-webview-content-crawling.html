详情页爬取与反爬内容提取 ​

想象你在 VSCode 里点开一条知乎回答。你期望看到的，是你登录后刷知乎时那一模一样的画面——正文、作者、你点没点过赞、底下还挂着哪些回答，甚至能叫 AI 给你解释某个词啥意思。

但你后台去抓数据时，麻烦来了：直接对知乎发 HTTP 请求？多半 403，反爬直接挡掉。就算绕过了，拿到的也是一坨没跑过 JS 的原始 HTML——那些点开页面才懒加载出来的后续回答、那个只有登录账号才会亮起的「已赞同」按钮、那个点了才会弹出的 AI 面板，全都没有。

说白了，用户要的是「像登录态浏览器里看到的样子」，而不是一段干瘪的原始 HTML。

那这个扩展怎么做？它没有硬啃 HTTP，也没有去猜知乎的加密接口，而是走了第三条路。

核心思想：借一台渲染好的真浏览器，钻进去把数据抠出来 ​

前面第 3 章已经把那台「防反爬浏览器引擎」搭好了：一台单例 Chrome，启动时抹掉 navigator.webdriver、伪造 UA、注入已清洗的 Cookie，必要时还能模拟人类滚动。换句话说，「一台伪装好、已经登录的浏览器」这件事，前几章已经替我们解决了。

所以本章不再讲浏览器怎么伪装、Cookie 怎么清洗、全局单例容器怎么设计（这三件事分别在第 3、2、1 章讲透了）。本章要回答的是下一个问题：

拿到一台伪装好、已经渲染出页面的真浏览器之后，怎么从这个页面里把数据稳稳地抠出来？

答案是两步：

  1. 钻进页面的上下文里执行一段脚本（page.evaluate），把已经渲染好的 DOM 抠成结构化数据。打个比方：HTTP 抓包像隔着橱窗看送货单——只能看到货物清单，摸不到实物；而 page.evaluate 是直接走进店里、站在货架边上把东西拿下来，连刚补货的、只有会员才亮起来的那些都能拿到。
  2. 给「动态、会残留、会缓存旧结果」的页面配上一套一致性护栏，保证抠出来的东西确实是「这次的、新的、归属正确的」。

这个扩展里有两个对等的实例共用这套思路，却各自长出一套不同的护栏，正好把「在真实页面上下文里提数据」要付出的代价照得清清楚楚：

  • 详情页结构化提取：抠回答、抠作者、抠投票态，滚动触发懒加载，每批到上限就停。
  • 知乎直答 AI 提取：拦截 AI 链接、模拟点击面板、轮询等结果，用关键词校验拒绝旧缓存。

心智模型：六步走完一次提取 ​

不管哪个实例，流程都挂在同一条主干上：

借页面（复用伪装好的那台 Chrome）
   ↓
导航 + 等就绪（网络空闲只等 5 秒，超时不致命）
   ↓
页面上下文执行脚本，把渲染好的 DOM 抠成数据
   ↓
（多回答场景）模拟滚动触发懒加载，比滚动前后高度判断是否到底
   ↓
套一致性护栏（详情页：按 id 去重 + 每批上限；AI 直答：先关旧面板 + 关键词校验）
   ↓
结果回传前端；面板关闭时中断递归、归还页面实例

其中「网络空闲只等 5 秒、超时不致命」是知乎特有的坑：它的长连接特别多，HTTP 请求挂在那儿可能永远等不到「网络空闲」，于是这步被当成「最多等 5 秒的强制等待」，超时了也不报错，直接继续读页面。同理，「爬到一半发现登录态没了」直接复用第 2 章那套 DOM 登录墙探测，命中就早退去换登录提示页，不在这里重讲。

下面把两个实例分别拆开。

实例一：详情页——在渲染好的 DOM 里抠回答 ​

一次抠全量，再靠滚动补齐 ​

点开一个问题页，第一件事是在页面上下文里跑一段脚本，把页面上所有 .List-item（每条回答一个）抠成结构化对象：回答 id（name 属性）、作者、点赞数、投票态（赞同按钮的 active class）、正文 innerHTML。这是一次性的 page.evaluate，把整个列表读出来。

但知乎的问题页是懒加载的——首屏只给你十几条，往下滚才会继续吐。所以抠完一批后，还得模拟人类滚动触发下一批，然后再抠一次。

这就引出第一个要紧的问题：什么时候停？ 你不能无脑滚到底（一次拉太多，知乎会判定异常流量，把那个费劲弄来的签名 Cookie 直接烧到失效），也不能滚不够（用户翻到下面发现是空的）。这里的解法是「每批 N 条上限 + 递归滚动」。

四道护栏把滚动兜住 ​

光「滚动 → 抠」还不够，因为页面是活的，随时可能出状况。实际跑了三道护栏 + 一道去重：

抠全量回答 → 按 id 去重（Set），只算本批真正新增的
   → 本批新增 ≥ 上限？是 ⇒ 停，等用户翻到接近末尾再触发下一批（护栏②）
   → 否 ⇒ 滚动前记页面高度 → 模拟滚动 → 滚动后记高度
        → 高度没变？是 ⇒ 到底了，用实际已加载数覆盖页面声称的总数，停（护栏①）
        → 否 ⇒ 重新抠全量 → 回到开头（递归）

这里有个容易踩的坑：判断上限为什么用「本批新增」而不是「累计数」？ 因为递归每一轮都会重新解析全量回答——懒加载的 DOM 是动态的，上一轮抠到的节点可能已经被回收——只有用 Set 去重后算「本批新增」，这个数才等于真正新出现的回答数。要是拿累计数比，你永远滚不动，累计数一直在涨。

演示：一个声称有 50 个回答的页面 ​

下面这段骨架不连真知乎，而是配一段带定时器的本地 HTML 模拟懒加载，把「页面上下文抠数据、滚动前后比高度、批次到上限即停」演出来。重点是机制，不是能不能开箱即跑：

ts
// 详情页批次加载骨架（演透原理，不连真知乎）
async function crawlQuestionDetail(page: any, batchLimit = 10) {
  const loadedIds = new Set<string>();   // 去重护栏
  let batchNew = 0;

  // 在页面上下文里把已渲染的回答抠成结构化对象
  const parseAll = () =>
    page.evaluate(() =>
      [...document.querySelectorAll(".List-item")].map((el: any) => ({
        id: el.getAttribute("name"),
        author: el.querySelector(".AuthorInfo-name")?.textContent?.trim() ?? "",
        content: el.querySelector(".RichContent-inner")?.innerHTML ?? "",
      }))
    );

  for (;;) {
    const answers = await parseAll();           // ① 抠全量
    let newCount = 0;
    for (const a of answers)                    // ② 去重，只算本批新增
      if (!loadedIds.has(a.id)) { loadedIds.add(a.id); newCount++; }
    batchNew += newCount;

    if (batchNew >= batchLimit) return loadedIds.size; // ③ 批次上限即停（护栏②）

    const hBefore = await page.evaluate(() => document.body.scrollHeight);
    await page.evaluate(() => window.scrollBy(0, window.innerHeight)); // 模拟人类滚动
    await new Promise(r => setTimeout(r, 600));                         // 给懒加载留时间
    const hAfter = await page.evaluate(() => document.body.scrollHeight);

    if (hBefore === hAfter) return loadedIds.size;      // ④ 高度不变 ⇒ 到底（护栏①）
  }
}

执行轨迹（输入「50 个回答的问题页，每批上限 10」）：

导航 → 抠首批（初始化去重集合）→ 发现 8 条
滚动 → 高度变大 → 再抠 → 去重后新增 6 条 → 本批累计 14 ≥ 10 → 停 ✅
（导航计数显示「已加载 14 / 50」，批次复位；用户翻到接近末尾时再触发下一批）

这里正好演示了两道护栏怎么配合：批次上限让你「主动停一停」（省 Cookie、让用户先看到内容），到底探测让你「滚不动就认输」（防死循环）。一主动一被动，把一条无限滚动的页面折成可控的批次。

文章页和想法页（pin）不分批——它们就一整篇内容，被直接打包成「单个回答」塞进列表，loadComplete 直接置真，复用同一套渲染逻辑。批次只对「多回答的问题页」有意义。

实例二：知乎直答 AI——拦截外链 + 两阶段轮询 ​

第一步：把外链劫持成 VSCode 内入口 ​

知乎的「直答」AI 本来是个外链（指向 zhida.zhihu.com）。如果原样放出去，用户点了就在外部浏览器打开，脱离扩展控制。所以扩展在渲染 HTML 之前先扫一遍所有 <a>：命中直答域的，把原 href 剥掉、把关键词预解析存进 data-zhida-keyword 属性、把 onclick 改成本地的 openZhidaPanel 弹窗函数。

ts
// 渲染前：把直答外链劫持成弹窗入口
if (href.includes("zhida.zhihu.com")) {
  const kw = decodeURIComponent(new URL(href).searchParams.get("q") || "")
    || link.text().trim();              // 兜底：用链接纯文字当关键词
  link.attr("data-zhida-href", href);
  link.attr("data-zhida-keyword", kw);
  link.attr("href", "javascript:void(0)");   // 原外链失效
  link.attr("onclick", `openZhidaPanel('${href}', '${kw}')`);
}

点关键词从此不再跳外站，而是触发扩展里的 AI 提取流程。这一步是为后面「在页面上下文里点 AI 面板、抠答案」铺路——你得先有一个可控的入口，才谈得上控制它的生命周期。

第二步：点开面板，两阶段轮询抠答案 ​

入口有了，难点也来了：AI 面板是单例 DOM + 异步加载 + 会残留旧结果。这三条凑一块儿，直接坑死「傻等」式的轮询。

为什么不能傻等「完成回答」字样出现？因为这个面板是同一个容器被反复复用的——你上一轮问的答案还挂在 DOM 里没清掉，浏览器甚至可能缓存了上一次的结果。要是你只是「等『完成回答』出现就拿」，很可能拿到的是上一轮的旧答案，直接弹给用户，那就出洋相了。

所以 AI 直答配了两道护栏：

先关旧面板（点关闭按钮，等它从 DOM 消失，最多 2 秒）—— 杜绝抓到上一轮残留
   ↓
点击当前关键词链接（精确 href → 去来源参数模糊匹配 → q= 关键词，三级兜底）
   ↓
阶段①：等面板出现（5 秒）
   ↓
阶段②：等「思考中」状态（3 秒）—— 确认这次确实发起了新查询
   ↓
阶段③：轮询（最长 30 秒），直到「完成回答」出现 且 面板查询块文本包含本次关键词
        → 关键词不符？返回「继续等」中间态，不当成完成
   ↓
取走答案 HTML 回传前端

关键词校验是这里的关键一招：每次轮询都拿本次查询的关键词去核对面板顶部那个「你问的是 XXX」的查询块，对不上就判定为「这是旧缓存」，继续等。这一下把「新结果 vs 旧残留」的判断从「猜时间」变成了「查内容」，可靠得多。

ts
// 两阶段轮询 + 关键词校验（演透护栏三）
// waitFor(cond, ms) = 轮询到 cond 返回非空值就返回它，超过 ms 抛超时
async function fetchZhida(page: any, keyword: string) {
  await closeExistingPanel(page);                // 先关旧面板防残留
  await clickZhidaLink(page, keyword);           // 三级兜底找到要点的元素

  await waitFor(() => panelExists(page), 5000);  // 阶段①：等面板出现
  await waitFor(() => isThinking(page), 3000);   // 阶段②：等思考中（确认新查询）

  // 阶段③：轮询直到「完成回答」且关键词匹配
  return waitFor(async () => page.evaluate((kw) => {
    const q = document.querySelector('[data-testid="Block:zhida_answer_query_block"]');
    if (q && kw && !q.textContent?.includes(kw)) return null; // 关键词不符 = 旧缓存，继续等
    const btn = document.querySelector('[data-testid="Button:thinking_node"]');
    if (!btn?.textContent?.includes("完成回答")) return null;  // 还在思考
    return document.querySelector('[data-testid="Block:zhida_answer_result_block"]')
      ?.querySelector(".Render-markdown")?.innerHTML ?? null;
  }, keyword), 30000);
}

第三步：实在不行，换一个临时源页重试 ​

如果轮询超时、或者面板压根没出现，当前页面可能已经 DOM 漂移、或者 AI 入口没渲染出来。这时既不硬等，也不直接报错，而是新开一个临时源回答页重建上下文再点一次：

判定错误类型：只有「未找到 / 未出现」这类，且有源回答页 URL ⇒ 重试
   ↓
新开临时页 → 导航到源回答页 → 重跑 fetchZhida
   ↓
不管成败，finally 里关掉临时页（多消耗一个页面实例，但必须回收）
其它错误（超时、面板未出现）⇒ 直接放弃，回传错误

注意这道护栏能救的面是有限的——它只救「未找到/未出现」，其它错误直接放弃。这是个有意识的取舍：与其把所有错误都包装成「再试一次」（白费时间、多烧页面实例），不如只救那些「换上下文确实有希望」的情况。

关键权衡 ​

这一章真正值得带走的是下面这几个「选了 A，换来 B，代价是 C」。

1. 选「在真实浏览器页面上下文里提数据」，而非 HTTP 抓包或官方接口。 换来的是：能拿到 JS 渲染后的完整 DOM——懒加载出来的后续回答、当前账号的投票态、动态弹出的 AI 面板；并且天然绕过知乎对纯 HTTP 的反爬。 代价是：每个详情页要占一个完整的浏览器页面实例（重资源），而且页面是活的——会残留旧弹窗、会缓存上一轮结果、会异步加载——必须再叠一套一致性护栏，生命周期清理负担重。换句话说，HTTP 抓包是「轻但拿不到东西」，页面上下文是「拿得到但要伺候它」。上面那几道护栏、临时页重试，全是在还这笔「伺候」的债。

2. 详情页选「每批 N 条上限（默认 10）+ 递归滚动」，而非一次性滚到底。 换来的是：单次会话请求量可控，降低被知乎判成异常流量、把签名 Cookie 烧到失效的风险；用户也能尽快看到首批回答，不用干等。 代价是：必须同时维护去重（按回答 id）、到底探测（滚动前后高度不变即止）、页面被关就中断递归这三道护栏，且要在快读到末尾时再预触发下一批，衔接逻辑变复杂。这个「每批上限」是整个详情页唯一暴露给用户的可调旋钮（读自 VSCode 配置），它就是「加载体验 vs 烧 Cookie」这个权衡的具象化——调大，少点几次「加载更多」但更容易触发反爬；调小，安全但交互啰嗦。

3. AI 直答选「先关旧面板 + 关键词校验」两道护栏判定结果归属，而非简单等「完成回答」字样。 换来的是：能可靠区分「本次查询的新结果」与「上一轮残留 / 浏览器缓存的旧 AI 答案」，不会把旧答案误弹给用户。 代价是：轮询要同时驱动一个状态机（面板出现 → 思考中 → 完成），并引入一个「关键词未匹配就继续等」的中间态，而且每次必须先同步关闭旧面板、等它从 DOM 消失，交互链路明显变长。判断归属从「猜时间」升级成「查内容」，可靠性的提升是用更复杂的状态机换来的。

4. AI 直答失败时选「新开临时源页重试」，而非在当前页硬等或直接报错。 换来的是：当前页 DOM 漂移或 AI 入口没渲染时，能用源回答页重建上下文再点一次，抬高成功率。 代价是：多消耗一个页面实例且必须保证最终被关闭；而且重试只对「未找到/未出现」这类错误生效，其它错误直接放弃，护栏能救的面有限。这是「为可救的错误付出额外资源」的有意识取舍。

小结 ​

这一章讲的是：拿到一台伪装好的真浏览器之后，怎么从它渲染好的页面里稳稳抠数据。两条主线、一套核心思想——在页面上下文提数据 + 给动态页面配一致性护栏。详情页靠「去重 + 批次上限 + 到底探测」把无限滚动折成可控批次；AI 直答靠「先关旧面板 + 关键词校验」拒绝旧缓存、靠「换临时源页」兜底失败。护栏越严，结果越可靠，但状态机和资源开销也越重——这就是「在真实页面上下文里提数据」要还的债。

不过本章只讲了「把数据抠出来」。抠出来的回答列表、AI 答案，要怎么在 VSCode 的 webview 面板里渲染出来、用户翻页时怎么只推增量而不丢滚动位置、扩展和 webview 之间怎么双向通信——那是紧邻的下一章「详情页 HTML 渲染与双向消息」要解决的问题。
