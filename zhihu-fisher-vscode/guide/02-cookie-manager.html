Cookie 凭证的清洗与校验 ​

本章属于 primitive 层。前置：无（与「全局共享状态容器」并列的地基章）。 学完你能：用一句话讲清"为什么 Cookie 在发请求前必须经过『清洗 → 静态校验 → 动态探测』三道预处理，以及这三步为什么要拆成两层而不是合并成一个超级校验"。

1. 为什么需要它（设计动机） ​

上一章把模块级单例这个"放共享数据的槽"立起来了。但容器是骨架，真正活着的载荷要陆续往里填——本章关心的就是头一份载荷：用户从浏览器扒下来、要发给知乎的 Cookie 字符串。

想象你刚装好扩展，从浏览器 DevTools 里把整段 Cookie 复制粘贴进来。这一串字符大概是 key1=v1; key2=v2; key3=v3... 的样子，但你不知道里面其实塞了什么：

  • 百度统计、Google Analytics 这些第三方跟踪项会跟着一起被复制
  • 知乎最关键的那个签名/登录凭证未必还在里面（也许浏览器里早过期被清掉了）
  • 即便都在，凭证可能已经失效，但字符串本身不会告诉你

如果这一坨原样发出去，后果是一连串"程序坏了"的错觉：

  • 第三方项一起发 → 知乎直接 403
  • 关键项缺失 → 被静默重定向到别处
  • 已过期 → 撞上一面登录墙

用户看到一片空白，根本分不清是 Cookie 出了问题，还是程序坏了。这就是本章要解决的矛盾：用户给的是一个不可信、又无法自校验的字符串，但下游每条请求通道对它的"干净度"要求严苛且各不相同。所以入口处必须先做预处理，再放行。

2. 核心思想 ​

Cookie 不是一份静态凭证，而是一个会脏、会缺、会失效的活动状态——所以入口处必须做"清洗 → 静态校验 → 动态探测"三道预处理，把不可用的 Cookie 在真正发请求之前拦下或修正。

打个比方：从浏览器扒 Cookie 像从旧钱包里倒出一沓纸，里面混着过期的超市优惠券、别人的名片、还有你真正要用的那张会员卡。你不能整沓塞进刷卡机，得先抖掉杂物（清洗）、确认会员卡还在（静态校验）、刷一下看读卡器认不认（动态探测）。

3. 心智模型（Cookie 从输入到被判失效的生命周期） ​

一段 Cookie 从被粘进来到被判定失效，要走七步：

  1. 入库：三个入口之一——用户手粘、扫码登录回传、或旧格式历史配置的兼容迁移
  2. 入库即清洗：过一遍黑名单前缀过滤，抖掉已知第三方项
  3. 双写：同时写进内存槽（运行时读）和持久化配置（重启恢复）
  4. 用前静态校验：查关键安全项的 key 是否存在；缺则弹窗引导用户重新登录
  5. 按通道再清洗：发请求前，HTTP 通道再过一遍全量过滤；浏览器通道只定向移除一个特定项
  6. 请求发出
  7. 动态探测兜底：返回页面里冒出登录按钮 → 反推 Cookie 已失效 → 去抖提示

把这条流程压成一张分类表，三种病对应三种处理：

病症状处理
脏含第三方统计项清洗
缺缺关键安全项静态校验警告
失效过期动态探测反推

后文四个关键权衡，全部围绕"这三种处理各自怎么做、为什么这么做"。

4. 关键权衡 ​

4.1 黑名单过滤而非白名单——换新增项的零改码 ​

理论上"只保留知乎域 Cookie"最稳妥的做法是白名单：列出所有已知知乎 Cookie 名，不在表里的全删。但知乎的 Cookie 名多，且会随版本变动。

本机制改用黑名单：只列已知的第三方前缀（百度统计、百度搜索、Google Analytics 等），不在表里的全部保留。

换来：知乎新增一个自有 Cookie 时无需改代码即可保留——只关心"是不是已知的脏"，不关心"是不是知乎的"。

代价：当出现一个未列入黑名单的新第三方跟踪项时，它会被原样放行。这张表需要持续维护。

化解的本质矛盾：维护成本 vs 漏放风险。白名单的维护成本随知乎自家 Cookie 增长，黑名单的维护成本随第三方跟踪项增长，后者变动频率更低，所以选了黑名单。

一个旁证：那个会引起重定向的 BEC 项本身是知乎域 Cookie，却被额外塞进了第三方黑名单里。这说明实现是黑名单，命名却写的是"只保留知乎 Cookie"（白名单语义）——名字描述的是目标，代码做的是手段。

4.2 静态校验只查"有没有"，不查"对不对" ​

校验函数解析出所有 key，判断"请求签名项"（__zse_ck）与"登录凭证项"（z_c0）是否都存在，返回布尔。完全不校验值。

换来：纯本地、零网络、毫秒级的快速预检，一次 Set.has 就够了。

代价：key 在但值已过期这种最常见的失效，本地校验根本看不出来。

化解的本质矛盾：校验速度 vs 校验深度。要把"值还活不活"查到底，就必须发请求；可发请求又贵又慢。所以拆成两层：静态层负责"明显残缺"，动态层负责"看似完整其实死了"。

4.3 失效判定靠"副作用"反推，而非主动校验 ​

Cookie 字符串里没有可靠的有效期字段，无法主动判断是否失效。本机制的做法是：先发一次真实请求，再看返回页面里有没有冒出登录按钮（选择器 .SignFlow-submitButton）——找到按钮就反推 Cookie 已失效。

换来：完全不必理解知乎的会话协议或加密机制，只看最终呈现给用户的页面长什么样。

代价：必须承受一次失败请求才能知道；且反推准确性强依赖那个登录按钮的 DOM 选择器不被知乎改版。

化解的本质矛盾：协议理解成本 vs 改版脆弱性。要"主动校验"就得逆向知乎的会话加密，根本无从下手；要"反推"只需绑定一个 DOM 选择器，一个选得好的选择器能用很久。选了后者。

同一原理有两种载体：在 Puppeteer 页面上下文里用 page.$(selector) 查；在纯 fetch 通道里没有 page 对象，就用 cheerio 在返回 HTML 里查同一个选择器。原理一致，载体随通道变。

4.4 清洗策略按传输通道分化 ​

两类通道对 Cookie 杂质的容忍度完全不同，所以清洗力度也不同：

  • HTTP 通道（热榜、列表、API）：第三方 Cookie 一旦同发就会被知乎回 403，所以走全量过滤
  • 真实浏览器通道（详情页爬取）：对第三方容忍度高，真正惹麻烦的只是一个会触发"重定向到热榜"的特定项（BEC），所以只做定向移除

换来：按各通道的真实威胁模型精准处理，不会"为了统一而误伤"。

代价：两套清洗逻辑并存，调用方必须知道该用哪套；调用点甚至出现"两种都调一遍"的防御性重复（先定向移除、再全量过滤）。

化解的本质矛盾：单一处理简化 vs 精准匹配。两类通道的失败模式（403 vs 重定向）完全不同，一类要"全清"，一类要"只拔刺"。强行合并只会让其中一类失败。

5. 最小原理演示 ​

下面这段脚本只演透三件套的原理骨架——黑名单过滤（对应 §4.1）、静态校验只查存在性（对应 §4.2）、DOM 登录墙反推（对应 §4.3）。每一步对应一条权衡，与各权衡的代价一并可见。

ts
// 用户从浏览器整段扒下来的 Cookie（含杂质 + 关键项）
const rawCookie = "z_c0=AAA; __zse_ck=BBB; Hm_lvt_xxx=ccc; _ga=ddd; BEC=eee; _gid=fff";

// 已知第三方前缀表（节选，实际更长）
// 注意 BEC 也被列进来：它是知乎域但会触发重定向，所以一并剔除
const thirdPartyPrefixes = [
  "Hm_lvt", "HMACCOUNT",
  "BAIDUID", "BDUSS",
  "_ga", "_gid",
  "BEC",
];

// 清洗：黑名单匹配规则为「等于前缀 / 以前缀加 _ 或 . 开头」
function clean(raw: string): string {
  return raw
    .split(/;\s*/)
    .filter((pair) => {
      const key = pair.split("=")[0]?.trim();
      if (!key) return false;
      return !thirdPartyPrefixes.some(
        (p) => key === p || key.startsWith(p + "_") || key.startsWith(p + ".")
      );
    })
    .join("; ");
}

// 静态校验：只查关键安全项的 key 是否存在，不查值
// 通过只代表"存在"，不代表"有效"——值可能早已过期
function isComplete(cleaned: string): boolean {
  const keys = new Set(
    cleaned.split(/;\s*/).map((p) => p.split("=")[0]?.trim())
  );
  return keys.has("z_c0") && keys.has("__zse_ck");
}

// 动态探测：返回页面里冒出登录按钮，就反推 Cookie 已失效
// 真实环境里这段 HTML 由 fetch 或 Puppeteer 返回
const LOGIN_WALL_SELECTOR = ".SignFlow-submitButton";
function looksLikeLoginWall(html: string): boolean {
  return html.includes(LOGIN_WALL_SELECTOR);
}

// 演一遍
const cleaned = clean(rawCookie);
console.log("清洗后:", cleaned);
console.log("静态校验通过?", isComplete(cleaned));

// 假设 Cookie 实际已过期，请求返回的 HTML 长这样
const fakeResponseHtml =
  "<div>...</div><button class='SignFlow-submitButton'>登录</button>";
console.log("动态探测判失效?", looksLikeLoginWall(fakeResponseHtml));
// 通过了静态校验的 Cookie，依然可能被动态探测判失效——两层缺一不可

跑一下：清洗后只剩 z_c0=AAA; __zse_ck=BBB，静态校验通过，但动态探测依然判定失效。这正是 §4.2 的代价在运行时的具象——本地校验看不见"值死了"。

6. 执行轨迹 ​

拿一段具体输入走一遍七步：

输入（用户粘的）：z_c0=AAA; __zse_ck=BBB; Hm_lvt_xxx=ccc; _ga=ddd; BEC=eee

清洗（黑名单逐项匹配）：

项命中规则处理
z_c0不匹配任何前缀保留
__zse_ck不匹配保留
Hm_lvt_xxx匹配 Hm_lvt_剔除
_ga等于 _ga剔除
BEC等于 BEC（知乎域但被列黑名单）剔除

清洗结果：z_c0=AAA; __zse_ck=BBB

静态校验：z_c0 在、__zse_ck 在 → 通过（注意：通过只代表存在，不代表有效）

假设值实际已过期 → 发请求 → 返回 HTML 含 .SignFlow-submitButton → 动态探测反推"已失效" → 去抖提示用户更新

这条轨迹演的是核心思想：通过了静态校验的 Cookie，依然可能被动态探测判失效——两层缺一不可。

7. 教学简化说明 ​

本章演示故意省略了 VSCode 配置持久化与弹窗 UI、扫码登录回传链路、旧格式 JSON 自动迁移、真实网络请求与真实浏览器注入、去抖定时器的工程化包装。这些是工程脚手架，不是原理；想看实现可读 src/core/zhihu/cookie/index.ts。

8. 小结 ​

干净的 Cookie 不等于"对的 Cookie"——这是本章最该带走的一句话。黑名单过滤只解决脏，静态校验只解决缺，动态探测只解决失效；三个步骤各管一类病，谁也不能替代谁。但光有干净的 Cookie 还不够，知乎反爬逼着我们必须用真实浏览器执行 JS 才能把签名 Cookie 写活，那就是下一章「防反爬浏览器引擎」要做的事。
