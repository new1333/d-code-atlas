Cookie 凭证的清洗与校验 ​

一个会让人抓狂的清晨 ​

想象这个场景：你兴冲冲地从浏览器把知乎的 Cookie 整段复制进了插件，以为马上就能刷到热榜。结果点开一看——什么都没有。不是报错，不是崩溃，就是安安静静一片空。

到底是 Cookie 坏了，还是程序坏了？你完全无从判断。更可能的情况是：程序正拿着一串「带病」的 Cookie 在拼命请求，被知乎一遍遍拒之门外，而这一切对用户是静默的。

这一章要解决的，就是这一件事——别让有问题的 Cookie，还有机会被发出去。 用户给的那一坨字符串，进门前必须先过几道关。

先把 Cookie 想清楚：它是一坨「会生病」的字符串 ​

在写任何处理逻辑之前，先想清楚 Cookie 到底是什么。它不是什么神秘凭证，剥到最底下，就是一串用 ; 分隔的 key=value：

z_c0=AAA; __zse_ck=BBB; Hm_lvt_xxx=ccc; _ga=ddd; BEC=eee

其中真正能证明「你登录了知乎」的，只有那么两三个 key——比如 z_c0（登录凭证）和 __zse_ck（请求签名）。剩下那一大串，是浏览器去各种网站溜达时顺手攒下的：百度统计、Google Analytics、各种跟踪器。

把这样一坨东西原样发给知乎，会出三种「病」：

  • 脏：夹带了第三方站点的 Cookie。知乎一看你请求里带着百度、谷歌的痕迹，直接判你是机器人，回个 403。
  • 缺：少了那个真正能证明身份的关键 key。带着残缺凭证去，等于没登录。
  • 失效：key 都在，但值过期了。字符串本身看不出有效期，你只能发出去试。

这三种病，对应的治法完全不同。清洗治脏，静态校验治缺，动态探测治失效。这三道关是这一章的主线。

说人话就是：Cookie 不是「设定一次就永远有效」的凭证，而是一个「会变脏、会缺件、会过期」的活动状态。所以入口处不能只是「存起来」，必须「先处理再说」。

第一道关：清洗——把第三方 Cookie 刷掉 ​

先解决「脏」。

最直觉的清洗方式是白名单：列出所有知乎自己用的 Cookie 名，只留这些，其余全删。听起来最干净。但知乎的 Cookie 名会随版本变动，今天你列全了，明天它加一个新名字，白名单就漏了——一个合法的知乎 Cookie 被误删，请求照样废。

于是这里反过来，用黑名单：只列几个已知的第三方前缀（百度统计的 Hm_lvt、百度的 BAIDUID、谷歌的 _ga 等），凡是 key 等于这些前缀、或者以「前缀加 _/.」开头的，统统剔除，剩下的全留。判定逻辑长这样：

ts
const THIRD_PARTY_PREFIXES = [
  "HMACCOUNT", "Hm_lvt", "Hm_lpvt",   // 百度统计
  "BAIDUID", "BDUSS", "BIDUPSID",     // 百度搜索
  "_ga", "_gid", "_gat",              // Google Analytics
];

// 给一段原始 Cookie，刷掉第三方，返回干净的那串
function clean(cookie: string): string {
  const kept = cookie.split(/;\s*/).filter((e) => {
    const key = e.split("=")[0]?.trim();
    if (!key) return false;
    const isThirdParty = THIRD_PARTY_PREFIXES.some(
      (p) => key === p || key.startsWith(p + "_") || key.startsWith(p + ".")
    );
    return !isThirdParty; // 不是第三方，才保留
  });
  return kept.join("; ");
}

跑一下你给的那坨脏 Cookie：

ts
const raw = "z_c0=AAA; __zse_ck=BBB; Hm_lvt_xxx=ccc; _ga=ddd; BEC=eee";
console.log(clean(raw));
// => "z_c0=AAA; __zse_ck=BBB; BEC=eee"

百度统计项、谷歌项刷掉了，知乎自己的留下了。这就是清洗。这里有个值得停一下的设计选择，后面「关键权衡」会展开。

第二道关：静态校验——只查「有没有」，不查「对不对」 ​

「脏」治好了，现在看「缺」。

洗完之后能不能直接发请求？还不行，得先确认那两个能证明身份的关键 key 还在不在。要查的是 __zse_ck（请求签名）和 z_c0（登录凭证）。但注意，这一关只查 key 在不在，完全不查它的值对不对、有没有过期：

ts
const REQUIRED_KEYS = {
  SIGN: "__zse_ck",   // 请求签名，发请求必备
  LOGIN: "z_c0",      // 登录凭证，证明你是登录态
};

// 检查关键 key 是否齐全；只查「在不在」，返回缺了哪些
function checkComplete(cookie: string): { ok: boolean; missing: string[] } {
  const keys = new Set(
    cookie.split(/;\s*/).map((e) => e.split("=")[0]?.trim()).filter(Boolean)
  );
  const missing = Object.entries(REQUIRED_KEYS)
    .filter(([, k]) => !keys.has(k as string))
    .map(([name]) => name);
  return { ok: missing.length === 0, missing };
}

为什么只查存在性？因为「在不在」这件事是纯本地判断，拆个字符串就行——毫秒级、零网络。这一关过了，你至少能保证：发出去的请求带着完整的关键项，不会被知乎在最基本的安全校验上一票否决。

缺了怎么办？这里不硬猜，直接算出缺的是哪一项，弹个窗引导用户去重新登录（扫码或手粘）。绝不带着残缺的 Cookie 往下走。

但这里埋着一个雷：key 在，不代表它还有效。这就是为什么必须有第三道关。

第三道关：动态探测——靠「副作用」反推它是不是失效了 ​

前两道都过，Cookie 看起来「干净又完整」。但它可能已经过期了。问题是，Cookie 字符串里没有一个可靠的「有效期」字段，你光看那串字符，根本无从判断它是不是死的。

那怎么办？唯一可靠的办法，是真去问一次知乎。但不是问知乎「这个 Cookie 有效吗」（知乎没这种接口），而是发一次真实请求，看它反应：如果返回的页面里冒出了一个登录按钮——那就说明知乎没认出你，Cookie 失效了。

这就是「靠副作用反推」：不直接校验凭证，而是观察一次请求造成的后果。

ts
const LOGIN_WALL_SELECTOR = ".SignFlow-submitButton";

// 给一段「请求返回的 HTML」，看里面有没有登录按钮；
// 有 → 反推 Cookie 已失效
function looksLikeLoginWall(html: string): boolean {
  return html.includes(LOGIN_WALL_SELECTOR);
}

// 模拟一次「Cookie 已过期」的返回：页面里冒出了登录按钮
const fakeExpiredResponse = '<button class="SignFlow-submitButton">登录</button>';
console.log(looksLikeLoginWall(fakeExpiredResponse)); // => true，判定失效

这里的关键不在那个选择器写得多巧妙，而在整个判定的思路：放弃去理解知乎那套复杂的会话协议和加密，转而观察一个谁都看得懂的副作用——页面有没有逼你登录。

这套「看登录按钮」的探测，在两处地方都在用：真实浏览器通道里，是拿着浏览器页面对象去页面里找这个选择器；纯 HTTP 通道里没有页面对象，就在抓回来的 HTML 字符串里内联找同一个选择器。一个原理，两处地方各用各的法子。

注意这三道的递进关系：通过了静态校验的 Cookie，依然可能被动态探测判失效。 第二道说「key 都在」，第三道可能说「但它死了」。两层缺一不可。

清洗还要分通道：同样的「脏」，威胁不一样 ​

到这里三道关齐了。但清洗这一道还有个进阶细节。

同样是「洗 Cookie」，发请求时其实分两条通道，它们对杂质的容忍度天差地别：

  • 原始 HTTP 通道（拉热榜、列表、调 API）：对第三方 Cookie 零容忍。多发一个百度的 Cookie，知乎就回 403。所以走全量过滤，把黑名单里那一票全刷掉。
  • 真实浏览器通道（用真实浏览器打开详情页）：浏览器本身就带一堆 Cookie，知乎对这条通道的杂质容忍度高。真正会惹麻烦的，只有一个特定的项（BEC）——带上它，知乎会把你重定向到热榜页，详情页根本打不开。所以这条通道只做定向移除，单独把这一项抠掉就行：
ts
// 只移除单个已知会惹麻烦的项（BEC：避免被重定向到热榜）
function removeOnly(cookie: string, target: string): string {
  return cookie
    .split(/;\s*/)
    .filter((e) => e.split("=")[0]?.trim() !== target)
    .join("; ");
}

换句话说，不是所有地方都用同一把大刷子，而是看每条通道真正怕什么，精准处理。

串起来：一个 Cookie 从进门到被判失效 ​

把前面几块拼起来，一段 Cookie 的完整生命是这样的：

入库（手粘 / 扫码回传 / 旧格式迁移）
   │
   ▼
① 清洗（黑名单刷掉第三方）         ← 治脏
   │
   ▼
② 双写（内存槽 + 持久化配置）       ← 读时内存优先，防「刚扫码还没落盘」
   │
   ▼
③ 用前静态校验（关键 key 齐不齐）   ← 治缺；缺则弹窗引导登录
   │
   ▼
④ 按通道再清洗                     ← HTTP 全量过滤 / 浏览器定向移除
   │
   ▼
⑤ 发请求
   │
   ▼
⑥ 动态探测兜底                     ← 治失效；撞登录墙就提示用户更新

（那个「内存槽」是第 1 章搭的全局共享状态容器，这里只往里放 Cookie，不展开它本身。）还有个工程小细节：失效提示会带去抖——好几个列表同时撞上失效时，短时间内只弹一次窗，免得刷屏。这种包装点到为止，原理还是上面那三道。

最后给一个能直接 bun run（或 node）跑的完整脚本，把三道串起来看一遍：

ts
// cookie-lifecycle.ts
const THIRD_PARTY_PREFIXES = ["HMACCOUNT","Hm_lvt","Hm_lpvt","BAIDUID","BDUSS","BIDUPSID","_ga","_gid","_gat"];
const REQUIRED_KEYS = { SIGN: "__zse_ck", LOGIN: "z_c0" };
const LOGIN_WALL_SELECTOR = ".SignFlow-submitButton";

function clean(cookie: string) {
  return cookie.split(/;\s*/).filter((e) => {
    const key = e.split("=")[0]?.trim();
    if (!key) return false;
    return !THIRD_PARTY_PREFIXES.some(
      (p) => key === p || key.startsWith(p + "_") || key.startsWith(p + ".")
    );
  }).join("; ");
}
function checkComplete(cookie: string) {
  const keys = new Set(cookie.split(/;\s*/).map((e) => e.split("=")[0]?.trim()).filter(Boolean));
  const missing = Object.entries(REQUIRED_KEYS).filter(([, k]) => !keys.has(k)).map(([n]) => n);
  return { ok: missing.length === 0, missing };
}
function looksLikeLoginWall(html: string) { return html.includes(LOGIN_WALL_SELECTOR); }

// 1) 用户粘进来一坨脏 Cookie
const raw = "z_c0=AAA; __zse_ck=BBB; Hm_lvt_xxx=ccc; _ga=ddd; BEC=eee";
console.log("原始 Cookie:\n  " + raw);

// 2) 清洗
const cleaned = clean(raw);
console.log("清洗后:\n  " + cleaned);

// 3) 静态校验
const { ok, missing } = checkComplete(cleaned);
console.log(ok ? "静态校验: 关键项齐全（但只代表'在'，不代表'有效'）"
               : "静态校验: 缺 " + missing.join(", ") + "，弹窗引导重新登录");

// 4) 假设校验过了，发请求；模拟一个「已过期」的返回（页面冒出登录按钮）
const fakeExpiredHtml = '<button class="SignFlow-submitButton">登录</button>';
console.log(looksLikeLoginWall(fakeExpiredHtml)
  ? "动态探测: 撞登录墙 → Cookie 已失效，提示用户更新"
  : "动态探测: 正常");

输出会告诉你：清洗刷掉了第三方，校验发现关键项齐全，但动态探测最后判定它其实已经失效——这正是这一章想演透的那句话：干净、齐全，不等于还活着。

关键权衡 ​

这一章的机制不薄，下面把四条最核心的「选择 → 换来 → 代价」逐条摊开。

权衡一：清洗用黑名单，不用白名单 ​

选择：用一张「已知第三方前缀」黑名单做过滤，命中前缀的才删，其余全留。

为什么不用看似更稳的白名单（只留知乎自己的 Cookie）？因为知乎的 Cookie 名多、且会随版本变。一旦知乎新增一个自有 Cookie 名，你的白名单没跟上，这个合法 Cookie 就被误删，请求直接坏掉——而你很难第一时间察觉。

换来的是：知乎以后再加任何新的自有 Cookie，都不用改一行代码就能自动保留。维护面从「得追着知乎的 Cookie 名跑」缩小到「只需维护一张固定的第三方前缀表」。

代价是：一旦冒出一个没被列进黑名单的新第三方跟踪项（比如某天知乎页面接了个新的统计 SDK），它会被原样放行，照样可能在 HTTP 通道上招来 403。这张表需要持续盯、持续补。换句话说，黑名单赌的是「第三方跟踪项是有限且可枚举的」，一旦赌错，漏网的杂质会悄悄混过去。

权衡二：静态校验只查「有没有」，不查「对不对」 ​

选择：校验只判断 __zse_ck 和 z_c0 这两个关键 key 是否存在，完全不校验它们的值是否还有效。

换来的是：一道纯本地、零网络、毫秒级的快速预检。它能在发请求之前，就拦下「用户复制的时候漏了关键项」这种最常见的残缺输入，避免把明显残废的 Cookie 送上网白白浪费一次请求。

代价是：它管不了「key 在、但值已过期」这种最常见的失效场景——而这恰恰是用户最常遇到的（昨天还能用，今天就不行了）。所以校验被刻意拆成两层：静态存在性（本地、快、负责拦残缺）+ 动态有效性（联网、慢、负责查死活）。静态这层管不到的部分，必须老老实实交给动态那层兜底，谁也替不了谁。

权衡三：失效判定靠「副作用」反推，而不是主动校验 ​

选择：不试图读懂知乎那套会话协议，而是发一次真实请求，靠「返回页面里有没有冒出登录按钮」来反推 Cookie 是否失效。

换来的是：完全不必理解知乎的会话协议和加密。知乎那套登录态怎么签发、签名怎么算，统统可以当成黑盒——你只需要认得一个登录按钮长什么样。这是一个「用一次失败请求的代价，换来对复杂协议零依赖」的划算买卖。

代价有两个。第一，必须承受一次注定失败的真实请求（静态校验拦不住的失效，要等请求发出去才知道），多少有些浪费。第二，也是更要命的：这个反推的准确性，强依赖那个登录按钮的 DOM 选择器不被知乎改版。一旦知乎哪天把 .SignFlow-submitButton 换了名字或换了结构，你的「失效探测器」会突然哑火——失效了也探测不出来，于是用户又开始看到一片空白，回到本章开头那个让人抓狂的清晨。

权衡四：清洗策略按通道分化，而不是全局一刀切 ​

选择：HTTP 通道走「全量过滤」（黑名单全刷），真实浏览器通道只走「定向移除」（只抠掉 BEC）。

换来的是：按每条通道的真实威胁模型精准处理。HTTP 通道怕的是「任何」第三方杂质（一发就 403），所以下重手；浏览器通道根本不怕一般的第三方 Cookie（浏览器自己就带一肚子），唯一怕的只是 BEC 这个会触发重定向的特定项，所以只精准动它一个。一刀切地给浏览器通道也做全量过滤，要么没必要（徒增开销），要么反而可能洗掉浏览器正常需要的东西。

代价是：存在两套清洗逻辑，调用方必须知道自己该用哪套。这件事复杂到什么程度呢——在某些调用点，甚至出现了「两种都调一遍」（先定向移除、再全量过滤）的防御性写法，就为了万无一失。这是「精准」的必然伴生物：每多一种威胁模型，就多一条必须被正确选择的代码路径，调用方的认知负担和出错概率也随之上升。

小结 ​

这一章把「Cookie」从一个静态凭证，重新定义成一个会脏、会缺、会失效的活动状态，并在入口处摆了三道关——清洗、静态校验、动态探测——外加一道分通道的精细化清洗。核心就一句话：让任何一份有问题的 Cookie，都没有机会带着脏污或缺件被发出去；至于它是不是还活着，只有真发一次请求、看知乎的反应才知道。

这套预处理，是后续每一个请求通道都绕不开的前提。但哪怕 Cookie 干净又有效，纯 HTTP 去拉知乎的内容，仍然很容易被反爬识破——下一章就会讲，为什么有些时候必须放弃这种轻量请求，转而启动一台真实的 Chrome 浏览器来正面对抗知乎的反爬。
