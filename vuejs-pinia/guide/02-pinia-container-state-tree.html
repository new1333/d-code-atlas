Pinia 容器与集中式状态树 ​

本章属于 primitive 层。前置：无。 学完你能：用一句话讲清「为什么 Pinia 要把全部状态聚成一棵树、把全部副作用归进一个作用域，再捆进一个中央容器」——以及这么设计换来什么、付什么代价。

1. 为什么需要它 ​

上一章讲了一个底层小机制：把回调收进一个 Set，触发时遍历调用，再借 onScopeDispose 让这些订阅随所在作用域自动回收；detached 选项还能让订阅脱离组件生命周期独立存活。那章留下的直觉是——作用域是副作用的回收单元，一个作用域里的计算属性和监听可以一刀全停。

那章的作用域是用在单个订阅上的。可一个真实应用里有几十个 store，每个 store 又各自带着自己的状态、一堆计算属性、一堆监听。一旦 store 多起来，三个躲不掉的问题就浮上来：

  • 状态住在哪里？如果每个 store 自己揣着自己的状态、散落在各自的闭包里，你没法把「整个应用此刻的全部状态」一次性拍成一张快照。可服务端渲染偏偏就需要这张快照——服务端得把状态塞进 HTML 交给客户端重新接手。
  • 副作用由谁管？每个 store 的计算属性和监听都是响应式副作用。如果它们各挂各的、没有统一归属，应用卸载或测试结束时，你根本没有一个把手能把它们一起关掉。
  • 应用从哪儿拿到状态库？组件树里的代码要找它，组件树外的代码（普通函数、动作内部）也要找它，这得有个固定入口。

这三个问题各自独立都不难，难的是要一起解决，而且解法不能互相打架。Pinia 的做法很直接：造一个中央容器，把这三件事捆在同一个对象上一起办了。换句话说，没有这个容器之前，状态、副作用、入口是三盘各自为政的散沙；有了它，三盘散沙被收进同一个篮子。

2. 核心思想 ​

把分散的三样东西——状态、副作用、实例名册——聚到一个中央容器里统一托管。

这个「聚」字是全章的眼。在此之前，每个 store 像自给自足的小作坊：自己存状态、自己开监听、自己管自己。容器做的事，是把这些小作坊赖以生存的三种底层资源（状态的存放处、副作用的栖身之所、实例的名册）从 store 身上收上来，集中替它们保管；store 自己不再操心这些基础设施，只管业务逻辑。聚拢之后，三样东西各自长成一个可被整体操作的东西：状态聚成一棵树，副作用聚进一个作用域，实例聚进一张名册。后面所有的收益，都是这个「聚」动作的直接后果。

3. 心智模型 ​

容器长什么样？想象一个普通对象，上面开着四个槽位：

  • state：一棵集中状态树。它就是一个 ref，里头装着一个普通对象 {}。每个 store 会按自己的 id 为 key，把状态挂进这棵树。
  • _e：一个独立的副作用作用域。所有 store 的计算属性和监听都建在这个作用域里。
  • _s：一张 store 名册，本质是个按 id 索引的 Map，登记着已经创建出来的每个 store。
  • _a：容器所属的那个宿主应用（Vue app）的引用。

容器对象上还有一个 install 方法，这是它上岗的入口，下面会讲。

这里有个容易忽略的细节：整个容器对象会被打上「不要响应式」的标记（对应 Vue 的 markRaw）。原因在于容器里揣着宿主应用的引用，而应用对象又庞大、又反过来引用着容器。要是容器被响应式化，框架会试图把容器、连同它引用的应用、连同应用引用的一切，都深层代理一遍——一个性能黑洞，还可能绕成循环引用。贴上这个标记，等于告诉框架：「我自己不是数据源，别代理我的内部字段。」容器字段的变更因此不被响应式追踪，但这些字段基本是初始化时写一次的低频字段，谈不上损失。

容器的一生分四步：

  1. 出生：开一个脱离父级的作用域，在里面建一棵空的状态树 {}，把作用域、状态树、空名册装进容器对象。
  2. 上岗：宿主应用通过插件机制挂载容器。这一步容器把自己登记为「当前活跃实例」、记住所属应用、用 provide 把自己注入整棵组件树。
  3. 收纳：此后每个 store 被首次用到时，把自己的初始状态挂进状态树里属于自己的那个 id 桶下，分散的状态一点点聚满这棵树。
  4. 退场：销毁时停掉作用域（全部副作用瞬时失效）、清空状态树和名册。

4. 关键权衡 ​

状态聚成单棵树：换整树快照，付命名约定的代价 ​

容器最重要的一个决定，是不让每个 store 各存各的状态，而是要求所有 store 把状态交出来，挂到同一棵按 id 分桶的树上。

换来的是整棵树可以一次性序列化。服务端渲染时，服务端只要序列化这棵树，就能把整个应用此刻的状态塞进 HTML 传给客户端；客户端拿到后再灌回去，无缝接手。没有这棵集中树，你得挨个遍历每个 store 去拼这张快照，还得保证顺序和格式一致。同一个机制也让批量改状态时能对着整树做合并、让开发者工具能在一个面板里巡视全部状态。

代价是状态之间的隔离靠 id 字符串，靠的是「大家约定不重名」，而不是类型系统的强约束。两个 store 写了同一个 id，编译器不会拦你，运行时却会互相覆盖。另外这棵树的形状是「id → 状态」的扁平字典，而不是业务领域的自然结构——一个「订单」的状态和它下属的「订单项」状态，在这棵树上只是两个平级的 key，体现不出归属关系。

这里化解的本质矛盾，是「状态既要按 store 各自独立封装、又要能作为一个整体被外部一次性消费」——独立自治和整体消费天生打架。聚成一棵树，是用「放弃领域结构的自然性、改用统一字典」这个折中，把整体消费这条需求接住了。凡是要把一堆各自管理的状态块做成可整体快照、可整体传输的场景（任何 SSR 框架的状态桥接都是），都会撞上同一个矛盾，解法骨架都是「找一个统一的聚合点」。

用一个独立作用域托管全部副作用：换一键销毁，付常驻内存的代价 ​

第二个决定，是把所有 store 的计算属性和监听，统统建在容器出生时开的那个独立作用域里，而不是建在各自的组件上。

换来的是一句 stop() 就能拆掉整个应用全部 store 的副作用。测试场景下每个用例开个新容器、跑完一键销毁，互不污染；多应用场景下每个应用有自己的容器和作用域，互不干扰；应用卸载时也是一句话清场。这就是把上一章「作用域是副作用回收单元」的直觉，从单个订阅的尺度，直接放大到了整个应用的尺度。

代价是这个作用域脱离父级，不随任何组件的生命周期自动回收，必须有人显式喊停。「detached 作用域需要主动停止」这条特性上一章已经讲透，这里不重复；容器层面真正的新代价是——它成了整个应用副作用的唯一回收点，一旦没人喊停，泄漏的不是一两个订阅，而是全应用所有 store 的计算属性和监听。

背后还是上一章见过的那个矛盾：响应式副作用想随某个生命周期集体回收，又绝不能绑死在某个组件的生命周期上——真绑上去，组件一卸载就把全局 store 连带销毁了。容器层的解法是选一个不归属任何组件的独立作用域来收场，把集体回收的把手交还给应用本身。这个矛盾在别的框架根级 effect 清理、任何资源管理设计里都能认出来。

5. 最小原理演示 ​

下面的代码只演核心思想：一个中央容器如何把「独立作用域 + 集中状态树 + 名册」三件套托管起来，以及两个最实在的收益——整树可序列化、停作用域则副作用全失效。为了不引入完整运行时，这里用一个极简的 mock 扮演宿主框架的副作用作用域：它只是把「副作用」收进一个集合，停止时统一清空，恰好把「作用域＝副作用的回收单元」演透了。

ts
// mock 一个副作用作用域：收进来的 effect 用集合记下，stop 时统一清空
class MiniEffectScope {
  private effects = new Set<() => void>()
  constructor(public detached = false) {}
  run<T>(fn: () => T): T {
    return fn() // 真实运行时会在这里建立 effect 与作用域的依赖绑定
  }
  track(effect: () => void) {
    this.effects.add(effect)
  }
  stop() {
    this.effects.clear() // 一刀全停：这正是「一键销毁」的把手
  }
}

// 极简的 ref：读写一个值，供集中状态树用
function ref<T>(initial: T) {
  return { value: initial }
}

// 标记一个对象「不要响应式」——真实库里是 Vue 的 markRaw
function markRaw<T>(obj: T): T {
  return Object.assign(obj, { __skipRaw: true })
}

// 造一个中央容器：托住作用域、状态树、名册三件套
function createMiniPinia() {
  const scope = new MiniEffectScope(true)              // 脱离父级：不随组件生命周期回收
  const state = scope.run(() => ref<Record<string, any>>({}))! // 集中状态树，初始空对象
  const pinia = markRaw({
    state,                                             // 全部 store 的状态都挂到这一棵树上
    _e: scope,                                         // 所有 store 的副作用都归这个作用域管
    _s: new Map<string, any>(),                        // store 名册：按 id 登记
    install(app: any) {
      ;(globalThis as any).activePinia = pinia         // 容器一上岗就把自己设为默认实例
      app.provide(pinia)                               // 注入组件树，组件内靠注入定位容器
    },
  })
  return pinia
}

// 一个 store 被首次用到时：把初始状态挂进集中树、登记名册、把副作用归进容器作用域
function mountStore(pinia: any, id: string, initialState: any, effect?: () => void) {
  pinia.state.value[id] = initialState                 // 状态聚进同一棵树
  pinia._s.set(id, { id, state: initialState })        // 登记进名册
  if (effect) pinia._e.track(effect)                   // 副作用归进容器的统一作用域
}

const pinia = createMiniPinia()
mountStore(pinia, 'counter', { count: 0 }, () => {})
mountStore(pinia, 'user', { name: 'ada', age: 30 }, () => {})

// 收益一：整棵树可一次性序列化（服务端渲染靠的就是这一点）
console.log(JSON.stringify(pinia.state.value))
// {"counter":{"count":0},"user":{"name":"ada","age":30}}

// 收益二：停作用域，全部 store 的副作用瞬时失效
pinia._e.stop()

每个 store 不再自己存状态，而是把状态交出去挂到 pinia.state 这棵树上；副作用也不再各管各，而是登记进 pinia._e。容器什么都不算计，它只负责「聚」。

6. 执行轨迹 ​

拿一个具体输入走一遍，看容器内部的状态怎么变。

一开始 createMiniPinia() 造出容器，此时的状态树是一棵空树：state.value = {}，名册也是空的。

接着宿主应用挂载容器，走 install：容器把自己登记为默认实例，再通过 provide 把自己注入组件树。此刻组件树里的任何组件都能靠注入拿到这个容器；状态树还是空的 {}，因为还没有任何 store 被用过。

某个组件首次用到了 counter store，mountStore 把它的初始状态写进状态树的 'counter' 桶：state.value 变成 { counter: { count: 0 } }，名册里也多了一条 counter 的登记。user store 被用到时同样挂上去，状态树变成 { counter: { count: 0 }, user: { name: 'ada', age: 30 } }。

这时整棵树可以随时被序列化拍成一张快照——服务端渲染就是在这里把状态打包塞进 payload 交给客户端的。

最后销毁：调用 pinia._e.stop()，counter 和 user 两个 store 的全部计算属性和监听瞬时失效；再把 state.value 重置回 {}、清空名册。容器回到了刚出生时的空样子，所有资源干净退场。

7. 教学简化说明 ​

本章演示故意省略了几样东西：插件系统（容器还有收集和搬运插件的职责，留给后续章节）、开发者工具的自动接入、默认实例在组件外的完整寻址回退、完整的类型泛型，以及多应用隔离的边界处理。mock 出来的作用域也只演示「收进集合、统一清空」这一层语义，省略了真实运行时里 effect 与作用域的依赖追踪细节。这些裁剪都是为了把「聚到一个容器里统一托管」这一个核心思想讲透。

8. 小结 ​

这一章只造了容器本身。后面所有的花样——懒装配、双管道、插件、开发者工具、服务端渲染——本质都是往这个容器里装东西，或者从这棵状态树上取东西；离开了这个聚合点，它们都无处落地。

但容器上岗时做了一个留下尾巴的决定：它靠 provide 把自己注入组件树，组件内的代码靠注入就能找到它。可动作、普通函数这些跑在组件树之外的代码，手里并没有注入上下文，注入这条路对它们是断的。下一章就接着这个口子讲——怎么在任意上下文里都能找回这个容器。
