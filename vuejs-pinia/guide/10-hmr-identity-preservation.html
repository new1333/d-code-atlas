热更新与 Store 身份保持 ​

本章属于 system 层。前置：「defineStore 的懒装配与循环引用破解」「Setup Store 的运行时自动分流」。 学完你能：用一句话讲清「热更新时为什么不 new 一个新 store、而是原地改写旧 store，以及这套身份保持换来了什么、付出了什么」。

1. 为什么需要它 ​

上一章讲了插件如何在每个 store 建好时挂载扩展。那是在「store 一次创建、长期不变」的视角下说话。可一旦进入开发，store 哪里会建一次就定型：你会反复改它的状态、动作、计算属性，保存，再看效果。这就引出了热更新（HMR）要管的那件事。

在 Vite 这类带热更新的构建工具里，改一个普通模块，工具会悄悄换掉那个模块，让页面局部生效、不刷新整页。可 store 不是普通模块。组件在渲染时拿到 store 的引用，并长期攥在手里（一句 const store = useCounter() 就是攥住了一个对象地址）。如果热更新像换普通模块那样，直接换成一个全新的 store 对象，所有攥着旧引用的组件都还看着旧对象、用不上新逻辑；要让它们用上新逻辑，就得把这些组件全部卸载重挂。这一重挂，组件自己持有的本地状态、滚动位置、输入焦点全没了。一次保存触发一次小刷新，开发的反馈循环就这么被拖慢。

理想很直接：改完即时生效、组件无感、已经改过的状态值原样保留。可「换定义」和「保持引用」天生打架——任何「换」都想换掉对象，任何「保持」都想留住对象。

Pinia 解这道题的底子，前两章已经埋好。第 4 章讲过 store 是懒创建、首次调用才登记进注册表；第 5 章讲过 setup 返回的成员会被自动分成状态、计算属性、动作三类。热更新正是踩在这两块底子上：靠注册表里那个已存在的旧实例来认人，靠成员分类时顺手记下的一份清单来知道「该搬谁、该删谁」。这两套机制本章只看它们的新侧面，不重复展开。

2. 核心思想 ​

Pinia 的办法是：旧壳留着，只换里面的零件。说得更准一点，它把「换定义」这件事，从「换一个对象」降级成「换这个对象身上的几个字段」。对象还是那个对象，地址没变，攥着它的组件根本察觉不到换过；但对象身上的某个动作已经是新实现、某个计算属性是新增的、某个被删的动作已经不见了。

「引用不变」是整套机制的命门。下面所有花样——找回容器、建影子、嫁接、迁移、静音——全是在履行这条契约：你可以改 store 的内容，但绝不能换 store 这个人。

3. 心智模型 ​

先认得几个关键角色：

  • 注册表：容器里那张「id → store 实例」的表。旧实例就是身份锚点，热更新时「认人」全靠它。
  • 迁移清单：建店时顺手记下的一份名册，分三栏——哪些是状态、哪些是动作、哪些是计算属性，外加一个临时状态桶。热更新就是对着新旧两份清单做比对。
  • 影子实例：热更新过程中临时建出来的「新定义样品」，用一个加了 __hot: 前缀的假 id 标记，嫁接完就销毁。

整个流程走下来是这样一条线：

A. 开发者保存文件，构建工具热替换该模块，把新模块的全部导出交给一个热更回调。 B. 回调先找回容器：优先从构建工具跨次热更持久化的数据槽里读，读不到就回退到建店工厂身上记录的一个指针（首次建店时写下）。找回后立刻写回数据槽，保证连续多次保存都拿到同一个容器。 C. 回调遍历新模块的导出，挑出「是建店工厂，且它的 id 在注册表里已经存在」的那些。只热更真正被用过的 store，从没被用过的直接跳过。 D. 命门：拿到注册表里的旧实例，把它当作一个特殊的「热参数」传给新工厂去调用，也就是 useStore(pinia, 旧实例)。 E. 新工厂发现这个 id 已经存在，便不再重建真 store，而是用一个假 id 走一遍完整的建店流水线，产出一个影子实例。影子的状态被隔离进临时桶，不污染真的集中状态树。 F. 在旧实例上触发热更新：对着影子的清单，逐个搬状态、重包动作、替换计算属性、删掉失效成员；搬的过程中把集中状态树里这个 store 的槽位重新指向新状态，并且全程静音，不让订阅把这次「换底」误报成一次普通变更。 G. 收尾：把影子的临时痕迹从注册表和集中状态树里删干净，免得泄漏。旧实例的引用从头到尾没换过。

4. 关键权衡 ​

换内容，不换对象 ​

第一条也是最根本的一条：Pinia 选择不 new 一个新 store，而是保持旧对象身份、把新定义的成员原地迁移进去。换来的是组件无需重新挂载——订阅关系、已经修改过的状态值都自然延续下去，useCounter() === 旧引用 在热更新前后严格成立。

代价是，这套「原地迁移」不是免费的，得专门写一套成员级的迁移逻辑。热更新要遍历新清单的每一个状态键，逐个决定是搬运还是合并；遍历每一个动作，重新包裹一遍，好让动作订阅仍能追踪到它；遍历每一个计算属性，重新装上；最后还得把旧清单和新清单做一遍 diff，专门清理那些「旧有、新无」的失效成员。

这套迁移逻辑里还有个挺现实的岔路：状态搬运不能一刀切。声明式风格（Options）的 state 形状是预先写死的，遇到嵌套对象可以递归合并，把用户已经改过的旧数据小心翼翼地合并进新形状里，保住每一层嵌套。可命令式风格（Setup）的状态是一堆散装的 ref，属性在运行时还能增增减减，这时候递归合并反而会把运行时新加的键弄丢，所以只能整个替换。为两种风格各写一套合并策略，就是「换内容不换对象」这条选择带来的真实维护成本。

这条权衡化解的本质矛盾，是「换定义」和「保持引用」这对天生的死对头。任何框架只要想在开发期做到「改了即时生效、状态不丢」，都得面对它。React 的 Fast Refresh 在组件层面解的就是同一道题。抓住这条本质矛盾，你就能在任何一个带热更新的状态方案里，认出这套「保持身份、原地迁移」的骨架。

先搭影子，再拆零件嫁接 ​

第二条是上一条得以实现的巧妙手法。原地迁移需要「按新定义生成出来的那一套成员」，可这套「生成成员」的逻辑，建店流水线里早就写好了一遍——就是第 5 章那个把 setup 返回值自动分流的引擎。在热更新里重写一遍，既冗余又容易和原逻辑走偏。

换个说法：与其复制一条生产线，不如复用原来的生产线。Pinia 的做法是，新工厂发现这个 id 已存在，就用一个加了 __hot: 前缀的假 id，原封不动地走一遍完整建店流水线。Options 和 Setup 两种风格各走各的分类路径，热更新这边一行分类代码都不用重写。产出的这个影子实例带着全新的成员，随即把这些成员拆下来，嫁接到旧 store 身上（也就是上一条权衡讲的那个原地迁移），嫁接完再把影子从注册表和集中状态树里删掉。

打个比方，这就像先在隔壁搭一个装好全套新家具的样板间，再一件件搬进老房子——老房子的地址没变，住户不用动，但屋里已是新配置。换来的是对整套建店流水线的完整复用：分类、包裹、装计算属性，全是现成的。代价是出现短暂的「双实例」，旧 store 和影子同时在内存里待一小会儿，影子还在注册表和集中状态树里留了两条临时痕迹，必须事后清理，否则就是泄漏。这条权衡化解的本质矛盾，是「我需要新定义产生的零件」和「我不想重写产生零件的流水线」——用「造个样品再嫁接」的方式，让「换内容」复用「造内容」的同一台机器。这个骨架在工厂模式、原型模式里都能见到同构的身影。

5. 最小原理演示 ​

下面这段极简骨架，只演示「保持对象身份」和「建影子再嫁接」这两条核心。插件链、订阅静音、Options 与 Setup 双分支、真实的模块系统全部省略，用一个普通函数调用模拟「这是新模块导出的工厂」。

ts
// 热更新与 Store 身份保持 —— 最小原理演示
// 只演「保持对象身份」+「建影子再嫁接」；省略订阅、静音、Options 分支、真实模块系统

let activePinia: any

function createPinia() {
  const pinia = { _s: new Map<string, any>() } // 注册表：id -> store 实例（身份锚点）
  activePinia = pinia
  return pinia
}

// 建店工厂：返回 useStore；首次调用才真正建店并登记
function defineStore(id: string, setup: () => Record<string, any>) {
  function useStore(pinia = activePinia, hot?: any) {
    // 首次使用：跑 setup 建店，登记身份，装上热更新入口
    if (!pinia._s.has(id)) {
      const store = setup()
      store._hotUpdate = makeHotUpdate(store)
      pinia._s.set(id, store)
    }
    // 无论冷热，都从注册表拿这同一个旧实例（身份钉死在这里）
    const store = pinia._s.get(id)!

    if (hot) {
      // 命门所在：用同一条 setup 再跑一遍，产出全新零件的影子，再嫁接到旧 store
      const shadow = setup()   // 影子：复用建店流水线产出的「新定义样品」
      store._hotUpdate(shadow) // 把影子的零件原地搬上旧 store，对象引用不变
    }
    return store
  }
  useStore.$id = id
  return useStore
}

// 旧 store 身上的热更新：逐个迁移成员、删掉失效成员，全程不换对象
function makeHotUpdate(store: any) {
  return (incoming: any) => {
    for (const key in incoming) {
      if (typeof incoming[key] === 'function') {
        store[key] = incoming[key]      // 动作：换成新实现
      } else if (!(key in store)) {
        store[key] = incoming[key]      // 新增的状态：补上
      }
      // 已存在的状态：什么都不做，用户改过的旧值原样保留
    }
    // 旧有、新无的成员：原地删除（内部成员以 _ / $ 开头，不参与迁移）
    for (const key in store) {
      if (key.startsWith('_') || key.startsWith('$')) continue
      if (!(key in incoming)) delete store[key]
    }
  }
}

// 热更新入口：构建工具热替换模块时，回调拿到「新模块导出的工厂」
function acceptHMRUpdate(useStore: any) {
  return (newModule: any) => {
    for (const name in newModule) {
      const candidate = newModule[name]
      // 只热更「是工厂 且 注册表里已存在」的 store；没被用过的不管
      if (typeof candidate === 'function' && candidate.$id
          && activePinia._s.has(candidate.$id)) {
        const old = activePinia._s.get(candidate.$id)
        candidate(activePinia, old) // 命门：旧实例作热参数，去调新工厂
      }
    }
  }
}

再接一段场景，把计数器 store 改一次，看身份与状态如何保持：

ts
// ---- 场景：改一个计数器 store，看身份与状态如何保持 ----
createPinia()

// v1：初始定义 —— 状态 count、动作 increment
const useCounter = defineStore('counter', () => ({
  count: 0,
  increment() { this.count++ },
}))

const R = useCounter() // 某组件在渲染期拿到，并长期持有引用 R
R.increment(); R.increment(); R.increment(); R.increment(); R.increment()
// 此时 R.count === 5

// 保存文件：开发者把 increment 改名 bump、新增 doubled、保留 count
// 「新模块导出的工厂」—— 同 id、新 setup
const useCounterV2 = defineStore('counter', () => ({
  count: 0,
  doubled() { return this.count * 2 },
  bump() { this.count++ },
}))

// 触发热更新（真实场景由构建工具的 import.meta.hot 回调发起）
acceptHMRUpdate(useCounter)({ default: useCounterV2 })

// ---- 四条断言演透「保持身份」----
console.assert(R === useCounter(), '① 身份保持：旧引用仍是当前 store')
console.assert(R.count === 5, '② 状态保留：用户已改的 count 原样留下')
console.assert(R.doubled() === 10, '③ 新成员生效：doubled 已嫁接进来')
R.bump()
console.assert(R.count === 6 && !('increment' in R), '④ 新动作可用、旧动作已删')
console.log('断言全部通过 —— 热更新全程零组件重挂载')

四条断言把本章的灵魂演透了：① 是命门，热更新前后 R === useCounter() 严格相等，组件攥着的引用始终有效；② 是状态延续，用户已经改到 5 的 count 没被新定义里的默认值 0 冲掉；③④ 是原地改写，新动作 bump、新成员 doubled 已经长在旧对象身上，被删的 increment 已不复存在。全程没有任何组件被卸载重挂。

6. 执行轨迹 ​

拿上面那个计数器场景，放慢动作走一遍，看每一步数据长什么样。

起步时，注册表是 { counter → R }，R = { count: 5, increment, _hotUpdate }，某组件攥着 R。

保存文件后，热更回调拿到新模块 { default: useCounterV2 }。回调找回容器 activePinia，遍历导出：useCounterV2 是函数、它的 $id 是 'counter'、注册表里有 counter，命中。id 没变（新旧都叫 counter），取出旧实例 R。

接着是命门那一行：useCounterV2(activePinia, R)。进入新工厂后，注册表里已经有 counter，跳过创建环节；hot 参数是 R，为真，于是走热分支。用假 id __hot:counter 跑一遍 setup，得到影子 { count: 0, doubled, bump }（真源里影子的状态会被隔离进临时桶，不碰真的集中状态树）。随后 R._hotUpdate(影子) 在 R 上原地迁移：

  • count：已存在且不是函数，跳过。旧值 5 留下。
  • doubled：是函数，R.doubled = 影子.doubled，新增。
  • bump：是函数，R.bump = 影子.bump，新增。
  • 删除循环：increment 不在影子里，删掉；_hotUpdate 以 _ 开头，跳过。
  • 真源在这一步还会把集中状态树里 counter 的槽位重新指向影子的状态桶，并关掉订阅监听做静音，换完再恢复。演示为了聚焦身份保持，省略了这一段。

收尾，R 变成 { count: 5, doubled, bump, _hotUpdate }，引用未变。真源还会把影子从注册表和集中状态树里删掉，演示因为没把影子登记进表，省了这一步。

回到组件那边：它攥的 R 还是原来那个地址，但 R.bump 已经是新动作、R.doubled() 能算出 10、R.increment 没了。整个过程没有组件被重挂。

7. 教学简化说明 ​

本章演示故意省略了几样东西：插件链如何参与热更新、订阅管道的真实静音实现（关掉监听开关、用 nextTick 延迟恢复）、Options 与 Setup 两种风格的状态合并差异（演示只演扁平成员，相当于 Setup 风格的整替）、真实的 Vite/webpack 模块系统与 import.meta.hot 的数据槽持久化、id 被改写时退化为整页刷新的分支，以及生产构建下整套热更新逻辑被开发环境守卫整块裁除。另外，演示里的 store 是普通对象，只演示身份保持，不演示响应式的依赖追踪。

8. 小结 ​

热更新的本质，是把「换定义」降成「换对象身上的字段」。对象还是那个对象，开发迭代却能飞快推进。它把开发期的速度，建在了运行时身份的不变性上——身份不变是契约，原地迁移是履行契约的手段。顺带留下的那个「热更新进行中」标志，以及这套身份保持机制本身，恰好是下一章「开发者工具的可观测性接入」要观察的对象。
