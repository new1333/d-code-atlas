## 修复 GitHub Pages 样式 404 问题

### 问题根因（已通过浏览器验证确认）
- GitHub Pages 实际部署在 `https://new1333.github.io/d-code-atlas/<key>/`（项目级 Pages，子路径 = 仓库名）。
- 但 `scripts/publish-sites.mjs` 注入的 VitePress `base` 是 `/${key}/`，导致产物内所有资源路径（CSS/JS/字体/内部链接）变成 `/pinia_v2/assets/...`。
- 浏览器将其解析为 `https://new1333.github.io/pinia_v2/assets/...` → **404**，页面无样式（已实测：`/pinia_v2/assets/style.B5z3LJQ_.css` 返回 GitHub 404 页，而 `/d-code-atlas/pinia_v2/assets/style.B5z3LJQ_.css` 返回真实 CSS）。
- 聚合页 `index.html` 用相对链接 `${key}/`，在 `/d-code-atlas/` 下正确，无需改。

### 修复方案

**修改 `scripts/publish-sites.mjs` 的 `injectBase`：base 前缀按以下优先级推导**
1. `ATLAS_PAGES_BASE` 环境变量（显式覆盖，为未来自定义域名留口子，需以 `/` 开头和结尾）；
2. `GITHUB_REPOSITORY` 环境变量取 `owner/repo` 的 repo 部分（CI 环境）；
3. 从 `git remote get-url origin` 解析仓库名（本地 fallback）。

最终注入 `base: "/<repoName>/<key>/"`。

**同步更新工作流 `.github/workflows/deploy-sites.yml`**：在 Build 步骤前补一行注释说明 base 推导依赖 `GITHUB_REPOSITORY`（CI 天然提供，无需额外配置）。

**更新脚本顶部注释**，说明 base 含仓库名前缀的原因。

### 验证步骤（"直到部署正常、页面正常、样式正常"）
1. **本地构建核验**：运行修正后的 `bun scripts/publish-sites.mjs`，检查 `dist-sites/pinia_v2/index.html` 头部资源路径是否为 `/d-code-atlas/pinia_v2/assets/...`（而非 `/pinia_v2/...`），并确认 config.ts 被正确还原。
2. **类型检查**：`bunx tsc --noEmit`（脚本是 `.mjs`，主要确保引擎源码未被波及）。
3. **提交 + 推送到 dev 分支**：遵循 Conventional Commits，`fix(publish): base 注入仓库名前缀，修复 GitHub Pages 子路径部署样式 404`。
4. **触发 CI**：`workflow_dispatch` 触发 Deploy Atlas Sites（或等 push 触发）。
5. **线上浏览器验证**：用浏览器打开线上 `pinia_v2` 页面，截图确认样式/字体加载正常，导航链接可点击跳转，聚合页入口正常。

### 涉及文件
- `scripts/publish-sites.mjs`（核心修改）
- `.github/workflows/deploy-sites.yml`（注释说明，可选）
- 不改动任何 `config.ts`（注入仍在构建期临时进行并还原）

### 回归风险
- 低。改动仅影响 CI/本地发布脚本的 base 注入逻辑，不触及引擎源码（`src/`）与已入库的 `atlas/*/site` 配置。
- `config.ts` 的还原逻辑不变，本地源只读原则（AC-2）保持。
